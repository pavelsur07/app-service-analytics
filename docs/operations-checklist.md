# Операционный чек-лист

Не архитектурные решения, а обязательные к выполнению вещи.
Список короткий намеренно: всё, что здесь есть, отделяет
«работает у меня» от «работает у клиентов».

## Перед заведением первого администратора сервиса

Порядок обязателен и именно в этом направлении: ограничение по адресам
ставится **до** того, как в проде появится учётная запись, которой можно
войти. Пока таблица `administrator` пуста, вход не пускает никого — это
и есть окно, в котором ограничение надо успеть поставить.

Причина в ADR-017: второй фактор (TOTP) отложен вопреки требованию
ADR-007 «с первого дня», и ограничение по адресам — единственное, что
это отступление закрывает. Администратор видит финансы всех клиентов.

- [x] **Ограничение по адресам на `admin.conwix.com`.** Middleware
      `ipAllowList` на роутере `admin` в `traefik/dynamic.prod.yml`,
      не в nginx: за Traefik `$remote_addr` в nginx — адрес самого
      Traefik. Поставлено 2026-08-29: корпоративный VPN
      (`72.56.81.118/32`, `72.56.28.86/32`) — и больше никто. Список
      ведётся в репозитории — там же его и менять.

      **Правится файл в репозитории, а не копия на сервере.** Выкладка
      делает `rsync traefik/dynamic.prod.yml` на `/opt/conwix/traefik/`
      (`.github/workflows/ci.yml`, шаг «топология и статика на сервер»),
      поэтому правка руками на сервере проживёт до ближайшего деплоя
      и исчезнет молча — контур снова откроется всему интернету,
      и никто об этом не узнает.

      Конвейер к этому уже готов: админская smoke-проверка выкладки
      ходит не с раннера, а с самого сервера (адрес раннера заранее
      неизвестен и в список не попадёт), поэтому включение списка
      её не ломает и трогать её не нужно.
- [x] **Адрес машины разработки убран** 2026-08-29 — раньше, чем
      требовалось (пункт был привязан к появлению TOTP). Пока второго
      фактора нет, этот список и есть весь периметр админки, и лишних
      адресов в нём быть не должно. Следствие: проверить поведение
      админки снаружи с машины разработки больше нельзя — только
      с VPN либо запросом в nginx с самого сервера.
- [x] Проверено с адреса вне списка: `admin.conwix.com` отвечает
      403, а `app.conwix.com` продолжает работать. Проверка обязательна —
      ошибка в маске тихо открывает контур всем.
- [x] Проверено с адреса из списка: админка открывается. Перепроверено
      владельцем с VPN 2026-08-29 **после** сужения списка — до сужения
      проверка шла с машины разработки, и её одной было бы мало:

- [ ] **Удалить `/root/conwix-superadmin-password`** — сразу, как пароль

## Перед открытием самостоятельной регистрации

- [ ] В GitHub repository variables задан публичный
      `SMARTCAPTCHA_CLIENT_KEY`; не secret и не server key. CI передаёт его
      браузерной сборке как `VITE_SMARTCAPTCHA_CLIENT_KEY`. Не печатать даже
      публичное значение в logs/artifacts без необходимости; проверить можно
      по имени переменной. Пустое или не соответствующее `ysc1_...` значение
      обязано оборвать production build fail-fast, а не выпустить форму без
      работающей проверки.
- [ ] `MAILER_DSN` и `MAILER_FROM` заданы в `/opt/conwix/.env`, а письмо
      подтверждения фактически дошло до внешнего ящика. Письмо регистрации
      отправляется синхронно, чтобы открытый токен не попадал в PostgreSQL;
      при отказе SMTP запрос вернёт ошибку, а новую ссылку выпускает endpoint
      повторной отправки. Одна лишь запись в логах не подтверждает доставку.
      Ссылка несёт bearer token только во fragment
      `/confirm-email#token=...`, не в query: fragment не отправляется nginx,
      а frontend стирает его до первого React render. Query-вариант считается
      недействительной ссылкой.
- [ ] Для домена `MAILER_FROM` проверены SPF и DKIM; письмо подтверждения не
      попадает в спам. Для клиента письмо в спаме неотличимо от неотправленного.
- [ ] `SELLER_APP_ORIGIN=https://app.conwix.com`, а
      `REGISTRATION_DOCUMENTS_VERSION` совпадает с опубликованной версией
      пользовательского соглашения и политики обработки персональных данных.
      Версию задаёт deployment job из `.github/workflows/ci.yml`, атомарно
      обновляя только эту строку в `/opt/conwix/.env`; клиент не может
      подменить её в запросе. При смене документов сначала меняется значение
      в workflow и проходит review, затем публикуются согласованные тексты.
- [ ] До merge все три юридические страницы доступны по точным URL:
      `https://conwix.com/privacy.html`, `https://conwix.com/oferta.html` и
      `https://conwix.com/personal-data.html`. Проверить успешный HTTP-ответ
      каждой страницы, а не только наличие ссылок в форме:

      ```bash
      curl --fail --silent --show-error --location --output /dev/null https://conwix.com/privacy.html
      curl --fail --silent --show-error --location --output /dev/null https://conwix.com/oferta.html
      curl --fail --silent --show-error --location --output /dev/null https://conwix.com/personal-data.html
      ```
- [ ] **Блокер публичного открытия:** юридические страницы сейчас загружают
      Google Fonts, одновременно текст политики отрицает трансграничную
      передачу. До открытия регистрации убрать внешнюю загрузку либо отдельно
      согласовать политику с фактической передачей; зелёная сборка этот
      юридический блокер не снимает.
- [ ] Реальный `SMARTCAPTCHA_SERVER_KEY` получен по защищённому каналу и
      записан только в `/opt/conwix/.env` с правами, доступными оператору;
      не раскрывать его ни в чате, ни в аргументах команд, ни в GitHub
      logs/artifacts, ни в репозитории. До merge и deploy проверить лишь
      наличие непустой строки, не печатая файл или значение:

      ```bash
      : "${PRODUCTION_SSH_TARGET:?задайте SSH target production-сервера}"
      ssh "$PRODUCTION_SSH_TARGET" 'set -eu
        test -f /opt/conwix/.env
        awk '\''BEGIN { found=0 }
             /^SMARTCAPTCHA_SERVER_KEY=.+$/ { found=1 }
             END { exit(found ? 0 : 1) }'\'' /opt/conwix/.env'
      ```

      Ненулевой код останавливает merge/deploy до безопасного добавления
      реального ключа владельцем. Фиктивный ключ в production недопустим;
      Compose требует секрет до смены контейнеров и передаёт его только `api`.
      Эта проверка доказывает только наличие, не корректность пары ключей:
      неверный или отозванный server key блокирует открытие формы и rollout
      Stage 3 до успешного live smoke ниже.
- [ ] После deploy проверить ответы защиты регистрации. `429` с
      `Retry-After` означает исчерпанный email- или IP-лимит; не повторять
      запрос раньше указанного срока и не считать это отказом Yandex.
      `503 captcha_unavailable` с `Retry-After: 30` — fail-closed: новая
      регистрация не создаёт компанию, пользователя, audit или письмо, но
      вход и работа существующих клиентов продолжаются.
- [ ] Для каждого `503 captcha_unavailable` в журнале есть один
      `warning`: `SmartCaptcha verification unavailable` с категорией
      причины и, если получен, HTTP-статус провайдера либо
      `Registration protection unavailable` для отсутствующего client IP.
      Запись обязана оставаться sanitized: без server key, CAPTCHA-токена,
      тела/сообщения Yandex, email и IP. Обычный `422 captcha_invalid`
      предупреждения не создаёт.
- [ ] `SELLER_APP_ORIGIN` задаёт единственный ожидаемый SmartCaptcha
      `host[:port]`. Ответ `status=ok` без `host`, с пустым или отличающимся
      host обязан дать sanitized `503 captcha_unavailable`; внешний host и
      поле `message` Yandex не попадают в журнал.
- [ ] При необходимости отката сначала вернуть предыдущий image tag и
      убедиться, что `api` здоров, вход работает и текущий тег ожидаемый;
      затем откатить Compose вместе с веткой релиза. Только после работающего
      отката можно удалить `SMARTCAPTCHA_SERVER_KEY` из окружения: удаление
      раньше заблокирует разбор текущего Compose и перезапуск сервисов.
      Миграций и необратимых изменений данных в Stage 2 нет.
- [ ] Живой успешный smoke (`status=ok`) **выполняется после реализации
      Stage 3, но до публичного открытия браузерной формы**: только
      frontend-виджет сможет получить настоящий одноразовый CAPTCHA-токен.
      Пройти регистрацию через production-виджет и тем самым проверить
      реальную пару client/server keys и точное совпадение ожидаемого
      `host[:port]` из `SELLER_APP_ORIGIN`. Неверный/отозванный ключ, чужой
      host или любой другой неуспех блокирует rollout и открытие формы;
      `message` Yandex не использовать для ветвления и не логировать. До
      Stage 3 не подделывать токен и не считать `422` проверкой успешной
      связки ключей.
- [ ] После deploy пройти `/sign-up` через production-виджет с новым внешним
      почтовым ящиком/алиасом, которым управляет оператор: получить письмо,
      проверить отсутствие `?token=` и наличие `#token=` в ссылке, открыть её,
      убедиться, что fragment исчез из адресной строки до POST, затем проверить
      открытую сессию и защищённый `/onboarding`.
      Это реальная mailbox smoke-проверка доставки, пары client/server keys и
      host; лог или synthetic token её не заменяют. При проблеме виджета,
      ключей, host или доставки не объявлять регистрацию открытой: откатить
      frontend static artifact на предыдущий run, не меняя backend и данные.

## До первого платящего клиента

- [ ] **Резервное копирование PostgreSQL с восстановлением на момент времени.**
      Настроить — половина дела. Обязательно **развернуть копию и убедиться,
      что данные на месте**. Непроверенная копия резервной копией не является.
- [ ] Расписание копий и срок хранения зафиксированы письменно.
- [ ] Raw-слой входит в периметр копирования: это единственный источник
      истины при пересчётах.
- [ ] Мастер-ключ шифрования учётных данных — в секретах окружения,
      отдельно от репозитория и от дампов базы. Проверить, что он
      не попадает в резервные копии базы в открытом виде.
- [ ] **Приватный ключ расширения сохранён вне машины разработчика.**
      Лежит в `~/.secrets/conwix-extension.pem` (режим 600), в репозитории
      его нет и быть не должно — там только публичная часть. Нужен,
      чтобы собрать самоподписанный CRX с тем же идентификатором;
      потеря означает, что расширение с прежним ID больше не собрать,
      и всем, у кого оно установлено распакованным, придётся ставить
      заново. После публикации в сторе подписывает стор, но до неё
      единственная копия ключа — эта.
- [ ] Трекер ошибок подключён и получает исключения из воркеров,
      а не только из веб-процесса.
- [x] У контейнеров, ходящих наружу, два независимых DNS-резолвера
      (`x-egress-dns` в `docker-compose.prod.yml`). Резолверы хостера
      15 августа 2026 перемежающимися отказами съели 36 синхронизаций
      за шесть часов, а днём раньше — девять дней добора расходов.
      Признак в failed-очереди: `Could not resolve host`.
- [x] Сообщение, исчерпавшее ретраи, сохраняется, а не удаляется
      (`failure_transport` в `config/packages/messenger.yaml`). Смотреть
      и переотправлять:

      make api-console CMD="messenger:failed:show"
      make api-console CMD="messenger:failed:retry"

      Ретраи растянуты примерно на полчаса (30 секунд, множитель 3,
      потолок 10 минут). Умолчание — семь секунд на три попытки — для
      площадки, отвечающей ошибкой минуту, означает одну попытку,
      повторённую трижды подряд.
- [ ] **Журнал живёт только до следующей выкладки.** Записи идут
      в stderr, то есть в журнал контейнера; `docker compose up -d`
      с новым образом пересоздаёт контейнер, и всё, что он написал,
      исчезает вместе с ним. Обещание CLAUDE.md «обращение "не сходится
      за 15 июля" превращается в один запрос по логам» выполняется
      только внутри одной выкладки. Сборщик логов или том с ротацией —
      отдельная работа, см. «Отложено сознательно».
- [x] Оповещение о свежести данных: письмо, если по активной выгрузке
      дольше 36 часов не появлялось новых raw-документов
      (`worker-freshness`, `app:ingestion:check-data-freshness`).
      По выгрузке, а не по подключению: продажи и расходы встают порознь,
      и вставшие расходы при живых продажах — рабочий экран с завышенной
      маржой, а не пустой. Каталог не отслеживается намеренно.
      Меряется raw-слоем, а не фактами: у продавца бывает день без единого
      заказа, и «нет новых фактов» назвало бы исправную синхронизацию
      сломанной. Порог не «сутки»: на тихом подключении raw-документ
      появляется примерно раз в сутки (ADR-006, дедуп по body_hash),
      и ровно суточный порог давал бы ложные тревоги от смещения тика.
- [ ] **SMTP и адреса оповещений заданы на проде**: `MAILER_DSN`,
      `MAILER_FROM` и `ALERT_EMAIL` в `/opt/conwix/.env`. `MAILER_FROM` —
      ящик из учётных данных SMTP, не любой адрес: провайдер отклонит
      письмо с чужого домена, и оповещение не уйдёт ни разу. Пока их нет, `worker-freshness`
      падает на первом тике и уходит в перезапуск, а шаг «все сервисы
      здоровы» красит выкладку. Это намеренно: сторож, молчащий из-за
      ненастроенной почты, неотличим от сторожа, которому не о чем
      доложить, — и тогда весь пункт выше существует только на бумаге.
- [ ] Оповещение о недоступности приложения.
- [ ] Staging: копия схемы с боевыми данными для прогона миграций.
- [ ] Воркеры под менеджером процессов, с перезапуском при каждом релизе

## Раз в релиз

- [ ] Миграция прогнана на копии боевых данных.
- [ ] Миграция прочитана человеком.
- [ ] Воркеры перезапущены после выкладки.
- [ ] Включён новый коннектор — история за прошедшие дни добрана вручную.
      Планировщик тянет узкое окно и только вперёд, поэтому дни до выкладки
      не появятся сами никогда, а экран покажет их как посчитанные.
      Для расходов Ozon:

      make api-console CMD="app:ingestion:backfill-ozon-expenses <companyId> <accountId> <from> <to>"

      Диапазон берётся по первому дню, за который уже есть продажи:
      добирать глубже незачем — сверять расход будет не с чем.

      **Добор проверяется, а не считается выполненным.** Площадка
      отвечает ошибкой время от времени, и один день из десяти доезжает
      не с первого раза. Считать дни, а не сообщения:

      select report_type, min(period), max(period), count(distinct period)
      from marketplace_raw_document group by report_type;

      Дни расходов обязаны совпасть с днями продаж. Не совпали —
      недостающие ставятся повторно, это безопасно (загрузка идемпотентна).

## Расширение браузера — откуда брать сборку

Расширение не выкладывается конвейером: оно живёт в браузере продавца,
а не на сервере, и ставится вручную через `chrome://extensions`.

Собранный пакет приезжает артефактом задачи `frontend` — на странице
прогона в GitHub Actions, имя `extension-<номер прогона>`. Скачать,
распаковать, «Загрузить распакованное расширение» → папка `dist`.

Собирать локально и тащить с машины сборки по SSH больше не нужно.
Сборка в артефакте всегда production: смотрит на `app.conwix.com`,
локальных доменов в манифесте нет по построению.

## Расширение браузера — перед каждой публикацией

Отдельный раздел, потому что здесь конвейер не помогает: сборка бывает
зелёной у расширения, которое не выполняется вовсе. Три дефекта пакета 4
нашлись открытой карточкой в браузере — ни CI, ни оба внешних ревьюера
их не увидели. Проверять руками, на **свежем профиле Chrome**: в рабочем
профиле лежит старое подключение и прогретый кэш, и они прячут ровно те
отказы, которые ловит клиент.

- [ ] Консоль вкладки маркетплейса **без наших ошибок**. Первое, что
      смотреть, — `SyntaxError` в `content/*.js`: content-script MV3
      грузится обычным скриптом, и любой `import` в нём означает, что
      скрипт не выполнился ни разу. Сборка при этом зелёная.
- [ ] Консоль **без ошибок гидратации** с упоминанием наших узлов.
      Карточка приходит с сервера отрисованной; узел, вставленный до
      гидратации, ломает страницу маркетплейса. Это хуже, чем отсутствие
      панели: мы портим чужой сайт.
- [ ] Сеть идёт из service worker, не из content-script. Признак
      нарушения — `blocked by CORS policy` в консоли вкладки.
- [ ] Панель появилась на карточке своего товара и цифры совпадают
      с теми, что показывает приложение по тому же артикулу.
- [ ] Панель исчезла и появилась заново при переходе на соседний товар
      без перезагрузки страницы.
- [ ] Панель читается на тёмной теме маркетплейса.
- [ ] Якорь не найден → предупреждение в консоли. Проверять именно
      наличие сигнала: молчащая панель неотличима от «нет продаж».
- [ ] **Первый снимок приходит сразу после включения.** Нажать
      «Отслеживать цену» и открыть экран «Цены и соинвест»: цена и
      соинвест обязаны появиться в течение секунд, а не со следующим
      обходом. Ждать полчаса, чтобы понять, работает ли фича, —
      это и есть тот отказ, который неотличим от сломанного сбора.
- [ ] **Кнопка отслеживания показывает настоящее состояние, а не
      желаемое.** Включить, перезагрузить карточку — кнопка обязана
      остаться в положении «Не отслеживать». Проверять именно
      перезагрузкой: состояние приходит с сервера, и ошибка здесь
      выглядит как работающая кнопка, которая ничего не сохранила.
- [ ] Отказ сервера виден продавцу текстом. Проверяется дешевле всего
      на потолке: включить пятьдесят первый артикул и убедиться, что
      под кнопкой написано, почему нельзя, а не «не удалось».
- [ ] Кнопка вернулась в прежнее положение, когда сервер недоступен.
      Выключить сеть, нажать — переключиться она не должна.
- [ ] **Фоновые окна не мешают работать.** Включить отслеживание пары
      артикулов и оставить браузер на час. Окна обязаны появляться
      свёрнутыми, не перехватывать фокус и закрываться сами. Всплывшее
      поверх работы окно — отказ: продавец выключит расширение
      в тот же день, и никакая история цен этого не окупит.
- [ ] Визиты размазаны, а не идут пачкой. Смотреть по `changed_at`
      соседних наблюдений: при N артикулах шаг обязан быть около
      30 мин / N, а не «всё в одну минуту раз в полчаса».
- [ ] Наблюдения не дублируются. Повтор одного и того же момента
      отсекает база, но два окна на один артикул за цикл означают
      сломанный обход:

      select marketplace_sku, count(*), min(observed_at), max(observed_at)
      from price_observation
      where observed_at > now() - interval '2 hours'
      group by marketplace_sku;

- [ ] **Витринная цена прочитана, а не пропущена.** В консоли фонового
      окна не должно быть `витринная цена не прочитана`. Это единственный
      признак того, что Ozon перестал публиковать разметку schema.org:
      наблюдений просто не будет, и снаружи это неотличимо от «расширение
      не запускалось».
- [ ] Разрешений в манифесте по-прежнему два — `storage` и `alarms`.
      Управление окнами их не требует; появившийся `tabs` означает,
      что кто-то полез читать чужие вкладки.
- [ ] Манифест боевой сборки: локальных доменов нет, разрешений
      не больше, чем нужно. Локальный домен в опубликованном пакете —
      отказ на ревью в сторе.
- [ ] `key` в манифесте и `PINNED_EXTENSION_ID` в приложении выведены
      из одного ключа. Расходятся — приложение отправляет токен
      несуществующему получателю, а человек видит «расширение
      не приняло подключение» и ищет причину не там.
- [ ] Размер content-script в пределах порога. Он грузится на каждой
      карточке, в отличие от popup, который открывают по клику.

## Расширение браузера — раз в месяц

- [ ] Открыть карточку своего товара и убедиться, что панель на месте.
      Маркетплейс меняет вёрстку без предупреждения, и якорь отваливается
      молча — единственный признак живёт в консоли клиента, куда мы
      не смотрим.
- [ ] Доля обращений к API расширения, отвечающих 401. Устойчивый рост
      означает, что клиенты не переподключаются после истечения токена
      и расширение у них просто перестало работать.

## Отложено сознательно

Не делать, пока не сработает условие:

| Что | Когда браться |
|---|---|
| Самостоятельная регистрация, восстановление пароля | ручное заведение тормозит, ориентир 10–15 компаний |
| Второй фактор для селлеров, роли и разрешения | клиенты просят доступ для сотрудников |
| Экспорт данных клиента | первый запрос от клиента или требование договора |
| Долговременное хранение журнала | первое обращение, которое не удалось разобрать из-за пропавших логов |
| `company_id` в журнале воркеров | первая запись в журнал из обработчика очереди |
| Справедливое распределение очереди между клиентами | один клиент реально блокирует остальных |
| Объектное хранилище под raw | объём мешает резервному копированию; схема ключей принята заранее — см. ниже |
| Отдельное аналитическое хранилище | пороги из ADR-001 |
| Тарифы | до этого — булевы флаги на компании, кода про деньги нет |

### Схема ключей объектного хранилища

Принята заранее, чтобы переезд не потребовал переименования уже
накопленного сырья:

```
raw/v1/company={uuid}/marketplace={slug}/account={uuid}/report={slug}/period=YYYYMMDD_YYYYMMDD/{sha256}.json.gz
```

Ключ детерминирован полями уникального индекса `raw_document` —
повторный PUT перезаписывает тот же объект, а не создаёт второй.

Переезд тянет за собой: версионирование бакета становится обязательным;
восстановление — двухкомпонентным (PostgreSQL на момент времени плюс
бакет на тот же момент); раздел резервного копирования переписывается
целиком.
