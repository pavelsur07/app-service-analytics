## ADR-048: Календарь плана — ограниченное чтение и полная команда

**Дата:** 2026-10-27
**Статус:** Accepted
**Модуль:** SalesPlanning
**Дополняет:** ADR-046 §6, не меняя виды событий, период или лимит500.

### Контекст

ADR-046 разрешает до500 сохранённых событий на версию и полный PUT snapshot.
Общий предел экранных списков —200. Применять командный предел к списку
ответа нельзя; частичный GET также нельзя ошибочно отправить как полный PUT,
иначе оставшиеся события будут удалены.

### Решение

GET `/api/companies/{companyId}/sales-plans/{planId}/calendar` читает DBAL
в readonly DTO, по keyset `(date_from, id)`, не больше200 сохранённых событий
на страницу (по умолчанию50). Query возвращает DBAL QueryBuilder,
Application read-action выполняет один statement и маппит DTO. Ответ содержит nextCursor, version шапки и границы сезона.
Границы season_start/season_end вычисляются из шапки отдельными readonly
полями; они не тратят сохраняемый лимит и не принимаются в PUT.

PUT того же пути принимает expected version и полный набор до500 записей.
Перед редактированием клиент дочитывает все страницы одной версии; при
изменении версии перечитывает набор. Сохранение неполного списка при
незавершённой загрузке UI не предлагает. Сервер проверяет expected version
и не обещает неподвижный snapshot между отдельными GET-страницами.

Запись существующего события сохраняет его UUID; новый UUIDv7 создаётся
приложением. Ссылка id допустима только на запись этого плана компании.
Дубли id или одинаковых событий внутри команды отвергаются. Пересечения
разных видов допустимы по ADR-046. Полная команда может удалить событие,
не передав его id; точный before/after каждого изменения попадает в аудит.

Для команды и копирования допускается загрузить ограниченный ORM-агрегат
до500 событий этой версии. Это человеческая запись в общем EntityManager,
не Entity-список для отображения. Проверочный overscan обнаруживает нарушение
лимита и завершает команду ошибкой, не обрезает данные. Company scope явный.
Header optimistic flush сериализует изменения раньше дочерних записей;
календарь и аудит входят в ту же внешнюю транзакцию. Сохранение полного
snapshot повышает версию шапки; неизменённые события сохраняют id.

Календарь новой версии копируется ORM с новыми UUID в транзакции копирования
плана. DBAL-исключение ADR-041 относится только к sales_plan_line. Удаление
SKU из draft в одной транзакции удаляет его события с аудитом и сохраняет
plan-wide события. Отмена/отказ от версии сохраняют календарную историю.

### Последствия и проверка

С явным limit200 большой календарь читается максимум тремя страницами; фронтенд должен
учитывать целостность загрузки и версию перед полным сохранением.
Проверяются tenant/version/id/SKU guards, граница200/500, переход страниц
без дублей, неизменность виртуальных границ, ORM copy/remove-SKU и rollback.
Новых внешних зависимостей, складских команд или видов календаря нет.

Отклонены: ответ одним списком500; PUT загруженной первой страницы вместо
полного набора; сохранение второй копии дат сезона; DBAL-запись календаря.
