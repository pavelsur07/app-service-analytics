## ADR-047: SalesPlanning — проверка статуса и версии при ORM-переходах

**Дата:** 2026-10-27
**Статус:** Accepted
**Модуль:** SalesPlanning
**Уточняет:** ADR-008 и ADR-040 §8; сохраняет ORM-запись шапки/аудита ADR-041.

### Контекст

ADR-040 §8 буквально требует `WHERE status = 'approved'` и ожидаемую версию
при первом обновлении утверждённой шапки. Doctrine ORM с `#[Version]`
формирует `UPDATE ... WHERE id = ? AND version = ?`; домен проверяет статус
загруженной версии до её изменения. Статус в SQL Doctrine не добавляет.
Это расхождение текста и реализации, а не исключение, выводимое из кода.

Прямой DBAL UPDATE человеческой шапки противоречит ADR-041. Собственный
ORM persister ради второго предиката создаёт дополнительный механизм записи.
Нужна явная форма той же защиты от гонок в рамках обычного ORM.

### Решение

Предусловие статуса проверяется доменным методом на ORM-загруженной шапке.
Предусловие версии проверяется дважды: ожидаемая версия запроса против
загруженной версии, затем штатный optimistic UPDATE Doctrine по версии.
Для внутренней утверждённой шапки при replacement используется версия,
загруженная внутри операции; клиент передаёт expected version черновика.

Любое производственное изменение статуса проходит только через ORM и
увеличивает версию. Поэтому если после чтения другой запрос изменил статус,
он обязательно изменил и версию: optimistic UPDATE проигрывает и откатывает
операцию. Успех обновления той же версии подтверждает, что проверенный
доменом статус не был изменён конкурентом. Это заменяет буквальное
требование SQL-предиката статуса ADR-040 §8; смысл предусловия сохраняется.

Создание revision, replacement и отмена по-прежнему первым шагом одной
транзакции обновляют одну и ту же утверждённую шапку. Для создания/reuse draft
домен явно меняет сохраняемый счётчик даже при совпадающих updatedAt, чтобы
ORM не пропустил UPDATE. Проверка наличия draft выполняется после flush
этой шапки. Полагаться только на ранее прочитанный статус запрещено.

Replacement сначала переводит старую шапку в superseded и flush-ит её,
затем утверждает новую: это соблюдает частичный unique index approved.
Шапки, аудит, освобождение всех старых claims и занятие новых дней остаются
в одной внешней транзакции. Ошибка версии, пустой план или конфликт claims
откатывают всё. Уникальные ключи draft/approved и claims сохраняются.

Нативные записи статуса вне ORM не разрешаются. Контролируемое SQL-создание
legacy fixture в тесте не является производственным путём изменения статуса.
Чтение исходной шапки и внутренних версий остаётся company-scoped.

### Проверка и последствия

Интеграционные сценарии должны воспроизводить изменение версии источника
после ORM-чтения и отсутствие draft/аудита при отказе; устаревшую версию target
при replacement с откатом уже flush-нутого superseded источника; повторное
создание с возвратом существующего draft после сериализующего UPDATE;
конфликт стороннего плана с восстановлением шапок/claims/аудита.
Настоящие параллельные соединения дополнительно проверяются задачей A10.

Новой схемы, блокировок редактирования и механизма записи нет. Издержка —
гарантия зависит от запрета неверсионированных производственных записей
статуса. Будущий такой путь должен пересмотреть это решение, а не обходить его.

Отклонены: DBAL-запись шапки; кастомный ORM persister; один precheck без
изменения версии; надежда только на unique violation, закрывающий EntityManager.
