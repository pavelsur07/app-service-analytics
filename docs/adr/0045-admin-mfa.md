# ADR-045: обязательный второй фактор администраторов

**Дата:** 25.10.2026.
**Статус:** Accepted — решение согласовано владельцем; поставка требует проверок и ревью.
**Уточняет:** ADR-007 и ADR-017; прекращает отступление об отложенном TOTP.
**Согласование:** владелец принял `docs/plan/security-remediation-stage-5.md`
ответом «Согласовать вариант из плана» 25.10.2026, включая OTPHP 11.5.0.

## Причина

Пароль администратора открывает данные всех клиентов. IP allowlist/VPN
сохраняется, но не заменяет второй фактор. Любой администратор, включая
существующих владельцев, проходит MFA до привилегированных действий.

## Решение

Используется `spomky-labs/otphp` 11.5.0: TOTP, SHA-1, 6 цифр, период
30 секунд, окно ±1 шаг. Секрет создаёт библиотека криптографически случайно.
Принятый time-step монотонен и одноразов: повтор и конкурентное погашение
не открывают второй сеанс. Проверка по RFC6238 — независимыми тестовыми
векторами; тестовая реализация HMAC в Playwright не используется продуктом.

После пароля создаётся ограниченный challenge на 5 минут, HTTP 202 с
состоянием enrollment_required/verification_required. Symfony principal
содержит обычные роли, но единый guard после firewall и до контроллеров
не даёт никаких привилегий без серверного MFA-proof. Нельзя принимать
наличие ROLE_ADMIN за завершённый вход. Прежние сессии без proof также
отклоняются. Публичный технический admin ping остаётся без секретов.

Challenge и proof привязаны к administratorId и версии MFA. Guard читает
свежую версию из БД на каждом запросе; сброс/перевыпуск резервных кодов
увеличивает версию и аннулирует прежние сессии. Для любого действия
controller повторно сопоставляет challenge/proof с текущей версией, а
репозиторий проверяет ожидаемую версию под общей транзакционной блокировкой.
Успешный второй шаг меняет идентификатор сессии. Прежний challenge после
успеха удаляется, proof живёт в пределах существующего срока сессии.

До полного входа доступны только status/enroll/confirm/verify и выход,
а не данные компаний, ссылки или управление администраторами. Seller,
extension и internal не приобретают MFA-исключений или новых полномочий.
CSRF-защита этапа 2 применяется и к MFA endpoints.

## Данные и атомарность

`administrator_mfa` хранит administratorId, зашифрованный секрет, состояние,
версию и последний принятый шаг. `administrator_mfa_recovery_code` —
UUIDv7, administratorId, SHA-256 случайного 128-битного кода и consumedAt.
Связь системная, companyId отсутствует по построению.

Секрет шифруется штатным libsodium secretbox со случайным nonce; отдельный
ключ MFA выводится из APP_ENCRYPTION_MASTER_KEY через HKDF с контекстом
conwix.admin-mfa.v1. В хранилище есть версия упаковки. Собственные TOTP или
криптографические примитивы не реализуются. Защита резервной копии требует
сохранения мастер-ключа вне самой базы, как для ключей площадок.

Enrollment сохраняется ORM; погашения и переходы делаются DBAL в узкой
системной auth lifecycle-границе, аналогично ADR-037. Одноразовые изменения
условны внутри UPDATE; общей advisory transaction lock по administratorId
сериализуются enrollment/verify/regeneration/reset. PK и уникальный хэш кода
защищены БД. Запись audit коммитится с изменением. Новых Facade, очередей
или межмодульных связей не появляется.

10 резервных кодов показываются единожды после подтверждения TOTP.
Повторный вход принимает TOTP либо один резервный код; перевыпуск требует
полного входа и свежего одноразового кода, отменяет прежний набор и чужие
сеансы этого аккаунта. Секрет настройки доступен только недавнему входу по
паролю до подтверждения enrollment; после включения его чтение запрещено.
Ответы с секретом/кодами — no-store. В UI они не сохраняются в storage,
URL или query-кэше, mutation-кэш удаляется при уходе со страницы.

В audit пишутся факты настройки, подтверждения, входа, перевыпуска и
операторского сброса. Значения секретов и хэшей не пишутся. Для сброса
фиксируются субъект, оператор SuperAdmin и несекретный номер внешней
проверки личности. Секреты/коды не передаются через Messenger и не включаются
в production telemetry или review-пакеты.

## Ограничение попыток

Redis sliding-window: 5 MFA-операций за 5 минут на администратора и
25 за 5 минут на IP. Счётчик общий для challenge этого аккаунта, новый
парольный вход/новый challenge не сбрасывает лимит. Оба счётчика потребляются
до дорогих действий/разбора кода, ключи — HMAC. Парольный login_throttling
и IP allowlist/VPN остаются обязательными.

## Восстановление

С резервным кодом пользователь входит обычным вторым шагом. При потере
всех факторов восстановление выполняет оператор по SSH после отдельной
проверки личности, а не через публичный HTTP endpoint:

```
app:identity:reset-admin-mfa <email> --operator=<superadmin-email> \
  --identity-reference=<несекретный-номер-проверки> [--apply]
```

Без apply команда ничего не меняет. Оператор должен существовать и иметь
SuperAdmin; для последнего владельца оператором может быть он сам после
внешней проверки личности и доступа через доверенный SSH-контур. Выбор email
в аргументе не является доказательством личности: его подтверждают до
запуска команды, ссылка на проверку — след, не автоматический валидатор.
Пароль и TOTP-секрет не передаются аргументами. Reset создаёт новый секрет,
увеличивает версию, отменяет все прежние коды/сессии и требует нового
парольного входа и enrollment. Публичного bypass, временного входа только
по паролю и отключения MFA всем при аварии нет.

## Поставка и откат

Одна миграция добавляет две таблицы, существующие факты не меняются.
Frontend и backend выкладываются совместимой парой. После выкладки
существующий владелец на следующем входе настраивает свой authenticator
сам; до этого системные действия закрыты. Агент не подключает чужой фактор
и не читает реальные резервные коды ради smoke-теста.

Down удаляет только новые таблицы, но теряет MFA-секреты/резервные коды:
для восстановления требуются зашифрованная резервная копия и мастер-ключ.
Перед откатом к старому приложению закрыть admin-контур внешним сетевым
ограничением: откат к паролю без ограничения не считается безопасным.
Production down и операторский reset без отдельного основания не запускаются.

## Проверки

HTTP: password-only и legacy session не открывают системный контур,
enrollment/verification/recovery/expiry/throttling и сброс версии.
Integration: одноразовость, изоляция администраторов, атомарность audit и
двухпроцессное конкурентное погашение с наблюдаемой блокировкой PostgreSQL.
UI: один существующий admin e2e дополнен MFA и восстановлением.
Миграция: schema validate и db-rebuild-check на локальных томах.
