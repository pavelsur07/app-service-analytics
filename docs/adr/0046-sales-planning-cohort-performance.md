## ADR-046: Дневное планирование — исходная цель и когортный результат

**Дата:** 2026-10-27
**Статус:** Accepted
**Модуль:** SalesPlanning; Ingestion — пакетное чтение через существующий Facade
**Уточняет:** ADR-040/041 в части семантики цели, базы сравнения и чтения фактов
**Не меняет:** классификацию ADR-019/020, зрелость ADR-029 и методики старых отчётов

### Контекст

Владелец задаёт план на каждый день в начале сезона и далее контролирует
движение относительно него. Загрузка фактов и пересчёт прогноза не должны
переписывать цель. Требуются дневные и накопительные показатели по SKU.
Из количества заказов исключаются отмены до передачи в доставку.

Исходные поля quantity/РРЦ по ADR-040 не определяют, что пользователь считал
продажей. Существующий условный процент выкупа не равен продажам / заказам.
Поэтому переименование старых штук в новую метрику меняет смысл сохранённых данных.
Схема цели, межмодульный контракт и правила базы сравнения требуют отдельного ADR.

### Решение

#### 1. Явная метрика цели

В шапке версии плана хранится nullable enum `metric`:

- `retained_sales` — выкупленные штуки за вычетом уже состоявшихся клиентских возвратов;
- `orders_excluding_pre_handover_cancellations` — заказанные штуки без подтверждённых T1.

Рекомендованный выбор для контроля продаж — retained_sales. Черновик без
выбора допустим для совместимости старого сценария создания, но утверждение
нового плана и сравнение выполнения требуют выбранной метрики.
Старые строки остаются NULL: миграция не подставляет методику автоматически.

Метрика выбирается явной командой с expected version и аудитом. Утверждённая
шапка не правится: выбор для старого плана проходит через новый draft той же
линии без изменения исходных чисел. При первой интерпретации старой цели
аудит содержит идентификатор числовой базы. После выбора ненулевой метрики
её нельзя менять в следующих версиях той же линии; другая метрика — новый план.

#### 2. Исходная цель и версии

База сравнения — первая успешно утверждённая версия линии, упорядоченная
по version_number. Draft/discarded никогда не являются базой. Новая активная
версия не подменяет исходную цель. Отмена сохраняет историю и числовую базу,
но закрывает линию по ADR-040. До первого утверждения интерфейс показывает
черновик, а не выполнение утверждённой цели.

Жизненный цикл и запрет пересечений реализуются по ADR-040: изменения в draft,
копия approved в новый draft, superseded для прежней активной версии,
cancelled/discarded без удаления шапок. Все изменения защищены версией и аудитом.
Сведения об утверждении — approved_by_user_id и approved_at — сохраняются
и после superseded/cancelled. Ссылка на автора индексируется в той же миграции.

#### 3. Количество заказов и наблюдаемые продажи

Зерно измерения — компания × кабинет × SKU × business_date заказа.
Для Ozon используется существующая дата в МСК; поздние исходы уточняют
первоначальную когорту, включая когорты окончившегося сезона.

```text
rawOrdered = сумма всех количественных аллокаций
excludedT1 = сумма аллокаций с подтверждённым outcome T1
effectiveOrdered = rawOrdered − excludedT1
observedRetainedSales = сумма аллокаций D
```

Исходные факты не удаляются. Active, T2/P/R и unknown остаются в effectiveOrdered.
Unknown не объявляется T1 без доказательства; источником классификации остаётся
buyout_outcome. D уже исключает аллокацию R — вычитать R из D второй раз нельзя.

Условный процент выкупа остаётся D/(D+T2+P) по действующей методике;
его нельзя умножать на effectiveOrdered для получения продаж.
Если нужна конверсия D/effectiveOrdered, это отдельный явно названный показатель.

#### 4. Деньги, прогноз и качество

Наблюдаемая денежная оценка продаж — сумма цены исходной товарной строки,
умноженной на оставшееся количество D. Это оценка по цене продажи до расходов,
а не начисления и не payout. Выручка плана по РРЦ подписывается отдельно.
При отсутствии цены либо несовпадении валюты денежной оценки нет; штуки остаются доступны.
Money и целые минорные единицы обязательны, float запрещён; округление — явно.

Текущий projectedBuyout Ingestion сохраняет собственное имя и методику.
Он не выдаётся за итоговый нетто-прогноз, пока не реализована оценка будущих
возвратов. Поле expectedNetSales до этого NULL с объясняющей причиной.
Возвратная модель этапа B, её горизонт, обучение и критерии допуска принимаются
отдельным уточняющим ADR после проверки источников; этот ADR их не выдумывает.

Ноль, отсутствие загрузки, частичная загрузка, preliminary и mature различаются.
Зрелость выкупа не означает завершение возвратного хвоста.
Полнота загрузки postings не доказывает полноту возвратов по другой временной оси.
Нельзя объявлять восстановимым исторический срез mutable sales/returns
только на основании first_loaded_at. Исторический backtest требует пригодных ревизий.

#### 5. Пакетное чтение и API

SalesPlanning читает факты только через IngestionFacade::salesCohortMetrics:
companyId первым, кабинет берётся из своей проверенной шапки плана,
запрос содержит ограниченный набор SKU, диапазон и начало накопления.
Публичные readonly DTO не раскрывают Infrastructure-типы.
Обратной зависимости и SQL-соединений таблиц разных модулей нет.

Запрос возвращает до 50 SKU; вложенный ряд каждого SKU — до 184 дней.
QueryBuilder и PostgreSQL выполняют суммы и накопление до отсечения видимого
окна; Application соединяет готовые компоненты и вычисляет конечные отношения
«результат / цель» в точной арифметике. Каждый список ограничен менее 200 элементов.

Новый GET `/api/companies/{companyId}/sales-plans/{planId}/performance`:
from/to, groupBy (day/week/month/period), limit (20 по умолчанию, максимум 50)
и keyset cursor по SKU с привязкой к параметрам и базе сравнения.
Для day — до 31 колонки, для агрегированных интервалов — до 184 дней.
Неверные границы/лимиты — 422 без тихого усечения.
Старый GET плана и его quantity/revenueMinor не меняют смысл.

Ответ указывает baselinePlanId, метрику, calculatedAt, начало накопления,
качество и область сводки. Сумма текущей страницы не называется итогом всего плана.
Проценты считаются из компонентов, не средним дневных процентов; пустой знаменатель — NULL.
Текущий день отмечается неполным; основное сравнение по умолчанию — по вчера включительно.
Согласованность одного ответа обеспечивается read-only REPEATABLE READ на общей
DBAL connection. Между разными HTTP-страницами неподвижный исторический срез не обещается.

Новые контракты описываются OpenAPI в коде, TS-типы генерируются. В seller
используются createCompanyApiClient, companyQueryKey и TanStack Query.

#### 6. Календарь плановых событий

Enum: season_start, season_end, replenishment, sales, replenishment_stop.
Границы сезона вычисляются из неизменяемого периода шапки, без второй копии дат.
Остальные записи хранятся в sales_plan_calendar_entry: UUIDv7, company_id,
sales_plan_id, nullable marketplace_sku, kind, date_from/date_to.
Одна запись относится ко всему плану либо SKU из него; группы не вводятся.

sales — интервал; replenishment и replenishment_stop — точки с равными датами.
Подсорт означает плановое поступление на площадку. Стоп подсорт прекращает
планирование новых пополнений, не продажи и не уже отправленные партии.
Совмещение продаж и подсорта в один день разрешено.
Границы записей — внутри периода плана; предпоставки до старта при необходимости
потребуют отдельного расширения, а не молчаливого изменения границ сезона.

До 500 сохранённых записей на версию. PUT `/sales-plans/{planId}/calendar`
принимает expected version в поле version и полный ограниченный набор записей.
Запись через ORM только в draft, аудит точных предыдущих/новых значений,
копирование в новую версию вместе с планом. Это календарные отметки, не команды складу.

#### 7. Миграции и предел объёма

Факт-таблицы и их ключи не меняются. Для согласованного пакета изменения
SalesPlanning — одна итоговая миграция, Entity схемы и рабочий down.
Проверка пустой локальной dev/test-базы обязательна до выпуска.
Ограничения ADR-040/041 по длине плана, SKU, UUIDv7 и валюте сохраняются.
Новых библиотек, сервисов, транспортов очереди и автоматического подсорта нет.

### Альтернативы, которые отвергли

- Переписывать цель текущим темпом: исчезает исходный ориентир владельца.
- Признать старые штуки нетто автоматически: нет доказательства пользовательского смысла.
- Считать только переданные заказы: свежие ожидающие отправки заказы пропадают из спроса.
- Вычитать все отмены: невыкупы после передачи исчезают из оценки когорты.
- Назвать текущий прогноз выкупа нетто-прогнозом: будущие клиентские возвраты не оценены.
- Один взаимоисключающий статус дня: продажи и подсорт могут совпадать.
- Читать соседние таблицы SQL-join либо по SKU в цикле: нарушает границы и бюджет.

### Последствия

**Получаем:** воспроизводимую исходную цель, явную семантику метрик,
когортный план-факт без потери отмен и ограниченное межмодульное чтение.

**Платим:** хранение метрики/утверждения/календаря, отдельные DTO и контракт;
старым целям нужен явный выбор смысла. Поздние исходы меняют исторические
результаты; новый нетто-прогноз требует отдельной модели и проверки качества.

**Условия пересмотра:** запросы не укладываются в бюджет на измеренном стенде;
появилась вторая площадка с другой датой/идентичностью; нужны вложенные группы,
предпоставки вне периода или согласованный исторический срез между страницами.
