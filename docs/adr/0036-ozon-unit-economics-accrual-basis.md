## ADR-036: Юнит-экономика Ozon по методу начисления

**Дата:** 2026-09-28
**Статус:** Accepted
**Модуль:** Ingestion
**Уточняет:** ADR-012 (выручка и комиссия из `by-day` теперь пишутся —
в ту же `marketplace_expense_fact`; запрет касался двойного счёта
с `sales_fact`, а юнит-экономика `sales_fact` больше не читает),
ADR-013 (дата себестоимости — дата начисления продажи, а не дата заказа)
**Не меняет:** ADR-009 (`sales_fact` и её бизнес-дата — для план-факта
и процента выкупа), ADR-019/020 (процент выкупа), ADR-035 (реклама по SKU)

### Контекст

Сверка с отчётом кабинета «Начисления» за август 2026 (выгрузка
владельца, 17 192 строки, сопоставление с продом по отправлению и SKU):

- расходы `marketplace_expense_fact` совпали с кабинетом до копейки
  (−642 593,07 ₽ по всем типам);
- выручка `sales_fact` совпала у 1 215 из 1 215 сопоставимых отправлений;
- **возвраты юнит-экономика не вычитает:** 102 возврата за месяц
  (−248 162 ₽ выручки, +119 076,30 ₽ комиссии) остаются в `sales_fact`
  со статусом `delivered`, и `UnitEconomicsQuery` берёт их как продажи;
- выручка идёт по дате заказа (ADR-009), расходы — по дате начисления
  (ADR-012): в одном месяце на экране смешаны два разных периода;
- **разбор `by-day` пропускает возврат молча.** Возврат приходит
  начислением `POSTING`, где у товара `delivery: null` и есть только блок
  `commission` с отрицательной `sale_amount`. Блок `commission` разбор
  отбрасывал целиком (ADR-012), и такое начисление давало ноль строк
  без ошибки.

На фикстуре `finance-accrual-by-day-2026-07.json` у всех 255 начислений
сумма составляющих — услуги доставки, `item_fees`, `non_item_fee`,
`sale_amount` и `sale_commission` — равна `total_amount`, и у всех 31
блоков `commission` `seller_price = sale_amount` (30 продаж, 1 возврат).
Группа «Продажи» кабинета (Выручка + Баллы за скидки + Программы
партнёров) за август равна сумме `seller_price` продаж — 2 895 370,00 ₽.

Юнит-экономика — это деньги, и отчёт, с которым её сверяет клиент, —
начисления площадки.

### Решение

**1. Юнит-экономика считается по методу начисления.** Выручка, комиссия,
возвраты и расходы берутся из `/v1/finance/accrual/by-day` по дате
начисления (`date` начисления, часовой пояс площадки). `sales_fact`
юнит-экономика не читает. Реклама по SKU — из Performance API, как
в ADR-035: её день совпадает с днём начисления «Оплаты за клик».
Количество заказов (по дате заказа) из юнит-экономики убирается.

**2. Выручка и комиссия пишутся в `marketplace_expense_fact`.** Зерно
и ключ не меняются: одна сумма одного типа по одному товару в одном
начислении, `source_row_id = accrual_id | marketplace_sku | fee_type_id`.
Из блока `commission` товара `POSTING` — две строки:

| Строка | `fee_type_id` | Сумма |
|---|---|---|
| Выручка (цена продавца) | `0` | `sale_amount` |
| Вознаграждение за продажу | `69` (`SaleCommission`) | `sale_commission` |

Код `0` — наш: в справочнике `accrual/types` выручки нет, а нумерация
площадки начинается с `1`. Код `69` — площадки. Оба — в `OzonFeeTypeNames`,
список «типы продажи» — одна константа, по которой фильтруют читатели.
Знак — площадки: продажа `+` / `−`, возврат `−` / `+`.

Таблица становится полной лентой начислений `by-day`. Имя `expense`
исторически неточно; переименование таблицы не окупается.

**3. Продажа или возврат — по знаку строки выручки.** Ноль — отказ
документа.

**4. Штука = строка выручки.** Поля количества в `by-day` нет. Разбор
требует `sale_amount = seller_price`; иначе документ отклоняется
исключением, raw остаётся. Строка на несколько штук станет отказом,
а не ошибкой в количестве.

**5. Баланс начисления.** Сумма всех строк, разобранных из начисления,
равна его `total_amount`; иначе документ отклоняется исключением, raw
остаётся. Начисление, часть денег которого разбор не понял, больше
не проходит незамеченным.

**6. Себестоимость** (ADR-013): у продажи — цена, действующая на дату
начисления продажи; у возврата — сторно по цене исходной продажи (строка
выручки со знаком `+` той же пары «отправление + SKU» у той же компании
и подключения). Продаж такой пары несколько (несколько штук одного
артикула в отправлении, начисленных разными начислениями) — берётся
самая ранняя: какую именно штуку вернули, ответ площадки не говорит,
а правило должно быть одно и детерминированное. Если исходная продажа начислена раньше загруженной
истории — по цене на дату возврата.

**7. Читатели расходов исключают типы продажи.** «Расходы товара»
и разбивка по типам в юнит-экономике суммируют всё, кроме `[0, 69]`.
Читатели, фильтрующие по своим типам (сверка рекламы — 41, локализация —
логистика), не меняются.

### Альтернативы, которые отвергли

- **Возвраты из `marketplace_return_fact` × `sales_fact`, по дате заказа.**
  Без новой загрузки и совпадало с кабинетом до копейки, но сумму
  возврата выводит, а не берёт; частичный возврат это правило сломает.
  И главное — юнит-экономика — это деньги, а деньги считает площадка.
- **Возвраты из `by-day` по дате начисления, продажи — по-прежнему
  по дате заказа.** В одном месяце выручка одних заказов и возвраты
  других: маржа за период искажена в любую сторону.
- **Отдельная факт-таблица продаж из `by-day`.** Новая схема, Entity,
  Builder, writer и миграция ради двух строк на начисление, которые
  ложатся в существующий ключ без изменений. Отвергнута владельцем.
- **Выручка из `seller_price` вместо `sale_amount`.** Сегодня они равны;
  баланс начисления сходится по `sale_amount`, её и берём, а равенство
  проверяем.

### Последствия

**Получаем:**
- юнит-экономика сходится с отчётом кабинета «Начисления» по построению;
- возвраты вычитаются деньгами площадки, включая возврат комиссии;
- разбор больше не теряет деньги молча — отказ документа вместо тишины;
- лента начислений целиком — основа для отчёта «Экономика по категориям».

**Платим:**
- юнит-экономика есть только за дни, за которые загружен `by-day`;
  история до начала загрузки — добором (`backfill-ozon-expenses`);
- заказы из юнит-экономики уходят — они только на план-факте;
- любой новый читатель `marketplace_expense_fact`, суммирующий «все
  расходы», обязан исключить типы продажи;
- строгая проверка баланса отклоняет страницу с незнакомой формой
  начисления: ни выручка, ни расходы этой страницы и следующих
  не пишутся, пока разбор не научится. Страницы дня до отклонённой
  остаются записанными — запись идёт порциями по ходу чтения
  (CLAUDE.md §6), удаления у начислений нет. День в отчёте частичный,
  а не пустой, пока разбор не исправлен и день не догружен повторно;
- отклонённый день видно в трекере и в очереди failed, но не на экране:
  raw сохраняется до разбора, и контроль покрытия считает день
  загруженным. Отметка «день разобран» — изменение схемы raw-слоя,
  отдельным решением.

**На что обратить внимание потом:**
- день отклонён проверкой баланса → в ответе площадки форма, которую
  разбор не знает (первый кандидат — компенсации: +11 960,94 ₽ за 31.08
  в кабинете, в фактах их нет);
- `sale_amount ≠ seller_price` → появились строки на несколько штук,
  правило «штука = строка» пересматривается;
- площадка завела тип начисления с кодом `0` → код выручки меняется.
