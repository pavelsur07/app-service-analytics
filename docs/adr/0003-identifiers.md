## ADR-003: Стратегия генерации идентификаторов

**Дата:** 2026-08-02
**Статус:** Accepted
**Модуль:** весь проект

### Контекст

Продукт хранит финансовые данные конкурирующих между собой селлеров.
Идентификаторы попадают в URL и видны клиенту. Таблицы фактов растут
до десятков миллионов строк с постоянной вставкой.

Смена стратегии идентификаторов после накопления данных — необратимая
операция, затрагивающая все таблицы и все внешние ключи.

### Решение

UUIDv7 для всех сущностей, на которые ссылаются извне: `Company`, `User`,
`MarketplaceAccount`, `Sku`, `Plan`, `CostHistory` и аналогичные.

Генерация на стороне приложения через `symfony/uid`, до вставки в БД.
В PostgreSQL — нативный тип `uuid`, не `varchar`.

Таблицы фактов (`sales_fact` и подобные) отдельного суррогатного ключа
не получают: первичный ключ естественный, совпадающий с ключом
идемпотентности — `(company_id, marketplace, business_date, row_hash)`.

Первым столбцом любого составного индекса по данным компании идёт `company_id`.

### Альтернативы, которые отвергли

- **serial / bigserial** — отвергли: последовательные id раскрывают
  объёмы бизнеса клиенту, допускают перебор при единственной забытой
  проверке доступа, и не позволяют собрать граф объектов в памяти
  до записи (id известен только после вставки).
- **UUIDv4** — отвергли: полная случайность ломает локальность вставки
  в B-tree, страницы индекса фрагментируются, деградация проявляется
  на десятках миллионов строк — то есть именно на таблицах фактов.
- **ULID** — отвергли: свойства близки к UUIDv7, но требует внешней
  библиотеки и не имеет нативного типа в PostgreSQL.
- **UUID в varchar(36)** — отвергли: 36 байт вместо 16, медленнее
  сравнение, больше индексы, при нулевой выгоде.
- **Суррогатный UUID на таблицах фактов** — отвергли: лишние 16 байт
  на строку и лишний индекс на десятках миллионов записей;
  ссылок на отдельную строку продажи извне не бывает.

### Последствия

**Получаем:**
- Идентификатор известен до вставки: граф связанных объектов собирается
  в памяти и пишется одним flush; идемпотентные ключи сообщений
  формируются заранее.
- Перебор по URL невозможен даже при ошибке в проверке доступа.
- Локальность вставки в индекс сопоставима с автоинкрементом.
- Сортировка по id совпадает с сортировкой по времени создания.

**Платим:**
- 16 байт вместо 8 в каждом индексе; на таблицах фактов
  и их составных индексах расход ощутим.
- Идентификаторы нечитаемы глазами: в поддержке копируем, а не диктуем.

**На что обратить внимание потом:**
- Размер индексов таблиц фактов растёт быстрее самих данных →
  проверить, не появился ли где-то ненужный суррогатный ключ.
