## ADR-006: Ingestion — сырьё, идентификация фактов, пересчёт

**Дата:** 2026-08-02
**Статус:** Accepted
**Модуль:** Ingestion; заменяет часть ADR-003 о первичном ключе таблиц фактов

### Контекст

Маркетплейсы меняют выданные данные задним числом: перевыпускают отчёты
о реализации, доначисляют комиссии, проводят возвраты и корректировки
спустя недели, иногда в пределах квартала.

Из этого следует проблема, которую первоначальная схема не решала.
Ключ идемпотентности, построенный на хэше содержимого строки, защищает
от повторного запуска обработчика, но не от изменения данных в источнике:
при перевыпуске отчёта хэш меняется, и вместо замены строки в таблице
оказываются две — устаревшая и актуальная. Все расчёты после этого
удваивают показатели.

Дополнительно: клиент сверяет цифру с отчётом площадки и требует
объяснения расхождений — значит, каждая строка факта должна быть
прослеживаема до исходного документа. Площадки отдают даты в собственных
часовых поясах, а селлеры находятся в разных, поэтому «продажа 12 августа»
требует однозначного определения.

Первичный ключ таблиц фактов — самое необратимое место схемы:
после накопления десятков миллионов строк и партиционирования
его смена означает перезапись всей истории.

### Решение

**Сырьё.** Ответ внешнего API сохраняется целиком в PostgreSQL (`jsonb`)
до какого-либо разбора, вместе с временем получения и хэшем тела.
Raw-слой никогда не мутируется. Уникальность — по компании, площадке,
типу отчёта, периоду и хэшу тела: повторное получение идентичного
ответа не создаёт новой записи.

**Идентификация факта.** Первичный ключ строки факта:
`(company_id, marketplace_account_id, source_row_id)`,
где `source_row_id` — стабильный идентификатор строки в источнике.
Где площадка такого идентификатора не даёт — детерминированный суррогат,
построенный из полей, однозначно определяющих строку в отчёте
и не изменяющихся при корректировке (идентификаторы заказа, отправления,
товара, склада, тип операции). Изменяемые величины — суммы, количества,
статусы — в суррогат не входят.

**Обнаружение изменений.** `row_hash` остаётся колонкой, но не входит
в первичный ключ. Его роль — детектор: совпал с сохранённым, запись
пропускается; не совпал, строка обновляется. Запись выполняется
вставкой с обновлением при конфликте.

**Отчёты без построимого идентификатора строки** (агрегированные сводки)
перезаписываются целиком в границах периода: удаление и вставка
в одной транзакции по ключу компания + подключение + тип отчёта +
бизнес-дата.

**Прослеживаемость.** Каждая строка факта хранит ссылку на raw-документ,
из которого получена её текущая версия. При обновлении ссылка
перезаписывается на новый документ.

**Битемпоральность.** Строка факта хранит бизнес-дату (когда событие
произошло), время первой загрузки и время последнего обновления.

**Часовой пояс.** Бизнес-дата определяется в часовом поясе площадки,
приводится при нормализации и хранится как дата без времени.
Часовой пояс задаётся конфигурацией коннектора, а не выводится из данных.

**Пересчёт.** Скользящее окно последних N дней (по умолчанию 45)
пересчитывается при каждом запуске синхронизации. Отдельно — периодический
глубокий рескан за предыдущий квартал для длиннохвостых корректировок;
оба параметра конфигурируемы, глубокий рескан включается после накопления
истории глубже квартала.

**Устойчивость к дрейфу схем.** Сырой ответ валидируется по ожидаемой
структуре при разборе. Неудача разбора не теряет данные — raw уже
сохранён — и попадает в трекер ошибок как исключение.

**Лимиты запросов** применяются на уровне подключения, а не глобально.

### Альтернативы, которые отвергли

- **Хэш содержимого в первичном ключе** (первоначальный вариант ADR-003) —
  отвергли: изменение данных в источнике порождает вторую строку вместо
  замены первой, и все агрегаты удваиваются. Ошибка молчаливая
  и проявляется через недели после перевыпуска отчёта.
- **Версионирование фактов (valid_from / valid_to)** — отвергли: точнее
  отражает историю, но добавляет условие по интервалу в каждый
  аналитический запрос и кратно усложняет витрины. История изменений
  при необходимости восстанавливается из raw-слоя, который сохранён целиком.
- **Полный пересчёт всей истории при каждой синхронизации** — отвергли:
  к концу первого года это часы работы на каждого клиента.
- **Только скользящее окно, без глубокого рескана** — отвергли:
  корректировки приходят глубже 45 дней, и они останутся неучтёнными.
- **Бизнес-дата в UTC** — отвергли: не совпадает с отчётом площадки,
  клиент видит расхождение по дням на границах суток.
- **Часовой пояс из данных ответа** — отвергли: площадки непоследовательны
  в разметке, и правило перестаёт быть детерминированным.
- **Raw-слой в S3 с метаданными в PostgreSQL** — отвергли на текущей
  стадии: добавляет компонент и усложняет транзакционность записи
  ради проблемы объёма, которой пока нет.
- **Разбор ответа без сохранения сырья** — отвергли: глубина истории
  в API площадок ограничена, переспросить нельзя, и неверно понятое
  поле нельзя переиграть.

### Последствия

**Получаем:**
- Перевыпуск отчёта заменяет строку, а не удваивает её.
- Повторный запуск обработчика по-прежнему безопасен.
- Любая цифра прослеживается до исходного документа.
- Изменения данных задним числом видны по времени обновления строки.
- Разбор можно переиграть на сохранённом сырье без обращения к API.

**Платим:**
- Требуется стабильный идентификатор строки; для части отчётов его
  приходится конструировать, и правило построения нужно проверять
  на реальных данных каждой площадки.
- Для агрегированных отчётов действует отдельная стратегия перезаписи —
  две модели обновления вместо одной.
- История изменений самой строки факта не хранится в таблице фактов;
  восстанавливается только из raw.
- Raw-слой увеличивает объём базы в несколько раз и требует политики
  хранения.

**На что обратить внимание потом:**
- Доля отчётов, где стабильный идентификатор строки построить не удаётся,
  растёт → пересмотреть модель в пользу версионирования.
- Корректировки приходят глубже квартала → расширять глубокий рескан.
- Объём raw-слоя начинает мешать резервному копированию →
  выносить в объектное хранилище с метаданными в PostgreSQL.
- Растёт доля неудачных разборов → площадка изменила формат.
