## ADR-004: Представление денежных величин

**Дата:** 2026-08-02
**Статус:** Accepted
**Модуль:** весь проект, критично для Finance и Costing

### Контекст

Продукт считает юнит-экономику, и его цифры клиент сверяет с отчётами
маркетплейсов. Расхождение в копейки подрывает доверие ко всему расчёту.

Деление денег возникает в двух местах: распределение общих расходов
(реклама, хранение, штрафы) между SKU и пересчёт валюты. Оба дают
накапливающуюся ошибку при неявном округлении. Разделить 100 на трёх —
это 33.34 / 33.33 / 33.33, а не 33.33 трижды: остаток обязан
куда-то деться, иначе сумма частей не равна целому.

Валюта не является отдалённой перспективой: WB и Ozon уже сегодня
отдают заказы в KZT, BYN и USD в тех же отчётах. Первый импорт реального
отчёта столкнётся с этим. Добавление валюты к денежным колонкам постфактум —
миграция всех таблиц фактов, то есть ровно та необратимость, которую
этот ADR должен предотвращать.

Представление денег пронизывает схему БД и весь домен — смена постфактум
затрагивает каждую денежную колонку и каждый расчёт.

### Решение

Денежные величины представлены Value Object `Money` = сумма в минорных
единицах (целое число) + код валюты по ISO 4217.

Хранение суммы — `bigint` через собственный Doctrine Type.
Код валюты — отдельная колонка `char(3)`, одна на строку факта, поскольку
все суммы одной строки отчёта выражены в одной валюте. Дублировать
валюту рядом с каждой денежной колонкой не требуется.

Конструктор `Money` не принимает `float`; допустимы целые минорные
единицы или строка. Валюта обязательна, значения по умолчанию нет.

Любая операция между величинами разных валют завершается исключением.
Конвертация не реализуется до появления курсов с привязкой к дате;
до тех пор несовпадение валют — ошибка, а не повод для молчаливого приведения.

Отчётная валюта компании хранится отдельным полем и на этапе MVP
используется только для отображения; сведение разных валют в один
показатель откладывается вместе с конвертацией.

Деление выполняется только операцией аллокации с распределением остатка,
гарантирующей равенство суммы частей исходной величине.
Правило округления указывается явно при каждой операции;
значения по умолчанию нет.

Внутренняя реализация арифметики — `brick/money`, скрытая
за собственным API Value Object.

### Альтернативы, которые отвергли

- **float / double в денежных полях** — отвергли: молчаливая потеря
  точности, проявляющаяся как расхождение с отчётом площадки
  спустя недели, с трудноустановимым источником.
- **decimal в БД без Value Object** — отвергли: точность хранения
  не защищает от ошибок в арифметике; правила округления и аллокации
  остаются размазаны по коду.
- **Money без валюты, валюта по триггеру** — отвергли: валюты приходят
  с первым же реальным отчётом, а добавление колонки к таблицам фактов
  постфактум — миграция всей истории. Три байта на строку дешевле.
- **Валюта отдельной колонкой к каждой денежной сумме** — отвергли:
  все суммы строки отчёта выражены в одной валюте, дублирование
  не добавляет выразительности и утяжеляет схему.
- **Молчаливое приведение разных валют по текущему курсу** — отвергли:
  курс на момент расчёта не равен курсу на дату события; результат
  невоспроизводим и необъясним клиенту.
- **Собственная арифметика без библиотеки** — отвергли: аллокация
  с остатком и правила округления — именно те места, где самописная
  реализация выглядит корректной и ошибается на краях,
  а цена ошибки высока.
- **brick/money как публичный тип в домене** — отвергли: сторонний тип
  в сигнатурах всего домена делает замену библиотеки дорогой.

### Последствия

**Получаем:**
- Невозможно случайно создать деньги из float или без валюты —
  правило проверяется типом, а не вниманием ревьюера.
- Сумма распределённых частей всегда равна исходной величине.
- Правило округления видно в месте вызова, а не спрятано в умолчании.
- Схема готова к мультивалютным отчётам без миграции таблиц фактов.
- Замена внутренней библиотеки не затрагивает домен.

**Платим:**
- Три байта на строку факта за валюту, которая у большинства клиентов
  всегда одна.
- Обёртка над библиотекой: дополнительный слой кода, требующий
  поддержки при обновлении зависимости.
- Каждое денежное поле требует явного Doctrine Type в маппинге.
- Многословность в местах деления: правило округления пишется всегда.
- До появления конвертации сведение разных валют в один показатель
  невозможно; в интерфейсе это придётся объяснять.

**На что обратить внимание потом:**
- Клиенты с продажами в нескольких валютах просят единый итог →
  пора вводить курсы с привязкой к дате события и конвертацию.
- Обращения «не сходится с отчётом площадки» с расхождением в единицы
  минорных единиц → искать место, где деление обошло аллокацию.
