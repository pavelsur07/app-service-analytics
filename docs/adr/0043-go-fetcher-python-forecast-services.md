## ADR-043: Сервисы на Go (загрузка Ozon) и Python (прогноз поставок)

**Дата:** 2026-10-24
**Статус:** Proposed
**Модуль:** Ingestion, новый модуль прогноза поставок, инфраструктура
**Пересматривает:** ADR-001 — отказ от Python и от отдельного сервиса
ingestion
**Затрагивает:** ADR-007 (расшифровка ключей вторым процессом),
ADR-024 (порт хранилища сырья на Go), ADR-027 (очередь истории),
ADR-028 (владелец лимита Ozon)
**Не меняет:** ADR-006, ADR-009, ADR-034, ADR-038, ADR-042 — идентификация
фактов, бизнес-дата, замена дня снимка и отметка загрузки дня остаются
в PHP без изменений

### Контекст

ADR-001 отверг Python («второй незнакомый язык при отсутствии сегодняшней
проблемы») и отдельный сервис ingestion («blast radius растёт, отладка
становится распределённой, продуктовой выгоды ноль»). Обе причины
сформулированы как «нет сегодняшней проблемы». Этот ADR утверждает,
что проблемы появились, и обязан их показать.

**Загрузка Ozon.** Продукт переходит в промышленную эксплуатацию. Загрузка —
почти целиком ожидание сети: страница ответа Ozon разбирается за
миллисекунды, а ждётся секундами. Один PHP-воркер держит один запрос
в полёте; конкурентность растёт только числом процессов, каждый из которых
держит в памяти весь контейнер Symfony.

> **[Заполнить до принятия — без этого решение не обосновано]**
> - текущее число подключений и прогноз на 3/6 месяцев;
> - запросов к Ozon на подключение в сутки (синхронизация + бэкфилл
>   ADR-027 + рескан ADR-006);
> - p95 длительности запроса к Ozon, память одного `worker-ingestion`;
> - расчёт: сколько PHP-процессов нужно на целевое число подключений
>   и во что это упирается (память сервера, соединения PostgreSQL);
> - что из этого измерено на проде, а что оценено.

**Прогноз поставок.** Новая функция: сколько и когда везти на склады
и кластеры Ozon. Нужны статистические и ML-модели (сезонность,
прерывистый спрос, доверительные интервалы), для которых в экосистеме PHP
готовых библиотек нет, а в Python они стандарт (polars, statsmodels,
scikit-learn). Писать их на PHP — значит писать собственную статистику
и не иметь способа сверить её с эталоном.

Решение дорого отменяемо: два языка переживают задачу, у каждого свой
тулинг, CI, образ и правила. Поэтому ниже граница проведена так, чтобы
самое рискованное — идентификация фактов и изоляция арендаторов —
не переписывалось.

### Решение

#### 1. Языки и где они живут

- **Go** — только загрузка данных из внешних API площадок. **Python** —
  только аналитические расчёты над уже загруженными фактами.
  Другие задачи на этих языках — новый ADR.
- Код — в `services/<имя>/`, у каждого сервиса свой Dockerfile, lock-файл
  и тесты. В `api/` Go и Python не появляются.
- Версии зафиксированы как везде: Go 1.25.x (`go` и `toolchain`
  в `go.mod`), Python 3.14 через `uv` с `uv.lock`. Образы без `latest`.

```
services/
  ozon-fetcher/          Go
    cmd/fetcher/
    internal/
      job/               захват fetch_job, статусы
      ozon/seller/       Seller API
      ozon/performance/  рекламный API (ADR-026)
      ratelimit/         лимит на подключение (ADR-028)
      credentials/       расшифровка ключей (ADR-007)
      rawstore/          S3 + строка raw-документа (ADR-024)
  supply-forecast/       Python
    src/supply_forecast/
      jobs/              захват forecast_job
      inputs/            SQL только по представлениям analytics.*
      model/             расчёт
      outputs/           INSERT … ON CONFLICT в supply_*
packages/
  job-contracts/         JSON Schema полезной нагрузки заданий + примеры
```

#### 2. Граница Go: сеть — Go, смысл — PHP

**Go делает:** захватывает задание загрузки, расшифровывает ключи
подключения, соблюдает лимит, проходит пагинацию, сохраняет каждую
страницу ответа как raw-документ (объект в S3 + строка в базе) и отмечает
итог задания.

**Go не делает:** не решает, что и за какой период загружать; не разбирает
ответы; не пишет факты; не ставит отметку загрузки дня; не меняет
состояние подключения.

**PHP делает, как сейчас:** расписание, окна, бэкфилл и рескан —
только теперь их результат не сообщение Messenger с HTTP-вызовом внутри,
а строка `fetch_job`. Разбор, upsert фактов, замена дня снимка, отметка
`completed_at` (ADR-038), контроль свежести.

**Отказ авторизации.** Go записывает итог задания `auth_failed` с ответом
площадки. Переход подключения в `broken`, уведомление и аудит делает PHP,
подхватив этот итог: доменное правило ADR-007 остаётся в одном месте.

**Проверяемый признак:** после перевода всех отчётов в `api/src` нет
ни одного HTTP-клиента к хостам Ozon, кроме исключения из «Открытых
вопросов» (проба ключей при подключении), а в `services/ozon-fetcher`
нет кода, пишущего в факт-таблицы.

#### 3. Обмен PHP ↔ Go — через таблицы PostgreSQL

- `fetch_job` — Entity и миграция в PHP. Поля: `id` (UUIDv7),
  `company_id`, `marketplace_account_id`, тип отчёта, период, полезная
  нагрузка `jsonb` по схеме из `packages/job-contracts`, статус, итог,
  попытки, время. Уникальный индекс на естественном ключе задания
  (компания, подключение, тип отчёта, период, поколение) — повторная
  постановка перехватывается как конфликт (§4 правил).
- Связь задания со страницами — `fetch_job_document(job_id, page_no,
  raw_document_id)`: raw-документы дедуплицируются по содержимому
  (ADR-006), и одна страница может указывать на уже существующую строку.
- Захват — `SELECT … FOR UPDATE SKIP LOCKED` с арендой по времени;
  истёкшая аренда возвращает задание в очередь. Задание завершается
  успехом только когда записаны **все** страницы — это то же условие,
  что у отметки загрузки дня.
- **Go → PHP:** PHP-планировщик на каждом тике забирает задания
  со статусом `fetched` (тем же `SKIP LOCKED`), переводит их в
  `parse_queued` и ставит сообщение разбора в существующий
  `async_ingestion`. Конфигурация Messenger меняется только в том, что
  обработчик загрузки больше не ходит в сеть.
- Синхронных HTTP-вызовов между сервисами нет. Транспорт Messenger
  Go не читает и не пишет.

#### 4. Обмен PHP ↔ Python

- Python читает **только представления схемы `analytics`**: продажи,
  остатки (с отметкой полноты снимка, ADR-034), план SalesPlanning,
  каталог. Представления создаются Doctrine-миграциями и проходят ревью
  как Facade: это и есть межмодульный контракт для Python. Чтение таблиц
  модулей напрямую запрещено правами роли, а не договорённостью.
- Результат — в таблицы `supply_*` через `INSERT … ON CONFLICT`
  по естественному ключу (компания, прогон, SKU, кластер, дата).
  У каждой таблицы — Entity в PHP, ORM её не пишет (§6 правил).
- Владелец таблиц `supply_*`, экранов и постановки `forecast_job` —
  новый PHP-модуль прогноза поставок. Его границы и зависимости
  (чтение Ingestion и SalesPlanning через Facade) — **отдельный ADR**,
  этот только резервирует место.
- Прогон запускается заданием `forecast_job` (после полной загрузки дня
  или по запросу пользователя), устроенным как `fetch_job`.
- **Деньги в Python не вычисляются.** Если прогнозу понадобится денежная
  величина — целое в минорных единицах + валюта, деление только
  аллокацией с явным правилом округления (ADR-004), и это новый пункт
  согласования. `float` допустим только для штук, ставок и долей
  внутри модели; на границе записи штуки округляются по правилу,
  записанному в коде.

#### 5. Схема — только Doctrine

Go и Python не выполняют DDL и не содержат миграций. Любая их таблица,
представление или индекс — Doctrine-миграция в `api/` с Entity,
проходящая обычный `migrations:diff` и `make db-rebuild-check`.
Изменение контракта таблицы и кода сервиса — в одном PR.

#### 6. Изоляция арендаторов

Deptrac и PHPStan до Go и Python не дотягиваются, поэтому изоляцию
держит база, а код повторяет правило §1:

- **Отдельная роль PostgreSQL на сервис**: `conwix_fetcher`,
  `conwix_forecast`. Права — только на свои таблицы и представления;
  запись — только в свои результаты.
- **Row-Level Security** на всех таблицах с `company_id`, доступных
  этим ролям: политика `company_id = current_setting('app.company_id')::uuid`.
  Забытый фильтр в коде даёт пустой результат, а не чужие данные.
- **Захват задания — межарендаторное чтение**, операционная задача
  по §1. Оно выполняется отдельной функцией/запросом, видимой из имени
  (`claim_next_fetch_job`), со ссылкой на §1 в комментарии. После захвата
  транзакция делает `SET LOCAL app.company_id` из строки задания,
  и всё дальнейшее идёт под RLS.
- В коде сервисов — `companyID` первым параметром каждой функции
  доступа к данным компании, как в PHP.
- **Хранилище сырья на Go** (`rawstore`) повторяет ADR-024: раскладка
  `raw/v1/<company>/<account>/…`, сборка ключа с проверкой сегментов,
  отказ на ключе вне префикса компании задания, условная запись
  с 412 как «уже записано». Ключ пересобирается из полей, а не
  принимается готовым. Эталонные ключи — общий тестовый набор для PHP и Go.
- Обязательный тест изоляции между компаниями — в каждом сервисе.

#### 7. Ключи подключений

Go получает тот же мастер-ключ из секретов окружения и расшифровывает
`sodium_crypto_secretbox` совместимой реализацией
(`golang.org/x/crypto/nacl/secretbox`) с учётом версии ключа (ADR-007).
Учётные данные — сущность Identity, поэтому Go читает их через
представление с минимумом колонок, созданное миграцией, а не таблицу.
Совместимость шифра проверяется тестом на эталонных шифротекстах,
выпущенных PHP. Python ключей не получает.

#### 8. Лимит запросов

Единственный владелец лимита к Ozon — Go (ADR-028 переносится:
пауза на подключение и метод, блокировка на запись паузы, повтор,
знающий про лимит). Отказ лимита откладывает задание, а не сжигает
попытку. Формат ключей Redis — часть контракта, если проба ключей
остаётся в PHP (см. «Открытые вопросы»).

#### 9. Топология и поставка

| Контейнер | Сети | Роль БД |
|---|---|---|
| `fetcher-ozon` (Go) | `internal` + `egress` (Ozon, S3) | `conwix_fetcher` |
| `worker-ingestion` (PHP) | без egress к Ozon после перевода | как сейчас |
| `forecast` (Python) | только `internal` | `conwix_forecast` |

- Наружу через Traefik ни один из сервисов не публикуется. Фронтенд
  говорит только с PHP API.
- Образ каждого сервиса публикуется в ghcr только с `master`, как PHP.
- CI блокирует merge: Go — `gofmt`, `golangci-lint` (с запретом `float64`
  в денежном пакете), `go test -race`, `govulncheck`; Python — `ruff`,
  `mypy --strict`, `pytest`, `pip-audit`. Фильтр путей
  `bin/ci-classify-paths` получает флаги `go` и `python`.
- Логи — JSON с `request_id`/`job_id` и `company_id` во всех записях
  через общий обработчик, как `RequestContextProcessor`. Ошибки —
  GlitchTip через Sentry SDK.
- Контроль свежести не меняется: он меряет `completed_at`, которую
  по-прежнему ставит PHP. Добавляется контроль очереди: задание старше
  порога в `pending`/`fetched` — оповещение.

#### 10. Порядок перехода

- Исполнитель задания выбирается **по типу отчёта** конфигурацией:
  `php` или `go`. Первым переводится FBO postings v3 (ADR-042).
- Сверка после перевода — неделя: отметки дня ставятся, число
  и `body_hash` страниц на тот же период совпадают с последними
  загрузками PHP, расхождений фактов нет. Теневой двойной загрузки нет:
  она удваивает запросы в лимит Ozon.
- Откат — переключение типа отчёта обратно на `php`.
- PHP-загрузчики удаляются только после перевода всех отчётов и двух
  недель без отката.
- Python — после появления модуля прогноза поставок (отдельный ADR),
  одной узкой полоской до экрана.

### Альтернативы, которые отвергли

- **Масштабировать PHP-воркеры числом процессов.** Отвергаем при условии,
  что замеры из «Контекста» это подтвердят: память на процесс
  и соединения PostgreSQL растут линейно числу запросов в полёте.
  Если замер покажет, что целевая нагрузка помещается в разумное число
  процессов, — этот ADR не принимается.
- **Асинхронный PHP (amphp, ReactPHP, Fibers).** Решает конкурентность
  без второго языка, но это экзотика по меркам проекта: тонкий корпус
  примеров, несовместимость с частью Symfony-компонентов, неочевидная
  отладка. «Скучные технологии» здесь сильнее довода «один язык».
- **Go загружает и разбирает, пишет факты сам.** Удваивает самую
  рискованную логику — состав `source_row_id`, бизнес-дату, деньги,
  замену дня снимка — и две реализации расходились бы молча. Узкое место —
  сеть, а не разбор.
- **Go как HTTP-сервис, который PHP вызывает синхронно.** Возвращает
  ожидание сети в PHP-процесс — ровно то, от чего уходим, — и добавляет
  распределённую отладку.
- **RabbitMQ/Kafka для обмена.** Новый компонент в проде; ADR-001 уже
  отверг RabbitMQ по той же причине. Таблица заданий видна обычным SQL.
- **Doctrine-транспорт Messenger с JSON-сериализатором для Go.**
  Привязал бы Go к внутреннему формату таблицы `messenger_messages`
  и заголовкам Symfony, которые не являются публичным контрактом.
- **Python читает таблицы модулей напрямую.** Обходит Facade, и Deptrac
  этого не увидит. Представления дают ту же скорость и остаются
  контрактом под ревью.
- **Python читает данные через HTTP API PHP.** Лимит 200 строк на страницу
  (§5) и гидрация JSON на объёмах истории продаж — расточительно,
  а изоляцию даёт и RLS.
- **Отдельная база на сервис.** Репликация фактов между базами, второй
  бэкап и рассогласование — без выгоды на нашей стадии.
- **Отдельные репозитории.** Контракт таблицы и код сервиса должны
  меняться в одном PR; в разных репозиториях это невозможно.

### Последствия

**Получаем:**

- Конкурентность загрузки ограничена лимитом Ozon, а не числом
  PHP-процессов и памятью сервера.
- PHP-воркеры занимаются разбором и расчётами и не простаивают в сети.
- Прогноз поставок на стандартных библиотеках с эталонами для сверки.
- Изоляция арендаторов для новых сервисов — на уровне базы (RLS):
  сильнее, чем договорённость в коде.

**Платим:**

- Три языка и три набора тулинга, CI, образов и правил у команды
  из одного человека. Каждое обновление зависимостей — втрое.
- Распределённая отладка загрузки: задание проходит PHP → Go → PHP.
  Обращение «не сходится за 15 июля» требует связки по `job_id`
  в логах двух процессов.
- Мастер-ключ шифрования учётных данных во втором процессе.
- Логика лимита и раскладки ключей сырья существует на двух языках
  до конца перехода — и навсегда, если проба ключей останется в PHP.
- Правила проекта (CLAUDE.md, patterns.md, шаблон ревью) нужно
  переписать для Go и Python; модели генерируют на них код в другом
  стиле, и ревьюер должен знать правила каждого языка.
- RLS — новый механизм в проекте; его надо тестировать так же строго,
  как подписчики изоляции.

**На что обратить внимание потом:**

- Задания в `pending` дольше 15 минут при отсутствии пауз лимита —
  узким местом стал не Go, а разбор в PHP или лимит Ozon; Go-сервис
  не масштабируется дальше, смотреть на воркеры разбора.
- Расхождение фактов после перевода отчёта на Go — откат типа отчёта
  и разбор до продолжения перехода.
- Появление второй площадки (Wildberries) — проверить, что граница
  «Go загружает, PHP разбирает» держится, а не тянет разбор в Go.
- Python-сервис просится в задачи кроме прогноза (отчёты, витрины) —
  это новый ADR, а не расширение молча.
- Если через полгода после принятия Python-прогноз так и не дошёл
  до экрана — вопрос об отказе от Python ставится заново.

### Открытые вопросы — закрыть до принятия

1. **Проба ключей при подключении** (`ConnectOzonAccountAction`) —
   синхронный вызов из HTTP-запроса пользователя. Варианты: оставить
   в PHP как документированное исключение с общим форматом ключей лимита
   в Redis; или сделать подключение асинхронным (задание пробы в Go,
   экран ждёт результат) — это изменение контракта API, используемого
   фронтендом.
2. **Рекламный API** (ADR-026): его отчёты асинхронные (запрос →
   статус → выгрузка). Переводится ли он в Go вместе с Seller API или
   отдельным этапом.
3. **Модуль прогноза поставок** — имя, границы, зависимости: отдельный ADR
   до первой строки Python.
4. **Замеры из «Контекста».** Без них раздел «Альтернативы» не доказывает
   отказ от масштабирования PHP.
