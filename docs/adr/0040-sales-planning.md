## ADR-040: Планирование продаж — модуль SalesPlanning, план по SKU и дням

**Дата:** 2026-10-17
**Статус:** Accepted
**Модуль:** SalesPlanning (новый); Ingestion — только новый метод Facade
**Уточняет:** ADR-008 и ADR-011 (модуль «Planning», упомянутый там как
будущий, — это SalesPlanning; требования версии и журнала применяются
к нему без изменений), ADR-016 (второй потребитель `IngestionFacade`)
**Не меняет:** ADR-004, ADR-006, ADR-009

### Контекст

Контроль план-факт продаж — один из трёх функциональных блоков продукта
(ADR-001). Факт есть давно, плана нет. Первый этап — только ввод
и хранение плана; сравнения с фактом в нём нет (`docs/plan/sales-planning-stage0.md`).

Чем план отличается от всего, что проект хранит до сих пор:

- **Его вводит человек.** Как и себестоимость (ADR-013), и отсюда версия,
  журнал и вопрос «что стояло до правки».
- **Он про будущее, а не про прошлое.** Площадка его не знает
  и перевыпустить не может; источник истины — только наша база.
- **Его зерно — SKU × день,** а период выбирается под задачу: день,
  неделя, месяц, сезон 3–4 месяца. Хранимое зерно одно; период —
  способ ввода и чтения.
- **Он однозначен.** На один SKU в один день действует один утверждённый
  план, иначе на вопрос «сколько планировали 15 июля» два ответа,
  и будущее сравнение с фактом считает неизвестно что.

### Решение

**1. Модуль `SalesPlanning`.** Новый модуль, папка появляется вместе
с первой задачей (этап 0.2), не раньше. Таблицы — с префиксом `sales_plan`.

**2. Зависимости.**

```
SalesPlanning → Identity → Shared        IdentityFacade: подключение компании, журнал
SalesPlanning → IngestionFacade          только чтение каталога SKU подключения
```

Ingestion о планах не знает и знать не будет — обратного вызова нет,
как в ADR-016. Будущее сравнение с фактом пойдёт тем же путём:
агрегаты продаж читаются через `IngestionFacade`, а не SQL-соединением
таблиц двух модулей, которого Deptrac не видит.

**3. Модель.**

`sales_plan` — шапка, одна строка на версию плана:

```
id, company_id, marketplace_account_id, name, date_from, date_to,
currency char(3), status, lineage_id, version_number,
created_by, created_at, approved_by, approved_at, version
```

`sales_plan_line` — строки, плотные: каждый SKU плана имеет строку
на каждый день периода, в том числе с нулём штук.

```
PK id (UUIDv7)
UNIQUE (company_id, sales_plan_id, sku, plan_date)
quantity int ≥ 0, price_minor bigint > 0
```

Ключ — суррогатный, естественный — уникальным индексом. Запрет
суррогата (CLAUDE.md §2) написан для фактов, а строку плана пишет ORM:
дата в составном идентификаторе Doctrine не превращается в ключ
карты идентичности, и это тот же выбор, что у себестоимости (ADR-013).

Выручка плана (`quantity × price`) вычисляется при чтении и не хранится:
хранимое произведение рано или поздно разошлось бы с множителями.
Неделя, месяц и весь план — сумма дней при чтении.

Период плана задаётся при создании и не меняется: другой период —
другой план.

**4. Артикул — SKU площадки в пределах подключения.** Тот же тип
и тот же смысл, что `marketplace_sku` у фактов и каталога, — будущее
сравнение соединяет их без перевода. Выбор и импорт проверяются
по каталогу подключения через `IngestionFacade` двумя методами:
поиск SKU для выбора — страница с лимитом (CLAUDE.md §5); проверка
набора — список SKU целиком одним запросом, как `listingSnapshotsAt`
(ADR-016), без обхода страниц и без запроса на SKU. Пропажа SKU
из каталога позже план не ломает. Переход на артикул продавца — при появлении второй
площадки, отдельным решением.

**5. Дата — календарный день в часовом поясе площадки** (для Ozon — МСК,
ADR-009). Та же шкала, что бизнес-дата факта продаж; иначе план
и факт одного дня окажутся разными сутками.

**6. Деньги.** Цена — РРЦ за штуку, `Money` в минорных единицах (ADR-004).
Валюта одна на план и хранится колонкой шапки: план в двух валютах
невозможен структурно, а не проверкой. `Money` строки собирается
из `price_minor` строки и `currency` шапки.

**7. Раскладка периода по дням.** Пользователь вводит по SKU штуки
за период и цену. Штуки — целые: `base = floor(total / days)`, остаток
`r` — по одной штуке первым `r` дням. Сумма дней строго равна
введённому. Цена не делится — копируется в каждый день. После раскладки
любой день черновика правится отдельно; итог периода — сумма дней.
Профили (дни недели, сезонность) — следующие этапы, тем же контрактом:
меняется только правило раскладки.

**8. Статусы и версии.**

```
draft ──утвердить──► approved ──новая версия утверждена──► superseded
  │                     │
  └─отказаться─► discarded   └─отменить─► cancelled
```

- Шапки не удаляются никогда — ни одного статуса. Отказ от черновика —
  `discarded`, строки остаются: прежние значения не теряются (п. 10).
- `draft` — единственный правимый статус. В нём можно ввести SKU
  за период, поправить день и убрать SKU из плана целиком.
- `approved`, `superseded`, `discarded`, `cancelled` не правятся.
- Правка утверждённого — копия в новый `draft` той же линии
  (`lineage_id` — id первой версии, `version_number + 1`). В новой
  версии SKU можно убрать: утверждение освободит его дни.
- Отмена утверждённого (`cancelled`) — способ освободить дни плана,
  утверждённого по ошибке. В той же транзакции освобождаются дни (п. 9)
  и открытый черновик линии уходит в `discarded`. Линия после отмены
  закрыта: планировать снова — новым планом.
- Все переходы — условные обновления по статусу и версии, и все,
  что касаются линии, идут через **шапку её утверждённой версии**:
  создание новой версии, утверждение новой версии и отмена обновляют
  эту шапку первым шагом транзакции (`WHERE status = 'approved'`
  и ожидаемая версия). Так три операции сериализуются на одной строке:
  проигравшая находит шапку уже не `approved` или с другой версией
  и откатывается. Черновик в закрытой линии появиться не может.
- В линии не больше одного `draft` и одного `approved` — частичные
  уникальные индексы `(company_id, lineage_id) WHERE status = …`.
- Утверждение новой версии в одной транзакции переводит прежнюю
  в `superseded` и освобождает её дни (п. 9).

**9. Запрет пересечения — таблица занятых дней.**

```
sales_plan_day_claim
PK (company_id, marketplace_account_id, sku, plan_date)
sales_plan_id
```

Утверждение — `INSERT … SELECT` строк плана с `ON CONFLICT DO NOTHING`
и сверка числа вставленных строк с числом строк плана. Меньше — день
занят другим утверждённым планом: откат, ответ со списком конфликтов.
Проверки «занято ли» перед вставкой нет: два параллельных утверждения
прошли бы её оба (CLAUDE.md §4). Уникальный ключ сериализует их сам.

Та же таблица отвечает на вопрос «какой план действует на SKU в день» —
будущее сравнение с фактом читает её, а не ищет утверждённый план
перебором статусов.

**10. Версия и журнал.**

*Версия.* Оптимистичная версия — на шапке (ADR-008); шапка — граница
согласованности. Любая правка строк в той же транзакции явно
увеличивает версию шапки: ORM сам её не повышает, если изменились
только строки. Каждый запрос на изменение — правка, утверждение,
отказ, отмена — несёт ожидаемую версию плана. Утверждение начинает
транзакцию с обновления шапки по версии: параллельная правка строк
либо ждёт его и падает на версии, либо закоммичена раньше — и тогда
на версии падает утверждение. План не может быть утверждён
без дней, добавленных в него параллельно.

*Журнал* (ADR-011, «планы правятся на месте — журнал, без вариантов») —
через `IdentityFacade::recordAuditEntry`. Запись — на каждое действие
пользователя по каждому затронутому SKU: ввод SKU за период, правка
дня, удаление SKU из черновика, утверждение, отказ, отмена.
«Было» и «стало» хранят **точные значения дней** этого SKU до и после
действия (дата, штуки, цена) — не итог периода: после ручных правок
дней итог прежнюю раскладку не определяет. Каждая запись
самодостаточна: что ввёл пользователь, читается из неё самой,
без следующей записи и текущей таблицы. Это не больше 184 значений
на сторону.
Переходы статуса пишут «было/стало» статуса: строки при них не меняются.

Журнал заводится с первым сценарием, правящим план (этап 0.4),
а не отдельным этапом после.

**11. Запись.** Данные вводит человек — ORM (CLAUDE.md §6), со сбросом
порциями. Исключение одно — занятие дней (п. 9): `ON CONFLICT` ORM
не выражает, и это тот же приём, что первичная вставка `short_link`
в ADR-022.

**12. Изоляция.** Все составные ключи и индексы — `company_id`
первым столбцом; маршруты — `/api/companies/{companyId}/sales-plans/…`.
Межарендаторных чтений в модуле нет.

**13. Лимиты.** Период — до 184 дней, SKU в плане — до 1000. Третий
лимит — **строк на версию** (SKU × дни): создание плана, ввод SKU
и копия версии пишут строки через ORM в одном HTTP-запросе, и он
обязан укладываться в синхронный бюджет (`patterns.md`, «меньше двух
секунд»). Значение строкового лимита задаёт замер на этапе 0.4,
а не оценка; до замера действует 30 тыс. строк. Константы, обратимы;
превышение — 422.

Если замеренный лимит окажется мал для реальных каталогов, путей два,
и оба — отдельным решением владельца, не правкой реализации:
копия версии и раскладка через DBAL `INSERT … SELECT` (второе узкое
исключение из ORM-записи, по образцу ADR-022) или асинхронный сценарий
(новое сообщение очереди).

### Альтернативы, которые отвергли

- **Положить планы в Ingestion, как себестоимость (ADR-013).** Себестоимость
  читает сам расчёт юнит-экономики внутри Ingestion; план Ingestion
  не нужен ни для чего. Ingestion собирает то, что отдаёт площадка;
  смешивание связало бы цикл загрузки с циклом ввода и раздуло модуль,
  который и так самый большой.
- **Хранить ввод (SKU × период), а дни вычислять.** Ломается на первой
  правке отдельного дня (акция с другой ценой) и на пересечении планов
  разной длины: «занятость» пришлось бы считать по диапазонам.
- **Хранить выручку плана.** Производная величина, расходится
  с множителями при первой правке.
- **Запрет пересечения проверкой перед утверждением** — запрещено §4.
- **Exclusion constraint по диапазону дат на шапке.** Пересечение здесь —
  по SKU и дню, а не по периоду плана: два плана на один месяц
  с разными SKU законны.
- **Частичный уникальный индекс на строках утверждённых планов.**
  Требует статуса в каждой строке и переписывания всех строк версии
  при каждом утверждении и вытеснении.
- **Валюта в каждой строке.** Допускает план в двух валютах, который
  потом пришлось бы запрещать проверкой.
- **Физическое удаление черновика и журнал итогами.** Удалённые строки
  с ручными правками дней не восстанавливаются ни из таблицы, ни
  из итога периода в журнале — это потеря прежнего значения,
  которую запрещает ADR-011.
- **Утверждённый план без отмены.** План, утверждённый по ошибке,
  занимал бы дни SKU навсегда.
- **Артикул продавца вместо SKU площадки.** Нужен при второй площадке,
  сегодня — лишний перевод в каждом соединении с фактами.

### Последствия

**Получаем:**

- зерно плана совпадает с зерном факта (SKU × бизнес-дата) — сравнение
  на следующем этапе пишется соединением, без пересчёта;
- однозначный действующий план, гарантированный ключом в базе;
- история без удаления: что планировали на момент утверждения,
  восстанавливается всегда;
- границы модулей проверяет Deptrac: `SalesPlanning` видит Ingestion
  только через Facade.

**Платим:**

- плотные строки, и каждая новая версия копирует их целиком —
  отсюда строковый лимит версии (п. 13) уже лимитов по SKU и дням;
- занятые дни дублируют строки утверждённых планов;
- брошенные черновики остаются строками (`discarded`) и растят таблицу;
- у `IngestionFacade` второй потребитель.

**На что обратить внимание потом:**

- строковый лимит версии мешает реальному каталогу → решение
  владельца по п. 13;
- строк `sales_plan_line` > 20 млн или утверждение > 5 с → хранить
  только отличия версии или партиционировать по компании;
- понадобилось планировать по артикулу продавца на двух площадках →
  отдельный ADR, ключ строки меняется;
- понадобился вызов из Ingestion в SalesPlanning → останавливаться:
  зависимость односторонняя.
