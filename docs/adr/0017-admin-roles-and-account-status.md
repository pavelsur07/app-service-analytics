## ADR-017: Роли администраторов и блокировка аккаунта клиента

**Дата:** 2026-08-29
**Статус:** Proposed
**Модуль:** Identity
**Уточняет:** ADR-007, ADR-011

### Контекст

Раздел Admin — системный контур управления сервисом целиком (не отдельной
компанией). Первая функция — управление аккаунтами: регистрация нового
клиентского аккаунта, блокировка, включение. Контроль оплат откладывается
полностью — модели биллинга в проекте нет, отдельная задача в будущем.

ADR-007 уже развёл контур администраторов от контура продавца (свой
firewall, своя таблица), но не различал роли внутри него, и любые
чувствительные учётные записи заводились только консольной командой.
Сейчас нужно первое разделение: `SuperAdmin` остаётся bootstrap-ролью,
`Admin` — операционной, для повседневного управления аккаунтами.

### Решение

**Роль администратора** — поле `role` (`ADMIN` | `SUPER_ADMIN`) на
существующей сущности администратора. `SuperAdmin` создаётся только
консольной командой, без UI-пути — ни для первого, ни для последующих.
`Admin` создаётся через форму, доступную только `SuperAdmin`. Права
разведены через `role_hierarchy` (`ROLE_SUPER_ADMIN: [ROLE_ADMIN]`) и
Voter'ы на конкретные действия (управление администраторами — только
`SuperAdmin`; управление аккаунтами клиентов — обе роли).

**Статус аккаунта** — поле `status` (`active` | `blocked`) на `Company`.
Переходы — явные доменные методы, не общий сеттер (`block(reason)` /
`activate()`), инвариант тот же, что и у остальных сущностей проекта.
Проверка статуса встраивается в уже существующую точку проверки членства
в компании (ADR-002: контекст компании явно в URL, не в сессии) —
блокировка действует немедленно на следующий же запрос, отдельного сброса
сессий в Redis не требуется.

**Аудит-журнал** — заводится таблица журнала (первая фактическая
реализация требования ADR-007/ADR-011), пишется минимум для: регистрация
аккаунта, блокировка, включение, создание `Admin`. Формат «было/стало»,
актор, время — по правилу ADR-011 (переходы обратимы, значит журнал
обязателен, признак из ADR-011 соблюдён явно).

**Кросс-тенантное чтение** списка аккаунтов для админки — существующее
исключение CLAUDE.md §1 («операционные системные задачи»), не новое.
Реализуется как отдельный именованный Query, недостижимый из Ui продавца
по Deptrac, с docblock-ссылкой на правило.

**Оплата** — не моделируется в этой задаче. Поле `status` у `Company` —
единственный крючок, который может понадобиться будущему биллингу; сама
интеграция получает свой ADR, когда появится.

**Модуль** — новый не заводится. Всё живёт в `Identity`, который уже
владеет `Company`, `User`, сущностью администратора и аутентификацией.

### Альтернативы, которые отвергли

- **Полноценная система разрешений (`Role`/`Permission` таблицы)** —
  отвергли: для двух статичных ролей это абстракция без второго случая;
  `role_hierarchy` + Voter'ы дают то же самое без новой схемы.
- **Отдельный backend-модуль `Admin`/`Ops`** — отвергли: нет своей
  предметной терминологии, все сущности уже принадлежат `Identity`.
- **Сброс сессий в Redis при блокировке** — отвергли: компания и так
  проверяется на каждом company-scoped запросе, докидывать проверку
  статуса в ту же точку дешевле.
- **Контроль оплат в этой же задаче** — отвергли: модели биллинга нет ни
  в одной ADR, это отдельный bounded context.

### Последствия

**Получаем:** минимальная ролевая модель без лишней машинерии; блокировка
работает сразу, без специальной инвалидации сессий; кросс-тенантное
чтение в админке следует уже согласованному правилу.

**Платим:** задача физически включает первую реализацию аудит-журнала —
это больше, чем «добавить два поля». Открыт вопрос оптимистичной
блокировки на `Company.status` — решается на этапе реализации после
проверки текущего кода `Company` (см. Stage 4 задания).

**На что обратить внимание потом:** третья роль или гранулярные права →
переходить от `role_hierarchy` к явным Voter'ам на каждое действие (уже
введены здесь) и только тогда — к permission-таблице; интеграция оплат
получает свой ADR и не должна писать в `Company.status` в обход доменных
методов, введённых здесь.
