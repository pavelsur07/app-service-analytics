# ADR-052: Озон Ads — наблюдение и управление расходами рекламы

**Дата предложения:** 08.11.2026.
**Статус:** Accepted для observe 00–08 и UI этапа 10, стендовых проверок 11 по прямым поручениям владельца от 08.11.2026; управление рекламой — Proposed.
**Область:** предлагаемый модуль Advertising, Go-сервис ozon-ads-controller,
Identity, сервисные контракты, seller UI.

Владелец поручил реализацию «Первый выпуск 00–08 автономно и останавливаемся
проверяем». Это принимает нижеописанные границы наблюдения и подготовительный
расчёт; не допускает реальное управление или живую выкладку этапа 12. Последующее
поручение «действуй дальше» разрешает продолжение интерфейса наблюдения:
[объём и приёмка этапа 10](../plan/ozon-advertising-stage10-implementation.md).
Незакрытые доказательства этапов 02/04 продолжаются отдельно, не объявляются SLA.
Продуктовые D1–D5/U1 сохраняются. Исполнитель и право записи остаются Proposed.
Точный срез реализации и исключения — [отчёт 00–08](../plan/ozon-advertising-00-08-implementation.md).

## Контекст

Нужна стратегия «Контроль затрат»: дневной лимит и ежедневное окно работы
существующей кампании Ozon. Контроль должен обслуживать несколько кабинетов
и выдерживать задержки/отказ общей очереди. Нельзя обещать точное ограничение
суммы только на основании быстрого HTTP-ответа: расход источника может отставать,
а команда остановки — иметь неопределённый исход.

В исследовании первого клиента сохранены первоначальные шесть ответов и
следующий набор из 60. Подтверждены синхронные агрегат/SKU и асинхронная цепочка
submit → status → download. Есть устойчивые межисточниковые различия. Свежесть
данных, квоты и задержка фактической остановки — разные свойства.

## Решения, выбранные владельцем

| ID | Решение | Граница применения |
|---|---|---|
| D1 | Агрегированный JSON с явными датами — основной источник; SKU — сверка; асинхронные отчёты — история | Выбранные и проверенные CPC-сценарии |
| D2 | Для защиты брать большую сопоставимую сумму и хранить расхождение | Одна кампания/день/валюта/НДС/состав расходов; источники не складываются |
| D3 | Защита бюджета важнее полного расходования | Ранняя остановка допустима; утрата контроля запрещает start и требует stop в пределах права |
| D4 | Кампания без достаточной истории сначала наблюдается | Автоматический start только после пригодной основы оценки запаса |
| D5 | После смены суток ждать пригодных данных, не считать пропуск нулём | Готовность внутри окна → новый preflight; вне окна → без старта |
| U1 | Один пункт основного меню «Озон Ads», страницы внутри через Tabs | Кампании, Стратегии, История действий, Настройки |

Численный резерв квоты 30%, интервалы из расчёта и профиль пилота 1 → 3 → 10
не объявляются отдельными утверждёнными решениями владельца. Это параметры
предложения для проверки, с источниками и допущениями в документах ниже.

## Предлагаемая архитектура

### 1. Владение и зависимости

- PHP-модуль Advertising: политики, версии, права, пользовательский аудит,
  seller API и проекция исполнения. Слои Domain/Application/Infrastructure/Ui.
- Go-сервис `services/ozon-ads-controller`: оперативные чтения, сохраняемый
  планировщик, расчёт решений и, после отдельного допуска, исполнитель команд.
- Identity владеет подключениями/ключами. Доступ Advertising — только через
  разрешённый Facade; конкретные методы и узкие границы Deptrac фиксируются
  в пакете этапа 05 до реализации. Прямого доступа к таблицам Identity нет.
- Ingestion/ozon-fetcher остаются контуром истории в существующих границах.
  Их коннектор не получает права управления, новый сервис не расширяет их задачи.
- Сервис имеет собственную БД и роль без доступа к БД Conwix. UI говорит только
  с PHP; пользовательский запрос не вызывает Go синхронно.
- Чтения/намерения и runtime доставляются по версионированным контрактам
  `services/_contracts/`; межсервисные токены разделены по направлению.

Доступ сервиса к выдаче подключений — сервисный контур CLAUDE.md §1, отдельные
firewall/внутренние маршруты и точные границы классов контроллера/запроса.
Это не общее межарендаторное разрешение для пользовательских сценариев.

### 2. Доставка и критический путь

Оперативный путь «прочитать → решить → отправить → сверить» не зависит от
Messenger и очереди истории. Дедлайны сохраняются в БД Go, таймеры восстанавливаются
после рестарта. Нужны приоритет stop, ресурсный резерв и запрет новых start
при нехватке ёмкости. Другой кабинет не блокируется ожиданием одного API.

PHP атомарно сохраняет намерение и изменение доставки, Go применяет версию
до подтверждения. Потеря ack и перестановка версий безопасны. Отключение
доставляется явно; частичная выдача не заменяет полный набор. До кода выбрать
snapshot/delta-протокол, не теряющий поздние commit, и полную пересинхронизацию.
Доставка at-least-once; exactly-once внешнего HTTP не обещается.

PHP получает результаты фоновым обменом и отдаёт локальную проекцию UI.
Сохранённая настройка отличается от применённой. Контрактная ошибка не
превращается в частично применённую политику.

### 3. Деньги и данные

Применяется ADR-004: Money, целые минорные единицы и валюта, явное округление,
никаких float в промежуточной денежной арифметике. UUIDv7 генерируются приложением,
PostgreSQL uuid; внешние ID — строки без потери точности JavaScript Number.

Оперативные наблюдения содержат scope компании/кабинета/кампании, отчётный день,
источник, fetched_at, nullable source watermark, сумму, валюту, денежную базу
и качество покрытия. История источника не подменяется техническим временем HTTP.

Предлагается ограниченное расширение правил первой волны сервисов только для
нового контроллера: расчёт/хранение оперативных денежных наблюдений и передача
настроек/денежной проекции по внутренним контрактам. Сейчас services/AGENTS.md
ограничивает такие вычисления/ответы; до принятия ADR это расширение не действует.
При принятии должны быть согласованно обновлены применимые правила и границы
контрактов, без распространения исключения на ozon-fetcher и другие сервисы.

Секреты не хранятся в БД, логах, фикстурах и трекере. Деньги/тела ответов не
попадают в технические логи. Предметный аудит и сроки хранения каждого типа
определяются до соответствующей миграции. Человеческие настройки PHP — ORM;
оперативные наблюдения Go — явные SQL с ограничениями ключей и безопасным повтором.
Пользовательские списки — нужные колонки/DTO, лимит и keyset для истории.

### 4. Решение по бюджету

После проверки сопоставимости C = max(расход агрегата, сумма пригодных SKU,
ранее принятый C этого дня). Дубли не увеличивают SKU-сумму; частичный ответ
не считается полным. Финансовая коррекция вниз хранится отдельно и не
возобновляет расходы автоматически.

Запас R оценивает возможные расходы за горизонт данных/опроса/повторов/stop/
восстановления с резервом неопределённости и округлением вверх. При C >= B − R
требуется stop; без пригодного R и остатка start запрещён. Неизвестный лаг
источника не превращается в доказанную границу риска. Точные правила — в ТЗ.

Окно полуоткрытое: start включительно, stop исключительно. Повышение лимита
после стопа само не делает resume. Новый день не снимает ручную/защитную блокировку.

### 5. Квоты и интервалы

Числа сохранены из переданного владельцем раздела Limits: общий HTTP —
100000/сутки, выгрузки — min(активные кампании × 240, 2000), одна одновременно
на аккаунт и пять на организацию, потолок 2000/24 ч также у организации.
Batch учитывается по числу кампаний. Квоты операций управления ведутся отдельно.

Из определения метода нужно установить исключения оперативного агрегата/SKU;
синхронность сама по себе не означает освобождение. Scope, reset и определение
«активной» ещё уточняются. Реплики и ключи одного кабинета не получают каждый
полный независимый остаток. Управляющие квоты бюджета/стратегии не переносятся на stop.

X рассчитывается по самому строгому счётчику с прочими потребителями и резервом.
Обычный опрос не обходится вкладками, браузером или рестартом. Предложенные
минутные профили и их допущения находятся в отдельном расчёте; это не SLA Ozon.
Расписание stop и уже принятое решение не ждут X; запас учитывает интервал опроса.

### 6. Полномочия, конкуренция и команды

Компания и кабинет передаются явно. Право просмотра не даёт управление.
Нужна подтверждённая привязка внешнего кабинета и один управляющий владелец
кампании независимо от числа ключей. Эвристика совпадения SKU из ADR-026
не заменяет доказательство принадлежности для записи. Неоднозначность блокирует её.

Аренда имеет generation; перед HTTP проверяются право, версия и владение.
Намерение сохраняется до сети. Потерянный ответ — unknown и сверка, а не
слепой повтор. Новый владелец сначала разбирает неопределённые операции.
Поздний start при desired stopped компенсируется stop в пределах полномочий;
внутренний fencing не объявляется поддержкой fencing со стороны Ozon.

Плановое отключение сначала останавливает и сверяет кампании, экстренный отзыв
права немедленен и не задерживается ради stop. Неподтверждённый исход остаётся
видимым, даже если ключ больше не работает. Права не обходятся ради безопасности бюджета.

## Два выпуска и допуск

**Observe первым:** реальные разрешённые чтения, качество данных, настройки
расчёта, предполагаемые решения, четыре Tabs. Коннектор блокирует все операции
изменения рекламы, включая GET с эффектом; разрешённые token/report POST
не блокируются только из-за HTTP-глагола. Прямой API не создаёт рабочую команду.
Пользователь видит, что автоматической защиты ещё нет. Неизвестные величины
показываются честно. Проверки доступа, квот, CI и независимое ревью обязательны.

**Control позднее:** после закрытия условий допуска, реализации/проверки
исполнителя и явной активации выбранных политик с новым preflight. Старые
предполагаемые решения не исполняются. Этап пилота отдельно измеряет реальные
задержки. Возврат control → observe начинается с запрета start и сверки stop;
unknown не считается безопасно завершённым переходом.

Q1–Q7 не закрываются наличием ADR: полнота/новый день, scope квот, запас,
идентичность кабинета, актуальные команды, численный риск и watermark остаются
с проверками и статусами в ТЗ. Их открытость не мешает подготовке reader/UI
на фикстурах после принятия соответствующего объёма, но блокирует зависимый допуск.

## Отвергнутые альтернативы и последствия

- Общая очередь для остановок: задержка/отказ очереди создаёт неконтролируемый риск.
- Три сервиса «чтение/решение/команда»: добавляют сетевые зависимости критическому пути.
- Расширить существующий загрузчик до управления: размывает ADR-026/043 и права коннектора.
- Считать пустой ответ нулём или доверять меньшему расходу: противоречит D2/D5.
- Исполнять накопленные решения observe: они устаревают и не являются командами.
- Принять фиксированные 10% или 6 минут за гарантию: ни одна такая гарантия не доказана.

Цена решения — собственное состояние/миграции, координация квот, наблюдаемость,
контракты и восстановление. Ранняя остановка/недорасход — допустимый результат D3.
Сбой всего Conwix/Ozon не устраняется заменой очереди; ограничение площадки
остаётся единственной внешней защитой, если оно существует для выбранного режима.

## Условия принятия и пересмотра

Для принятия соответствующего объёма: завершить архитектурный пакет этапа 05,
разобрать независимое ревью, определить точные границы изменений правил/контрактов
и зафиксировать решение владельца. Принятие observe не принимает незакрытый control.
Этот документ не запускает миграцию, merge или выкладку.

Пересмотр нужен при смене денежных источников/базы, схемы полномочий, области
квот, переходе к общей сумме нескольких кампаний, автоматическому bootstrap,
новому типу рекламы либо новым межмодульным зависимостям. Изменение принятого
необратимого решения оформляется следующим ADR, не молчаливой правкой.


## Реализация observe 00–08: точные границы

- Новый Advertising зависит от Identity только через company-scoped
  `IdentityFacade::findOzonAdvertisingTarget/recordAuditEntry`. SQL к Identity нет.
- Операционная выдача политик: ровно `ObservationConfigurationController` →
  `ServiceObservationPoliciesQuery`; оба исключены из широких слоёв Deptrac.
  Это существующий сервисный случай §1, не разрешение всем seller-контроллерам.
- Политики и подтверждённая проекция в PHP; отдельная БД/роль `svc_ozon_ads`
  у Go. Ключи выдаются существующим marketplace-connections v1, не пишутся в БД.
- Исключение к первой волне ADR-043: только ozon-ads-controller разбирает
  расходы в Money, вычисляет max/расхождение/оценку запаса и хранит нормализованный
  runtime. ozon-fetcher эти права не получает. Денежные поля имеют bigint/
  currency; JSON-контракты содержат целые minor units, float запрещён линтером.
- В PHP используется существующий Shared Money (уточнение владельца в ходе
  реализации); новый денежный VO для PHP не вводится.
- Контракт `ozon-ads-observe/v1`: полная ограниченная выдача, атомарная замена,
  монотонная версия, TTL 120 с; обратная проекция текущего состояния без
  синхронного обращения PHP к Go из пользовательского запроса.
- Никакого исполнительного задания: только `would_run/would_stop/blocked`.
  Модель операции/исполнитель этапа 09 не создаются ради будущего использования.
- Raw-ответы работающего сервиса не сохраняются: собственной S3-конфигурации
  в 00–08 нет; проверенные исследовательские ответы остаются fixtures.
- Интервал минимум 600 с, 10 политик на кабинет, 10 000 на полную выдачу,
  квота сервиса 70 000 HTTP/24 ч. Это консервативные технические ограничения
  observe, не доказанный паспорт нагрузки и не квота всех потребителей Ozon.
- Живое включение запрещено до координации общих квот и приёмки 11/12.
  Резерв в рабочем observe неизвестен; контроль расходов не обещается.

## Продолжение: стенд observe этапа 11

Поручение владельца «продолжай» после этапа10 допускает стендовые проверки,
выделение штатного bounded worker loop для воспроизводимой нагрузки,
clock-step guard и закрытую операционную диагностику каждой кампании.
Новые публичные API/межмодульные связи/БД/очереди/зависимости не вводятся.
[Паспорт до замеров](../plan/ozon-advertising-stage11-passport.md),
[матрица, результаты и оставшиеся гейты](../plan/ozon-advertising-stage11-implementation.md).
Пороги5/35с относятся только к синтетическим профилям и не допускают live.
Общая квота других потребителей, host failover/clock calibration/production
watcher остаются незакрытыми. Право управления рекламой этим не расширяется.
