## ADR-043: Загрузка Ozon отдельным Go-сервисом `ozon-fetcher`

**Дата:** 2026-10-24
**Статус:** Accepted (2026-10-24)
**Модуль:** Ingestion (только выдача подключений), новый `services/ozon-fetcher`,
инфраструктура
**Пересматривает:** ADR-001 — отказ от отдельного сервиса ingestion
**Затрагивает:** ADR-007 (ключи подключений покидают PHP-процесс),
ADR-024 (второе хранилище сырья), ADR-028 (второй источник запросов
к Ozon с тем же Client ID)
**Не меняет:** загрузку, разбор и факты в PHP (ADR-006, 009, 034, 038, 042) —
на время этого ADR они работают как работали
**Не решает:** передачу результата сервиса в PHP и переключение загрузки
на него (вторая волна, отдельный ADR); Python и прогноз поставок (отдельный
ADR вместе с модулем прогноза)

### Контекст

ADR-001 отверг отдельный сервис ingestion: «blast radius растёт, отладка
становится распределённой, продуктовой выгоды ноль». Продукт переходит
в промышленную эксплуатацию, и загрузка в её нынешнем виде не масштабируется:

- в проде один `worker-ingestion` — задания выполняются строго по одному;
- ожидание паузы лимита — `sleep()` внутри процесса
  (`OzonSellerRateLimitingClient`), воркер в это время стоит;
- конкурентность в PHP растёт только числом процессов по 112–256 МБ.

Прод Conwix под нагрузкой ещё не был, своих замеров нет. Свидетельство —
соседний продукт того же владельца, ВашФинДир (`app-service-finance`):
на той же площадке и том же устройстве загрузки — очередь по одному,
ожидание на эндпоинтах, лавины ошибок и повторов. Там с 13.10.2026 построен
Go-сервис `services/ozon-fetcher` (14 этапов, выложен в прод за allowlist
кабинетов): автономный планировщик, параллельные кабинеты, лимитер
на кабинет и endpoint с адаптацией на 429, классы ошибок, raw в S3,
журнал загрузок в своей БД.

Владелец решил (24.10.2026): внедрить такой же сервис в Conwix
**параллельно**, не трогая загрузку в PHP; PHP дорабатывается отдельно.

Решение дорого отменяемо: второй язык, второй образ, вторая БД, второй
бакет и выдача ключей всех компаний второму процессу переживают задачу.

### Решение

#### 1. Модель — как в ВашФинДир

`services/ozon-fetcher` — автономный сервис:

- сам решает, что и когда загружать (свой планировщик и журнал);
- получает подключения и ключи из PHP по внутреннему API;
- кладёт ответы Ozon как есть в свой бакет S3, постранично;
- ведёт в своей БД журнал: задачи, попытки, объекты, лимиты;
- **не пишет в БД Conwix и не читает её**, не разбирает ответы, не создаёт
  фактов, не меняет состояние подключения, не ставит отметку загрузки дня.

PHP в этой волне меняется ровно в одном месте — выдаче подключений (п. 4).
Загрузка, разбор, факты, контроль свежести и экраны остаются в PHP
без изменений и от сервиса не зависят.

#### 2. Код — перенос из ВашФинДир с адаптацией

- Источник — `app-service-finance`, `services/ozon-fetcher` и правила
  `services/AGENTS.md`, `services/go.md`, контракты `services/_contracts/`
  на коммите `a9eb74206`. Коммит-источник записывается в README сервиса.
- После переноса это **два независимых сервиса**: общего Go-модуля и общей
  выкладки нет. Исправление, найденное в одном, переносится в другой
  руками отдельной задачей.
- Адаптация к Conwix — пункты 3–8. Где правила ВашФинДир расходятся
  с правилами Conwix, действуют наши: фикстуры — побайтовые ответы
  кабинета по §9 вместо обезличенных; миграции с рабочим `down` вместо
  forward-only; деньги, если появятся, — минорные единицы и валюта
  (ADR-004) вместо десятичных строк.

#### 3. Хранение

- **БД:** отдельная логическая БД `ozon_fetcher` на том же инстансе
  PostgreSQL, роль `svc_ozon_fetcher` с правами только на неё. Доступа
  к БД Conwix у роли нет. В БД сервиса — только техническое состояние:
  задачи, попытки, объекты, лимиты. Ни денег, ни ключей, ни тел ответов.
- **Миграции** сервиса — goose, встроены в бинарник, прогон явной
  командой, не при старте. По правилам Conwix: рабочий `down` или пометка
  «откат только восстановлением»; одна миграция на задачу; проверка
  с пустой базы входит в `make db-rebuild-check`.
- **Идентификаторы:** `connection_ref` ВашФинДир заменяется парой
  `company_id` + `marketplace_account_id` (UUID из Conwix). Таблицы
  сервиса несут обе колонки; новые идентификаторы сервиса — UUIDv7.
- **S3:** отдельный бакет сервиса, отдельный пользователь хранилища
  с правами только на него. Бакет сырья PHP (ADR-024) не трогается.
  Ключ объекта начинается с компании:
  `ozon/{company_id}/{marketplace_account_id}/{resource_type}/{period_key}/…`,
  объекты неизменяемы, запись `If-None-Match: *`. Сегменты проверяются при
  сборке ключа, как в `RawObjectKey`; `company_id` и
  `marketplace_account_id` берутся из одной записи выдачи подключений.

#### 4. Выдача подключений — единственная правка PHP

`GET /api/internal/marketplace-connections` — контракт
`marketplace-connections` v1 из ВашФинДир с заменой `connection_ref`
на `marketplace_account_id`. Отдаёт активные подключения Ozon
с расшифрованными ключами Seller и Performance.

Это **межарендаторное чтение, отдающее секреты всех компаний**, и оно
входит в PHP через контроллер. Ни один из трёх случаев §1 CLAUDE.md
его не покрывает: операционная задача идёт мимо контроллера, системный
контур — экран администратора. Поэтому ADR вводит **сервисный контур**
со всеми условиями сразу:

- отдельный firewall без сессии; учётные данные — статический токен
  направления «сервис → PHP» не короче 32 символов из секретов окружения;
  сравнение за постоянное время;
- endpoint недоступен снаружи: публичные vhost nginx отвечают 404
  на `/api/internal/`, запрос принимается только с внутреннего имени
  в docker-сети `internal`;
- запрос подключений — свой DBAL-запрос с межарендаторным именем
  (`ActiveOzonConnectionsForServiceQuery`), не метод репозитория;
  ссылка на этот ADR и §1 в докблоке;
- контроллер и запрос вынесены из широких слоёв в собственные узкие
  слои Deptrac на класс; грант — только этой паре;
- в журнал и трекер не попадают ни ключи, ни тело ответа; каждое
  обращение пишется строкой аудита: время, число подключений;
- в сервисе ключи живут только в памяти, не попадают в БД, логи
  и GlitchTip; кэш обновляется поллингом, 401 от Ozon по кабинету
  форсирует обновление.

Токен направления «PHP → сервис» заводится сразу для `/internal/*`
сервиса (статус, покрытие), даже если PHP их пока не вызывает.

#### 5. Лимиты Ozon при параллельной работе

PHP и сервис ходят в Ozon с одним Client ID, и у каждого свой лимитер
(у PHP — паузы в Redis, ADR-028; у сервиса — `connection_limit` в его
БД). Общего лимитера нет намеренно: он связал бы сервис с Redis и кодом
PHP. Вместо этого:

- сервис включается за `OZON_FETCHER_CONNECTION_ALLOWLIST`, сначала
  на одном подключении, с консервативными лимитами по endpoint'ам;
- критерий расширения allowlist: число отказов лимита у PHP
  (`OzonSellerRateLimited` в журнале) за сутки не выросло относительно
  недели до включения, а отметки загрузки дня ставятся как раньше;
- выросло — сервис на этом подключении выключается до разбора.

#### 6. Наблюдаемость

- `slog` JSON: `service`, `job_id`, `trace_id`, `company_id`,
  `marketplace_account_id`, `resource_type`, `outcome`, `error_class`.
  Без ключей, тел ответов и сумм.
- Отдельный проект GlitchTip, только ERROR.
- `GET /health`, `GET /ready`, `GET /internal/fetch-status`,
  `GET /internal/coverage` (контракт `service-coverage` v1).
- Контроль свежести Conwix не меняется: он смотрит на загрузку PHP.

#### 7. Репозиторий, CI, выкладка

```
services/
  AGENTS.md            правила всех сервисов (адаптация из ВашФинДир)
  go.md                правила Go
  _contracts/
    marketplace-connections/v1/
    service-coverage/v1/
  ozon-fetcher/        cmd/, internal/, test/, go.mod, docker/Dockerfile
  docker/postgres/     init dev-БД сервиса
```

- Go — версия из ВашФинДир (1.27), пин в `go.mod`; образы без `latest`.
- Dev: compose-профиль `services`, мок Ozon вместо `api-seller.ozon.ru`;
  реальных ключей в песочнице нет, как и для PHP.
- CI блокирует merge: `gofmt`, `go vet`, `golangci-lint`, `go test -race`,
  `govulncheck`; проверка ответа выдачи подключений по JSON Schema
  контракта — и в PHP-тесте, и в Go-тесте. `bin/ci-classify-paths`
  получает флаг `services`.
- Образ сервиса публикуется в ghcr только с `master`. Деплой создаёт роль
  и БД, прогоняет миграции сервиса отдельным шагом; контейнер запускается
  только при `OZON_FETCHER_ENABLED=true`. Сеть — `internal` + `egress`,
  без роутера Traefik.
- Откат — `OZON_FETCHER_ENABLED=false` и деплой, либо `docker stop`.
  Загрузка PHP от сервиса не зависит.

#### 8. Тесты

- Обязательное покрытие: изоляция (объект одной компании не пишется
  под префикс другой; выдача подключений не доступна без токена,
  с токеном другого направления и снаружи), идемпотентность записи
  страниц и захвата задач, лимитер (429 у одного кабинета не тормозит
  другие), классы ошибок.
- Парсинг ответов Ozon сервису не нужен, но разбор страниц и курсоров —
  на фикстурах. Фикстуры — по §9 CLAUDE.md, те же ответы кабинета, что
  в `api/tests/Fixtures/Marketplace/ozon`.

### Альтернативы, которые отвергли

- **Общая БД, PHP ставит задания, Go пишет raw-документы Conwix**
  (первая редакция этого ADR). Требует переделать планировщик и разбор
  в PHP — противоречит решению «параллельно, не трогая PHP» — и
  привязывает сервис к схеме Doctrine и RLS.
- **Писать сервис с нуля.** Дольше, и ошибки, уже пройденные
  в ВашФинДир (лимитер, lease, `not_ready`, `obsolete_endpoint`),
  пришлось бы пройти заново.
- **Один сервис на оба продукта.** Связал бы выкладки и данные двух
  продуктов с разными клиентами; ключи компаний одного продукта
  оказались бы в процессе другого.
- **Общий Go-модуль для двух копий.** Преждевременно до второго
  расхождения, которое захочется синхронизировать; пока — ручной перенос.
- **Go расшифровывает ключи сам** (мастер-ключ в сервисе, чтение
  шифротекстов из БД Conwix). Мастер-ключ во втором процессе и доступ
  сервиса к БД Conwix хуже одного endpoint'а с узкой границей.
- **Общий лимитер PHP и Go через Redis.** Формат ключей Redis становится
  межъязыковым контрактом ради периода параллельной работы; allowlist
  и критерий из п. 5 закрывают риск дешевле.
- **Сразу переключить загрузку на сервис.** Без периода параллельной
  работы нечем доказать, что сервис загружает то же и не хуже.

### Последствия

**Получаем:**

- Параллельная загрузка по кабинетам, ограниченная лимитом Ozon,
  а не числом PHP-процессов.
- Отчёт, который ещё не готов, — исход `not_ready`, а не ожидание
  в процессе; ошибки разделены по классам с разной реакцией.
- Одна модель сервиса в двух продуктах владельца: опыт и исправления
  переносимы.
- Загрузка PHP не меняется и не зависит от сервиса: откат бесплатный.

**Платим:**

- Второй язык, тулинг, CI, образ, БД и бакет у команды из одного человека.
- Ключи всех компаний покидают PHP: endpoint выдачи — самая дорогая
  точка утечки в системе, и его граница проверяется так же строго, как
  вход.
- Двойные запросы к Ozon на период параллельной работы.
- Две копии сервиса, расходящиеся со временем; исправления переносятся
  руками.
- Второе хранилище сырья: до второй волны raw одних и тех же ответов
  лежит в двух бакетах.
- Правила Conwix нужно расширить (ниже); до этого сервис нельзя писать
  агентом.

**На что обратить внимание потом:**

- Рост отказов лимита у PHP после включения — п. 5, выключить.
- Сервис месяц загружает все подключения без ошибок класса `auth`/
  `invalid_*` вне инцидентов Ozon — готовность ко второй волне (передача
  raw в PHP и переключение), отдельный ADR.
- Через три месяца после включения вторая волна не начата — пересмотреть,
  нужен ли сервис, или двойная загрузка стала постоянной издержкой.
- Расхождение копий в ВашФинДир и Conwix больше чем в одном исправлении
  за квартал, перенесённом руками, — вопрос об общем модуле.

### Первая волна, окна и хранение (решения владельца 24.10.2026)

**Ресурсы — пересечение** того, что сервис ВашФинДир уже загружает,
с тем, что загружает Conwix. Сверка эндпоинтов и тел запросов
на коммите-источнике:

| Ресурс | Эндпоинт | Запрос совпадает | В первой волне |
|---|---|---|---|
| Начисления по дням (ADR-038) | `POST /v1/finance/accrual/by-day` | да: `date`, `last_id` | да |
| Продажи FBO (ADR-042) | `POST /v3/posting/fbo/list` | нет: сервис не шлёт `translit: false` | да, с правкой: `translit: false`, как в PHP |
| Каталог | `POST /v3/product/list` | да: `visibility: ALL`, `last_id`, `limit` | да |
| Карточки | `POST /v3/product/info/list` | да: `product_id[]` | да |
| Рекламные кампании (ADR-026) | `GET /api/client/campaign` | да | да |
| Расход рекламы | `GET /api/client/statistics/expense/json` | период: сервис — день, PHP — окно | да, по дню |
| Дневная статистика рекламы | `GET /api/client/statistics/daily/json` | период: сервис — день, PHP — окно | да, по дню |

Вне первой волны:

- есть только в Conwix — сервису дописываются во второй волне:
  остатки по кластерам `/v1/analytics/stocks` (ADR-034; у сервиса
  другой метод, `/v4/product/info/stocks`), возвраты `/v1/returns/list`,
  товары кампании `/api/client/campaign/{id}/v2/products`, реклама по SKU
  `/api/client/statistics/products/sku` и `/api/client/statistics/json`
  (ADR-035), заказы CPO `/api/client/statistic/orders/generate/json`;
- есть только в ВашФинДир — при переносе выключаются: FBS
  `/v4/posting/fbs/list`, начисления по отправлениям, типы начислений,
  реализация, взаиморасчёты, асинхронный отчёт статистики рекламы,
  `/v4/product/info/stocks`. Код остаётся, ресурсы не планируются.
  Включить — отдельное решение.

`dir` в запросе FBO, который шлёт PHP, v3 молча игнорирует
(комментарий в сервисе ВашФинДир); расхождением это не считается.

**Окна планировщика — как в ВашФинДир:** хвост — вчера и три дня
до него ежедневно; пропуски M, M-1, M-2 — проверка ежедневно; M-1 целиком —
раз в неделю; M-2 — финальная перезагрузка 10-го числа; старше M-2 —
только по ручному запросу; первичная загрузка нового подключения —
текущий месяц, затем M-1 и M-2 (≈90 дней). Окна пересчёта ADR-006 в PHP
не меняются: сервис только набирает raw.

**Хранение raw в бакете сервиса — 90 дней** с момента записи объекта,
правилом жизненного цикла бакета. Строки журнала (`raw_object`) об
удалённых объектах остаются с отметкой. Срок пересматривается ADR второй
волны: когда PHP начнёт читать raw сервиса, хранение должно покрывать
глубокий рескан ADR-006.
