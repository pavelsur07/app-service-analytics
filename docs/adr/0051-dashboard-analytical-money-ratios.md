# ADR-051: Аналитические отношения денежных сумм

Дата: 2026-11-06. Статус: Accepted.

## Контекст

ADR-004 и CLAUDE.md §3 описывают деление денег только аллокацией.
Дашборд уже использует SQL numeric для ДРР и стоимости продажи.
Средняя цена и продажи в день требуют отношения итогов, а не распределения
исходной суммы между получателями. Владелец поручил автономную реализацию
плана docs/plan/dashboard-sales-metrics.md с этим уточнением.

## Решение

Для аналитических отношений в слое чтения разрешено точное деление
денежной суммы в минорных единицах через PostgreSQL numeric. Результат
округляется один раз до минорной единицы: половина от нуля, явно ROUND(numeric).
Нулевой знаменатель даёт null. Валюта обязательна и не смешивается.
float запрещён, включая промежуточные значения.

Это уточнение имеет приоритет над общим запретом деления вне аллокации
в ADR-004 и CLAUDE.md §3 только для аналитических отношений.
Распределение денег между SKU/получателями остаётся аллокацией через Money
с сохранением суммы. Денежные значения приложения по-прежнему представлены
Money; readonly DTO чтения и API передают целые минорные единицы с валютой сводки.

Для виджета продаж: продажи в день = сумма положительной выручки / число
календарных дней включительно; средняя цена продажи = сумма положительной
выручки / сумма quantity. Возвраты отдельны. Каждый период имеет собственные
границы. Отношения вычисляются из итогов, не из дневных средних.

## Альтернативы

- Расчёт в React: дублирует определения и денежную арифметику между клиентами.
- Аллокация: части имеют разную стоимость при остатке и не описывают среднее.
- float: не гарантирует точную арифметику и округление.
- Сохранение производных значений: создаёт необходимость их синхронизации с фактами.

## Последствия

Определения и округление централизованы на сервере. SQL-тесты должны проверять
границы периодов, знаменатели, половину копейки, валюты и изоляцию компаний.
Средняя цена единицы не называется средним чеком заказа.
