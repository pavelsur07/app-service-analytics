## ADR-008: Конкурентное редактирование

**Дата:** 2026-08-02
**Статус:** Accepted
**Модуль:** весь проект, критично для Costing и Planning

### Контекст

Часть данных редактируется людьми: себестоимость, планы продаж, настройки
подключений, справочники. Согласно ADR-002 доступ к компании имеют несколько
пользователей, а сам пользователь может работать в двух вкладках.

Сценарий потери данных выглядит безобидно: двое открывают форму
себестоимости, первый сохраняет, второй сохраняет через минуту и молча
затирает правку первого. Ни ошибки, ни записи в журнале — расхождение
обнаружится через недели при разборе «почему прибыль другая».

Для финансового продукта это хуже явного отказа: результат выглядит
корректным и ему верят.

Одновременно есть данные, где конкурентного редактирования не существует
в принципе: строки фактов пишутся только процессом загрузки и никогда
не редактируются человеком. Введение там механизма защиты означало бы
расход без выгоды.

### Решение

Редактируемые человеком сущности получают версию — целочисленное поле,
управляемое ORM и увеличиваемое при каждом изменении.
Это касается: себестоимости, планов и их версий, учётных данных подключений,
справочников и настроек компании.

Таблицы фактов и любые данные, изменяемые только процессом загрузки,
версии не получают. Их согласованность обеспечена правилами ADR-006.

**Сквозной контракт.** Версия входит в ответ на чтение сущности и обязательна
в запросе на изменение. Запрос без версии отклоняется; принимать изменение
«без версии» как безусловное запрещено — это возвращает исходную проблему.

**Конфликт версий** приводит к отдельному коду ответа и сообщению
о том, что данные изменил другой пользователь. Интерфейс предлагает
перечитать и повторить, но не выполняет слияние автоматически.

**Пессимистическая блокировка не применяется.** Блокировок на уровне
строк БД на время работы пользователя с формой не берём.

Отдельно от этого: изменение себестоимости и планов попадает в аудит-журнал
согласно ADR-007. Версия защищает от потери правки, журнал отвечает
на вопрос, кто и когда её сделал.

### Альтернативы, которые отвергли

- **Ничего не делать, последняя запись побеждает** — отвергли: молчаливая
  потеря данных в финансовом продукте, обнаруживаемая через недели.
- **Пессимистическая блокировка на время редактирования** — отвергли:
  требует освобождения по таймауту, оставляет висящие блокировки при
  закрытии вкладки, и приводит к «запись занята пользователем X»
  как штатному состоянию.
- **Сравнение всех полей вместо версии** — отвергли: объём передаваемых
  данных и ложные конфликты на полях, которые никто не менял.
- **Сравнение времени изменения вместо версии** — отвергли: разрешение
  часов и рассинхронизация серверов делают сравнение ненадёжным
  на коротких интервалах.
- **Версия на всех сущностях, включая факты** — отвергли: лишняя колонка
  и обновление счётчика на десятках миллионов строк, которые правит
  только процесс загрузки.
- **Автоматическое слияние конкурирующих правок** — отвергли: для денежных
  величин слияние без участия человека даёт результат, за который
  никто не отвечает.

### Последствия

**Получаем:**
- Правка не теряется молча; конфликт становится видимым событием.
- Механизм штатный для ORM, собственного кода почти не требует.

**Платим:**
- Версия обязана проходить через контракт API и состояние формы —
  клиентский код усложняется, и об этом легко забыть при добавлении
  нового экрана редактирования.
- Пользователь при конфликте теряет введённое, если интерфейс
  не сохранит его локально.
- Ещё одна колонка и ещё один код ответа в контракте.

**На что обратить внимание потом:**
- Конфликты происходят регулярно на одной и той же сущности → это сигнал
  о неверной гранулярности редактирования, а не о поведении пользователей:
  вероятно, форма правит слишком много за раз.
- Появление массового импорта себестоимости → определить поведение
  при конфликте для пакетной операции, оно не выводится из этого решения.
