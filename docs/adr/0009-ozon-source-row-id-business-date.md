## ADR-009: Ozon — состав `source_row_id`, определение бизнес-даты продажи

**Дата:** 2026-08-08
**Статус:** Proposed
**Модуль:** Ingestion
**Уточняет:** ADR-006 (общие правила идентификации фактов и raw-слоя
для Ozon не меняются, здесь — конкретные значения для этой площадки,
не отменяющие правило)

### Контекст

Tracer bullet требует первого реального коннектора: один эндпоинт,
один отчёт, сквозь все слои до экрана. ADR-006 задал общее правило —
первичный ключ факта естественный, `source_row_id` строится из полей
источника, не меняющихся при корректировке; где площадка не даёт
готового идентификатора строки — детерминированный суррогат.
Для Ozon этот суррогат не выбран, и без него миграция пакета 4
не может быть написана — это прямое стоп-условие «схема таблиц фактов».

Источник данных — `/v2/posting/fbo/list` с `with.financial_data=true`.
Решение принято раньше и здесь не пересматривается; причина — метод
живёт годами и обновляется описаниями, а не отключениями, в отличие
от `/v3/finance/transaction/list`, разбитого на новые эндпоинты
6 июля 2026. Важное следствие выбора: `financial_data` отдаёт разбивку
по каждому товару внутри отправления (`products[].commission_amount`,
`price` и другие поля), а не сумму на отправление целиком — значит,
задача деления одной суммы между товарами (аллокация, ADR-004)
в этом источнике не возникает. Она встретится в другом отчёте,
но не здесь и не сейчас.

Ozon возвращает по одному отправлению (`posting_number`) список товаров
(`products[]`), каждый со своим `sku` и количеством. Второй способ
получить те же продажи — отчёт о реализации — даёт `row_number`,
нестабильный между перевыпусками отчёта, и цикл обновления в месяц;
он отклонён ранее по той же причине, что и весь `finance/*`.

Дата в ответе присутствует в двух ролях: момент оформления заказа
(`in_process_at` / `created_at` отправления) и момент физической
доставки, определяемый последним статусом в цепочке. Обе — в часовом
поясе Ozon (МСК), сервер не отдаёт смещения явно в других зонах.

Выбор между ними — компромисс, видимый клиенту в каждой цифре:
дата заказа даёт значение сразу, но оно уменьшается при последующей
отмене; дата доставки стабильна, но сегодняшний день почти пуст,
а план-факт запаздывает на цикл доставки. Продукт контролирует
план-факт, а не бухгалтерский результат периода — задержка в неделю
для этой задачи дороже, чем последующая правка вниз.

### Решение

**`source_row_id`.** Конкатенация `posting_number` и `sku` через
разделитель `|`: `{posting_number}|{sku}`. Не хэш — конкатенация:
оба поля стабильны, не входят в изменяемую часть отправления,
и открытая строка читается при отладке без обратного преобразования.
Тип колонки — `text`.

Ozon отдаёт один и тот же `sku` в отправлении не более одного раза
(количество — отдельным полем `quantity`), поэтому пара уникальна
без порядкового номера строки. Если хотя бы одна фикстура пакета 0
покажет повтор `sku` внутри одного `posting_number` — решение
пересматривается до начала пакета 4, не после.

**Бизнес-дата.** Дата заказа (`in_process_at` отправления), приведённая
к дате без времени в часовом поясе Ozon. Статус отправления
(`status` из ответа: `awaiting_packaging`, `delivered`, `cancelled`
и другие) хранится отдельной колонкой факта, не сворачивается
в бизнес-дату и не фильтруется при загрузке — витрина считает
«заказано / доставлено / отменено» явно по этой колонке.

**Часовой пояс.** Фиксированная константа коннектора Ozon — `Europe/Moscow`,
не параметр из ответа и не настройка per-account: у Ozon нет
пользовательских часовых поясов кабинета, в отличие от общего правила
ADR-006, допускающего часовой пояс конфигурацией подключения.

**Идентификация товара.** `sku` Ozon — числовой идентификатор площадки,
хранится дополнительной колонкой `marketplace_sku`, отдельно
от внутреннего товарного справочника (справочника пока нет —
вне tracer bullet).

**Деньги.** Сумма и комиссия берутся из `financial_data.products[]`
построчно, не из `financial_data` уровня отправления. Валюта — `RUB`
константой коннектора: Ozon возвращает суммы без явного кода валюты,
селлеры Ozon работают в рублях.

### Альтернативы, которые отвергли

- **`row_number` отчёта о реализации** — отвергли: нестабилен между
  перевыпусками одного и того же периода, и сам отчёт закрывается
  раз в месяц — обратная связь при повторной загрузке через день
  ничего не покажет.
- **Хэш `posting_number + sku` вместо конкатенации** — отвергли:
  для отладки строка читается напрямую, хэш требует обратного маппинга;
  выгоды хэша (фиксированная длина) здесь не нужны, `text` не индексируется
  по длине критично на этом объёме.
- **Бизнес-дата = дата доставки** — отвергли: план-факт по определению
  сверяется с текущим планом на текущий период, а не с историческим;
  задержка на цикл доставки делает свежие данные пустыми,
  и это противоречит самому смыслу контроля план-факта.
- **Бизнес-дата в UTC** — отвергли по той же причине, что и в ADR-006
  для общего случая: расхождение с личным кабинетом Ozon по дням
  на границах суток проваливает критерий приёмки «цифра сходится
  до копейки за конкретный день».
- **`operation_id` / поля новых `finance/accrual/*` эндпоинтов как основа
  ключа** — отвергли: эндпоинты переписаны 6 июля 2026, `operation_id`
  приходит не для всех типов операций, справочник типов вынесен
  отдельным запросом. Строить необратимый ключ на API, которое площадка
  меняет прямо сейчас, — смешивать вопрос «наш конвейер неверен»
  с вопросом «у площадки поменялось».
- **Аллокация суммы отправления между товарами поровну или по цене** —
  отвергли как ненужную для этого отчёта: `financial_data.products[]`
  уже даёт сумму на товар, аллокация из ADR-004 понадобится для другого
  источника, не для FBO posting list.

### Последствия

**Получаем:**
- Повторная загрузка того же периода не создаёт вторых строк:
  `(company_id, marketplace_account_id, source_row_id)` детерминирован
  и стабилен при перевыпуске ответа.
- Отмена отправления после первой загрузки не исчезает бесследно —
  строка обновляется по статусу, а не удаляется и не дублируется.
- Свежая цифра доступна сразу в день заказа, что соответствует
  задаче план-факта.
- Деньги на строку не требуют аллокации в этом источнике —
  меньше кода и меньше места для ошибки в первом срезе.

**Платим:**
- Цифра «продажи сегодня» будет уменьшаться при последующих отменах —
  экран обязан явно показывать состав по статусам, иначе клиент
  увидит необъяснённое падение вчерашней цифры.
- `Europe/Moscow` захардкожен в коннекторе Ozon, а не вынесен
  в конфигурацию подключения — при появлении второй площадки
  с иным устройством часовых поясов конфигурация ADR-006 всё равно
  понадобится, здесь она просто не используется на старте.
- `RUB` константой — тот же компромисс: если Ozon для части селлеров
  вернёт суммы в другой валюте, это обнаружится не тестом, а расхождением
  на сверке (критерий приёмки №3), и колонку валюты придётся получать
  не константой.

**На что обратить внимание потом:**
- Фикстура пакета 0 покажет повтор `sku` в одном `posting_number` →
  пересмотреть состав `source_row_id` до пакета 4, добавив порядковый
  номер строки.
- Доля отправлений без `financial_data.products[]` (частичные ответы,
  ошибки API) растёт → решение об аллокации из ADR-004 понадобится
  и для этого источника.
- Появление второго кабинета Ozon с иностранным юрлицом или второй
  площадки → `Europe/Moscow` и `RUB` константами пересматриваются
  в пользу конфигурации подключения из ADR-006.
