# Architecture Decision Records

Записи принятых архитектурных решений. Каждая фиксирует контекст,
решение, отвергнутые альтернативы и последствия.

## Зачем

Через полгода вы (или новый разработчик) спросите «почему мы выбрали
именно это». Ответ должен быть в файле, а не в памяти. Отдельная
ценность — раздел с отвергнутыми альтернативами: он не даёт заново
обсуждать вопрос, который уже закрыт.

## Когда писать ADR

Только для решений, которые дорого или невозможно отменить:

- схема данных на таблицах фактов, ключи, партиционирование;
- модель мультитенантности;
- границы модулей и направление зависимостей;
- контракт API, влияющий на внешних потребителей;
- выбор технологии, которую нельзя убрать за день.

**Не писать** для обратимых решений — выбор библиотеки для мелкой задачи,
структура папки, формат логов. Их дешевле переделать, чем документировать.

## Статусы

| Статус | Значение |
|---|---|
| Proposed | предложено, обсуждается |
| Accepted | принято, действует |
| Superseded by ADR-NNN | заменено другим решением |
| Deprecated | больше не применяется |

Принятый ADR не редактируется. Изменилось решение — пишется новый
со ссылкой на предыдущий, старому проставляется Superseded.

ADR-006 заменяет раздел ADR-003 о первичном ключе таблиц фактов.
Остальная часть ADR-003 (UUIDv7 для сущностей) продолжает действовать.

ADR-009 и ADR-010 уточняют ADR-006 и ADR-007 соответственно: общие
правила не меняются, задаются конкретные значения и случай, которого
исходный ADR не предусматривал.

ADR-011 уточняет ADR-007 и ADR-008: ни одно из четырёх событий ADR-007
не отменяется, определяется, чем требование журнала закрывается и когда
журнал обязателен; тот же признак отвечает, каким сущностям нужна версия.

ADR-017 уточняет ADR-011 и **частично отступает** от ADR-007 — единственный
случай отступления в реестре, поэтому он назван здесь, а не только внутри
самого ADR. Вводится роль внутри контура администраторов, которую ADR-007
не различал, и сам контур строится впервые: решение ADR-007 о двух firewall
и двух таблицах до сих пор оставалось нереализованным. Аудит-журнал
не заводится заново — существующий расширяется на актора-администратора
и на события без компании; здесь ADR-011 только уточняется.

ADR-018 уточняет ADR-017: решение не отменяется, но межарендаторное
чтение админки названо третьим, отдельным случаем исключения CLAUDE.md §1
(а не разновидностью операционных задач), и узкий слой Deptrac выдаётся
на класс, а не на контур. Расхождение нашло внешнее ревью Stage 5.

ADR-019 уточняет ADR-006, ADR-009, ADR-011 и ADR-015 для истории статусов,
возвратов и метрики выкупа Ozon: raw-правила сохраняются, текущий sales fact
дополняется link columns, а outcome/матурация/прогноз вычисляются при чтении.

ADR-020 заменяет ADR-019 целиком, повторно принимая без изменений его решения
об источниках, ключах, классификации, метриках, прогнозе и backfill. Изменено
только требование к SQL-плану: коррелированный prefix scan заменён оконными
агрегатами внутри tenant-scoped истории и защищён plan-регрессиями.

ADR-021 частично заменит решение ADR-007 об отложенной самостоятельной
регистрации только после перехода в `Accepted`. Пока ADR-021 имеет статус
`Proposed`, он фиксирует поэтапную реализацию и не меняет принятые решения.

Отступают от ADR-007 два его пункта, оба записаны в ADR-017 разделом
«Отступление от ADR-007» с условием прекращения: второй фактор (TOTP)
откладывается, разные имена сессионных кук заменяются host-only куками.
Отступление вступило в действие вместе с переводом ADR-017 в `Accepted`
(по завершении этапа, на котором контур администраторов появился в коде).
