# Ozon FBO: проверка источника доступного остатка для I-2

**Дата проверки:** 2026-09-20. **Статус:** полный ответ нового метода по текущему каталогу сохранён; семантика доступного остатка и выбор метода ещё не подтверждены. Код загрузки остатков не начинался.

## Уже сохранённый JSON-ответ

В репозитории есть [побайтовая фикстура ответа `/v3/product/info/list`](../../api/tests/Fixtures/Marketplace/ozon/product-info-list-2026-08-13.json), снятая 2026-08-13 с разрешённого кабинета первого клиента. SHA-256: `4196cb7f30324ba93e3a015895b3650b77c56cf4a75e2c4829a95f6da0baaac6`. Повторно копировать тот же ответ под новым именем не требуется: тесты будущего парсера I-2 должны читать именно этот файл, если будет выбран данный метод.

Проверка всего JSON, без публикации артикулов и идентификаторов:

| Наблюдение | Результат |
| --- | ---: |
| `items` | 62 |
| Строки `items[].stocks.stocks[]` с `source = "fbo"` | 62 |
| Строки с `source = "fbs"` | 8 |
| FBO с `present > 0` и `reserved > 0` | 14 |
| FBO с `present = 0` и `reserved = 0` | 10 |

Наблюдаемая форма строки FBO: `source`, `sku`, целочисленные `present` и `reserved`. В этом ответе нет `warehouse_id` в строке остатка. Среди значений встречаются `present = 68`, `reserved = 3`. Это пример **формы ответа**, а не основание считать доступным остатком `68`, `65` или другое число. Текущий `OzonProductInfoListParser` разбирает карточку и игнорирует `stocks`; `FetchOzonCatalogHandler` уже получает и сохраняет raw-ответ. Фикстура используется действующими тестами каталога и цены; изменение её содержимого сломало бы правило неизменности исходного ответа.

Фикстура является ответом именно `/v3/product/info/list`. Она не является ответом `/v4/product/info/stocks` или `/v1/product/info/stocks-by-warehouse/fbo`. Нельзя переносить на другие методы её структуру, признак завершения выборки или смысл полей.

## Контрольный ответ `/v1/product/info/stocks-by-warehouse/fbo`

По прямому поручению пользователя 2026-09-20 выполнены read-only запросы с предоставленным временным ключом. Ключ и заголовки авторизации не сохранены. Сначала `/v3/product/list` вернул 62 SKU кабинета; затем для них запрошены остатки с `limit = 1000`. Ответ сохранён без изменения полей и значений в двух файлах:

Следующая страница получена с `cursor` первой страницы. Всего 1434 уникальные пары SKU + склад, 62 SKU и 48 складов; все 62 SKU совпадают с каталогом ранее сохранённой фикстуры. У строки есть `sku`, `offer_id`, `product_id`, `warehouse_id`, целочисленные `present` и `reserved`. На 12 строках одновременно `present > 0` и `reserved > 0`. В ответах нет полей покупателя или контактов; сохранены только данные товара и склада. Эти наблюдения подтверждают структуру и завершение пагинации для данного снимка, но не определяют, следует ли считать доступным остатком `present`, `present - reserved` или иной показатель. Сверка с числом «доступно к продаже» в кабинете ещё нужна.

## Проверка актуальных кандидатов

[Официальный канал уведомлений Ozon Seller API](https://t.me/s/OzonSellerAPI/660) объявил в июле 2026 года `/v1/product/info/stocks-by-warehouse/fbo` как новый метод получения остатков на складах FBO. Само объявление не содержит тело ответа, правила пагинации и определение доступного количества. Официальная [ссылка на метод](https://docs.ozon.ru/api/seller/) из объявления в текущем окружении открывается с циклическим перенаправлением; её описание не прочитано. `/v4/product/info/stocks` остаётся ещё одним кандидатом, но его структуру нельзя доказывать фикстурой `/v3/product/info/list`.

Выбор для I-2 делается после сравнения: (1) поля и пагинация сырого ответа метода, (2) его описание Ozon, (3) число «доступно к продаже» по тому же SKU/кабинету в контрольном срезе личного кабинета. Если складской разрез действительно нужен источнику, приоритет у метода, который возвращает его явно. Если `/v3/product/info/list` окажется достаточным для агрегата Этапа 0, использовать существующий опрос каталога без второго внешнего вызова; это решение всё равно требует доказанного определения доступного количества и полноты среза.

## Какая фикстура нужна при выборе нового метода

Для выбранного метода нужен **сырой JSON ответа целиком**, без нормализации и ручной подмены чисел, в `api/tests/Fixtures/Marketplace/ozon/`. Вместе с файлом фиксируются точный путь метода, дата снятия, безопасные параметры запроса (без ключей), количество страниц и контрольное значение доступного остатка из личного кабинета на близкий момент. При пагинации хранятся все страницы отдельно, включая последнюю; неполный набор не доказывает нулевой остаток отсутствующего SKU.

Для повторного контрольного снимка можно запустить [`bin/capture-ozon-fbo-stocks.sh`](../../bin/capture-ozon-fbo-stocks.sh) из корня репозитория: скрипт спросит реквизиты, получит список SKU из каталога и сохранит исходный ответ каждой страницы остатков. Он прекращает работу без сохранения страниц, если каталог неполон, ответ имеет неожиданную форму или курсор повторяется. Полноту и смысл полей нового снимка всё равно нужно проверить перед использованием в расчётах.

Перед сохранением проверить по `CLAUDE.md` §9 отсутствие персональных данных покупателей, данных третьих лиц и других клиентов. Если они появились, обезличить только запрещённые поля и явно описать расхождение с побайтовым ответом. Не помещать в фикстуру заголовки `Api-Key`, `Client-Id` и секреты. Для контрольного значения достаточно указать SKU в приватной рабочей записи и подтвердить числовое совпадение; в этом документе коммерческий идентификатор не нужен.

## Выход проверки I-2 до реализации

- Ссылка на точную фикстуру выбранного метода и её SHA-256.
- Таблица полей: SKU, склад (если есть), тип FBO/FBS, фактическое и зарезервированное количество, поле или подтверждённая формула доступного остатка.
- Правило полной загрузки: страницы, пустой результат, отсутствующий SKU, ошибка одной страницы, повтор идентичного ответа.
- Пример сверки доступного количества с контрольным значением; отдельно проверка строки с ненулевым резервом.
- Решение, переиспользовать ли опрос каталога или добавить отдельный read-only клиент и сообщение очереди.

Пока эти пункты не выполнены, доступный остаток в `Inventory` не рассчитывается и не показывается как достоверный показатель.
