## ADR-014: Сбор наблюдений цены с карточки Ozon через расширение

**Дата:** 2026-08-17
**Статус:** Proposed
**Модуль:** новый — `PriceMonitoring`
**Уточняет:** ADR-010 (аутентификация расширения не меняется; здесь —
решение по данным, которое ADR-010 явно отложил: «сбор наблюдений цен,
схема факт-таблицы под них и вопрос отдельного модуля к этому ADR
не относятся»)

### Контекст

Селлер хочет отслеживать по конкретным SKU на Ozon две цены — витринную
(без скидки банка/платёжной системы) и свою собственную цену со скидкой —
и видеть, сколько Ozon доплачивает поверх скидки продавца (СПП,
«соинвест»). Данные не приходят ни из одного API Ozon, которым уже
пользуется коннектор (ADR-009, ADR-012) — их можно получить только
с отрисованной страницы карточки, то есть только через расширение.

Рассмотрено три варианта, кто отправляет снимок цены раз в 30 минут:

| Вариант | Суть | Причина отказа |
|---|---|---|
| A. Только открытая вкладка | продавец держит карточку открытой | не решает задачу — нельзя требовать держать открытыми десятки вкладок |
| B. Service worker дёргает Ozon напрямую (API/HTML) | обход браузерной сессии | отдельный недокументированный скрейпер, риск тихой поломки при смене API/анти-бот, не покрыт существующим чек-листом публикации |
| **C. Service worker открывает фоновые вкладки по списку** | переиспользует тот же content-script, что уже читает карточку | выбрано |

### Решение

Service worker расширения по `chrome.alarms` (не `setInterval` — см.
`docs/patterns.md`) раз в 30 минут получает список отслеживаемых SKU
для компании и последовательно открывает каждый в фоновом
свёрнутом окне (`focused: false`), дожидается снимка от content-script,
отправляет наблюдение на бэкенд, закрывает окно. Визиты размазываются
равномерно по 30-минутному окну, не пачкой.

Бэкенд получает новый модуль `PriceMonitoring` с двумя сущностями:
список отслеживания (`TrackedSku`) и факт-наблюдение (`PriceObservation`).
СПП не хранится — вычисляется при чтении (`seller_price − displayed_price`),
по тому же принципу, что и маржа в ADR-013 §4.

### Альтернативы, которые отвергли

- **Вариант A** — отвергли: не масштабируется, продавцу пришлось бы
  постоянно держать открытыми вкладки всех отслеживаемых товаров.
- **Вариант B** — отвергли: новая недокументированная поверхность
  (парсинг внутреннего API или HTML вне контекста браузерной сессии
  продавца), которая ломается тихо и не покрыта ни одним существующим
  чек-листом.
- **Хранить СПП материализованным полем** — отвергли по прецеденту
  ADR-013: пересчёт при чтении проще и не может разойтись с исходными
  данными.

### Последствия

**Получаем:**
- данные, которые ни один API Ozon не отдаёт;
- переиспользование уже отлаженного пути чтения карточки (тот же
  content-script, что кормит текущую оверлей-панель).

**Платим:**
- наблюдения идут, только пока у продавца запущен браузер с профилем
  расширения — это не фоновая служба 24/7. Интерфейс обязан показывать
  «последнее наблюдение: N назад», а не подразумевать непрерывность;
- новая поверхность в манифесте: разрешение на создание/закрытие вкладок
  (`tabs`), больше, чем сейчас проверяет чек-лист публикации;
- при большом списке SKU 30-минутное окно становится тесным — см.
  «На что обратить внимание потом».

**На что обратить внимание потом:**
- если список отслеживания на компанию вырастет настолько, что
  последовательные фоновые визиты не укладываются в 30 минут —
  тогда обсуждать параллельность (сейчас — последовательно/малая
  конкурентность, без доказанной необходимости большего);
- если понадобится гарантированная работа независимо от того, запущен
  ли браузер продавца — это отдельное решение (серверный headless-рендер),
  кратно дороже, не рассматривается сейчас.

## 1. Цель фичи

Селлер по клику начинает получать историю двух цен по SKU на Ozon и
производную от неё величину СПП — сколько Ozon в среднем доплачивает
поверх его собственной скидки. Это не входит ни в один из трёх текущих
блоков (план-факт, юнит-экономика, остатки) буквально — это новый,
четвёртый источник данных, который в будущем может стать входом для
юнит-экономики (реальная цена, по которой платит покупатель, против
цены, которую видит продавец).

## 2. Пользовательский сценарий

1. Продавец на карточке товара Ozon, оверлей-панель Conwix уже отображается
   поверх карточки.
2. Нажимает кнопку «Добавить в отслеживание» в этой панели.
3. SKU появляется в списке отслеживания компании.
4. Раз в 30 минут service worker расширения по списку открывает SKU
   в фоновом окне, читает две цены, отправляет снимок на бэкенд.
5. Продавец в приложении Conwix видит историю цены по SKU и СПП.

## 3. Границы (scope)

### В работе
- Кнопка «Добавить в отслеживание» в существующей оверлей-панели.
- Список отслеживания (создание, чтение) — новая сущность.
- Периодический сбор снимка цены расширением (service worker + фоновые окна).
- Приём снимков на бэкенде, хранение, вычисление СПП при чтении.
- Кнопка «Остановить отслеживание» — минимальный toggle, раз панель уже
  редактируется. **Это добавление, не часть исходного описания — если не
  нужно сейчас, вычеркнуть, экономит один эндпоинт.**

### Явно вне рамок
- Экран/виджет истории цены и СПП в приложении продавца (`apps/seller`) —
  отдельная задача, после того как данные начнут копиться.
- Работа без запущенного браузера продавца (headless на сервере).
- Несколько активных Ozon-подключений на одну компанию для этой фичи —
  см. открытый вопрос №3.
- Отслеживание на Wildberries — только Ozon, по сценарию.

## 4. Модель данных

Новый модуль `PriceMonitoring`. Зависимости строго вниз, как у всех
модулей: `PriceMonitoring → Identity → Shared`. От `Ingestion` не зависит —
это независимый источник данных, не коннектор к площадке.

### Entity `TrackedSku`

Управляется действием пользователя (клик), не сырой факт — по аналогии
с `cost_price` из ADR-013: суррогатный `UUIDv7`, состояние меняется явно.

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | UUIDv7 | суррогатный PK |
| `company_id` | UUID | tenant, обязателен в каждом запросе репозитория |
| `marketplace_account_id` | UUID | ссылка на Identity, **не** `#[ManyToOne]` — строкой (см. anti-pattern №3 в `PATTERNS.md`) |
| `marketplace_sku` | text | как в ADR-009 |
| `status` | enum: `active` / `stopped` | soft-стоп, не удаление |
| `created_at` | timestamptz | |
| `created_by_user_id` | UUID | кто нажал кнопку — пригодится при «почему нет данных» |
| `stopped_at` | timestamptz, nullable | |

Уникальный индекс: `(company_id, marketplace_account_id, marketplace_sku)`.
Повторное «добавить в отслеживание» для уже активной записи — идемпотентно,
просто 200, новую строку не создавать.

### Entity `PriceObservation`

Факт, присланный клиентом. Неизменяемый после записи — это не
битемпоральная сущность вроде себестоимости (её никто не правит задним
числом), а точка во времени, ближе по духу к фактам продаж ADR-006/009.

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | UUID | **генерируется расширением** в момент успешного чтения цены на странице, присылается как есть — это же ключ идемпотентности при повторной отправке после таймаута/retry |
| `company_id` | UUID | |
| `marketplace_account_id` | UUID | |
| `marketplace_sku` | text | |
| `observed_at` | timestamptz | момент снимка, присылает клиент, UTC ISO8601 — это не «бизнес-дата» календаря вроде даты заказа, а точный момент, поэтому без завязки на часовой пояс Ozon |
| `displayed_price` | Money (RUB, минорные единицы + `char(3)`) | базовая витринная цена Ozon, **до** скидки банка/платёжной системы |
| `seller_price` | Money (RUB) | цена продавца со своей скидкой |
| `source` | text, константа `'extension'` | задел на случай другого способа сбора позже |
| `captured_by_user_id` | UUID | чей браузер снял — для отладки пропусков |
| `extension_version` | text | версия сборки расширения — та же логика, что уже используется для диагностики 401 в чек-листе |

Уникальный индекс на `id` (он же идемпотентность). Дополнительный индекс
`(company_id, marketplace_account_id, marketplace_sku, observed_at)` под
чтение истории.

Деньги — по образцу ADR-013 §6: собственный Doctrine-тип `Money`, валюта
отдельной колонкой, наружу `int` не выходит, умножения здесь нет вовсе
(это не расчёт себестоимости, просто хранение двух цен).

### Миграция

Две новые таблицы, без изменения существующих. FK на `company` и
`marketplace_account` — как везде в проекте, строкой/UUID, без
`#[ManyToOne]` на Entity чужого модуля.

## 5. API-контракт

Аутентификация — существующий токен расширения (ADR-010), тот же
механизм, что уже использует `/api/extension/me`. Повторить его паттерн,
не изобретать новый.

### `POST /api/extension/tracked-skus`

Запрос: `{ "marketplaceSku": "123456789" }`

Резолвит `marketplace_account_id` сам бэкенд — единственное активное
Ozon-подключение компании (см. открытый вопрос №3 про множественные
подключения).

Ответ: `201` с созданной записью, либо `200`, если SKU уже отслеживается
активно (идемпотентно).

### `POST /api/extension/tracked-skus/{marketplaceSku}/stop`

Переводит запись в `stopped`. `404`, если не найдена активной.
*(вычеркнуть вместе с кнопкой «Остановить», если решите не делать сейчас)*

### `GET /api/extension/tracked-skus`

Список активных SKU компании — service worker дергает его в начале
каждого 30-минутного цикла, **не доверяя только локальному
`chrome.storage`**: список мог измениться не с этого устройства.

Ответ: `[{ "marketplaceSku": "...", "status": "active" }, ...]`

### `POST /api/extension/price-observations`

Запрос:
```json
{
  "id": "uuid-сгенерированный-расширением",
  "marketplaceSku": "123456789",
  "observedAt": "2026-08-17T09:00:00Z",
  "displayedPrice": { "amount": 129900, "currency": "RUB" },
  "sellerPrice": { "amount": 139900, "currency": "RUB" }
}
```

Валидация:
- SKU должен быть `active` в `TrackedSku` этой компании — иначе `404`,
  наблюдения для неотслеживаемых SKU не принимаются (не место для
  произвольной записи чем попало).
- Повтор того же `id` — `200` без создания второй строки (идемпотентность
  на случай retry после сетевого таймаута).

Rate limit — существующий Redis-компонент (см. `README`/`CLAUDE.md`,
раздел про Redis: сессии, rate limit, распределённые блокировки),
не новая инфраструктура. Порог — на компанию, с запасом сверх
разумного числа отслеживаемых SKU, чтобы поймать сбойную сборку
расширения, а не легитимную нагрузку.

## 6. Расширение (`apps/extension`)

### Service worker — оркестрация

- Один повторяющийся `chrome.alarms.create('price-sync', { periodInMinutes: 30 })`.
- По срабатыванию: `GET /tracked-skus` → на каждый SKU считается
  сдвиг внутри окна (`delay_i = i * 30мин / N`) → по каждому создаётся
  **отдельный одноразовый alarm** (`chrome.alarms.create(name, { when })`),
  не `setTimeout` — service worker засыпает, таймеры не переживут сон.
- По срабатыванию одноразового alarm: `chrome.windows.create({ url, focused: false, state: 'minimized' })`
  на карточку SKU → ждём сообщение от content-script с прочитанными
  ценами (таймаут ~15 c) → на успехе шлём `POST /price-observations` →
  закрываем окно в любом случае (успех, таймаут, ошибка).
- Небольшая конкурентность (например, не больше 2 окон одновременно),
  не открывать все SKU разом — и по нагрузке, и чтобы не выглядеть
  как всплеск ботового трафика для Ozon.
- Ошибка чтения цены (якорь не найден, страница не загрузилась) —
  логируется предупреждением и пропускается, без бесконечных ретраев
  в рамках этого же цикла — по аналогии с уже принятым правилом
  «якорь не найден → предупреждение в консоли» из чек-листа.

### Content-script — чтение цены

Переиспользует тот же путь, что уже находит карточку для текущей
оверлей-панели. **Новая часть** — само чтение двух цен: сейчас
content-script их не читает вовсе (оверлей показывает цифры Conwix
из API, не цену со страницы). Требует спайка — см. открытый вопрос №1.

Нужно уметь отличить обычный визит продавца от фонового
capture-визита service worker'а (например, параметром в URL или
сообщением от service worker сразу после создания окна), чтобы не
слать снимок цены при каждом обычном открытии карточки — только
по явному запросу.

### Overlay — кнопка

Кнопка «Добавить в отслеживание» (и, если оставляем, «Остановить») —
в уже существующей панели, чужая поверхность (Shadow DOM, свои стили,
без `packages/ui` — как записано в `docs/patterns.md`).

### Манифест

Новое разрешение на управление вкладками/окнами (`tabs`, возможно
`windows`) — расширяет то, что уже проверяет чек-лист публикации
(«разрешений не больше, чем нужно» — здесь действительно нужно,
это не лишнее). Раздел
«Расширение браузера — перед каждой публикацией» в
`docs/operations-checklist.md` стоит дополнить пунктами под эту фичу
(нет заметного мигания окон, не дублируются наблюдения, троттлинг
реально размазан) — отдельным маленьким PR к чек-листу вместе с фичей.

## 7. Расчёт СПП

Не хранится. Вычисляется в запросе на чтение (когда появится экран —
вне рамок этой задачи, но контракт расчёта фиксируем сейчас, чтобы
таблица была готова под него):

```
СПП = seller_price − displayed_price
```

Положительное значение — Ozon добавил скидку сверх скидки продавца.
Что означает отрицательное значение (витринная цена выше цены продавца)
и нужно ли поджимать к нулю — не решено, см. открытый вопрос №4.
Постоянного числа таблица не хранит: как и с маржой в ADR-013,
это ещё один JOIN/вычисление в том же запросе, не отдельное поле.

## 8. Нефункциональные требования

- **Многотенантность:** каждый метод репозитория `PriceMonitoring`
  принимает `companyId`, без исключений — IDOR здесь так же критичен,
  как везде в проекте.
- **Идемпотентность:** оба POST-эндпоинта идемпотентны по описанным
  выше ключам — обязательное условие, раз клиент (расширение) может
  повторить запрос при сетевом сбое.
- **Логирование:** приём наблюдения для неотслеживаемого SKU — ожидаемое
  доменное условие (`warning`, не `error`) — шум в Sentry на IDOR-подобные,
  но не аномальные случаи не нужен.
- **Тесты** (минимум, см. таблицу в `CLAUDE.md`):
  - повторная отправка одного и того же `id` наблюдения не создаёт вторую строку;
  - наблюдение для чужой компании / неотслеживаемого SKU отклоняется;
  - изоляция между компаниями (IDOR-тест на список и на приём наблюдения);
  - расчёт СПП на паре известных значений, включая отрицательный случай;
  - rate limit срабатывает при превышении порога.

## 9. Открытые вопросы — закрыть до/во время реализации

1. **Спайк, обязательный перед кодированием content-script.** Как
   технически достать «цену продавца со скидкой» со страницы карточки —
   она не обязана быть видимым текстом на витрине (СПП по сути и есть
   скрытая величина). Нужно открыть карточку своего товара под
   расширением и посмотреть, что реально доступно: видимый DOM,
   встроенный в страницу JSON-стейт, что-то ещё. Без этого пункт 6
   («Content-script — чтение цены») не написать достоверно — в этом
   задании селекторы намеренно не выдуманы.
2. Точный URL-паттерн для открытия карточки по `marketplace_sku` без
   человекочитаемого слага (`ozon.ru/product/{sku}/` — редиректит ли
   Ozon корректно) — проверить руками, отдельно от спайка №1.
3. Компания с несколькими Ozon-подключениями: сейчас предполагается
   одно активное на компанию (соответствует текущему `MarketplaceAccount`
   в реальных данных проекта — селлеров с двумя кабинетами Ozon пока не
   встречалось). Если бэкенд находит больше одного — решить: `409` с
   явной ошибкой (предлагается) или что-то другое. Не строить выбор
   подключения в интерфейсе заранее.
4. Формула СПП при `displayed_price > seller_price` (случай, когда
   витринная цена выше цены продавца) — хранить как есть или считать
   аномалией/нулём. Нужно решить до того, как появится читающий экран,
   не сейчас критично для приёма данных.
5. Кнопка «Остановить отслеживание» — подтвердить, что нужна сейчас,
   а не при следующей итерации (см. пометку в разделе 3).

      `TrackedSku` (идемпотентно при повторном клике).
- [ ] Service worker раз в 30 минут проходит по списку отслеживания
      компании и открывает каждый SKU в фоновом свёрнутом окне,
      визиты размазаны по окну, не пачкой.
- [ ] Content-script в фоновом визите читает и отправляет `displayed_price`
      (без скидки банка/платёжной системы) и `seller_price`.
- [ ] Наблюдение с уже виденным `id` не создаёт вторую строку.
- [ ] Наблюдение для SKU, не отслеживаемого этой компанией, отклоняется.
- [ ] Ошибка чтения цены на одном SKU не прерывает цикл по остальным.
- [ ] Тесты из раздела 8 написаны и проходят.
- [ ] Пункт про новое разрешение манифеста и troubleshooting добавлен
      в `docs/operations-checklist.md`.
