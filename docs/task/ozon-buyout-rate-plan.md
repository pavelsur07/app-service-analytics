# План работ: процент выкупа по SKU (Ozon)

**Для кого:** рабочее задание для Claude Code. Здесь — решения и их обоснование
в объёме, нужном для исполнения; полная дискуссия, из которой они выведены,
осталась в чате Project.

**Модуль (бэкенд):** Ingestion — тот же, где уже живут `sales_fact` (ADR-009)
и `marketplace_expense_fact` (ADR-012). Новой сущности/модуля не заводим —
нет второго потребителя, который оправдал бы границу.

**Не входит в объём этой работы:**
- push-уведомления вместо опроса — Stage N, отдельная задача. Схема пакета 1
  спроектирована так, чтобы источник записи (тик синхронизации → вебхук)
  можно было заменить, не трогая таблицу и расчёт.
- перенос на Wildberries — по принципу «не абстрагировать до второго случая»:
  абстракция коннектора пишется после второго коннектора, не до первого.
- категорийный уровень отката в прогнозе (пакет 6) — `category_id` пока нет
  в модели, заводить его ради этого рано.

**Порядок пакетов последовательный**, каждый следующий зависит от предыдущего:
0 → ADR → 1 → 2 → 3 → 4 → 5 → 6 → 7. Пакет 4 требует 2 и 3 одновременно.

## Пакет 0 — разведка (без продакшн-кода)

**Предмет:** снять живые фикстуры и закрыть три вопроса, от которых зависит
схема. Без ответов ADR и миграция пакета 1 не пишутся — то же правило, что
уже останавливало миграцию в ADR-009 до выбора `source_row_id`.

Проверить и зафиксировать фактом, не документацией (принцип «основание —
сверка», уже применённый в ADR-009 и ADR-012):

1. Есть ли поле `substatus` уже в ответе `/v2/posting/fbo/list` (который и так
   тянется каждый тик), или для него нужен отдельный вызов `posting/fbo/get`
   на каждое отправление. Если substatus даёт прямую разметку «не забрал на
   ПВЗ» vs «отменил в пути» — парсинг причин отмены для этой части не нужен.
2. `POST /v1/returns/list` на реальных данных: состав ответа для типа
   `PartialReturn`, и каким полем дочернее отправление (статус «Отменено»)
   связывается с `order_number` родительского. `order_number` сейчас не
   хранится отдельной колонкой в `sales_fact` (ADR-009 фиксирует только
   `posting_number|sku`) — проверить, что поле вообще есть в уже
   загружаемом `/v2/posting/fbo/list`, или его придётся добавлять.
3. Фактический срок хранения на ПВЗ до автоматического перехода в
   невостребованный — из справки Ozon для используемой схемы (FBO/FBS),
   не предполагать числом.

**Критерий готовности:** три пункта закрыты на реальном кабинете, находки
записаны (годятся как черновик раздела «Контекст» будущего ADR).

**Ревью:** не требуется — не диф в продакшн-коде.

## Пакет 1 — таблица истории статуса отправления

**Предмет:** `marketplace_posting_status` — append-only таблица, по паттерну
ADR-015 (история цены продавца), не ADR-006 (восстановление из raw): статус
нужен для регулярных агрегатов по датам и когортам, а не для разового
форензик-запроса, и raw-jsonb-дифф для этого не годится — то же
рассуждение, из-за которого цену продавца в итоге вынесли отдельной
таблицей.

**Схема:**
- Естественный ключ `(company_id, marketplace_account_id, posting_number,
  changed_at)`, суррогата нет (§2 правил).
- Колонки `status`, и `substatus`, если пакет 0 подтвердит его полезность.
- `changed_at` — момент, когда синхронизация впервые увидела значение, не
  момент реальной смены статуса у площадки. Зафиксировать это честно в
  комментарии к колонке — так же, как уже сделано для цены в ADR-015.
- `raw_document_id` — прослеживаемость, как у всех фактов (ADR-006).
- Строка появляется, только если значение отличается от последнего
  известного для того же `posting_number` — условие внутри `INSERT`, не в
  ветке кода (§4), одним запросом на всю выгрузку (§6).

**Аудит-след по ADR-011:** отдельный журнал не нужен — таблица append-only,
переходы необратимы, `changed_at` фиксирует момент, условие «новое
значение» защищает от параллельной перезаписи внутри самого `INSERT`. Все
четыре условия ADR-011 выполнены конструкцией таблицы — указать это прямо
в ADR, чтобы вопрос не поднимался ревьюером заново.

**Критерий готовности:** миграция применяется и откатывается на копии
боевых данных; повторный прогон синхронизации на тех же входных данных не
создаёт новых строк.

**Ревью:** оба — миграции и схема данных, плюс Ingestion/идемпотентность
(обе строки порога ревью).

## Пакет 2 — запись истории при синхронизации

**Предмет:** обработчик, уже читающий `/v2/posting/fbo/list`, на каждом
тике сравнивает `status`/`substatus` с ближайшим хронологическим
предшественником в
`marketplace_posting_status` по `posting_number` и вставляет при отличии.
Один SQL-запрос на всю выгрузку тика, не построчная проверка (§6).

**Критерий готовности:** на фикстуре с изменением статуса между двумя
тиками — ровно одна новая строка; на фикстуре без изменений — ноль новых
строк; повторный прогон обработчика на одном и том же raw-документе не
дублирует.

**Ревью:** оба (Ingestion: идемпотентность).

## Пакет 3 — источник возвратов

**Предмет:** коннектор к `/v1/returns/list` — сырьё в raw-слой по общему
правилу (ADR-006: `jsonb`, дедуп по хэшу тела, без мутаций), разбор в
структуру, отдельную от `sales_fact`: это не выручка и не расход, а
разметка исхода.

**Что храним:** `order_number`, `sku`, `type` (`PartialReturn` / прочее),
`posting_number` дочернего отправления, дата. Если пакет 0 показал, что
`order_number` не хранится в `sales_fact` — добавить его туда же
(отдельная маленькая миграция, тот же STOP-повод, что и пакет 1).

**Критерий готовности:** фикстура с `PartialReturn` из пакета 0 разбирается
и находит родительский `posting_number` через `order_number`; повторная
загрузка не дублирует.

**Ревью:** оба (новый источник Ingestion, идентификация фактов).

## Пакет 4 — классификация исходов

**Предмет:** на каждую строку `sales_fact` (`posting_number|sku`) навесить
одну из категорий T1 / D / T2 / P / R:

1. Базовая категория — от терминального статуса `marketplace_posting_status`
   по `posting_number`: T1 — отменено до передачи в доставку, D —
   доставлено, T2 — отменено/не забрано на этапе доставки или в ПВЗ.
2. Причины отмены — через словарь `cancel-reason → категория`. Словарь —
   конфиг-таблица, не enum в коде: список причин у площадки динамический
   (тот же урок, что ADR-012 уже получил на другом источнике).
3. Override из пакета 3: если `(order_number, sku)` встретился в возвратах
   с `type = PartialReturn` — понизить именно эту SKU-строку из D в P.
   Прочие типы возврата — в R, не влияют на процент выкупа.

**Критерий готовности:** на смешанном отправлении (несколько SKU, один — с
`PartialReturn`) только затронутый SKU меняет категорию, остальные
наследуют исход отправления без изменений.

**Ревью:** один, но с обязательной ручной проверкой на реальных причинах
отмены из пакета 0 — ошибка здесь не ловится линтером или тайпчекером, это
неверная цифра, которая выглядит верной, то есть ровно тот класс дефекта,
который их чек-лист ревью (5B) требует ловить в первую очередь.

## Пакет 5 — метрика и матурация

**Предмет:** расчётный слой (вьюха/сервис, не факт-таблица):

- Конверсия «заказ → доставка» = `D / (T1+D+T2)`.
- Процент выкупа (основной) = `D / (D+T2+P)`.
- Перцентили p50/p90/p95 времени «отгружен → терминальный статус» из
  `marketplace_posting_status`, для порога матурации.
- Когорта считается финальной, когда `сегодня − дата_заказа > p95`; иначе —
  «предварительно», с явной долей ещё не разрешившихся заказов рядом, а не
  вместо неё.

**Критерий готовности:** API/экран отдаёт пару чисел (значение среди
разрешившихся + доля разрешившихся) для любой запрошенной когорты, не одно
смешанное число.

**Ревью:** оба, если пакет уже джойнит `marketplace_expense_fact` (денежная
величина); один — если это чисто счётная витрина без сумм.

## Пакет 6 — прогноз на сегодня

**Предмет:**
- Базовая ставка — скользящее окно 28–30 дней **дозревших** когорт
  (`[сегодня − p95 − 30; сегодня − p95]`), пересчитывается на лету при
  каждом обращении, отдельного джоба не заводим.
- Иерархический откат: SKU-ставка при ≥ 20–30 дозревших заказов в окне,
  иначе — ставка уровня `marketplace_account`. Третий уровень (категория)
  не заводить — нет потребителя.
- Прогноз для сегодняшних заказов не на одной ставке для всех: ставка
  `T1+D+T2` для заказов, ещё не переданных в доставку; узкая ставка
  `D/(D+T2)` — для уже переданных (T1-риск снят).
- Опционально — доверительный интервал `n·p ± √(n·p·(1−p))`, одна формула,
  не отдельная инфраструктура.

**Критерий готовности:** для тестовой когорты сегодняшних заказов прогноз
меняется сам по мере смены их статусов в течение дня, без ручного
пересчёта.

**Ревью:** один (расчётная логика, без изменения схемы и без записи денег).

## Пакет 7 — экран «Выкуп»: список по SKU + разворачивание в дневной график

**Предмет:** список по SKU (сводная строка + таблица) с разворачиванием
строки в дневной график факт/прогноз (накопительный прогноз, пакет 6).
Связка с юнит-экономикой (расходы `POSTING`-категории из
`marketplace_expense_fact`) исключена из этого пакета: юнит-экономика сама
ещё честно пишет «себестоимость не учтена» (ADR-013), пристраивать к
незавершённому экрану ещё один срез рано — отдельный пакет, когда тот
экран доделан.

**Компоновка — только существующие примитивы `packages/ui`** (`Button`,
`Input`, `Card`, `Badge`). `Table`/`Dialog`/`Tabs`/`Select` в ките
сознательно нет до третьего продуктового повторения — вводить их этой
задачей нельзя:

- Заголовок + период — три `Button` (7 / 30 / 90 дней), период в URL, не
  в локальном стейте. Не `Select`: три пресета не оправдывают выпадающий
  список.
- Сводная строка — обычный текст, `tabular-nums`, без карточек: «84%
  выкуп · 92% заказов разрешилось · 1 240 из 1 480 шт».
- Таблица — обычная `<table>`, как `SalesFactsTable.tsx`, не
  `react-table` (нечем управлять без клиентской сортировки). Колонки:
  Артикул / Заказано / Выкуп (одно число — накопительный прогноз,
  `tabular-nums`, мелкой строкой под ним разбивка `T1 2% · T2 10% · P
  2%`) / Статус — `Badge`, нейтральный «матурировано» или warning
  «предварительно · 61%».
- Отдельного переключателя «Факт/Прогноз» нет: накопительный прогноз
  (пакет 6) сам равен факту на дозревших когортах и оценкой — на свежих,
  второе число на этом экране избыточно.
- Клик по строке — accordion, не модалка: в ките нет `Dialog`, вводить
  его ради одного графика — лишний примитив раньше третьего повторения.
  Разворачивается доп. `<tr>` с `<td colSpan>`, внутри — `Card` с
  графиком `recharts` (`LineChart`, серии «Факт» и «Прогноз» по дате
  заказа) — то же самое, что показано в чате примером по одному SKU.
- Три явных состояния (загрузка/пусто/данные) — тот же принцип, что для
  денег («0%» во время загрузки — не «ещё не загрузилось», а неверная
  цифра, которой поверят), хоть здесь и не деньги в чистом виде.

**Критерий готовности:**
- Период — три `Button`, состояние в URL, не в локальном стейте.
- Строка разворачивается без ухода со страницы и без сброса пагинации

- «Предварительно N%» — `Badge` варианта warning с текстом внутри, не
  голый цвет.
- T1/T2/P видны сразу под процентом, без дополнительного клика.
- Три состояния (загрузка/пусто/данные) — для сводной строки и для
  графика по клику отдельно.

**Ревью:** один — новый read-контракт и экран, денежная арифметика не
пересчитывается на фронте, миграций нет.

## Порядок исполнения каждого пакета

Без отклонений от процесса в CLAUDE.md: план (что меняем, какие файлы,
критерий готовности) → проверка STOP-условий → реализация с тестами в
одном изменении → самопроверка по их чек-листу → внешнее ревью по уровню
из таблицы выше → разбор замечаний до отсутствия принятых → отчёт (Задача /
Сделано / Файлы / Ревью / Отклонено / Проверка / Открыто).

Один пакет — один предмет ревью. Пакеты 1–4 (схема и ingestion) не сшивать
в один диф с пакетами 5–7 (расчёт и экран) — разный порог ревью, разная
цена ошибки.
