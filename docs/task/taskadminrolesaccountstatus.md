# Задание: роли администраторов и блокировка аккаунта клиента

Формат: описание того, что нужно получить на каждом этапе, без конкретной
реализации (имена классов, SQL, код) — это решает исполнитель (Claude Code)
по `CLAUDE.md`, `docs/patterns.md`, `docs/structure.md` и ADR ниже, следуя
своему обычному циклу («Разбор → План → STOP? → Реализация → Самопроверка →
Ревью → Отчёт»). Один пакет на ревью — один этап, не всё сразу.

Ниже сущности названы по смыслу (`Company`, «сущность администратора»,
«статус аккаунта») — точные имена классов/таблиц в текущем коде исполнитель
сверяет сам на шаге «Разбор», в этот документ они не заложены.

---

## Контекст и цель

Раздел Admin — системный контур управления сервисом целиком, не отдельной
компанией. Первая функция этого контура: управление клиентскими аккаунтами
(регистрация, блокировка, включение). Для этого вводится вторая роль внутри
уже существующего контура администраторов (ADR-007): `SuperAdmin` и `Admin`.

Контроль оплат в это задание не входит — см. «Что не входит».

## Допущение, зафиксированное на этапе обсуждения

И `Admin`, и `SuperAdmin` могут выполнять управление аккаунтами
(регистрация / блокировка / включение). Только `SuperAdmin` может заводить
`Admin`. Если это не так — поправить это задание до передачи в работу,
дальше оно на этом допущении построено.

## Что не входит (явно, чтобы не расширялось по ходу)

- Контроль оплат / биллинг / интеграция с платёжным провайдером —
  отдельная задача с собственным ADR.
- Самостоятельная регистрация клиента (self-service) — остаётся отложенной
  по ADR-007.
- Permission-система сверх двух статичных ролей — вводится только если
  появится третий случай (rule of three).
- Просмотр содержимого аудит-журнала через UI — журнал в этом задании
  только пишется; экран чтения, если понадобится, — отдельная задача.
- Принудительная инвалидация уже открытых сессий заблокированной компании —
  блокировка действует с первого следующего запроса, этого достаточно
  (см. ADR ниже, раздел «Решение»).

## Изменения в ADR

Ниже — новый ADR, который должен появиться в `docs/adr/017-admin-roles-and-account-status.md`
и быть добавлен в реестр `docs/adr/README.md` (следующий свободный номер —
017 на момент написания этого задания; проверить перед созданием файла,
что за это время не появился более свежий). Статус — `Proposed`: файл
создаётся первым шагом (до кода), после чего статус переводится в
`Accepted` при подтверждении, что реализация ниже ему соответствует.

ADR **уточняет** ADR-007 (роль внутри контура администраторов, которую
ADR-007 не различал) и ADR-011 (первая фактическая реализация
аудит-журнала, который ADR-007/ADR-011 требовали, но не строили) —
оба остаются в силе, ни один пункт не отменяется.

```markdown
## ADR-017: Роли администраторов и блокировка аккаунта клиента

**Дата:** 2026-08-29
**Статус:** Proposed
**Модуль:** Identity
**Уточняет:** ADR-007, ADR-011

### Контекст

Раздел Admin — системный контур управления сервисом целиком (не отдельной
компанией). Первая функция — управление аккаунтами: регистрация нового
клиентского аккаунта, блокировка, включение. Контроль оплат откладывается
полностью — модели биллинга в проекте нет, отдельная задача в будущем.

ADR-007 уже развёл контур администраторов от контура продавца (свой
firewall, своя таблица), но не различал роли внутри него, и любые
чувствительные учётные записи заводились только консольной командой.
Сейчас нужно первое разделение: `SuperAdmin` остаётся bootstrap-ролью,
`Admin` — операционной, для повседневного управления аккаунтами.

### Решение

**Роль администратора** — поле `role` (`ADMIN` | `SUPER_ADMIN`) на
существующей сущности администратора. `SuperAdmin` создаётся только
консольной командой, без UI-пути — ни для первого, ни для последующих.
`Admin` создаётся через форму, доступную только `SuperAdmin`. Права
разведены через `role_hierarchy` (`ROLE_SUPER_ADMIN: [ROLE_ADMIN]`) и
Voter'ы на конкретные действия (управление администраторами — только
`SuperAdmin`; управление аккаунтами клиентов — обе роли).

**Статус аккаунта** — поле `status` (`active` | `blocked`) на `Company`.
Переходы — явные доменные методы, не общий сеттер (`block(reason)` /
`activate()`), инвариант тот же, что и у остальных сущностей проекта.
Проверка статуса встраивается в уже существующую точку проверки членства
в компании (ADR-002: контекст компании явно в URL, не в сессии) —
блокировка действует немедленно на следующий же запрос, отдельного сброса
сессий в Redis не требуется.

**Аудит-журнал** — заводится таблица журнала (первая фактическая
реализация требования ADR-007/ADR-011), пишется минимум для: регистрация
аккаунта, блокировка, включение, создание `Admin`. Формат «было/стало»,
актор, время — по правилу ADR-011 (переходы обратимы, значит журнал
обязателен, признак из ADR-011 соблюдён явно).

**Кросс-тенантное чтение** списка аккаунтов для админки — существующее
исключение CLAUDE.md §1 («операционные системные задачи»), не новое.
Реализуется как отдельный именованный Query, недостижимый из Ui продавца
по Deptrac, с docblock-ссылкой на правило.

**Оплата** — не моделируется в этой задаче. Поле `status` у `Company` —
единственный крючок, который может понадобиться будущему биллингу; сама
интеграция получает свой ADR, когда появится.

**Модуль** — новый не заводится. Всё живёт в `Identity`, который уже
владеет `Company`, `User`, сущностью администратора и аутентификацией.

### Альтернативы, которые отвергли

- **Полноценная система разрешений (`Role`/`Permission` таблицы)** —
  отвергли: для двух статичных ролей это абстракция без второго случая;
  `role_hierarchy` + Voter'ы дают то же самое без новой схемы.
- **Отдельный backend-модуль `Admin`/`Ops`** — отвергли: нет своей
  предметной терминологии, все сущности уже принадлежат `Identity`.
- **Сброс сессий в Redis при блокировке** — отвергли: компания и так
  проверяется на каждом company-scoped запросе, докидывать проверку
  статуса в ту же точку дешевле.
- **Контроль оплат в этой же задаче** — отвергли: модели биллинга нет ни
  в одной ADR, это отдельный bounded context.

### Последствия

**Получаем:** минимальная ролевая модель без лишней машинерии; блокировка
работает сразу, без специальной инвалидации сессий; кросс-тенантное
чтение в админке следует уже согласованному правилу.

**Платим:** задача физически включает первую реализацию аудит-журнала —
это больше, чем «добавить два поля». Открыт вопрос оптимистичной
блокировки на `Company.status` — решается на этапе реализации после
проверки текущего кода `Company` (см. Stage 4 ниже).

**На что обратить внимание потом:** третья роль или гранулярные права →
переходить от `role_hierarchy` к явным Voter'ам на каждое действие (уже
введены здесь) и только тогда — к permission-таблице; интеграция оплат
получает свой ADR и не должна писать в `Company.status` в обход доменных
методов, введённых здесь.
```

## Этапы реализации

Каждый этап — отдельный пакет на ревью (`make review TASK="..."`), со своим
циклом `CLAUDE.md`. Порядок фиксирован: следующий этап зависит от
предыдущего.

### Stage 1 — Аудит-журнал (инфраструктура)

**Цель.** Есть куда писать «было/стало, кто, когда» для последующих
этапов — до появления первого использующего это события.

**Definition of Done.**
- Журнал переживает удаление записи, к которой относится (append-only,
  ничего не перезаписывается).
- Запись содержит как минимум: тип события, кто выполнил, когда, что было
  и что стало.
- Гонка одновременной записи двух событий не теряет ни одно из них
  (журнал только дописывается, конфликтов на запись нет по построению).
- Ничего не подключено к нему ещё — это инфраструктура для Stage 2–5.

### Stage 2 — Роль администратора и bootstrap SuperAdmin

**Цель.** В контуре администраторов есть различимые роли, верхняя
недостижима из UI.

**Definition of Done.**
- У сущности администратора есть роль из двух значений.
- Создание администратора с верхней ролью возможно только консольной
  командой; ни один HTTP-маршрут этого сделать не может (и не должен
  появиться на этом этапе).
- Права проверяются через `role_hierarchy`/Voter, а не проверкой строки
  роли в контроллере.
- Существующие администраторы (если есть) получают роль без потери
  доступа — миграция данных, не только схемы.

### Stage 3 — SuperAdmin создаёт Admin через форму

**Цель.** Первый экран в системном разделе: `SuperAdmin` заводит `Admin`.

**Definition of Done.**
- Действие доступно только `SuperAdmin`; `Admin` получает отказ на
  попытку (проверяется тестом, не только UI).
- Создание нового `Admin` пишет событие в аудит-журнал (Stage 1).
- Экран живёт в системном разделе, не путается с разделами, скоупнутыми
  на компанию.

### Stage 4 — Статус аккаунта (`Company`: active/blocked)

**Цель.** У `Company` есть статус, который реально останавливает доступ.

**Definition of Done.**
- Переход между `active` и `blocked` — явные доменные операции, не
  произвольная запись поля.
- Заблокированный аккаунт: ни один пользователь компании не проходит
  проверку доступа со следующего запроса; данные не удаляются и не
  помечаются неполными задним числом.
- Гонка двух одновременных переключений статуса не создаёт
  рассогласования (перед реализацией — проверить, есть ли уже у `Company`
  поле версии по ADR-008: если есть — использовать его по общему правилу,
  если нет — закрыть гонку условием внутри самого `UPDATE`, как это уже
  сделано для `revoked` в ADR-007/ADR-010, версию не заводить отдельно
  под эту задачу).
- Каждый переход пишет событие в аудит-журнал (Stage 1).

### Stage 5 — Экран управления аккаунтами

**Цель.** `Admin`/`SuperAdmin` видят список клиентских аккаунтов и
управляют ими из одного экрана.

**Definition of Done.**
- Список аккаунтов читается одним явно поименованным запросом,
  недостижимым из Ui продавца (кросс-тенантное чтение по исключению
  CLAUDE.md §1), с пагинацией и лимитом по общим правилам проекта.
- Регистрация нового аккаунта создаёт `Company` и её первого
  пользователя-владельца атомарно (одна транзакция), по аналогии с тем,
  что раньше делала консольная команда для первых клиентов.
- Кнопки блокировки/включения на этом экране используют доменные операции
  из Stage 4, доступны и `Admin`, и `SuperAdmin`.
- Действия отражаются в аудит-журнале и видны как факт (не обязательно
  через UI журнала — достаточно, что запись создаётся).
