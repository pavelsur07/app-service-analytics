# Stage 3 самостоятельной регистрации: браузерный интерфейс

**Дата:** 2026-09-02

**Статус:** утверждено владельцем 2 сентября 2026 года

**Исходное задание:** `docs/task/task-signup-onboarding-ozon-oauth.md`, только Stage 3

## Цель и границы

Пользователь должен самостоятельно пройти регистрацию в `apps/seller`,
получить нейтральное сообщение об отправленном письме, подтвердить адрес
и оказаться на первом экране онбординга. Регистрация защищена уже
развёрнутым backend Stage 2; этот пакет добавляет получение настоящего
одноразового токена через невидимый виджет Yandex SmartCaptcha.

В пакет входят публичные экраны регистрации, повторной отправки письма,
подтверждения адреса и стартовый экран `/onboarding` вне оболочки компании.
В пакет не входят подключение кабинета Ozon, первоначальная загрузка данных,
OAuth, новые backend endpoints, миграции или изменение схемы OpenAPI.

## Принятые решения

- Используется официальный пакет `@yandex/smart-captcha` и компонент
  `InvisibleSmartCaptcha`. Версия будет зафиксирована package lock; прямой
  самостоятельный lifecycle внешнего `captcha.js` не пишется.
- Проверка запускается только после успешной локальной валидации формы.
  Обычный пользователь не видит отдельной галочки или задания; окно задания
  показывает сам провайдер только подозрительному трафику.
- Shield-уведомление SmartCaptcha об обработке данных не скрывается.
- Client key публичный, но зависит от окружения: исходники его не содержат.
  Production-сборка получает значение через GitHub repository variable
  `SMARTCAPTCHA_CLIENT_KEY`, а приложение — через
  `VITE_SMARTCAPTCHA_CLIENT_KEY`.
- Server key остаётся только в окружении production API и во frontend не
  передаётся ни при сборке, ни в рантайме.
- API Stage 1–2 уже содержит нужный контракт. Stage 3 использует
  `/api/auth/sign-up`, `/api/auth/email-verification/resend` и
  `/api/auth/email-verification/confirm` без backend-правок.
- Юридическое согласие — одна обязательная непредзаполненная отметка с тремя
  отдельными ссылками:
  - `https://conwix.com/oferta.html`;
  - `https://conwix.com/privacy.html`;
  - `https://conwix.com/personal-data.html`.

Официальные контракты провайдера:

- [невидимая CAPTCHA](https://yandex.cloud/ru/docs/smartcaptcha/concepts/invisible-captcha);
- [React-компоненты](https://yandex.cloud/ru/docs/smartcaptcha/concepts/react);
- [назначение client/server keys](https://yandex.cloud/ru/docs/smartcaptcha/concepts/keys).

## Маршруты и пользовательский поток

### `/sign-up`

Публичная страница вне `CompanyLayout` содержит email, пароль, название
компании и обязательное юридическое согласие. Пароль проверяется на минимум
12 символов, название — на непустое значение и максимум 255 символов,
email — встроенной проверкой `react-hook-form`. Сервер остаётся источником
истины для окончательной валидации.

Первое нажатие submit не отправляет API-запрос. После локальной валидации
оно переводит невидимый виджет в активное состояние. Только callback
`onSuccess(token)` вызывает signup mutation с текущими значениями формы и
полученным токеном.

После `202` браузер делает `replace` на `/sign-up/email-sent`. Email не
передаётся в URL, query string или `localStorage`. Текст результата одинаков
для нового и уже занятого адреса и не раскрывает состояние аккаунта.

На странице входа появляется ссылка «Создать аккаунт», а на регистрации —
«Уже есть аккаунт? Войти».

### `/sign-up/email-sent`

Страница сообщает, что письмо отправлено, предлагает проверить входящие и
спам и содержит переход к повторной отправке. Она не показывает введённый
email и не обещает, что новый аккаунт был создан.

### `/resend-confirmation`

Публичная форма принимает только email. После `202` показывает тот же
нейтральный результат для неизвестного, подтверждённого и неподтверждённого
адреса. Так frontend сохраняет oracle-safe поведение backend.

### `/confirm-email?token=...`

Страница один раз читает токен из query string, немедленно удаляет query
через `history.replaceState` и выполняет POST подтверждения. Токен не
попадает в TanStack Query, `localStorage` или сообщения интерфейса.

Исходы:

| Результат API | Экран | Следующее действие |
|---|---|---|
| `200`, `outcome=confirmed` | короткое состояние успеха | `replace` на возвращённый `/onboarding` |
| `409`, already consumed | ссылка уже использована | перейти ко входу |
| `410`, expired/unknown | ссылка недействительна или истекла | запросить новое письмо |
| отсутствующий/пустой token | ссылка некорректна | запросить новое письмо |
| сеть/5xx | временная ошибка | повторить подтверждение без возврата секрета в URL |

Для безопасного повтора при transport/5xx токен остаётся только в памяти
страницы. Обновление вкладки после удаления query не повторяет запрос и
показывает путь к повторной отправке.

### `/onboarding`

Маршрут защищён `RequireAuth`, но расположен вне `/companies/:companyId` и
`CompanyLayout`: сразу после подтверждения companyId ещё не участвует в
адресе. До Stage 4 экран показывает начало подключения Ozon и объясняет,
что следующим шагом понадобятся название магазина, `Client-Id` и `Api-Key`,
но не содержит неработающей формы или фиктивной кнопки сохранения.

## Архитектура frontend

Изменения остаются в существующей фиче `apps/seller/src/features/auth`:

- `model/useSignUp.ts` — типизированная signup mutation;
- `model/useResendConfirmation.ts` — нейтральная resend mutation;
- `model/useConfirmEmail.ts` — одноразовый confirm POST;
- `lib/signupFailure.ts` — чистое отображение API-кодов в поля или общую
  ошибку;
- `lib/captchaFlow.ts` — чистый автомат состояний, не допускающий POST до
  успешного callback и повторную отправку одного токена;
- `lib/confirmationOutcome.ts` — отображение HTTP/outcome в одно из трёх
  пользовательских состояний;
- `ui/SignUpPage.tsx` — форма и координатор invisible CAPTCHA;
- `ui/EmailSentPage.tsx` — нейтральный результат;
- `ui/ResendConfirmationPage.tsx` — форма повторной отправки;
- `ui/ConfirmEmailPage.tsx` — погашение токена и три исхода;
- `ui/OnboardingStartPage.tsx` — защищённая граница следующего этапа.

Новый общий layout-примитив не создаётся: login и signup — только второе
повторение похожей карточки, а правила UI Kit выделяют примитив на третьем.
Checkbox остаётся локальной разметкой формы по той же причине. Существующие
`Button`, `Card`, `Input` и `StatusPanel` переиспользуются без `className`
наружу и без новых цветовых токенов.

`Root.tsx` только объявляет публичные маршруты и защищённый `/onboarding`.
Ни один экран Stage 3 не получает `companyId`, не создаёт company query key
и не использует `createCompanyApiClient`: auth endpoints по правилам проекта
вызываются через `apiPost` до выбора компании.

## Состояние SmartCaptcha

`SignUpPage` различает следующие состояния:

1. `idle` — форма редактируется, CAPTCHA не запущена;
2. `checking` — локальная форма валидна, виджет выполняет проверку;
3. `submitting` — получен токен, единственный POST выполняется;
4. `failed` — показана ошибка, виджет пересоздан для нового токена.

Форма блокирует повторный submit в состояниях `checking` и `submitting`.
Callback CAPTCHA принимает только непустую строку. `onTokenExpired`,
`onNetworkError`, `onJavascriptError` и закрытие challenge без успеха
очищают ожидающий токен, возвращают возможность повтора и не вызывают API.

После любого завершившегося API-запроса экземпляр виджета пересоздаётся
через изменяемый React `key`. Повторно отправлять тот же токен нельзя: Stage 2
и Yandex считают его одноразовым. Ошибка полей также не сохраняет токен «до
следующего submit».

## Ошибки и тексты

Backend-сообщение используется как безопасный fallback, а стабильные коды
получают понятное представление:

| Код/ситуация | Представление |
|---|---|
| `email_invalid` | ошибка поля email |
| `password_too_short` | ошибка поля пароля |
| `company_name_invalid` | ошибка названия компании |
| `legal_consent_required` | ошибка рядом с отметкой |
| `captcha_invalid` | «Не удалось подтвердить проверку. Попробуйте ещё раз» и новый токен |
| `registration_rate_limited` / 429 | «Слишком много попыток. Попробуйте позже» |
| `captcha_unavailable` / 503 | «Проверка временно недоступна. Попробуйте позже» |
| SmartCaptcha network/JS error | локальная ошибка до API и кнопка повтора |
| SMTP/неизвестная 5xx/сеть приложения | общая временная ошибка без деталей |

В UI не показываются server key, client IP, CAPTCHA token, confirmation
token, ответы Yandex или различие «адрес существует / не существует».

## Конфигурация и зависимости

`@yandex/smart-captcha` добавляется только в `apps/seller` с точной
production-версией и обновлением `package-lock.json`. Перед установкой
проверяются метаданные пакета и install scripts по существующей npm-политике.

Root host variable `SMARTCAPTCHA_CLIENT_KEY` пробрасывается в контейнер
`node-seller` как `VITE_SMARTCAPTCHA_CLIENT_KEY`. GitHub Actions передаёт
repository variable в frontend и e2e jobs. Production-сборка должна
fail-fast завершаться при пустом или не похожем на `ysc1_...` значении;
публичный ключ при этом закономерно присутствует в собранном JavaScript.

Автоматические тесты не требуют рабочего ключа и не загружают внешний
скрипт. Локальная разработка формы требует явно заданный dev client key;
в репозитории документируется имя переменной, но не production-значение.

## Тестовая стратегия

Работа идёт по TDD. Сначала появляются падающие проверки, затем минимальная
реализация.

### Модель и API

- типизированный MSW-handler принимает полный signup payload, включая
  `captchaToken`, и возвращает контрактный `202`;
- resend использует только email и одинаковый `202`;
- confirm различает `200`, `409`, `410` и transport/5xx;
- `signupFailure` проверяет все известные коды и безопасный fallback;
- `confirmationOutcome` проверяет все три продуктовых исхода.

### UI и безопасность состояния

- статический рендер формы содержит три точных юридических URL;
- checkbox не отмечен по умолчанию и связан с текстом согласия;
- чистый `captchaFlow` доказывает, что submit до успешного callback не
  выдаёт команду POST, а первый непустой токен выдаёт её ровно один раз;
- тот же автомат проверяет, что network/JS/expired callbacks не выдают POST,
  после ошибки позволяют повтор и увеличивают ключ нового экземпляра
  виджета;
- страница подтверждения удаляет token из URL до сетевого вызова;
- нейтральные экраны не содержат email и не различают существование
  аккаунта;
- `/onboarding` проходит через `RequireAuth` и не входит в CompanyLayout.

Статический UI проверяется через используемый в проекте
`renderToStaticMarkup`, интерактивная оркестрация — через чистый автомат без
добавления второго DOM test runner. HTTP идёт через типизированный
`openapi-msw`. Ручной `Response`, подмена глобального `fetch` и настоящий
запрос к Yandex запрещены.

Stage 3 не расширяет текущий seller Playwright сценарием регистрации:
локальный e2e не может получить production-токен Yandex, а backend Stage 2
не допускает обход защиты. Сквозной сценарий регистрации и онбординга по
ключам добавляется на Stage 6, как требует исходное задание. В этом пакете
браузерная связка покрывается обязательным production smoke.

### Полная проверка пакета

- focused Vitest тесты auth UI/model/lib;
- `make front-typecheck front-lint front-test front-knip front-build`;
- `make api-types-check` для подтверждения синхронности импортируемой схемы;
- полный `make ci-local`, включая backend и существующие 7 Playwright tests;
- внешний review пакета Stage 3 до merge.

## Rollout и эксплуатация

1. До push задать GitHub repository variable `SMARTCAPTCHA_CLIENT_KEY`
   предоставленным владельцем публичным client key и проверить только факт
   непустого значения/префикс, не печатая значение в logs.
2. Перед merge повторно проверить доступность трёх юридических URL и наличие
   production `SMARTCAPTCHA_SERVER_KEY` без чтения секрета.
3. Убрать внешнюю загрузку Google Fonts с юридических страниц `conwix.com`
   либо отдельно согласовать её с текстом политики. Сейчас страницы содержат
   запрос к `fonts.googleapis.com`, одновременно заявляя отсутствие
   трансграничной передачи; это блокирует публичное объявление регистрации,
   но не разработку приложения в этом репозитории.
4. После зелёного CI смержить и развернуть Stage 3.
5. Немедленно выполнить живой smoke на `https://app.conwix.com/sign-up`
   через реальный виджет и внешний почтовый ящик: `202`, доставка письма,
   переход по ссылке, открытая сессия и `/onboarding`.
6. Убедиться, что API развёрнут ожидаемым тегом, сервисы здоровы и pending
   migrations нет. Stage 3 миграций не добавляет.
7. При ошибке client/server pair, host validation, загрузки скрипта или
   доставки письма не объявлять регистрацию открытой; откатить frontend
   static artifact на предыдущий run, не меняя backend и данные.

Живой smoke создаёт настоящий аккаунт. Используется отдельный адрес-алиас,
а его последующая очистка выполняется только отдельным подтверждённым
действием после проверки отсутствия подключений и фактов.

## Риски и принятые компромиссы

- Официальный React-пакет добавляет одну frontend-зависимость, но убирает
  собственную реализацию lifecycle внешнего скрипта и его событий.
- Невидимая CAPTCHA не гарантирует отсутствие задания: подозрительный
  пользователь может увидеть challenge. Это сознательный баланс защиты и
  конверсии; обычному трафику отдельное действие не показывается.
- Сбой Yandex закрывает только новую регистрацию. Вход и существующие
  company-scoped экраны не зависят от frontend-виджета.
- Client key публичен и виден в bundle. Его хранение в GitHub variable —
  управление окружением, а не попытка сделать ключ секретом.
- Временный стартовый `/onboarding` не подключает Ozon. Он фиксирует
  правильную границу маршрутизации Stage 3 и заменяется рабочей формой в
  Stage 4 без изменения confirmation flow.
- Повтор после transport error теоретически может встретить уже погашенный
  токен, если ответ потерялся. UI покажет «уже использована» и отправит ко
  входу; повторно подтверждать адрес небезопасно и не требуется.

## Критерий готовности Stage 3

Stage 3 готов, когда все пункты его Definition of Done выполнены, package
review принят, CI зелёный, production использует ожидаемый client key, а
живой browser smoke подтвердил связку widget → server validation → email →
session → `/onboarding`. До устранения отмеченного расхождения юридических
страниц регистрация не объявляется публично открытой.
