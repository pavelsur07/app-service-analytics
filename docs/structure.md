# Структура репозитория

Живой документ. Обновляется в том же коммите, что и изменение структуры.

## Верхний уровень

```
app-service-analytics/
├── CLAUDE.md
├── README.md
├── Makefile              оркестрация Docker и вызов composer-/npm-скриптов;
│                         `make` без аргументов — список целей
├── docker-compose.yml    dev-окружение
├── docker-compose.prod.yml  описание prod-топологии: веб и воркер
│                         из одного образа; не выкладка
├── playwright.config.ts  один конфиг на репозиторий, проекты seller и admin
├── package.json          только @playwright/test под этот конфиг
├── bin/
│   └── review-prepare.sh сборка пакета для внешнего ревью (make review-prepare)
├── traefik/
│   └── dynamic.yml       статическая маршрутизация по доменам (file provider)
├── .dockerignore         контекст сборки — корень репозитория
├── docker/
│   ├── nginx/            vhost: *.conwix.localhost снаружи,
│   │                     *.conwix.internal внутри сети
│   └── php/
│       └── Dockerfile    один файл, стадии base / prod-deps / prod / dev;
│                         выбор через --target
├── docs/
│   ├── adr/
│   ├── plan/
│   ├── structure.md
│   ├── patterns.md
│   └── operations-checklist.md
├── api/                  Symfony
├── apps/
│   ├── seller/           app.conwix.com
│   └── admin/            admin.conwix.com
├── packages/
│   └── api-schema/       OpenAPI + сгенерированные TS-типы
└── .github/
    └── workflows/
        └── ci.yml        конвейер: фильтры по путям, кэш, публикация образа
```

**Конвейер — один файл, шесть задач.** `changes` считает диф и отдаёт
два флага; `backend` и `frontend` идут под этими флагами; `contract`
и `e2e` — без условий, всегда. Завершает `image`: собирает стадию `prod`
из `docker/php/Dockerfile` и публикует в ghcr с тегом сборки, только
с `master`; там же проверяется, что в опубликованном образе нет
инструментов разработки. Статика фронтенда уезжает артефактом из задачи
`e2e`. Развёртывание в конвейер не входит.

Почему фильтры именно такие и почему контрактные проверки выведены
из-под них — `patterns.md`, раздел «Конвейер».

Лендинг `conwix.com` живёт в отдельном репозитории: другой цикл релизов,
другие люди, другой стек. Связывать его выкладку с выкладкой продукта незачем.

**Почему монорепозиторий.** Контракт между API и фронтендом проверяется
генерацией типов; в разных репозиториях это означает публикацию пакета
и версионирование — расход, не оправданный при одном разработчике.
Изменение эндпоинта и его потребителя попадают в один коммит.

**Платим:** CI прогоняет обе половины на любое изменение (лечится фильтрами
по путям); разделение репозиториев позже стоит день и теряет общую историю.

### Два имени у одного хоста

Снаружи, из браузера разработчика — `app.conwix.localhost`
и `admin.conwix.localhost`. Внутри docker-сети эти адреса недостижимы:
по RFC 6761 резолверы отображают весь домен `.localhost` в loopback,
игнорируя DNS. Поэтому у тех же vhost'ов есть вторые имена
`app.conwix.internal` и `admin.conwix.internal` — их используют
контейнеры, обращающиеся друг к другу по HTTP, в частности Playwright.

Подробности и отвергнутые варианты — в `patterns.md`, раздел
«Сеть окружения».

## api/ — Symfony

```
api/
├── bin/
├── config/
├── migrations/           одна папка на весь проект
├── public/
├── src/
│   ├── Shared/
│   ├── Identity/
│   └── Ingestion/
├── tests/
├── deptrac.php
├── phpstan.neon
├── phpstan-baseline.neon
├── .php-cs-fixer.dist.php
└── composer.json
```

`config/reference.php` порождается Symfony при сборке контейнера
и в репозитории не отслеживается: его содержимое зависит от окружения
последней сборки (под `--env=test` пропадает блок `when@dev`), поэтому
отслеживаемый он делал дерево грязным после каждого прогона тестов.
Проект им не пользуется — конфигурация вся в YAML, `App::config()`
не вызывается, PHPStan смотрит только `src` и `tests`.

Рецепт `doctrine/doctrine-bundle` заводит по умолчанию `src/Entity/`
и маппинг на неё в `config/packages/doctrine.yaml` — этой папки в проекте
нет и не будет: сущности лежат в `Domain/` соответствующего модуля,
маппинг в `doctrine.yaml` под это уже переписан. Рецепт может завести
её заново при установке любого пакета — тогда её снова удаляют
(проверка в `api/bin/` это ловит).

Стандартной папки `src/Controller/` из шаблона Symfony нет: маршруты
находятся по тегу автоконфигурации сервиса (атрибут `#[Route]`), а не
по пути к файлу, поэтому контроллер всегда лежит в `Ui/` своего модуля —
сейчас это `Shared/Ui/Controller/` для двух эндпоинтов-заглушек, ничьей
предметной логики не касающихся.

Модули — только спроектированные. Catalog, Costing, Finance, Planning,
Inventory обсуждались, но решения по ним не приняты и папок под них нет.
Модуль появляется вместе с ADR и первой задачей, а не заранее.

### Внутри модуля

```
Identity/
├── Domain/           сущности, Value Object, доменные сервисы,
│                     интерфейсы репозиториев
├── Application/      сценарии, DTO, обработчики сообщений,
│                     Facade — публичный контракт модуля
├── Infrastructure/   реализации репозиториев, SQL-запросы чтения,
│                     внешние клиенты
└── Ui/               контроллеры, консольные команды
```

Ingestion дополнительно:

```
Ingestion/Infrastructure/Connector/
├── Wildberries/
└── Ozon/
```

Общая абстракция коннектора появляется после второго коннектора,
не до первого.

### Почему так

Направление зависимостей из ADR совпадает с путями к файлам, поэтому
Deptrac проверяет его механически: `Domain` не знает про `Infrastructure`,
`Ui` не обращается в чужой модуль, вход в модуль — только через
`Application/Facade`.

**Миграции — одна папка на проект.** Doctrine исполняет их в общем порядке;
разделение по модулям ломает предсказуемость при связанных изменениях.
Плата — папка станет длинной.

**`Shared` — только технический слой.** Как только туда попадает что-то
предметное, модуль перестал быть модулем. За этой папкой нужно следить:
она естественным образом превращается в свалку.

**Не заводить** папок `Services`, `Helpers`, `Utils`, `Managers`,
`Common`. Они не про предметную область и притягивают код, которому
не нашлось места, — а место обычно есть, просто неочевидное.

## tests/

```
tests/
├── Unit/
├── Integration/
├── Functional/
├── E2e/
├── Support/
│   └── Builder/
└── Fixtures/
    └── Marketplace/
        ├── wildberries/
        └── ozon/
```

Внутри уровней структура зеркалит `src/` — по упавшему тесту сразу видно,
что сломалось.

`Support/Builder` общий на все уровни: билдер умеет и собрать объект
в памяти для unit-теста, и сохранить для integration.

`Fixtures/Marketplace` — сохранённые реальные ответы площадок. Когда
площадка меняет формат, обновляется файл и падают ровно затронутые тесты.

**`E2e/` — не PHPUnit по существу.** Реальный e2e — Playwright поверх
собранного фронтенда (`apps/*/tests/e2e`, конфиг в корне репозитория).
Здесь остаётся один помеченный skipped тест-заглушка, чтобы набор PHPUnit
был объявлен и зелёным сам по себе, не завися от фронтенда.

## apps/ — фронтенд

Обе половины устроены одинаково:

```
apps/seller/
├── src/
│   ├── app/          роутер, провайдеры, точка входа
│   ├── shared/       ui, форматирование, хелпер ключей кэша,
│   │                 разбор ошибок API
│   ├── api/          клиент, привязанный к компании
│   └── features/
│       └── accounts/
├── index.html
└── vite.config.ts
```

Внутри фичи — `ui/`, `model/` (хуки и запросы), `lib/` (чистые функции).
Три папки, не больше.

**Имена фич совпадают с именами модулей бэкенда.** При разборе обращения
открываются `features/<имя>` и `src/<Имя>` без выяснения соответствия.

**`shared/` содержит ровно то, что правила проекта делают обязательно
единственным:** хелпер ключей кэша с `companyId`, форматирование денег,
разбор ошибок API. Папка и есть механизм обеспечения единственности.

Фичи создаются по мере появления экранов. Пустых папок нет.

**Текущее состояние.** До первой настоящей фичи `features/` и `app/`
ещё нет — заводить их сейчас означало бы абстрагироваться до первого
случая. Но `api/` и `shared/` уже появились: без них не собрать
зависимости и проверки (клиент — чтобы запретить голый `fetch`,
`lib/` — под обязательный тест форматирования).

```
apps/seller/
├── src/
│   ├── App.tsx                        три состояния: загрузка, ошибка, данные
│   ├── main.tsx                       точка входа
│   ├── index.css                      @import "tailwindcss"
│   ├── api/
│   │   ├── client.ts                  единственное место с fetch — apiGet()
│   │   └── schema.ts                  реэкспорт типов из packages/api-schema
│   └── shared/
│       └── lib/
│           └── formatMinorAmount.ts   копейки → отображаемая сумма
├── tests/e2e/                         Playwright-сценарий этого приложения
├── eslint.config.js                   границы импортов + свои правила
├── knip.json
├── index.html
└── vite.config.ts
```

`apps/admin` устроен так же и не делит код с `apps/seller`: это два
независимых приложения, различаются только эндпоинтом и подписью
на экране. У каждого свой сквозной сценарий в `tests/e2e/` — стартовый
экран и три поля ответа своего эндпоинта.

**Конфиг Playwright один, в корне репозитория** — `projects` seller
и admin, `testDir` каждого указывает в своё приложение. Так и было
задумано «когда сценарии понадобятся обоим»; момент наступил вместе
со вторым сценарием. Почему конфиг не может лежать в приложениях
и что из этого следует для контейнера — `patterns.md`, раздел
«Playwright — общий конфиг».

## packages/api-schema

```
packages/api-schema/
├── package.json      devDependency openapi-typescript, скрипт generate
├── openapi.json      выгружается из Symfony (make api-doc-export)
└── src/schema.d.ts   генерируется из openapi.json (make api-types)
```

Оба файла (`openapi.json`, `src/schema.d.ts`) — в репозитории.
`make api-types-check` перегенерирует оба заново и проверяет отсутствие
разницы: сначала `openapi.json` против кода контроллеров, потом
`schema.d.ts` против `openapi.json` — расхождение на любом из двух шагов
роняет проверку.

Отдельный пакет, а не папка внутри приложения, потому что потребителей два
и ни один не главнее — `openapi-typescript` ставится один раз сюда,
не в оба приложения.

**`openapi-typescript` не установлен в оба приложения.** `npm workspaces`
для одного реэкспорта — избыточная перестройка окружения (у каждого
приложения свой контейнер и свой `node_modules`, п. «Node-окружение»
`patterns.md`); вместо этого `apps/*/src/api/schema.ts` реэкспортирует
типы относительным путём (`../../../../packages/api-schema/src/schema`),
для чего `packages/` домонтирован в `node-seller`/`node-admin` рядом
с `apps/`.
