# Этап 0.5 — экран «План продаж» в apps/seller

Общий план — `sales-planning-stage0.md`, API — этап 0.4 (ADR-040, ADR-041).

## Результат

Продавец в своём кабинете:

1. видит список планов компании — название, период, статус, число SKU,
   штуки, выручка;
2. создаёт черновик — подключение, название, период;
3. открывает план и добавляет SKU: ищет товар в каталоге подключения,
   вводит штуки за период и РРЦ; повторный ввод того же SKU — перераскладка;
4. смотрит план с группировкой «весь период / месяц / неделя / день».

Правка отдельного дня — этап 0.6, утверждение — 0.7, импорт — 0.8.

## Решения внутри этапа

- **Адреса — про предметную область** (`structure.md`): `sales-plans`
  и `sales-plans/:planId`; пункт меню «План продаж».
- **Фича `features/sales-planning`** — `model` (хуки TanStack Query),
  `lib` (чистые функции), `ui` (экраны). Импорт из других фич запрещён
  линтером, поэтому разбор суммы `parseAmountToMinor` переезжает
  из `features/costs/lib` в `shared/lib` — вместе со своим тестом.
- **Ключи кэша — только `companyQueryKey`** (§7):
  `['company', id, 'sales-planning', <сущность>, параметры]`.
  Мутации инвалидируют весь раздел `sales-planning` компании.
- **Сеть — только `createCompanyApiClient`**, типы ответов — только
  из `api/schema` (§10).
- **Деньги**: РРЦ вводится рублями и переводится в копейки строкой
  (`parseAmountToMinor`), выручку считает сервер, на экране — только
  `formatMinorAmount`; арифметики над деньгами в компонентах нет (§10).
  Валюта — `RUB`, как у себестоимости: подключения сегодня только Ozon.
- **Версия** (ADR-008): ввод SKU отправляет версию из последнего ответа;
  409 — сообщение «план изменил кто-то ещё» и перечитывание плана.
- **Отказ сервера показывается его текстом** (`patterns.md`).
- **Сетка**: строки — SKU, колонки — корзины группировки (у всех SKU
  одни и те же дни — строки плотные); при «день» таблица прокручивается
  по горизонтали. Обычная `<table>`, без TanStack Table: сортировки
  и фильтрации на клиенте нет (`patterns.md`, «Списки и таблицы»).
- **Страницы**: «Ещё» по `nextCursor` — и для списка планов, и для SKU.

## Шаги

1. `shared/lib/parseAmountToMinor.ts` + тест; `features/costs` импортирует
   оттуда.
2. `features/sales-planning/lib/salesPlan.ts`: подписи статусов
   и группировок, проверка формы черновика (даты по порядку, период
   не длиннее 184 дней), разбор штук (целое ≥ 0, ≤ 1 000 000).
3. `features/sales-planning/model`: `useSalesPlans`, `useCreateSalesPlan`,
   `useSalesPlan`, `useSetSalesPlanSkus`, `useCatalogSkus`.
4. `ui/SalesPlansPage.tsx` (список и форма черновика),
   `ui/SalesPlanPage.tsx` (шапка, группировка, сетка, ввод SKU).
5. Маршруты в `app/Root.tsx`, пункт в `app/Sidebar.tsx`.
6. Тесты.

## Тесты

- Ключи кэша: содержат `companyId`, различают компании, план, группировку,
  курсор (§10 «изоляция кэша при смене компании»).
- Чистые функции: `parseAmountToMinor` (перенесённый тест), проверка
  формы черновика, разбор штук, подписи.
- Разбор ошибок API — уже покрыт `ApiError.test.ts`; новый код
  его переиспользует.
- Сквозной сценарий Playwright не меняется: один на приложение (§10).

- Vitest: ключи кэша и чистые функции.
