# product-research-ozon — этап 5: доставка, повторы и восстановление

Дата: 01.11.2026. Статус: реализация. Основание: ADR-050, этапы 1–4 приняты.

## Результат и границы

Пользователь создаёт запуск проекта; Symfony атомарно сохраняет замороженные
параметры и outbox. После commit уведомление через существующий Messenger
async_ingestion вызывает relay. Company-scoped фоновая команда подбирает
недоставленное и сверяет известные запуски даже при потерянном уведомлении.
Пользовательские HTTP-запросы читают только локальные данные и не вызывают Python.
Транспорт задаётся существующим TransportNamesStamp, messenger.yaml не меняется;
этот способ доставки реализует уже принятое решение ADR-050.

Python принимает опубликованный v1 после commit, создаёт месячные задания,
worker выполняет один ограниченный шаг страницы. Паузы сохраняются в БД,
не удерживают процесс/транзакцию. Один серверный токен, общий provider gate,
явный allowlist компаний, company/source scope. Новых пакетов, Facade,
транспортов или брокеров нет. Два точных Messenger-адаптера Infrastructure
выделены Deptrac в узкий слой; остальные разрешения не расширяются. Одна миграция Symfony и одна Alembic на задачу.

Этот этап реализует статусы/историю запусков и дозагрузку непокрытых месяцев
того же проекта. Межпроектный кэш, сводные статусы проекта и политика повторного
использования снимков — этап 6, UI — 7, production Python/реальный egress — 8.
Существующие project responses до этапа 6 остаются контрактом черновика;
новые run endpoints явно возвращают состояние запуска. Флаг модуля закрыт.

## Правила выполнения

- PHP: UUIDv7 requestId — ключ повторного пользовательского запроса; server run ID
  генерируется приложением. UNIQUE(company, project, requestId), отдельное UNIQUE
  для одного активного запуска проекта. Повтор того же ввода возвращает прежний
  запуск, другого — 409. Проект блокируется до проверки/фиксации параметров.
- Run и намерение доставки — одна ORM-транзакция. Сбой уведомления не откатывает
  принятый run. Relay ставит DB lease и отмечает доставку только после проверенного
  202 с правильными company/run/source. Потеря ответа допускает повтор POST.
- Python: UNIQUE(company,run), hash канонических проверенных параметров;
  другой payload — conflict. Run + до 24 jobs + начальные snapshot ID — один commit.
  202 — receipt приёма, повтор receipt не выдаётся за текущий прогресс.
- Даты/дни/partial неизменны после принятия. Задержанная доставка через полночь
  допускает уже зафиксированный неполный срез до прошедшего дня, не расширяя его
  до нового вчера/конца месяца. Будущих дат нет, полные месяцы не режутся.
- Закрытые ready-месяцы того же проекта остаются покрытыми при дозагрузке;
  текущий partial не считается окончательным покрытием. В активный run добавленные
  позже периоды не попадают. Новые задачи не смешивают старые страницы.
- Job lease и snapshot lease согласованы fencing: commit страницы/manifest
  дополнительно проверяет текущий job owner/попытку/дедлайн внутри SQL-транзакции.
  Старый worker не публикует после потери аренды/ротации/смены snapshot.
- Справедливый выбор компаний и месяцев через явную системную очередь с
  FOR UPDATE SKIP LOCKED; межарендаторный выбор только в worker, с allowlist.
- Network/5xx и временные инфраструктурные отказы: до трёх повторов шага сверх
  начального (60/120/240 секунд), успех шага сбрасывает счётчик. Курсор/ID-проверка
  сохраняются. 202/429 не тратят network budget, Retry-After не сокращается.
- Полнота/некорректный ответ: одна новая попытка месяца целиком, новый snapshot ID;
  повторная ошибка — incomplete_snapshot. Старые страницы остаются в истории.
- Дедлайн месяца — 24 часа от приёма; ожидание за дедлайн не вызывает новый API.
  Ready, закоммиченный до дедлайна, восстанавливается после потери ack и позже.
- 401/403 ставят auth pause подключения. Остальные месяцы запуска завершаются
  credentials_rejected без новых API; уже готовые результаты сохраняются.
  Другие ожидающие запуски подбираются на paused gate без ожидания дальнего retry.
  Ротация generation допускает новую попытку, старый процесс не снимает pause.
- Progress revision монотонна, обновления PHP принимаются только для совпавших
  company/run/source/месяцев и новой revision. Ошибка не маскируется пустым успехом.
  Сырые строки, суммы, S3-ключи и секреты в HTTP/логи не попадают.

## 5.1. Чистая политика повторов и контракт — TDD

Цель: воспроизводимые решения без I/O/sleep.
Задачи: frozen run/job DTO, валидация месяцев, retry/deadline policy, публичные
коды v1. Готовность: U01–U06 и C01, начальный Red до реализации.

## 5.2. Приём и устойчивая очередь Python

Цель: одна логическая работа при повторах и восстановление после crash.
Задачи: одна Alembic, atomic admission, fair claim/lease, snapshot job fencing,
checkpoint/restart, progress/snapshot metadata v1, явные enable/allowlist/budgets.
Готовность: I01–I08/C02; legacy этапов 1–4 не сломан.

## 5.3. Запуск и outbox Symfony

Цель: принять намерение пользователя без синхронного Python HTTP.
Задачи: Entity/Builder run и месячных параметров, одна Doctrine-миграция,
ORM start/idempotency/активный run, Messenger notification после commit,
фоновый relay/poll с DBAL lease и ограниченными Query/DTO.
Готовность: P01–P05, F01–F04; все запросы company-scoped.

## 5.4. Runtime и сквозная приёмка

Цель: несколько месяцев с ошибками проходят путь PHP→Python→S3→PHP progress.
Задачи: выключенный по умолчанию worker, один шаг за тик, восстановление,
конкурирующие процессы/соединения, fixture-only HTTP smoke и генерация OpenAPI/TS.
Готовность: I09–I12, C03; исходные фикстуры не меняются, live MPStats нет.

## 5.5. Проверки, независимое ревью и доставка

Цель: проверенный полный diff и постоянный отчёт.
Задачи: PHP/Python-гейты, up/down/up, полный изолированный db-rebuild-check до
ревью, новые независимые Claude либо Codex CLI 5A/5B при недоступном Claude,
разбор/повтор, зелёный CI/PR/merge, явная Symfony-миграция после штатного deploy
гейта, production smoke при закрытом флаге, документальное закрытие.
Готовность: G01–G08; Python production-активация не переносится из этапа 8.
