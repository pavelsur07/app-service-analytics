# Поэтапный план устранения угроз безопасности Conwix

Дата: 25 октября 2026 года. Статус: проект плана, реализация не начата.

> Для исполнителя: выполнять задачи по этапам с `superpowers:executing-plans`;
> независимое ревью проводить по `CLAUDE.md` и `docs/review-package-template.md`.
> Чекбоксы обозначают будущую работу, а не уже выполненные проверки.

**Цель:** устранить четыре угрозы из [отчёта](securety_chek.md), закрыть
пробелы проверок и отдельно реализовать второй фактор администраторов.

**Архитектура:** сохранить разделение сессионных seller/admin, Bearer-контура
расширения и внутреннего сервисного API. Отзыв выполнять в транзакционной
границе Identity, CSRF-защиту — централизованно перед изменяющими запросами,
секрет расширения оставлять в доверенных контекстах браузера.

**Стек:** PHP 8.4, Symfony 7.4, Doctrine/PostgreSQL, React/TypeScript,
Chrome MV3, Docker Compose, существующие цели Makefile и GitHub Actions.

**Основания:** `AGENTS.md`, применимые разделы `CLAUDE.md`, ADR-007,
ADR-010, ADR-017, ADR-037. Исходный отчёт — статический анализ, не
подтверждение эксплуатации на работающем стенде.

## 1. Что установлено и какие решения нужны

| Пункт отчёта | Уточнение по репозиторию | Решение плана |
|---|---|---|
| P1: токены живут после сброса пароля | Это явно принятое поведение ADR-037, включая отвергнутую альтернативу отзыва | Сначала согласовать пересмотр ADR-037; затем атомарно отзывать токены пользователя во всех компаниях |
| P1: CSRF с соседнего поддомена | Seller/admin используют cookie-сессии; клиенты отправляют JSON, но DELETE бывает без тела | Защищать все изменяющие сессионные запросы, включая запросы без тела и login/logout |
| P2: storage доступен content scripts | `browserStorage()` возвращает `chrome.storage.local`; worker и popup — доверенные потребители | Установить `TRUSTED_CONTEXTS` и исключить гонки инициализации |
| P3: Zod и аудит | `make audit` проверяет Composer, seller, admin, api-schema; extension отсутствует, хотя CI уже устанавливает его зависимости | Обновить уязвимый путь зависимостей и добавить extension в обязательный аудит |
| MFA | ADR-017 откладывает TOTP только до первого администратора вне владельцев продукта | Отдельный этап с ADR, enrollment и восстановлением; при достижении условия ADR-017 этап становится блокирующим |

До начала **реализации**, одним согласованием необходимо утвердить:

1. Изменение ADR-037: сброс пароля завершает и сессии, и доступ всех
   расширений пользователя, с обязательным переподключением браузеров.
   Уточнить ADR-010 и текст уведомления; не маскировать это как исправление
   кода без изменения принятого решения.
2. Контракт CSRF: предлагается обязательный `X-Conwix-Request: 1` для
   изменяющих запросов seller/admin, проверка точного Origin и отклонение
   неподходящего Content-Type. Это изменение контракта существующих клиентов.
3. Для MFA: отдельное уточнение ADR-017/ADR-007, TOTP с резервными кодами,
   порядок подключения существующих администраторов и восстановления доступа.
   Выбор новой библиотеки, если потребуется, включить в то же согласование
   с точным пакетом и версией до установки. Не писать собственную криптографию.

Подготовка этого документа ничего из перечисленного не утверждает.
Новых внешних сервисов, межмодульных Facade, изменений очереди или фактов
план не предполагает. Обнаружение необходимости таких решений возвращает
соответствующий этап к плановому согласованию.

## 2. Порядок и границы поставок

| Этап | Приоритет | Зависимости | Проверяемый результат |
|---|---|---|---|
| 0. Базовая проверка и решения | До изменений | Нет | Воспроизводимые сценарии, матрица маршрутов и согласованные изменения правил |
| 1. Отзыв после сброса пароля | P1 | 0, пересмотр ADR-037 | Старые Bearer-токены получают 401 |
| 2. Защита сессионного API от CSRF | P1 | 0, согласованный контракт | Запрос с соседнего origin не меняет данные |
| 3. Изоляция storage расширения | P2 | 0 | Content script не читает секрет; worker/popup работают |
| 4. Зависимости и аудит | P3 | 0 | Исправлен Zod; CI проверяет extension |
| 5. MFA администраторов | Архитектурный риск | 2 и отдельное решение MFA | Пароль без второго фактора не открывает системный контур |
| 6. Повторная проверка и закрытие | Для каждой поставки и всей программы | Поставленные этапы | Доказательства устранения и зафиксированные остаточные риски |

Предлагается отдельный PR на этап; этап 2 допустимо разбить на совместимое
обновление клиентов и последующее включение серверного ограничения.
Не объединять обе P1 с большим MFA-изменением. Этапы 1–4 технически могут
готовиться независимо после этапа 0; порядок поставки по умолчанию — таблица.
Если условие обязательного MFA уже наступило, не выдавать новые аккаунты
администраторов до этапа 5; после P1 этап 5 получает приоритет над P2/P3.

Альтернативы: единый большой PR усложняет проверку и откат; исправления
только на Nginx не обеспечивают атомарность отзыва и защиту storage.
Поэтому выбран набор небольших поставок с тестами на каждой границе.

## 4. Этап 1. Атомарный отзыв токенов при сбросе пароля

**Изменяемые файлы:**

- `api/src/Identity/Infrastructure/Repository/DoctrinePasswordResetTokenRepository.php`;
- `api/src/Identity/Infrastructure/Repository/DoctrineExtensionTokenRepository.php`
  и `api/src/Identity/Application/IssueExtensionTokenAction.php` — граница гонки выпуска;
- `api/tests/Integration/Identity/DoctrinePasswordResetTokenRepositoryTest.php`;
- `api/tests/Integration/Identity/DoctrineExtensionTokenRepositoryTest.php`;
- `api/tests/Functional/Identity/PasswordResetControllerTest.php`,
  `api/tests/Functional/Identity/ExtensionTokenControllerTest.php`;
- `docs/adr/0037-password-reset.md`, `docs/adr/0010-extension-token.md`,
  уведомление `api/src/Identity/Infrastructure/Notification/MailPasswordResetEmailSender.php`.

**Интерфейсы:** сохранить публичный
`resetPassword(string $tokenHash, string $passwordHash, DateTimeImmutable $now): ?string`
и контракт HTTP сброса. Массовый отзыв по userId — только внутри явно
описанной pre-auth границы сброса, не новый общий метод company-репозитория
без companyId. Если понадобятся новые классы, ограничить доступ Deptrac.

- [ ] Добавить падающие integration/functional тесты: у A есть токены
  двух компаний, у B — свой; после сброса A оба его токена получают 401,
  токен B продолжает работать. Старые сессии A завершаются, новый пароль
  позволяет войти и выпустить рабочий токен.
- [ ] В существующей транзакции после успешного погашения ссылки обновить
  все ещё не отозванные `extension_token` пользователя: `revoked_at = now`,
  `revoked_by_user_id = userId`. Уже записанный след отзыва не перезаписывать.
  Смена пароля, погашение ссылок, отзыв и аудит должны коммититься вместе.
- [ ] Проверить rollback при ошибке записи: старый пароль и состояние
  токенов сохраняются, ссылка не расходуется частично. Невалидная,
  истёкшая или повторно использованная ссылка не отзывает ничего.
- [ ] Закрыть гонку выпуска и сброса общей транзакционной сериализацией
  по пользователю и повторной проверкой актуальности сессии в границе
  выпуска. Одной блокировки недостаточно: запрос, прошедший аутентификацию
  до сброса и ожидающий блокировку, не должен выпустить действующий токен
  после него. Использовать единый порядок блокировок, без задержек-sleep
  в тестах; проверить оба порядка на независимых соединениях БД.
- [ ] Гарантию определить точно: новые проверки Bearer после commit
  сброса отвергают прежние токены. Запрос, уже прошедший аутентификацию до
  commit, не считать автоматически отменённым; проверить последствия
  таких запросов и явно записать границу гарантии.
- [ ] Обновить ADR и письмо: после сброса требуется переподключить
  расширения. Не выполнять массовый отзыв у всех пользователей системы;
  сбросы, произошедшие до выкладки, не считать защищёнными задним числом.
- [ ] Выполнить backend-проверки раздела 10 и обязательное ревью.

**Готовность:** подтверждены 401, изоляция пользователей, rollback,
конкурентный выпуск и отсутствие повторного изменения следа отзыва.
Схема БД по умолчанию не меняется; если для корректной границы понадобится
миграция, включить её в этот этап с Entity, down и `db-rebuild-check`.

**Выкладка и откат:** проверить сброс на специально заведённом тестовом
аккаунте. При откате кода не восстанавливать отозванные секреты; браузеры
подключаются новым токеном. Приостановка фонового сбора цен после сброса —
ожидаемый результат, который должен быть объяснён пользователю.

## 5. Этап 2. Централизованная CSRF-защита seller/admin

**Изменяемые/новые файлы:**

- новый `api/src/Identity/Ui/EventListener/SessionRequestProtectionSubscriber.php`;
- `api/config/packages/security.yaml`, `api/config/services.yaml` и конфигурация
  окружений — только где необходимо подключение/параметры защиты;
- `apps/seller/src/api/client.ts`, `apps/admin/src/api/client.ts`;
- новые тесты клиентов рядом с ними и
  `api/tests/Functional/Identity/SessionRequestProtectionTest.php`;
- существующие Auth/Admin/PasswordReset functional-тесты и
  `apps/admin/tests/e2e/admin.spec.ts`, `apps/seller/tests/e2e/seller.spec.ts`;
- источник OpenAPI и сгенерированные контракты при изменении описания API.

**Правила предлагаемого контракта:**

| Запрос | Требование |
|---|---|
| Изменяющий seller/admin | `X-Conwix-Request: 1` обязателен, независимо от наличия тела и текущей сессии |
| Origin присутствует | Только точное совпадение scheme/host/port с origin своего контура; `null`, соседние и поддельные suffix-host отклоняются |
| Origin отсутствует | Проверить точный origin Referer, если он есть; без обоих разрешать только при обязательном специальном заголовке и закрытом CORS |
| Тело JSON API непустое | Требовать `application/json` с допустимым charset; простые `text/plain`, form-urlencoded и multipart не принимать |
| POST/DELETE без тела | Не требовать фиктивного JSON-тела; заголовок и правила origin обязательны |
| GET/HEAD | Только чтение; никаких изменений состояния |
| OPTIONS | Корректная обработка preflight без изменения состояния и без разрешения чужого origin |
| `/api/extension/`, `/api/internal/` | Собственная Bearer-аутентификация; освобождение только точными границами этих контуров, а не по наличию Authorization |

Выбор заголовка вместо отдельного CSRF-токена опирается на запрет CORS
для чужих origin и невозможность простого браузерного запроса добавить
такой заголовок. Заголовок не является секретом. Точный Origin —
дополнительная защита; SameSite и `Sec-Fetch-Site: same-site` сами по себе
не закрывают соседний поддомен. Обоснование —
[OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

- [ ] Написать падающие тесты: запрос SuperAdmin с соседнего HTTPS-origin
  и JSON в `text/plain` не создаёт администратора; проверить отсутствие
  строки в БД и побочных эффектов. Повторить с `application/json` и
  поддельным специальным заголовком: неверный Origin всё равно отвергается.
- [ ] Покрыть матрицу: отсутствующий/неверный заголовок, `Origin: null`,
  отсутствие Origin и оба варианта Referer, порты dev, чужой admin/seller
  origin, все изменяющие методы, login/logout и публичные pre-auth формы.
  Наличие произвольного Bearer-заголовка не должно обходить защиту сессии.
- [ ] Реализовать subscriber до побочных эффектов, включая json_login
  и logout firewall; приоритет события проверить functional-тестами.
  Плохой Origin/защитный заголовок возвращает JSON 403, неподходящий тип
  непустого тела — JSON 415 после прохождения защитных проверок.
- [ ] Добавить заголовок во все изменяющие вызовы двух API-клиентов;
  companyClient продолжает пользоваться seller-клиентом. Тесты — через
  типизированный MSW, без подмены глобального fetch.
- [ ] Проверить запросы расширения и внутреннего сервисного контура:
  корректный токен работает без браузерных CSRF-заголовков, неверный
  токен/чужая компания по-прежнему отклоняются своей защитой.
- [ ] Проверить реальные Nginx/Traefik на тестовом стенде: админский API
  закрыт на seller-хосте, Origin/Referer не переписываются, произвольные
  Host/X-Forwarded-* не определяют доверенный origin.
- [ ] Обновить контракт, тестовые помощники и e2e; выполнить проверки
  backend, seller, admin, API и независимое ревью раздела 10.

**Готовность:** браузерный сценарий с тестового соседнего origin отклонён
на стенде, штатные seller/admin сценарии проходят. CORS не разрешает
чужие origin с credentials и специальным заголовком. Администратора нельзя
создать простым запросом или обходом ранней обработки firewall.

**Выкладка:** сначала выпустить клиентов с заголовком, затем включить
серверное требование. Старым вкладкам потребуется обновление; при 403
показать понятную ошибку без бесконечных повторов. При несовместимости
выпускать исправление клиента/защиты; возврат уязвимой версии сервера
считать повторным открытием P1, а не успешным завершением этапа.

## 6. Этап 3. Закрыть секрет расширения от content scripts

**Файлы:** `apps/extension/src/shared/connection.ts`,
`apps/extension/src/shared/chrome.d.ts`,
`apps/extension/src/background/index.ts`, точка входа
`apps/extension/src/popup/main.tsx`, тесты рядом с connection и background.
`apps/extension/manifest.config.ts` менять только при подтверждённой
необходимости обозначить минимальную поддерживаемую версию Chrome.

- [ ] Добавить типизированный вызов
  `chrome.storage.local.setAccessLevel({ accessLevel: 'TRUSTED_CONTEXTS' })`.
  Сохранить storage.local и существующее подключение при обновлении.
  API и ограничение доступа описаны в
  [документации Chrome](https://developer.chrome.com/docs/extensions/reference/api/storage).
- [ ] Выделить общую инициализацию с Promise готовности для trusted-контекстов;
  зарегистрировать слушатели worker синхронно на верхнем уровне, но доступ
  к секрету и обработку сообщений/alarms выполнять после успешного ограничения.
  Защитить также путь popup, который может обратиться к storage независимо.
- [ ] Не ограничиваться `onInstalled`/`onStartup`: проверить обновление,
  пробуждение worker и прямой запуск popup. При отказе API не продолжать
  операции с секретом и не возвращать доступ к untrusted-контекстам.
- [ ] Тестировать порядок инициализации, отказ setAccessLevel и сообщения,
  пришедшие до готовности. Прежние connection/catalog/priceSync сценарии
  должны продолжать работать после установки ограничения.
- [ ] Убедиться, что ответы runtime сообщений не содержат token или
  исходную запись connection. Не добавлять «универсальное чтение storage»
  через worker: это обошло бы установленную защиту.
- [ ] Проверить в настоящем Chromium: content script не может прочитать
  секрет; popup и worker могут; подключение сохраняется после рестарта;
  обновление установленной предыдущей версии также закрывает storage.
  Использовать локальные страницы/фикстуры, без запросов к кабинетам площадок.
- [ ] Выполнить проверки extension и ревью раздела 10.

**Готовность:** доказана браузерная изоляция, а не только вызов API в моке;
нет токена в сообщениях, DOM и логах. Риск выполнения кода в самом trusted
worker/popup остаётся за границами этого исправления.

**Выкладка:** новая версия расширения, фиксация версии с защитой; старая
установленная версия остаётся уязвимой до обновления. Уже украденный токен
ограничение storage не отзывает — применять штатный отзыв/сброс из этапа 1.
Откат расширения к версии без ограничения снова открывает P2.

## 7. Этап 4. Устранить уязвимость зависимости и пробел CI

## 8. Этап 5. MFA системных администраторов

Это отдельный проект после P1, а не скрытое расширение небольшого исправления.
Ниже — обязательные подэтапы; точные маршруты, DTO, имена таблиц и библиотеку
закрепить в отдельном согласованном ADR/плане **до реализации MFA**.

**Области:** `api/src/Identity/Domain/Administrator.php`,
`api/src/Identity/Ui/Security/AdminLoginSuccessHandler.php`, admin-firewall,
новые Identity-модели/обработчики MFA, миграция и `apps/admin/src/`.

### 5.1. Модель угроз и восстановление

- [ ] Утвердить TOTP, обязательность для всех администраторов, границы
  неполной сессии, управление устройством и безопасное восстановление.
  Список разрешённых IP/VPN и login_throttling сохранить.
- [ ] Определить хранение: TOTP-секрет шифруется с управляемым ключом;
  резервные коды хранятся только как хэши. QR/секрет и коды не попадают
  в логи, аудит, телеметрию или очередь; показываются только при настройке.
- [ ] Описать потерю устройства и последнего SuperAdmin, включая проверку
  личности и аудит восстановления. «Отключить MFA через обычную сессию»
  не является восстановлением. Не вводить скрытый аварийный HTTP-обход.

### 5.2. Реализация и проверки

- [ ] Сделать одну итоговую миграцию этапа, Entity для схемы и рабочее
  восстановление. Выполнить `make db-rebuild-check` на локальной базе.
- [ ] Пароль создаёт только ограниченное состояние ожидания MFA;
  до успешного второго фактора запрещены данные компаний, создание
  администраторов и все остальные привилегированные операции.
- [ ] Enrollment завершать только после проверки TOTP; проверять лимиты,
  срок challenge, окно времени, повторное использование TOTP и гонки.
  Успешный вход меняет идентификатор сессии. Изменение/отключение MFA
  требует повторного подтверждения; старые сессии аннулируются.
- [ ] Резервный код погашается атомарно один раз; параллельные запросы
  не могут успешно использовать его дважды. Перевыпуск отменяет старые коды.
- [ ] Добавить admin UI настройки/входа/восстановления, обновить источник
  API, экспорт и типы; seller и extension остаются в своих контурах.
- [ ] Проверить HTTP и e2e: пароль без MFA не даёт доступ, роли соблюдаются,
  brute force ограничен, коды не повторяются, потерянное устройство
  восстанавливается по утверждённой процедуре, обход через seller-хост закрыт.

### 5.3. Включение

- [ ] Сначала развернуть совместимую схему и рабочий enrollment,
  проверить процедуру восстановления на тестовом стенде.
- [ ] Подключить владельцев продукта, проверить резервные коды и только
  затем принудительно включить MFA с завершением прежних admin-сессий.
- [ ] Не выдавать доступ первому внешнему администратору до обязательного
  MFA; обновить ADR-017 и операционный чек-лист, сохранив историю исключения.

**Готовность:** все привилегированные действия требуют полного входа;
есть проверенное восстановление без обхода второго фактора. Backend/admin/API,
миграция, e2e и Claude + два Codex-ревью пройдены. При отказе предпочитать
временное закрытие admin-контура отключению второго фактора для всех.

## 9. Основные риски проверки

| Условие | Где проверяется | Ожидаемое поведение |
|---|---|---|
| У пользователя несколько компаний и браузеров | Этап 1, integration + functional | Все его токены отозваны, чужие сохранены |
| Выпуск токена уже начался перед сбросом | Этап 1, тест двух соединений | Старая сессия не создаёт токен после сброса |
| Нестандартный запрос: пустое тело, отсутствующий Origin, ранний logout | Этап 2, HTTP + e2e | Политика защиты применяется до изменения состояния |
| Worker спит, обновляется или ошибается при ограничении storage | Этап 3, unit + настоящий браузер | Секрет не выдаётся до готовности, нет небезопасного fallback |
| Неполная MFA-сессия и параллельное погашение кода | Этап 5, integration + functional | Привилегий нет, одноразовость обеспечена БД |

## 10. Проверки, независимое ревью и выпуск каждого этапа

Во время реализации сначала добавить тест уязвимого поведения и убедиться,
что он падает на прежнем коде, затем внести минимальное исправление и
подтвердить успешный результат. Не закреплять уязвимость как ожидаемое
поведение. Для браузерных ограничений unit-тест не заменяет реальный браузер.

| Изменённая область | Команды через существующий Makefile |
|---|---|
| Backend | `make lint stan deptrac structure-check`, `make test-unit test-int test-func` |
| Seller | `make front-typecheck front-lint front-knip front-test front-build APP=seller` |
| Admin | `make front-typecheck front-lint front-knip front-test front-build APP=admin` |
| Extension | `make front-typecheck front-lint front-knip front-test front-build APP=extension` |
| API | `make api-doc-export api-types`, затем `make api-types-check` |
| Схема БД | `make db-rebuild-check` после проверки, что тома локальные dev/test |
| Общие блокирующие проверки | `make audit`, `make test-e2e`, обязательный зелёный CI по всему diff ветки |
| Устранение пробела проверки Go | `make ozon-fetcher-vulncheck`; при изменении Go — гейты `services/go.md` |

Если меняется общий UI, проверить всех его потребителей, включая popup.
Не запускать PHP/Composer/Node/npm на хосте. Уже пройденный обязательный CI
не повторять локально без причины; незапущенную проверку не считать успешной.

- [ ] Сформировать предметные review-пакеты по
  `docs/review-package-template.md`, включить все свои новые и изменённые
  файлы; исходные чужие файлы использовать как контекст, не как свой diff.
- [ ] Для этапов 1, 2, 3, 5: Claude и два независимых прохода Codex
  по аутентификации/секретам/изоляции. Для этапа 4: Claude; при выходе
  в рисковые области — расширить порог по таблице `CLAUDE.md`.
- [ ] Разобрать замечания, принятые исправить и перепроверить; отклонённые
  объяснить. Для каждого дополнительного прохода записать число новых
  уникальных принятых замечаний сверх предыдущих.
- [ ] Сохранить ссылки на ответы ревью и доказательства проверок в PR
  либо постоянной документации; `var/review/` не считать архивом.
- [ ] Перед merge убедиться в зелёном обязательном CI для окончательного
