## 3. Карта методов и стоимости

HTTP-вес ниже — одна **явная** отправка в коде без скрытых повторов транспорта
и редиректов. В будущей защите резервируется консервативная стоимость всех
возможных отправок, включая OAuth/ошибки. Успешный логический вызов сам по себе
не доказывает одну физическую HTTP-попытку и не подтверждает остаток площадки.

| Метод | Потребитель | Явный HTTP-вес | Генерации статистики |
|---|---|---|---|
| POST `/api/client/token` | PHP, fetcher, Ads | 1 при запросе нового токена | Не заказывает отчёт; исключение из общего HTTP не подтверждено |
| GET `/api/client/campaign` | Все три | 1 | Не заказывает асинхронный отчёт |
| GET `/api/client/campaign/{id}/v2/products` | PHP-проба ключа | 1 на пробуемую кампанию, до 3 за пробу | Не заказывает асинхронный отчёт |
| GET `/api/client/statistics/expense/json` | PHP, fetcher | 1 на запрос периода | Синхронный ответ; исключение из квот требует подтверждения метода |
| GET `/api/client/statistics/daily/json` | PHP, fetcher | 1 на запрос периода | То же; не переносить исключение оперативного SKU автоматически |
| GET `/api/client/statistics/campaign/product/json` | Ads | 1 на цикл кабинета | Без асинхронной генерации; соответствие актуальному исключению проверяется до live |
| POST `/api/client/statistics/products/sku` | PHP, Ads | 1 на порцию; PHP может читать два дня и несколько порций | Оперативное исключение описано Ozon; общий HTTP всё равно учитывается локально |
| POST `/api/client/statistics/json` | PHP | 1 на заказ | До 10 кампаний; консервативно вес по числу кампаний, не 1 на batch |
| POST `/api/client/statistics` | Fetcher, пока вне FirstWave | 1 на заказ | Та же отдельная проверка квот, версии метода и кампаний |
| GET `/api/client/statistics/{UUID}` | PHP, fetcher | 1 на проверку плюс OAuth при необходимости | Не повторять POST ради ожидания готовности |
| GET `/api/client/statistics/report` либо допустимая ссылка файла | PHP, fetcher | 1 на скачивание плюс OAuth при необходимости | CSV/ZIP не является бесплатным HTTP |
| POST `/api/client/statistic/orders/generate/json` | PHP | 1 на заказ | Организационный отчёт CPO; точный вес не установлен, нулём не считается |

Скрипт фикстур разрешает дополнительные разведочные методы; это не активные
периодические пути приложения и не основание дать их контроллеру Ads.
Ни один метод изменения рекламы в объём observe не добавляется.

## 4. Расчёт штатной нагрузки: условия, а не назначенные доли

### PHP

Проба ключа: токен + кампании + до 3 списков товаров = до 5 явных HTTP,
без редиректов/повторов. После успеха ставится первичная история за 12 месяцев,
кусочками до 30 дней: нельзя оценивать стоимость подключения только этой пробой.

Обычное окно — 45 дней, два сообщения. Каждый обработчик получает свой OAuth.
Головной кусок: token + expense + daily + campaign + SKU-порции по доступным
дням. Старый кусок: token + expense + daily. При одном batch для сегодня и
вчера получается 9 явных HTTP/тик. При штатной паузе 1800с это примерно 48
тиков и 432 HTTP/сутки на кабинет **до истории/ошибок/ручных запусков**.
Число SKU-порций зависит от кампаний с расходом; при их отсутствии запросов меньше.

Для одного успешно заказанного отчёта с P проверками готовности:

```text
заказ: token + POST = 2
проверки: P × (token + status) = 2P
готовый файл: GET на уже полученном токене = 1
итого: 3 + 2P явных HTTP
```

В Check-handler `MAX_ATTEMPTS=20`: для успешной цепочки без дополнительных
повторов это до 43 явных HTTP на отчёт. Это не общий верхний предел: 429,
Messenger redelivery, повторный заказ, ручной retry и рестарт создают дополнительный
расход. Первичная/ручная история зависит от периода и количества кампаний.

Rescan задаётся **часом**, не durable-признаком «один раз за сутки».
Штатно в этот час может попасть два тика; перезапуски/ручной запуск могут
добавить ещё. Понедельничный глубокий рескан использует 184 дня — 7 кусков.
Идемпотентность raw/фактов не означает отсутствия повторных запросов Ozon.

### ozon-fetcher

В FirstWave есть campaigns, expense, daily; асинхронные отчёты не включены.
Для прогретой истории: 1 campaign + 14 expense + 14 daily = 29 явных чтений
на сутки/кабинет; токены и повторы отдельно. Холодная история стартует от M−2
и может сделать существенно больше запросов. Дневной tail перечитывается один
раз по `planner_run`, но это не общий счётчик HTTP.

### Ads

Текущий цикл до 10 политик кабинета: campaign + aggregate + SKU = 3 явных
чтения. При X=600с: 144 цикла дают 432 чтения/сутки, OAuth отдельно.
Первый цикл с новым токеном — 4 явных HTTP. При предположении токена 30 минут
и непрерывной работе без ошибок выходит около 48 OAuth/сутки, то есть 480
явных HTTP/кабинет. TTL фактически приходит в ответе, поэтому 480 не является cap.
Повтор при 401, перезапуски и цена фактической полноты данных учитываются отдельно.

Для проектирования берётся верхняя стоимость и проверка допуска перед сетью,
а не эти средние числа. 10 минут — текущий инженерный минимум, не обещанная
частота актуализации Ozon. Доли `B_php/B_fetcher/B_ads` не назначаются по одному
снимку; расчёт X остаётся в [N1](ozon-advertising-observe-launch-plan.md#42-интервал-x-минут).

## 6. Найденные пробелы для реализации N2

1. Учет нужен в PHP, включая пробы новых ключей, оба worker-процесса и CLI,
   а не только в двух Go-сервисах. Seller Redis-limiter декорирует `ozon.client`,
   Performance использует другой scoped client.
2. Fetcher OAuth идёт напрямую в `send`; установка `.WithLimiter(limits)`
   не ограничивает эти запросы. Суточный допуск должен закрывать и этот путь.
3. Fetcher разрешает до 5 переходов на том же хосте; один `send` может содержать
   несколько HTTP. В PHP `max_redirects` не задан, установленный контракт
   HttpClient имеет default 20. N2 либо запрещает redirects, либо отдельно
   резервирует каждый переход. Не расширять allowlist по содержимому редиректа.
4. Ads запрещает redirects, но штатный Go Transport допускает неявный повтор
   некоторых запросов на использованном соединении при сетевой ошибке
   ([официальный контракт Go](https://pkg.go.dev/net/http#Transport)).
   Проблема воспроизведена для Ads на настоящем localhost-сокете: token успешен,
   ответ campaign на использованном соединении потерян, Transport повторяет GET.
   Итог baseline: **2 резерва, 3 полученных сервером HTTP**, вызов завершается
   успехом. `make ozon-ads-controller-stand OZON_ADS_STAND_TEST=TestQuotaTransportProbe`
   с `-race` подтвердил воспроизведение; лог `var/ads-quota-transport-probe.log`.
   Временная диагностическая проба не оставлена тестом, утверждающим дефект нормой.
   Общий риск относится и к fetcher; его отдельное воспроизведение здесь не выполнено.
5. Общая генерация CSV не координируется между PHP, Go и другими ключами.
   Локальная занятость задачи/разнесённое окно времени не заменяет общего
   ограничения аккаунта/организации и резерва неизвестного исхода.
6. Нужны bootstrap и изменение долей с сохранением прошлого окна. Нельзя
   запустить новый ledger с полным остатком при работающем PHP/fetcher.

Рекомендация N1 сохраняется: явные фиксированные доли для **трёх** внутренних
потребителей и прочих обнаруженных интеграций, резерв и консервативное окно.

Conwix» может быть консервативной моделью, но не учитывает неизвестный внешний
трафик и не заменяет доказательство области. Красивый расчёт из 30 наблюдённых
вызовов не закрывает вход N1/N5.

## 9. Независимое исправление сетевой границы Ads

Полный N0/N1 ещё открыт. Независимо от выбора долей исправляется уже
доказанный дефект существующего `Take`: клиент Ads использует собственный
clone штатного Transport, HTTP/1 и новое соединение для каждой явной отправки.
Неявный повтор на использованном соединении запрещён; потерянный ответ
возвращается как транспортная ошибка, следующий явный запрос снова требует квоту.
HTTP/2 и произвольные opaque RoundTripper не допускаются, исходный клиент
вызывающей стороны не изменяется. Редиректы остаются запрещёнными.

Цена решения: дополнительные TCP/TLS handshakes. Это поправка безопасности
учёта в отключённом observe, не объявление успешного live p99. Порогов стенда
не меняем; приёмка на реальной сети остаётся N3/N5. PHP/fetcher и их лимитеры
в этом исправлении не меняются, общий счётчик этим не появляется.

Регрессии: mock обрывает ответ и получает ровно две зарезервированные отправки;
TLS-сервер с поддержкой HTTP/2 получает только HTTP/1 и отдельные соединения;
настройки вызывающего Transport сохраняются; непрозрачный/typed-nil транспорт
отклоняется. Полные результаты контейнерных гейтов, review и CI фиксируются
перед принятием изменения, не подменяются результатом диагностической пробы.
