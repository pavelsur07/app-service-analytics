## 1. Результат продукта и ответственность

Пользователь задаёт кампании суточный лимит расходов и ежедневное окно работы.
Система проверяет условия запуска, контролирует расход и запрашивает остановку
при приближении к бюджету, окончании окна или потере достоверного контроля.
Срок отправки команды и подтверждение состояния отделены от прекращения показов
и поздних начислений Ozon. Без подтверждённой гарантии площадки абсолютный нулевой
перерасход не обещается.

| Область | Ответственный компонент |
|---|---|
| Пользовательское намерение, права, история настроек, API интерфейса | PHP-модуль `Advertising` — рабочее имя |
| Сроки проверок, оперативный расход, решение и исполнение | Go-сервис `ozon-ads-controller` — рабочее имя |
| Разрешения и выдача реквизитов | Identity через согласованный сервисный контракт |
| Исторические отчёты и итоговая сверка | Ingestion / ozon-fetcher в существующих границах |
| Экран «Озон Ads» и Tabs | `apps/seller`, типы API и компоненты дизайн-системы |
| Работоспособность, тревоги, восстановление | Эксплуатация и независимый наблюдатель |

Оперативный путь «прочитать → решить → остановить → проверить» не зависит от
общей очереди. Диспетчеризация сроков и ограничение параллелизма остаются внутри
контроллера. Два экземпляра на одном сервере не считаются защитой от отказа сервера.

## 2. Навигация: один пункт «Озон Ads», страницы через Tabs

Требование владельца: **в основном меню один раздел «Озон Ads»; остальные
страницы модуля открываются вкладками внутри него**, без отдельных пунктов меню.
Начальная вкладка — «Кампании». Рекомендуемый состав:

| Tab | Назначение | Содержание MVP |
|---|---|---|
| Кампании | Оперативный обзор | Кабинет, кампания, статус Ozon, состояние контроля, сегодняшний расход, лимит, окно, свежесть и причина остановки |
| Стратегии | Настройка управления | «Контроль затрат», назначение кампании, бюджет, расписание, версии, включение/пауза стратегии; без других стратегий в MVP |
| История действий | Объяснимость | Изменения пользователя, решения контроллера, команды, подтверждения, ошибки и конфликты |
| Настройки | Условия работы раздела | Выбор существующего подключения, доступность ключа, часовой пояс, поддерживаемые сценарии; переход к существующему управлению подключением |

Отдельный рекламный мастер ввода ключей не дублировать: переиспользовать
существующий сценарий подключения. Диагностика для продавца не показывает
секреты, внутренние токены и технические детали, не помогающие принять решение.

Активная вкладка хранится в URL, например в параметре `view`, по действующему
паттерну seller; окончательный путь определяется при реализации маршрута.
Прямые ссылки, обновление страницы и Back/Forward восстанавливают вкладку.
Кабинет и фильтры сохраняются при переключении Tabs в пределах одной компании;
при смене компании недействительный кабинет сбрасывается, кэш изолирован.
Форма редактирования и детали кампании — внутри выбранной вкладки либо в drawer,
а не новый пункт меню. Несохранённый ввод не теряется молча при переходах.

Общий заголовок «Озон Ads», выбор кабинета и индикатор состояния остаются над Tabs.
На узком экране вкладки доступны без обрезания текста и действий. Нужны
клавиатурная навигация, фокус, `tablist` / `tab` / `tabpanel` и их связи.

В просмотренном `packages/ui/src` отдельного Tabs-компонента нет; есть пример
URL-вкладок в `UnitEconomicsPage`. Будущая реализация использует примитивы и
токены `packages/ui`; необходимость общего Tabs оценивается по правилам проекта,
без новой UI-зависимости и без попутной переделки существующих экранов.

## 3.1. Первый выпуск и отдельный допуск управления

План достаточно определён для подготовительной реализации после принятия
архитектурных решений соответствующего объёма. Наличие открытых вопросов о
реальных start/stop не блокирует разработку чтения, расчёта и интерфейса на моках.
Это не отменяет текущего указания «код не пишем»: сейчас дополняются документы.

**Первый выпуск — наблюдение (observe):**

1. Этап 05: ADR и контракты для PHP/Go, денег, собственного хранения,
   company-scoped чтений, квот и технического запрета изменения рекламы.
2. Этапы 06–07: модель, доставка версий, чтение, нормализация и качество снимков.
3. Этап 08: расчёт «запустил бы / остановил бы / данных недостаточно» на
   фикстурах и моках; нет передачи решений в рабочий исполнитель.
4. Этап 10 в объёме observe: «Озон Ads», четыре Tabs, сохранение настроек
   расчёта, расходы и объяснимые предполагаемые решения.
5. Этап 11 в объёме observe: изоляция, безопасность чтения, квоты, рестарт,
   ошибки, нагрузка, UI и доказательство отсутствия вызовов изменения рекламы.
6. Этап 12: ограниченный выпуск observe с разрешёнными чтениями реальных данных.

Этап 09 не является зависимостью первого выпуска; исполнитель может готовиться
позже на моках. Этапы 02/04 продолжаются параллельно и дают доказательства для
будущего управления. Нумерация отражает предметные этапы, а порядок выпуска
определяется зависимостями. Незакрытая часть этапа явно остаётся незакрытой.

| Условие | До первого живого observe | До пилота управления |
|---|---|---|
| Архитектура и полномочия | ADR/контракты наблюдения, компания/подключение проверены | Дополнительно права записи и владение внешним кабинетом |
| Данные | Чтение и качество показываются честно; неизвестные значения допустимы | Доказаны условия допуска start, включая D4/D5 |
| Квоты | Консервативный бюджет чтения/генераций и известные общие потребители | Дополнительно резерв команд/подтверждений и предел масштаба |
| Запас и риск | Неподтверждённый запас отображается как неизвестный | Пригодный расчёт и согласованный критерий риска |
| Start/stop | Заблокированы технически, знания схем не требуется для observe | Актуальные схемы, моки, восстановление и отдельный допуск |
| Проверки | Весь CI и ревью diff первого выпуска | Все новые проверки/ревью команд и затронутых частей |

Неуточнённая свежесть не скрывается: observe не обещает удержать бюджет и не
показывает, что кампания находится под защитой. Права и изоляция компании
обязательны уже для чтения. Нельзя ослаблять гейты первого выпуска ссылкой
на то, что он «только наблюдает».

### Чек-лист приёмки первого выпуска observe

- [ ] Приняты ADR/контракты объёма observe и пройдены требуемые проверки/ревью.
- [ ] Рабочий коннектор допускает только разрешённые аналитические операции;

- [ ] Прямой вызов API управления не обходит режим; задание изменения рекламы не создаётся.
- [ ] После рестарта/изменения конфигурации observe не превращается в управление автоматически.
- [ ] UI явно сообщает «Режим наблюдения: реклама не изменяется автоматически»;

- [ ] Неизвестный расход/запас остаётся неизвестным; предполагаемое решение

- [ ] Формы сохраняют параметры расчёта; исторические предполагаемые решения

- [ ] «Озон Ads» и все четыре Tabs приняты по навигации, правам и изоляции кэша.

**Переход к управлению:** закрыть оставшиеся условия Q1–Q7 в объёме допуска,

за уже известные до пилота. Включение управления требует отдельной активации
выбранных политик с preflight, не одного переключения общего флага.

## Этап 01. Карта API и границы поддержки

**Цель:** определить, какие возможности площадки подходят стратегии.
**Ответственность:** исследование Ozon. **Вход:** этап 00.

Работы: получить читаемую актуальную спецификацию либо официальные разъяснения;
описать методы списка, статуса, расхода, старта и остановки. Методы записи
изучать по документации, не вызывать. Для каждого метода указать тип кампании,
область квоты, формат и единицы денег, период, timezone, пагинацию, ошибки,
семантику пустого ответа и повтора. Уточнить отличие квот отчётности от RPS.

**Артефакт:** матрица возможностей и карточки методов со ссылками и датой проверки.

### Чек-лист приёмки этапа 01

- [ ] Для методов чтения подтверждены точные HTTP method/path и параметры; гипотезы помечены отдельно.
- [ ] Для будущих старта/остановки описаны допустимые состояния и результат команды либо зафиксирован блокер.

- [ ] Установлены правила отчётного дня и периода CSV либо эти методы исключены из суточного контроля.
- [ ] Поля `dailyBudget` и недельного бюджета не трактуются как доступная гарантия только по их наличию.
- [ ] Поддерживаемые CPC-сценарии отделены от бонусных, CPO и смешанных; исключения объяснены.
- [ ] Ошибка доступа, истечение access token и отзыв Client Secret различаются по подтверждённому контракту.

**Условие перехода:** для сбора серии выбран подтверждённый метод чтения и безопасный режим запросов.
Неподтверждённые права записи блокируют будущий этап 09, а не подменяются сторонним SDK.

## Этап 02. Серия наблюдений расходов, полноты и задержек

**Цель:** выбрать источник оперативного расхода на основании серии, а не одного ответа.
**Ответственность:** исследование данных. **Вход:** карточки методов чтения этапа 01.

Работы: заранее составить ограниченный график чтений в пределах известных квот;
наблюдать активные и неактивные кампании, начало/конец отчётного дня и последующий
день. Сопоставлять одинаковые кампании и периоды у `daily`, SKU, `expense` и CSV,
только если его период подтверждён. Ничего не переключать ради эксперимента.
Собирать ответы и метаданные существующими средствами, без реализации сервиса.

- [ ] Пройдены frontend-гейты, Vitest/MSW, Playwright seller и применимые admin-регрессии; изменения общего UI проверены у всех потребителей.
- [ ] Пройдено независимое ревью; методы записи в Ozon ещё не включены для клиентов.

## Этап 11. Нагрузочная и аварийная приёмка на стенде

**Цель:** подтвердить профиль из этапа 04 до подключения живого управления.
**Ответственность:** backend, frontend и эксплуатация. **Вход:** этапы 06–08 и 10
для observe; дополнительно 09 для команд. Первый объём не закрывает проверки управления.

Работы: воспроизвести обычную/пиковую нагрузку на мок Ozon; массовые дедлайны,
историю, медленные чтения, квоты, отказ очереди/PHP/Go/БД/сети и восстановление.
Проверить мониторинг и безопасный порядок выключения контроллера.

**Артефакт:** отчёт замеров и матрица аварий с ожидаемым/фактическим результатом.

### Чек-лист приёмки этапа 11

- [ ] Все параметры нагрузки и пороги взяты из этапа 04, не выбраны после просмотра результата.
- [ ] В отчёте явно выбран объём observe/control; проверки команд, отложенные
      до control, не объявлены пройденными в первом выпуске.
- [ ] Нормальная нагрузка и массовые остановки укладываются во внутренние SLO.
- [ ] Отказ общей очереди не нарушает контроль; история не вытесняет ресурс остановок.
- [ ] При перегрузке срабатывает запрет новых стартов, а не неограниченное накопление задач.
- [ ] Отказ исполнителя, split-brain, поздний HTTP-ответ и восстановление БД не дают небезопасного запуска.
- [ ] Для 401/403/429/5xx и устаревших данных зафиксированы состояние, тревога и действие восстановления.
- [ ] Мониторинг замечает просроченную проверку каждой кампании, а не только heartbeat процесса.
- [ ] Проверены ротация/отзыв ключа, потеря разрешения и отсутствие секретов в логах и трассировках.
- [ ] Репетиция rollback начинается с запрета стартов и проверки остановок, а не с выключения контейнера.
- [ ] Закрыты замечания ревью и зелёный обязательный CI всего diff, включая audit и e2e.

## Этап 12. Первый выпуск: наблюдение на реальных данных

**Цель:** проверить качество решений при реальном поведении Ozon.
**Ответственность:** эксплуатация и аналитика. **Вход:** этап 11 в объёме observe,
чек-лист раздела 3.1 и согласованный режим чтения. Этап 09 не требуется.

Работы: включить отдельный режим наблюдения только для выбранных кабинетов;
считать «запустил бы / остановил бы», но технически блокировать исполнение.
Наблюдать длительность и набор сценариев, установленные до начала этапа.
Сверить суммы с историей и оценить достаточность данных и потенциальный недорасход.

**Артефакт:** отчёт наблюдений, перечень ложных решений и уточнённая оценка риска.

Нужно различать приёмку самого первого выпуска и завершение исследования для
control. Observe может показывать «недостаточно данных»; это корректный результат,
а не разрешение управления. Незавершённая серия наблюдений оставляет допуск
control закрытым, даже если интерфейс и reader уже выпущены.

### Чек-лист приёмки этапа 12

- [ ] Режим не способен отправить команду записи; пустой allowlist не подключает ни одного кабинета.
- [ ] Выполнены заранее заданные длительность/выборка и сценарии дней; пробелы явно перечислены.
- [ ] Расходы сверены с независимым источником по одинаковым периодам и денежной базе.
- [ ] Не обнаружены ложные нули, пропуски кампаний или смена источника со сбросом расходов.
- [ ] Нарушения свежести и доставки настроек приводят к ожидаемому защитному решению.
- [ ] Пороги ложных остановок/недорасхода выполнены либо пересмотр продукта оформлен до пилота.
- [ ] Указано ограничение: без реальной остановки нельзя доказать фактический предотвращённый перерасход.
- [ ] Обнаруженные дефекты исправлены, затронутые проверки и ревью повторены.
- [ ] Перед будущим control исторические решения observe не ставятся в очередь;
      каждая выбранная политика проходит явную активацию и новый preflight.

## Этап 13. Ограниченный пилот управления

**Цель:** подтвердить действительное выполнение остановки и расписания на ограниченном масштабе.
**Ответственность:** владелец продукта и эксплуатация. **Вход:** этап 12, разрешение
на реальное управление в согласованном плане и выполненные предусловия проекта.
Текущие реквизиты для сбора фикстур такого разрешения не дают.

Работы: выбрать кампании с известной принадлежностью и ограниченным риском;
назначить ответственного за ручное восстановление. Сначала проверить остановку
и последующее наблюдение, затем старт по расписанию. Установить заранее условия
паузы пилота; не начинать с массового подключения и не менять ставки/недельные бюджеты.

**Артефакт:** протокол пилота с командами, подтверждениями, расходами и инцидентами.

### Чек-лист приёмки этапа 13

- [ ] Зафиксированы кампании, окна, допустимый риск, длительность, ответственный и условия прекращения пилота.
- [ ] Проверены остановка по времени, остановка по бюджету и защитная остановка по реальным наблюдениям.
- [ ] Измерены отдельно отправка, подтверждение статуса и поздние начисления; статус не назван доказательством отсутствия всех будущих списаний.
- [ ] Запуск не происходит вне окна, после ручной/аварийной блокировки или без пригодного остатка.

## 4. Общие проверки будущих этапов реализации

Чек-листы этапов дополняют, а не заменяют правила репозитория. Команды выполняются
только при реализации соответствующей области; создание плана не является их успешным прогоном.

| Область | Обязательные проверки |
|---|---|
| PHP | `make lint stan deptrac structure-check` и затронутые `make test-*` |
| Go | Цели `make <name>-lint <name>-vet <name>-test`, после появления сервиса |
| БД | `make db-rebuild-check`, проверки down/восстановления и миграций |
| API | `make api-doc-export api-types`, затем `make api-types-check` |
| Seller | `make front-typecheck front-lint front-knip front-test front-build APP=seller`, Vitest/MSW и Playwright |
| Общий UI | Проверки всех потребителей, включая popup расширения |
| Перед merge | Зелёный обязательный CI всего diff, включая `make audit` и `make test-e2e` |

Ревью итогового кода — Claude; деньги, схема, авторизация, изоляция и рисковые
области сервиса дополнительно требуют двух проходов Codex. При недоступном Claude
действует установленная замена двумя новыми сессиями Codex CLI. Самопроверка
не заменяет независимое ревью. Только Markdown без принятия необратимого ADR,
как текущий документ, не требует внешнего ревью.

Для каждого этапа сохранять отчёт: объём, доказательства по чек-листу, выполненные
команды, результаты, замечания/разбор, уникальные принятые каждого дополнительного
прохода, ограничения и решение о переходе. Непройденная приёмка означает незакрытый этап.
