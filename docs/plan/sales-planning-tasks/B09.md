### Точный вход, результат и отказы по бюджету

`Q/NetTargetRequest.php` — readonly request:
`__construct(array $marketplaceSkus, DateTimeImmutable $from, DateTimeImmutable $to,
?DateTimeImmutable $accumulationFrom = null)`.
SKU — distinct list 0..50, UTF-8 без controls, 1..64 символа. Даты date-only:
берём `Y-m-d`, нормализуем UTC midnight; `accumulationFrom <= from <= to`,
включительный диапазон `[accumulationFrom ?? from, to]` 1..184 календарных дня.
Неправильные input/UUID — `InvalidArgumentException` до SQL; future order day
относительно actual readAt не маскируется под наблюдённый ноль.
Нулевой SKU list возвращает empty result без Connection/Clock/training.
Нет caller-provided `asOf`, limit увеличения или произвольного historical read.

`Q/NetTargetLimits.php` — finite operational limits, constructor с defaults:
`groups=20000, sourceKeys=50000, revisions=400000, statuses=200000,
receipts=50000, groupsPerSkuDay=200, sourcesPerGroup=128,
revisionsPerSource=128, statusesPerGroup=512, outputBytes=33554432,
phpAllocationBytes=50331648, phpPeakBytes=100663296, computeSeconds=5`.
SourceKeys — общий предел distinct sales+return keys, не 50k каждого вида.
Все defaults можно уменьшать DI в tests; отрицательные/ноль/неfinite значения
запрещены; верхние пределы нельзя увеличивать request-параметром.

Результат target query: максимум50 SQL rows по SKU, в каждой `days<=184`,
в дне `groups<=200`, в группе `parts<=128` настоящих source parts и
`returns<=128` trace-ссылок, причём combined distinct sources группы<=128.
Это **не flat200 на всё окно**: у разных дней разные200 groups; дополнительно
действуют глобальные20k/50k. Group identity — настоящий
`(business_date, order_number, marketplace_sku)`. Missing order — явный unknown,
никакой synthetic `orderNumber` для bucket/source key не создаётся.
Rows для missing identity сохраняются только как bounded diagnostic source
part с nullable order; B04/B08 evidence для них не конструируется.

Каждое растущее source чтение имеет sentinel `max+1`, в том числе historical
seed, order-link expansion, latest keys, revisions/status/receipts. `COUNT`/`SUM`
для проверки выполняются только по уже ограниченным materialized inputs,
без `COUNT(*)` над факт-таблицей. Sentinel или превышение любого nested/global
лимита даёт **отказ всего target batch**, без числового partial population.
Отдельный scalar `NetTrainingBudgetFailure(input, observed, maximum)` переиспользуем;
`input_budget_exceeded` не заменяется `0`/empty array как полным результатом.

**До любого JSON/DTO** `target_output_budget` проверяет cardinalities и
консервативный byte upper bound. Для каждого выбранного scalar учитываются
фиксированная JSON syntax и `6 * octet_length(text)` для worst-case escaping;
для null/bool/numbers фиксированные верхние lengths, source IDs не считаются
ограниченными только потому, что обычно короткие. Сумма в PostgreSQL `numeric`,
дополнительно считаются повторения trace в разных группах. Только ветка
`budget.ok` материализует JSON. Одного32MiB cap недостаточно для PHP памяти:
producer **до JSON** вычисляет fixed-shape allocation upper bound: два raw
JSON buffers, `4×text-value bytes`, `128×scalar slots`, `1024×container nodes`,
`512×source/result DTO nodes`, включая simultaneous decoded/source/result
structures и compact model memo. Если bound>48MiB, whole batch refusal ещё
в SQL; это effective emitted-size limit, не обещание выдать все20k groups.
Query отдаёт scalar counts/byte estimate рядом с JSON, mapper до `json_decode`
проверяет их finite bounds, actual byte length и
`memory_get_usage(true)+next allocation upper bound+8MiB headroom<=96MiB`.
Mapper обрабатывает и освобождает один SKU JSON за раз. Затем проверяет depth,
scalar types/counts и output bounds. Whole-buffer decode, после которого
проверяется память, запрещён: он может OOM прежде typed отказа.
Перед очередной DTO allocation/reduction проверяются тот же memory budget и
monotonic `hrtime` compute deadline5s; это не второй business Clock/readAt.
Actual peak сверх бюджета/исчерпанный deadline дают typed whole unavailable
`input_budget_exceeded` с budget input `php_memory`/`compute_deadline`, не partial
total. Бюджеты/предварительная оценка проверяются под128M, без поднятия ini.

### Source selector, closure и аллокация

Новый `Q/NetTargetSourceSql.php` сам связывает параметры с микросекундами и
поставляет current-target CTE; training selector не вызывается. Каждый base
scan/join явно содержит company/account predicates. Последовательность:

1. `target_current_seed` и `target_historical_seed`: current sales **или любая
   видимая accepted revision**, чьи SKU/date входят в полный requested range.
   Historical seed ограничен `revisionSentinel` до distinct. Обе ветки нужны
   даже если нынешняя строка полностью ушла из SKU/date/order запроса.
2. `seed_keys`, bounded histories исходных keys, `seed_orders`: union current
   и historical order aliases. Не фильтровать sibling SKU/date.
3. `current_order_keys`, `historical_order_links`, `expanded_keys`: все source
   keys всех siblings этих orders, включая historical membership; limit+1 на
   каждом растущем наборе. Дочитать full bounded histories найденных keys.
4. `return_keys`, `return_revisions`: current+historical return membership по
   всем найденным aliases, не только requested SKU. Одного current return join
   недостаточно при переносе order/SKU. Sales/return histories <=128/key,
   combined revisions<=400k, combined keys<=50k.
5. `target_alias_links`, `target_closure_proof`: полная history identity каждого
   найденного sibling проверяется до allocation. Для численно пригодного batch
   identity стабильна, все aliases принадлежат seed_orders; это fixed point
   одного expansion. Если обнаружен внешний alias или identity move, batch
   `source_history_unavailable`; дальше не раскрываем произвольный граф и не
   пытаемся предсказать unaffected remainder. Historical-only seed также
   сохраняет affected requested cell как unknown, а не empty0.
6. `sales_revisions`, `return_revisions`, `status_inputs`, `receipt_inputs`,
   `input_metrics/input_budget` по тем же bounded principles, что B02, но без
   gross90/origin157..67 и без фильтра mature target. Statuses нужны по всем
   current/historical posting aliases. Latest source state берётся по
   `fact_revision`, никогда по UUID/timestamp/raw hash как порядку accepted ABA.
7. `target_latest_sales`, `target_latest_returns`, `target_status` — latest
   bounded raw states. ProofSql на них проверяет chain/status/typed quantity/
   coverage и предоставляет `training_sales`, `training_returns`,
   `training_status` — compatibility CTE с точными колонками, ожидаемыми
   `NetTrainingOutcomeSql::ctes()`. Название
   здесь техническое; population текущая. SQL canonical classifier добавляется
   без изменения; final requested SKU/date filter применяется **после** его
   order/SKU prefixes и order sibling flags.
8. `target_quantity_proof`, `target_delivery_proof`, `target_readiness`,
   `target_groups`, `target_output_budget`, затем bounded hierarchy. Наряду с
   canonical rows проверяются raw source quantities и typed return capacities
   **до** canonical `LEAST/GREATEST`: ClientReturn<=delivered capacity,
   Cancellation<=cancelled capacity; quantity<=0, unknown type/unmapped cause,
   source discrepancy, R overflow не clipping. Сумма canonical allocations
   равна исходной source quantity; active+return остаётся unknown по ADR019.

Отказ closure — сознательно консервативный operational результат всей B09
batch. Он не меняет правила исключения B02 training и не требует новых индексов.
Индексы уже есть: current sales company/date и company/account/order/SKU,
revisions company/account/order/SKU/captured и PK source/revision, posting
company/account/posting/observed/raw, receipts company/account/report/marked/window.
У historical seed нет отдельного date/SKU index; perf Task5 обязан измерить
его bounded account scan на noise, а не тихо добавить индекс/схему.

### Доказательства source, origin и terminal zero

Цепочка source: min revision1, max=count=visible current fact_revision,
initial capture явный, все revision в том же epoch/version, LivePolling/upsert,
`first_loaded_at >= epoch.start`, capture monotone и <=readAt, stable identity.
Latest selected revision согласуется с current mutable quantity/status/identity;
legacy0/missing revision/capture gap/backfill/replay/unknown не объявляются proof.
Sales quantity после первого доказанного delivered не менялась. ClientReturn
deltas используют accepted `captured_at`; known nonClient→Client начинает новый
R, обратный переход/decrease/link move портит affected batch. Visual-change
timestamp не становится возрастом R. Source ID/hash/counter не доказывают
commit visibility: пригодность только внутри actual current RR.

Каждый posting status anchored к accepted sales revision с тем же raw/status,
known exact status/substatus, one-order identity. Противоречивые same-time
статусы, unknown predecessor, terminal reversal, активный status после terminal,
missing anchor — incomplete. UUID/raw sort используется только для стабильного
порядка канонического SQL; semantic same-time tie им не разрешается.

Delivered origin — **первый** known delivered status, которому предшествует
known active observation строго раньше, с доказанным initial polling completion
между initial active capture и delivery. `resolved_at`, first_loaded_at,
initial-terminal/backfill и `resolution_observed` сами origin не создают.
Точно same-instant return/origin без ordering proof — unavailable.
При R>0 и нескольких origins одного order/SKU —
`ambiguous_delivery_allocation`; posting из return не физическая аллокация.
При отсутствии R различные origins оцениваются по настоящим source parts
отдельно. При одинаковом origin canonical partial D/R allocation безопасен
для quantity; original price/source trace сохраняется без денежного вывода.

`D` — остаток после уже известных R, включая известные lateR после H.
T1/T2/P/R без D/open дают terminal0 после доказанного current outcome/history/
postings/returns input; training для них не нужен. Missing history/load/source
не доказывает0. Initial known ClientReturn может дать0, если delivered capacity
и полная текущая conservation доказаны; initial delivered с положительным D
никогда не получает придуманный origin. Empty requested day получает0 только
с положительным day coverage; будущий/непокрытый день остаётся unavailable.

### Время, readiness и общий snapshot

Все UTC instants — `Y-m-d H:i:s.u`, сравнение context — fingerprint **плюс**
epoch.start/end `U.u`. Date bounds — MSK calendar dates, H/L — ровно
60/7×86400 секунд от delivery origin; age=floor точного elapsed/86400.
`H` полуоткрытый; текущий knownR не удаляется из-за позднего bin.

Для target не применяется p95, training window или собственная gross maturity:
freshD<60 использует уже дозревшую training curve. Возрасты60..66 возвращают
`target_horizon_not_ready`. Для >=67 source `NetTargetReadinessRow`, затем
его Application-представление `DeliveredTargetReadiness`, подтверждает
его собственные history/postings, daily_complete_receipts_v1 и deep completion:

- каждый MSK день от origin day до MSK дня origin+67 включительно имеет live
  completed witness после конца дня и не позже day-end+24h; timely failure
  исправлен strictly later timely success; latest failure исправлен strictly
  later completed <=T, equal timestamp остаётся ambiguous;
- отдельный deep receipt покрывает visual dates origin..origin+60 включительно,
  completed>=origin+67 и <=T; будущие completion/receipts запрещены;
- coverageFrom<=origin, coverageThrough>=origin+67 и <=T; последний полный
  MSK день может сделать реальную готовность позже математических67 суток.

Current-coverage policy согласована internal root ruling, отдельно от maturity:

- Current postings: LivePolling/version completed, покрывающий order business
  day, после latest relevant accepted sales/status capture, <=T и strictly
  later любого covering failure. Конец заказного дня не требуется. Для D
  дополнительно есть initial completion между known active и delivered.
- Для всех positive компонентов — current returns refresh, чей visual window
  включает текущий MSK visual day: completed<=T, strictly после latest relevant
  accepted return capture и failed; как conservative consistency guard также
  strictly после latest relevant sales/status capture. Нет floor до секунды.
  Receipt подтверждает observed refresh **частичного текущего дня**, а не
  полноту его будущего остатка. Missing current-day receipt/tie — unavailable.
- FreshD<60: дополнительно timely full MSK days от origin day до последнего
  закрытого дня включительно; если origin сегодня, этот набор пуст, но current
  refresh обязателен. Timely/live/version и strict failure resolution те же,
  что для aged daily proof; поздний refresh не исправляет пропущенный день.
  Deep completion и собственный H+L не требуются.
- Open с known nonterminal/no-delivery history: current refresh + history,
  postings и typed capacities, без daily aging от рождения заказа. Его return
  tail ещё не начался. Present return evidence при active, в том числе
  ClientReturn, остаётся unknown/contradictory согласно classifier.
- Aged>=67: current refresh/reconciled D(T) **и** собственные daily-through67,
  deep>=67 выше. Known lateR сохраняется в D(T), не обнуляется по horizon.
- Для confirmed terminal0 и empty day также нужны positive source/coverage
  proof: completed postings за полный запрошенный день, current return refresh
  и отсутствие failing/corrupt aliases. Initial delivered/R может доказать
  нулевой остаток только при согласованной capacity/conservation; положительный
  D требует отдельного observed origin. Для empty day postings receipt должен
  быть после day-end, для terminal source в текущем дне достаточно его реальных
  completed observations. Нет mandatory training или H+L для terminal0.

Это наблюдённая operational полнота, не гарантия будущих событий площадки.
Receipt calendar строится одним bounded account relation: unique нужные даты
для fresh origin..closedDay либо aged origin..67; каждый interval<=68 MSK
dates, global group bound20k. Генерация не зависит от возраста старого open.
Input count/byte/time budgets проверяются до JSON, full receipt arrays наружу
не выгружаются. Target SQL не создаёт20k×68 day-series JSON.

### Reasons и precedence

Порядок: foreign scope exception → context/snapshot mismatch → input/query/
output budget → history/closure/quantity/status/coverage target reason → model
unavailability. Source-corruption не исправляется statistical account fallback.

attempt reasons сохраняют SKU/account объяснение. Основные значения:

|---|---|
| `source_history_unavailable` | epoch/chain/gap/move/fixedpoint/legacy; nonempty source absence без доказанного day coverage |
| `postings_coverage_missing`, `returns_coverage_missing` | missing/failed/late/tied required receipts; нынешний refresh не заменяет timely history |
| `delivery_observation_unknown`, `ambiguous_delivery_allocation` | positive D без known→delivered либо неоднозначный R между origins |
