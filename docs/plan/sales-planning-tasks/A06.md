# A06 — неизменная исходная цель линии

## План до кода

1. Добавить SalesPlanBaselineQuery и readonly Row внутри SalesPlanning.
   CompanyId первым; requested plan проверяется в той же компании,
   кандидат базы — той же lineage и компании. LIMIT1 всегда.
2. База — минимальный version_number среди approved/superseded/cancelled;
   draft и discarded никогда не выбираются. Nullable approval metadata
   старой версии не исключает историческую числовую цель по её статусу.
3. Вернуть id/lineage/versionNumber/metric/currency/период исходной цели.
   Nullable metric не подставляется автоматически. Выбранный смысл legacy
   новой версии не переписывает исходные числа или метаданные базы.
4. TDD integration на реальном A07/A08/A09 lifecycle: до утверждения
   базы нет; после revision/daily edit/replacement база остаётся первой;
   открытый/отброшенный draft и отмена не подменяют её. Чужая компания
   не находит requested plan или базу. Копии разных линий не смешиваются.
5. Прочитать только нужные колонки DBAL, без Entity hydration списка,
   запросов в цикле и COUNT фактов. Запрос дневных чисел базы — A24,
   публичный performance и UI позже; здесь только определение базы.
6. Индекс company/lineage/version_number нужен для порядка исходных версий
   и уже существующего MAX версии: partial draft/approved индексы не покрывают
   superseded/cancelled историю. Добавить ORM index и расширить единственную
   pending миграцию feature, включая down. Проверить на пустой local dev/test
   базе после проверки Compose volumes и отсутствия других DB-прогонов.
7. Затронутые tests/backend gates + оба Codex CLI review и разбор замечаний.
