> Реализация после root GO завершена, local unit/static gates зелёные.
> Финальные независимые Codex CLI, CI и production-приёмка принадлежат root.

**Результат:** применить B03 conditional risk к текущему оставшемуся D,
сохранив точные количества и явные причины unavailable, и выбрать целую

## Обязательные правила

- H60/L7, age вычисляется от доказанного observed delivery origin до того же
  current readAt/context. Future/unknown origin не даёт придуманный возраст.
- При0<=a<H свежий target D не ждёт собственногоH+L: пригодная training
  population уже дозрела. Для targeta>=H риск0 разрешён только после его
  доказанной готовностиH+L/coverage; возраст сам по себе не доказывает zero.
- `futureReturns=currentD*q(a)`, `retainedDelivered=currentD-futureReturns`.
  currentD уже уменьшен на известные R, повторного вычитания R нет.
- Подтверждённый компонент без оставшегося D даёт0 без training; probability
  при этом не выдумывается. Unknown/contradictory input не превращается в0.
- Пригодность B03: initial100units/30posts, risk30units/10provedlowerbound.
  Fallback выбирает ВЕСЬ коэффициент/curve одной scope, не смешивая
  числители, denominator, sample либо timestamps/contexts разных scopes.
- Scope company/account target/batch/context проверяется до выдачи metadata;
  account fallback только того же account/company/read snapshot.
- Все количества точные до будущего представления. Float, clipping и
  переполнение промежуточного int multiplication запрещены. Уже установлен
  brick/math0.19.0 (через brick/money0.14.1 в composer.lock); можно применить
  существующий BigRational/BigInteger по локальному vendor API, без composer
  changes и без собственного generic fraction framework.
- Новых SQL/writer/schema/Facade/API/UI/runtime config/dependencies не нужно. Target
  evidence contract пока pure typed input для последующего orchestrationB09;
  наличие поля не выдаётся за доказательство реальных production данных.
  Runtime/queue/security config не меняется; исключение — root-owned
  explicit Deptrac classification установленного BrickMath, ruling ниже.
- Source/target freshness, no-future-leak и target-ready evidence на одном
  current context описать явно. Historical manifestB15 и qualityB16/B17
  не реализуются этой задачей; numerical rollout остаётся закрытым.
- В каноническом global плане B05 — OPEN до передачи, не agedD. Устаревшие
  B03 preplan ссылки target-age→B05 уточняются root: agedD readiness относится
  к B04 как части уже утверждённой логики ADR-049.

### Контракт доверия target и readiness

`DeliveredTargetEvidence` — внутренний вход, не клиентский DTO. Для
`inputComplete=true, unavailableReason=null` будущий B09 обязан установить
из одного current readonly RR: reconciled current D после всех известных R,
известные непротиворечивые outcomes/quantities, accepted history после epoch,
доказанный previous-known→delivered origin для положительного D и однозначную
order/SKU allocation. Несколько postings допустимы только с одинаковым origin.
Ни initial/backfilled delivered, ни assigned delivery date не дают origin.
Неизвестные, неполные и противоречивые источники передаются как unavailable.
Нулевой D допустим только после подтверждения отсутствия оставшегося delivered
компонента; null D или отсутствующая строка не являются подтверждением нуля.
Known R отдельным аргументом не передаётся: повторного вычитания конструктивно нет.

Readiness привязана к тем же context/order/SKU/origin и означает проверенный
reader результат по `daily_complete_receipts_v1`. Требуются непротиворечивая
история, postings completeness, daily returns completeness на нужном диапазоне
origin..H+L без восстановленного задним числом onset; отдельный deep completion
не раньше origin+67d. Диапазон `coverageFrom<=origin`,
`coverageThrough>=origin+67d`; completion/coverage timestamps не позже readAt.
Daily extent соответствует B02 required_daily_windows и включает lag7d;
deep window origin..H с completion>=67d не заменяет daily extent67d.
Реальный producer полных MSK days может доказать readiness позже точного67d;
pure boundary67d test не утверждает наличие реальных receipts.
Это assertions trusted producer, а не receipts: одни bool поля и даты в DTO
не доказывают, что необходимые production observations существуют. B04 проверяет
согласованность assertions, но не объявляет реализацию producer/coverage готовой.
Положительный D возраста <60 не требует readiness собственного H+L; доверенный
current input и зрелая training population нужны всё равно.

Все DateTime значения UTC. Непустые order/SKU и неотрицательный known D —
инварианты конструктора; нарушение бросает InvalidArgumentException. Unknown
origin/неполные источники — обычные unavailable, не исключения. Readiness для
другой order/SKU/origin/context не используется; ошибочный target не исправляется
чужим training или readiness. Source time включает лишь accepted inputs и
receipts, видимые producer в том же RR и не позже readAt; B04 не перечитывает
mutable tables и не использует wall clock. Historical commit visibility по
одному timestamp/fingerprint не утверждается: это B15 manifest.

### Порядок проверки и unavailable

1. До любой выдачи source metadata проверить company/account target context,
   batch, batch context и supplied readiness context. Чужая scope бросает InvalidArgumentException даже
   при target D=0 или unavailable batch. Не возвращать чужие diagnostics.
2. Target требует непустой `context.snapshotId`; одного `single_statement`
   недостаточно для связывания отдельных target/training чтений. Target
   отсутствующий RR → `target_snapshot_missing`. Batch.readAt всегда совпадает
   с target.readAt; если batch context существует, совпадает и полный fingerprint;
   несовпадение → `training_context_mismatch`, без attempts. Это применяется
   также перед нулевыми shortcuts. Batch без context не является чужим source:
   отсутствие training не блокирует доказанный нулевой/готовый target.
3. Target `unavailableReason` имеет приоритет над inputComplete и D=0;
   иначе incomplete → `target_input_incomplete`, null D → `unknown_outcome`.
   Если origin передан, проверить future/epoch также до zero shortcut:
   противоречивое supplied evidence не маскируется нулём.
   Недоверенный ноль не становится числом. D=0 подтверждён → future0 + retained0 (обе дроби0/1)
   quantities, `probability=null`, `ageDays=null`, basis `no_remaining_delivery`,
   attempts пусты; training sample не нужен.
4. Положительный D с null origin → `delivery_observation_unknown`, origin>readAt
   → `delivery_observation_in_future`, origin вне epoch →
   `source_history_unavailable`. Для positive D доказанная allocation/history
   обязательна по target inputComplete contract, её failures сохраняются.
5. Возраст — полные UTC сутки по86400s с учётом microseconds, без float.
   Возраст результата capped at60; readiness проверяется точными timestamps,
   не округлённым age. До H возвращается0..59, ровно H переходит в mature branch.
6. a>=60: readAt<origin+67d → `target_horizon_not_ready`. В67d и позже без
   readiness → `target_readiness_missing`; неверная binding →
   `target_readiness_mismatch`; unsupported policy →
   `unsupported_target_coverage_policy`; future readiness timestamp →
   `target_evidence_in_future`; неполная история → `source_history_unavailable`;
   неполные postings → `postings_coverage_missing`; returns/диапазон/deep
   completion недостаточны → `returns_coverage_missing`. При всех доказательствах
   future=0, retained=currentD, probability=0/1 как детерминированный horizon
   результат, basis `mature_target`, без training/attempts. Уже известные поздние
   R учтены currentD, исторический D(H) не восстанавливается.
7. a<60: B03 build для exact target SKU. Source unavailable превращается в
   attempt с той же причиной; иначе `curve->remainingAt(age)`. Проверяются
   initial100units/30posts и risk30units/10lowerbound самим B03. При успехе
   применить всю эту вероятность и закончить. При отказе повторить build для
   account (`marketplaceSku=null`) из ТОГО ЖЕ batch; не брать отдельный batch
   или произвольный ScopedReturnCurve снаружи. При двух отказах общий reason
   `return_risk_unavailable`; attempts содержат обе исходные причины и samples.

### Exact arithmetic и локальный vendor API

Прочитаны `api/composer.lock` и `api/vendor/brick/math/src/{BigNumber,BigRational,
BigInteger}.php`: установлены brick/math0.19.0 через brick/money0.14.1.
`BigRational::ofFraction(BigNumber|int|string, BigNumber|int|string)` сразу
преобразует компоненты в BigInteger; `multipliedBy(int $currentD)` выполняет
произведение BigInteger, а `BigRational::of($currentD)->minus($future)` даёт
точный retained. Дроби автоматически сокращаются; метода `simplified()` здесь
нет. Исходные unreduced n/d B03 сохраняются отдельно в ReturnProbability.
`getNumerator()/getDenominator()` возвращают BigInteger; для тестов подходят
`isEqualTo`, `isLessThanOrEqualTo`, `plus`. Преобразования в float/decimal/int,
quantity display и rounding отсутствуют. Библиотека денег не используется.

Обнаружено расхождение правил и config: комментарий `api/deptrac.php` требует
явного покрытия внешних библиотек, но Brick\\Math не имеет слоя, хотя уже
используется в SalesPlanning. Это не разрешение молча обойти правило.
Root ruling: root добавляет explicit `BrickMath` layer и grants только
IngestionDomain (новый narrow quantity VO) и существующему
SalesPlanningApplication (`SalesPlanPerformanceCalculator` уже использует
BigDecimal/RoundingMode). Остальным слоям доступ запрещён; нет baseline/skip,
широких wildcard, новой зависимости Composer или межмодульной связи.
BigRational не экспортируется наружу VO. `api/deptrac.php` принадлежит root,
implementer его не меняет. Это делает coverage строже.
