# B14. Прогноз выполнения цели и темп — план реализации

> **RELEASED_VERIFIED: B14 завершён.** PR285, production `686-a3c0489`,
> проверка 2026-10-29T03:36:47Z. Исходный план и история решений ниже;
> численная публикация остаётся закрытой до B15–B18.

**Цель:** показывать фактическое и ожидаемое выполнение исходной ручной цели,
ожидаемое отклонение и темп для обеих метрик без повторного прибавления факта.

**Архитектура:** Ingestion сохраняет точные компоненты при существующем проходе
по источникам и календарной проекции B12. Через существующий Facade в
SalesPlanning поступают скалярные exact-компоненты; калькулятор считает только
отношения к исходной цели. Seller отображает готовые серверные значения.

**Стек:** PHP 8.4, Symfony 7.4, существующие Brick Math/Money, DBAL, PHPUnit,
генерируемые OpenAPI/TypeScript, React, Vitest и типизированный MSW.

## Global Constraints

- Зависимость B14 — завершённая B13, следовательно verified B11/B12 и их API.
  B12 принят и выпущен: release `682-7612f88`, master
  `7612f88962456ab44aa2089a224113c4d24987c7`, проверка root
  2026-10-29T01:04:04Z; source `bdcf3641c5c1cc65af8be3d5636dd1832d181c61`.
  Это исходные подтверждения root, не новые проверки этого design worker.
  B13 пока активная реализация (GOBASE `4559cba`), не verified production.
  Его окончательный UI сверить до реализации, не дублировать блок прогноза.
- Исходная baseline — первая утверждённая версия линии; новые версии, обучение,
  факт и прогноз не меняют её quantity/РРЦ/даты. PlanQuantity не прогнозируется.
- Retained: `Q = currentD − futureReturns + retainedOpen` целиком.
  Orders: `Q = effectiveOrderedQuantity − expectedFutureT1` целиком.
  Факт, будущие неразмещённые заказы, известные T1/R повторно не добавлять/вычитать.
- `expectedAttainmentBps = HalfUp(Q × 10000 / planQuantity, 0)`;
  при planQuantity=0 процент null, но доступные Q, отклонение и темп сохраняются.
  `expectedGoalQuantity = HalfUp(Q, 3)`,
  `expectedQuantityDeviation = HalfUp(Q − planQuantity, 3)`,
  `expectedSpeed = HalfUp(Q / calendarDays, 3)`. Каждое отношение из exact Q,
  не из ранее округлённого expectedGoalQuantity. Нулевые дни остаются ошибкой.
- Новый expected bps проверять **до native cast/JSON** на диапазон
  `0..min(PHP_INT_MAX, 9007199254740991)`: контракт TS — number, formatter
  использует integer quotient/remainder. Выход за него делает все четыре
  expected goal поля null с `goal_attainment_overflow`. Фактические поля и
  отдельный net quantity/money неизменны. Float/clamp/truncation запрещены.
  Это уточнение root только для нового expected bps, не изменение legacy bps.
- Unknown/отсутствующий нужный компонент — null с причиной. Полные period и
  cumulative не заменять суммой доступных детей. Доступность денег отдельно.
- Company/account/readAt/epoch/snapshot берутся из существующего server scope.
  Все чтения внутри прежнего read-only RR; клиент не выбирает эти параметры.
- Publication gate B12 `NET_FORECAST_PUBLISHED_MODEL_VERSION` default closed:
  unset/empty/whitespace/несовпадающая версия закрыты. Закрытый путь не запускает
  net read и не раскрывает прогноз через goal/bps/deviation/speed или exact DTO.
- Enabled synthetic path не доказывает качество. Production numeric release
  остаётся за B15/B16/B17/B18 и HTTP prerequisite `docs/patterns.md`:
  >3 s требует отдельного согласованного архитектурного решения. B14 не открывает gate.
- Exact SUM до единственного округления; никаких float, средних вероятностей,
  React-арифметики денег или умножения decimal3 на цену. Money B11/B12 не пересчитывать.
- Новых SQL, зависимостей, очередей, миграций, таблиц и межмодульных грантов нет.
  Shared compute/memory/output/precision budgets B11/B12 не повышать и не обходить.
- Итоговый код проверяет root двумя отдельными Codex CLI сессиями по waiver
  владельца; Claude для этой фичи пропущен. Текущий этап не запускал код/ревью.

## Review Focus

1. PRE имеет T2/P: `1 − pGross` не является pT1; явный различающий тест в задаче 1.
2. Частичная недоступность скрытого дня портит cumulative, но не соседний
   доступный period; отсутствие цены не скрывает quantity (задачи 1–3).
3. Decimal3 → bps/deviation повторно округляет: границы дробей и знака
   проверяются из exact-компонентов (задача 2).
4. Closed publication при хороших источниках не публикует альтернативные
   expected-поля и не делает тяжёлого net чтения (задача 3).
5. Revision, граница месяца/MSK и другой tenant с тем же SKU не меняют baseline,
   область данных и календарный знаменатель (задача 3).

## Что существует и чего недостаточно

`SalesPlanMetric` содержит ровно `retained_sales` и
`orders_excluding_pre_handover_cancellations`. Текущий
`SalesPlanPerformanceCalculator::calculate(int $quantity, Money $revenue,
int $days, SalesPlanMetric $metric, ?SalesCohortComponents $cohort)` уже выбирает
observedNetSalesQuantity либо effectiveOrderedQuantity, считает фактические
отклонение/bps/темп и отдельно observedSalesSpeed. Expected поля — placeholders.
`SalesPlanPerformanceValues`/`PerformanceValuesResponse` имеют expectedGoalQuantity,
expectedAttainmentBps, expectedSpeed и строковый forecastUnavailableReason;
**поля expectedQuantityDeviation сейчас нет**.

`ReadSalesPlanPerformanceAction` читает original baseline под snapshot, передаёт
её period/cumulative quantity, считает дни включительно: bucketFrom..bucketTo
либо baseline.dateFrom..bucketTo. Текущий/будущий день МСК подавляет cohort.
`SalesPlanPerformanceRequest` ограничивает day 31 днём, остальные группы 184,
SKU limit ≤50. Эти границы не менять.

`NetForecastQuantities` сохраняет currentD, eligibleOpenQuantity, futureReturns,
retainedOpen и expectedNet как exact numerator/denominator. **Отдельных PRE и
future T1 там нет.** `NetForecastPart` сохраняет diagnostics openPre/openPost,
но не исходное eligibleOpenPre; взять eligibleOpenQuantity за PRE нельзя.
Probability в openPre — только pGross. Source trace не повод читать graph повторно.

Достаточные данные доступны раньше, внутри `AggregateNetForecastAction::part`:
`NetTargetPartRow::eligibleOpenPre` и resolution существующего `open()`.
`OpenRetentionResolution::selected->grossRate` для успешного PRE net —
`ScopedPreHandoverGrossRate`; его source — проверенная
`GrossTrainingAggregateRow` с t1Quantity, grossQuantity, t2Quantity, pQuantity.
`selected->grossProbability->denominator` — исходный, **не сокращённый** размер
той же mature terminal population. `BuildPreHandoverGrossRateAction` уже проверяет
company/account/context, completeness, readiness и sample thresholds.

Поэтому `pT1 = выбраннаяPreGross.source.t1Quantity /
выбраннаяPreGross.probability.denominator`. Брать numerator у SKU, denominator у
account или остаток от pGross запрещено. На T1=10, G=70, T2=15, P=5:
pT1=0.10, pGross=0.70, дополнение 0.30 неверно; PRE100 даёт futureT1=10.

Уточнение root при refresh: T1 availability независима от retention curve/
returns coverage, если сама PRE/effective population доказана. В фактическом
коде `OpenRetentionResolution::selected` существует лишь при успешной целой
gross+return паре; `OpenRetentionAssessment::unavailable()` обнуляет
grossProbability, хотя сохраняет grossRate. Значит старое решение B14 «брать
только selected retention или null» недостаточно и **заменено** ниже явным
сохранением пригодного PRE gross в том же assessment pass.

Вторая граница: B12 публикует decimal3 net quantity. Её недостаточно для exact
выполнения/темпа B14. Через существующий Facade нужен внутренний scalar carrier
до калькулятора; новые rational поля в HTTP JSON не нужны.

Фактический B12 уже имеет отдельные `SalesCohortNetMapper` и
`SalesCohortNetValues`. Mapper вызывается сразу после reader, **до gross SQL**,
использует request-local WeakMap по идентичности immutable `NetForecastScope`,
проверяет guard до/после каждой occurrence и перед return. Затем Facade
делает `unset($net)` и читает gross. `NetForecastBatch` переносит шесть
скаляров от Aggregate: computeDeadlineNs/allocationBaselineBytes/outputBytesUsed/
allocationLimitBytes/peakLimitBytes/outputLimitBytes. Сейчас mapper тратит
локальный `$used`, но наружу остаток бюджета не возвращает. Это конкретный
недостающий handoff B14; отдельный новый бюджет калькулятора недопустим.

`NetForecastQuantities::expectedNetDecimal()` уже делает прямое деление
валидированного numerator через BigInteger→BigDecimal/HalfUp без нового GCD.
Ни этот formatter, ни исходный quantity precision proof/chronological fallback
не требуют замены. Прежние предположения об inline mapping и BigRational
для каждого конечного поля ниже заменены этим фактическим устройством.

## Выбор подхода

Выбран минимальный проход: day-only futureT1 из существующей PRE resolution,
два exact scalar отношения в существующем mapper и продолжение того же
бюджета в SalesPlanning. Альтернатива вычислять цель из decimal3 отвергнута:
теряет точность. Повторный reader/graph traversal или GCD-конверсия каждого
поля отвергнуты: меняют стоимость и близки к исчерпанному бюджету. Новый общий
budget framework, глобальный cache, очередь, dependency или grant не нужны.
Это проектное решение в выданном root объёме, не уже реализованная B14.

Root явно принял уточнение FIRST valid PRE gross при refresh: прежняя фраза
«тот же selected PRE source» смешивала выбор net gross+return пары с T1-only
моделью. Целостность означает один source для t1Numerator/denominator, а не
обязательность return curve для T1. Ошибка здесь либо скрывала бы доступные
orders, либо меняла T1 вслед за доступностью returns при неизменной PRE
population. Обе ситуации требуют отдельных adversarial tests и двух review CLI.

## Выбранное bounded дополнение B14

1. Добавить отдельный `NetForecastFutureT1` VO; не менять смысл net quantity VO.
   В существующем part-проходе умножить PRE на pT1.
   Передавать локальный аккумулятор в уже существующие group/part вызовы;
   сохранять дополнительный exact carry только на day. Не удерживать новые
   ссылки на исходный graph в carrier; существующий полный graph B12 сохраняется.
   Не создавать новый per-part сериализуемый диагностический payload.
2. Сохранить первую пригодную **PRE gross population** в существующем
   `AssessOpenRetentionAction` loop SKU→own account, до применения return curve.
   Добавить `selectedPreGross` к `OpenRetentionResolution`; это отдельный
   выбор gross для T1, не замена нынешнего `selected` целой retention пары.
   Оба скаляра T1 берутся из одного выбранного grossRate. Если SKU gross
   пригоден, а его returns нет, T1 остаётся SKU даже при retained fallback
   на account. Если SKU gross непригоден — account, если оба непригодны — null
   с gross-specific reason. Не искать случайный source среди diagnostics,
   не вызывать второй resolver/read/build и не выводить пригодность из текста
   return reason. Target/context guards остаются до loop; malformed/foreign
   target и непригодный gross не допускаются независимо от returns.
   Доказанный PRE=0 даёт exact0 без training; invalid/unknown input не становится0.
   Нет риска T1 у POST; known T1 уже исключены из effective и не участвуют снова.
3. Day и scope futureT1 имеют собственную доступность: отсутствие delivered
   return risk или POST retention не подменяет известный PRE=0 неизвестным;
   повреждённый source/identity или unknown part делает соответствующий полный
   futureT1 unavailable. Отсутствие цены относится только к money.
   `emptyComplete=false` у пустого дня, **исходный** NetTargetDayRow unavailableReason и отсутствующий
   обязательный день также делают futureT1 unavailable; отсутствие строк не0.
   Уже вычисленный net day/scope reason из return model не копировать в T1;
   его отдельный sticky reason задают target identity/completeness/PRE/gross.
4. B12 `ProjectNetForecastSeriesAction` в прежнем одном проходе прибавляет
   day futureT1 к period/cumulative. Никакого second SQL/graph traversal.
   Sticky unavailable внутри диапазона; следующий независимый period начинает
   свой аккумулятор заново, cumulative продолжает оставаться unavailable.
   Текущий `publish()` переиспользует scope по quantities/revenue/reason/quality.
   Добавить в условие futureT1 identity/reason: одинаковый retained не доказывает
   одинаковые orders. Empty scope получает явный futureT1 zero. Предыдущий
   quantity folding proof не доказывает безопасность новой T1 суммы: сначала
   chronological T1 addition с прежним precision guard, без расширения proof.
5. Facade передаёт exact retained и futureT1 со своими reasons в новом
   `SalesCohortGoalForecast`. SalesPlanning выбирает Q по enum и делает только
   конечные отношения. Никакой импорт NetForecast внутренних классов в SalesPlanning.

## Карта файлов и интерфейсов после GO

Новые B14 файлы:

- `api/src/Ingestion/Domain/ValueObject/NetForecastFutureT1.php` — private
  canonical numerator/denominator strings и reason, **без постоянно хранимого
  Brick объекта и его дублированных строк**. BigInteger/BigRational допустимы
  только как временные значения exact сложения/умножения с guard вокруг операции.
  Методы:
  `zero(): self`, `unavailable(string $reason): self`,
  `fromProbability(int $eligibleOpenPre, int $t1Numerator, int $denominator): self`,
  `plus(self $other): self`, `numerator(): ?string`, `denominator(): ?string`,
  `storageBytes(): int`; readonly `?string $unavailableReason`.
  Во входной вероятности проверять0≤t1Numerator≤denominator, denominator>0,
  PRE≥0; результат futureT1 лежит в0..PRE и может быть больше1.
  Precision≤16384 digits; plus сохраняет первый unavailable reason.
  Создать один request-local zero в Aggregate и передавать его day/projector/
  emptyScope; не создавать тысячи zero объектов и не вводить static cache.
  Для unavailable использовать immutable значения; plus с доказанным zero
  возвращает существующий operand. Нормализовать/сокращать при создании суммы,
  не повторно при публикации. Private storage явно учитывать в Aggregate charge:
  `128 + 2*(strlen(n ?? '') + strlen(d ?? '')) + 6*strlen(reason ?? '')`
  как консервативный **полный charge самого scalar VO**, включая обычный128B
  object header. Explicit branch добавляет только remainder после уже взятого
  header, не взимает его дважды; enclosing container/property-key charge остаётся.
  Это не измерение PHP heap: реальную allocation/peak ограничивает общий guard.
- `api/src/Ingestion/Application/Facade/SalesCohortGoalForecast.php` — readonly
  scalar DTO: `?string retainedNumerator`, `?string retainedDenominator`,
  `?string retainedUnavailableReason`, `?string futureT1Numerator`,
  `?string futureT1Denominator`, `?string futureT1UnavailableReason`.
  Каждая пара либо целиком валидна с reason=null, либо null/null с reason.
  Деноминаторы positive canonical integer; доступные числители nonnegative.
  Каждая строка ≤16384 digits; никаких Brick/internal DTO в типах carrier.
  Его объём учесть в общем projection/output accounting, не завести новый лимит.
  Не сериализовать в HTTP, не переносить в PerformanceCohortResponse.
- `api/src/Ingestion/Application/Facade/SalesCohortForecastBudget.php` —
  readonly **только скалярный** внутренний DTO: шесть non-null int полей с

  Не переносит batch/context/Closure/Brick; не попадает в HTTP/metadata.

## Общий budget до конца goal projection

Обоснование лимита provenance каталога: actual `AggregateNetForecastAction::open`
использует key `$group->marketplaceSku.'|'.$stage`; memo локален одному вызову
aggregate и одному context. PRE stage фиксирован, age/order/date в coefficient
key нет; выбор rate использует training batch и request SKU, target PRE
умножается после memo hit. При request≤50SKU существует≤50PRE keys. Target
identity/completeness проверяется для каждого part до cache; scope/context не
становятся глобальным cache. При будущем изменении этой зависимости пересмотреть
доказательство, не обрезать каталог до50 и не терять entries.

Private provenance нужен будущему B15: version фиксирует deterministic policy,
catalogue — фактически выбранный basis и целую probability pair для каждого
SKU. B15 обязан сохранить реальный training row ledger/его hash и company/
account/readAt/epoch/captureVersion/snapshot context в forward manifest вместе
с policy version и production source hash. Сейчас NetForecastBatch context
остаётся его владельцем, на Facade границе scope берётся из вызова и actual
metadata. Каталог не доказывает replay или качество и не заменяет input ledger;
новые публичные quality поля и capture/write-сценарий не входят в B14.

Все изменения этого раздела **предлагаются для B14**, в B12 их ещё нет.
Значения caps: compute5s, peak100663296B (96MiB), allocation50331648B
(48MiB) **с уже включённым в проверку reserve8388608B**, output33554432B
(32MiB), precision16384 decimal digits. Более строгие фактические runtime
limits из batch сохраняются через min. Нельзя считать allocation как48+8MiB.

1. Aggregate добавляет charge новых coefficient memo/day/scopes в исходный
   used, передаёт тот же deadline/baseline. `charge()` не видит private поля:
   добавить explicit NetForecastFutureT1 storage branch; private scope carry
   также charge явно, независимо от сериализации. Полный group/part/source
   graph остаётся сохранённым и counted, как в B12; не выбрасывать diagnostics
   или брать более ранний baseline ради прохождения.
2. Mapper добавляет private scalar carrier и public projection к inherited
   used и возвращает updated budget только после final guard. Scope identity
   cache остаётся per-call; private carrier не удерживает исходный scope/graph.
   Каждый выходной occurrence расходует output, даже при reuse одного объекта.
3. Facade освобождает raw batch/mapper WeakMap **до** gross. Query builder
   создаётся до измерения; `hrtime(true)` непосредственно вокруг каждого из
   двух `executeQuery()->fetch*()` даёт два непересекающихся DB I/O interval.
   Только их сумма записывается в grossSqlElapsedNs. Mapping, DTO construction,
   транзакционные control statements и время между mapper/calculator не
   исключаются. SQL ошибки сохраняют прежнее поведение, не выдают budget token.
4. Проверка compute после gross: `hrtime(true) - grossSqlElapsedNs <=
   originalComputeDeadlineNs`. Вычитание elapsed безопаснее переноса deadline;
   elapsed>=0 и measured интервалы принадлежат только этому вызову. Нельзя
   заменить на `now+5s`, начинать baseline после gross или занулить used.
   Допустимо передать remainingNs только вместе с точным checkpoint и вычитать
   всю последующую работу; выбран выше более простой original-deadline DTO.
5. ReadAction создаёт request-local `$used = budget.outputBytesUsed`, closure
   принимает `int $extraBytes=0`, проверяет неотрицательность и remaining до
   сложения, затем прежние compute/allocation/peak/output границы. Calculator
   вызывает его до/после дорогих операций и добавляет charge четырёх полей с
   reason по каждой period/cumulative occurrence. После вставки результата
   и перед возвратом view — ещё guard. Heap/peak включают retained carrier,
   временные BigInteger, gross rows, plan rows и весь результат; reset peak нет.
6. Поздний общий budget failure → `input_budget_exceeded` для **всего net/goal
   forecast batch**. В bounded read-only in-memory fallback на уже прочитанных
   baseline/gross rows построить factual DTO с null net/goal и assessment reason;
   никаких повторных SQL/прогноза. Освободить partial view/carrier/bySku до
   fallback; reserve8MiB остаётся запасом для отказа, его фактическую достаточность
   проверить. Успешный результат не публиковать частично. Factual/observed/gross,
   original readAt, baseline/calendar и trusted publication status сохраняются.
   Это request-wide resource failure; обычный goal_attainment_overflow остаётся
   локальным выбранному goal результату и не отменяет независимый net quantity.

Простого guard только вокруг mapper теперь недостаточно: новый calculator
работает после двух SQL. Нельзя засчитывать их walltime в compute, но нельзя
исключать вместе с ними всю post-mapper обработку. Полный HTTP walltime
измеряется отдельно; внутренний5s budget не доказывает HTTP<3s и не открывает gate.

## Exact goal calculation без лишних rational conversions

Сначала валидировать canonical nonnegative N, positive D, обе половины пары
и длины≤16384. На metric retained: N/D из carrier expectedNet. На orders:
`N = BigInteger(effectiveOrders)*D_t1 - N_t1`, `D=D_t1`; отрицательный N →
`goal_component_mismatch`, без clamp. PRE=0 даёт N=effectiveOrders,D=1 даже
без unused model. Unknown/input failure не становится zero. Каждый новый
целочисленный intermediate bounded≤16384 digits (знак не digit), операции
окружены guard; overflow precision → общий input_budget_exceeded.

Из единственных parsed N,D получить независимо:

- Q: `N.toBigDecimal().dividedBy(D, 3, HalfUp)`;
- bps: `(N*10000).toBigDecimal().dividedBy(D*planQuantity, 0, HalfUp)`;
  при planQuantity=0 пропустить деление и оставить bps null;
- deviation: `(N - planQuantity*D).toBigDecimal().dividedBy(D, 3, HalfUp)`;
- speed: `N.toBigDecimal().dividedBy(D*calendarDays, 3, HalfUp)`.

Результат bps сначала сравнить как BigInteger с JS_SAFE_MAX и PHP_INT_MAX,
лишь затем cast. При overflow все четыре goal поля null/reason;
при zero plan Q/deviation/speed доступны/reason=null. Exact signed decimal
normalizes `-0.000` к `0.000`. Денежный результат не участвует в этих формулах.

Не строить 3–4 `BigRational::ofFraction()` на occurrence. Не считать goal в
Ingestion: там ещё нет baseline/effectiveOrders/calendar. Не cache результат
только по carrier: planQuantity/days/effectiveOrders могут различаться.
Начальный вариант — один parse N/D на вызов calculator и никакого нового cache;
если profiling выявит существенный parse cost, узкий per-request WeakMap
по carrier допускает **только parsed scalar pairs**, не готовые goal результаты,
с charge/guard и освобождением в этом же запросе. Оптимизация только после замера.
