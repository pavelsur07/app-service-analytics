# B13. Нетто-прогноз в seller — план реализации

> Завершено: source `3900aad`, master `ea84c1c`, PR #284.
> Production `684-ea84c1c` проверен 2026-10-29 01:46:47 UTC.
> Два отдельных Codex CLI0/0,19/19codeblobs,560tests/E2E/CI683684SUCCESS.
> На390px сохраняется ограничение fixedsidebar; numeric publication закрыта.

**Цель:** отдельно показывать полный ожидаемый нетто-результат размещённых
заказов в штуках и деньгах, объясняя недоступность каждого показателя.

**Архитектура:** расширить существующий `PerformanceGrid` небольшим read-only
блоком по типам B12. `point[mode]` остаётся единственным источником period /
cumulative; Query, scope, исходная цель и gross-блок сохраняются. Описание
методики выводится один раз над таблицей, причины — возле соответствующих чисел.

**Стек:** существующие React / TypeScript strict, TanStack Query, `packages/ui`,
Vitest, типизированный MSW и seller Playwright journey. Без новых зависимостей.

**Spec:** [общий план B13](../sales-planning-daily-implementation.md),
[A40](A40.md), [проект B12](B12.md), [будущая B14](B14.md),
[ADR-049](../../adr/0049-net-sales-forecast-observations-and-horizon.md),
[правило ревью владельца](../sales-planning-review-rule.md).

## Global Constraints

- Это небольшая законченная UI-задача после B12, не redesign и не новая модель.
  Название реального компонента — `PerformanceGrid`, не `SalesPlanPerformanceGrid`.
- Net — полный итог `D − futureReturns + retainedOpen`, не добавка к факту,
  не gross buyout, не сезонный прогноз ещё не размещённых заказов.
  Клиент не вычисляет эту формулу, цены, отношения или суммы.
- Ручные baseline/quantity/РРЦ, редактор, текущие observed и gross значения не
  меняются. Expected attainment / goal quantity / speed принадлежат B14.
- Quantity — серверная decimal string с тремя знаками. Не преобразовывать через
  Number/parseFloat, не округлять повторно и не суммировать отображённые дни.
- Money берётся только из `expectedNetRevenue`, с его currency и authoritative
  fractionDigits от backend. Выбранный root проект нового net transport передаёт
  minor canonical signed string; см. preflight ниже.
  Не подставлять
  цену/валюту плана, не получать деньги умножением quantity на РРЦ.
- Null/undefined означает «—» и объяснение, не ноль. Доступность units и money
  независима. Доказанный сервером `0.000` / `minor: '0'` отображается числом.
- Только API-типы из `apps/seller/src/api/schema` → `packages/api-schema`.
  Не редактировать генерацию вручную и не вводить ручную копию API DTO / `any`.
- `createCompanyApiClient`, `companyQueryKey`, TanStack Query и параметры
  существующего performance query сохраняются; новых запросов и локального
  хранилища net данных нет. UI не передаёт model/epoch/account/readAt.
- Текущий UI запрашивает 20 SKU на страницу; day максимум 31 видимый день,
  accumulated horizon ограничен сервером. Не расширять окна/лимиты, не добавлять
  запрос на каждый SKU/день и клиентское получение всех страниц.
- Default-closed B12 остаётся закрытым. `validation_pending` и `not_assessed`
  не означают обученность, успешное качество или проверенные источники.
  Данные B16 ещё отсутствуют. B13 не открывает публикацию и не обещает accuracy.
- Применять существующие `Badge`, `Card`, `Button`, семантические `dl/details`
  и классы токенов; `packages/ui` менять не требуется.
- Root проводит две реальные отдельные Codex CLI сессии после реализации.
  Claude пропущен по явному правилу владельца для этой фичи; остальные gates
  сохраняются. Этот design-only проход не является ревью кода.

## Review Focus

1. Доступные units при отсутствующей цене: quantity видна, money «—» со своей
   причиной, observed/gross не подавлены (шаги 1–2).
2. Закрытая публикация при полном gross coverage: только pending/not_assessed,
   без ложного «обучено», epoch/readAt из legacy или зелёного quality pass (шаг 2).
3. Скрытые дни накопления: cumulative ровно из API, даже если period доступен,
   а cumulative null; доступный ноль не теряется в truthiness (шаги 1–2).
4. Большой minor, отрицательная сумма, валюта с иным exponent: root разрешает
   границу до кода; проверка не маскирует проблему через clamp/подмену валюты (шаг 0).
5. Переключение компании/версии/страницы и ошибка повторного запроса: старый
   net не остаётся на новом scope; клавиатурный доступ и причины без цвета (шаг 3).

## Что существует сейчас

- `ui/PerformanceGrid.tsx` — таблица SKU × даты, sticky row headers, caption,
  focusable horizontal region; в ячейке отдельные Orders / Sales / Attainment /
  Buyout / Forecast. Значение выбирается `const value = point[mode]`.
- `ui/PerformanceForecast.tsx` — именно текущий gross прогноз выкупа, с
  объяснением unestimated ≤10% / >10%. Это правило не переносится в net.
- `ui/PerformanceSales.tsx` показывает observed quantity/revenue/speed и устаревающее
  общее сообщение «Пока не оцениваем будущие возвраты…». B13 убирает только этот
  placeholder; для B14 не добавляет фиктивных чисел или прогнозной скорости.
- `ui/PerformanceQuality.tsx` описывает загрузку заказов и current/future day.
  Его зелёный complete badge не является оценкой net и не переиспользуется как такая.
- `ui/SalesPlanPerformance.tsx` владеет URL window/mode/cursor, обновлением,
  loading/error/success, recovery и page navigation. Metadata net можно разместить
  внутри существующей success ветки перед `PerformanceGrid`.
- `model/useSalesPlanPerformance.ts` строит company query key с planId, окном,
  grouping, cursor, limit, headerVersion; отключает запрос при пустом company/plan.
- `tests/fixtures/salesPerformance.ts` типизирован через `satisfies`; network test
  получает typed MSW response через настоящий QueryClient/client и рендерит grid.
- Принятая B12 generated schema содержит nullable decimal3 quantity, новый
  string-minor Money с authoritative fractionDigits0..4, независимые nullable
  причины, compact quality и top-level netForecast metadata. Legacy Money
  остаётся numeric; generated files в B13 не меняются. Root сверил actual
  PHP/OpenAPI/TS и production release, ручные API-копии/casts не нужны.

## Выбранный подход и интерфейсы

Использовать отдельную группу показателей внутри существующей date-cell;
это сохраняет сравнение по датам и различает fact/gross/net без второй таблицы.
Новая таблица дублировала бы scope и navigation; смешивание с gross-блоком
сделало бы прежние 10% правила двусмысленными. Выбор следует design brief;
новых продуктовых решений на согласование не требуется.

Следующие поля подтверждены accepted source и проверенным выпуском B12:

| Источник | Использование в B13 |
|---|---|
| `cohort.expectedNetSalesQuantity: ?string` | «Ожидаемые нетто-продажи», `90.000` → `90,000 шт.` |
| `cohort.expectedNetRevenue` | «Ожидаемая нетто-выручка»; принят отдельный DTO `{minor: string, currency: string, fractionDigits: int}`; B12 проверен на production |
| `netForecastUnavailableReason`, `netForecastMoneyUnavailableReason` | Отдельная объясняющая строка возле недоступного показателя |
| `cohort.netForecastQuality` | Только реальные scope/reasons и assessment/validation; нет synthetic sample sums |
| top-level `netForecast` | Методика, horizonDays, assessmentStatus, validationStatus; readAt только если сервер прислал |

В выпущенном B12 top metadata: methodology=`observed_retention_h60_v1`,
trainingVersion=`net_training_observed_v1`, horizonDays=60,
scope=`placed_order_cohorts`; закрытый путь имеет readAt/epochId/captureVersion=null,
assessmentStatus=`not_assessed`, validationStatus=`validation_pending`.
Эти строки — ожидаемый контракт для preflight; UI не хардкодит 60 вместо поля.
Наличие methodology/trainingVersion описывает предусмотренную методику,
не доказывает, что по этой строке было обучение. `release_approved` означает
разрешение публикации, а `assessed` — попытку оценки, не заявленную точность.

### Тексты и состояния

- Краткое пояснение методики: «Полный ожидаемый результат уже размещённых
  заказов с учётом будущих клиентских возвратов. Наблюдаемые продажи уже входят
  в него. Будущие заказы не учитываются. Горизонт возвратов — {horizonDays} дней
  от доставки». Это не обещание доставки/итога через 60 дней от сегодняшнего дня.
- `validation_pending`: «Проверка качества прогноза ещё не завершена.
  Численная оценка пока не публикуется». `not_assessed`: «Оценка по этим данным
  не выполнялась». Не писать «не хватает истории» при closed path: источники
  ещё не читались. Обе строки могут быть видимы в общем methodology блоке.
- `cohort == null`: обе пары имеют «—» и «Нет полных данных для нетто-прогноза»;
  existing current/future quality поясняет календарную причину. Не создавать cohort.
- Доступная quantity с money null: количество показать; перевод money reason
  отнести только к деньгам. Нулевая цена, если сервер прислал minor='0', — число.
- Словарь покрывает подтверждённые публичные причины B12, в том числе pending,
  source history, budget и missing price/currency/mismatch. Не выводить внутренние
  raw codes как понятное объяснение и не считать внутренний B11 список публичным.
  Неизвестная причина → «Нетто-прогноз недоступен» / «Нетто-выручка недоступна»,
  без догадки о причине или подстановки нуля.
- Training scopes/reasons переводить только из фактического compact quality;
  пустой список при not_assessed не означает успешные источники. Не показывать
  sample count, accuracy, backtest, историческую воспроизводимость, которых API нет.
- Состояния доступны текстом, не только цветом/title. Нативные `details/summary`
  доступны с клавиатуры. Повторять полное описание модели в каждой ячейке не нужно.

### 1. Отображение чисел и причин

- [ ] RED: `90.125` → `90,125 шт.`, `0.000` → `0,000 шт.`, большая decimal string
  сохраняет все цифры; null не передаётся formatter. Для reason проверяются
  pending / missing price / неизвестный код и независимость unit/money текстов.
- [ ] RED exact money helper: `9223372036854775807` и `-9223372036854775808`
  (64-bit PHP_INT_MAX/MIN) сохраняют все цифры; явно переданные JPY exponent0,
  RUB2, KWD3, CLF4,
  каждый со строками `0`, `1`, `-1`. RUB `-1` → `-0,01 ₽`, KWD `-1` →
  `-0,001 KWD` с локальным символом/пробелами Intl, CLF `-1` → `-0,0001 CLF`,
  JPY `-1` → минус одна иена. Для неизвестного клиентскому Intl кода с exponent4
  строка `-1` остаётся `-0,0001 CODE`: отображение кода вместо символа не меняет сумму.
  Проверить отсутствие зависимости от default2 и отказ при нецелом/недопустимом
  fractionDigits; нарушение контракта не превращается в ноль или guessed exponent.
  В тестах проверять точные цифры и знак, учитывать NBSP в локализованной валюте.
  Для RUB max → `92 233 720 368 547 758,07`, min →
  `-92 233 720 368 547 758,08` (разделители Intl); ни округления последней копейки.
  Canonical contract исключает `-0`, ведущие нули, exponent notation и дробный minor.
- [ ] RED net component: quantity доступна/money отсутствует, оба null,
  cohort null/undefined, настоящий zero quantity/zero money, ненулевая цена,
  currency из money при отличающейся plan currency. Знак/границы денег — по
  разрешённому root контракту; запрещены abs/clamp/FX/wholeUnits округление.
- [ ] Реализовать presentation helper, общий exact money helper и net component,
  запустить scoped RED→GREEN
  через существующий контейнерный front-test workflow; не придумывать Make FILTER.
  Сохранить точную команду и результат, не только ожидаемый PASS.

## Денежная граница и принятое совместимое решение

`PerformanceMoneyResponse.minor` сейчас `number` в TS; PHP native int/bigint
может выйти за `Number.MAX_SAFE_INTEGER`. Из прочитанной схемы не следует safe-range
ограничение. `shared/lib/formatMinorAmount.ts` форматирует `minor / 100` через Intl,
без проверки safe integer; при больших minor возможна потеря точности уже при JSON
parse, а вблизи safe-range — при показе дроби. Простая проверка safe integer не
доказывает точность всей области форматирования.

Тот же helper предполагает scale 100 для всех валют, а Intl выбирает знаки по
currency. ADR-004 задаёт ISO minor units; schema допускает произвольную string.
Существующие tests покрывают лишь положительные RUB/USD и wholeUnits;
отрицательные деньги и верхняя граница не проверены. Quantity pattern B12 отдельно
неотрицательный и не задаёт ограничений знака Money.

Root принял и проверил следующий контракт B12; B13 реализует его отображение:

1. **B12-owned принятый контракт:** новый `PerformanceNetMoneyResponse` вместо
   предложенного legacy `PerformanceMoneyResponse` только для expectedNetRevenue.
   Поля `minor: string`, `currency: string`, `fractionDigits: int`;
   fractionDigits authoritative от backend, minor canonical signed integer,
   pattern `^(0|-?[1-9][0-9]*)$`. PHP сериализует `(string) $money->minorAmount()`
   без float; `PHP_INT_MIN` не проходит через `abs`. Legacy observedRevenue,
   planRevenueRrp, revenueDeviation и gross shapes не меняются. Source OpenAPI
   и generated TS получают string и integer стандартной генерацией B12.
   Минимальная proposed Shared extension B12: `Money::fractionDigits(): int`
   как scalar wrapper над private Brick currency; Brick не выходит из Money.
   Это вне B11 ownership, требует отдельной B12 проверки, не изменения модели.
   PHP tests фиксируют JSON strings обоих integer bounds, 0/-1, currency и
   authoritative exponent JPY0/RUB2/KWD3/CLF4; это работы B12/root,
   не разрешение design worker менять Shared, API или чужой план.
2. **B13-owned реализация:** новый shared seller `formatMinorAmountExact`.
   Масштаб брать исключительно из `fractionDigits` DTO, не из Intl metadata,
   локального списка валют или default2. Intl используется только для группировки,
   десятичного разделителя и locale placement знака/валюты в `ru-RU`; шаблону
   явно задаётся серверное число дробных знаков. Currency не подменяется плановой.
   Неизвестный клиентскому Intl, но валидный серверный код выводится кодом рядом
   с точно собранной суммой; отсутствие знакомого символа не повод менять масштаб.
   Если currency formatter отверг код, использовать decimal locale parts и сам
   серверный код, сохранив authoritative scale и знак. Невалидный fractionDigits
   — нарушение контракта: явно недоступное значение без угадывания суммы.
   Root сверяет допустимые целочисленные bounds exponent с B12 до GO;
   обязательные 0/2/3/4 не урезать до 2. Новый валютный справочник/FX не нужен.
3. Внутри helper отделить знак строкой, дополнить magnitude нулями и разделить
   digits по exponent. Для группировки целой части допустим `BigInt(integerDigits)`
   с Intl `formatToParts`, без конверсии в Number; дробные digits подставляются
   строкой в currency parts. Минус формируется по исходному знаку, включая -1 minor
   при нулевой целой части; signed template не должен потерять его из-за `BigInt('0')`.
   Это форматирование готовой суммы, не денежная арифметика: нет суммирования,
   умножения, расчёта цен/модели или повторного округления. Компонент только вызывает
   helper. Не полагаться на `Intl.format(Number(decimalString))` или float division.
4. Root закрепляет boundary tests шага1 и проверку сериализации B12 перед GO.
   Invalid/noncanonical input не превращать в 0 или fallback RUB; ожидаемый API
   должен исключать его. Если обработка нарушения контракта требуется, показывать
   недоступное значение явно без молчаливого искажения, по согласованной API policy.

Это минимальный совместимый путь без изменения уже существующих денежных полей.
