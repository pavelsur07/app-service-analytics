## 2. Реальное хранилище и решения до GO

Существующий `Ingestion/Domain/RawDocumentStorage`:

```php
put(string $companyId, RawObjectKey $key, string $body): void;
get(string $companyId, RawObjectKey $key): string;
exists(string $companyId, RawObjectKey $key): bool;
```

`RawObjectKey::for(Uuid $companyId, Uuid $marketplaceAccountId,
string $reportType, DateTimeImmutable $period, string $bodyHash,
string $extension): RawObjectKey` строит
`conwix/raw/v1/companies/{company}/accounts/{account}/{report}/{Y}/{m}/{d}/{sha256}.json.gz`.
`S3RawDocumentStorage` проверяет компанию, gzip, `IfNoneMatch='*'`, ждёт
`resolve()` и принимает 412. Нет streaming put/get, list, delete, CAS по
capture ID или готового artifact registry. Наличие объекта не проверяет hash
байтов: B15 обязан проверять его сам при чтении, включая повтор после 412.

`MarketplaceRawDocument::capture(Uuid company, Uuid account, string report,
DateTimeImmutable period, string rawBody, ?DateTimeImmutable receivedAt)`
вычисляет SHA256 и UUIDv7. `MarketplaceRawDocumentRepository::add(document): Uuid`
сначала пишет объект, затем DBAL UPSERT по
`(company_id, marketplace_account_id, report_type, period, body_hash)` и
возвращает **реально существующий** UUID. Чтение:
`body(string companyId, Uuid accountId, Uuid id): string` и
`latestBody(string companyId, Uuid accountId, string reportType): ?string`.
Последний метод для replay B15 запрещён. `RawDocumentBody::read` пересобирает
ключ из scoped row; database-body fallback сам hash не проверяет.

**Фактический storage preflight root:** сохранённый локально
`var/sales-planning-b15-storage-preflight.json`, `2026-10-29T02:05:07Z`,
`appVersion=684-ea84c1c`: `conditionalWrite=ignored`, собственный healthcheck
штатно удалён; очистка его исторических версий не подтверждена.
Versioning `Enabled`. Lifecycle ответил HTTP404
`NoSuchLifecycleConfiguration` — это отсутствие политики, хотя обёртка JSON
помечает результат `unverified`. SDK не предоставляет нужных public-policy
методов; права и приватность **нового** prefix не проверены. Объекты компаний
probe не читал и не писал; этот design worker production не проверял.

**Дополнительный preflight root, 2026-10-29T02:25:49Z:** один свежий
синтетический объект в выбранном новом prefix успешно записан и прочитан
с проверкой size/SHA256; анонимный GET вернул HTTP403. Удалена только
полученная точная версия этого объекта, последующий GET подтвердил отсутствие.
Данные компаний и политики не менялись. Артефакт:
`var/sales-planning-b15-prefix-preflight.json`. Первый неуспешный запуск
проверочного скрипта сохранён отдельно; его пробная версия также удалена.
Это проверка одного пути, **не** аудит всей bucket policy, retention или recovery.

Следовательно, **прежний no-schema fixed-key root CAS отвергнут**: два разных
RR могут перезаписать один manifest. Выбран заранее предусмотренный fallback:
минимальный publication fact Ingestion, Entity и **одна additive migration**;
объекты содержат хэш в ключе, а победителя выбирает durable unique insert БД
после закрытия RR. Это предусмотренная полным планом альтернатива, не новый
объём и не новый запрос согласования. Implementation GO всё ещё не выдан.

Остаются отдельные artifact port/key в Ingestion и существующие client/bucket.
Synthetic payload не помещается в `MarketplaceRawDocument` или external API
raw namespace. Приватность бакета — архитектурное требование, а не доказанный
результат нового preflight. Поиск всех captures не нужен для v1.

Проверено чтением `api/config/services.yaml`: service `AsyncAws\S3\S3Client`
использует существующие `RAW_STORAGE_*`, pathStyleEndpoint=true, logger=null;
`string $rawStorageBucket` уже bind. В `api/deptrac.php` collector
`src/Ingestion/Infrastructure/Storage/.*` имеет доступ к AsyncAws/Domain/Uuid;
Application видит Domain port. Новый adapter использует этот client;
interface alias — обычный DI wiring. Новых dependency/module grants нет.
Это новый узкий API, **не** существующий контракт RawDocumentStorage.

Предлагаемая константа собственного monolith prefix:
`conwix/monolith/net-forecast/v1/companies/{company}/accounts/{account}/`.
Под ним root:
`{kind}/{requestId}/attempts/{attemptId}/manifests/{artifactSha256}.json`;
chunks: `{kind}/{requestId}/attempts/{attemptId}/chunks/{ordinal}-{sha256}.json`.
`kind` — enum `input|truth`; IDs канонические UUIDv7 приложения, hash —
64 lowercase hex. `artifactId` в дальнейших разделах означает requestId
**вместе с kind/company/account**, отдельного суррогатного ключа нет.
Всякий новый RR получает новый attemptId. Внутри attempt повтор допустим
только с теми же sealed bytes; root включает attemptId и полную identity.
Готовый path/URI извне не принимается. Prefix отделён от PHP raw и
Go `conwix/svc/...` ADR-044; fixed-key `manifest.json` больше не существует.

Writer до отправки проверяет SHA256 тела против typed key, после PUT делает
bounded GET и сверяет точные size/hash. `IfNoneMatch='*'` можно сохранить
как оптимизацию на поддерживающих providers; ни 2xx, ни 412 не доказывают
правильные bytes без GET. Игнорирование заголовка безопасно для identity:
по тому же content-addressed key наш writer может отправить лишь те же bytes.
Никакого fallback перезаписывания fixed root нет. Это не WORM/Object Lock:
ошибочная/чужая запись обнаруживается внешним DB hash, но может нарушить
доступность. SHA256 не защищает от администратора, меняющего и БД, и бакет.

**Минимальная предлагаемая схема `net_forecast_artifact`:**

| Колонки | Тип и назначение |
|---|---|
| `company_id`, `marketplace_account_id` | native `uuid`, NOT NULL, explicit scope |
| `kind`, `request_id` | `varchar(5)` enum input/truth и native `uuid`, NOT NULL |
| `request_hash` | `char(64)`, NOT NULL, SHA256 нормализованного исходного request |
| `attempt_id`, `artifact_hash` | native `uuid` и `char(64)`, NOT NULL, победивший attempt и hash envelope bytes |
| `manifest_byte_size` | `integer`, NOT NULL, 1..1048576, bounded read до decode |
| `published_at` | `datetime_immutable` / `TIMESTAMP(0) WITHOUT TIME ZONE`, UTC audit вставки, не capture/commit time |

Единственный необходимый индекс — естественный PRIMARY KEY
`(company_id, marketplace_account_id, kind, request_id)`. Он одновременно
закрывает unique first-winner, lookup B16 по exact ref и scoped request retry;
request_hash **не входит** в ключ, иначе другой request с тем же UUID создаст
второго winner вместо conflict. Отдельных global UUID, listing/date, parent
индексов и reservation/attempt таблиц нет. Parent input ref/hash, exact
`actualReadAt` с исходной UTC microsecond precision, codec/model versions и
counts остаются в sealed root, не дублируются усечённым timestamp БД. Reader
возвращает actualReadAt именно оттуда. Kind/hash/size проверяются Domain и
codec; ограничения и Doctrine mapping должны согласоваться в schema validation.
Plan/baseline refs остаются в payload: межмодульных ORM associations нет.

Entity `Ingestion/Domain/NetForecastArtifact.php` — `class`, составные
`#[ORM\Id]`, все колонки mapped; DBAL immutable INSERT, без ORM persist/flush.
`ON CONFLICT (company_id, marketplace_account_id, kind, request_id) DO NOTHING`
с последующим scoped SELECT в новом statement сохраняет первую строку,
никаких UPDATE winner/hash/readAt. Это не snapshot-day fact ADR-034.
Опора на существующий код: `SalesFactRevision`/B02 migration показывают
естественный составной ключ, Entity и DBAL факты; raw repository показывает
object-before-row и возвращает реальный winner. Его mutable COALESCE/no-op
UPSERT здесь **не копируется**, а отдельная immutable публикация описана явно.

**Открытое эксплуатационное расхождение:** ADR-024 требует lifecycle удаления
неактуальных версий, если provider игнорирует conditional PUT; реальный bucket
policy отсутствует. DB anchor снимает зависимость корректности B15 от CAS и
version cleanup, но не исправляет это нарушение и не даёт обещания ограниченного
роста bucket. Для B15 prefix остаётся проверить existing write/read IAM,
приватность, retention/recovery и исключение из 90-дневного service TTL.
Root должен зафиксировать способ закрытия эксплуатационного расхождения
до release readiness; этот дизайн не выдаёт waiver ADR-024. B15 не меняет lifecycle, retention, IAM,
bucket/dependencies/queue/transport/grants и не заводит deletion job.
Tenant export/deletion inventory включает новый prefix **и publication table**;
raw-storage verify эту отдельную таблицу не проверяет.

**Выбранная root граница:** goal/baseline принадлежат SalesPlanning. Plan-linked
capture использует узкий `CaptureSalesPlanForwardAction` в SalesPlanning:
он читает свои plan/baseline rows в общем RR и через существующий
`IngestionFacade` готовит manifest; публикация после RR также через Facade.
Прямой доступ SalesPlanning к Ingestion queries/storage запрещён. Новых
Deptrac grants нет: остаётся существующий разрешённый module link через
IngestionFacade. Уточнение prepare/publish, DB publication fact и своего
storage prefix фиксируется будущим исполнителем в ADR-049 до кода, а не
оформляется скрытым обходом правил. Core-only capture с goal not_applicable
не выбран вместо полной plan-linked приёмки.

## 3. Единица capture и неизменяемый контракт

Одна операция: явно известные company/account, explicit request UUIDv7,
версия формата, не более 50 SKU и 184 календарных дней с accumulation window.
Отдельный bounded application scenario/CLI; GET сохраняет read-only поведение.
Никакого общего обхода компаний, scheduler, новой очереди или вызова Ozon.
Пустые/nullable результаты тоже фиксируются с причинами; они нужны для null
share, а не превращаются в scoreable forecasts.

Private capture обращается к реальному внутреннему source/model/numeric path
даже при закрытом **public** publication gate B12–B14. Иначе нельзя накопить
forward quality для открытия gate. Это не публичный bypass: capture artifact
доступен только явному внутреннему сценарию; HTTP/Facade response publication
policy сохраняется. Недостаточный training/coverage по-прежнему даёт null;
закрытый validation gate не должен искусственно обнулять уже вычисленные
пригодные private numbers. В artifact раздельно сохранить source/model reason
и public policy `validation_pending`. Scheduled/request time — только audit;
actualReadAt всегда принадлежит winning RR manifest, не времени первого retry.

Root manifest `net_forward_manifest_v1` содержит:

- tenant/account, artifact/request IDs, normalized request hash, тип artifact,
  model/training/coverage/capture/codec versions, software release;
- один `readAtUtc`, pin snapshot diagnostic, epoch ID/start/end/cutover release,
  timezone policy, H=60, L=7, windows и все effective operational caps;
- scope: SKU, order-date/accumulation ranges, grouping, filters, plan ID/version,
  baseline ID и **видимые значения** baseline/goal/metric/currency/period;
- полный model input: точные gross numerator/denominators/p95, return profile
  bins0..59/boundary60, samples/risk lower bounds/exclusions, fallback scope и
  выбранные coefficients; сохранить и отвергнутые scope attempts;
- typed target rows **до агрегации**: order/SKU/source/posting identities,
  D(T)/knownR/openPre/openPost/T1/T2/P/unknown, delivery origins/readiness,
  accepted revision IDs/values, unit minor price/currency, return links;
- source evidence segments: реально видимые relevant sales/return revision
  IDs с потреблёнными значениями; status composite IDs `(posting_number,
  raw_document_id)` с observed fields; receipts IDs/полями, включая failures
  и successful empty; current source membership/revision proof, которым
  пользовался SQL. Capture time не заменять business/visual time;
- прогноз и две базы **на T**: mature return-share baseline и старый
  projectedBuyout, каждая с version/scope/inputs/null reason. Старую методику
  не изменять; несопоставимый scope хранить unavailable, не выдумывать число;
- quantities и money по публикуемым scopes, null reasons/coverage, суммы и
  дроби как canonical integer strings с currency. Части до округления
  воспроизводятся из inputs/coefficient pairs, а не из округлённого JSON API;
- упорядоченные descriptors chunks: type, number, rowCount, byteSize, SHA256,
  key reconstruction metadata; total counts, root schema version.

**Representation decision:** hashes aggregates или только first/latest IDs
недостаточны. Хранить actual consumed row IDs **и значения нужных колонок**,
а не всё raw API и не PII/warehouse descriptions. Это даёт replay без доступа
к будущему source DB и audit принятых/исключённых групп. Для training account
fallback scope включает account-wide population до SKU/page filtering,
closure всех исторических связей и completeness witnesses. Нельзя выгрузить
только 50 запрошенных SKU и назвать это audit account training.

**Зависимости B14/B16, без изменения их реализации.** После принятого B14
сверить independent first-valid PRE gross T1 policy
`pre_t1_gross_first_valid_v1`: PRE gross выбирается независимо от retained
pair fallback, последний не меняется. Private catalog <=50 SKU — только
ограниченный перенос вычисленной provenance; catalog сам по себе не заменяет
actual inputs/training/evidence для replay и audit. Manifest должен сохранить
реально выбранные PRE и retained scopes/rational rates, все attempts/reasons,
policy versions и фактическое потребление. Текущие B14 сигнатуры provisional;
B15 не пересматривает его бюджеты или расчётную логику.

Переданное root prospective решение B16 от 2026-10-29:
`simple_mature_return_linear_h60_v1`, conservative ready/null-share/money gates
зафиксированы до реальных outcomes. B15 сохраняет отдельную фактически
видимую в **том же RR** baseline membership/rate, version, exact fractions,
fixed price/currency T и unknown reasons; независимо от selection модельного
fallback. Подмена базовой population модельной без доказательства равенства
или её будущая реконструкция из DB недопустимы. Старый projectedBuyout также
фиксируется на T и не меняет методику. Фактический B16 protocol scope/windows/
currencies ещё не выбран и не sealed; он должен быть закреплён до сбора
соответствующего оценочного набора. Это dependency, не заявление об actual
samples, predictive accuracy или B16 GO; B16 документы здесь не меняются.

Версионированный encoder задаёт точные field order, UTC precision, null,
UTF-8, list ordering и canonical integer strings; unknown fields/versions
fail closed. Plain JSON envelope хранит typed payload и `payloadSha256`,
хешируемый только по canonical payload bytes (без самого поля hash).
`artifactSha256` полных envelope bytes возвращается в `ArtifactRef`; truth
и B16 dataset фиксируют его независимо. Chunk hashes входят в root payload.
Невалидные числа/валюта/версии не приводятся к default. SHA256 проверяет
целостность и ссылки; ожидаемый root hash закреплён durable DB publication
fact, chunk hashes — в этом root. Приватность S3 проверяется отдельно.
Hash в том же объекте не является подписью против
администратора, способного переписать его целиком. Reader при replay по
ArtifactRef обязан также сверить внешний ожидаемый artifactSha256.

## 4. Один RR, seal, публикация и повтор

1. Проверить explicit authorized tenant/account и принадлежность plan;
   нормализовать request, вычислить requestHash из **исходных параметров**,
   включая версию request policy, kind, plan ID и для truth exact parent
   input ref/hash; не из mutable plan values/readAt/нового software release.
   Scoped DB lookup по полному PK — быстрый путь, не гарантия дублей.
   Найденная строка с другим requestHash даёт explicit conflict; с тем же —
   fully verified winner. Ни ошибка DB/S3, ни corruption не означают absent.
2. Capture orchestration требует отсутствия внешней транзакции. Открыть
   собственный read-only RR, pin **до** единственного readAt. Прочитать
   plan/baseline и весь input/model/baselines через одну Connection,
   context/readAt/pinned snapshot. Common RR допускает внутренний guard
   `NetTrainingSnapshot`, но выход из nested savepoint не означает закрытия
   внешнего RR. Capture не принимает произвольный прошлый `asOf`.
3. Выделить минимальный typed `NetForecastReadFrame` (context, targets,
   training, calculation inputs). `ReadNetForecastAction` и capture используют
   общую materialization path; training не вызывается повторно со свежими
   часами. Дополнительное evidence читается **в том же pinned RR**, теми же
   source selectors/predicates. После RR искать revisions по времени нельзя.
4. `NetForwardEvidenceQuery` выдаёт bounded DBAL/keyset pages релевантных
   source rows; stable identity сортировка не является causal order.
   Связать evidence с реально потреблёнными row sets/context, проверить
   лимиты/полноту; сериализовать private local spool до закрытия RR.
   Все страницы принадлежат одному snapshot; overflow не усекать до success.
5. Завершить **внешний** RR; после успешного выхода проверить, что DBAL/native
   Connection не находится в транзакции. Закончить hash/root seal над уже
   материализованными bytes. DB/S3 writes внутри RR запрещены; spool — ещё
   не опубликованный artifact. Ошибка закрытия RR отменяет подготовку.
6. Вне любой DB transaction проверить spool; записать и прочитать обратно
   все bounded chunks attempt, затем content-addressed root. Проверить
   SHA256/size/scope/version каждого объекта и всех descriptors. Root включает
   tenant/account/request/hash/kind/attempt, parent ref/hash для truth,
   exact readAt, versions/counts. S3 объект сам по себе ничего не публикует.
7. Только после полного object verification открыть короткую собственную
   **READ COMMITTED read-write** transaction. Выполнить INSERT публикационного
   факта с `ON CONFLICT (...) DO NOTHING RETURNING` нужных колонок. При
   конфликте отдельным следующим SELECT по полному PK прочитать winner:
   один CTE INSERT+SELECT может не увидеть concurrent winner в statement
   snapshot. Уникальный PK ждёт конкурирующий INSERT; если тот rollback,
   текущий INSERT может победить. В этой транзакции нет S3 IO/долгого RR.
   Сравнить requestHash; mismatch — conflict без изменения winner. Commit
   собственных изменений — точка durable публикации, не время SQL RETURNING.
8. После commit получить winner через scoped reader и полностью сверить
   DB anchor/root/chunks/parent. Возвращать **winner artifact с его actualReadAt**,
   никогда локальный результат проигравшего RR. Ошибка финального чтения не
   откатывает уже committed факт; вызывающий получает unavailable и может
   повторить чтение по прежней identity. UUIDv7 генерируются приложением.

| Сбой/гонка | Состояние и повтор |
|---|---|
| Chunk/root PUT, hash verification или timeout до DB INSERT | Публикации нет; только bounded orphan attempt. Exact sealed bytes можно повторить в пределах бюджета, после потери spool новое T — новый RR/attempt. |
| Ответ PUT потерян | Сначала bounded GET того же hashed key; если hash совпал, не писать заново. Только доказанный 404 допускает ограниченный exact-byte retry. Ошибку доступа/timeout не считать отсутствием. |
| Два разных RR одного requestHash | Оба могут загрузить свои blobs; committed PK выбирает один. Loser читает и возвращает winner, свои objects не удаляет. |
| Одинаковый request UUID, разные requestHash | PK один, проигравший получает explicit conflict; ни новое readAt, ни UPDATE опубликованной строки не допускаются. |
| DB INSERT/commit отказал до durable commit | Objects orphan; до разрешения неопределённости успех не сообщать. При достоверном rollback тот же prepared attempt можно перепубликовать. |
| Ответ COMMIT потерян / Connection разорвана | Через восстановленную connection отдельный scoped lookup; если row есть — verified winner, если достоверно absent — повтор INSERT с теми же bytes. DB unavailable остаётся unavailable, не новый request UUID. |
| Сбой после commit, потерян stdout | Повтор с исходным request UUID находит тот же DB row/root; новый capture не нужен. |
| После публикации missing/tampered chunk/root, unknown codec | Corruption/unavailable; не заменять row/root новым capture или свежими source данными. Восстановление exact bytes/hash — отдельный recovery, не silent retry. |

DB и S3 не образуют распределённой транзакции: проверка до INSERT исключает
публикацию **известно** неполного attempt, но не гарантирует, что объект не
исчезнет позже. Read verification и coordinated DB+bucket recovery обязательны.
Root hash из БД закрепляет ожидаемые bytes; объект с hash внутри себя не
может заменить этот внешний anchor. При утрате DB публикаций одни orphan
roots не доказывают, какой RR победил: автоматического восстановления winner
сканированием S3 нет. При потере spool до публикации прежний T не captured;
новая попытка имеет новое actualReadAt, не время первого запроса.

Reader: caller authorization → DB SELECT по company/account/kind/request UUID
→ key, пересобранный **из scoped row** → ожидаемые DB hash/size → root scope,
requestHash/attempt/codec → bounded chunk descriptors/hash → replay.
Parent truth указывает `(kind=input, requestId, artifactHash)` того же
company/account и тоже читается через DB anchor. Parent допускается только
input без parent (один уровень, без цепочек/cycles). Ни глобального UUID-only
lookup, ни S3 LIST, ни прямого чтения caller-provided URI нет. B16 передаёт
exact typed refs; batch <=50, metadata одним bounded scoped DB query по
списку `(kind,requestId)`, без SQL в цикле. ArtifactRef включает kind,
requestId и ожидаемый artifactHash; scope передаётся отдельными обязательными
параметрами. Missing ref не заменяется latest. Cache в v1 не нужен; если
появится — company/account/kind/request/hash/codec/model обязательны в ключе.
Артефакты/ключи/тела не выходят в публичный HTTP или логи.

**Orphan/version budget, без обещания глобального GC.** Предлагаемые caps §5:
один новый attempt на invocation, <=128 chunks + 1 root, <=129 MiB object
bytes. Максимум две передачи одних bytes на key (первичная + один retry,
включая скрытые SDK retries) в общем deadline; затем explicit failure.
При игнорируемом CAS это максимум две версии/key от данной invocation,
<=258 MiB записанных bytes, без учёта provider overhead. Lost-response GET
снижает дубли, но не делает check-before-PUT защитой от гонок; корректность
обеспечивают hashes и DB PK. Параллельные attempts умножают объём.
После рестарта счетчик SDK retries не доказывает lifetime bound: повторные
ручные invocations могут накапливать новые orphan attempts/версии без верхнего
глобального предела. Нет scheduler или бесконечного retry loop; root задаёт
конечный capture batch и контролирует storage growth. При превышении
операционного бюджета прекращают новые captures, а не удаляют winner.
Durable глобальная квота/GC не добавляются в B15; lifecycle discrepancy остаётся
открытым эксплуатационным риском, а bounded invocation — не его исправлением.

## 5. Бюджет и работа с памятью

Пределы B11 остаются: 20k groups, 50k source keys, 400k revisions,
200k statuses, 50k receipts, 128 sources/group, 128 revisions/source,
512 statuses/group; target output32 MiB, PHP allocation48 MiB/peak96 MiB,
mapping+compute5s и SQL statement timeout5s. Training limit type допускает
широкую конфигурацию — capture не использует это как разрешение расширения.

Новый **предлагаемый** artifact budget для проверки перед GO: query page200 rows,
chunk до1 MiB uncompressed, total capture до128 MiB/128 chunks плюс root
до1 MiB, локальный spool до130 MiB, capture wall deadline30s. Limits только
уменьшаются из request/DI, не увеличиваются. Эти числа не измеренный результат;
root принимает их после локального resource fixture, при необходимости
сужает capture scope. Total-byte cap имеет приоритет перед row caps.

Не строить гигантский SQL `json_agg`/PHP graph source ledger. DBAL page
сериализуется и освобождается; один oversized row отклоняется до публикации.
Новый artifact adapter пишет **один bounded plain JSON chunk** string, без
gzip; raw adapter не меняется. Установленный SDK реально предоставляет
`GetObjectOutput::getContentLength(): ?int` и
`getBody(): AsyncAws\Core\Stream\ResultStream`, у которого
`getChunks(): iterable<string>` (`api/vendor/async-aws/core/src/Stream/ResultStream.php`).
Reader проверяет ContentLength, затем независимо считает накопленные stream
bytes и прекращает чтение на cap, до `json_decode`. Не использовать
`getContentAsString()` без ограничения, не принимать неожиданное gzip encoding.
Plain JSON устраняет decompression bomb; oversized response, ложный/отсутствующий
ContentLength и transport content encoding покрыть реальным adapter test.
Учесть JSON decode graph + SDK fetch buffer + model и измерить RSS/peak.
Размер SDK chunk также проверить в resource test: iterable API сам по себе
не обещает маленький chunk. Root<=1MiB, отдельный evidence chunk<=1MiB;
decoder depth/list counts и все fields ограничены до построения большого graph.

## 6. Truth и replay

`CaptureNetForecastTruthAction(companyId, accountId, inputArtifactId,
truthRequestId)` сначала проверяет input seal, затем в **новом собственном**
read-only RR получает только последующую evidence нужных target components,
фиксирует truthReadAt/epoch/visible revisions/receipts и публикует отдельный
immutable truth root с обязательным input ID/hash. Input никогда не дописывается.

Компонент идентифицируется company/account/order/SKU/source row + part kind
и сохранённым origin/quantity; одинаковые source IDs в другом tenant не совпадают.
Source corrections, связь на другой order/SKU, ambiguous multi-origin allocation,
неизвестный onset, quantity decrease и неточность происхождения дают explicit
pending/censored/ineligible reason, а не искусственную аллокацию или clipping.

| Состояние в input T | Правило target и готовности |
|---|---|
| D(T), origin известен, tail открыт | Только **новые** accepted ClientReturn increments remaining units после T и строго до origin+60d; knownR(T) не вычитать ещё раз. Ждать origin+67d и operational coverage. |
| D(T), срок origin+67d уже прошёл | Сохранённый D(T) — rolling target base. Известные на T поздние R уже в нём; будущие события после H в target не входят. Проверить исходный coverage, а не переписать D из текущей таблицы. |
| Open на T, delivered позже в d | Actual observed d с previous-state proof; target готов не раньше d+67d и необходимых receipts. T+67 не критерий. |
| T1/T2/P без доставки | Нулевой вклад после доказанного terminal observation+7d, непротиворечивой истории и coverage. |
| Unknown/open, нет terminal/закрытого tail | Pending/censored; timeout/p95 не создаёт ноль. |

Пример ADR: open(T) → delivered(T+20) → return(T+75) включён (возраст55);
truth не раньше T+87. Возврат ровно origin+60d исключён из horizon.
Same-second success/failure ambiguous; UUID/time не создают причинный порядок.
Late commit с captureTime<T **не входит в input**, но появляется в позднем truth
как новое видимое evidence; он не должен задним числом менять D(T)/обучение.
Если порядок/возраст этой revision относительно component origin нельзя
доказать, target не scoreable; timestamp alone не снимает ambiguity.

Повторные truth observations создают новые artifact IDs; старый pending truth
не мутируется. Первая доказанно ready версия по зафиксированной политике
становится выбранным label; B16 фиксирует **точные truth IDs/hashes** в dataset,
не `latest`. После поздней correction нельзя молча переписать уже оценённый
label: новая версия/diagnostic invalidation и явный пересчёт dataset.
Aggregate ready только при готовности всех составляющих. Pending/null/ineligible
учитываются долями отдельно и не попадают в scored holdout.

Retention money truth использует **price/currency T** и те же scope rounding
правила; later price correction — отдельная диагностика. Replay восстанавливает
targets + aggregates/coefficients из manifest и вызывает существующую чистую
арифметику; current source DB, новые receipts, mutable plan, latestBody, clock
и marketplace API для replay запрещены. Replay prediction и audit training
membership — две проверки; сохранённых агрегатов без evidence для второй мало.

## 7. Календарная готовность: даты условные

Переданный root факт: epoch `01a18233-77aa-78ea-bdce-9d5b273a286f`,
`accepted_state_v1`, start `2026-10-28T05:54:45Z`, end=null; последний переданный
проверенный B11 prod `675-93a9377`, проверка 28 октября 22:09:47 UTC.
В design-only эти production факты самостоятельно не проверялись.

- 60+7 полных суток от epoch start = **2027-01-03T05:54:45Z**. Это только
  арифметическая нижняя граница H+L для delivery origin не раньше epoch,
  не доказательство существования первой пригодной delivery/receipt/sample.
  Return training interval заканчивается строго `< T−67d`, поэтому origin
  ровно epochStart входит лишь **после** этой границы, не в её точную секунду.
- Требуются prior known state, непрерывная daily returns coverage, deep
  completion в [origin+67d,T], пригодный p95/gross scope, min100 units/30 postings
  и risk-set30/10; наступление даты не гарантирует ни одного из этих условий.
- Calendar origins в двух неделях — отдельный B16 gate. Для business-week
  Europe/Moscow следующая неделя после начала epoch начинается
  2026-11-02 00:00 MSK = 2026-11-01T21:00Z; её первый возможный origin+67d =
  **2027-01-07T21:00Z**. Это иллюстративная нижняя граница дозревания origins
  двух таких недель, не дата готовности B16. Timezone week policy ADR явно
  не задаёт: до B16 зафиксировать MSK либо другое единое правило, не выбирать
  его после просмотра метрик.
- Первые numeric forward predictions зависят от фактического зрелого training.
  Если новый age0 D прогноз получен ровно 2027-01-03T05:54:45Z, его H+L
  наступает 2027-03-11T05:54:45Z. Это **пример**, не универсальный минимум:
  age59 targets созревают раньше, open после T — позже actual delivery.
- Capture nullable artifacts может начаться после B15 release сразу, но
  empty/null predictions не дают требуемые scoreable cases. Ни сегодняшний
  B02 capture, ни synthetic clock travel не закрывают B16.

Невосстановимые срезы: до epoch; через gap/rollback capture; legacy/backfill
без onset; прошлые RR без сохранённого visible set; прежние mutable quantities,
prices/plan goals без versions; ABA raw-only; пропущенный daily observation,
который поздний catch-up не исправляет. Narrow stable subset маркируется с
selection bias и не распространяется на общий numeric rollout.

Новые тесты расположить в `api/tests/Unit/Ingestion/NetForwardManifestCodecTest.php`,
`NetForwardTruthTest.php`, `api/tests/Integration/Ingestion/NetForwardArtifactTest.php`,
`NetForwardVisibilityTest.php`, `api/tests/Integration/SalesPlanning/CaptureSalesPlanForwardTest.php`;
Builder/support использовать существующий `NetTargetFixture` и настоящие writers.
Не создавать второй fixture framework. Meaningful обязательные случаи:

1. Две Connection: transaction A записала revision/receipt с captureTime<T,
   задержала COMMIT; B pin RR и capture; A commit; B завершает. Sealed B/replay
   не содержат A, следующий новый capture содержит. Повторить для status,
   training revision, current source price и success receipt; timestamp/counter
   фильтр отдельно демонстрирует, почему старый asOf недопустим.
2. Training/target/evidence/plan/baseline изменяются между SELECT: один RR
   сохраняет старый согласованный набор. Cross-company/account IDs, injected
   descriptor/key, чужой parent truth и совпадающие request IDs не читаются.
3. Future return/type/link/decrease/price/model-training changes не меняют
   sealed forecast; unknown initial/revision gap/ABA/failure receipt остаются
   явными причинами. Replay не вызывает source query (spy), hash tamper,
   truncated chunk, unknown version, missing manifest/receipt дают отказ.
4. Known R(T) не double subtract; mature D(T) остаётся D(T); open→d(T+20)
   →R(T+75), ready T+87; exact H boundary; terminal+L; mixed ready/pending
   aggregate; MSK midnight и полные UTC86400s; late same-second ambiguity.
5. Money: fixed T unit price, multi-currency/invalid currency/overflow,
   rational replay, HalfUp после SUM, null quantity не становится полным money.
6. Реальные две DB Connection: одновременные разные RR одного PK,
   commit/rollback первого INSERT, отдельный SELECT после ON CONFLICT,
   requestHash conflict; loser возвращает exact winner readAt с microseconds.
   Потерянные PUT/COMMIT ответы, crash на каждом S3→DB рубеже, DB outage,
   опубликованный missing chunk, 412 и 2xx с неверным body/hash. Adapter double
   **игнорирует IfNoneMatch**, оба attempts сохраняют разные hashed roots,
   PK выбирает один; distinct company/account/kind с тем же UUID независимы.
   Проверить отсутствие S3 IO под RR/RC, запрет publish под чужой transaction,
   lost stdout retry, неизменность existing DB row, отсутствие duplicate ref
   или silent source recapture при corruption. Не дергать production S3.
   Fresh schema rebuild и down/up; один natural PK покрывает scoped lookup
   (локальный EXPLAIN); reader не принимает произвольный path/global UUID.
7. Limit+1 sentinel для каждой растущей population; UTF-8 byte budget,
   oversized row/object/encoding, 128-chunk и общий deadline, actual memory/RSS.
   Null/excluded observations остаются в знаменателе missingness; никакой
   успешной усечённой выборки вместо unavailable. Orphan/transport retry caps
