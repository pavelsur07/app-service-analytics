# B06 — исход открытого заказа после передачи в доставку

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development.
> Один fresh implementer; root выполняет actual Codex CLI в двух отдельных сессиях,
> Git/CI/merge/production. Работать автономно в уже согласованном объёме.

**Goal:** получить точную вероятность будущего gross-выкупа уже переданной
в доставку открытой части заказа и применить её к известному количеству.
**Architecture:** Domain считает условную вероятность по полной исходной
выборке B02; Application выбирает целую пригодную строку SKU → свой кабинет.
Переиспользуются B05 GrossProbability, GrossDeliveryQuantity, OpenTargetEvidence
и проверка сохранения исходных количеств PreHandoverGrossSample.
**Tech Stack:** PHP 8.4/Symfony, существующий private brick/math0.19; без новых зависимостей.
**Spec:** docs/adr/0049-net-sales-forecast-observations-and-horizon.md §3–4;
canonical B06 в docs/plan/sales-planning-daily-implementation.md.

## Global Constraints

- `pGrossPost=G/(G+T2+P)`, G=D+R. T1 исключается только из условной
  post-handover population; full raw source по-прежнему обязан сохранять
  sampleQuantity=G+T1+T2+P. Не применять pre pGross к post targets.
- Пригодная именно условная population: минимум100 units G+T2+P и30
  dedicated postHandoverPostings, включительно. Большие full sample или T1
  не заменяют эту выборку. Отсутствие dedicated count → unavailable.
- Post postings — distinct исходные postings с post-handover количествами;
  возможен posting с частичными T1 и post исходами. Не выводить условный count
  из full postings или количества T1. Допустимые необходимые границы:
  0≤postPostings≤fullPostings и postPostings≤postQuantity; положительное
  postQuantity не согласуется с postPostings0. Нулевой postQuantity требует0.
  Необходима также fullPostings−postPostings≤T1 quantity; это не disjointness.
- Full source raw counts nonnegative и согласованы без int overflow;
  postQuantity вычислять как sampleQuantity−T1 после полной валидации.
  Post denominator0 даёт insufficient, не p0. Genuine G0 при пригодной
  условной выборке даёт эмпирическое0. Expected quantity exact, не float.
- CompanyId первым, accountId следующим; foreign scope отвергать до metadata
  или zero shortcut. Тот же настоящий непустой readonly RR snapshot и полный
  context fingerprint/readAt с microseconds; single_statement не RR.
- Только уже размещённые, подтверждённо известные открытые after_handover units.
  Unknown/incomplete/conflicting evidence не становится0. Wrong stage не
  проходит даже для target quantity0. Trusted zero → quantity0 без fake p0
  и без training, но с проверками scope и присутствующего context.
- Training source требует inputComplete, отсутствие unavailable/budget failure,
  доступный p95≥0, валидные diagnostics/counts. Не изобретать source maturity.
  Каждая попытка сохраняет целый original row и его diagnostics.
- Не менять B02 SQL/DTO/writers/schema, B03/B04/B05 поведение, Facade/API/UI,
  очереди, конфигурацию, зависимости или ADR. OpenTargetEvidence получает
  только additive AFTER_HANDOVER constant. Domain не зависит от Infrastructure.
- B07 добавляет будущий return factor, B08 интегрирует unknown/fallback,
  B09 даёт реальный target producer, B11 деньги, B12+ контракт/UI. Здесь
  target evidence остаётся trusted typed input, не доказанным SQL producer.
  Числовой rollout и качество на реальных данных не объявляются пройденными.

- `PreHandoverGrossSample(int sampleQuantity, int samplePostings,
  int grossQuantity, int t1Quantity, int t2Quantity, int pQuantity)` — final
  readonly Domain VO. Конструктор проверяет full counts вычитанием из остатка,
  не суммированием: все количества неотрицательны, полный исход сохранён,
  `0 <= samplePostings <= sampleQuantity`, непустая sample требует postings.
  Его `probability()` имеет pre denominator и **не вызывается** из B06.
- `GrossProbability(int numerator, int denominator)` хранит точные несокращённые
  int-компоненты, проверяет denominator>0 и 0<=numerator<=denominator.
  `GrossDeliveryQuantity::fromProbability(int, GrossProbability)` выполняет
  умножение через private BigRational; наружу numerator/denominator — строки.
  `zero()` даёт quantity0 без выдуманной probability.
- `GrossTrainingAggregateRow` — readonly B02 DTO: nullable SKU, inputComplete,
  unavailableReason, nullable sampleQuantity/samplePostings/grossQuantity/
  t1Quantity/t2Quantity/pQuantity/**postHandoverPostings**/p95Seconds,
  int excludedGroups/excludedDays, nullable budgetFailure. DTO не валидирует
  raw counts и не вычисляет вероятность; все нужные проверки делает B06 adapter.
  Source SQL, DTO, schema, writer и receipt maturity остаются без изменения.
- `NetTrainingBatch(companyId, accountId, readAt, ?context, gross, returns,
  ?unavailableReason)` содержит list полных строк SKU и account (SKU=null).
  `NetTrainingContext::assertScope()` бросает при foreign company/account;
  `fingerprint()` включает readAt с microseconds, весь epoch/cutoverRelease,
  snapshot и version/coverage policy. RR доказательство здесь trusted typed
  context B02, а не верификация произвольной строки snapshot запросом в БД.
- `OpenTargetEvidence(context, orderNumber, marketplaceSku, stage,
  ?eligibleOpenQuantity, inputComplete, ?unavailableReason)` уже валидирует

### Точные новые интерфейсы и readiness

`final readonly PostHandoverGrossSample` в Domain:

```php
public function __construct(
    public PreHandoverGrossSample $source,
    public int $postHandoverPostings,
);
public function probability(): ?GrossProbability;
```

Свойство `public int $postHandoverQuantity` вычисляется один раз как
`source.sampleQuantity - source.t1Quantity` после полной constructor-validation
исходного VO. Дополнительная проверка dedicated count:
`0 <= postHandoverPostings <= source.samplePostings`,
`postHandoverPostings <= postHandoverQuantity`,
положительная post quantity требует count>0; нулевой quantity требует count0.
Нарушение — InvalidArgumentException (`Invalid post-handover gross sample.`).
Дополнительно `source.samplePostings - postHandoverPostings <= source.t1Quantity`:
каждый full posting вне post имеет минимум1 T1 (B02 canonical raw.quantity>0).
Это необходимая граница, а не равенство или предположение непересечения:
posting может иметь одновременно T1 и post quantities. Nullable source count
обрабатывается Application до конструктора. Если post quantity<100 или dedicated
count<30 — null; иначе `new GrossProbability(source.grossQuantity,
postHandoverQuantity)`. Empty0/0 — insufficient; настоящий G0 при достаточной
условной population — probability0. Все операции int bounded, без суммы raw counts.

`final readonly ScopedPostHandoverGrossRate` повторяет публичную форму B05:
companyId, accountId, DateTimeImmutable readAt, ?NetTrainingContext context,
?string marketplaceSku, ?GrossTrainingAggregateRow source,
?GrossProbability probability, ?string unavailableReason. Source сохраняется
тем же объектом целиком вместе со всеми diagnostics, включая T1/full sample
и dedicated post count. DTO не выполняет fallback или source reads.

`final readonly BuildPostHandoverGrossRateAction`:

```php
public function build(string $companyId, string $accountId,
    NetTrainingBatch $batch, ?string $marketplaceSku = null
): ScopedPostHandoverGrossRate;
```

Порядок проверок и причин фиксируется до PHP:

1. Batch company/account и присутствующий context scope; foreign — исключение,
   до unavailable metadata. Затем отсутствующий context →
   `training_context_missing`; null/пустой/whitespace/`single_statement`
   snapshot → `training_snapshot_missing`; readAt `U.u` отличается от context →
   `training_context_mismatch`. Batch unavailableReason передаётся без изменения.
2. Ровно одна строка с точным SKU (в том числе null для account), иначе
   `gross_training_row_missing` / `gross_training_row_ambiguous`, source=null.
   Из других SKU ничего не заимствуется.
3. Выбранная source сохраняется при любом отказе: budgetFailure →
   `input_budget_exceeded`; !inputComplete или unavailableReason → исходная
   причина либо `gross_training_input_incomplete`; p95=null →
   `maturity_unavailable`; p95<0/excludedGroups<0/excludedDays<0 →
   `invalid_gross_training_counts`. p95=0 разрешён; maturity заново не выводится.
4. Любое отсутствующее raw quantity/full postings/**dedicated post postings** →
   `gross_training_counts_missing`. Полная валидация через
   PreHandoverGrossSample, затем PostHandoverGrossSample; InvalidArgumentException
   → `invalid_gross_training_counts`. Не ослаблять full counts для post оценки.
5. Nullable conditional probability → `insufficient_sample`, иначе reason=null.
   Adapter строит ровно одну оценку; fallback только в assess.

`final readonly PostHandoverGrossAssessment` аналогичен B05: private constructor,
public ?GrossDeliveryQuantity quantity, ?GrossProbability probability,
?string basis, list<ScopedPostHandoverGrossRate> attempts, ?string unavailableReason.
Фабрики:

```php
public static function available(GrossDeliveryQuantity $quantity,
    ?GrossProbability $probability, string $basis, array $attempts): self;
public static function unavailable(string $reason, array $attempts = []): self;
```

available разрешает только `no_eligible_open`, `sku`, `account`;
probability=null тогда и только тогда, когда basis=no_eligible_open, где eligible
quantity обязано0. Иначе InvalidArgumentException (`Invalid post-handover gross
basis.`). unavailable требует trim(reason) непустой (`Unavailable post-handover
gross needs a reason.`), обнуляет quantity/probability/basis и хранит attempts.

`final readonly AssessPostHandoverGrossAction` получает constructor-injection
BuildPostHandoverGrossRateAction и имеет:

```php
public function assess(string $companyId, string $accountId,
    OpenTargetEvidence $target, NetTrainingBatch $batch
): PostHandoverGrossAssessment;
```

Порядок: target scope → batch scope → присутствующий batch context scope
(исключения прежде metadata/zero); target snapshot readiness
(`target_snapshot_missing`); batch.readAt `U.u` против target.context.readAt
и при наличии batch.context его полный fingerprint против target.context
(`training_context_mismatch`); target unavailableReason/!inputComplete
(исходная причина/`target_input_incomplete`); stage строго AFTER_HANDOVER
(`unsupported_target_stage`); quantity=null (`unknown_eligible_open_quantity`).
Только затем trusted quantity0 даёт available(zero(), null, no_eligible_open, []).
Для такого нуля training/context у batch не обязателен; **присутствующий**
контекст всегда проверяется. Для положительного target отсутствующий context →
`training_context_missing`. Далее попытки SKU → свой account(null); выбирается
первая целая probability и ровно её raw source/diagnostics; количество через
GrossDeliveryQuantity::fromProbability. Обе неуспешны →
`gross_probability_unavailable` с обеими полными attempts. Return factor,
retention, projectedBuyout и интеграция B09 в Task1 отсутствуют.
