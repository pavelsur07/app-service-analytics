# A42 — календарь по версии, аудит и наследование

## План до кода

1. SetSalesPlanCalendarAction принимает company/plan/expected version,
   trusted actor и полный набор до500 записей. Existing id допустим только
   у записи этой версии; для новой id создаётся приложением. Дубли id/
   одинаковых событий отвергаются. Пересечение разных видов допустимо.
2. Проверить draft/версию и SKU из собственных строк плана одним SQL
   проверочным запросом. Не читать соседние таблицы/каталог и не делать N+1.
3. Общая ORM transaction: сохраняемый counter шапки меняется даже при
   одинаковом timestamp и flush-ится первым, затем ограниченные Entity
   календаря обновляются/создаются/удаляются. Внешний flush атомарно пишет
   календарь и точные before/after audit каждого изменённого события.
   Полный snapshot save повышает header version; неизменённые события
   сохраняют id и не порождают фиктивных изменений аудита.
4. Approved календарь read-only. Copy revision переносит календарь через
   ORM с новыми UUID внутри существующей source-first транзакции копии;
   исходный календарь остаётся неизменным. ORM-календарь не подпадает под
   DBAL-исключение для sales_plan_line. Отмена/отказ сохраняют историю.
5. При удалении SKU из draft убрать и его календарные записи с аудитом
   в той же транзакции/версии, сохранив plan-wide события. Утверждённая
   исходная версия новой линии остаётся неизменной.
6. Integration через реальные команды: сохранение/частичное изменение/id,
   exact audit/actor; tenant/stale/approved/unknown SKU/501/invalid id;
   rollback audit и календаря при optimistic race; copy и remove SKU.

Файлы: Application calendar command/outcomes/results; Domain header counter;
calendar ORM repo; существующие revision-copy/remove-SKU с нужными тестами.
Schema уже A41, API и generated файлы — A43. Внешних действий нет.
