# A18 — текущий прогноз выкупа без нового смысла показателя

## План до кода

1. Прочитать ADR-019/029/031/032/033 и текущий BuyoutForecastQuery.
   Переиспользовать SQL-фрагменты maturity/training days, handover curve,
   unit forecast, unestimated и правила допустимости агрегата.
2. Включить в источник SalesCohortMetricsQuery training_rows по зрелым
   дням 30-дневного окна своего кабинета. SKU с >=30 обучающих штук имеет
   приоритет; иначе fallback того же кабинета; без выборки ставка null.
   Набор видимых SKU не сужает обучение и не делает N+1.
3. Стадии до/после handover используют соответствующую ставку и поправку
   возраста доставки. Подтверждённые T1 исключаются из экранного факта,
   но сохраняются в обучении будущих исходов.
4. Добавить currentProjectedBuyoutQuantity/RateBps и unestimatedQuantity/
   RateBps в дневную Row. При >10% без оценки прогноз null; <=10% действует
   текущая поправка ADR-031. Количество прогноза включает известные D,
   не прибавлять наблюдаемый факт второй раз. Это ещё не нетто-прогноз.
5. Сохранить точные SQL numeric-компоненты ожиданий строками для будущих
   сумм/группировок A23/A25: не суммировать округлённые дневные прогнозы.
   Финальный legacy currentProjected quantity округляется тем же helper,
   денежная оценка D остаётся Money без float и смены валюты.
6. TDD интеграционные контрпримеры: 24D+6T1 обучают pre=0.8/post=1;
   SKU override и account fallback; отсутствие выборки; terminal unknown
   ровно10% и выше; толькоT1/R даёт0quantity/nullrate; foreign training
   не даёт оценку. Сравнить с неизменённым BuyoutDailyQuery на подходящих
   fixtures. Сохранить regression денег/частичных исходов/изоляции.
7. Запустить integration и backend-гейты; оба независимых Codex CLI прохода.

Файлы: SalesCohortMetricsQuery/Row, SalesCohortForecastQueryTest и этот план.
Existing Buyout-отчёты/пороги/публичные API/схема не меняются. Поле будущего
нетто-прогноза с причиной его отсутствия — отдельная A19.
