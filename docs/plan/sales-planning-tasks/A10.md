4. Concurrency barrier без production hooks/decorators: winner worker начинает внешнюю DB transaction, вызывает настоящую Application action с её обычным EM/Identity audit и repository nesting. После реальных header/claims/audit flush печатает HELD result+backendPID, удерживает внешнюю transaction до ограниченного stdin COMMIT. Второй process печатает свой distinct backendPID до вызова настоящего action, читает precommit состояние и блокируется на реальном UPDATE/unique claim. Родитель наблюдает PostgreSQL wait_event_type=Lock и pg_blocking_pids(second) содержит winnerPID, только после доказательства overlap освобождает winner COMMIT. Затем читает typed outcome loser и actual committed DB state.
5. Время ограничено: process timeout и lock/statement timeouts, bounded barrier polling со сбросом pg_stat snapshot и короткими паузами; отсутствие Lock — failure, не flaky blind sleep. При premature worker exit выводить только bounded synthetic diagnostics. try/finally всегда terminate/wait children и cleanup собственных fixture. Не оставлять открытые transaction/locks/worker handles.
6. Сценарий dayedit vs approve одного draft в обоих порядках: winner фактически сохраняет edit или approval под outer transaction; loser с той же expected version блокируется и получает VersionConflict. После edit winner повторное approval по свежей версии подтверждает, что claims покрывают именно committed числа; после approval winner строки неизменны, поздняя правка не может изменить approved content. Проверить versions/status/day values/audit counts/claims и no leaked loser audit.
7. Сценарий два разных draft одной компании/account/SKU/dates: winner approved держит claims; loser доходит до конкурирующего INSERT unique key, ожидает lock, после winner commit получает DayConflict, остаётся draft. Winner complete claims/audit, loser claims0/approval audit0/header rollback. Дополнительно такой же SKU/day другой компании получает independent approval и не раскрывает/разделяет claims.
8. Сценарий copy vs cancel одного approved source в обоих winning orders: source first UPDATE реально блокирует loser. Copy winner создаёт committed draft и повышает source version; loser cancel staleVersion получает VersionConflict; после fresh cancellation draft discarded/claims0. Cancel winner → loser copy VersionConflict; источник cancelled, draft отсутствует, revision audit0 и claims0. Повтор revision fresh-version до cancel возвращает existing draft; после cancel новая revision запрещена. No open draft после любого успешного cancel.

Outcome guard повторов/tenant limits сохраним; существующие deterministic A07–A09 тесты продолжают проверять подробные no-write boundaries.
