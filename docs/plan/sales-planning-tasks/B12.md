# B12. Нетто-прогноз в Facade и performance API — план реализации

> Завершено: source `bdcf364`, squash master `7612f88`, PR #283.

**Цель:** провести результат B11 через существующий Ingestion Facade в
performance API: количество, деньги, методика и честное качество, сохранив
закрытым численный production rollout до B15/B16/B17.

**Архитектура:** default-closed путь сохраняет прежний gross read и не запускает
новый net compute. В разрешённом internal/test пути — один bounded net batch
на страницу SKU внутри того же read-only RR, затем точная композиция дневных
значений в периоды и накопительные диапазоны внутри Ingestion. SalesPlanning получает только Facade DTO; его калькулятор
не пересчитывает нетто-модель или деньги.

**Стек:** PHP 8.4, Symfony 7.4, DBAL, существующие Money/Brick Math, PHPUnit,
Nelmio OpenAPI, генерируемая TypeScript-схема.

**Spec:** [B12 общего плана](../sales-planning-daily-implementation.md),
[ADR-049](../../adr/0049-net-sales-forecast-observations-and-horizon.md),
[ADR-004](../../adr/0004-money.md), [зависимость B11](B11.md),

## Global Constraints

- Изменение аддитивное; существующие observed facts, gross projectedBuyout,
  coverage, baseline, ручная цель, cursor и calendar bounds сохраняются.
  `expectedGoalQuantity`, attainment и forecast speed принадлежат B14.
- `companyId` первым параметром, account только из проверенной шапки плана.
  Не принимать company/account/model/readAt/epoch из клиентского query.
- Не более 50 SKU × 184 дня с учётом accumulationFrom. Day HTTP сохраняет
  максимум 31 видимый день. 20 000 groups, 50 000 source keys, 5 s compute,
  96 MiB peak, 48 MiB allocation, 32 MiB output и precision 16 384 digits
  не повышать. Mapping, деньги и новая проекция делят один compute budget.
- `expectedNet = D − futureReturns + retainedOpen`; уже известный R не вычитать
  повторно; текущий факт и будущие неразмещённые заказы не прибавлять.
- Quantity: exact SUM → decimal string с **3 знаками, HALF_UP** только на
  Facade/transport boundary. Money: exact scope SUM → один HALF_UP до minor.
  Не складывать округлённые дни и не умножать decimal3 quantity на цену.
- Unavailable не равен нулю. Money и quantity имеют отдельные причины.
  Currency обязательна; FX/подстановка валюты плана запрещены.
- Новых таблиц, миграций, зависимостей, очередей, buckets, manifests, SQL-цен,
  публичных raw/source traces и новых межмодульных связей нет.
- Использовать текущие разрешения `api/deptrac.php`: IngestionFacade уже может
  обращаться к IngestionApplication/Domain/Infrastructure; SalesPlanningApplication
  — только к IngestionFacade. Не добавлять imports внутренних NetForecast DTO
  в SalesPlanning и не расширять Deptrac.
- Claude пропущен по явному правилу владельца для этой фичи. Реальный итоговый
  код проверяет root двумя отдельными Codex CLI сессиями, с разбором замечаний.
  Этот design-only этап проверок/ревью кода не выполнял.

## Review Focus

1. Скрытый день до visibleFrom повреждён: cumulative null, доступный period
   сохраняется; частичная сумма не становится полным итогом (шаг 2).
2. Половины minor на разных днях и дробные количества: week/month/cumulative
   округляют свою точную сумму, а не отображённые дочерние значения (шаг 2).
3. Два tenant/account с одинаковыми SKU, смена суток и конкурентная revision:
   один scope/readAt/RR для source+training+gross ответа (шаг 3).
4. Хорошие synthetic inputs при configured capture epoch: production JSON
   всё ещё null/validation_pending; техническая готовность не quality pass (шаг 4).
5. Недоступные деньги, overflow дочернего Money и большой rational carry:
   сохранить quantity и точный родительский результат, не обойти budgets (шаги 1–2).

## Проверенные текущие интерфейсы

- `IngestionFacade::salesCohortMetrics(string $companyId, string $accountId,
  SalesCohortRequest $request): SalesCohortBatch` сейчас выполняет maturity+series
  (два SQL), использует Clock и не открывает свою RR-транзакцию.
- `SalesCohortRequest` содержит SKU, from/to/accumulationFrom, groupBy
  day/week/month/period и valuationCurrency. SQL формирует clipped buckets;
  cumulative всегда начинается с accumulationFrom, не с первого видимого дня.
- `ReadSalesPlanPerformanceAction::__invoke(companyId, planId, request)` уже
  читает шапку, исходную baseline и SKU page в `SalesPlanPerformanceSnapshot`.
  Он сопоставляет buckets по `bucketFrom|bucketTo`; текущий/будущий MSK день
  делает coverage partial и подавляет cohort. Это поведение сохраняется.
- `ReadNetForecastAction::__invoke(companyId, accountId, NetTargetRequest)`
  возвращает внутренний `NetForecastBatch`; training и target используют один
  `NetTrainingContext` и фактический snapshotId. Empty SKU не читает источники.
- В текущих Batch/Sku/Day/Group/Part доступны exact `NetForecastQuantities`.
  Контракт B11 добавляет `?Money expectedNetRevenue`, money reason и day-only
  exact carry по выбранному root решению; root подтвердил итоговый B11 перед
  task 1 GO. Private day carry и существующие guards используются без новых caps.
- Публичные `SalesCohortComponents → SalesPlanPerformanceCohort →
  PerformanceCohortResponse` уже имеют nullable expectedNetSalesQuantity и
  строковый placeholder netForecastUnavailableReason. Денег/quality там нет.
- `NetTrainingContext::MODEL_VERSION = net_training_observed_v1`,
  `ObservedReturnCurve::MODEL_VERSION = observed_retention_h60_v1`, HORIZON=60.
  Это разные версии, не заменять одну другой.

## Обязательная reconciliation B11 до GO

Готовых Money day/SKU/batch недостаточно для произвольного clipped week/month
и cumulative. Сложить их нельзя. Решение ниже **выбрано root до реализации B11** и уже внесено в его план/brief.
Проверка окончательного реализованного B11 остаётся предусловием B12 GO.

**Выбранный root вариант:** сохранить `NetForecastRevenue` только на минимальном
внутреннем `NetForecastDay`: private readonly поле `exactRevenue` и accessor
`exactRevenue(): NetForecastRevenue`. Part/group/SKU/batch продолжают отдавать
готовый Money без дополнительных retained accumulator. Brick остаётся private
в VO. B12 затем одним хронологическим проходом складывает дни в два текущих
аккумулятора на SKU: period и cumulative. Это не повторная модель и не второй SQL.

B11 должен включить новый carry в свой фактический memory guard и явный учёт
размера. `get_object_vars()` существующего charge не видит private рационал:
нужен `NetForecastRevenue::storageBytes(): int` с консервативной оценкой
по длинам exact числителя/знаменателя/валюты/причины без создания JSON и без
публичного Brick. Charge day явно учитывает этот размер; 16k precision остаётся
в VO. Публикуемая структура carry не сериализует. В существующий 32 MiB budget
консервативно включить и retained carry, и новую series; не исключать carry из
всех лимитов под предлогом отсутствия в JSON. Проверять реальный peak/allocation.
Overflow опубликованного day Money не уничтожает exact carry: родительская
signed сумма может вернуться в native range. Source/currency failure остаётся sticky.

**Альтернатива:** передавать requested bucket/range specification в исходный
aggregation pass и сразу сохранять готовые scope Money без retained day carry.
Она экономит retained память, но связывает B11 с календарной проекцией B12 и
меняет контракт обхода сильнее. Вернуться к ней только отдельным решением root, если измерение покажет, что carry не помещается в действующие лимиты. Не делать
автоматический fallback, не добавлять второй набор SQL или второй бюджет.

## Предлагаемый публичный контракт и rollout

`cohort.expectedNetSalesQuantity: ?string` и
`cohort.expectedNetRevenue: ?PerformanceNetMoneyResponse` — полный итог
соответствующего period/cumulative, не дополнительный остаток к observed.
`netForecastUnavailableReason: ?string` относится к quantity,
`netForecastMoneyUnavailableReason: ?string` — к деньгам.
`netForecastQuality` содержит `sourceUnavailableReason: ?string`,
`sourceMoneyUnavailableReason: ?string`, `trainingScopes: list<string>`
(только реально выбранные sku/account), `componentReasons: list<string>`
(уникальные, стабильный порядок), `validationStatus: string`, `assessmentStatus: string`
(`not_assessed` либо `assessed`).
Не суммировать samplePostings разных частей: training может быть общий.
Нет source-row IDs, raw keys, credentials, snapshotId или trace arrays.

Top-level `netForecast` содержит methodology=`observed_retention_h60_v1`,
trainingVersion=`net_training_observed_v1`, horizonDays=60,
readAt nullable, epochId nullable, captureVersion nullable,
coveragePolicy=`daily_complete_receipts_v1`, validationStatus=`validation_pending`,
scope=`placed_order_cohorts` (область методики, не утверждение о выполненном чтении),
assessmentStatus=`not_assessed` до фактического net read. При будущей разрешённой публикации
validationStatus=`release_approved`; это статус trusted deployment допуска. Значения версий брать из существующих
констант; scope — описание текущего чтения, не историческая воспроизводимость.
При отсутствии context не выдумывать epoch/readAt; использовать реальный batch.
Это **новые предложенные поля**, не утверждение об их наличии в нынешнем API.

### Два пути чтения и честные metadata

В коде сейчас нет numeric flag, только `NET_FORECAST_CAPTURE_EPOCHS_JSON` и
null placeholders. Root в `.superpowers/sdd/B12/progress.md` одобрил новый
узкий default-closed gate, но запретил его включение в B12 и тяжёлый net compute
в закрытой production ветке. Gate применяется **к новой работе и публикации**,
а не к проверкам доступа/плана и не к существующему gross чтению.

Фактическая граница доверия public performance:

1. `CompanyAccessSubscriber` на `kernel.controller` проверяет компанию и
   пользователя; не разрешённый запрос заменяется 403-controller до action.
2. Controller валидирует allowlist query/date/group/limit/cursor.
3. `ReadSalesPlanPerformanceAction` под прежним `SalesPlanPerformanceSnapshot`
   выполняет `SalesPlansQuery::withPlanId(companyId, planId)` с SQL
   `p.company_id=:companyId`, возвращая 404 для foreign plan. Проверяются
   closed status, metric, исходная baseline, диапазон и cursor binding.
4. `SalesPlanBaselineQuery` соединяет baseline по company **и** account/lineage.
   В Facade передаются account из проверенной шапки и SKU проверенной страницы,
   а не параметры клиента. Только после этих шагов вызывается Facade/gate.

Сам `salesCohortMetrics` — внутренний scoped read, **не авторизация membership**
и не проверка существования account в Identity. Его нынешние maturity, metrics,
coverage SQL явно фильтруют company+account. Closed branch оставляет эти чтения
и параметры; не возвращает фиктивный успешный HTTP ответ до action guards.
Не добавлять account-existence SQL и не выдавать отсутствующую пару за проверенную
Identity связь. Прямой внутренний вызов с foreign account остаётся scoped-empty/
missing по нынешнему контракту, без чужих данных. Request validation сохраняется.

**Closed nonempty:** `allowsModel()` false → один нынешний `Clock::now()` для
legacy calculatedAt → два прежних SQL maturity+series → нынешний mapping плюс
pending net DTO. Не вызывать ReadNetForecastAction, ReadNetTrainingAction,
NetTargetQuery, projector или CaptureEpochs::at; не добавлять NetTrainingSnapshot
и его control SQL к этому пути. В public GET прежний outer RR остаётся на месте;
standalone gross Facade сохраняет свой существующий транзакционный контракт.

`SalesCohortNetMetadata::pending(): self` и
`SalesCohortNetQuality::pending(): self` создают только следующие значения:

- quantity/revenue = null, обе публичные причины = `validation_pending`;
- validationStatus=`validation_pending`, assessmentStatus=`not_assessed`;
- net readAt, epochId, captureVersion = null, sourceUnavailableReason и
  sourceMoneyUnavailableReason = null, trainingScopes/componentReasons = [];
- статические methodology/trainingVersion/H/coveragePolicy описывают методику,
  которую предполагается применять, но не факт обучения или покрытия.

Не копировать legacy calculatedAt в net readAt; не угадывать epoch по текущей
дате; отсутствие source reasons при not_assessed не означает source success.
Capture config может быть полным, пустым или ошибочным — closed branch его
не читает и не делает из него выводов. Gross `returnsCoverage=not_assessed`
сохраняется. При `cohort=null` не создавать искусственный cohort ради net:
сохраняются прежний coverage и top-level pending metadata.

**Empty SKU при любом gate:** прежний Clock один раз, [] SKU, ноль SQL;
не открывать новую snapshot, не читать epochs, не вызывать net action. Net
metadata pending/not_assessed/null, даже если test gate разрешён: оценки не было.

**Enabled nonempty (сейчас только изолированный internal/test путь):**
NetTrainingSnapshot оборачивает net+gross, переиспользует outer RR. Один net read
и один projector; legacy calculatedAt берётся из фактического netBatch.readAt,
а не из второго Clock. Если отказ не получил readAt, один fallback Clock только
для legacy; net readAt остаётся null. Actual context заполняет epoch/captureVersion
только при наличии context. assessmentStatus=`assessed` означает попытку чтения,
не качество модели; source failures/validation независимы. Missing epoch даёт
фактический source_history_unavailable, не предполагаемый отказ closed пути.

### Одобренная root конфигурация и условия будущего включения

- Pattern уже есть: `api/config/services.yaml` default parameter и explicit
  constructor argument через `%env(default:...:...)%` у CaptureEpochs.
- Новый параметр `net_forecast.published_model_default: ''`, необязательный env
  `NET_FORECAST_PUBLISHED_MODEL_VERSION`; `$publishedModelVersion` получает
  `%env(default:net_forecast.published_model_default:NET_FORECAST_PUBLISHED_MODEL_VERSION)%`.
  Это новое изменение B12, не существующий механизм и не секрет.
- `NetForecastPublication::__construct(string $publishedModelVersion = '')`;
  `allowsModel(string $modelVersion): bool` — только строгое совпадение непустой
  текущей model version. Empty/whitespace/другая version/`true`/`1`/опечатка закрыты.
- B12 не устанавливает prod env, не включает sample env и не создаёт клиентского
  query/admin switch. Тестовый exact-version fixture доказывает transport,
  не predictive accuracy и не readiness HTTP выпуска.
- Будущее включение требует **всех** предусловий: verified B15/B16 evidence,
  B17 checks/reviews, B18 authorized release и отдельно измеренный полный HTTP
  путь **менее 3 секунд** по patterns либо отдельно согласованная и прошедшая
  review совместимая async архитектура. Флаг не удовлетворяет ни одному из них.
- HTTP измерение охватывает auth/request, baseline+page, оба модуля, SQL,
  mapping/compute и serialization на согласованной representative нагрузке
  (1/50 SKU, max horizon, dense/large groups, cold/warm условия); root фиксирует
  окружение, профили и времена. Unit microbenchmark/один лёгкий запрос не заменяют
  этот prerequisite. При превышении или отсутствии evidence B18 заблокирован.
- Внутренний guard 5 s не означает HTTP SLA 5 s и не отменяет patterns >3 s.
  Очередь, waiver и изменения production здесь не вводятся; текущий B12 default
  не добавляет тяжёлый compute и потому не использует молчаливое исключение.
