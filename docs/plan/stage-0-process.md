# Stage 0 — процесс работы агента и внешнее ревью

## Цель

Зафиксировать, как агент ведёт задачу, когда останавливается, что и как
уходит на внешнее ревью и по какому правилу разрешаются расхождения.

Все три инструмента — Claude Code, Codex CLI, Kimi CLI — установлены
на одной машине. Ревью выполняется локальными вызовами, а не через сервис.

---

## Главная проблема, которую решает этот этап

Внешний ревьюер не видит наших правил. Он добросовестно предложит ровно то,
что мы отвергли: API Platform вместо контроллеров, `findAll()` для списка,
Redux для серверного состояния, Symfony Forms, глобальные фикстуры.

Это не его ошибка — это мейнстрим и большинство примеров в обучающих данных.
Но без контекста половина замечаний будет спором с уже принятыми решениями,
и агент начнёт их отрабатывать.

Поэтому **на ревью уходит не только диф**, а диф вместе с выдержкой правил
и релевантными ADR. И заранее задано правило, по которому замечание
принимается или отклоняется.

---

## Цикл работы над задачей

```
1. Разбор     — прочитать CLAUDE.md, релевантные ADR, patterns.md
2. План       — что меняем, какие файлы, какой критерий готовности
3. STOP?      — если сработало условие остановки, спросить и ждать
4. Реализация — код + тесты в одном изменении
5. Самопроверка — по чеклисту ниже
6. Внешнее ревью — если задача попадает под порог риска
7. Разбор замечаний — принять / отклонить с причиной
8. Повтор 4–7 до отсутствия принятых замечаний
9. Отчёт      — что сделано, что отклонено и почему, чем проверять
```

Пункты 4–8 повторяются, пока остаются принятые замечания. Задача
не закрывается с невыполненным принятым замечанием.

---

## Условия остановки

Агент прекращает работу и задаёт вопрос, если задача требует:

- изменения схемы БД на таблицах фактов — ключи, индексы, партиционирование;
- новой миграции любого рода;
- нового межмодульного взаимодействия или нового Facade;
- установки пакета — на бэкенде или на фронтенде;
- изменения конфигурации очереди, транспортов или маршрутизации сообщений;
- изменения контракта API, уже используемого фронтендом;
- обхода любого правила из `CLAUDE.md`;
- решения, противоречащего принятому ADR;
- расширения объёма задачи за пределы поставленного.

Отдельно: `merge` и принудительная перезапись истории — никогда автономно.

---

## Порог внешнего ревью

Два ревью на каждый коммит избыточны по времени и вниманию.
Порог задаётся риском изменения.

| Что затронуто | Ревью |
|---|---|
| Миграции и схема данных | оба |
| Денежная арифметика, аллокация, округления | оба |
| Аутентификация, секреты, изоляция арендаторов | оба |
| Ingestion: идентификация фактов, идемпотентность, пересчёт | оба |
| Контракт API | один |
| Новый сценарий или обработчик без перечисленного выше | один |
| Конфигурация, стили, тексты, документация | не требуется |

При сомнении — на ступень выше.

## Как устроен вызов

Три команды, детали — в Stage 3.

```
make review-prepare   собирает пакет: диф, изменённые файлы,
                      выдержку правил, релевантные ADR
make review-codex     прогоняет Codex CLI, ответ в var/review/codex.md
make review-kimi      прогоняет Kimi CLI,  ответ в var/review/kimi.md
make review           оба сразу
```

**Пакет для ревьюера содержит:**

1. Постановку задачи одним абзацем.
2. Диф изменений.
3. Раздел «обязательные правила» из `CLAUDE.md` целиком — он короткий.
4. Тексты ADR, относящихся к затронутой области.
5. Явную просьбу: проверять соответствие приложенным правилам, а не
   предлагать общепринятые альтернативы; при несогласии с самим правилом —
   сказать об этом отдельным пунктом, а не оформлять как дефект кода.

Пункт 5 — не вежливость. Без него ревьюер по умолчанию сравнивает код
с мейнстримом, а не с нашими решениями.

**Ревьюер не запускает тесты и не собирает проект.** Его задача — читать.
Прогон проверок — работа Makefile и конвейера.

## Разбор замечаний

| Замечание | Действие |
|---|---|
| Указывает на нарушение записанного правила | принять, исправить |
| Указывает на реальный дефект — ошибка, гонка, утечка, N+1 | принять, исправить |
| Предлагает альтернативу, отвергнутую в ADR | отклонить со ссылкой на ADR |
| Вкусовое: стиль, именование, «я бы сделал иначе» | отклонить с одной строкой причины |
| Указывает на пробел в самих правилах | не исправлять код молча — вынести отдельно |

**Расхождение между ревьюерами разрешается соответствием ADR, а не
большинством голосов.** Два инструмента — не голосование; их ценность
в том, что они ошибаются по-разному.

Последняя строка таблицы — самая полезная. Замечание, показывающее,
что правило отсутствует или сформулировано плохо, ценнее найденной опечатки:
оно чинит не одно изменение, а все будущие. Такие случаи собираются
и превращаются в правки `patterns.md` или новый ADR.

## Финальная самопроверка

Порядок фиксированный, первый пункт всегда первый.

```
1.  Каждый метод репозитория принимает companyId; поиска по одному id нет
2.  Ключ кэша на фронтенде содержит companyId
3.  Списки читаются через DBAL, сущности для отображения не гидрируются
4.  Ни один список не отдаётся без ограничения количества
5.  Деньги — Money с валютой; float в денежных вычислениях нет
6.  Обработчик очереди идемпотентен через уникальный индекс,
    конструкции «найти, и если нет — записать» нет
7.  Новое поле-ссылка получило индекс в той же миграции
8.  Запросов в цикле нет
9.  Тесты написаны в том же изменении; обязательное покрытие соблюдено
10. Границы модулей не нарушены — Deptrac зелёный
11. Отладочный вывод, закомментированный код, TODO без задачи — отсутствуют
12. Документация обновлена: structure.md при изменении структуры,
    patterns.md при изменении паттерна или зависимости
```

Красный пункт означает, что задача не закончена. Не «отметить и объяснить» —
исправить и пройти чеклист заново.

## Отчёт по задаче

Короткий, в теле изменения или отдельным файлом:

```
Задача:        одно предложение
Сделано:       список изменений по существу
Файлы:         затронутые пути
Ревью:         кто ревьюил, сколько замечаний принято
Отклонено:     замечание → причина
Проверка:      команды, которыми ревьюер может убедиться
Открыто:       что осталось и почему
```

---

## Не входит

- Многоступенчатый процесс с этапами, отчётами по этапам и гейтами
  выкладки. Он оправдан на большом проекте с владельцем, который неделями
  не смотрит в код; при работе за одной машиной это церемония.
- Внешнее ревью как блокирующая проверка в конвейере. Ответ языковой
  модели недетерминирован; ставить на нём гейт сборки нельзя.
  Ревью — часть работы до коммита, а не после.
- Автоматическое применение замечаний без разбора.

---

## Критерий готовности

1. Раздел о режиме работы, условиях остановки, пороге ревью и чеклисте
   добавлен в `CLAUDE.md`.
2. Шаблон пакета для ревьюера лежит в репозитории.
3. **Stage 1 выполнен по этому процессу, и процесс не пришлось нарушать.**

Третий пункт — основной. Процесс, написанный и не проверенный на реальной
задаче, обычно оказывается неудобным в первый же день и тихо перестаёт
соблюдаться.
