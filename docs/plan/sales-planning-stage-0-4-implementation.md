**Результат:** Planning воспроизводимо считает ожидаемые продажи по текущим заказам и плану, отдельно от существующего отчёта Ingestion. ## Настройки и формулы

Первую версию создать для кабинета при первом использовании с зафиксированными значениями: окно коэффициента 30 **полных завершённых** календарных дней, минимальная выборка 30 единиц, резерв 80%, границы зелёной/жёлтой зоны 95%/80%, окно скорости 14 дней, порог свежести 60 минут, ритм обновления 15 минут. Пользовательское изменение настроек добавляет новую версию с предыдущей версией, актором и временем в одной транзакции; старая версия остаётся неизменной. Проверять `0 <= yellow < green <= 100`, допустимые длины окон, резерв `0..100` и положительную выборку. Настройки читаются строго по компании и кабинету.

```text
resolved = T1 + D + T2 + P + R
ownRate = (D + R) / resolved, если resolved >= minSample
rate = ownRate либо versioned fallback
forecastOpen = openEligible × rate
expected = bought + forecastOpen
deviationUnits = expected − plan
fulfilment = expected / plan, только plan > 0
```

Для `resolved` использовать `planningResolutionTotals` по `FIRST_KNOWN_OUTCOME`; неизвестные исходы и текущий незавершённый день не входят. `R` остаётся выкупом; backfill без доказанной даты не входит в окно. Коэффициент хранить как точную целочисленную дробь либо decimal с явной точностью, промежуточные значения считать без `float`, округлять прогноз **после суммирования** только для отображения до одного знака. Точную величину сравнивать с порогами. Источник коэффициента (`sku` или `fallback`) и объём выборки всегда видны.

## Шаги и качество

1. Сначала зафиксировать контрольный пример: заказано 10, D=4, T1=2, открыто 4, при 75% факт 4, прогноз 3, ожидается 7, план 10, выполнение 70%, красный. Проверить также частичный исход, R после D, нулевой план и неизвестный исход.
2. Получить когорты по дате заказа и агрегат исходов по окну одной версии Ingestion; версия сменилась между страницами или пакетами — полный повтор без публикации смеси. Для каждой даты `bought` является фактом исходной когорты, открытое количество участвует только в прогнозе; `unknown` показывается отдельно.
3. Сигнал: зелёный `>=95%`, жёлтый `>=80%`, красный ниже. План отсутствует, явно равен нулю, дата ещё впереди, источник неполный/старый или есть неизвестные исходы — отдельное качество и причина **вместо** обычного цвета. Если собственного коэффициента мало, резервный разрешён только с пометкой. Возвращать количественное объяснение и версии плана/настроек/источника.
4. Передать готовую расчётную структуру задаче 0.5; пока нет атомарного сохранения, не выдавать смешанные данные через публичный `daily` API. Настройки можно выдавать собственным API уже в 0.4. Проверить SQL `EXPLAIN` на объёме чужого кабинета.

**Проверки:** unit для дроби, округления, порогов и перечисленных состояний; integration для смены версии источника и идентичных SKU разных кабинетов; functional для правок настроек, акторов и конфликтов. `make db-rebuild-check`, `make lint stan deptrac structure-check`, затронутые тесты, генерация API-типов, `make api-types-check`, `make audit`. Коду/схеме/расчёту нужны Claude и дополнительные Codex-проходы по риску.

**Готовность:** расчёт проверяется вручную по входным количествам; факт не задвоен, а качество и источник коэффициента видны.
