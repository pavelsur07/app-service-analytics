# Performance API: измерение отправок PHP и fetcher

09.11.2026. Вторая часть [постоянного observe](ozon-ads-continuous-execution.md),
подготовка N0/N2 из [плана допуска](ozon-advertising-observe-launch-plan.md).
Основа: ADR-026, ADR-043, ADR-052. Статус: реализация и локальная проверка;
пока не является поставленной защитой общей квоты.

## Результат

До отправки Performance HTTP процесс фиксирует одну попытку в собственной БД.
OAuth, успешный/ошибочный запрос, статус/скачивание отчёта и каждый явный повтор
проходят ту же границу. Рестарт и откат прикладной транзакции счётчик не уменьшают.
При отказе записи отправка запрещена. Нельзя включать подсчёт только успешных
ответов: Ozon мог получить запрос до потери ответа или завершения процесса.

Это измерение, без cap/долей и без нового интервала X. Работающий PHP/fetcher
не останавливается из-за отсутствия паспорта. Запись в БД становится необходимым
условием отправки; это дополнительная причина временной ошибки при отказе БД.
Контроллер Ads, его прежний локальный ledger и live-допуски не изменяются.
Исполнителя команд управления кампаниями по-прежнему нет.

## Граница и хранение

В каждой собственной БД таблица `performance_http_logical_count`:

| Поле | Смысл |
|---|---|
| bucket_start | Начало минуты, PostgreSQL timestamptz |
| operation | Один элемент закрытого списка операций |
| attempts | Положительный bigint; атомарное увеличение через upsert |

Первичный ключ `(bucket_start, operation)` суммирует реплики и подключения.
Нет company/account/client ID, ключей, URL, тел, денег или валют. Это операционный
агрегат всех подключений данного потребителя; он не позволяет распределить
расход по отдельным организациям. В будущем его можно использовать как более
строгую общую оценку доли, но нельзя объявлять точным расходом пилотной организации.
Сервисы не обращаются к чужим БД; публичного или межсервисного API не добавлено.

PHP использует отдельное DBAL-соединение к разрешённой собственной БД, с тем же
разрешённым именем базы (в тестах — test suffix), без прикладной транзакции
и её middleware. Короткая транзакция устанавливает statement_timeout 5 секунд
и lock_timeout 2 секунды, делает upsert и commit до HTTP. Соединение закрывается
штатным kernel reset. ORM Entity описывает только схему.

Fetcher пишет через свой pgxpool, отдельным autocommit от транзакции задачи;
действуют штатные statement_timeout 5 секунд и lock_timeout 3 секунды, context
вызова сохраняется. Пара подключения валидируется, но в агрегат не сохраняется.
Фиксированные имена операций не содержат идентификаторов кампаний/отчётов.

Автоматическое удаление накопленных счётчиков в этом изменении не запускается.
На время измерения сохраняется вся история; перед постоянной эксплуатацией
должны быть заданы срок и отдельная ограниченная очистка вне сохранённого окна
доказательств. Верхняя структурная скорость: 14400 строк/сутки у PHP (10 операций)
и 10080 у fetcher (7); реальная зависит от используемых операций. Запросы оценки
выполняются по диапазону времени, а не обходом всей растущей таблицы.

## Одна резервация и транспорт

Учтённая попытка — консервативная резервация перед отправкой, а не подтверждение
доставки/успеха у Ozon. Падение между commit и отправкой, DNS/TLS-сбой могут
увеличить счётчик без HTTP у площадки. Вычитать такие попытки нельзя.

Скрытые повторные HTTP ломают эту оценку. Поэтому:

- PHP Performance-клиент явно использует уже установленный Symfony
  NativeHttpClient, HTTP/1.1, Connection: close, max_redirects=0. Установленный
  CurlResponse способен автоматически повторить GET после сетевого сбоя даже
  при http_version=1.1; одной этой опции у cURL недостаточно. Другие клиенты PHP
  не изменяются. Прежние timeout/max_duration по 10 секунд сохраняются.
- Fetcher клонирует штатный http.Transport, использует новые HTTP/1-соединения,
  запрещает HTTP/2 и автоматические редиректы. Исходный клиент не меняется;
  opaque/typed-nil Transport отклоняется до отправки. Штатный timeout сохраняется.
- Повтор после 401, Messenger redelivery и повтор задачи снова резервируются.
  Ошибка записи не приводит к отправке с предупреждением.

Любой 3xx, в том числе на том же хосте, теперь возвращается как ошибка вместо
перехода. Это сознательное ограничение доступности: если Ozon изменит download
на редирект, история потребует отдельной доработки с резервированием каждого
проверенного перехода. Автоматический переход по неизвестному URL не включается.
Новые TCP/TLS-соединения увеличивают задержку и нагрузку; live SLA не заявляется.
Пробовать реальные ключи или дополнительно заказывать отчёт ради smoke не нужно.

## Границы доказательства и факты владельца

09.11 владелец подтвердил: Performance API **пилотной организации** использует
только Conwix. Это не утверждение об остальных компаниях и не спецификация
scope/reset общей квоты. Отдельного внешнего монитора пока нет; решение по новому
провайдеру в N4 ещё предстоит конкретизировать, внешний сервис здесь не создаётся.

Старая история логов не становится полным окном. Нужны фактическое начало новой
версии у всех PHP worker/scheduler/web/CLI и fetcher, отсутствие старых реплик
и ручных скриптов, подтверждение scope/reset, часы/дрейф и bootstrap. Протяжённость
между первым и последним ненулевым bucket сама по себе не доказывает непрерывность.
Счётчик не доказывает, что минуту без записей никто не выполнял запросов старым
образом. Минутные границы при будущей оценке окна округляются консервативно.

Генерации отчётов — отдельная квота с весом по кампаниям, слотами и неизвестным
исходом POST. Данный HTTP-агрегат не заменяет её ledger и не устанавливает причину
прошлых 429. Пустая таблица, новый ключ/версия и down/up не создают новый остаток.

## Миграции и выкладка

API: `Version20261109071000`; fetcher: `00005_performance_logical_count.sql`.
Обе миграции добавляют только новую техническую таблицу, старый код совместим.
Перед запуском нового кода применить обе явно по действующим production-гейтам,
после сборки образов и отказа автоматической выкладки на pending migration.
Не применять миграции кодом старого образа, где их ещё нет.

Для отката приложения таблицы оставляются: уменьшение версии не требует удаления
истории. Down существует для пустого локального roundtrip; удаление production
истории не входит в задачу и уничтожило бы накопленное доказательство покрытия.
После частичного отката весь период требует повторного аудита.
