# ТЗ: планирование продаж и подсорт на Ozon (v2.7)

Версия: 24.10.2026

## 1. Назначение и принципы

Документ описывает, **что** должна делать система планирования продаж и подсорта на Ozon. **Как** это реализовать (стек, хранилище, архитектура, интерфейс), решает команда разработки. Рекомендации по реализации собраны в разделе 11 и не обязательны.

В версии 2 работа перестроена так, чтобы польза появлялась с первой фазы: сначала отчёты для ручного планирования, затем простой сквозной подсорт с проверкой на прошлом сезоне, и только потом уточнения. **Версия 2.7 — итоговая: ТЗ готово к реализации.** Расчётное ядро дальше меняется только через тест, который не проходит (раздел 13). История версий — в разделе 14.

**Принципы этапов:**

- этап решает одну задачу и даёт проверяемый результат;
- этап опирается только на результаты этапов, от которых зависит (таблица зависимостей ниже);
- этап сдаётся и принимается отдельно;
- отчёты фазы 1 полезны сами по себе, без прогноза и рекомендаций;
- этапы фаз 2А и 2Б обязательны; этап фазы 3 делается, только если бэктест показал, что он заметно улучшает точность.

## 2. Что делает система

Каждый день система:

1. забирает данные из Ozon: заказы, выкупы, возвраты, остатки, воронку, поставки;
2. показывает отчёты: где товар скоро закончится, где его не было и сколько спроса потеряно, какой реальный выкуп, догоняем ли план и каким будет итог сезона;
3. прогнозирует остаток на каждом кластере Ozon на каждый день до конца сезона;
4. рекомендует, когда, сколько и в какой кластер отправить товар;
5. рекомендует, когда дозаказать товар у поставщика (фаза 4);
6. предупреждает о рисках: дефицит, затоваривание, отставание от плана, пора начинать распродажу.

В первой версии система **только рекомендует**. Решения принимает человек, и каждое решение фиксируется.

**Область первой версии:** только сезонный товар, у которого есть дата начала и дата конца сезона. Всесезонный (базовый) ассортимент не входит в v1.

## 3. Термины, исходы заказа, временная основа и единицы

| Термин | Что означает |
| --- | --- |
| SKU | Артикул + размер (баркод). Основная единица планирования |
| Сезон | Период от даты старта продаж d_start до даты конца сезона d_end |
| К-сезонности, k(d) | Вес дня в спросе сезона по дате заказа. Сумма весов за сезон равна 100% |
| Кластер | Группа складов Ozon |
| Кластер покупателя | Кластер, к которому относится регион покупателя. Спрос и наличие считаются по нему |
| Заказ | Заказанная покупателем штука |
| Отгрузка | Заказ, списанный с остатка склада Ozon |
| Отмена до отгрузки | Заказ отменён до списания с остатка. Товар не покидает склад |
| Отмена после отгрузки | Заказ отменён после списания. Товар возвращается на склад так же, как невыкуп |
| Выкуп | Заказ, который покупатель получил и оплатил |
| Невыкуп | Заказ, который покупатель не забрал. Товар возвращается на склад Ozon |
| Возврат после выкупа | Выкупленный товар, который покупатель вернул позже. Товар возвращается на склад Ozon |
| Нетто-выкуп | Выкуп, по которому не было возврата после выкупа |
| Когорта | Все заказы одного SKU, сделанные в один день |
| Исходы когорты завершены | Нет открытых заказов, и окно возврата после выкупа прошло для каждого выкупа когорты. Заказ, открытый дольше таймаута, помечается «закрыт по таймауту» и исключается из долей; ожидаемые возвраты по уже выкупленным заказам таймаут не отменяет |
| Лаги | Через сколько дней после заказа наступает выкуп, возврат невыкупа на склад, возврат после выкупа на склад |
| Оценка спроса дня, E(d) | Сколько заказов было бы в кластере покупателя при полном наличии (этап 1.7) |
| Потенциальный спрос | Факт заказов в дни полного наличия; max(факт, E) в дни без наличия и частичного наличия |
| Упущенный спрос | Потенциальный спрос минус фактические заказы = max(0, E − факт) |
| Итоговые нетто-продажи сезона | Нетто-выкупы по заказам с датой заказа от d_start до d_end, включая исходы после d_end: состоявшиеся + ожидаемые |
| Ожидаемые продажи | Будущая часть итоговых нетто-продаж: по открытым заказам, по выкупленным в окне возврата и по будущим заказам, ограниченным доступным товаром |
| Физический остаток после сезона | Товар после последнего исхода заказов сезона: на Ozon и в обратной логистике — основной показатель; на своём складе — отдельно |
| Срок поставки, LT | От решения отправить товар до момента, когда он доступен к продаже в кластере, дни |
| Страховой запас, SS | Запас на случай колебаний спроса и задержек поставки, штуки |
| Период покрытия, H | На сколько дней вперёд после прихода рассчитывается партия, дни |
| Дни покрытия | На сколько дней хватит текущего остатка при текущей скорости заказов |
| К-распроданности, ST | Итоговые нетто-продажи сезона / закуплено на сезон (этап 1.12) |
| Локализация, L | Доля заказов, отгруженных из того же кластера, где находится покупатель |
| Стоимость под риском | Штуки под риском × цена закупки |
| Недополученная выручка (оценка) | Упущенный спрос × b × средняя цена продажи |

**Состояния заказа.** У каждого заказа в каждый момент ровно одно состояние:

- открыт → отменён до отгрузки;
- открыт → отменён после отгрузки;
- открыт → не выкуплен;
- открыт → выкуплен → возвращён после выкупа;
- открыт → закрыт по таймауту.

Событие, пришедшее позже (возврат после выкупа, поздний статус), меняет состояние заказа и пересчитывает его когорту задним числом.

**Доли исходов.** Считаются по зрелым когортам — с завершёнными исходами (без заказов, закрытых по таймауту) за скользящее окно (этап 1.9). Знаменатель — все заказы, кроме r:

| Доля | Определение |
| --- | --- |
| c | Отмены до отгрузки / все заказы |
| c₂ | Отмены после отгрузки / все заказы |
| u | Невыкупы / все заказы |
| β | Выкупы / все заказы |
| r | Возвраты после выкупа / **выкупы** |

Выполняется c + c₂ + u + β = 1. Производные доли:

| Показатель | Формула | Что значит |
| --- | --- | --- |
| b | β × (1 − r) | Нетто-выкуп от всех заказов |
| Доля отгрузки | 1 − c | Сколько заказов списывает товар |
| Нетто-выкуп от отгруженных | b / (1 − c) | Сколько отгруженных единиц станут продажей |
| Возврат невыкупа от отгруженных | (c₂ + u) / (1 − c) | Поток возврата с лагом невыкупа |
| Возврат после выкупа от отгруженных | β × r / (1 − c) | Поток возврата с лагом возврата после выкупа |

Числовой пример — в разделе 12, пример 1.

**Временная основа и итоговые продажи (обязательно для всех этапов):**

- k(d), план, спрос и скорость привязаны к **дате заказа**.
- В сезон засчитываются заказы с датой заказа от d_start до d_end включительно. Их исходы входят в итоговые нетто-продажи сезона, даже если наступили после d_end.
- Заказы с датой до d_start — **досезонные**: в продажи сезона не входят. Их отмены и возвраты, ставшие доступными после d_start, считаются поступлением сезона в дату доступности (пример 10).
- Итоговые нетто-продажи сезона используются в ST, в доле продаж партии (этап 2.9) и в закупке (этап 4.1). Они состоят из трёх частей — состоявшиеся нетто-выкупы, ожидаемое изменение по существующим заказам и продажи по будущим заказам; каждая часть учитывается ровно один раз (этапы 1.11, 1.12).
- Физический остаток после сезона — отдельный показатель: он показывает, что вернулось или не продалось, и в ST не входит.
- В прогнозе остатка исходы относятся к дате события по лагу.

**География:**

- спрос, наличие, восстановление спроса, скорость и доли спроса считаются по **кластеру покупателя**;
- заказ, обслуженный складом другого кластера, — это факт спроса кластера покупателя, поэтому межкластерная отгрузка не увеличивает суммарный спрос;
- остаток кластера — сумма остатков складов этого кластера; отгрузки по складам нужны только для баланса товара и локализации.

**Календарь расчёта:**

- часовой пояс — московское время;
- **расчётные сутки** — интервал между двумя последовательными ежедневными снимками (этап 0.2). Событие относится к расчётным суткам по своей метке времени, дата суток — дата закрывающего снимка. Так остаток на конец дня и движения дня покрывают один и тот же интервал; календарные сутки 00:00–24:00 используются только в отчётах;
- события после снимка относятся к следующим расчётным суткам;
- порядок операций внутри прогнозного дня: остаток на начало дня → приход поставок → возвраты, ставшие доступными к продаже, и освобождённый резерв → отгрузки → остаток на конец дня. Возврат физически приходит на склад по лагу, а доступен к продаже через τ_resell дней после прихода — одинаково во всех расчётах;
- день **полного наличия** — остаток на начало и на конец дня выше порога;
- день **без наличия** — остаток на начало и на конец дня не выше порога и прихода за день не было;
- день **частичного наличия** — всё остальное, в том числе день, когда утром товара не было, а днём он пришёл и продавался.

**Единицы измерения:**

- План сезона V — нетто-выкупы по дате заказа, штуки.
- Остатки, отгрузки, SS и рекомендации к отправке — штуки.
- LT, H, окна расчёта — дни.
- Переход от нетто-выкупов к заказам: заказы = нетто-выкупы / b. Отгрузки = заказы × (1 − c).
- Невыкупы и возвраты после выкупа — два отдельных потока прихода на склад, с долями из таблицы выше.
- Скорость заказов — средние заказы в день за дни полного наличия, штуки в день.
- Разброс спроса — через CV (этап 2.3).
- Деньги: недополученная выручка — по цене продажи; ущерб, приоритеты и цена решений — по закупочной стоимости (требование 4.11).

## 4. Общие требования ко всем этапам

1. **Ежедневный пересчёт.** Все отчёты и расчёты обновляются каждый день после загрузки данных.
2. **История сохраняется.** Загруженные данные не перезаписываются бесследно. Видно, какими были данные и расчёты на любую прошлую дату. Для каждого события хранятся и момент, когда оно произошло, и момент, когда оно стало известно системе. Это нужно для объяснимости и бэктеста.
3. **Повторная загрузка безопасна.** Повторный запуск загрузки за день не задваивает данные.
4. **Параметры редактирует человек.** Все пороги и настройки меняются без разработчика. У каждого параметра есть стартовое значение (раздел 10). Каждое изменение журналируется: кто, когда, старое и новое значение.
5. **Объяснимость.** По каждому расчётному числу можно раскрыть, из чего оно получено.
6. **Уровень данных.** Если у SKU не хватает своей истории, берутся данные уровнем выше: артикул (все размеры) → аналог → категория → значение вручную. Использованный уровень показывается рядом с числом.
7. **Ошибки видны.** Если загрузка не прошла или данные неполные, это видно пользователю.
8. **Потенциальный спрос.** План-факт, доли размеров и регионов, коррекция прогноза, сезонность из своей истории и оценка темпа сезона считаются по потенциальному спросу (этап 1.7). Скорость — по дням полного наличия (раздел 3). Распроданность, ожидаемые продажи и итоги сезона — только по фактическим и ожидаемым продажам: упущенный в прошлом спрос продажами уже не станет.
9. **Отчёты.** Каждый отчёт — таблица с фильтрами по сезону, категории, артикулу, SKU и кластеру, сортировкой и выгрузкой в Excel. Способ показа (экран в системе, BI, файл) выбирает команда.
10. **Единицы, временная основа, география и календарь** — по разделу 3.
11. **Единая база ущерба.** Приоритет алертов и цена решений считаются в закупочной стоимости штук под риском — и для дефицита, и для затоваривания. Оценка через маржу — в следующей версии.
12. **Расчёт на неполных данных.** Расчёт за день запускается, только когда контроль качества (этап 1.5) пометил данные полными. Если данные неполные, показываются расчёты прошлого дня с пометкой даты. Пользователь с правом правки может явно разрешить расчёт на неполных данных; это журналируется, а результаты помечаются как ненадёжные.
13. **Роли.** Просмотр; правка параметров и справочников; решения по рекомендациям. Одна учётная запись может иметь несколько ролей.
14. **Производительность.** Ежедневный расчёт завершается до времени готовности, которое задаёт бизнес (раздел 10, открытые вопросы — закрыть до фазы 2А), на объёме SKU и складов, который задаёт бизнес. Ориентир — полный пересчёт не дольше 1 часа.
15. **Обязательные тестовые сценарии.** Каждый расчётный этап фаз 1–3 проверяется на числовых примерах раздела 12 и на применимых граничных случаях. Доли в таблицах примеров приведены округлённо: расчёт ведётся по исходным дробям без промежуточного округления, результат сравнивается с точными ожидаемыми значениями из тестовых данных прототипа с допуском 0,01 шт.; значения в таблицах раздела 12 могут быть округлены (помечены «≈»), округление до коробов — отдельная операция в конце. Граничные случаи:
    - нулевой спрос за окно;
    - b = 0 и b = 1;
    - SKU без истории;
    - первый день сезона и последние дни сезона, когда до d_end меньше LT;
    - поздние возвраты: после закрытия когорты и после d_end;
    - частичная поставка;
    - товара на своём складе меньше одного короба;
    - одновременный дефицит в нескольких кластерах.
16. **Правила для граничных случаев.** Разработчик не выбирает поведение сам — оно задано здесь:

| Случай | Поведение |
| --- | --- |
| b ниже минимума (параметр) на уровне SKU | Берётся уровень выше. Если на всех уровнях b ниже минимума — рекомендации по SKU не формируются, причина «нет выкупа» |
| c = 1 или нет отгрузок в окне | Берётся уровень выше; если не помогает — рекомендации не формируются, причина «нет отгрузок» |
| K ниже минимума (параметр), включая первый день сезона | w = 0, V_прогноз = V |
| Нет V и нет истории SKU | Прогноз не считается, рекомендации не формируются, причина «нет плана» |
| Сумма оставшихся весов k равна нулю | V_ост = 0 |
| Дата расчёта позже d_end | V_ост = 0, новые рекомендации не формируются; отчёты по исходам заказов сезона продолжают обновляться |
| Прогноз дня равен нулю | День исключается из расчёта CV |
| Нулевой знаменатель метрики или наблюдений меньше минимума (параметр) | Статус «недостаточно данных» вместо значения; в приёмке такая ячейка не считается ни пройденной, ни проваленной |
| Базовой скорости нет ни на одном уровне | Оценка спроса дня не считается, день помечается «не восстановлено», потенциальный спрос = факт |
| Нет зрелых когорт в окне (обычно первые 5–6 недель сезона) | Зрелые когорты прошлого сезона того же SKU → уровень выше → ручное значение; если нет и его — рекомендации не формируются, причина «нет данных о выкупе» |
| Дата расчёта раньше d_start | k(d) = 0 вне сезона; досезонные заказы не прогнозируются, но фактические уменьшают остаток; дата риска может приходиться на d_start |

**Цель:** не считать на неполных данных.

### Этап 1.7. Отчёт «Дефициты и упущенный спрос»

**Вопрос:** где товара не было и сколько спроса потеряно.

**Правила восстановления спроса** (по кластеру покупателя, типы дней — по разделу 3):

- базовая скорость — средние заказы в день за последние 14 дней полного наличия SKU в кластере покупателя (окно — параметр), приведённые к текущему дню через k(d); дни с k = 0 (вне сезона) в окно не входят;
- нужно не меньше 5 таких дней (параметр). Если меньше — скорость артикула в кластере × доля размера, затем категория. Если нет и её — день помечается «не восстановлено»;
- **оценка спроса дня** E(d) = базовая скорость с сезонной поправкой — для дней без наличия и частичного наличия;
- **потенциальный спрос** = max(факт заказов, E). В день полного наличия — факт;
- **упущенный спрос** = max(0, E − факт). Заказы кластера покупателя, обслуженные другим кластером, входят в факт, поэтому не увеличивают потенциальный спрос;
- в ежедневном расчёте и в бэктесте используются только предшествующие дни. В отчётах за прошедшие периоды можно брать дни до и после дефицита.

**Что показать** по SKU × кластер покупателя за период: дни без наличия, дни частичного наличия, факт заказов, потенциальный спрос, упущенный спрос в штуках, недополученная выручка (оценка) и стоимость под риском по цене закупки.

### Этап 1.11. Отчёт «План-факт и прогноз спроса сезона»

**Вопрос:** догоняем ли план, каким будет спрос сезона и сколько его осталось.

**Что сделать:**

- принять объём сезона V по SKU или артикулу (нетто-выкупы по дате заказа, штуки) — ввод или импорт; для артикула — доли размеров;
- принять К-сезонности: из своей истории или МПСтат, по неделям с профилем дня недели;
- план по дням:

$$
\text{Plan}(d) = V \times \frac{k(d)}{\sum_{t=d_{start}}^{d_{end}} k(t)}
$$

- накопленная доля сезонности на сегодня: K = Σ k(t) от d_start до вчера / Σ k(t) за сезон;
- **нетто-выкупы с начала сезона по дате заказа** состоят из двух частей. Каждая считается один раз и хранится отдельно:
    - **состоявшиеся нетто-выкупы** S_факт = выкуплено − уже возвращено после выкупа, по всем когортам сезона;
    - **ожидаемое изменение по существующим заказам** ΔS = открытые отгруженные × β / (1 − c) × (1 − r) + открытые неотгруженные × b − ожидаемые будущие возвраты по выкупленным. ΔS = 0 только у когорты с завершёнными исходами; закрытие заказов по таймауту ожидаемые возвраты по известным выкупам не обнуляет;
- ожидаемые будущие возвраты по выкупленным считаются отдельно для каждой даты выкупа, с учётом уже состоявшихся возвратов:

$$
\text{Будущие возвраты} = (N - R) \times \frac{r \times (1 - F(a))}{1 - r \times F(a)}
$$

N — выкуплено в эту дату, R — уже возвращено из них, a — возраст выкупа в днях, F — из этапа 1.9. Результат никогда не больше N − R;
- оценка нетто-выкупов с начала сезона = S_факт + ΔS;
- потенциальные нетто-выкупы с начала сезона = потенциальный спрос (этап 1.7) × b;
- оценка спроса сезона по факту и прогноз спроса сезона:

$$
V_{\text{факт}} = \frac{\text{Потенциальные нетто-выкупы с начала сезона}}{K}, \qquad V_{\text{прогноз}} = w \times V_{\text{факт}} + (1 - w) \times V
$$

- вес факта w растёт с K (правило — параметр, по умолчанию w = K). Если K ниже минимума, w = 0 (требование 4.16);
- **оставшийся спрос сезона** — только на будущие дни, уже прошедший спрос (включая открытые заказы) в него не входит:

$$
V_{\text{ост}} = V_{\text{прогноз}} \times (1 - K)
$$

- прогноз заказов на будущий день d: Заказы(d) = V_ост × k(d) / Σ k(t) по оставшимся дням / b;
- отклонение факт / план за 7, 14, 28 дней по потенциальному спросу.

V_прогноз и V_ост — это **спрос**, а не продажи. Сколько из него станет продажами, зависит от наличия товара (этапы 1.12 и 2.2). S_факт и ΔS передаются в этапы 1.12 и 2.2 раздельно.

Числовые примеры — раздел 12, примеры 2 и 4.

**Готово, когда:** сумма плана по дням равна V. Результаты на примерах 2 и 4 раздела 12 совпадают. Оценка нетто-выкупов когорты никогда не отрицательна, в том числе при большой доле уже состоявшихся возвратов (пример 2б). Закрытие заказов по таймауту не обнуляет ожидаемые возвраты по известным выкупам (пример 2в). На тестовом SKU, идущем на 20% выше плана, V_прогноз растёт к V × 1,2 по мере прохождения сезона. При w = 1 выполняется V_ост + потенциальные нетто-выкупы с начала сезона = V_прогноз.

### Этап 1.12. Отчёт «Распроданность»

**Вопрос:** где риск затоваривания к концу сезона.

**Что показать** по SKU:

$$
ST_{total} = \frac{S_{\text{факт}} + \Delta S + S_{\text{буд}}}{\text{Закуплено на сезон}}
$$

$$
ST_{mp} = \frac{\text{То же по продажам на Ozon}}{\text{Остаток на Ozon на } d_{start} + \text{поставлено на Ozon за сезон}}
$$

- S_факт и ΔS — из этапа 1.11, S_буд — продажи по будущим заказам с датой до d_end. Каждая часть входит в ST ровно один раз; в отчёте показываются все три;
- закуплено на сезон = доступный остаток на d_start (снимок начала d_start, без резерва) + отмены и возвраты досезонных заказов в дату их доступности + все поступления от поставщиков на сезон, включая заказанные и ещё не пришедшие. Это накопленный объём, а не текущий остаток;
- текущее значение ST — только S_факт / закуплено на сезон;
- в фазе 1 S_буд — оценка сверху: min(V_ост, весь доступный товар: Ozon + в пути + свой склад + заказано у поставщика с приходом до d_end). С фазы 2А её заменяет прогноз по кластерам из этапа 2.2;
- восстановленный спрос в ST не используется;
- отдельно показывается физический остаток после сезона;
- цель ST проверяется на базовой линии этапа 0.3 до того, как начнёт ограничивать поставки: для категорий с низким выкупом поздние возвраты остаются на складе, и цель 95% может быть недостижима.

Сортировка по стоимости ожидаемого остатка после сезона по цене закупки.

**Готово, когда:** SKU с ожидаемым ST ниже цели попадают в начало списка. Дефицит в прошлом не увеличивает ожидаемые продажи. Заказ последнего дня сезона с выкупом после d_end входит в итоговые нетто-продажи. На примере 2 раздела 12 ожидаемое изменение учитывается один раз.

### Этап 1.13. Отчёт «Воронка»

**Вопрос:** почему SKU отстаёт от плана.

**Что показать:** заказы = показы × CTR × CR. Каждый множитель сравнивается с обычным уровнем SKU (медиана за окно). Показывается, какой множитель упал: показы (видимость), CTR (карточка в выдаче), CR (цена, отзывы, размер). Дни без наличия и частичного наличия исключаются. При малом числе показов или переходов (порог — параметр) берётся уровень артикула или категории.

**Готово, когда:** на тестовом SKU с искусственно сниженными показами причина — «показы».

### Этап 1.14. Отчёт «Сроки поставок»

**Вопрос:** сколько на самом деле идёт товар до продажи.

**Что показать** по кластеру и складу: фактические поставки с длительностью каждого шага (создание → отгрузка → приёмка → доступно к продаже), медиана, среднее, стандартное отклонение и 80-й процентиль полного срока, число поставок в выборке.

**Готово, когда:** срок каждой поставки совпадает с датами в Ozon.

## 7. Фаза 2. Подсорт

Фаза 2 состоит из двух обязательных частей. **2А** (этапы 2.1–2.7) — рекомендации ближайшей поставки на самой простой модели и проверка на прошлом сезоне. **2Б** (этапы 2.8–2.9) — план поставок на весь сезон и правило последней поставки. Упрощения 2А сознательные: что из них уточнять, решает бэктест (этап 2.6).

**Упрощения фазы 2А:**

- один b и одна доля отмен c на артикул или категорию (этап 1.9);
- средние лаги выкупа, возврата невыкупа и возврата после выкупа (этап 1.9) вместо распределения;
- оба вида возвратов приходят в тот же кластер, откуда отгружен заказ;
- срок поставки LT по кластеру — медиана из этапа 1.14 или ручное значение;
- рекомендуется только ближайшая поставка.

### Этап 2.1. Прогноз спроса по кластерам

**Цель:** знать, сколько заказов будет в каждом кластере в каждый будущий день.

**Что сделать:**

- прогноз заказов SKU на будущие дни до d_end — по формуле этапа 1.11 (V_ост, разложенный по k(d) на оставшиеся дни и переведённый в заказы через b);
- разделить спрос по кластерам покупателей по долям потенциального спроса из этапа 1.10.

**Готово, когда:** сумма прогноза по кластерам и дням равна V_ост / b. На тестовом SKU совпадает с ручным расчётом.

### Этап 2.2. Прогнозный остаток

**Цель:** увидеть, сколько товара будет на каждом кластере в каждый день и сколько из спроса станет продажами.

Расчёт ведётся двумя балансами. Доли исходов — по разделу 3, порядок операций в дне — по календарю раздела 3.

**Начальное состояние прогноза:**

- начальный остаток = «доступно к продаже» (этап 1.3). Резерв обслуживает только уже сделанные и не отгруженные заказы (открытые неотгруженные в когортах), новый спрос из него не покрывается. По каждому такому заказу моделируется вся оставшаяся цепочка исходов: доля c — отмена до отгрузки, единица возвращается в доступный остаток (освобождение резерва, лаг отмены); доля (1 − c) — отгрузка из резерва, которая не уменьшает доступный остаток; по этим отгрузкам приходят возвраты невыкупа ((c₂ + u) / (1 − c)) и возвраты после выкупа (β × r / (1 − c)) со своими лагами и доступностью через τ_resell, а их нетто-продажи (b / (1 − c)) входят в ΔS этапа 1.11 (пример 9);
- обратная логистика: товар, у которого исход уже наступил (невыкуп, отмена после отгрузки, возврат после выкупа), но который ещё едет на склад, — из «товар в пути обратно» этапа 1.3. Он приходит по оставшемуся среднему лагу. Возвраты, уже физически пришедшие, но ещё не доступные к продаже (в обработке), берутся со своей датой доступности;
- уже отгруженные открытые заказы и выкупленные в окне возврата — ожидаемые исходы из этапа 1.11.

**Баланс спроса** (по кластеру покупателя X, за день):

$$
D_X = C_X + T_X + L_X
$$

- D — прогноз заказов (этап 2.1);
- C — **покрытые** заказы, обслуженные доступным остатком своего кластера. Покрытый заказ списывает (1 − c) единиц товара, поэтому C = min(D, доступный остаток / (1 − c));
- из покрытых заказов C × c отменяются до отгрузки, C × (1 − c) отгружаются;
- непокрытый спрос D − C один раз переносится в другие кластеры. Запрос в кластер Y = p × (D − C) × доля Y из этапа 1.10 (таблица «в дни без наличия»), без доли самого X — остальные доли перенормируются;
- **сумма входящих переносов** в Y от всех кластеров ограничена остатком Y после его собственного спроса / (1 − c). Если запросов больше, лимит делится между отправителями пропорционально их запросам. Это T — **перенесено**. Повторного переноса нет;
- L — **потеряно** = D − C − T. Это упущенный спрос в прогнозе.

**Баланс товара** (по кластеру, за день):

$$
\text{Ост}_{конец} = \text{Ост}_{начало} + \text{Приход поставок} + \text{Возвраты, ставшие доступными} + \text{Освобождение резерва} - \text{Отгрузки}
$$

- Ост — доступный к продаже остаток. Возвраты физически приходят на склад по лагу и становятся доступными через τ_resell дней (раздел 3); возвраты в обработке показываются отдельно;
- отгрузки = (собственные покрытые заказы + принятые перенесённые заказы других кластеров) × (1 − c);
- доступный остаток для отгрузок дня = остаток на начало + приход поставок + возвраты, ставшие доступными в этот день + освобождение резерва. Освобождение резерва — открытые неотгруженные заказы, которые по прогнозу отменятся до отгрузки: их количество × c, со сдвигом на средний лаг отмены до отгрузки (этап 1.9);
- физический приход возвратов невыкупа = отгрузки × (c₂ + u) / (1 − c), со сдвигом на средний лаг невыкупа;
- физический приход возвратов после выкупа = отгрузки × β × r / (1 − c), со сдвигом на средний лаг возврата после выкупа;
- приход поставок — поставки в пути по дате доступности к продаже и принятые рекомендации (этап 2.5) по ожидаемой дате прихода;
- остаток не бывает ниже нуля;
- горизонт прогноза — до d_end + максимальный лаг + τ_resell, чтобы посчитать остаток после сезона и проверку последней партии.

**Ожидаемые продажи** = отгрузки × b / (1 − c), отнесённые к дате заказа. Это S_буд для этапа 1.12.

Числовые примеры — раздел 12, примеры 5, 5б, 9 и 10.

**Готово, когда:**

- **воспроизведение остатка:** если подставить фактические движения дня, расчёт сходится с фактическим остатком в пределах допуска этапа 1.5;
- на каждом дне и кластере выполняется D = C + T + L, а отгрузки = (C + принятые T) × (1 − c);
- сумма входящих переносов в любой кластер не больше его свободного остатка / (1 − c);
- результаты на примерах 5, 5б, 9 и 10 раздела 12 совпадают;
- сценарий с одновременным дефицитом в нескольких кластерах не даёт отрицательных остатков и двойного переноса.

Точность прогноза остатка, сделанного заранее, — отдельная метрика (WAPE остатка на горизонте LT, этап 2.6), а не критерий этого этапа.

### Этап 2.3. Страховой запас

**Цель:** держать запас на колебания спроса.

$$
SS = z \times CV \times \bar{D} \times \sqrt{LT}
$$

- z — по целевому уровню сервиса (95% → 1,65);
- D̄ — прогноз **отгрузок** кластера в день на ближайший период LT = заказы × (1 − c): SS сравнивается с остатком в штуках, а заказ списывает (1 − c) единиц. SS округляется вверх до целой штуки;
- LT — медиана срока поставки из этапа 1.14;
- CV — разброс относительной ошибки дневного прогноза:

$$
CV = \operatorname{std}_{d \in \text{окно}} \left( \frac{\text{Факт}(d) - \text{Прогноз}(d)}{\text{Прогноз}(d)} \right)
$$

- в окно (параметр) входят только дни полного наличия с прогнозом больше нуля;
- если таких дней меньше минимума (параметр), берётся запасной CV — по ошибкам на уровне SKU × кластер, объединённым по артикулу или категории (CV агрегированного ряда занижает разброс); при отсутствии истории — стартовое значение (параметр);
- пока система не хранит собственных прогнозов, прогнозом дня считается скорость за предыдущие 28 дней полного наличия с сезонной поправкой.

Разброс срока поставки в 2А не учитывается. Он добавляется в этапе 3.4, если бэктест покажет, что задержки поставок — заметная причина дефицитов.

**Готово, когда:** SS совпадает с ручным расчётом. При идеальном прогнозе CV = 0 и SS = 0. Видно, из каких значений SS посчитан.

### Этап 2.4. Рекомендация подсорта

**Цель:** сказать, когда, сколько и в какой кластер отправить ближайшую поставку.

**Что сделать:**

1. **Дата риска** — первый день, когда в прогнозе (этап 2.2, со всеми ожидаемыми приходами, возвратами и принятыми рекомендациями) выполняется хотя бы одно: остаток на конец дня ниже SS **или** собственный остаток не покрывает спрос кластера покупателя (C < D). Второе условие работает и при SS = 0.
2. Дата отправки = дата риска − LT. Если она уже прошла — пометка «срочно», дата прихода = сегодня + LT, показывается упущенный спрос до прихода.
3. **Объём** — минимальное количество, при котором на **всём интервале** от даты прихода до даты прихода + H − 1 включительно (ровно H дней) каждый день выполняются оба условия: остаток на конец дня не ниже SS и C = D. Все приходы и возвраты внутри интервала учитываются. После добавления партии прогноз пересчитывается. Объёмы считаются в **два прохода**: первый проход рекомендует партии всем кластерам, второй пересчитывает прогноз с этими партиями как приходом (включая переносы спроса между кластерами) и окончательно подбирает объёмы — иначе кластер закупает под перенос спроса соседа, которому партия уже рекомендована (пример 11).
4. Округлить вверх до кратности короба, не меньше минимальной партии.
5. **Распределение при нехватке своего склада.** Свободно на своём складе = остаток − резерв (этап 2.5) + поступления от поставщиков с датой доступности не позже даты отправки. Если свободного меньше, чем нужно всем кластерам:
    - до распределения для каждого кластера считается допустимый максимум партии по проверке шага 6, и потребность кластера в распределении = min(потребность, допустимый максимум); кластер с допустимым максимумом ниже минимальной партии в распределение не входит и помечается «запрет последней поставки»;
    - кластеры упорядочиваются по приоритету: ранняя дата риска → больший упущенный спрос до прихода в закупочной стоимости → больший прогноз спроса → порядок кластеров в справочнике;
    - в этом порядке каждому кластеру выделяется его **полная минимальная партия**, пока хватает свободного остатка;
    - оставшиеся коробы раздаются по одному по наибольшей оставшейся потребности;
    - если выделение какого-то кластера оказалось ниже его минимальной партии, оно возвращается в общий пул, и распределение повторяется без этого кластера. Такой кластер помечается «не набралась минимальная партия». После распределения прогноз пересчитывается; если допустимость партий изменилась, распределение повторяется — не больше заданного числа раз (параметр).
6. **Проверка последней партии** (базовая, для одной ближайшей партии): продажи кластера списываются сначала с текущего остатка, затем с партии (FIFO); вернувшаяся единица снова доступна через τ_resell. Нормированная доля продаж партии = min(1, нетто-продажи единиц партии до d_end / (объём × b / (1 − c))). Если она ниже порога, партия уменьшается до наибольшего объёма, кратного коробу, при котором порог выполняется; если такой объём меньше минимальной партии — партия не рекомендуется. В рекомендации показываются обычная и нормированная доли. Проверка применяется дважды: до распределения (допустимый максимум для шага 5) и к итоговой партии. Для плана сезона из нескольких партий проверка расширяется в этапе 2.9.
7. Уже принятые и отправленные рекомендации учитываются в прогнозе как приход и повторно не предлагаются.

Числовые примеры — раздел 12, примеры 6, 7, 8, 8б и 11.

**Результат:** список: SKU, кластер, дата отправки, количество в штуках и коробах, причина, пометка «срочно».

**Готово, когда:** результаты на примерах 6, 7, 8 и 8б раздела 12 совпадают. При SS = 0 и пустом кластере дата риска находится. Принятая вчера и не отправленная поставка не появляется сегодня повторно. При нехватке своего склада сумма рекомендаций не превышает свободный остаток, каждая партия кратна коробу и не меньше минимальной; если допустимое распределение существует, хотя бы один кластер получает партию — в том числе когда приоритетному кластеру партия запрещена правилом последней поставки. Если товара меньше одного короба, рекомендация не формируется и это видно.

| --- | --- | --- |
| Предложена | Система рекомендует | Не учитывается как приход |
| Принята | Человек согласился, возможно изменив количество или дату | Товар резервируется на своём складе; партия — ожидаемый приход в кластер |
| Просрочена | Принята, но не отправлена к плановой дате отправки | Резерв сохраняется; ожидаемый приход каждый день переносится на «сегодня + LT» |
| Отправлена | Связана с поставкой Ozon из этапа 1.4 | Резерв сохраняется, пока импорт своего склада не отразит списание, и только тогда снимается; дальше товар учитывается как поставка в пути по данным Ozon. Из свободного остатка товар вычитается ровно один раз при любом порядке событий |
| Частично отправлена | Отправлено меньше принятого | Неотправленная часть остаётся принятой, пока человек её не отменит |
| Отклонена / отменена | Человек отказался | Резерв снимается |
| Закрыта | Поставка доступна к продаже | — |

**Что ещё сделать:**

- принять рекомендацию на объём больше свободного остатка своего склада нельзя: система показывает доступный максимум;
- связку рекомендации с поставкой Ozon система предлагает по SKU, количеству и дате, человек подтверждает;
- при изменении или отклонении — причина из списка (нет товара, нет слотов, не согласен с прогнозом, другое) и комментарий;
- просроченная рекомендация попадает в алерт, если остаётся неотправленной дольше срока (параметр);
- отчёт: доля принятых рекомендаций и итог по SKU для каждого варианта — что было бы при рекомендации и что получилось по факту.

**Готово, когда:** все переходы статусов работают на тестовом сценарии, включая частичную отправку, просрочку и отмену. Резерв своего склада равен сумме принятых, просроченных и отправленных, но ещё не списанных импортом своего склада рекомендаций. Тест: на складе 96 шт., принято 48 для A, поставка создана в день 1, списание в импорте — в день 3; в дни 1–2 свободно 48, а не 96. У просроченной рекомендации ожидаемый приход сдвигается каждый день.

### Этап 2.6. Бэктест

**Цель:** проверить модель и политику поставок до использования в работе, решить, что уточнять, и определить уровень допуска к эксплуатации.

**Протокол:**

1. Протокол, допущения симуляции, метрики и пороги приёмки согласуются **до** запуска.
2. Данные прошлого сезона делятся на период настройки параметров и отложенный проверочный период (параметр, по умолчанию последние 6–8 недель с данными). На проверочном периоде параметры не меняются.
3. **Воспроизводимость:** расчёт на историческую дату использует только события, **известные системе** к этой дате (требование 4.2), а не просто произошедшие до неё. Версии параметров, сезонности и справочников на каждую дату фиксируются. Для истории, загруженной задним числом, момента получения нет: фильтр работает по дате события, а такой период помечается как ограничение теста.
4. Разложение ошибки по источникам: объём сезона, сезонность, доли исходов, лаги, доли кластеров, срок поставки.
5. Сверка продакшен-расчёта с прототипом на Python на тех же данных: расхождение = Σ|разница рекомендованных штук| / Σ рекомендованных штук по SKU × кластер, не больше порога.
6. **Покрытие:** проверка охватывает не меньше заданной доли потенциального спроса (параметр, стартовое значение 80%). SKU со статусом «недостаточно данных» перечисляются вместе с их долей спроса.

**Критерии приёмки** (все три обязательны):

| Критерий | Что проверяет | Как считается | Пройден, если |
| --- | --- | --- | --- |
| А. Прогноз спроса | Точность прогноза заказов | WAPE = Σ\|прогноз − факт\| / Σ факт; смещение = Σ(прогноз − факт) / Σ факт. По SKU × кластер покупателя × день проверочного периода, горизонт LT, только дни полного наличия, против **фактических** заказов | WAPE и смещение в пределах согласованных порогов |
| Б. Ограничения | Корректность рекомендаций | Доля рекомендаций, соблюдающих кратность, минимальную партию, свободный остаток своего склада, отсутствие дублей | 100% |
| В. Политика поставок | Качество решений о поставках | Симуляция, описанная ниже. Доля потерянного спроса ΣL / ΣD по потенциальному спросу и стоимость остатка после сезона на Ozon и в обратной логистике; остаток своего склада и доля дней без наличия — информационно | Не хуже базовой линии по дефициту при остатке не выше базовой линии, с допусками протокола |

**Симуляция для критерия В:**

- свой склад стартует с фактического остатка на начало проверочного периода. Дальше к нему добавляются фактические поступления от поставщиков в их фактические даты и вычитаются **моделируемые** отправки. Фактический остаток своего склада в последующие дни не подставляется;
- поступления от поставщиков — внешние для сравнения: закупка относится к фазе 4;
- все рекомендации исполняются; сроки поставки — из фактического распределения;
- спрос — потенциальный спрос этапа 1.7, одинаковый для системы и базовой линии;
- базовая линия — фактическая ручная политика на тех же днях, SKU и поступлениях. Потерянный спрос L в базовой линии — упущенный спрос этапа 1.7, в симуляции — из баланса этапа 2.2.

**Дополнительно, информационно:** точность прогноза остатка (WAPE остатка на горизонте LT) — целевая метрика этапов 3.1 и 3.2.

- минимум наблюдений проверяется на двух уровнях: пара SKU × кластер покупателя получает статус «недостаточно данных», если в проверочном периоде у неё меньше 14 дней полного наличия (параметр); критерий в целом считается, только если по остальным парам набирается не меньше 300 наблюдений SKU × кластер × день (параметр). Окончательные значения — в протоколе (требование 4.16);
- критерий В сравнивает с базовой линией, а не задаёт абсолютных порогов: результат симуляции зависит от допущений.

**Теневой режим.** Если истории остатков нет и её нельзя восстановить из движений, бэктест заменяется теневым режимом на 4–6 недель: система каждый день считает прогнозы и рекомендации, решения принимаются вручную. Критерии А и Б считаются на свежем факте; по критерию В рекомендации сравниваются с ручными решениями.

**Допуск к эксплуатации:**

| Уровень | Условие | Что разрешено |
| --- | --- | --- |
| Ограниченный пилот | Критерии А и Б пройдены (на проверочном периоде или в теневом режиме); по критерию В рекомендации не хуже ручных решений; покрытие не ниже заданного | Рекомендации используются на пилотной группе SKU; размер группы и срок пилота — в протоколе |
| Полное использование | Пилотная группа не хуже контрольной группы на ручном планировании по дефициту при не большем остатке за срок пилота | Рекомендации используются на всём ассортименте |

**Сопоставимость пилотной и контрольной групп** (закрепляется в протоколе пилота до его начала):

- группы подбираются случайно с разбивкой по категории, объёму спроса и доле выкупа;
- на старте у групп сопоставимые дни покрытия;
- дефицит считается как доля потенциального спроса, остаток — в днях покрытия, а не в штуках;
- обе группы оцениваются на одну и ту же дату.

**Результат:** отчёт по трём критериям, список SKU с наибольшей ошибкой, список уточнений фазы 3 в порядке пользы, решение об уровне допуска.

**Готово, когда:** отчёт согласован, уровень допуска определён по таблице выше, выбраны этапы фазы 3.

### Этап 2.7. Параметры и объяснимость

**Цель:** чтобы человек мог настраивать систему и понимать рекомендации.

**Что сделать:**

- все параметры раздела 10 редактируются на своём уровне с переопределением на уровне SKU;
- журнал изменений параметров;
- по каждой рекомендации — раскрытие: дата риска, LT, SS и CV, H, прогноз остатка по дням, приходы внутри периода, уровень данных;
- выгрузка рекомендаций в Excel.

**Готово, когда:** любой параметр меняется без разработчика, изменение видно в журнале и в пересчёте на следующий день.

**Фаза 2Б. План сезона и правило последней поставки** — обязательная часть фазы 2.

### Этап 2.8. План поставок на весь сезон

**Что сделать:**

- план строится **хронологически по дате отправки** через все кластеры: на каждом шаге берётся ближайшая дата отправки среди всех кластеров, партии с одной датой распределяются по шагу 5 этапа 2.4, затем прогноз пересчитывается — и так до d_end. Получается план поставок по датам на весь сезон (пример 12);
- каждая моделируемая отправка плана уменьшает свободный остаток своего склада для следующих партий — даже если человек её ещё не принял. Один и тот же товар не может попасть в две партии;
- поступления от поставщиков добавляются к своему складу только в дату их доступности;
- ближайшая поставка — к исполнению, остальные — ориентир и вход для закупки (этап 4.1).

**Готово, когда:** при выполнении плана прогнозный остаток кластера не опускается ниже SS и спрос покрыт до d_end, кроме дней, где мешает нехватка товара или правило последней поставки. Сумма партий плана в любой день не больше свободного остатка своего склада на дату отправки.

### Этап 2.9. Правило последней поставки

Базовая проверка одной ближайшей партии — в этапе 2.4 (шаг 6). Этап 2.9 распространяет её на план сезона из нескольких партий (этап 2.8) и добавляет цену решения и иерархию ограничений.

**Что сделать:**

- продажи кластера распределяются по **FIFO**: сначала текущий остаток, затем партии в порядке прихода;
- единица партии считается проданной, если её списал заказ с датой до d_end включительно и этот заказ закончился нетто-выкупом — даже если выкуп произошёл после d_end;
- вернувшаяся единица (невыкуп или возврат после выкупа) возвращается в свою партию и снова доступна к продаже через τ_resell дней после физического прихода — так же, как в этапе 2.2;
- **доля продаж партии** нормируется на достижимый выкуп, иначе при нетто-выкупе от отгруженных ниже порога порог недостижим даже для партии, отгруженной полностью:

$$
\text{Доля продаж партии} = \min\left(1,\ \frac{\text{Нетто-продажи единиц партии}}{\text{Объём партии} \times b / (1 - c)}\right)
$$

- в рекомендации показываются обе величины: **обычная доля** (нетто-продажи партии / объём партии) и **нормированная**. Решение принимается по нормированной;
- если нормированная доля ниже порога — партия уменьшается до наибольшего объёма, кратного коробу, при котором порог выполняется; если такой объём меньше минимальной партии — партия не отправляется, причина указывается;
- порог партии и цель ST — разные ограничения. Порог касается только последних партий сезона, а ST — итога сезона, который поднимается за счёт повторных продаж возвратов в течение сезона. Достижимость цели ST проверяется отдельно (этап 1.12);
- плановая распродажа в v1 не моделируется: цель ST считается по итоговым нетто-продажам сезона;
- показывается цена решения: на сколько штук и какую закупочную стоимость изменились ожидаемый упущенный спрос и ожидаемый физический остаток после сезона.

Числовой пример — раздел 12, пример 7.

**Иерархия ограничений** (сверху — сильнее):

1. свободный товар на своём складе;
2. правило последней поставки;
3. кратность короба и минимальная партия;
4. уровень сервиса и период покрытия: до даты переключения (по умолчанию пик k) — целевой z и H, после — сниженные z и H (параметры).

Уровень сервиса никогда не отменяет запрет правила последней поставки.

**Готово, когда:** результаты на примере 7 раздела 12 совпадают, включая обе доли. Ближе к d_end рекомендации уменьшаются, система объясняет почему и показывает цену решения. Тест с несколькими партиями даёт доли продаж по FIFO, совпадающие с ручным расчётом.

## 8. Фаза 3. Уточнения

Каждый этап фазы 3 заменяет одно упрощение фазы 2. Этап берётся в работу, только если бэктест (этап 2.6) показал, что соответствующий источник ошибки заметен. После этапа бэктест повторяется. Уточнение включается, если улучшилась **его целевая метрика**, а критерии А, Б и В этапа 2.6 не ухудшились.

| Этап | Что уточняет | Делать, если бэктест показал | Целевая метрика |
| --- | --- | --- | --- |
| 3.1 | Распределение лагов вместо среднего | Ошибка прогноза остатка из-за сроков выкупа и возвратов | WAPE прогноза остатка кластера на горизонте LT |
| 3.2 | Матрица возвратов по складам | Невыкупы и возвраты часто приходят в другой кластер | WAPE прогноза остатка по кластерам |
| 3.3 | % выкупа по SKU и холодный старт | b заметно различается между размерами или артикулами | Ошибка b по SKU и критерий А |
| 3.4 | Разброс срока поставки | Дефициты из-за задержек поставок | Критерий В: дефицит при не большем остатке |
| 3.5 | Распределение дефицитного товара | Свой склад регулярно не покрывает все кластеры | Разброс дней покрытия кластеров после распределения и критерий В |
| 3.6 | Стабилизация рекомендаций | Рекомендации заметно меняются день ото дня | Доля рекомендаций, изменившихся на горизонте заморозки, при не худшем критерии В |
| 3.7 | Выбор склада внутри кластера | Сроки приёмки по складам кластера сильно различаются | Средний фактический срок приёмки |

### Этап 3.1. Распределение лагов

**Что сделать:** вместо средних лагов использовать распределения: какая доля выкупов, возвратов невыкупа и возвратов после выкупа наступает на 1-й, 2-й, … день после заказа (из этапа 1.9). Применять в прогнозе остатка (этап 2.2) и при расчёте ожидаемых выкупов открытых заказов (этап 1.11). Вероятность выкупа открытого заказа становится условной по его возрасту и вычисляется по распределениям лагов выкупа и невыкупа, без заранее заданного направления: с возрастом она может как падать, так и расти.

**Готово, когда:** сумма долей каждого распределения равна 100%. Сумма ожидаемых исходов по когорте равна числу заказов.

### Этап 3.2. Матрица возвратов

**Что сделать:** для каждого склада отгрузки — доли невыкупов и возвратов после выкупа, пришедших на каждый склад. Последние данные весят больше старых (окно — параметр). Использовать в прогнозе остатка вместо возврата в тот же кластер.

**Готово, когда:** доли в каждой строке дают 100%.

### Этап 3.3. % выкупа по SKU и холодный старт

**Что сделать:**

- человек назначает SKU-аналог;
- b, c и лаги считаются с переходом по уровням: SKU → артикул → аналог → категория → вручную;
- смешиваются **количества** по каждому исходу (отмены до и после отгрузки, невыкупы, выкупы, возвраты после выкупа) с одним и тем же весом, а доли и b вычисляются из смешанных количеств. Так сохраняется равенство b = β × (1 − r). Вес своих данных растёт с числом заказов n в зрелых когортах; для доли выкупа это выглядит так:

$$
b_{SKU} = \frac{n \times b_{own} + m \times b_{higher}}{n + m}
$$

m — параметр «вес уровня выше» в штуках.

**Готово, когда:** у нового SKU b равен уровню выше и плавно сдвигается к собственному по мере накопления заказов. При n = 0 и отсутствии всех уровней используется ручное значение.

### Этап 3.4. Разброс срока поставки

**Что сделать:** добавить разброс срока в страховой запас:

$$
SS = z \times \sqrt{\overline{LT} \times \sigma_D^2 + \bar{D}^2 \times \sigma_{LT}^2}
$$

σ_D = CV × D̄ из этапа 2.3; среднее и стандартное отклонение LT — из этапа 1.14. Для даты отправки используется **средний** LT, а не процентиль: риск задержки уже заложен в SS. Пока поставок в кластер меньше порога (параметр), используются ручные LT и σ_LT.

**Готово, когда:** видно, из каких поставок посчитаны LT и σ_LT. Переключение «ручной → факт» срабатывает на пороге.

### Этап 3.5. Распределение дефицитного товара

**Что сделать:** если своего склада не хватает на все кластеры, вместо простого правила этапа 2.4:

- распределять в коробах так, чтобы выровнять дни покрытия кластеров после прихода поставки;
- не разрывать размерную сетку: ключевые размеры артикула распределяются в первую очередь и в те же кластеры;
- правило последней поставки (этап 2.9) действует до распределения;
- если коробов меньше, чем кластеров с риском, коробы получают кластеры с самой ранней датой риска.

**Готово, когда:** на тестовом сценарии дни покрытия кластеров после распределения отличаются не больше чем на покрытие одного короба. Сценарий «коробов меньше, чем кластеров» отрабатывает по дате риска.

### Этап 3.6. Стабилизация рекомендаций

**Что сделать:**

- дни отгрузки на Ozon по неделе (параметр). Дата отправки сдвигается на ближайший день отгрузки раньше расчётной;
- предложенная рекомендация на ближайшие N дней (параметр) не меняется, если новое количество отличается от прежнего меньше порога (параметр);
- изменённая рекомендация помечается и показывает, что изменилось и почему.

**Готово, когда:** при небольших колебаниях факта рекомендации на горизонте заморозки не меняются.

### Этап 3.7. Выбор склада внутри кластера

**Что сделать:** предлагать склад внутри кластера по фактическому сроку приёмки (этап 1.14) и доступности слотов, если данные о слотах есть (этап 0.1).

**Готово, когда:** при прочих равных предлагается склад с меньшим сроком приёмки.

## 9. Фаза 4. Расширения

Этапы фазы 4 независимы друг от друга, порядок определяет бизнес. Зависимости — в разделе 1.

### Этап 4.1. Рекомендация закупки у поставщика

Здесь зафиксирован принцип расчёта. Детальные правила согласуются перед стартом фазы 4.

**Что сделать:**

- прогноз запаса SKU по датам до d_end: свой склад + Ozon + в пути на Ozon. Заказы у поставщика в начальный запас не входят и добавляются только в дату прихода. Баланс тот же, что в этапе 2.2: минус ожидаемые отгрузки, плюс возвраты, ставшие доступными, плюс приходы от поставщика;
- дата заказа = первый день, когда запас падает ниже суммарного SS, минус закупочный lead time. Если дата уже прошла — пометка «срочно»;
- объём — минимальный, при котором запас не ниже SS до d_end, с учётом минимального заказа у поставщика;
- объём ограничен сверху целью ST_total: итоговые нетто-продажи сезона / закуплено на сезон;
- если минимальный заказ у поставщика приводит к ST_total ниже цели, система не выбирает сама, а показывает два варианта: «заказать минимум» (ожидаемый остаток на d_end в штуках и закупочной стоимости) и «не заказывать» (ожидаемый упущенный спрос в штуках и закупочной стоимости);
- показывать сумму закупки в рублях по цене закупки.

**Готово, когда:** на тестовом SKU рекомендация совпадает с ручным расчётом. Конфликт минимального заказа и ST_total показывается двумя вариантами.

### Этап 4.2. FBS

**Что сделать:** для SKU с флагом FBS показывать, какой спрос закроет свой склад, пока в кластере дефицит до прихода поставки. FBS-заказы уменьшают доступный остаток своего склада в этапе 2.4.

**Готово, когда:** при дефиците в кластере видна доля спроса, покрытая FBS, и доступный остаток своего склада уменьшается на неё.

### Этап 4.3. Локализация в распределении

**Что сделать:** при распределении поставки между кластерами (этап 3.5) при прочих равных отдавать приоритет кластерам с локализацией ниже целевой. Правило последней поставки и выравнивание дней покрытия важнее локализации.

**Готово, когда:** при равных днях покрытия поставка уходит в кластер с худшей локализацией.

### Этап 4.4. Коррекция по скорости продаж

**Что сделать:**

- коэффициент = потенциальный спрос / прогноз за скользящие 7–14 дней с поправкой на сезонность, без промо-дней;
- сглаживание и коридор (минимум и максимум коэффициента) — параметры;
- коэффициент действует на горизонте не дальше LT, дальше — V_ост из этапа 1.11;
- **работа по исключениям:** коэффициент внутри коридора применяется автоматически; вне коридора — только после подтверждения человеком;
- в отчёте видны оба прогноза: без коррекции и с коррекцией.

**Готово, когда:** коэффициент вне коридора без подтверждения не меняет рекомендации. Бэктест с коррекцией точнее, чем без неё; иначе коррекция не включается.

### Этап 4.5. Промо-календарь

**Что сделать:**

- календарь акций Ozon и собственных промо: даты, SKU или категории, ожидаемый коэффициент подъёма спроса;
- прогноз заказов в дни акций умножается на коэффициент;
- промо-дни исключаются при расчёте базовой скорости, восстановленного спроса, сезонности из своей истории и коррекции (этап 4.4);
- после акции — отчёт: ожидаемый и фактический подъём.

**Готово, когда:** перед акцией рекомендации подсорта учитывают подъём спроса, а промо-дни не завышают базовую скорость.

### Этап 4.6. Ценовой индекс и алерт распродажи

**Что сделать:**

- по данным МПСтат прошлых сезонов индекс цены по неделям: медианная цена недели / медианная цена в начале сезона, по категории или аналогам;
- неделя, когда рынок обычно начинает снижать цены;
- алерт, если прогноз ST_total ниже цели **или** до начала рыночного снижения меньше X дней. Алерт говорит «пора начинать», размер скидки не предлагает.

**Готово, когда:** на данных прошлого сезона индекс показывает неделю начала снижения цен.

### Этап 4.7. Центр алертов

**Что сделать:** собрать предупреждения всех отчётов и рекомендаций в один список с приоритетом по стоимости под риском (требование 4.11).

| Алерт | Когда срабатывает | Источник |
| --- | --- | --- |
| Риск дефицита | Остаток упадёт ниже SS раньше, чем придёт ближайшая поставка | 2.2, 2.4 |
| Срочная отправка | Дата отправки уже прошла | 2.4 |
| Принятая не отправлена | Принятая рекомендация не отправлена дольше срока | 2.5 |
| Рваная сетка | В кластере нет ключевого размера | 1.8 |
| Риск затоваривания | Прогноз ST_total на d_end ниже цели | 1.12 |
| Отклонение от плана | Потенциальный спрос / план за окно вне коридора | 1.11 |
| Падение % выкупа | b упал больше порога | 1.9 |
| Последняя поставка | Правило запрещает или уменьшает отправку | 2.9 |

## 11. Рекомендации по реализации (не обязательны)

**Характер расчётов.** Математика простая: суммы по окнам, доли, процентили, стандартное отклонение, один квадратный корень. Машинного обучения и оптимизации в v1 нет. Сложность в объёме (например, 1 000 SKU × 30 складов × 180 дней — около 5 млн ячеек прогноза в день) и в аккуратности логики: состояния заказов и поздние события, сдвиги по лагам, дни без наличия, история на каждую дату, статусы рекомендаций.

**Где что считать:**

| Что | Где удобнее | Почему |
| --- | --- | --- |
| Отчёты фазы 1, когорты, доли кластеров, контроль качества | SQL в базе данных | Группировки и оконные функции по большим таблицам быстрее в базе |
| Прогноз остатка и рекомендации (фазы 2–3) | Основной язык команды | Пошаговую логику проще читать и тестировать в коде |
| Прототип формул и бэктест | Python (pandas) | Быстро проверить формулы на прошлом сезоне до продакшена |

**Практические правила:**

1. **Начать с этапа 0.2 сегодня.** Простой скрипт сохранения остатков стоит дёшево, а каждый пропущенный день — потерянная история для бэктеста.
2. **Прототип раньше продакшена.** Модель фазы 2А сначала собирается на Python по данным прошлого сезона. Расхождение прототипа и продакшен-расчёта на одних данных — критерий приёмки этапа 2.6.
3. **Отчёты фазы 1 — без интерфейса.** Если экрана в системе ещё нет, отчёты можно выдавать BI-инструментом или файлом Excel. Интерфейс делается, когда стабилизируется набор отчётов.
4. **Считать пакетами.** Прогноз считается сразу по всем SKU и дням, а не ячейка за ячейкой с отдельным запросом к базе.
5. **Хранить промежуточные результаты.** b, c, лаги, доли кластеров, LT, SS, CV, V_прогноз, V_ост и прогнозы дня сохраняются на каждую дату расчёта — для объяснимости, расчёта CV и бэктеста.
6. **Состояния — событиями.** Состояния заказов и статусы рекомендаций удобно хранить как журнал событий с датой, а текущее состояние вычислять. Тогда поздние события и пересчёт когорт задним числом получаются естественно.
7. **Тесты на маленьких примерах.** Числовые примеры раздела 12 — готовые автотесты; к ним добавляются граничные сценарии из требований 4.15 и 4.16.

**Когда понадобится Python в продакшене.** Если в следующих версиях появятся оценка эластичности или статистические модели спроса, их удобнее делать на Python отдельным сервисом. В v1 это не требуется.

| r | 6 / 60 | 0,10 |
| b | 0,60 × (1 − 0,10) | 0,54 (54 нетто-выкупа из 100) |
| Нетто-выкуп от отгруженных | 0,54 / 0,90 | 0,60 (54 из 90 отгруженных) |
| Возврат невыкупа от отгруженных | (0,05 + 0,25) / 0,90 | 0,333 (30 штук) |
| Возврат после выкупа от отгруженных | 0,60 × 0,10 / 0,90 | 0,067 (6 штук) |

Проверка: 10 + 5 + 25 + 60 = 100.

### Пример 2. Нетто-выкупы когорты с незавершёнными исходами (этап 1.11)

**2а. Обычная когорта.** Вчерашняя когорта: 120 заказов. Отменено до отгрузки 10, выкуплено 100, возвратов после выкупа пока 0, открыто и уже отгружено 10. К возрасту выкупа 1 день наступает 5% будущих возвратов после выкупа: F(1) = 0,05.

| Часть | Расчёт | Штуки |
| --- | --- | --- |
| Состоявшиеся нетто-выкупы S_факт | 100 − 0 | 100 |
| Будущие возвраты по выкупленным | (100 − 0) × 0,10 × 0,95 / (1 − 0,10 × 0,05) | −9,55 |
| Будущие выкупы открытых отгруженных | 10 × (0,60 / 0,90) × (1 − 0,10) | +6,00 |
| Ожидаемое изменение ΔS | 6,00 − 9,55 | −3,55 |
| **Оценка нетто-выкупов когорты** | S_факт + ΔS | **96,45** |

В ST входят S_факт = 100 и ΔS = −3,55 — каждая часть один раз. Если взять «оценку» 96,45 за состоявшуюся часть и снова добавить ΔS, получится 92,9: двойной счёт.

**2б. Много возвратов уже состоялось.** Выкуплено 100, уже возвращено 70, r = 0,8, F(a) = 0,5.

| Вариант | Расчёт | Будущие возвраты | Оценка нетто-выкупов |
| --- | --- | --- | --- |
| Условная формула v2.3 | 30 × 0,8 × 0,5 / (1 − 0,8 × 0,5) | 20 | 30 − 20 = 10 |
| Формула v2.2 | 100 × 0,8 × 0,5 | 40 | 30 − 40 = −10 (невозможно) |

**2в. Выкуп незадолго до таймаута.** Таймаут заказа — 45 дней, окно возврата — 30 дней. В когорте 100 выкупов совершены на 44-й день, оставшиеся открытые заказы на 45-й день помечены «закрыт по таймауту». Возраст выкупов a = 1, r = 0,1, F(1) = 0,05.

| Вариант | Ожидаемые будущие возвраты | Оценка нетто-выкупов |
| --- | --- | --- |
| v2.4: таймаут касается только открытых заказов | 100 × 0,1 × 0,95 / (1 − 0,1 × 0,05) = 9,55 | 100 − 9,55 = 90,45 |
| v2.3: когорта закрыта, ΔS = 0 | 0 | 100 (возвраты потеряны) |

### Пример 6. Страховой запас и объём партии с приходом внутри H (этапы 2.3, 2.4)

**Страховой запас:** CV = 0,3, спрос 20 заказов в день при c = 0,1, то есть D̄ = 18 отгрузок в день, LT = 9 дней, z = 1,65. SS = 1,65 × 0,3 × 18 × √9 = 26,73 → 27 шт. (округление вверх).

**Партия.** Интервал проверки — ровно H дней: от дня прихода до дня прихода + H − 1. Для простоты расход постоянный: спрос 20 заказов в день, отгрузки 18 шт., возвраты 4 шт. в день, чистый расход 14 шт. в день. Остаток на конец дня 0 — 200 шт. Поставка в пути 50 шт. приходит в начале дня 20. H = 14 дней, короб 12 шт.

| Шаг | Расчёт | Результат |
| --- | --- | --- |
| Остаток на конец дня n | 200 − 14 × n (+50 с дня 20) | день 12: 32; день 13: 18 |
| Дата риска | первый день с остатком < 27 | день 13 |
| Дата отправки | 13 − 9 | день 4, приход в начале дня 13 |
| Интервал проверки | дни 13–26 | 14 дней |
| Самый жёсткий день | день 26: 200 + Q + 50 − 14 × 26 ≥ 27 | Q ≥ 141 |
| Округление до коробов | 141 / 12 → вверх | 12 коробов = 144 шт. |

Если не учесть поставку в пути внутри H, получится Q ≥ 191 → 16 коробов = 192 шт.: на 48 шт. больше нужного. Если ошибочно включить в интервал день 27 (H + 1 дней), получится Q ≥ 155 → 13 коробов = 156 шт.

**При SS = 0** дата риска всё равно находится: на конец дня 14 остаётся 4 шт., в день 15 собственного остатка не хватает на спрос (C < D). Дата риска — день 15.

### Пример 7. Правило последней поставки (этапы 2.4, 2.9)

К приходу партии в кластере 40 шт. До d_end по заказам сезона будет отгружено 80 шт.; возвраты по ним приходят слишком поздно для повторной продажи. Нетто-выкуп от отгруженных b / (1 − c) = 0,60. Порог 70%, короб 12 шт., минимальная партия 24 шт.

| Вариант | Расчёт по FIFO | Обычная доля | Нормированная доля | Решение |
| --- | --- | --- | --- | --- |
| Партия 60 шт. | Первые 40 отгрузок — из текущего остатка, следующие 40 — из партии. Нетто-продажи партии: 40 × 0,6 = 24 | 24 / 60 = 40% | 24 / (60 × 0,6) = 66,7% | Ниже порога — уменьшить |
| Наибольший проходной объём | 40 / Q ≥ 0,7 → Q ≤ 57 | — | — | Округление вниз до коробов |
| Партия 48 шт. | Из партии отгружено 40, нетто-продажи 24 | 24 / 48 = 50% | 24 / (48 × 0,6) = 83,3% | Отправить 48 шт. |

Без нормировки доля даже для партии 40 шт., отгруженной полностью, была бы 24 / 40 = 60% и никогда не достигла бы порога 70%: правило запрещало бы любую позднюю поставку для товара с выкупом ниже 70%.

### Пример 10. Сквозной баланс товара за сезон (этапы 1.11, 2.2, 1.12)

Один кластер, без переносов и списаний; доли — из примера 1. На начало d_start доступно 100 шт.; в резерве 50 неотгруженных заказов, сделанных **до d_start** (досезонные). | --- | --- | --- | --- | --- |
| Старт: доступно 100 + поставка 50 | — | — | — | 150 |

| Цикл 2: 100 заказов, 90 отгружено | 90 | 54 | 36 | 119 − 90 + 36 = 65 |
| Цикл 3: 50 заказов, 45 отгружено | 45 | 27 | 18 (после d_end) | 65 − 45 + 18 = 38 |

**Итог сезона:**

| Показатель | Расчёт | Результат |
| --- | --- | --- |
| Нетто-продажи сезона | 54 + 54 + 27 | 135 |
| Закуплено на сезон | 100 (доступно на d_start) + 50 (поставка) + 5 (отмены досезонных) + 18 (возвраты досезонных) | 173 |
| ST_total | 135 / 173 | ≈ 78% |
| Баланс сезона | 173 = 135 + 38 | сходится |
| Баланс всего товара | 200 = 27 (досезонные продажи) + 135 + 38 | сходится |

Тот же баланс должен выполняться в прототипе на любых данных без списаний.

## 14. Приложение. История версий

**Что изменилось по сравнению с v1:**

| Было в v1 | Стало в v2 |

| Первая польза на этапе 14 из 23 | Отчёты для ручного планирования с фазы 1 |

**Что изменилось в v2.1 (по итогам рецензии):**

- единая временная основа: план, спрос и сезонность — по дате заказа (раздел 3);
- модель состояний заказа, отмены, оба вида возвратов как отдельные потоки прихода (раздел 3, этапы 1.2, 1.9, 2.2);
- точная формула оставшегося спроса сезона (этап 1.11);
- разделены потенциальный спрос, фактические и ожидаемые продажи; распроданность считается только по продажам (раздел 3, этапы 1.11, 1.12);
- подсорт по балансу всего периода покрытия, распределение сразу в коробах (этап 2.4);
- новое определение CV для страхового запаса (этап 2.3);
- статусы рекомендации и резерв своего склада (этап 2.5);
- протокол бэктеста: отложенный период, пороги до запуска, теневой режим (этап 2.6);
- план сезона и правило последней поставки стали обязательными (фаза 2Б), добавлены FIFO и иерархия ограничений (этап 2.9);
- закупка у поставщика по временному балансу запасов (этап 4.1);
- правила восстановления спроса, дня частичного наличия и переноса спроса при общем дефиците (этапы 1.7, 2.2);
- обязательные тестовые сценарии, эксплуатационные требования, единая база оценки ущерба (раздел 4);
- единый справочник параметров (раздел 10).

**Что изменилось в v2.2 (по итогам второй рецензии):**

- дата риска срабатывает и по непокрытому спросу, а не только по страховому запасу (этап 2.4);

- итоговые нетто-продажи сезона отделены от физического остатка; доля продаж партии нормирована на достижимый выкуп (раздел 3, этапы 1.12, 2.9);

- спрос и наличие — по кластеру покупателя; календарь расчёта в московском времени (раздел 3);
- свой склад в плане сезона, просроченные принятые рекомендации, необъяснённые расхождения данных, воспроизводимость бэктеста (этапы 1.5, 2.5, 2.6, 2.8);
- сквозные числовые примеры (раздел 12).
