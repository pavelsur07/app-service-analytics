# Переход продаж FBO на `/v3/posting/fbo/list`

**Дата:** 2026-10-21
**Модуль:** Ingestion
**Риск ревью:** high — Claude + оба прохода Codex (Ingestion: идентификация
фактов, идемпотентность)
**Статус:** решения 1–3 согласованы владельцем 2026-10-21; исполнение по этапам

## Проблема

С 2026-10-19 ~06:24 UTC Ozon отвечает на `POST /v2/posting/fbo/list`:

```
HTTP/2 400 {"code":9,"message":"obsolete method cannot be used"}
```

Затронуты оба подключения и все дни окна загрузки (GlitchTip #438, 749+
событий). Тело ответа видно в `marketplace_day_load.failure` после PR #238.
Ozon объявил замену на `/v3/posting/fbo/list` с 31.08.2026.

Последствия сейчас:

- **продажи и статусы отправлений** не обновляются с 19.10: заказов 19–21.10
  у нас нет, статусы «в пути → доставлен» за последний месяц застыли;
- **подключение нового кабинета и замена ключей** не проходят: проба
  ключей (`ConnectOzonAccountAction`, `ReplaceOzonCredentialsAction`)
  вызывает тот же метод и получит 400;
- контроль свежести должен был сработать по продажам (порог 36 ч).

Остальные методы Ozon в коде (`v1/analytics/stocks`, `v1/finance/accrual/by-day`,
`v1/returns/list`, `v3/product/list`, `v3/product/info/list`) не затронуты.

## Что известно о v3 (по живым фикстурам 2026-10-21)

Фикстуры сняты владельцем-ключом, только чтение, в
`api/tests/Fixtures/Marketplace/ozon/`:

| Файл | Отправлений | Назначение |
|---|---|---|
| `posting-fbo-list-v3-2026-07-01-page-001.json` | 86 | тот же день, что v2-фикстура `posting-fbo-list-2026-07-01.json` |
| `posting-fbo-list-v3-2026-10-19-page-001/002.json` | 100 + 5 | пагинация с данными на второй странице |
| `posting-fbo-list-v3-2026-10-20-page-001/002.json` | 100 + 0 | ровно 100 и пустая вторая страница с `has_next=false` |

Запрос:

```json
{"cursor":"","dir":"ASC","filter":{"since":"…+03:00","to":"…+03:00"},
 "limit":100,"translit":true,"with":{"analytics_data":true,"financial_data":true}}
```

Отличия от v2:

| | v2 | v3 |
|---|---|---|
| Обёртка ответа | `{"result":[…]}` | `{"postings":[…],"has_next":bool,"cursor":"…"}` |
| Пагинация | `offset`, `limit` ≤ 1000 | `cursor`, `limit` ≤ 100 |
| Комиссия товара | `financial_data.products[].commission_amount`, `commission_percent`, `currency_code` | `financial_data.products[].commission: {amount, percent, currency}` |
| Цена в `products[]` | `price: "2073.00"`, `currency_code` | `price: {amount: "2073", currency: "RUB"}` |
| Новые поля | — | `cancellation`, `external_order`, `is_extra_packed`, `is_sealed`, `storage_type` |

**Сверка v2 ↔ v3 на 01.07, 86 отправлений:** совпадают состав отправлений,
`posting_number`, `products[].sku`, `quantity`, `status`, `created_at`,
`in_process_at`, `financial_data.products[].price`, `product_id`, `payout`
и комиссия (сумма, процент, валюта) — расхождений 0.

Следствие: `source_row_id = posting_number|sku` и бизнес-дата по
`in_process_at` (ADR-009) на v3 дают те же ключи. Переход не создаёт
второй строки факта, перезагрузка окна обновляет существующие.

Проверка §9 по фикстурам: `legal_info` пуст во всех отправлениях, полей
с ФИО, телефоном, адресом, почтой покупателя нет; из доставки — город.
Ключа в файлах нет; `set-cookie` из `.headers` убран.

## Решения (согласованы 2026-10-21)

1. **Новый ADR-042 «Ozon: источник продаж FBO — `/v3/posting/fbo/list`».**
   ADR-009 прямо называет источником `/v2/posting/fbo/list` и обосновывает
   выбор тем, что метод «живёт годами». Принятый ADR не редактируется, так
   что смену источника записываем новым ADR. ADR-042 уточняет ADR-009:
   состав `source_row_id` и правило бизнес-даты не меняются (доказано
   сверкой выше), меняются только источник, пагинация и форма полей.
   *Альтернатива — без ADR — отвергаю: решение против принятого ADR без
   записи запрещено правилами.*

2. **Тип отчёта raw остаётся `ozon_posting_fbo_list`, тела двух форматов
   читаются обоими парсерами.** В raw-слое уже лежат тела v2: на них
   работают `BackfillOzonPostingStatusesCommand` и история выкупа
   (`OzonPostingRawHistoryQuery`, ADR-019/029). Raw неизменяем, поэтому
   парсеры различают формат по ключу верхнего уровня (`result` — v2,
   `postings` — v3) и разбирают оба. Отметки дня, контроль свежести,
   покрытие данных и дашборд завязаны на этот тип и не меняются.
   *Альтернатива — новый тип `ozon_posting_fbo_list_v3`: история выкупа,
   свежесть, покрытие и backfill стали бы читать два типа, а каждый
   потребитель — знать о версии метода. Дороже и без выигрыша.*
   Миграции схемы нет.

3. **Raw-документ на страницу, факты — после последней страницы.**
   Тот же порядок, что у возвратов (`FetchOzonReturnsHandler`): каждая
   страница сохраняется в raw до разбора; факты и статусы записываются
   в одной транзакции, когда `has_next=false`; отметка `completed` — только
   после этого. Отказ посреди листания: raw страниц остаётся, фактов
   за день нет, отметка `failed`. Уникальный ключ raw
   `(company, account, report_type, period, body_hash)` пропускает
   несколько страниц одного дня без изменений.
   Защита: потолок страниц на день (50 = 5000 отправлений, с запасом
   в 50× к нынешним объёмам) — громкий отказ при превышении; повтор
   курсора и `has_next=true` без курсора — отказ.
   `refuseSilentTruncation` (потолок 1000 в одном ответе) удаляется:
   пагинация заменяет его.

Остального в списке согласования нет: новых зависимостей, Facade,
изменений очереди и маршрутизации, контракта API фронтенда и схемы БД
не будет.

## Вне объёма (отдельными задачами)

- `OzonPostingFboListParser::money()` переводит сумму через `float`
  (`number_format`) — нарушение §3, существующее до этой задачи. В v3
  `price` и `commission.amount` приходят целыми, так что переход точность
  не ухудшает. Перевод на строковый разбор — отдельной задачей.
- Ответ Ozon с телом в отметке отказа (PR #238) сделан только для продаж;
  для остальных выгрузок — по мере надобности.
- Ozon анонсировал переход FBS на `/v4/posting/fbs/*` — FBS мы не грузим.
