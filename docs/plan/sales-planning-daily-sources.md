## A01. Исходы и правило учёта заказов

Источники: [ADR-019](../adr/0019-ozon-buyout-rate-sources-and-history.md),
[ADR-020](../adr/0020-ozon-buyout-rate-query-plan.md),
[ADR-029](../adr/0029-ozon-buyout-cohort-maturity.md),
[определение view](../../api/migrations/Version20260925150000.php),
[чтение исходов](../../api/src/Ingestion/Infrastructure/Query/Buyout/BuyoutOutcomeQuery.php).

| Исход / состояние | Значение | В «Заказали» без T1 | В состоявшихся нетто-продажах |
|---|---|---|---|
| T1 | Подтверждённая отмена до передачи в доставку | Исключить только аллоцированное количество | 0 |
| D | Доставленная и ещё не возвращённая часть количества | Включить | Количество D |
| T2 | Подтверждённый невыкуп после передачи | Включить | 0 |
| P | Частичный невыкуп конкретной SKU при выкупленном sibling | Включить | 0 |
| R | Количество клиентского возврата после доставки | Включить | 0; повторно из D не вычитать |
| active | Известный активный статус без исхода | Включить; отметить незавершённость | Пока 0, возможен прогноз |
| unknown | Нераспознанный исход или недостаточная история | Включить с явным качеством | Нет доказанной продажи и нет выдуманного исхода |

Active и unknown имеют outcome=NULL, а не два новых значения outcome.
Не все строки NULL прогнозируемы: is_forecast_eligible учитывает активность
и противоречивые возвратные данные. Активность сама по себе не гарантирует ставку обучения.

### Доказательство передачи и отмены

Действующая граница handover — первое наблюдение delivering.
awaiting_deliver, в том числе posting_transferring_to_delivery, передачу
не доказывает. Terminal cancelled без достаточного наблюдения до передачи
не превращается автоматически в T1; исход остаётся неизвестным.
Классификация использует историю и точный справочник причин, а не только
текущий sales_fact.status или cancel_reason_id.

Расчёт заказов использует готовый исход T1 из view, не повторяет
классификатор в SalesPlanning и не вычитает ожидаемые будущие T1 из факта.

### Количества и даты

Факт может делиться на несколько аллокаций исходов. Сумма аллокаций
равна исходной quantity. Частичный возврат не делает всю строку R.
Один возврат распределяется один раз по строкам order/SKU с учётом tenant
и кабинета; join по одному order_number без company/account запрещён.

rawOrderedQuantity = сумма всех количественных аллокаций;
preHandoverCancelledQuantity = сумма количества T1;
effectiveOrderedQuantity = rawOrderedQuantity − preHandoverCancelledQuantity.

D уже исключает количество R внутри доставленной строки. При исходных
трёх доставленных штуках и возврате одной D=2, R=1, нетто=2, а не 1.
Дата когорты — business_date заказа в МСК; дата отмены/выкупа/возврата
уточняет исходную когорту. Поздние исходы не изменяют исходную цель плана.

Условный процент выкупа D/(D+T2+P) не равен D/effectiveOrderedQuantity.
Не умножать effectiveOrderedQuantity на условный процент ради расчёта продаж.

### Проверка

Сопоставлено с BuyoutOutcomeQueryTest: смешанные заказы и изоляция,
частичный возврат, распределение возврата по нескольким postings,
разные причины отмены, консервативная классификация при разной истории.
Результат запуска integration записывается в журнал задачи после завершения.

## A03. Доступность входных данных

| Данные | Источник кода | Что подтверждено / ограничение |
|---|---|---|
| Количество и дата заказа | SalesFact, BuyoutOutcomeQuery | Штуки, бизнес-дата МСК; исходы распределяются количественно |
| Цена и валюта | SalesFact.amountMinor/currency, денежный BuyoutDailyQuery | amountMinor применяется за штуку: сумма quantity × amountMinor; это оценка продажи, не payout |
| История стадии отправления | MarketplacePostingStatus.observedAt | Неизменяемые наблюдения; это время наблюдения, а не точное событие площадки |
| Выкуп и его время | delivered-наблюдения, resolved_at, resolution_observed | Первый известный terminal без предыдущего наблюдения не доказывает точный момент закрытия; это важно для обучения |
| Количество клиентского возврата | MarketplaceReturnFact.quantity, returnType | Доступны текущие данные и естественный ключ returns.id; аллокация к order/SKU внутри компании/кабинета |
| Время возврата | visualStatusChangedAt, firstLoadedAt | Изменение визуального статуса и первое появление; не универсальная точная дата фактического возврата товара |
| Полнота загрузки дня заказов | MarketplaceDayLoad, DayLoadSql | completed_at и failed_at для типа отчёта/дня; старые raw без явной отметки требуют осторожности |
| Полнота возвратов | FetchOzonReturnsHandler, MarketplaceDayLoad для OzonReturnsList и raw-документы окна | Успех дневной загрузки postings не доказывает полноту хвоста возвратов когорты; успех/отказ помечаются на каждый день окна возвратов, но это иная временная ось |
| Исторический срез статусов | buyout_outcome_as_of, status observed_at | История статусов фильтруется по моменту наблюдения |
| Исторический срез quantity/price/returns | buyout_outcome_as_of, writers upsert | Фильтр first_loaded_at не восстанавливает прежние значения изменившейся строки; универсальный исторический money/net-backtest не доказан |

Domain/MarketplaceDayLoad.php, Infrastructure/Query/DayLoadSql.php,

### Следствия для реализации

1. Этап A может использовать текущие количества, наблюдаемые исходы и
   денежную оценку по цене исходной строки, явно называя методику.
2. Нулевой день подтверждается полнотой нужного источника, а не отсутствием строк.
   Отсутствующий или failed-прогон не превращается в нулевой результат.
3. Качество возвратов — отдельная ось; не назначать всей когорте complete
   только на основании completed_at дневной выгрузки заказов.
4. Этапу B нужны определение возвратного горизонта, пригодность наблюдений
   и защита от незавершённых хвостов. Наличие поля visualStatusChangedAt
   само по себе не завершает эту работу.
5. Честный исторический backtest денег и нетто требует неизменяемых ревизий
   либо сохранённых входных срезов. До этого можно проверять синтетические
   сценарии и накапливать прогнозы вперёд во времени; нельзя утверждать,
   что универсальная историческая проверка уже доступна.
6. Производительность текущего BuyoutDailyQuery с деньгами ограничена
   1 SKU / 31 днём; для сезона нужен bounded пакетный контракт, без N+1.

Это ограничения кода, не новая внешняя зависимость. Реальные данные
и ключи площадки при исследовании не использовались.
