# product-research-ozon — этап 8: приёмка и эксплуатация

Дата: 02.11.2026. Статус: подготовительная часть реализована; весь этап 8 остаётся открытым.
Основание: ADR-050, завершённые этапы 0–7.

## Цель

Подготовить воспроизводимую эксплуатацию и ограниченный выпуск. Сохранить
сырые месяцы и company/source изоляцию при сбое, восстановлении и выключении.
Автоматические тесты используют только сохранённые фикстуры. Фактический запуск
на MPStats и сведения о тарифе не подменяются успешным тестом.

## 8.1. Ограниченное включение и конфигурация

Цель: случайное включение глобального флага не открывает research всем компаниям.

Задачи:
- Единый company allowlist Symfony для availability и всех research data routes;
  существующий общий флаг сохраняется, пустой/невалидный список закрывает доступ.
- Python использует тот же явно заданный список; права seller и service token
  проверяются независимо. Публичного Python route/host port не добавлять.
- Подготовить отдельную production compose-конфигурацию сервиса с выключенным
  профилем по умолчанию и проверкой настроек до запуска. Секреты вне Git:
  отдельная роль/БД, отдельные права S3 на research prefix, directional tokens.
- Runtime image и проверка ревизии миграций; миграция отдельным операторским
  шагом, без автоматического применения. Без конфигурации текущий prod работает.

Готовность / TDD:
- [x] A01: global false, empty allowlist, foreign company закрыты; pilot открыт.
- [x] A02: невалидные ID/config не превращаются в unrestricted mode; нет утечки секретов.
- [x] A03: публичный internal route закрыт; токен другого направления отклоняется.
- [x] A04: dry-run production topology и disabled deploy не требуют настоящих секретов.

## 8.2. Восстановление, наблюдаемость и хранение

Цель: операционные доказательства сохранности связей DB → неизменяемый raw.

Задачи:
- Company/source scoped диагностика ограниченного окна: статусы, задержка,
  ошибки, происхождение API/cache; без сумм, SKU, тел, ключей и full table COUNT.
- Runbook согласованной остановки relay/worker, backup обеих БД, восстановления
  в изолированный контур и проверки связанных страниц/манифеста по SHA-256.
- Проверить восстановление реальным pg_dump/pg_restore на одноразовом local
  PostgreSQL, не перезаписывая dev/test или production БД.
- Current raw без TTL; snapshots проектов сохраняются весь срок. Orphan сырьё
  сохраняется до отдельного безопасного GC; автоматическое удаление не включать.
- Лимит хранилища и оповещения задаются до live включения, значения не изобретать.

Готовность / TDD:
- [x] O01: диагностика company/source scoped, bounded, различает cache/errors/late.
- [x] O02: dump → isolated restore → exact raw read + tenant denial подтверждены.
- [ ] O03: rollback сохраняет проекты/DB/raw; нет незаметного current expiration.
- [ ] O04: предупреждения задержки/ошибок/лимита и их доставка проверены.

## Входные данные и границы

Pilot компания подтверждена владельцем; allowlist сохранён вне Git на сервере,
при выключенном общем флаге. Для seller пока нет активного Ozon подключения
(ADR-021); gate сохраняется. Запрошены подтверждённые RPM/доступный API объём тарифа,
защищённое размещение production MPStats и отдельного S3 ключа, допустимые
rows/bytes/storage budget. На старте этапа в production не было RESEARCH_*/MPSTATS_*
значений; GitHub Secret MPSTATS_API_TOKEN существует, но его значение не читается.
Наличие старого тестового секрета не подтверждает действующий тариф/валидность.

CLAUDE.md «Периметр автономной работы» запрещает агенту самостоятельно обращаться
к реальному кабинету площадки; получение новых исходных данных выполняется
оператором отдельно. Историческое разрешение на фикстуры не расширяется на новые
живые обращения. Пока входные данные/внешние ресурсы не готовы, флаг остаётся
false, live-критерии остаются открытыми. Это незавершённость этапа8, а не PASS.

Новых зависимостей, межмодульных Facade, Messenger transports и аналитических
таблиц не требуется. Текущие v1/v2 schemas и frontend payloads не меняются.
