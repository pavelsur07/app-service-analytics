# План модуля «Планирование продаж»: Этап 0

Подробный порядок и планы отдельных задач: [Этап 00](sales-planning-stage-00.md).

## Цель и границы

Первый выпуск даёт менеджеру оперативный план-факт по SKU: дневной план, заказы, подтверждённые выкупы, прогноз из незавершённых заказов, сигнал отклонения, доступный остаток, скорость продаж и дни покрытия. Расчёты должны быть объяснимыми и сохраняться для сравнения прежнего прогноза с последующим результатом. Прогноз спроса на ещё не созданные заказы в этот этап не входит.

| Решение | Первый выпуск |
| --- | --- |
| Площадка и схема | Ozon FBO |
| Единица плана | Компания + кабинет + SKU площадки + дата заказа |
| Факт в строке даты | Подтверждённые выкупы заказов, созданных в эту дату |
| Возврат после выкупа | Отдельное событие; состоявшийся выкуп из факта не удаляется |
| Дата для скорости | Дата получения подтверждения; скорость явно обозначена как оценка |
| Остаток | Доступное для продажи количество |
| Товар в пути к клиенту и обратно | Следующий самостоятельный этап модуля остатков |

Например, заказ создан 10 сентября, а выкуп подтверждён 14 сентября. Его факт относится к строке плана **10 сентября**. Для скорости по подтверждениям он относится к **14 сентября**. Дата заказа, дата события источника (если она известна) и время наблюдения сохраняются раздельно.

## Границы модулей и предварительные задачи

### Существующий `Ingestion`: исходные данные

В проекте уже есть карточки товаров, отправления Ozon FBO, история статусов, возвраты и классификация исходов. Таблица `sales_fact` содержит отправления с разными статусами: её название не делает каждую строку подтверждённой продажей.

`Ingestion` отвечает за обращения к API, сохранение raw-ответов, нормализацию заказов и остатков, историю статусов, исправления источника, полноту загрузки и защиту от дублей. Отдельный модуль исполнения заказов для Этапа 0 не нужен.

**Задача I-1 — данные заказов для Planning.**

- [ ] Через узкий пакетный контракт `IngestionPlanningFacade` выдавать количества созданных, незавершённых, выкупленных и завершённых без выкупа единиц для компании, кабинета, SKU и периода.
- [ ] Отдельно выдавать неизвестные и противоречивые исходы; сохранять ссылки на исходные данные, время подтверждения и признак полноты загрузки.
- [ ] Различать регулярное наблюдение и историческую дозагрузку, чтобы старые результаты не стали сегодняшними продажами.
- [ ] Обеспечить повторную загрузку и исправления источника без дублирования единиц.

**Критерий:** судьба каждой единицы контрольного заказа проверяется по исходным данным; сумма известных и неизвестных состояний равна заказанному количеству.

**Задача I-2 — источник остатков Ozon FBO. Обязательна перед INV-1.**

Для `/v1/product/info/stocks-by-warehouse/fbo` уже [сохранены две страницы сырого JSON](../task/ozon-fbo-stock-source-research.md): в них есть `warehouse_id`, `present` и `reserved`. Какой показатель соответствует «доступно к продаже», ещё нужно подтвердить сверкой с кабинетом.

- [ ] Подтвердить по актуальному источнику Ozon точный метод, поля, полноту и смысл доступного остатка FBO.
- [ ] Добавить в Ingestion чтение и нормализацию полного снимка остатков, включая время наблюдения и ссылку на raw.
- [ ] Не публиковать частичный снимок после ошибки страницы или разбора; одинаковый ответ при новом опросе подтверждает свежесть.

**Критерий:** источник доступного остатка доказан и полный снимок можно получить отдельно для каждого кабинета. Подробный план — в [Этапе 00](sales-planning-stage-00.md).

### Новый `Inventory`: остатки товаров

`Inventory` определяет смысл доступного остатка, хранит текущие и исторические снимки, разделяет склады и состояния товара. Данные площадки загружает `Ingestion`; `Inventory` получает их через узкий `IngestionStockSourceFacade` и публикует собственный контракт чтения.

**Задача INV-1 — доступный остаток. Обязательна для Этапа 0.**

- [ ] Исследовать источник Ozon и зафиксировать точное поле или формулу доступного остатка; сверить с контрольным отчётом площадки.
- [ ] Проверить семантику резерва: уже исключённый из доступного остатка резерв нельзя вычитать второй раз.
- [ ] Разделить кабинет, SKU и схему исполнения; склад учитывать отдельным измерением, только если источник его предоставляет. Суммировать только совместимые доступные остатки FBO.
- [ ] Хранить снимки с временем наблюдения, источником и признаком полноты.
- [ ] Выдавать через `InventoryFacade` количество, время снимка и качество данных. Подтверждённый ноль должен отличаться от отсутствия данных.

**Критерий:** отображаемый остаток совпадает с определённым источником и не увеличивается за счёт резерва или товара в пути. Пока поле источника не проверено, показатель нельзя публиковать под названием «доступный остаток».

**Задача INV-2 — товар в пути. Выполняется отдельно после Этапа 0.**

- [ ] Добавить количества в пути к клиенту, от клиента на склад и уже вернувшихся, но пока недоступных товаров.
- [ ] Для каждого состояния определить источник, начало, завершение, частичное количество и обработку поздних исправлений.
- [ ] Возвращать товар в доступный остаток только после подтверждённой приёмки, а не по одной отмене заказа.

**Критерий:** физическая единица не учитывается одновременно в несовместимых состояниях.

### Новый `Planning`: планы и расчёты

`Planning` владеет планом, импортом, настройками расчётов, процентом выкупа для планирования, прогнозом, сигналами, скоростью, днями покрытия и историей расчётов. Предметные исходные данные он получает только через `IngestionPlanningFacade` и `InventoryFacade`. Обратных вызовов из источников в Planning нет.

```text
Planning → IngestionPlanningFacade → заказы, исходы, карточки
Planning → InventoryFacade → доступный остаток
Inventory → IngestionStockSourceFacade → исходные данные об остатках
Planning → IdentityAccountScopeFacade → принадлежность кабинета компании
```

Границы закреплены [ADR-024](../adr/0024-sales-planning-and-inventory-boundaries.md); Deptrac будет дополнен вместе с кодом. Отдельный `IdentityAccountScopeFacade` проверяет кабинет и не открывает Planning действующий Facade с ключами API. Прямые SQL-запросы из Planning к чужим таблицам не допускаются.

Общий `Catalog` понадобится при объединении одного товара из нескольких кабинетов и площадок. Модели спроса, закупки и распределение по складам также остаются самостоятельными будущими задачами; пустые модули под них заранее не создаются.

## Правила расчётов

### Состояния и процент выкупа

Расчёты ведутся в единицах товара, а не в количестве заказов или отправлений. Для одной когорты:

```text
Заказано = выкуплено + завершено без выкупа
         + незавершено и пригодно для прогноза
         + неизвестно / противоречиво
```

Одна единица не может одновременно попасть в факт и прогноз. Частичный результат распределяется по количеству. Неизвестные состояния не считаются ни отменой, ни обычной доставкой; оценка с такими данными помечается неполной.

Для Planning используется отдельный коэффициент:

```text
Процент выкупа = выкупленные единицы /
                 все единицы с достоверно известным результатом
```

В знаменатель входят отмены до доставки. Незавершённые и неизвестные исходы исключены. Последующий возврат не отменяет состоявшийся выкуп. Окно определяется датой получения достоверного результата; повторное наблюдение не переносит результат на новую дату.

В ADR-020 уже закреплён иной показатель Ozon с разделением стадий доставки. Новый ADR должен назвать методику Planning отдельно и не менять существующий экран выкупа.

| Начальная системная настройка | Значение |
| --- | ---: |
| Окно процента выкупа | 30 завершённых календарных дней |
| Минимальная выборка для собственного процента | 30 завершённых единиц |
| Резервный процент при малой выборке | 80% |
| Окно скорости | 14 завершённых календарных дней |
| Зелёная зона | Выполнение от 95% |
| Жёлтая зона | Выполнение от 80% до 95% |
| Красная зона | Выполнение ниже 80% |
| Плановый интервал обновления | 15 минут |
| Порог устаревания данных | 60 минут |

Эти стартовые значения являются продуктовым допущением. Они хранятся в версионируемой конфигурации, а не вшиваются в формулы. Пользователь видит применённый процент, окно, размер выборки и источник: собственный или резервный.

### Прогноз и сигнал

Для SKU и даты заказа:

```text
Прогноз незавершённых продаж = пригодное незавершённое количество × процент выкупа
Ожидаемый результат = подтверждённый факт + прогноз незавершённых продаж
Отклонение, шт. = ожидаемый результат − план
Выполнение, % = ожидаемый результат / план × 100
```

Коэффициент не применяется к уже подтверждённому факту. Расчёты выполняются с фиксированной точностью; округление отображаемого прогноза производится после суммирования, до одного знака после запятой. Сигнал определяется по значению до округления.

- План отсутствует: «План не задан», процент и сигнал не показываются.
- План равен нулю: показывается абсолютное отклонение, без деления на ноль и обычного цветового сигнала.
- Будущая дата: «Ожидается»; отсутствие заказов не окрашивается красным.
- Текущий день: предварительная оценка относительно полного дневного плана.
- Источник устарел, неполон или содержит неизвестные исходы: статус качества данных вместо достоверного зелёного, жёлтого или красного сигнала.

### Скорость и дни покрытия

```text
Скорость = подтверждённые выкупы за окно / число календарных дней окна
Дни покрытия = доступный остаток / скорость
```

Дни без продаж входят в окно, если загрузка за них была полной. Скорость называется «Скорость по подтверждённым выкупам, оценка»: при отсутствии точного времени выкупа берётся дата первого подтверждения системой. Историческая дозагрузка не создаёт всплеск скорости сегодня. Пока нет полного окна регулярных наблюдений или проверенной истории, выводится «Недостаточно данных».

| Состояние | Значение дней покрытия |
| --- | --- |
| Актуальный остаток равен нулю | `0`, «Нет доступного товара» |
| Остаток и скорость положительные | Расчётное значение |
| Остаток положительный, скорость равна нулю | «Нет продаж за период» |
| История скорости неполная | «Недостаточно данных» |
| Остаток неизвестен или устарел | «Нет актуальных данных» |

Дни покрытия — оценка без будущего пополнения и без моделирования перемещений товара.

### История и согласованность

Текущая оценка когорты меняется вместе со статусами. Отдельный исторический снимок сохраняет то, что пользователь видел в момент расчёта: версию плана, количества по состояниям, коэффициент и выборку, настройки и версию алгоритма, прогноз, факт, сигнал, снимок остатка, ссылки на источник и качество данных.

Повтор обработки тех же входов не создаёт дубль. Изменение входов создаёт новый снимок, не переписывая предыдущий. Новая версия публикуется целиком после успешного расчёта. При сбое остаётся прежняя версия с признаком устаревания; новые заказы нельзя показывать вместе со старым сигналом как единый расчёт. Время обновления заказов и остатков показывается раздельно.

## Интерфейсы, проверки и критерий готовности

Seller API располагается под `/api/companies/{companyId}/planning` и предоставляет: выбор SKU, чтение и изменение плана с версией, предварительную проверку и применение импорта, дневной отчёт и историю снимков. В ответах `0`, отсутствие данных и неполный результат различаются явно. Методы чтения данных компании принимают `companyId` первым параметром и требуют кабинет; списки ограничены, растущая история использует keyset-пагинацию.

Планы записываются ORM, расчётные факты и снимки — DBAL с уникальными ключами и безопасной повторной записью. Каждая таблица имеет Entity для описания схемы. OpenAPI и TypeScript генерируются из источника; существующий контракт экрана выкупа Ozon не выдаётся за методику Planning.

### Контрольные сценарии

| Сценарий | Ожидаемый результат |
| --- | --- |
| Заказано 10; выкуплено 4; отменено 2; незавершено 4; коэффициент 75% | Факт 4, прогноз 3, ожидаемый итог 7 |
| План 10 при ожидаемом итоге 7 | Выполнение 70%, отклонение −3, красный сигнал |
| Незавершённые единицы выкуплены | Выходят из прогноза и входят в факт один раз |
| Возврат после выкупа | Факт выкупа сохраняется; доступный остаток меняется после подтверждения Inventory |
| Выборка менее 30 единиц | Резервный процент и понятная подпись |
| Историческая дозагрузка | Нет всплеска сегодняшней скорости |
| Неизвестный или противоречивый статус | Неполная оценка без обычного цветового сигнала |
| Сбой последней страницы загрузки | Частичные данные не считаются полными |
| Повтор или конкуренция обработчиков | Нет дублей и публикации старой версии поверх новой |
| Изменение плана после просмотра импорта | Конфликт без частичной записи |
| Снятие и повторное создание плана | Версия не сбрасывается; старая вкладка и preview получают `409` |
| Одинаковый SKU в двух кабинетах или компаниях | Изоляция плана, расчётов и кэша |
| Позднее исправление источника | Текущая оценка меняется, исторический снимок сохраняется |
| Нулевой план, нулевая скорость, неизвестный остаток | Нет некорректного деления или вводящего в заблуждение значения |

При реализации требуются `make lint stan deptrac structure-check` и затронутые backend-тесты; `make front-typecheck front-lint front-knip front-test front-build APP=seller`; генерация контракта и `make api-types-check`; для каждой задачи со схемой — одна итоговая миграция и `make db-rebuild-check`; также `make audit`, `make test-e2e` и обязательные CI-проверки. SQL проверяется на объёмах и по правилам ADR-020. Изменения кода проходят независимое ревью Claude, а рисковые изменения схемы, изоляции и Ingestion — дополнительные проходы Codex по правилам проекта.

Этап 0 завершён, когда план вносится вручную и из Excel, факт и прогноз не задваиваются, доступный остаток определён однозначно, расчёты обновляются согласованно, а каждое значение можно объяснить через исходные данные, период, настройки и сохранённую версию расчёта.
