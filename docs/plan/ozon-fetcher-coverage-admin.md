# План: страница «Покрытие GO» в админке

Статус: реализован и выложен 25.10.2026 (PR #259), итог записан ниже.
Открыта проверка страницы владельцем с входом администратора на проде.
Ветка: `task/ozon-fetcher-coverage-admin`, один PR.
Основание: ADR-043 п. 4 и 6 — у сервиса есть `GET /internal/coverage`
(контракт `service-coverage` v1), потребитель в PHP предусмотрен «позже»;
токен «PHP → сервис» (`OZON_FETCHER_SERVICE_API_TOKEN`) на проде заведён.

## Решения владельца (25.10.2026)

1. Межарендаторное чтение отметок загрузки PHP из админки для сравнения
   с сервисом — **да**, только счётчики (системный контур, CLAUDE.md §1,
   ADR-018).
2. Сравнение PHP — **по кабинетам allowlist сервиса**: api получает тот же
   `OZON_FETCHER_CONNECTION_ALLOWLIST`.
3. Состояние сервиса (остановка, паузы) в шапке — **нет**, контракт
   `service-status` не заводится.
4. Пункт меню — **обеим ролям** администратора (`ROLE_ADMIN`).
5. **Снимок по расписанию** (ответ на замечание ревью о
   `services/AGENTS.md` §2): сервис из запроса пользователя не
   вызывается. Воркер `worker-service-coverage` раз в 5 минут снимает
   сводку в таблицу `service_coverage_capture` (последняя попытка
   и последняя успешная сводка); экран читает таблицу. Неудачная попытка
   не стирает последнюю сводку: экран показывает её со временем и
   состоянием попытки; попытка старше 15 минут — «сводка не обновляется».

## Зачем

Покрытие сервиса сейчас видно только из консоли
(`bin/ozon-fetcher-observe.sh` на проде). Страница отвечает без ssh:

1. Сервис отвечает? Насколько свежи цифры?
2. Какие дни и отчёты сервис не загрузил и почему?
3. Совпадает ли покрытие сервиса с загрузкой PHP?

## Что на экране

Сверху вниз — от вердикта к деталям.

1. **Шапка.** Заголовок «Покрытие GO», подзаголовок «ozon-fetcher».
   Вердикт плашкой: «в порядке», «есть отставание», «нужен человек»,
   «сервис не отвечает», «сервис выключен». Время ответа сервиса
   и время запроса, кнопка «Обновить». Кабинетов: Seller и Performance.
   Окно и пояс: «даты по МСК». Переключатель окна: 31 / 93 дня.
2. **Проблемы** — только если есть. Строка: тяжесть, ресурс, период,
   пояснение. Порядок — по тяжести, затем по дате (новые сверху).
3. **Матрица «ресурс × день»** по дневным ресурсам. Ячейка — состояние
   цветом и иконкой, текст `done/expected`, отметка PHP («PHP: n»);
   подсказка с разбивкой по статусам.
4. **Справочники и месяцы** — таблица: ресурс, период, состояние,
   `done/expected`, последняя успешная загрузка.
5. **Легенда** и абзац: «только счётчики; данные компаний и ключи сюда
   не попадают».

Состояния страницы без данных: загрузка; ошибка запроса к нашему API
(с «Повторить»); сервис выключен (не настроен адрес); сервис не отвечает
(сеть, 5xx, неверный ответ); снимок кабинетов ещё не получен (сразу после
старта сервиса). Ни одно из них не рисуется пустой матрицей.

### Состояние ячейки (ресурс × период)

По порядку, первое совпавшее:

| Состояние | Условие |
|---|---|
| нужен человек | `failed_permanent > 0` |
| ошибка, повтор | `failed_retryable > 0` |
| в работе | `running + pending > 0` |
| отчёт не готов | `not_ready > 0` |
| загружено | `done >= expected` и `expected > 0` |
| частично | `0 < done < expected` |
| не загружено | `done = 0` и `expected > 0` |
| нет данных | строки в ответе нет / `expected = 0` |

### Проблемы

| Тяжесть | Условие |
|---|---|
| нужен человек | ячейка «нужен человек» |
| расхождение с PHP | PHP загрузил день (`php ≥ 1`), а у сервиса `done < php` |
| не загружено | «не загружено» или «частично» у дня старше 2 суток |
| повторяется | «ошибка, повтор» |
| отставание | у дневного ресурса последняя успешная загрузка старше 36 ч |

«Отчёт не готов» и «в работе» у последних 2 суток — не проблема.

### Вердикт

1. Сервис выключен / не отвечает / снимка нет → соответствующая плашка.
2. Есть «нужен человек» → «нужен человек».
3. Есть любая другая проблема → «есть отставание».
4. Иначе → «в порядке».

### Чего на экране нет — намеренно

Названий компаний, кабинетов, сумм (контракт отдаёт только счётчики);
остановок и пауз сервиса, счёта 429/403 (решение 3); действий; оповещений.

## Практики, на которые опирается экран

- Вердикт и исключения сверху, полная матрица — ниже.
- Знаменатель всегда виден: `done/expected`, «ожидается» — из ответа
  сервиса, а не считается на фронтенде.
- Неизвестно ≠ ноль: недоступность сервиса — отдельное состояние.
- Свежесть самих цифр на экране.
- По каждому ресурсу отдельно, без одного общего процента.
- Бизнес-дата и пояс подписаны (МСК).
- Сравнение с эталоном: рядом с сервисом — PHP за тот же день.
- Доступность: цвет дублируется иконкой и текстом, матрица — `<table>`
  с заголовками строк и столбцов, подписи для экранного диктора.

## Устройство

```
worker-service-coverage ──каждые 5 мин── CaptureServiceCoverageAction
   └─ OzonFetcherCoverageClient ──GET /internal/coverage (93 дня)──▶ ozon-fetcher:8080
   └─ DbalServiceCoverageCaptureStore ──upsert──▶ service_coverage_capture

apps/admin ──GET /api/admin/services/ozon-fetcher/coverage?days=31|93──▶ api (Ingestion)
                                                                         ├─ DbalServiceCoverageCaptureStore::latest (последний снимок)
                                                                         └─ PhpDayLoadsForAdminQuery (marketplace_day_load)
```

Таблица `service_coverage_capture` (не факт-таблица, не данные компании):
`service` PK, `state`, `attempted_at`, `succeeded_at`, `payload` jsonb —
тело последнего успешного ответа, при чтении разбирается тем же строгим
разбором. Entity `ServiceCoverageCapture` без ORM-записи (§6), запись —
DBAL upsert; Builder в тестах (§9). Миграция одна, `down()` рабочий.

### Контракт `service-coverage` v1

- `example.json` — эталонный ответ (в контракте его нет).
- Go: тест — эталон проходит `schema.json`; ответ обработчика проходит
  `schema.json` (производитель).
- PHP: тест — эталон проходит `schema.json` (opis, уже в dev-зависимостях)
  и разбирается клиентом (потребитель).
- `README.md` и индекс `_contracts/README.md`: потребитель — PHP (админка).
- Схема не меняется: версия остаётся v1.

### PHP — модуль Ingestion

- `Infrastructure/ServiceCoverage/OzonFetcherCoverageClient` — scoped
  HttpClient `ozon_fetcher.client` (base_uri из `OZON_FETCHER_BASE_URL`,
  `timeout`/`max_duration` 5 с, без ретраев), токен
  `OZON_FETCHER_SERVICE_API_TOKEN` в заголовке Bearer. Строгий разбор
  ответа (все поля и типы по схеме v1); результат — readonly DTO
  `ServiceCoverageSnapshot` или исход `disabled` (адрес или токен
  не заданы), `not_ready` (503 `cabinets_not_ready`), `unavailable`
  (сеть, иной статус, неверный ответ — с причиной в журнал warning,
  без тела ответа и токена).
- `Infrastructure/Query/PhpDayLoadsForAdminQuery` — межарендаторное чтение
  `marketplace_day_load`: `report_type, period, count(DISTINCT
  marketplace_account_id)` где `completed_at IS NOT NULL`,
  `marketplace_account_id IN (allowlist)`, `report_type IN (4 типа)`,
  `period BETWEEN from AND to`. Возвращает QueryBuilder; лимит —
  4 типа × 93 дня + 1. Индекс: ведущего столбца `company_id` у запроса нет
  по построению (§1 «индекс следует за запросом»); таблица мала, план —
  `EXPLAIN` на проде, новый индекс только при плохом плане.
- Соответствие PHP ↔ сервис — константа в запросе:
  `ozon_posting_fbo_list → ozon.orders.fbo`,
  `ozon_accrual_by_day → ozon.finance.accrual-by-day`,
  `ozon_ad_expense → ozon.ads.expense`, `ozon_ad_daily → ozon.ads.daily`.
- `Ui/Controller/Admin/GetServiceCoverageController` —
  `GET /api/admin/services/ozon-fetcher/coverage?days=31`, `days` ∈
  {31, 93} иначе 422; окно — `days` суток по МСК, заканчивая сегодня.
  `#[IsGranted('ROLE_ADMIN')]`. Склейка ответов сервиса и PHP —
  в контроллере (синхронное чтение, как у прочих Ui модуля).
- Ответ `ServiceCoverageResponse`: `from`, `to`, `checked_at`,
  `service_state` (`ok|disabled|not_ready|unavailable`),
  `service_generated_at`, `cabinets_seller`, `cabinets_performance`,
  `php_compared` (allowlist задан), `rows[]`: `resource_type`,
  `period_key`, `cabinets_expected`, `done`, `running`, `pending`,
  `not_ready`, `failed_retryable`, `failed_permanent`,
  `last_success_at`, `php_cabinets` (`null` — тип без пары в PHP или
  сравнение выключено). Строка есть, если она есть у сервиса или у PHP.
- Deptrac: запрос и контроллер вынесены из `IngestionInfrastructure`
  и `IngestionUi` через `mustNot` в узкие слои `IngestionAdminCoverageQuery`
  и `IngestionAdminCoverageUi`; грант на запрос — только контроллеру.
  Клиент сервиса остаётся в широком `IngestionInfrastructure`: данных
  компаний он не читает.
- OpenAPI через атрибуты Nelmio, `make api-doc-export`, `make api-types`.
