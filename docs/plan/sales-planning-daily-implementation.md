# Дневной план-факт по когортам — подробный план реализации

> **Для исполнителя:** после согласования решений использовать
> `superpowers:executing-plans` и выполнять задачи по порядку с проверками.
> Автоматическая передача задач субагентам этим документом не поручается.

**Дата:** 27.10.2026.

**Статус:** реализация начата по поручению владельца от 27.10.2026.
Перед каждой задачей ведутся подробный план, чек-лист и отдельное Codex CLI ревью
в [журнале исполнения](sales-planning-daily-tasks.md). Новые архитектурные
решения оформляются ADR; недоступное обязательное ревью не разрешает merge.

**Цель:** сравнивать заданный в начале сезона дневной план с заказами,
выкупами, выручкой и скоростью по когортам, за день и накопительно.

**Архитектура:** SalesPlanning владеет целью и календарём; Ingestion —
исходными фактами, классификацией исходов и их агрегатами. Модули обмениваются
пакетными readonly DTO через IngestionFacade. Расчёты агрегатов выполняются
в PostgreSQL; Application соединяет готовые результаты по SKU и периоду.

**Стек:** существующие PHP 8.4, Symfony 7.4, Doctrine/DBAL, PostgreSQL,
React, TypeScript strict, TanStack Query, packages/ui. Новых зависимостей нет.

**Спецификация:** [дневное планирование](sales-planning-daily-plan-fact.md).
Этот документ уточняет предложение учёта заказов и декомпозирует работу.

## 1. Рекомендуемое решение по заказам

### 1.1. Три варианта

| Вариант | Плюсы | Ограничения |
|---|---|---|
| Все заказы минус подтверждённые отмены до передачи | Выполняет требование, показывает свежий спрос, сверяется с исходными данными | Исторический день уменьшается при позднем подтверждении отмены |
| Только переданные в доставку | Полезен для контроля логистики | Теряются свежие заказы в ожидании отправки; это другой показатель и другая задержка |
| Все заказы минус любые отмены | Простая формула | Скрывает невыкупы после передачи и искажает результат когорты |

**Рекомендация — первый вариант.** Второй можно вывести отдельной справкой
«Передано в доставку». Третий не использовать для основного показателя.
Это предложение, выбор реализации владельцем пока не зафиксирован.

### 1.2. Формула и единицы

```text
rawOrderedQuantity = сумма исходных заказанных штук
preHandoverCancelledQuantity = сумма штук с подтверждённым исходом T1
effectiveOrderedQuantity = rawOrderedQuantity − preHandoverCancelledQuantity
```

На экране «Заказали, шт.» = effectiveOrderedQuantity. В раскрытии:
«Всего заказали», «Отменили до доставки», «Неизвестный исход» и свежесть данных.
Не менять смысл существующего orderedQuantity в старом API Ingestion.

Считаются штуки товара, а не число заказов или отправлений. Заказ на пять
штук с отменой двух до передачи уменьшает количество на две, а не на пять.
Товарные строки разных postings не должны умножаться при связи с возвратами.

### 1.3. Что вычитается

Использовать действующую классификацию T1 из buyout_outcome, принятую
ADR-019/020. Не писать второй классификатор в SalesPlanning.

- Реальная передача подтверждается историей `delivering` по действующему ADR.
- `awaiting_deliver` и подстатус подготовки к передаче сами по себе её не доказывают.
- Отмена до передачи исключается при достаточном evidence для T1.
- Отмена после передачи (T2), частичный невыкуп (P) и клиентский возврат (R)
  остаются в знаменателе заказанных штук; их эффект отражается в продажах.
- Свежий заказ в ожидании отправки остаётся в количестве; это не отмена.
- Терминальная отмена без достаточной истории не объявляется T1.
  Она остаётся в количестве с признаком неизвестного исхода.
- Причина отмены сама по себе не заменяет историю передачи. Поздние
  противоречивые данные проходят действующие правила классификации.

При недостаточной истории результат означает «заказы без известных отмен
до доставки», а не доказанное количество всех фактически переданных штук.
В интерфейсе должна быть видна неопределённость.

**Пример на 100 шт.:** T1 = 10; T2/P = 15; D = 50; R = 5; активных = 15;
терминальных неизвестных = 5. Показываем «Заказали» = 90, известные
нетто-продажи = 50, неизвестный исход = 5. Текущий условный процент выкупа
равен 50 / (50 + 15) = 76,92%, а доля нетто-продаж от учтённых заказов —
50 / 90 = 55,56%. Это разные показатели.

### 1.4. Переучёт и аудит

Не удалять T1 из фактов, не переписывать исходное заказанное количество.
Исключение — правило чтения, маркированное `orders_excluding_confirmed_t1_v1`.
Изменение исхода пересчитывает первоначальную когорту и накопительные итоги.
Привязка остаётся к дате заказа в МСК, а не к дате отмены.

Невыясненные случаи нельзя автоматически вычитать как отмены или обнулять.
Показывать отдельно долю unknown и долю без оценки прогноза: это разные множества.

## 2. Продажи и прогноз: два последовательных результата

Рекомендуемый смысл цели — нетто-продажи, но владелец ещё не подтвердил
учёт клиентских возвратов. Согласование выполняется до изменения контрактов.

### Результат A: проверяемый план-факт и существующий прогноз выкупов

- Исходный план, effectiveOrderedQuantity, наблюдаемые нетто-продажи,
  фактическая выручка, скорости и накопление.
- В действующей количественной классификации D — оставшиеся выкупленные
  штуки, R — уже возвращённые. Наблюдаемые нетто-продажи = D.
  Повторно вычитать R из D нельзя. Тождество проверяется задачей A02.
- Текущий прогноз Ingestion выводить с названием «Прогноз выкупов по текущей
  методике», не как окончательный прогноз нетто-продаж с будущими возвратами.
- Не считать этот промежуточный результат полным выполнением требования
  прогноза нетто-продаж, если владелец выбирает именно нетто-цель.

### Результат B: прогноз итоговых нетто-продаж

```text
expectedNetSales = observedNetSales
                   + expectedRetainedSalesFromOpenOrders
                   − expectedFutureReturnsFromAlreadyBoughtUnits
```

Для открытого заказа вероятность зависит от стадии: до передачи учитывается
вероятность ещё возможной T1, после передачи — нет. Вычитание уже известных
T1 из экранного количества не даёт права исключать T1 из обучения
вероятности исхода свежего заказа до передачи.

Для выкупленной штуки учитывается условная вероятность будущего возврата
при её текущем возрасте, а не полная доля возвратов по всем возрастам.
Известный R даёт ноль оставшихся продаж; T1/T2/P также дают ноль.
Неизвестные и противоречивые исходы не получают выдуманную вероятность.

Если источники не позволяют оценить будущие возвраты, expectedNetSales
остаётся null с причиной. Не подставлять нулевую вероятность возврата.
Новый алгоритм принимается отдельной методикой и не меняет старые отчёты.

Для денег применять вероятности к денежным компонентам товарных строк
в точной арифметике. Не умножать суммарные штуки на среднюю РРЦ.
Если доступна только оценка по исходной цене строки, назвать её денежной
оценкой продаж; не выдавать за подтверждённые начисления или выплаты площадки.

## 3. Общие ограничения

- Компания, кабинет и SKU обязательны в области чтения; companyId первым параметром.
- Существующие контракты и проценты не меняют смысл. Новая ручка — дополнение.
- Исходная цель — первая успешно утверждённая версия линии; новую версию
  можно показать рядом, но она не подменяет исходную автоматически.
- Если старая цель не имеет явно выбранного смысла штук, сравнение
  блокируется пояснением до выбора методики, без автоматического перевода.
- Нет межмодульного SQL, запросов на каждый SKU, COUNT(*) по фактам,
  гидрации Entity для списков и денежных float.
- Одна итоговая миграция на отдельную задачу со схемой, Entity обязательны.
- Период плана до 184 дней, SKU до 1000 — текущие пределы ADR-040/041.
- Новые экранные лимиты: 20 SKU по умолчанию, максимум 50; максимум 31
  дневная колонка за запрос. Неделя/месяц/период допускают до 184 дней,
  но не более 1550 пар SKU × корзина; превышение — 422.
- Календарь: до 500 сохранённых записей на версию; это предлагаемое
  обратимое ограничение. Маркеры границ сезона вычисляются из шапки.
- PHP/Composer/Node/npm — только контейнеры и Makefile.
- Проверки и обязательное независимое ревью не ослабляются.

## 4. Фокус проверок

1. Отмена впервые видна терминальной: без evidence не вычитать T1 (A01, A12).
2. Часть количества одной SKU вернулась: не считать повторный возврат и
   не вычитать R дважды (A02, A14, B04, B10).
3. Разные цены или валюта: никакого усреднения РРЦ, неявной конвертации
   и float; несогласованность видна как отсутствие денежной оценки (A15, B11).
4. Смена страницы, новая версия плана и поздние исходы: исходная цель и
   начало накопления остаются теми же (A06, A25, A36, A46, A47).
5. Отсутствующая загрузка или обучение: не превращать в ноль и не считать
   сумму известных прогнозов полным итогом (A16, A19, A38, B08, B15).

    string $companyId,
    string $marketplaceAccountId,

SalesCohortRequest: список SKU, from/to, accumulationFrom, группировка.

накопительно: rawOrderedQuantity, preHandoverCancelledQuantity,

условные числитель/знаменатель выкупа, прогнозируемые компоненты и деньги.
Также maturityStatus, inFlightRateBps, unestimatedRateBps, качество загрузки.
Количество заказов/факта — int; деньги — Money/минорные единицы с валютой;
неокруглённые ожидания SQL numeric проходят как decimal string без float.
Новые межмодульные DTO не раскрывают Infrastructure-типы.

SalesCohortBatch: записи, calculatedAt, границы покрытия, методики и качество.
calculatedAt — время расчёта, не обещание произвольного исторического asOf.
Исторический прогноз публиковать лишь при наличии восстанавливаемых входов.

## 6. API и схема — предлагаемые решения для согласования

### API

```text
GET /api/companies/{companyId}/sales-plans/{planId}/performance
    ?from=YYYY-MM-DD&to=YYYY-MM-DD&groupBy=day|week|month|period
    &limit=20&cursor=...

PUT /api/companies/{companyId}/sales-plans/{planId}/calendar
    { version, entries: [...] }
```

GET возвращает baselinePlanId, baselineVersionNumber, методику цели,
calculatedAt, границы накопления, строку качества и страницу SKU.
Корзина содержит day/period и cumulative-компоненты, факт, ожидаемый итог,
выполнение в bps и абсолютные отклонения. Режим интерфейса не меняет
методику; сервер отдаёт обе формы для тех же корзин.

Курсор — по SKU, связан с planId, базовой версией, диапазоном и группировкой;
неприменимый курсор — 422. Сводка относится к явно названной области:
не выдавать сумму текущей страницы за весь план. Общую сводку реализовать
отдельным ограниченным агрегатом, если она входит в согласованный экран.

Ошибки: 403 по действующему контролю доступа, 404 чужой/отсутствующий план,
409 version_conflict при записи, 422 некорректный диапазон/лимиты,
явный код plan_metric_required до выбора смысла старой цели.
Доменную невозможность редактирования утверждённой версии сообщать
существующим стилем ошибок проекта, не смешивая с конфликтом версии.

### Схема

- Поле методики в sales_plan: старые строки остаются без переинтерпретации;
  выбор владельцем выполняется явной версионируемой командой с аудитом.
  Варианты метода фиксируются ADR, без свободного текста от браузера.
- Таблица sales_plan_calendar_entry: UUIDv7, company_id, sales_plan_id,
  nullable marketplace_sku, kind, date_from/date_to. FK/индексы компании
  и плана, ограничения диапазона; Entity обязательна.
- `season_start`/`season_end` enum вычисляются из неизменяемых границ шапки:
  не хранить вторую редактируемую копию тех же дат.
- `sales` — интервал; `replenishment` и `replenishment_stop` — точки,
  date_from = date_to. У одной даты допускается несколько разных событий.
- Первая версия: календарь плановых отметок по плану или одному SKU.
  Группы товаров и фактические складские операции сюда не включаются.
- Предлагаемый смысл replenishment — плановая дата поступления на площадку;
  replenishment_stop — прекращение планирования новых пополнений, не отмена
  уже отправленных партий. Требует подтверждения владельца.
- Календарь меняется только в draft по версии шапки, копируется вместе
  с новой версией и попадает в аудит. Границы сезона не закрывают поздние исходы.

Факт-таблицы, их ключи и индексы на старте не менять. Если SQL-замер
потребует этого, вынести конкретное решение в план до реализации.

## 7. Простые задачи и трудозатраты

План разбит на **68 простых задач: 50 в этапе A и 18 в этапе B**.
Одна задача имеет один проверяемый результат и оценку 1–4 инженерных часа.
19 прежних крупных задач теперь являются блоками для навигации, не единицами исполнения.

Для каждой кодовой задачи: сначала тест поведения и его ожидаемое падение,
затем минимальная реализация и повторная проверка. Тест входит в оценку задачи;
не заводить отдельную задачу только на шаблон класса или установку зависимости.
Файлы блока и контракты раздела 5 применяются ко всем его задачам.
Изменение чужих файлов и попутный рефакторинг не входят в объём.

Согласование решений — один пакет перед кодом. Документирование, исследование
источников и проверка существующего поведения могут выполняться до согласования.
Начинать блок при готовых входах; линейный порядок номеров не заменяет зависимости.

пакет покрывает только собственный diff. Заблокированный прогон не заменяется самопроверкой.

## 10. Единый пакет решений перед реализацией

1. Заказали = исходные штуки − подтверждённые T1; активные и unknown пока
   включены и объясняются отдельно. Это рекомендованный способ выполнить уточнение.
2. Цель — нетто-продажи; D не уменьшается на R повторно. Владельцу нужно
   подтвердить смысл цели; допустимо выбрать выкупы, но тогда методики и подписи отличаются.
3. Денежный результат — оценка оставшихся продаж по подтверждённой цене
   строки, после возвратов до расходов; не выплаты и не начисления площадки.
4. База — первая утверждённая цель; новая версия не подменяет её автоматически.
   Смысл старых штук выбирается явно без переписывания утверждённого плана.
5. Календарь — плановые точки/интервалы, поддерживает совмещение; подсорт
   означает поступление, границы сезона получаем из шапки.
6. Новый пакетный Facade, performance API, календарь и схема оформляются ADR.
7. Два результата A/B: A даёт контроль и существующий прогноз выкупа;
   полный нетто-прогноз появляется после проверки возвратной модели B.

Поручение владельца от 27.10.2026 запускает исполнение предложенного плана.
Необратимые решения всё равно оформляются ADR, а утверждённые старые планы
не переинтерпретируются без явного выбора смысла их штук.
Выбор способа исполнения и отдельные подтверждения каждого технического шага
не нужны: после единого согласования действует процесс AGENTS.md/CLAUDE.md.

## 11. Основания best practices

- Сохранять зерно факта и исходные количества, а исключения выполнять
  отдельной методикой чтения: [Kimball — Fact Tables](https://www.kimballgroup.com/2008/11/fact-tables/).
- Проценты агрегировать из суммарных компонентов, не средним дневных
  процентов: [Kimball — additive and non-additive facts](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/additive-semi-additive-non-additive-fact/).
- Проверять прогноз на последовательных прошлых срезах, используя лишь
  известные тогда данные: [Hyndman, Athanasopoulos — time series cross-validation](https://otexts.com/fpp3/tscv.html).
- Граница передачи, T1 и неизвестные исходы: [ADR-019](../adr/0019-ozon-buyout-rate-sources-and-history.md),
  [ADR-020](../adr/0020-ozon-buyout-rate-query-plan.md).
- Зрелость и качество действующего прогноза: [ADR-029](../adr/0029-ozon-buyout-cohort-maturity.md),
  [ADR-031](../adr/0031-ozon-buyout-forecast-unestimated-units.md),
  [ADR-033](../adr/0033-ozon-buyout-unestimated-share-contract.md).
