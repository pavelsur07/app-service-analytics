## 1. Результат этапа и границы

В Symfony появляется модуль `ProductResearchOzon`: авторизованный пользователь
может получить календарный предпросмотр, создать черновик проекта своей компании,
прочитать его, получить страницу списка, добавить периоды и скопировать проект.
Единственный источник календарных правил — сервер. На одинаковую дату проверки
одни и те же вводные дают одинаковый набор месячных срезов.

Проект исследования рынка не требует подключения собственного кабинета Ozon.
Проверку членства/состояния компании берём из существующего seller-контура;
`IdentityFacade::listConnections()` для выбора категории не используется.
Новых Facade, межмодульных связей, пакетов и транспортов очереди не требуется.
Связь с Identity для аудита уже разрешена ADR-050.

Этап содержит backend и генерацию публичной OpenAPI/TS-схемы. Seller-экраны —
этап 7; каталог/поиск категорий — этап 3; задания, outbox, прогресс, Python-вызовы,
кэш снимков, raw-загрузка и XLSX — последующие этапы. Статус этого этапа только
`draft`; готовность получения товаров или запуска исследования не заявляется.
Python-код, его БД и опубликованный межсервисный v1 менять для этого этапа не нужно.

### Граница до готовности каталога

- Application получает проверенную категорию через company-scoped порт внутри
  нового модуля. Вход — выбранный полный путь, а не произвольное название товара.
- Порт различает: категория подтверждена; неизвестна; каталог ещё не готов.
  Неизвестная категория — 422; неготовый каталог — 503. Пустой каталог не
  подменяет неготовность. Ожидаемые ошибки не содержат тела внешнего ответа.
- В unit/functional тестах порт получает фиксированный набор категорий для
  компаний A/B. Тестовый адаптер не регистрируется в prod и не наполняет БД.
- Production-реализация до этапа 3 честно сообщает неготовность. Публичные
  сценарии модуля закрыты серверным feature flag, по умолчанию false: авторизованный seller получает 404.
  Тесты явно включают flag. Его нельзя обойти прямым HTTP-запросом, скрыть
  только кнопку недостаточно. Включение проверок в CI не включает продукт.
- В этапе 3 порт подключается к полной локальной проекции каталога; обращения
  из пользовательского запроса к Python/MPStats не появляются.

## 2. Правила проекта и календаря

### Проект и диапазоны

- Компания — из маршрута и действующей проверки доступа, автор — из
  `RequestAttributes::ActorUserId`. Клиент не задаёт `id`, автора, companyId,
  статус, дату создания, версию создания или настройки источника.
- UUIDv7 генерируется приложением; дата события — aware UTC. Название до
  200 символов; комментарий до 2000; необязательное имя периода до 100.
  Лимиты проверяются до записи; строка из пробелов не считается названием.
- При отсутствии названия сервер предлагает имя из категории и уникальных
  диапазонов: «Хиджабы и тюрбаны женские · янв–мар 2026». Автоназвание укладывается
  в лимит без изменения полного пути категории; длинный вариант сокращается
  только как отображаемая подпись. Пользовательское имя не обрезается молча.
- FBS всегда true, RUB, «Новинки: Неважно» — фиксированные настройки ADR-050.
  Вход не разрешает выключить FBS, сменить валюту или добавить фильтры MPStats.
- Период — именованный диапазон `fromMonth` / `toMonth` в формате `YYYY-MM`.
  Например, «Сезон весна», март–май. Сезон может занимать несколько месяцев
  или пересекать год. Произвольные границы внутри месяца не принимаются и
  не округляются скрытно: единица методологии — целый календарный месяц.
- От 1 до 24 диапазонов на проект; от 1 до 24 уникальных месяцев после
  объединения. Лимит диапазонов защищает и ввод из множества дубликатов.
  Выход за любой лимит — 422, без частичного сохранения.
- Одинаковые диапазоны с одинаковым нормализованным именем не создают второй
  такой же период. Разные именованные сезоны могут пересекаться: месяцы всё
  равно уникальны. Порядок выдачи месяцев — хронологический.
- Добавление периодов сохраняет прежние периоды. Для повторной передачи того
  же периода определён no-op: дубля нет, лишняя версия не появляется.
- Метаданные задаются при создании/копировании. Произвольный PATCH, удаление
  проекта/периодов и смена категории существующего проекта в объём не входят.
  В копии можно выбрать другую подтверждённую категорию; FBS остаётся true.

### Календарь

- Одна проверка получает один момент из существующего `Psr\Clock\ClockInterface`,
  переводит его в `Europe/Moscow` и использует эту дату для всего результата.
  Это календарь Conwix, а не утверждение о timezone MPStats.
- Закрытый месяц: от первого до последнего числа включительно, правильное
  количество дней, `partial=false`. Скользящих «30 дней» нет.
- Будущий месяц запрещён. Текущий допускается только с явным
  `includeCurrentMonth=true`: от первого числа до вчера, `partial=true`.
  Первого числа текущий месяц запрещён даже с флагом: доступных дней нет.
- Если среди выбранных месяцев нет текущего, флаг не делает закрытые месяцы
  неполными. Выбранный текущий месяц со временем становится закрытым;
  пометка относится к вычисленному срезу, а не навсегда к строке проекта.
- Быстрые 3/6/12 — последние N **закрытых** календарных месяцев. «Год назад»
  сдвигает границы выбранного диапазона на 12 месяцев, сохраняя исходный
  диапазон. Дни февраля рассчитываются заново, не копируются из другого года.
- Предпросмотр возвращает нормализованные диапазоны, уникальные месяцы,
  `dateFrom`, `dateTo`, `days`, `partial`, количество, сводку и автоназвание;
  также `calendarDate` и `timezone`. Никаких обещаний попадания в кэш пока нет.
- Create/add/copy повторно вычисляют результат сервером. Клиент передаёт
  `previewCalendarDate`; если наступил другой день, получит 409
  `preview_outdated` и должен повторить предпросмотр. Это особенно важно
  для вчерашней границы и перехода месяца. Клиентские даты/счётчики срезов
  не принимаются как доверенный результат.
- В проекте хранятся намерение (диапазоны/флаг), а не вечный снимок предпросмотра.
  Точные интервалы будущего запуска фиксируются отдельно в этапе 4. Один
  календарный расчёт переиспользуется предпросмотром и подготовкой запуска;
  пока входа запуска нет, его совместимость подтверждают примеры v1.

## 3. Раскладка, данные и конкурентность

| Область | Ответственность |
|---|---|
| Domain | ResearchProject, именованный период, месяц, правила нормализации/календаря |
| Application | Preview/Create/List/Get/AddPeriods/Copy; транзакция, категория, аудит |
| Infrastructure/Repository | ORM-запись шапки/периодов, optimistic version |
| Infrastructure/Query | DBAL-чтение нужных колонок в readonly DTO, keyset |
| Ui | Request/Response DTO, тонкие контроллеры, OpenAPI и существующие guards |

Точные имена классов уточняются при реализации, без универсального workflow,
общего context-dict, календарного фреймворка и дублирования логики в контроллерах.
Интерфейс создаётся на реальной границе слоя/тестовой подмены, не для каждого класса.

Ожидаются две человеческие таблицы: `product_research_ozon_project` и
`product_research_ozon_period`. Шапка: UUID, company, проверенный category path
и revision каталога, имя, комментарий, флаг текущего месяца, draft, автор,
created_at/updated_at, optimistic version. Период: UUID, company, project,
границы месяцев (native date, первое число), нормализованное имя, порядок.
Структурные CHECK запрещают обратный диапазон/непервое число; зависимые от
сегодняшней даты проверки выполняет календарная политика. ORM Entity описывают
обе таблицы.
Отдельных таблиц «месяц проекта», сырья и задач пока нет.

- Company-scoped методы чтения принимают companyId первым параметром.
  Доступ к периоду включает одновременно компанию и проект.
- Уникальность периода защищена БД по company/project/границам/имени, не
  проверкой SELECT перед INSERT. Нормализованное пустое имя не nullable,
  чтобы NULL не обходил уникальность. Доменный no-op проверяется по актуальному агрегату; неожиданный конфликт
  ограничения в БД переводится в 409 с откатом, без повторного использования
  закрытого EntityManager или частичного сохранения.
- Связь периода с шапкой учитывает company; нельзя записать период A к проекту B.
  Индексы tenant-чтений начинаются с company_id; внешний User Entity не
  импортируется в Domain, автор хранится scalar UUID.
- Шапка и все периоды создаются одной ORM-транзакцией. Аудит через существующий
  IdentityFacade входит в тот же commit. В аудит не попадают полный комментарий,
  секреты или тела запросов; достаточно безопасных идентификаторов/счётчиков.
- Изменение периода проверяет `expectedVersion`. Защита от гонки исполняется
  в записи БД/ORM, а не только предварительным сравнением версии в PHP.
  Изменение только дочерней строки также должно менять version шапки.
- При двух изменениях с одной версией выигрывает одно; второе получает 409,
  без потери первого изменения и частично добавленных периодов.
- Копирование использует expectedVersion источника и согласованное чтение
  шапки/периодов в транзакции с блокировкой шапки. Новый UUID, новый автор,
  новая дата и draft; исходник не меняется. Ни сырьё, ни будущие задачи,
  статусы загрузки и связи снимков в копию не переносятся.
- Список: limit=50, максимум 200, keyset по UUIDv7 DESC, nextCursor через
  limit+1. Нет OFFSET, COUNT(*) и ORM-гидрации списка. Детальное чтение —
  нужные колонки и одна ограниченная пакетная выборка периодов, без N+1.

## 4. План API Symfony

Базовый путь `/api/companies/{companyId}/product-research-ozon`.
Это новые seller-endpoint'ы, существующие API и сервисный v1 не меняются.
Финальный формат фиксируется в коде и генерируемой схеме, не ручной правкой TS.

| Метод и путь | Назначение | Результат |
|---|---|---|
| POST /preview | Диапазоны либо явный shortcut + флаг | 200, календарь/сводка/calendarDate |
| POST /projects | Категория, диапазоны, флаг, optional name/comment, previewCalendarDate | 201, id/version и черновик |
| GET /projects?limit&cursor | Только проекты компании | 200, items/nextCursor |
| GET /projects/{projectId} | Шапка и периоды | 200 либо 404 |
| POST /projects/{projectId}/periods | Новые периоды, expectedVersion, previewCalendarDate | 200, версия и актуальный предпросмотр |
| POST /projects/{projectId}/copy | expectedVersion источника, previewCalendarDate, overrides категории/имени/комментария/периодов | 201, новый проект |

Preview не пишет данные и не создаёт сущность. В add-periods предпросмотр
оценивает объединение прежних и добавляемых диапазонов, а не только добавку.
Для shortcut и явных диапазонов формат взаимоисключающий; неоднозначное тело — 422.
Пустой overrides в copy сохраняет вводные источника, но даты проверяются заново.

Ошибки — существующий `ValidationErrorResponse`: 401 без seller-сессии,
403 чужая/заблокированная компания, 404 чужой/отсутствующий проект внутри
доступной компании, 409 version_conflict/preview_outdated, 422 неверные поля,
периоды, категория/лимит, 503 catalog_not_ready. Авторизация раньше бизнес-логики;
при feature flag=false нет записи, аудит-записей и обращения к категории.

Проверяется доступ именно seller-пользователя. Системный admin и extension token
не получают доступ только потому, что общий CompanyAccessSubscriber пропустил
их контур/проверил членство. Используются действующие security/CSRF/session guards;
новый firewall, расширение полномочий токена или система ролей не добавляются.

| F02 | Functional | admin / extension token / подмена author/company/status/id | контур не допущен; служебные поля отвергнуты, автор только из сессии |
| F03 | Functional | категория известна A, неизвестна B; каталог не готов | только подтверждённая категория; 422 / 503 различаются |
| F04 | Functional | preview → create → get → list → add → copy | draft сохраняется; версии, периоды, автор/даты корректны |
| F05 | Functional | preview вчера; save сегодня/после смены месяца | 409 preview_outdated, нового черновика/периода нет |
| F06 | Functional | валидные/невалидные JSON, лимиты, extra fields, FBS=false, неверная currency, CSRF | строго документированные ошибки; никакого скрытого приведения |
| F07 | Functional | flag=false, прямой create/add/copy и preview; штатный сервер без каталога | маршруты закрыты; тестовый справочник в prod не используется |
| C01 | Contract | месяцы из PHP preview → month в v1 corpus | даты/days/partial совпадают; числовые представления не расходятся |
| M01 | Migration | empty DB up → schema validate → down → up | одна миграция задачи, восстановление рабочее, существующие таблицы не потеряны |

Для текущего месяца дополнительно проверить второго числа (1 день), конец
месяца, explicit flag без текущего месяца и смену дня между preview/save.
Для API проверить неполные/неверные UUID, превышение строковых лимитов,
конкурентное изменение версии и отсутствие служебных полей в ответе.

Копирование в другую компанию не поддерживается. Cursor — позиция, а не
разрешение доступа: UUID из A не должен раскрывать записи A при запросе B.
Все данные создаются Builder'ами; тесты конкуренции используют настоящие
соединения, а не два последовательных вызова под одной транзакцией DAMA.

## 7. Изменяемые области и обязательные команды реализации

- `api/src/ProductResearchOzon/`, `api/tests/{Unit,Integration,Functional}/ProductResearchOzon/`,
  Builder'ы в `api/tests/Support/Builder/` и одна `api/migrations/Version*.php`.
- `api/deptrac.php`, `api/bin/check-src-structure.sh`, DI/route/ORM mappings,
  если текущая автоконфигурация не подхватывает модуль. Правила не ослабляются.
- OpenAPI-источник в контроллерах/DTO; результат генерации в `packages/api-schema`.
- `docs/structure.md`, применимые правила состава модулей и общий план;
  Make/CI только при необходимости нового гейта, без изменения транспортов.

Проверки во время реализации: затронутые `make test-unit test-int test-func`,
`make lint stan deptrac structure-check`; контракты — обе стороны. Схема:
`make db-rebuild-check` с предварительной проверкой локального назначения;
предпочтителен отдельный Compose project без конфликтующих host ports и без
удаления текущих dev PostgreSQL/S3-томов. Точные overrides/команды сохраняются
в локальном отчёте. Разрушительные цели не направляются на production.

Контракт: `make api-doc-export api-types`, затем `make api-types-check`.
Обязательные CI (включая audit и E2E) проверяют весь diff конечного head.
Если интерфейс seller не меняется, новые UI-тесты этапа 7 не пишутся здесь;
существующие frontend/TS и E2E-гейты выполняются по общему CI.

Реализация схемы/изоляции требует независимого Claude и двух Codex-проходов
5A/5B; при недоступном Claude — согласованная замена двумя новыми сессиями
Codex CLI без контекста автора. Самопроверка не заменяет ревью. Пакет покрывает
все файлы задачи; правки отчёта после ревью не маскируют изменения кода.
Результаты, hashes/пути ответов, разбор и число уникальных новых замечаний
дополнительных проходов сохраняются в отчёте этапа.

## 9. Приёмка по шагам без UI

В тестовом seller-контуре с разрешённым flag и подтверждённой категорией:
создать preview для двух весенних сезонов → увидеть 6 месяцев → сохранить →
прочитать из списка своей компании → добавить пересекающийся период → увидеть
уникальное объединение → скопировать → убедиться, что исходник не изменился.
Затем повторить чужим пользователем, с устаревшей version и на границе суток:
ожидать документированный отказ без частичной записи.

На production до этапа 3: убедиться, что новый незавершённый сценарий закрыт,
общие seller/admin smoke здоровы и тестовый каталог не опубликован.

Закрытие этапа подтверждается итоговым отчётом, ревью и фактической доставкой. Новых решений
вне ADR-050 и изменений уже опубликованного API план не требует; при обнаружении
такой необходимости её выносят в единую точку согласования до реализации.
