## 1. Основной вывод

В проекте есть основа: загрузка Ozon, raw-слой, история наблюдений статусов,
снимки остатков, отчёты по спросу, выкупу и локализации, ввод плана продаж.
Сквозной сезонный подсорт по правилам v2.7 пока не реализован.

Рекомендуемый путь: расширить `SalesPlanning`, добавить предметные модули
`Inventory` и `Replenishment` внутри PHP-монолита. Загрузку внешних данных
оставить в `Ingestion`. Python использовать для независимого прототипа,
производственный расчёт первой версии — на PHP. Сначала обеспечить входные
данные, их качество и воспроизводимость, затем реализовывать рекомендации.

Формулы расчётного ядра в этом документе не пересматриваются. Замечания к ним
при реализации оформляются воспроизводимым тестом по разделу 13 ТЗ.

| Вопрос | Сейчас | Требование v2.7 и рекомендуемое действие |

## 4. Границы модулей

### 4.1. Предлагаемое распределение

| Модуль | Что принадлежит модулю | Этапы |
|---|---|---|
| `Ingestion` | API Ozon, raw, наблюдения, нормализованные внешние факты заказов/возвратов/остатков/поставок, техническая полнота источников, внешние идентификаторы складов и кластеров | 0.1–0.2, внешние источники 1.2–1.5 |
| `Inventory`, новый | Внутренний товар, размер и группа артикула, категория, сопоставление SKU подключений, упаковка, закупочная цена, свой склад, поступления и заказы поставщикам, отгрузки и резервы, сопоставление поставок и сверка количества | 1.1, 1.4, товарная сверка 1.5, 1.14, резерв 2.5 |
| `SalesPlanning`, расширение | Сезоны, назначения SKU, план V, профили сезонности и доли размеров, восстановление спроса, когорты и коэффициенты для планирования, спрос по кластерам, план-факт и его отчёты | 1.7–1.11, 2.1; расчётные входы 1.9–1.10 |
| `Replenishment`, новый | Баланс товара и переноса спроса, SS, подбор и распределение партий, FIFO в симуляции, рекомендации, решения и их жизненный цикл, сценарии распроданности, бэктест политики, план поставок сезона | 1.6 и 1.12 с развитием модели, 2.2–2.9, применимые уточнения фазы 3 |
| `Identity` | Права, авторство, аудит и доступ к компании | Сквозная ответственность |
| `Shared` | Технические примитивы, Money, общие типы времени/идентификаторов по существующим правилам | Без предметных формул |

Сборное представление отчёта размещается у владельца сценария. Например,
распроданность использует план и итог симуляции, поэтому её сценарий находится
в Replenishment; он получает показатели плана через Facade. Приближение фазы 1
и симуляция фазы 2 должны отдавать одну явно помеченную метрику, без двух
разных определений в интерфейсе.

Существующие отчёты Ingestion сохраняют текущего владельца до отдельной задачи
перехода. Новые правила планирования не добавляются в общий старый SQL молча.

### 4.2. Почему два новых модуля

| Вариант | Оценка |
|---|---|
| Всё положить в Ingestion или SalesPlanning | Меньше новых папок, но сбор источников, товарные обязательства и вычислительная модель оказываются связаны одним жизненным циклом |
| Добавить Inventory и Replenishment | Рекомендуется: отдельные границы для реального свободного товара и для рекомендательной модели; соответствует масштабу команды |
| Сразу добавить Catalog, Forecasting, Purchasing, Reporting и отдельный сервис расчёта | Слишком много контрактов и эксплуатационных обязательств для первой версии |

Товарные атрибуты в Inventory — сознательное начальное размещение, а не правило
на все будущие модули. Catalog выделяется, когда появится самостоятельный
процесс ведения каталога и реальные потребители. Purchasing — когда управление
закупками выйдет за рамки импорта ожидаемых поступлений. Пустые модули заранее
не создавать. Границы по предметным возможностям соответствуют
[domain analysis и bounded contexts](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis).

### 4.3. Зависимости

Стрелка означает вызов разрешённого Facade:

```text
Inventory     → Ingestion
SalesPlanning → Inventory, Ingestion
Replenishment → SalesPlanning, Inventory, Ingestion

Все модули → Identity / Shared в пределах разрешённых слоёв
```

Это предлагаемая карта: новые связи вводятся только с ADR и точными грантами
Deptrac. Вызовы чужих модулей идут из Application. Domain не знает о Facade,
ORM, внешнем API и очередях.

Facade возвращает типизированный ограниченный пакет, версию/срез и ссылки на
происхождение данных. Вызов на каждый SKU запрещён: выбирать пачками. Чужие
Entity, QueryBuilder и таблицы не становятся публичным контрактом. SQL JOIN
таблиц двух модулей не используется как обход Facade. Для тяжёлого расчёта
потребитель может сохранять собственный воспроизводимый набор входов.

Расчёт запускает собственный периодический сценарий, проверяющий готовность
входов через Facade. Ingestion не вызывает SalesPlanning или Replenishment
после каждой загрузки. Межарендаторный обход компаний оформляется узкой
операционной границей по CLAUDE.md §1.

### 4.4. Размещение по слоям

| Слой | Примеры ответственности |
|---|---|
| `Domain` | Политика зрелости, восстановление спроса, баланс дня, распределение переносов, ограничения партии, допустимые переходы рекомендации |
| `Application` | Подготовить срез, запустить расчёт, принять рекомендацию, зарезервировать товар, опубликовать результат |
| `Infrastructure/Query` | SQL-агрегации и отчётные проекции в readonly DTO |
| `Infrastructure/Repository` или существующий `Persistence` | Сохранение агрегатов, пакетная запись производных данных по правилам проекта |
| `Ui` | Контроллеры, запросы/ответы, консольные команды |
| `apps/seller` | Таблицы, фильтры, объяснение, решения пользователя; серверное состояние через TanStack Query |

Не дублировать алгоритм симуляции для ближайшей поставки, плана сезона и
бэктеста: один производственный движок с разными входами. Независимый Python-
прототип проверяет результаты, а не импортирует тот же код.

## 5. Решения по данным и согласованности

### 5.1. Товар, кабинет и сезон

- Внутренняя единица товара — company-scoped UUIDv7, соответствующий физическому SKU/размеру. Баркод и артикул продавца — атрибуты, а не стабильный ключ.
- Привязка к площадке включает company, подключение и marketplace SKU; изменение привязки версионируется для исторического расчёта.
- Общий запас нескольких кабинетов резервируется в одном Inventory. Разные кабинеты не получают независимые копии остатка.
- Для одного SKU подключения и даты допускается один действующий сезон планирования. Исторические сезоны продолжают принимать поздние исходы.
- Симуляция охватывает все кластеры товара; при общем запасе кабинетов распределение также согласуется между ними. Нельзя планировать каждый кабинет на весь общий склад независимо.
- География имеет устойчивые внутренние ссылки и историю сопоставления с источником. Не считать совпадение названий кластеров вечной гарантией; неизвестное сопоставление показывать явно.

Точный состав ключей и индексов определяется отдельным ADR до миграции.

### 5.2. Два времени и история

Хранить время события и время получения знания о нём. Для наблюдения без
доказанной даты события сохранять интервал/оценку и признак качества; не выдавать
время первого опроса за точное время выкупа или физического прихода.

Для бэктеста нужны прежние значения событий, параметров, товарных связей и
сезонных профилей. Фильтр `first_loaded_at <= T` по изменённой текущей строке
не решает задачу. Предлагается сохранять неизменяемые ревизии необходимых
расчётных входов и их происхождение; текущие таблицы фактов остаются проекцией.
Не вводить полное версионирование всех фактов без отдельного решения.
Обоснование двух временных осей — [Bitemporal History](https://martinfowler.com/articles/bitemporal-history.html).

Первоначально показанная рекомендация сохраняется. Позднее событие создаёт
новый пересчёт; восстановленная история и исторически показанный результат
доступны как разные представления. Не переписывать принятое решение человека.

### 5.3. Частичные количества и резерв

Состояние отправления не заменяет количественные исходы его SKU. Частичный
выкуп, возврат и отгрузка учитываются количествами со связью с исходной строкой.
Избыточный или несопоставленный возврат — проблема качества, а не повод
молча обрезать количество и продолжить достоверный расчёт.

Принятие рекомендации, создание резерва и аудит выполняются одной транзакцией
в общей БД монолита через публичные сценарии модулей. Inventory блокирует
согласуемый запас либо выполняет условную запись с проверкой версии; порядок
блокировки нескольких позиций детерминирован. Повтор команды имеет стабильный
ключ операции и ограничение уникальности. Предварительное чтение остатка вне
транзакции не считается защитой. Механизмы блокировки описаны в
[PostgreSQL 16: Explicit Locking](https://www.postgresql.org/docs/16/explicit-locking.html).

Если свободный товар включает ожидаемые поступления до будущей отправки,
проверять обязательства по датам: поступление доступно только с даты его
доступности и не может обеспечить две конкурирующие партии. Перенос или
частичная поставка от поставщика пересчитывает обеспеченность принятых
обязательств и показывает дефицит, сохраняя решение человека.

В импорте своего склада нужны идентификаторы отражённых списаний и их
количества. Одной даты снимка или общего изменения остатка недостаточно, чтобы
доказать списание конкретной отгрузки. Если источник их не даёт — явная ручная
сверка. Пока списание не подтверждено, резерв сохраняется по правилу ТЗ;
не угадывать его снятие по падению общего остатка.

### 5.4. Запуск расчёта и качество

Сохранять логический запуск расчёта и отдельные попытки исполнения. В составе
запуска: компания, область подключений, сезон, дата, граница известных данных,
версия алгоритма, версии плана/параметров/справочников, перечень входов,
показатели качества, причины отсутствия рекомендаций и результаты.

Загрузка исходных пакетов должна давать согласованный срез: использовать
зафиксированные ревизии либо короткое согласованное чтение с последующим
сохранением входов. Не держать транзакцию чтения открытой весь час симуляции.

После успешного завершения всех необходимых частей атомарно публикуется ссылка
на новый результат. Устаревшая параллельная попытка не заменяет более свежий
результат. При сбое или неполноте остаётся предыдущий успешный расчёт с датой.
Ручной допуск неполных данных имеет отдельное право, комментарий и видимую
пометку во всех производных рекомендациях и выгрузках.

Результаты SalesPlanning и Replenishment связываются идентификатором входного
расчёта спроса и версиями Inventory. При принятии предложения проверяются
текущие обязательства и доступный запас; устаревшее предложение не резервирует
товар только потому, что в старом прогнозе его хватало.

Нужны раздельные показатели: техническая полнота загрузки Ingestion, сверка
товарного баланса Inventory и пригодность входов конкретного расчёта.
Статус «все HTTP-запросы прошли» не означает «данные подходят для подсорта».

### 5.5. Параметры, деньги, хранение и обмен

- Для параметров, где оба уровня допустимы, предложенный приоритет: SKU в сезоне → SKU → категория в сезоне → сезон → категория → компания → стартовое значение. У каждого параметра свой разрешённый набор уровней; например, даты сезона не наследуются от категории. Источник эффективного значения виден и сохраняется в запуске.
- Закупочную цену хранить как отдельную явно названную Money-величину с датой действия и временем записи. Для сравнения сценариев фиксировать цену оценки; не переоценивать историческое решение сегодняшней ценой.
- Ожидаемые штуки и доли считать без промежуточного экранного округления. В PHP использовать точные дроби/десятичные значения, в SQL — `numeric`; bps предназначены для представления. Денежная арифметика не проходит через float.
- Набор расчёта, коэффициенты, объяснение и прогнозы дня сохраняются на каждую дату по ТЗ. Формат и срок хранения деталей определяются замером; удаление деталей не должно уничтожать обещанную воспроизводимость.
- Предлагаемый минимум хранения расчётных входов и результатов — 24 месяца, но не менее двух полных сезонов и хвоста их исходов; детали политики приведены в D3. Правило 90 дней raw Go-сервиса нельзя автоматически считать достаточным.
- Не создавать параллельный сборщик поверх существующих снимков. Расширять подтверждённый источник. Перенос raw Go в PHP требует отдельного ADR и контракта.
- Для массовых импортов — предварительная валидация, отчёт строковых ошибок, идентификатор партии и однозначное подтверждение записи. Повтор той же партии не повторяет движения. Автоматические факты и введённые человеком данные пишутся по своим правилам проекта.
- Для v2.7 рекомендован настоящий `.xlsx`, потоковый экспорт через OpenSpout; сохранить уже запланированный CSV SalesPlanning как отдельный формат. Обоснование, проверка совместимости и граница новой зависимости — в D5. Экспорт привязан к сохранённому запуску, учитывает права и нейтрализует формулы в текстовых ячейках.

## 6. Предложения по всем открытым вопросам раздела 10 ТЗ

Пункты ниже — ответы-предложения, а не сведения о фактическом бизнесе.
Числовые ориентиры автора не являются универсальными best practices.
Факты о кабинете, процессе склада и приемлемом риске подтверждаются отдельно.

### Q1. Какие поля реально есть в API Ozon?

**Предложение:** завершить матрицу «поле → метод → зерно → дата события → время
получения → глубина → качество → замена → зависимые этапы». Для каждого поля
приложить ссылку на фикстуру и результат сверки. Существующие исследования
переиспользовать, пробелы проверять разрешённым чтением реального кабинета
в отдельной задаче аудита. В тестах внешнее API не вызывать.

Отдельно подтвердить резерв по складам, физический приход возврата и его
доступность, частичную приёмку, перемещения и отмену до/после отгрузки.
Отсутствующее поле не заменять нулём. Прокси допускается только с согласованной
методикой и пометкой качества; невозможность собрать баланс ограничивает допуск
модели. До завершения аудита точный набор доступных полей остаётся неизвестным.

### Q2. Воронка по карточке или размеру?

**Предложение:** хранить исходное зерно и источник. Показы, клики и заказы
сравнивать на сопоставимом уровне. Если показы и клики доступны только по
карточке, отчёт воронки делать по карточке/артикулу; не размножать одни показы
на каждый размер и не выдавать распределение за измеренный SKU-факт.

Рекламную статистику не считать полной органической воронкой. Пока нет
сопоставимых источников, выводить «данных недостаточно». Реальное зерно
подтвердить аудитом 0.1; альтернативный уровень отчёта согласовать для 1.13.

### Q3. Источник своего склада и заказов поставщикам?

**Предложение:** первая версия — шаблон импорта CSV и ручной ввод через Inventory.
Остатки передаются с моментом среза, заказы — с устойчивым номером документа,
SKU, количеством и ожидаемой датой доступности. Физическое наличие, ожидаемый
приход и резерв — разные величины. Нужны явные исправления и сверка отгрузок,
описанная в §5.3. Заказы поставщикам не увеличивают сегодняшний доступный запас.

Подтвердить фактическую систему-источник, единицы измерения, часовой пояс,
ответственного и возможность выгружать движения. WMS-интеграцию в v1 не вводить.

### Q4. FBS уже используется или это новый канал?

**Предложение:** границу v1 оставить FBO. Если FBS уже расходует тот же склад,
его фактические резервы и списания должны уменьшать свободный товар Inventory
с первой версии; это учёт реального ограничения. Прогноз переключения спроса
на FBS и рекомендации по нему остаются фазой 4.

Наличие FBS нельзя определить из архитектурных best practices — это факт
процесса бизнеса. Без подтверждённого учёта всех потребителей общего склада
автоматически считать его свободный запас достоверным нельзя.

### Q5. Как выбрать долю переноса спроса p?

**Предложение:** сохранить стартовые 50% из ТЗ как гипотезу теневого режима;
сравнить сценарии 0%, 50% и 100% на одинаковых входах. Отдельно обучать
направления переноса и проверять устойчивость размера партий к выбору p.

Доля межкластерных отгрузок сама по себе не измеряет p: в данных нет покупателей,
которые отказались заказывать из-за отсутствия товара. Не объявлять p
«измеренным» только по маршрутам отправлений. Перед пилотом зафиксировать
значение на обучающем периоде; проверочный период для подбора не использовать.

### Q6. Дни фактической отгрузки на Ozon?

**Предложение:** завести редактируемый календарь отправок и исключений;
фактические даты использовать для проверки календаря. При фазе 3.6 переносить
рекомендованную отправку на ближайший разрешённый день раньше расчётной.
Два дня в неделю из ТЗ — начальная настройка, конкретные дни подтверждает склад.

Календарь не должен автоматически обещать доступный слот Ozon. Ограничения
вместимости и транспорта включать только отдельной задачей, если они реально
нужны. До фазы 3.6 ограничение можно показывать человеку явно, сохраняя
базовую модель фазы 2А.

### Q7. Есть ли данные о лимитах и слотах приёмки?

**Предложение:** не делать доступность такого API предусловием первой версии.
При отсутствии подтверждённого источника — ручной признак ограничения/даты
срока его действия и причина решения «нет слотов». Не отображать неизвестный
слот как доступный. Влияние на расчёт согласовать до его внедрения, а не
добавлять скрыто к LT.

Этап 3.7 выполняется после аудита источника и подтверждения пользы. Историческая
медиана приёмки не гарантирует возможность записаться на будущую дату.

### Q8. Тарифы Ozon на локализацию?

**Предложение:** не использовать тарифы в решениях обязательных фаз 0–2Б:
ТЗ исключает их из денежной модели. Текущую аналитику начисленной логистики
оставить самостоятельным отчётом.

Для будущего расширения — подтверждённый официальный источник, версия тарифа,
период действия, категория и условия применения. Не подменять неизвестный
будущий тариф средней стоимостью прошлых начислений. Актуальные тарифы
в рамках этого разбора не проверялись.

### Q9. К какому времени нужны отчёты и когда делать снимок?

**Рекомендуемый стартовый профиль:** готовность к 08:00 МСК, необходимые
источники готовы до 06:30, предупреждение о риске опоздания в 07:00;
расчёт компании после готовности входов занимает не более 60 минут.
При неполноте — предыдущий успешный результат с датой и причиной задержки.
Часовые значения являются проектными ориентирами, а не нормативом отрасли.

Рекомендуемая целевая настройка снимка — 23:30 МСК с версией политики измерения
по D3. До перехода измерить задержку обновления Ozon и длительность обхода
пачек; если время источника не соответствует этому профилю, изменить профиль
до теневого запуска. Текущее расписание продолжает собирать историю до готовности
замены. Старые даты не переобозначать. Разделение календарных и расчётных суток
проверить в прототипе по разделу 13 ТЗ.

### Q10. Какой объём SKU, складов и пользователей закладывать?

**Предложение для первого нагрузочного профиля:** 1 000 SKU в плане, 30 кластеров,
184 дня, до 10 одновременно работающих пользователей на компанию; складские
факты проверять на фактическом числе складов кабинета с запасом роста ×2.
Это инженерная гипотеза для замера, не подтверждённый объём бизнеса и не
новый продуктовый лимит. Профиль конкурентной нагрузки: пять компаний одновременно
готовы к расчёту, два тяжёлых задания исполняются параллельно, остальные ожидают
с ограничением возраста очереди. Профиль проверять на ресурсах целевого окружения.

При таком профиле один прогноз — до 5,52 млн ячеек на запуск, ещё до хранения
версий и детализации партий. Считать пакетом по товару со всеми кластерами,
выбирать входы пачками, измерять SQL, CPU, память и запись результатов.
В бэктесте и онлайн-расчёте использовать один PHP-движок. Новый Python-сервис
или аналитическое хранилище рассматривать только после замеров и отдельного ADR.

### Q11. Пороги бэктеста, допущения и пилот?

**Предложение:** протокол согласовать до проверочного запуска. Числа ниже —
стартовые предложения для обсуждения с бизнесом, не доказанные пороги качества.

| Показатель | Предложение |
|---|---|
| Проверочный период | Последние 8 недель пригодной истории; обучение отдельно |
| Критерий А | WAPE заказов не выше 35%, абсолютное смещение не выше 10% |
| Сравнение прогноза | Дополнительный предлагаемый гейт: WAPE не хуже простого сезонно скорректированного прогноза скорости на тех же пригодных днях и горизонте; включить в протокол до запуска |
| Критерий Б | 100% соблюдения ограничений; недопустимы отрицательный запас, повторный резерв и превышение общего товара |
| Критерий В | Не хуже ручной политики по дефициту и стоимости остатка; начальный допуск ухудшения — 0, допуск численной погрешности описать отдельно |
| Покрытие и выборка | Не ниже 80% потенциального спроса, 14 дней полного наличия на пару и 300 наблюдений суммарно — стартовые требования ТЗ |
| Сверка прототипа | Расхождение рекомендованных штук не более 1% по формуле ТЗ |
| Если истории недостаточно | Теневой режим 4–6 недель по ТЗ; отсутствие данных не считать успешным бэктестом |
| Пилот | Стартовая доля — 20% пригодных внутренних товаров на 6 недель; при недостаточной мощности сравнения продлить набор/наблюдение, не объявлять успех по одной доле каталога |

Метрики показывать также по категориям и значимым кластерам, чтобы агрегат
не скрывал провал сегмента. Подбор параметров по проверочному периоду запрещён.
При стохастической выборке LT сохранять seed, повторять симуляцию на нескольких
seed и показывать разброс. Одинаковые внешние поступления и одинаковый
потенциальный спрос использовать для модели и базовой линии.

Единица распределения пилота — внутренний товар с общим запасом и всеми его
кластерами/кабинетами: он не должен одновременно попасть в контроль и пилот.
Группы формировать с разбивкой по категории, спросу и выкупу по протоколу ТЗ.
Влияние общей вместимости склада на обе группы отдельно зафиксировать.

Уточнённый порядок настройки, фиксации протокола и принятия результатов — D7.

## 8. Проверки реализации

- Примеры раздела 12 проверять на точных исходных дробях с допуском ТЗ; округление до коробов проверять отдельно.
- Дополнительно проверить частичные исходы, таймаут и поздний возврат, смену справочника, отсутствие/нулевое значение, изменение данных после даты бэктеста.
- Для Inventory — два одновременных принятия на последний короб, повтор команды, отмена, частичная отправка, оба порядка «импорт списания / событие отгрузки», общий запас двух кабинетов.
- Для расчёта — падение посреди этапа, повтор сообщения, устаревшая попытка, атомарная публикация, сохранение предыдущего результата, изоляция компаний и кэша.
- Для симуляции — D = C + T + L, отсутствие отрицательного запаса, согласование товара и нетто-продаж, отсутствие двойного переноса и использования одной партии дважды.
- Для отчётов — дата, методика и надёжность результата видны в экране и выгрузке; права на решения проверяются сервером.
- Для перехода методик — прежние API сохраняют свою семантику; сезонный план не требует РРЦ и не превращает старые штуки в нетто-выкупы автоматически.
- Для параметров — проверить примеры наследования D8, версию и дату действия; сегодняшняя правка не меняет зафиксированные входы старого запуска.
- Для прав — проверить каждое действие по матрице D8, сочетание ролей, отзыв прав, чужую компанию и скачивание сформированного ранее экспорта.
- Для истории — воспроизвести исправление прошлого события, повтор наблюдения A → B → A и повтор обработки того же наблюдения; первые два меняют знание, последний не создаёт новую ревизию.
- Backend: `make lint stan deptrac structure-check` и затронутые `make test-*`; схема — `make db-rebuild-check`; API — экспорт схемы/типов и `make api-types-check`.
- Frontend: `make front-typecheck front-lint front-knip front-test front-build APP=seller`; соответствующие seller/admin E2E по изменению.
- Перед merge — обязательный зелёный CI, включая audit и E2E. Ревью кода Claude, для рисковых областей дополнительно оба прохода Codex по правилам проекта.

Повтор очереди является нормальным режимом доставки. Дедупликация не сводится
к блокировке воркера: сохраняется устойчивый ключ бизнес-операции и ограничение
БД. Основание — [Symfony 7.4: Idempotent Handlers](https://symfony.com/doc/7.4/messenger.html#writing-idempotent-handlers).

Разделение ORM-записи агрегатов и SQL-проекций остаётся в существующей БД;
отдельное хранилище для CQRS не требуется. См.
[CQRS: separate models in a single data store](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs).

## 9. Рекомендуемые решения по оставшимся вопросам

Ниже семь пунктов прежнего списка согласования получили конкретные проектные
решения D1–D7. D8 дополняет их правилами параметров и прав. Для реализации
рекомендуется принять этот набор целиком после проверки влияния на ADR.
Наличие рекомендации не означает, что изменение уже согласовано или выполнено.

### D1. Модули, владельцы данных и контракты

**Решение:** принять модульный PHP-монолит с Inventory и Replenishment и карту
зависимостей §4.3. Один владелец записи у каждого вида данных: Ingestion —
наблюдаемая внешняя реальность, Inventory — доступный товар и обязательства,
SalesPlanning — цель и прогноз спроса, Replenishment — рекомендация и решение.

Межмодульный DTO содержит область компании/подключений, версию и границу среза,
признаки качества и ссылки на происхождение. Методы чтения получают companyId
первым и ограниченный набор SKU/дат. Команда резервирования принимает ссылку
на рекомендацию, её версию, количество, дату отправки и ключ операции;
Inventory возвращает подтверждённый резерв или предметную причину отказа.
При отмене и повторе используется тот же идентификатор обязательства.

Транзакцией принятия управляет Replenishment/Application. Inventory не делает
самостоятельный commit внутри Facade и не пишет в таблицы Replenishment.
При ошибке откатываются резерв, решение и аудит. Между несколькими БД такую
транзакцию в первой версии не распределяем. Принцип согласованного чтения
опирается на [PostgreSQL: Transaction Isolation](https://www.postgresql.org/docs/16/transaction-iso.html).

**Почему:** источник фактов, обещание физического товара и вычисленная
рекомендация меняются по разным причинам. Владение данными устраняет
неоднозначность «кто исправляет остаток» и не требует новых сервисов.

**Проверка:** Deptrac, отсутствие межмодульного SQL, откат всей транзакции
при отказе резерва/аудита и неизменность результата повторной команды.

### D2. Старые отчёты, нетто-цель сезона и РРЦ

**Решение:** старые отчёты сохраняют текущую методику. Для планирования вводятся
явные идентификаторы методик и их версии: исходные заказы, нетто-выкупы по дате
заказа, зрелость и восстановление спроса. В ответе и экспорте указываются
методика, дата среза и единица. Нельзя назвать два разных процента одинаковым
`buyoutRate` без пояснения знаменателя.

Сезонную нетто-цель хранить отдельным видом агрегата внутри SalesPlanning:
сезон/версия, SKU подключения, V, версия профиля k и размерных долей, статус,
авторство и аудит. Этот агрегат — единственный источник V для сезонного подсорта.
Plan(d) — точная производная V и k с сохранённой версией; её не заставляем
помещаться в целочисленные строки старого плана с обязательной РРЦ.

Существующий план «штуки + РРЦ» и его HTTP-контракт не меняются автоматически.
Для сезонных целей публикуется отдельный типизированный контракт в том же
seller-контуре, например `/api/companies/{companyId}/seasonal-sales-plans`.
Это предметный путь, а не отдельный контур аутентификации. Точный контракт
фиксируется OpenAPI перед реализацией клиента.

Ввод V не требует цены и валюты. Денежная оценка выполняется по отдельно
заданной закупочной цене Inventory. Старый план можно использовать как
предзаполнение только после явного выбора смысла его штук; автоматического
перевода через текущий b нет. Одновременно действующие цели одной метрики на
SKU и дату конфликтуют по правилам согласованности, описанным в новом ADR.

**Почему:** обязательная РРЦ и целочисленная раскладка старого агрегата не
должны определять семантику сезонного прогноза. Не требуется ослаблять старую
валидацию или заполнять цену фиктивным значением.

**Проверка:** создание и утверждение цели без РРЦ, сумма Plan(d) равна V
в точной арифметике, повторное утверждение не создаёт второй действующей цели,
старые клиенты читают прежний контракт. Изменение уточняет ADR-040/041 и
не меняет их задним числом.

### D3. Время, исторические ревизии и срок хранения

**Решение:** календарная дата заказа в МСК определяет сезон, когорту и k.
Товарный баланс использует интервалы последовательных снимков с явными
границами. Целевая настройка старта прогона — 23:30 МСК, принятие новой политики
измерения зависит от аудита источника Q1/Q9. Номинальное время, фактические
начало/конец и качество измерения сохраняются; пачки не объявляются строго
одновременным физическим снимком.

У политики снимка есть версия и дата начала действия. Её смена не переименовывает
старую историю. Разрыв между границами, пропуск снимка и длинный сбор пачек
попадают в качество; точные допуски выбираются по измеренной задержке источника
и фиксируются до теневого запуска. Правило отнесения событий на точной границе
интервала явно закрепляется и проверяется тестом прототипа.

Принятую ревизию события сохранять неизменяемо в БД владельца данных с временем
события, временем фиксации знания, источником, исходным ключом и содержимым.
Исправление — новая ревизия, текущая таблица — проекция. Новая ревизия и
обновление проекции выполняются одной транзакцией; это добавление журнала
ревизий по отдельному ADR, а не немедленная замена всех фактов на event sourcing.
Неизвестное время события остаётся неизвестным либо явно оценённым.

Отделять наблюдение от raw-объекта: повторное получение состояния A после B
является новым наблюдением, даже если байты A уже есть в хранилище. Повтор
обработки того же наблюдения использует его прежний ключ и не создаёт ревизию.
Первичная загрузка прошлой истории получает реальное время получения знания,
не искусственную дату «как будто знали тогда».

Для запуска сохранять неизменяемый манифест входов с контрольными суммами,
версиями и доступной копией необходимых значений. Одного списка хэшей без
данных недостаточно. Зафиксировать также версию алгоритма, порядок обхода,
правила округления и seed при стохастической симуляции. Входы собирать коротким
согласованным чтением или по закреплённым ревизиям, симуляцию выполнять вне
долгой транзакции. Сохранённое решение человека не пересчитывается на месте.

Хранение: минимум 24 месяца от запуска и не раньше окончания двух полных
сезонов с хвостом их исходов — применяется более поздняя граница. Пока есть
незавершённые обязательства или исходы, необходимые записи не очищаются.
В PostgreSQL держать индексы запусков, коэффициенты, решения и актуальные
проекции; объёмные входы и дневные прогнозы старше 90 дней переносить в
неизменяемые архивы в объектном хранилище с company-scoped доступом.

Архив — данные продукта, а не raw внешнего API: новый порт/префикс и контракт
чтения описываются ADR. Возраст 90 дней меняет способ доступа, но не уничтожает
детали, обещанные ТЗ; исторический отчёт может подготавливаться асинхронно.
Политику 90 дней raw Go не менять автоматически: манифест расчёта должен
оставаться воспроизводимым независимо от неё. Стоимость архива измеряется P0/P4.

**Почему:** два времени и доступные прежние значения необходимы для честного
ответа «что система знала тогда». Архив уменьшает рост горячих проекций,
сохраняя проверяемость исходной рекомендации.

**Проверка:** восстановление запуска после исправления прошлого события,
смены сезонности и архивации деталей, сверка контрольных сумм, отсутствие
влияния поздней загрузки на прежнюю границу знания.

### D4. Общий товар, складской импорт и списания

**Решение:** внутренний SKU/размер получает UUIDv7 в пределах компании.
Marketplace SKU связывается с ним явно по подключению; баркод, название и
offerId сами по себе не подтверждают общность запаса. Начальная загрузка
предлагает совпадения, человек подтверждает; неоднозначность остаётся видимой.
Общий товар разных компаний не объединяется.

На старте поддержать логические места хранения и их явную связь с кабинетами;
если склад один, создаётся один логический склад. Импорт склада содержит
`source`, номер/версию партии, момент среза, место хранения, внутренний SKU и
количество. Для движения дополнительно нужны внешний номер документа,
дата, количество и ссылка на отгрузку/поступление. Повтор партии безопасен;
исправленный файл — новая версия, а не второй приход. Снимок заменяет
подтверждённое состояние в своих границах и не складывается с предыдущим.

В Inventory вести количественные движения и обязательства без бухгалтерского
P&L. Свободный остаток — подтверждённое наличие за вычетом ещё не отражённых
обязательств и внешних резервов. FBS и другие реальные потребители склада
попадают во внешние резервы/движения даже при FBO-only прогнозе.
Поступления от поставщиков обеспечивают отправки только со своей даты
доступности; один объём нельзя обещать двум отправкам.

Автоснятие резерва допускается только по сопоставленному количеству отражённого
списания. Частичное списание снимает ту же часть резерва. Если выгрузка не даёт
ссылок на движения, пользователь выполняет явную сверку; остаток не считается
достоверным для новых обязательств при неразрешённом расхождении.

**Почему:** отдельная сущность физического товара нужна уже для общего склада,
а не только для второй площадки. Это новый контекст по отношению к ADR-013,
который отвергал промежуточный товар для другого сценария себестоимости;
отличие и границы следует прямо записать в новом ADR.

**Проверка:** два кабинета претендуют на один остаток, частичная отправка,
повтор импорта, исправление среза, разные порядки отражения списания,
перенос ожидаемого прихода и невозможность дважды обеспечить один объём.

### D5. Закупочная цена и Excel

**Решение по цене:** источником оценки риска служит введённая или импортированная
закупочная цена единицы внутреннего товара в Inventory, с явной валютой, датой
действия, временем записи и авторством. Тарифы, хранение, обратная логистика и
маржа в неё автоматически не добавляются. `MarketplaceListingCost` сохраняет
свою семантику юнит-экономики; копирование из него возможно только с явным
подтверждением соответствия цены.

Все сравниваемые сценарии запуска используют одну закреплённую цену оценки.
Отсутствующая цена — неизвестное значение, не ноль: отчёты в штуках доступны,
денежная приоритизация и соответствующий допуск данных требуют заполнения.
Отмена, дефицит цены и исправление цены не переписывают архив исходного решения.
В v1 не вводить партионную бухгалтерскую себестоимость: FIFO из ТЗ относится
к движению единиц партии в симуляции последней поставки.

**Решение по Excel:** рекомендовать `openspout/openspout` для последовательной
записи табличных `.xlsx`. Официальный проект поддерживает такой сценарий;
ветка 4.x в опубликованном `composer.json` включает PHP 8.4. Это не замер
совместимости приложения: перед установкой проверить конкретный стабильный
релиз, PHP-расширения и контейнер, закрепить версию по правилам проекта и
включить зависимость в единое согласование. Сейчас пакет не установлен.
Основания: [OpenSpout](https://github.com/openspout/openspout) и
[требования 4.x](https://github.com/openspout/openspout/blob/4.x/composer.json).

Экспорт формировать асинхронно с привязкой к компании, фильтрам и runId,
потоково по ограниченным страницам. В книге — данные и лист с метаданными
методики/качества; значения вычисляются сервером, сложные формулы Excel не нужны.
Файл не публикуется по открытому адресу, права проверяются также при скачивании.
Временный экспорт хранить 24 часа как стартовую настройку; это не срок хранения
исходного расчёта. CSV остаётся для совместимого обмена и импорта Inventory.

**Почему:** отчёты первой версии — таблицы, для них не нужна модель всей книги
в памяти. Отдельная закупочная цена исключает смешение оценки риска с полной
себестоимостью площадки.

**Проверка:** большой экспорт при ограниченной памяти, точность денег,
повтор запроса, изоляция компаний, отозванное право на скачивание и совпадение
выгрузки с тем же runId на экране.

### D6. Операционные настройки и производительность

**Решение:** принять стартовый профиль Q9/Q10 для стенда и теневого режима:
08:00 МСК, входы к 06:30, предупреждение в 07:00, расчёт до 60 минут на компанию;
1 000 SKU, 30 кластеров, 184 дня, пять компаний в общей очереди и два тяжёлых
расчёта одновременно. Это проверяемые начальные условия, не обещание мощности
на неизвестном оборудовании и не ограничение количества клиентов продукта.

Ввести ограничение одного тяжёлого расчёта компании одновременно, очередность
между компаниями и контроль времени ожидания. Логический запуск дополнительно
идентифицируется срезом и версиями входов. Повтор готового запуска с теми
же входами использует прежний результат; изменившийся вход создаёт новую
ревизию расчёта. Распределение внутри расчёта идёт по внутреннему товару со
всеми связанными кабинетами и кластерами. Общий пул товара не делить между
независимыми воркерами без согласования обязательств.

Измерять время подготовки/симуляции/записи, пиковую память, рост БД/архива и
возраст очереди. В HTTP остаются чтение результата и запуск задания. Прогресс
и отказ доступны пользователю. Периодический запуск следует существующему
циклу проекта; отдельный transport или сервис добавляется только по замеру
конкуренции с загрузкой и отдельному решению.

При неизвестных днях отгрузки фаза 2А показывает расчётную дату с ручным
решением; фазу 3.6 включать только после заполнения реального календаря.
Не назначать выдуманные вторник/пятницу как фактический процесс бизнеса.
Слоты остаются неизвестными, пока нет подтверждённого источника или ручной
проверки; рекомендация не считается бронью Ozon.

**Проверка:** полный профиль на целевом стенде, очередь пяти компаний, сбой
одной компании без остановки остальных, повтор после падения и сохранение
последнего успешного результата при пропуске срока.

### D7. Бэктест, пороги и решение о пилоте

**Решение:** в обучающей части использовать последовательные исторические
точки запуска с горизонтом LT, оценивая только доступные тогда данные.
Последние восемь недель пригодной истории оставить отдельным проверочным
периодом. После настройки зафиксировать параметры и протокол до его открытия.
Случайное перемешивание временных наблюдений не использовать. Принцип
проверки на будущих относительно обучения данных описан в
[Forecasting: Principles and Practice](https://otexts.com/fpp3/toolbox.html#time-series-cross-validation).

Для первого протокола рекомендованы ориентиры Q11: WAPE ≤35%, абсолютное
смещение ≤10%, 100% соблюдения ограничений, критерий В без ухудшения и
покрытие ≥80%. Дополнительно предложено требовать WAPE не хуже простого
сезонно скорректированного прогноза скорости на том же наборе наблюдений.
Это проектные пороги риска: источники best practices обосновывают процедуру
проверки, но не делают значения 35% и 10% универсальными.

До запуска определить сегменты принятия решения по категориям/спросу и
правила достаточности выборки. Минимумы ТЗ проверять без исключения неудобных
SKU ради зелёной метрики. Для недостаточного сегмента — статус «недостаточно
данных» и ограниченный допуск, а не успешная оценка. После неудачного теста
не подбирать параметры на его результатах и не объявлять повтор на тех же
данных независимым подтверждением: нужен новый отложенный период либо
следующий заранее зарегистрированный теневой цикл.

Пилот начинать с 20% пригодных внутренних товаров на шесть недель;
товар с общим запасом и его кабинеты/кластеры находятся в одной группе.
Формирование групп — по протоколу Q11. До старта оценить, хватает ли числа
независимых товаров и наблюдений для выбранного допустимого ухудшения.
Если шести недель недостаточно, продлевать наблюдение или сохранять
ограниченный пилот. Окончание сезона не является основанием снизить пороги.

**Проверка:** сохранённый протокол и входы, отдельные отчёты обучения/проверки,
сравнение с базовой политикой, анализ чувствительности p и LT, воспроизводимый
результат и явный уровень допуска из ТЗ.

### D8. Параметры и права без универсального конструктора ролей

**Решение по параметрам:** использовать порядок §5.5, для каждого параметра
перечислить разрешённые уровни, тип, диапазон, единицу и дату действия.
Эффективное значение вместе с источником фиксируется в запуске. Изменение
по умолчанию действует со следующего расчётного дня. Исправление прошлого —
отдельная ревизия с причиной; старый опубликованный запуск не переписывается.

Обязательные примеры проверки наследования:

- H категории =14, H сезона =7, H конкретного SKU =10 → используется 10.
- Для того же SKU задан H в конкретном сезоне =5 → используется 5.
- Есть общий H SKU =10 и H категории в сезоне =6 → используется 10, поскольку SKU специфичнее категории; источник виден рядом.
- Даты сезона нельзя переопределить категорией; неизвестное значение не является нулём и не отменяет проверку обязательного параметра.

**Решение по правам:** в Identity ввести фиксированные company-scoped назначения
трёх профилей; комбинация профилей допустима. Владелец компании получает все
права, новые назначения по умолчанию отсутствуют. Существующая роль Owner
не превращается в роль системного администратора. Изменение модели прав
уточняет ADR-002 и требует отдельного рассмотрения до миграции.

| Действие | Просмотр | Редактирование | Решения | Owner |
|---|---|---|---|---|
| Читать отчёты и экспортировать доступный расчёт | Да | Да | Да | Да |
| Править план, параметры, справочники и импорт Inventory | Нет | Да | Нет | Да |
| Явно допустить неполные данные с комментарием | Нет | Да | Нет | Да |
| Принять, изменить объём/дату, отклонить рекомендацию, связать поставку | Нет | Нет | Да | Да |
| Назначать профили участникам компании | Нет | Нет | Нет | Да |

Ручной допуск неполноты не отменяет жёсткие ограничения: чужую компанию,
несопоставленный товар для резервирования, отрицательный запас и превышение
доступных обязательств нельзя разрешить комментарием. Права проверяются
сервером на действии и объекте; полученный ранее файл не даёт вечного доступа
к скачиванию. Такой подход следует принципам минимальных прав и проверки
каждого запроса из [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).

**Проверка:** матрица действий, сочетания профилей, разные компании, отзыв
назначения между открытием формы и сохранением, версия параметров и аудит.

## 10. Какие подтверждения действительно остаются

Архитектурные вопросы теперь имеют рекомендуемые решения. Остались проверяемые
факты, которые нельзя достоверно получить из best practices. Вместо нового
круга общих вопросов нужны три набора артефактов:

| Подтверждение | Кто/когда | Если подтверждения нет |
|---|---|---|
| Матрица API: поля, зерно, даты, задержки, наличие резерва/возвратов/поставок, примеры и сверка | Разработчик с доступом к разрешённому кабинету, P0 | Историю продолжать копить; непроверенную возможность не объявлять реализованной; неподдержанный этап не допускать к рабочему использованию |
| Образцы склада: реальный файл, перечень всех потребителей запаса, товарные связи, отражённые списания, закупочная цена и календарь | Ответственный за склад/планирование вместе с разработчиком, до P3/P8 | Работать на тестовых данных или явно ограниченной области; не принимать обеспеченность общим складом как доказанную |
| Замер и протокол: целевые ресурсы, время готовности, профиль нагрузки, выбранные сегменты, риск и достаточность пилота | Разработчик и ответственный за бизнес-результат, до P7/P9 | Использовать рекомендуемые значения для стенда/тени; рабочий допуск выдавать только после выполнения гейтов |

Для реализации подготовить предметные ADR по границам/владению, семантике
сезонной цели, времени/истории, резервам и правам. Сверить затронутые принятые
ADR-002/006/013/034/040/041 и указать, что именно уточняется. В плане первой
реализационной задачи собрать соответствующие пункты единого согласования
по CLAUDE.md; не спрашивать разрешение повторно на каждом техническом шаге.
Пакет OpenSpout и новый архивный порт входят в это согласование, а не
устанавливаются или создаются в задаче редактирования плана.
