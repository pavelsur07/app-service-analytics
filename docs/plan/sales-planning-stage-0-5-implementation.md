# План 0.5: история расчётов и согласованное обновление

**Результат:** каждый опубликованный прогноз имеет неизменяемый снимок входов и результатов; текущий указатель всегда соответствует одному согласованному набору версий. Зависимость — [0.4](sales-planning-stage-0-4-implementation.md). Остаток и скорость добавляются в 0.6 без перезаписи старых снимков.

## Ключ снимка и схема

PK: `(company_id, marketplace_account_id, marketplace_sku, business_date, algorithm_version, input_fingerprint)`. В строке хранить `as_of_business_date`, `calculated_at`, версии плана/настроек/заказов, границы окон, исходные количественные компоненты, точную дробь коэффициента, источник коэффициента, прогноз, ожидаемый итог, отклонение, сигнал и качество. Предусмотреть nullable поля `velocity`, `velocity_window`, `inventory_source_snapshot_key`, `inventory_formula_version`, `available_stock`, `stock_cover_days` для 0.6; ранние снимки честно содержат `NULL`, а новый алгоритм 0.6 получает новую версию. `planning_calculation_current` имеет PK компании/кабинета/SKU/даты и FK на **весь** ключ snapshot, время публикации и порядок входного поколения. Ни одна таблица не объединяет кабинеты по одному SKU.

Fingerprint — каноническое кодирование только входов: ключ когорты; `asOfBusinessDate` в `Europe/Moscow`; точные границы 30-дневного и 14-дневного окна; версия плана и количество, версия настроек, версия полного наблюдения Ingestion, версия алгоритма; после 0.6 — ключ/версия Inventory. Использовать упорядоченные поля и SHA-256; выходы в fingerprint не входят. Повтор тех же входов даёт тот же PK, смена дня либо исправление старого заказа — новый. Полный набор входов сохраняется для ручной проверки хэша.

## Публикация и расписание

1. На каждом тике выбрать ограниченной keyset-страницей SKU с действующим планом **или** историей, по компании и кабинету из собственных таблиц Planning. Для первой истории без плана нужен SKU после ручной/импортной записи; пустой кабинет не создаёт расчёт. Один `RecalculatePlanningSkuMessage` ограничен одним SKU и максимум 90 днями; большие диапазоны разделять на сообщения. Периодические тики пересчитывают окна и старые когорты при исправленном исходе, даже если новый заказ сегодня не пришёл.
2. Обработчик читает все страницы Ingestion одной закреплённой версии и настройки/план, рассчитывает структуру 0.4. Перед публикацией в транзакции под блокировкой ключа когорты снова сверяет версии источника и настройки/план. Если хоть одна изменилась, откладывает новый расчёт; старую смесь не публикует. Вставить immutable snapshot через конфликт по PK, затем обновить current лишь для не более старого поколения. Повтор сообщения, конкурентные воркеры и сбой между вставкой и указателем не создают неконсистентного current.
3. API `/daily` возвращает опубликованные снимки и их качество. Если источник после публикации изменился либо время полной загрузки старше порога, статус `stale` вычисляется при чтении; числа снимка остаются прежними, новые заказы в него не подмешиваются. Если полного расчёта ещё нет — `missing`, не нули. `/calculations` выдаёт keyset-страницы 50/200 снимков с причиной сигнала и позднее подтверждённым фактом **той же когорты**, причём поздний факт помечен отдельным временем оценки.
4. `docker-compose.prod.yml` сейчас запускает опрос Ozon раз в 1800 секунд; это нельзя молча называть 900. Планировщик Planning запускается отдельной службой с 900 секундами и общей существующей `async_calc`. Если продуктовый SLA требует обновления заказов каждые 15 минут, изменить интервал Ozon в отдельной проверке нагрузки и отметить это в релизе; сам пересчёт не делает источник свежее.

## Проверки и завершение

Тестировать повтор и гонку двух воркеров, изменение плана/настроек/источника во время расчёта, смену дня без событий, поздний выкуп, старый заказ после backfill, сбой транзакции, курсор истории, одинаковый SKU двух кабинетов, сравнение вчерашнего прогноза с сегодняшним фактом. Проверить `make db-rebuild-check`, `make lint stan deptrac structure-check`, затронутые backend-тесты, `make api-doc-export api-types api-types-check`, `make audit`; релизные проверки и ревью по `AGENTS.md`.

**Готовность:** каждая цифра экрана относится к одному snapshot, старая версия не затирается, повтор пересчёта идемпотентен, задержка источника явно показана.
