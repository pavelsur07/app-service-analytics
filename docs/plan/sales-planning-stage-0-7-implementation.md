# План 0.7: экран планирования продаж для seller

**Результат:** менеджер открывает один SKU выбранного кабинета и видит план, заказы, факт, прогноз, сигнал, остаток, скорость и историю на одном экране. Зависимости — [0.3](sales-planning-stage-0-3-implementation.md), [0.5](sales-planning-stage-0-5-implementation.md), [0.6](sales-planning-stage-0-6-implementation.md). Экран не заменяет существующий отчёт выкупа.

## Экран и данные

Выбирать кабинет из действующего списка подключений компании, после смены кабинета сбрасывать SKU, период и курсор истории. SKU искать через `GET /planning/accounts/{accountId}/skus?search&limit&cursor`, показывать подпись и артикул, но ключом оставлять `marketplaceSku`. Все запросы идут через `createCompanyApiClient`, состояние — TanStack Query, ключи — `companyQueryKey(companyId, 'planning', ..., {accountId, sku, from, to, cursor})`. При смене компании или кабинета прежний ответ не отображать даже кратковременно; после правки и импорта инвалидировать только ключи соответствующих компании/кабинета/SKU. Типы — только из сгенерированного `packages/api-schema`, без ручного редактирования генерируемых файлов.

Таблица по дате **заказа**: план, заказано, незавершённые пригодные к прогнозу, прогноз, подтверждённый факт, ожидаемый итог, отклонение в штуках/процентах и сигнал. Неизвестные исходы показывать отдельно. Над таблицей — коэффициент выкупа, размер выборки, `sku/fallback`, доступный остаток и его время, скорость/окно, дни покрытия, последнее полное обновление заказов и время расчёта. По жёлтому/красному сигналу открыть объяснение с входными числами и настройками. Неполный/устаревший источник, отсутствие плана и будущая дата получают собственное состояние, а не цвет.

Редактор отправляет `expectedVersion`, показывает `409` и актуальное значение без потери ввода. Импорт показывает ошибки по строкам, новые/изменяемые/совпадающие записи, затем применяет `previewId`; при истечении или конфликте предложить новый просмотр. История keyset-страницами показывает старый коэффициент, прогноз, источники и позднейший факт той же когорты; исторический остаток брать только из сохранённого snapshot. Не подставлять сегодняшний остаток в прошлую дату.

## Проверки

Vitest + типизированный MSW: переключение двух компаний и двух кабинетов с одинаковым SKU; сброс выбранного SKU; поздний ответ старого запроса; версия плана/409; preview ошибочного XLSX; нулевой план; нулевая скорость; неполные данные; причина сигнала и история. Playwright: вход seller → выбор кабинета/SKU → ручной план → изменившийся факт/прогноз → просмотр предыдущего снимка. Проверить доступность таблицы и сигнала текстом, мобильную ширину и клавиатуру.

Выполнить `make front-typecheck front-lint front-knip front-test front-build APP=seller`, `make api-types-check`, `make test-e2e` в подготовленном окружении и `make audit`; типы API должны быть уже сгенерированы из backend. Общий клиент, если затронут, проверять с существующими seller-сценариями. Коду нужен Claude по `AGENTS.md`.

**Готовность:** все десять вопросов исходного ТЗ доступны по выбранному SKU, причины сигнала и качества понятны, кабинеты в данных и кэше разделены.
