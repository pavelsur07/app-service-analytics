# Планирование продаж — этап 0

Только ввод и хранение плана. Сравнения с фактом нет.

## Основа

- План — продажи по дням в разрезе отдельного SKU: количество и цена (РРЦ).
- Период выбирается под задачу: день, неделя, месяц, сезон (3–4 месяца).

## Модель данных

Полностью — ADR-040.

```
sales_plan            id, company_id, marketplace_account_id, name, date_from, date_to,
                      currency, status (draft | approved | superseded | discarded | cancelled),
                      lineage_id, version_number, version
sales_plan_line       PK id; UNIQUE (company_id, sales_plan_id, sku, plan_date) → quantity, price_minor
sales_plan_day_claim  PK (company_id, marketplace_account_id, sku, plan_date) → sales_plan_id
```

- Хранится всегда день, строки плотные. Неделя, месяц, сезон — сумма дней.
- Выручка плана = `quantity × price` — вычисляется, не хранится.
- Цена — минорные единицы; валюта одна на план, в шапке.
- Один утверждённый план на SKU × день — ключ `sales_plan_day_claim`.
- Лимиты: период до 184 дней, до 1000 SKU, строк на версию — по замеру
  в 0.4 (до замера 30 тыс.).

## Ввод

1. Выбрать подключение и диапазон дат.
2. По каждому SKU ввести количество за период и РРЦ.
3. Раскладка по дням:
   - равномерно;
   - количество целое, остаток — первым дням (наибольший остаток);
     сумма дней строго равна введённому;
   - цена не делится — копируется в каждый день.
4. Правка отдельного дня (акция, другая цена). Итог периода
   пересчитывается из дней.
5. Импорт и экспорт CSV: `sku | qty | price` на диапазон.
   SKU, которого нет в каталоге подключения, — ошибка строки, не тихий пропуск.

## Просмотр

- Таблица SKU × период; переключение группировки: день / неделя / месяц / весь план.
- Итоги по SKU и по плану: штуки, выручка плана.

## Жизненный цикл

- `draft` — свободно редактируется; отказ — `discarded`.
- `approved` — зафиксирован. Правка утверждённого — новая версия
  (копия в `draft`), исходная не переписывается. Отмена — `cancelled`,
  дни освобождаются.
- Ничего не удаляется. Каждое изменение плана — в аудит-журнал:
  кто, когда, точные значения дней до и после действия.

## Где живёт

**Отдельный модуль `SalesPlanning`** (ADR-040).

Почему не в Ingestion: Ingestion собирает данные с площадок, план вводит
человек. Разные источники, разные правила записи (факты — DBAL upsert,
план — ORM как редактируемые данные), разная скорость изменений.
Смешивание раздувает Ingestion и связывает два независимых цикла.

**Зависимости**

```
SalesPlanning → Identity → Shared
SalesPlanning → Ingestion (только Facade, только чтение каталога SKU)
```

- Каталог SKU подключения нужен для выбора товара и проверки импорта.
  Чтение — через `IngestionFacade`, по образцу PriceMonitoring (ADR-016).
  Обратного вызова нет.
- На этапах сравнения с фактом тот же Facade отдаст агрегаты продаж;
  на этапе 0 этого вызова нет.

**Раскладка**

```
api/src/SalesPlanning/
  Domain/          SalesPlan, SalesPlanLine, распределение по дням
  Application/     сценарии: создать, распределить, править день,
                   утвердить, импорт/экспорт
  Infrastructure/  репозитории, DBAL-запросы списков
  Ui/              контроллеры /api/companies/{companyId}/sales-plans/...
apps/seller/       раздел «Планирование»
```

## Решения (согласовано)

1. Новый модуль `SalesPlanning` — оформляется ADR.
2. Межмодульное чтение `SalesPlanning → IngestionFacade` — только каталог SKU
   подключения, только чтение. Новый метод Facade.
3. Импорт и экспорт — CSV, без новых зависимостей. `.xlsx` — отдельной задачей.
4. Артикул плана — SKU площадки в рамках подключения. Переход на артикул
   продавца — при появлении второй площадки, отдельным решением.
5. Пересечение утверждённых планов по одному SKU и дню запрещено.

## Этапы

Каждый этап — отдельный PR, доводится до merge.

**0.1 ADR**
- ADR-040: модуль `SalesPlanning`, границы, зависимости, модель, решения 1–5.
- Кода нет: пустой модуль не заводится (`structure.md`), папка — в 0.2.

**0.2 Модуль, схема и домен**
- Папка `api/src/SalesPlanning`, слои Deptrac, `structure-check`,
  маппинг Doctrine, `structure.md`, «Модули» в `CLAUDE.md`.
- Таблицы шапки, строк и занятых дней, Entity, Builder, одна миграция.
- Распределение количества по дням (наибольший остаток), цена в `Money`.
- Unit-тесты распределения и денежной части.

**0.3 Каталог SKU через Facade**
- Два метода `IngestionFacade` (ADR-040 п. 4): поиск SKU подключения
  с лимитом — для выбора; проверка списка SKU одним запросом — для
  создания плана и импорта.
- Integration-тест изоляции между компаниями.

**0.4 API: создание и просмотр**
- Создать план-черновик: подключение, диапазон дат, SKU, количество, РРЦ.
- Просмотр: SKU × период с группировкой день / неделя / месяц / весь план,
  итоги по SKU и плану. DBAL → readonly DTO, лимит.
- Версия плана в ответе и в запросе на изменение (ADR-008).
- Аудит ввода SKU за период: точные значения дней до и после (ADR-040 п. 10).
- OpenAPI, типы фронтенда.

**0.5 Экран «Планирование»**
- Раздел в `apps/seller`: список планов, создание, ввод по SKU, просмотр.
- Ключи кэша через общий хелпер.

**0.6 Правка дня**
- Изменение количества и цены отдельного дня в черновике; удаление SKU
  из черновика.
- Итог периода — из дней.
- Аудит правки дня и удаления SKU.

**0.7 Утверждение, версии, отмена**
- Таблица занятых дней; `draft → approved` — вставка с перехватом
  конфликта, не «проверить, затем записать»; утверждение по версии.
- Правка утверждённого — копия в новый черновик; утверждение новой
  версии — `superseded` прежней и освобождение её дней.
- Отказ от черновика (`discarded`), отмена утверждённого (`cancelled`)
  с освобождением дней.
- Аудит переходов статуса.

**0.8 Импорт и экспорт CSV**
- Экспорт плана: `sku | date | qty | price`.
- Импорт `sku | qty | price` на диапазон: построчные ошибки,
  неизвестный SKU — ошибка, не пропуск. Всё или ничего.

## Не входит в этап 0

Сравнение с фактом, отклонения, прогноз выполнения, раскладка
по сезонности и дням недели, план от прошлого года, сценарии,
связь с остатками и закупками.
