# product-research-ozon — этап 3: суточный кэш категорий

Дата: 01.11.2026. Статус: завершён, Symfony выложен за закрытым флагом. Основание: ADR-050, этап 3 общего плана.
Решения уже приняты: один серверный MPStats-токен, отдельный кэш каждой компании,
Python владеет источником, Symfony — локальной проекцией и seller API.

## Цель и границы

Повторный поиск и выбор категории не вызывают MPStats. Полный подтверждённый
справочник хранится 24 часа с момента загрузки источника, а не последнего поиска.
Python PostgreSQL хранит только пути/ID и техническое состояние; суммы из
category/list не сохраняются в БД и не участвуют в расчётах. Symfony PostgreSQL
содержит атомарную локальную проекцию для поиска и проверки категории проекта.
Redis для данных справочника не используется.

Сохраняем внутренний v1 (страницы <=100, revision, generated_at, opaque cursor).
PHP-фоновая команда работает с явно заданной компанией, --once либо своим
циклом; новых транспортов/маршрутов Messenger, Facade и межмодульных связей нет.
Пользовательский HTTP не вызывает Python, не ждёт MPStats и не запускает
фоновую загрузку синхронно. Первая синхронизация выполняется командой до
включения компании. UI относится к этапу 7, production-активация Python — к
этапу 8. Этот этап поставляет код/проверки/схему Symfony за закрытым флагом.

## Политика кэша

- Namespace: company_id + source_connection_id + версия семантики каталога.
  Один токен не разрешает общее использование каталога разных компаний.
- TTL ровно 24 часа; частые чтения не продлевают TTL. Source ID несекретен и
  одинаково настраивается у PHP/Python; credential generation — строго возрастающее
  целое 1..2147483647, меняется вместе с ключом при ротации.
- В кэше только полностью проверенная генерация. Ошибка/обрыв/потеря lease
  оставляет предыдущую генерацию неизменной; publisher проверяет fencing owner.
- Пустой подтверждённый каталог допускается. Отсутствующий, просроченный или
  не обновлённый из-за ошибки каталог даёт 503, а не успешный пустой поиск.
  Просроченная генерация сохраняется для восстановления, но не используется
  для нового выбора. Существующие проекты сохраняют прежний путь категории.
- Поиск от трёх букв, литеральные wildcard-символы, полный путь, лимит 50/200.
  Путь принимается только из актуальной проекции; revision записывается в проект.
- Python читает MPStats только при истечении TTL. DB lease/fencing защищает
  заполнение компании, общий gate подключения — квоту/одновременность токена.
  429 учитывает Retry-After без сокращения, 401/403 ставит паузу поколения ключа;
  сеть/5xx — контролируемый retry_at, без sleep в HTTP/удержания транзакции.
- До явной настройки catalog_enabled, токена, поколения, source ID и квоты
  живые запросы выключены. В dev нет egress к MPStats, тесты используют fixtures/mocks.
- Внутренние cursors подписаны, привязаны к компании/подключению/revision и сроку;
  неверный или устаревший cursor — conflict. PHP проверяет все страницы и единые
  revision/generated_at до одной транзакции публикации; прогресс не публикуется частями.

## Этапы реализации

### 3.1. Источник, правила, контракт (TDD)

Цель: зафиксировать действительный формат и правила TTL/страниц.
Задачи: перенести захваченный в этапе 0 category/list в проверенную fixture с
checksum/provenance; pure DTO/parser и проверки путей/ID, лимитов, дублей.
Готовность: U01–U04, C01; сторонние метрики игнорируются, float для денег не возникает.

### 3.2. Python-кэш и внутренний endpoint

Цель: один запрос источника на компанию за TTL, полная публикация и безопасные повторы.
Задачи: одна Alembic-миграция технического кэша; store/lease/gate; ограниченный
HTTP-клиент MPStats; signed keyset cursor; реализация существующего GET /categories.
Готовность: U05–U07, I01–I05, C02; migration up/down/up на пустой локальной БД.

### 3.3. Проекция и фон Symfony

Цель: поиск и проверка категории без сетевого вызова из seller HTTP.
Задачи: одна Doctrine-миграция, Entity/Builder для технической схемы, DBAL-порты,
фоновая company-scoped команда, bounded service client, TTL/fencing публикации.
Заменить unavailable lookup на чтение свежей проекции; сохранить тестовый адаптер этапа 2.
Готовность: I06–I10, F01–F03; source/tenant scope и сбой между страницами проверены.

### 3.4. Seller API и схема

Цель: ограниченный поиск по полному пути с явной недоступностью каталога.
Задачи: thin controller/DTO, права seller, строгие параметры, OpenAPI/TS генерация.
Готовность: F04–F07, C03; create/copy принимают только подтверждённые пути,
rename не переписывает старые проекты, flag=false закрывает новый endpoint.

### 3.5. Приёмка и доставка

Цель: проверенный воспроизводимый результат в репозитории и разрешённом production-контуре.
Задачи: гейты PHP/Python, полный rebuild собственной локальной БД, независимые
5A/5B Codex CLI в новых сессиях при недоступном Claude, разбор, PR/зелёный CI/merge,
явная миграция Symfony после штатного deploy gate, smoke и постоянный отчёт.
Python в production не включается раньше этапа 8; это не объявляется live-приёмкой MPStats.
Готовность: G01–G08, без ослабления проверок и без чужих файлов в diff.
