## 1. Задача и границы обещания

Пользователь выбирает рекламную кампанию, задаёт максимальный расход за сутки
и время ежедневного запуска и остановки. Conwix запускает кампанию только
в разрешённом окне и при наличии бюджета; останавливает по расписанию,
при приближении к лимиту или при потере достоверного контроля.

Контур остановки не зависит от Symfony Messenger, очереди истории и загрузки
аналитических отчётов. Планировщик с сохранёнными сроками всё равно необходим:
отказ от общей очереди не означает отсутствие диспетчеризации и ожидания ресурсов.

Стратегия ограничивает расходы, но не гарантирует равномерный расход или полное
освоение бюджета. Управление темпом расходования и ставками — отдельная стратегия.

Нельзя обещать «ни копейкой больше» и остановку показов точно в заданную секунду:
Conwix контролирует сроки своих действий, но зависит от свежести данных,
доступности Ozon и фактического применения команды. Нулевой суточный перерасход
требует подтверждённого жёсткого ограничения на стороне площадки. В изученных
источниках такое ограничение для предлагаемого сценария не подтверждено.

### Ограничения исследования

Основная спецификация `https://docs.ozon.ru/api/performance/` не вернула
читаемого содержимого веб-инструменту; загрузка через HTTP-клиент завершилась
циклом перенаправлений. Переходы из официальных новостей на методы и лимиты
также не дали содержимого. Поэтому точные пути/схемы методов записи, численные
квоты, TTL токена, пакетные размеры и SLA не считаются проверенными.

Доступны официальные новости Ozon for dev, публикация российского seller.ozon.ru
и русскоязычная справка на docs.ozon.kz. Последняя содержит выбор договора:
применимость её условий к целевому российскому кабинету необходимо подтвердить
по российской справке или поддержке. Значения из сторонних SDK и блогов
не использованы как контракт Ozon.

Свежий HTTP-ответ не доказывает свежесть расходов. Не найден документированный
верхний предел задержки статистики или применения остановки. Упоминание
финальности прошлых дней в [S1] не распространяем на все финансовые отчёты:
недельные корректировки [S4] учитываются отдельной сверкой.

## 3. Рекомендуемые ответы на продуктовые вопросы

Все решения ниже — предлагаемые defaults MVP, а не уже согласованные требования.

| Вопрос | Рекомендуемое решение | Обоснование |
|---|---|---|
| Какие кампании поддерживать? | Существующие обычные кампании «Оплата за клик», только проверенные типы/стратегии | Для них описан оперативный источник; не смешивать разные модели списания |
| Бюджет на кампанию или кабинет? | На одну кампанию; общий бюджет группы/кабинета — следующий этап | Общий лимит требует резервирования расходов нескольких одновременно работающих кампаний |
| Что означает сумма? | Расход CPC с НДС, RUB, целые копейки | Совпадает с базой оперативной метрики; не путать с пополнением или остатком счёта |
| Бонусы и оплата за заказ? | Не подключать бонусные и смешанные сценарии до проверки разделения расходов | Нет подтверждённого единого счётчика денежных списаний для этих сценариев |
| Какие сутки? | Сутки отчётности Ozon; предполагаемый default `Europe/Moscow` только после подтверждения часового пояса API | Дневной агрегат нельзя надёжно пересчитать на произвольный часовой пояс |
| Как показывать время? | Явно подписывать часовой пояс рядом с расписанием; хранить IANA zone и UTC-моменты выполнения | Исключает зависимость от часового пояса браузера/сервера |
| Ночное окно? | В MVP одно окно внутри суток, `start < stop`; переход через полночь отложить | Позволяет однозначно связать окно и дневной бюджет; позднее разбить ночное окно по отчётным дням |
| Когда сбрасывается бюджет? | В новый отчётный день, после получения валидных данных именно этого дня | Пустой ответ или вчерашний снимок не равен нулевому расходу |
| Учесть расход до включения стратегии? | Да, весь расход кампании за день | Иначе переподключение позволяет обойти лимит |
| Переносить остаток? | Нет | Суточное ограничение не превращается в накопительный бюджет |
| Растягивать расход? | Нет в MVP | Это отдельная задача управления темпом и эффективностью |
| Снижение лимита? | После применения версии сразу пересчитать остаток; при исчерпании запросить остановку | Снижение не отменяет уже понесённые расходы |
| Повышение лимита после бюджетной остановки? | Само повышение не запускает кампанию; отдельное явное возобновление | Избегаем неожиданного возобновления трат |
| Ручное выключение на Ozon? | Не включать обратно автоматически; при необъяснимом статусе фиксировать конфликт и приостанавливать автозапуск | Не бороться с пользователем или другими автоматизациями |
| Ручное включение вне окна? | При действующей стратегии запросить остановку и показать конфликт | Для передачи управления пользователь сначала отключает стратегию |
| Как отключить стратегию? | По умолчанию сначала остановить кампанию и подтвердить состояние | Выход из управления не должен молча оставлять активные расходы |
| После аварии? | После защитной остановки требовать явное возобновление; после штатного исчерпания бюджета разрешать следующий день | Не допускать циклов старт/стоп и внезапных расходов |
| Менять недельный бюджет Ozon? | Показывать отдельно; не выводить автоматически как `7 × суточный лимит` и не повышать скрыто | Минимумы, недельный период и распределение Ozon имеют собственную семантику |

Для выпуска нужно подтвердить допустимый риск перерасхода в рублях/процентах.
Если пользователь требует абсолютный ноль при полном отказе Conwix или Ozon,
а подходящего ограничения площадки нет, такой режим не выпускать под этим обещанием.

## 4. Распределение ответственности

| Компонент | Ответственность и данные |
|---|---|
| Новый PHP-модуль `Advertising` (рабочее имя) | Настройки, версии, авторизация, привязка кампании к компании/кабинету, пользовательский аудит, seller API и представление статусов |
| Новый `services/ozon-ads-controller` на Go (рабочее имя) | Планировщик, оперативные расходы, расчёт остатка/запаса, решение, вызов Ozon, подтверждение результата |
| БД контроллера | Применённые версии настроек, снимки оперативных расходов, сроки, аренды исполнения, журнал операций и причин решений; без ключей |
| Identity и внутренний контракт PHP | Авторизованная выдача подключений и ключей с ограниченным сроком действия разрешения; принадлежность и отзыв |
| Ingestion / ozon-fetcher | История и финансовая сверка; не источник срочного решения |
| Независимый наблюдатель | Просроченные проверки, потеря владельца, незавершённые остановки, уведомления; по умолчанию без права запуска/остановки |
| Общая очередь | Доставка уведомлений и аналитики; отказ не блокирует контроллер |

Получение расхода, решение и исполнение находятся в одном сервисе. Внутри него
отдельные пулы/лимиты для чтений и команд, чтобы медленное чтение не занимало
ресурсы остановки. Не создавать три микросервиса для этих трёх шагов.

PHP — источник пользовательского намерения; сервис — источник оперативного
состояния исполнения; Ozon — источник наблюдаемого состояния кампании.
Фронтенд общается только с PHP. Сервис не имеет доступа к БД Conwix.

### Контракты и доставка настроек

- Версионированные схемы в `services/_contracts/`; company/account/campaign scope
  обязателен, числа денег — целые минорные единицы и валюта.
- PHP сохраняет намерение; сервис получает изменения через внутренний API
  ограниченным по частоте опросом с курсором. Это не общая очередь Messenger.
- Сервис атомарно сохраняет версию и подтверждает применение; PHP показывает
  отдельно «сохранено», «применяется» и «применено». Старые версии не откатывают новые.
- Запрос аварийной остановки в UI имеет приоритет в выдаче изменений и срок
  доставки. Пока нет подтверждения Ozon, интерфейс не сообщает «остановлено».
- Сбой PHP не стирает уже принятое расписание и срок остановки.
- Действие разрешения ограничено во времени: контроллер начинает защитную
  остановку заранее, пока разрешение и ключи ещё действуют. После истечения
  не выполняет неавторизованные действия; остаточный риск отражается явно.
- Отзыв ключей/подключения требует отдельного протокола: обычное отключение
  сначала останавливает рекламу; экстренный отзыв нельзя задерживать ради остановки.

## 5. Исполнение без зависимости от общей очереди

1. Подготовить кампанию: проверить принадлежность, тип, настройки Ozon,
   версию политики, оперативный расход за нужный день и доступную ёмкость контроля.
2. Сохранить ближайшие сроки в БД сервиса, держать активные таймеры в памяти.
   Периодическая сверка БД восстанавливает пропущенное после перезапуска.
3. Перед запуском повторно проверить окно, остаток, свежесть, право исполнителя
   и отсутствие ручной/аварийной блокировки. Вне окна старт всегда запрещён.
4. Прочитать текущий расход, проверить полноту/период/валюту ответа, пересчитать риск.
5. При приближении к лимиту либо сроку остановки сохранить намерение остановить,
   затем вызвать Ozon напрямую через разрешённый коннектор.
6. Отдельно проверить состояние Ozon. Timeout записи означает неизвестный результат,
   а не доказанный отказ. Сначала сверить состояние, затем решать о повторе.
7. После остановки продолжать ограниченную сверку расходов: поздние начисления
   не означают автоматически, что показы продолжаются, и не дают права на перезапуск.

Хранить отдельно желаемое состояние, наблюдаемый статус Ozon и причину решения.
Минимальные состояния исполнения: `pending`, `running`, `stopping`, `stopped`,
`unknown`, `blocked`. Причины: расписание, бюджет, устаревшие данные, ручная пауза,
конфликт, потеря разрешения. `unknown` не отображается как безопасная остановка.

Повторяемость обеспечивается уникальностью операции и сверкой желаемого состояния,
а не обещанием exactly-once внешнего HTTP-вызова. Не предполагать поддержку
idempotency key у Ozon без подтверждения спецификацией.

## 6. Масштабирование, квоты и конкуренция

- Распределять кабинеты между экземплярами; сбой одного кабинета не останавливает остальные.
- Один исполнитель команд на кампанию, аренда с поколением владельца и проверкой
  актуальной версии перед отправкой. Изменение аренды само по себе не отменяет
  уже отправленный HTTP-запрос: takeover включает сверку всех неопределённых операций.
- Не считать внутренний fencing token защитой на стороне Ozon: площадка может
  его не поддерживать. После неоднозначного старта блокировать новые старты,
  сверять статус и повторять остановку при обнаружении активности.
- Остановка имеет приоритет над запуском, чтениями и историей; резервировать
  соединения, CPU и часть квот, если методы разделяют лимит.
- Область квоты выяснить по спецификации: кабинет, API-клиент, метод или группа.
  Разные экземпляры и историческая загрузка не должны тратить общую квоту независимо.
- Для 429 уважать документированный срок повтора; если он неизвестен — ограниченный
  backoff с jitter. Бесконечные повторы и параллельный шторм недопустимы.
- JWT/access token кэшировать в памяти до безопасного срока обновления,
  если это допускает спецификация; обновление одного подключения объединять
  в один запрос. Не переносить TTL по памяти или из стороннего SDK.
- Ёмкость оценивать как сумму `число запросов на проверку / интервал проверки`
  плюс статусы, запись и повторы. Учитывать пагинацию и число товаров, не только кампаний.
- Массовый старт/стоп по одинаковому времени — отдельный пик нагрузки. Для чтений
  допустим jitter, для старта запрещено сдвигать время раньше окна, для остановки
  допускается защитное упреждение, но не скрытая задержка за пределы окна.
- При нехватке ёмкости не принимать новые активные кампании; сначала сохранить
  контроль над текущими. Горизонтальное масштабирование не расширяет квоты Ozon.

## 7. Защитный запас и свежесть

Рекомендуемая модель оценки (не гарантия площадки):

```text
T = задержка статистики + интервал до проверки + задержка планировщика
    + время применения остановки + время аварийного восстановления
запас = округление_вверх(консервативная_скорость_расхода × T) + резерв_ошибки
порог = max(0, суточный_лимит − запас)
если наблюдаемый_расход >= порог: запросить остановку
```

Использовать целые копейки, целые единицы времени/рациональные отношения и явное
округление вверх. `float` запрещён и в промежуточном денежном расчёте.
Скорость по недавним наблюдениям — оценка, не верхняя граница будущего трафика.
Если запас съедает весь оставшийся бюджет, запуск запрещён.

Хранить `fetched_at`, отчётный день и, если доступно, время актуальности источника.
Не считать неизменившийся расход доказательством зависания: кампания может не
получать клики. Не считать HTTP 200 доказательством свежести. При отсутствии
watermark документировать невозможность надёжно обнаружить скрытую задержку.
Пропущенные страницы и неполные суммы не трактовать как полный расход.

Консервативно не уменьшать использованный для защиты расход внутри дня из-за
коррекции источника без сверки; финансовая история хранит корректировки отдельно.
После смены дня не применять снимок предыдущего дня и не считать отсутствие
данных новым нулём. Штатный новый запуск проходит полный preflight.

Численные интервалы не обещать до измерений. Сначала установить допустимый
перерасход, затем выбрать интервалы и запас, проверить их выполнимость по квотам.

## 8. Матрица отказов

| Сбой | Действие | Остаточное ограничение |
|---|---|---|
| Messenger/историческая очередь недоступна | Контроллер продолжает работу | Уведомления/аналитика могут задержаться |
| PHP недоступен | Исполнять принятую политику до защитного срока; новых запусков при неподтверждённом разрешении нет | Пользователь не может гарантированно доставить новую настройку |
| Один экземпляр упал | Резервный получает аренду, сверяет Ozon, сначала обрабатывает остановки | Уже отправленные команды могли выполниться позже |
| БД контроллера недоступна | Запретить старты; пытаться остановить известные активные кампании в пределах действующего разрешения | После полного рестарта без БД может не быть списка/ключей |
| Данные расходов недостоверны | Запросить защитную остановку, зафиксировать причину | Скрытую задержку без признака свежести нельзя всегда распознать |
| 429/timeout/5xx при остановке | Ограниченные повторы, чтение статуса, тревога | Возможен продолжающийся расход |
| Ключ отозван/401/403 | Запрет стартов, ограниченное обновление при допустимости, тревога | Без действующего ключа остановка может быть невозможна |
| Вся инфраструктура или связь с Ozon недоступна | Внешний мониторинг и заранее настроенные ограничения Ozon | Никакая локальная очередь или watchdog не обеспечит удалённую остановку |

Для высокой доступности нужны разные домены отказа, а не два контейнера на
одном сервере. Общая БД/сеть остаётся общей зависимостью. Наблюдатель с правом
аварийной записи — возможный следующий этап с отдельным протоколом владения,
а не второй независимый процесс, конкурирующий за ту же кампанию.

## 9. Безопасность и соответствие текущему проекту

- [ADR-026](../adr/0026-ozon-advertising-source.md) сейчас разрешает загрузку
  рекламы и защищает коннектор от записи. Не расширять его allowlist для всех
  фоновых загрузчиков: новый управляющий коннектор получает минимальный список
  разрешённых методов, явную авторизацию кампании и отдельные тесты.
- Проверка принадлежности рекламного ключа в ADR-026 эвристическая и допускает
  отсутствие SKU. Для записи этого недостаточно: проектирование должно определить
  доказательство/явное подтверждение привязки и запрет неоднозначных подключений.
- [ADR-043](../adr/0043-ozon-fetcher-go-service.md) и
  [правила сервисов](../../services/AGENTS.md) ограничивают первую волну
  техническими данными без вычисления денег. Новый контроллер требует отдельного
  ADR с явными границами хранения расходов и разрешённых операций.
- Ключи не сохраняются в БД сервиса, логах, фикстурах или трекере. Суммы не
  выводятся в технические логи; защищённый предметный аудит — отдельное хранилище
  в согласованных границах нового ADR.
- Компания и кабинет проверяются на каждом контракте; ключ владения кампанией
  включает company/account/provider campaign ID. Дублирование одного внешнего
  кабинета через разные подключения не должно создавать двух управляющих владельцев.
- UI использует существующие company-scoped API и cache keys. Операции управления
  требуют явного права; просмотр аналитики не даёт право запускать расходы.
- Конфигурация внешних ресурсов — `ops/`, назначение и применение — `ops/README.md`,
  карта — `docs/structure.md` в реализации. Этот план новые ресурсы не создаёт.

## 10. Измеримость и критерии приёмки

До реализации заполнить паспорт нагрузки: кабинеты, одновременно активные
кампании, товары/страницы на кампанию, одновременные старты/остановки, квоты,
пиковый расход и допустимый риск. Не заменять его произвольным обещанием «каждые 5 секунд».

Раздельно измерять:

- задержку планировщика относительно срока;
- интервал успешных проверок и известный возраст данных источника;
- время от сохранения настройки до её применения сервисом;
- время от решения остановить до отправки и до подтверждённого статуса;
- число неопределённых операций, 429 и пропущенных сроков;
- перерасход/недорасход по последующей сверке и длительность восстановления.

Внутренний SLO задаётся отдельно от наблюдаемой задержки Ozon. Измеренные p99
не объявляются жёстким максимумом. Для аварийных границ задать timeout и действие,
а не только целевой процентиль.

Обязательные сценарии проверки на моках/нагрузочном стенде:

1. Нагрузка истории и отказ очереди не задерживают контроль.
2. Массовая остановка и медленные чтения не исчерпывают резерв команд.
3. 429 одного кабинета не блокирует остальные; суммарная общая квота соблюдается.
4. Потеря исполнителя, аренды, БД и сети не приводит к небезопасному новому старту.
5. Timeout старта с поздним исполнением Ozon обнаруживается сверкой и остановкой.
6. Снижение бюджета, ручная пауза и новая версия имеют приоритет над старым стартом.
7. Полночь, вчерашняя/пустая/частичная статистика и поздняя корректировка не дают ложный остаток.
8. Повторы и перезапуски не сбрасывают дневной расход; другой tenant не получает управление.
9. Отзыв ключа и отключение стратегии дают честный статус неподтверждённой остановки.
10. Интерфейс не сообщает «остановлено» по одному успешному ответу записи без сверки состояния.

## 11. Этапы реализации после принятия решений

1. **Разведка API.** Получить читаемую актуальную спецификацию: типы кампаний,
   методы оперативного расхода/статуса/старта/остановки, область квот, timezone,
   единицы и НДС, пагинацию, свежесть, повторы, бюджетные ограничения.
   Получить побайтовые фикстуры первого клиента по CLAUDE.md §9; обезличивать
   только запрещённые категории данных (например, ПДн покупателей и реквизиты
   контрагентов). По умолчанию живые запросы делает человек; исключение для
   текущего поручения описано в разделе 14 и не разрешает будущие запросы записи.
2. **Проверка осуществимости.** По квотам и измерениям определить поддерживаемую
   нагрузку и риск. Если требуемая точность недостижима, сузить поддерживаемый
   режим или зафиксировать отказ от такой гарантии до разработки управления.
3. **ADR и контракты.** Согласовать денежные вычисления в Go, права записи,
   привязку кабинета, выдачу/отзыв ключей, межмодульные связи и правила отказа.
4. **Режим наблюдения.** Контроллер рассчитывает решения без записи в Ozon;
   сверить статистику и оценить ложные остановки/недостаточный запас.
5. **Управление на ограниченном списке кампаний.** Сначала остановка и проверка,
   затем запуск по расписанию. Пустой allowlist — никем не управляем.
6. **Нагрузочные и аварийные проверки.** Проверить критерии раздела 10,
   зафиксировать ёмкость и ограничения, затем расширять список.
7. **Промышленный выпуск.** По правилам проекта: обязательный CI, независимое
   ревью Claude и два прохода Codex для денег/изоляции/сервисов либо разрешённая
   замена недоступного Claude двумя новыми сессиями Codex CLI; затем rollout и smoke.

Откат управляющего сервиса отличается от отката загрузчика: сначала запретить
старты и подтвердить остановку управляемых кампаний, затем выключить сервис.
При недоступном Ozon не объявлять откат безопасным; сохранить мониторинг и список
неподтверждённых остановок. Простое выключение контейнера оставляет рекламу работать.

## 12. Решения для следующего согласования

Рекомендуемый пакет: одна существующая CPC-кампания на стратегию, расход с НДС,
сутки Ozon, одно дневное окно, без переноса остатка и автоматического изменения
ставок/недельного бюджета; остановка с запасом и явное возобновление после аварии.

До начала реализации согласовать одним пакетом:

- допустимый перерасход и недорасход, целевую нагрузку и правила ручного вмешательства;
- подтверждённую семантику суток и поддерживаемые типы кампаний;
- новый сервис с вычислением денег, контрактами, правами записи и привязкой кабинета;
- протокол отзыва, takeover и ограничения защиты при полном отказе;
- инфраструктуру высокой доступности, если она нужна для целевого SLO.

## 14. Дополнение: проверка чтением API 08.11.2026

После подготовки плана пользователь предоставил временные реквизиты первого
клиента и прямо поручил сохранить ответы как фикстуры. Выполнены авторизация
и шесть запросов чтения, без управления рекламой. Исходные ответы, параметры,
время и SHA-256 сохранены в
[наборе фикстур](../../api/tests/Fixtures/Marketplace/ozon/performance/cost-control-2026-11-08/README.md).

Наблюдения уточняют план, но не заменяют недоступную полную спецификацию:

- агрегированный `/api/client/statistics/campaign/product` вернул CSV, не JSON;
  период при вызове без параметров неизвестен, такой ответ нельзя автоматически
  использовать как расход текущего дня;
- `/api/client/statistics/expense/json` за сегодня вернул пустой `rows`,
  тогда как `/api/client/statistics/daily/json` за тот же день содержит
  десять строк с расходом; причина расхождения не установлена;
- `/api/client/statistics/products/sku` вернул данные одной работающей кампании
  за сегодня и вчера; расход за сегодня совпал с её строкой в `daily` в этом замере;
- JSON разных методов содержит денежные строки как с точкой, так и с запятой:
  будущий коннектор должен разбирать их по контракту конкретного метода;
- полученный access token имел TTL 1800 секунд. Это не подтверждает срок
  действия исходного Client Secret, указанный пользователем;
- список содержит 101 кампанию, в том числе 11 работающих. Число кампаний
  одного кабинета не является результатом нагрузочного теста.

Следующая разведка должна установить период агрегированной статистики,
полноту и свежесть дневных источников. Ни запросы записи, ни задержки
фактической остановки, ни численные квоты этим прогоном не проверялись.
