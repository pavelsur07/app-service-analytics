# Отчёт «Локализация» Ozon FBO — план (вариант A)

**Цель:** показать продавцу, в каких кластерах покупают его товары, из каких
кластеров их фактически везут и сколько стоит логистика локальной продажи
по сравнению с нелокальной. Итог — ответ на вопрос «какой SKU в какой
кластер довезти».

**Вне объёма:** время доставки (вариант B), остатки и рекомендация объёма
поставки (вариант C), оценка суммарной переплаты за нелокальность, FBS, WB.

## Что уже проверено

- `financial_data.cluster_from` / `cluster_to` есть у 7703 из 7703 отправлений
  в фикстурах; 25 кластеров; 39% продаж нелокальные. В сырье на проде
  лежат с первого дня загрузки (клиент уже запрашивает `financial_data`).
- Расходы категории `POSTING` (`/v1/finance/accrual/by-day`, ADR-012)
  несут `unit_number` = номер отправления и SKU: 69 из 70 отправлений
  фикстуры начислений нашлись в фикстуре продаж.
- Типы расходов по отправлению в фикстуре: 32 «Логистика», 29 «Доставка
  до места выдачи», 98 «Доставка до места выдачи силами Ozon», 59
  «Обратная логистика», 45 «Обработка возвратов, отмен и невыкупов».
- Логистика начисляется позже продажи: у свежих заказов её ещё нет.

## Решения на согласование

1. **Схема факт-таблицы `sales_fact`:** две nullable-колонки `cluster_from`,
   `cluster_to` (`text`), без индексов. Входят в `row_hash`. Смена формулы
   хэша проходит тем же путём, что у склада и города: бэкфилл из raw
   переводит хэш строк, совпадающих со снимком, а процедура и SQL-проверки
   записаны в докблоке миграции.
2. **Средняя логистика на штуку — деление денег.** §3 разрешает деление
   только аллокацией. Здесь не распределение суммы между получателями,
   а показатель для сравнения. Предлагаю считать в PostgreSQL на `numeric`
   (без float): `round(sum(amount_minor)::numeric / sum(quantity))`,
   округление половины от нуля до копейки, в API — `bigint` минорных
   единиц и код валюты. Правило округления указывается в ответе API
   и на экране. Если это обход правила — альтернатива: отдавать только
   суммы и штуки без удельного показателя, но тогда сравнение локальной
   и нелокальной логистики теряет смысл.
3. **Определения метрик** (фиксируются в ответе API и в подсказке экрана):
   - локальная продажа — `cluster_from = cluster_to`, строковое равенство
     названий Ozon. Показатель называется «доля локальных продаж», а не
     «индекс локализации»: у Ozon индекс считается по своей методике,
     и выдавать наш показатель за него нельзя;
   - в расчёт идут отправления с датой заказа в периоде (бизнес-дата,
     Europe/Moscow), кроме `cancelled`; единица — штуки;
   - прямая логистика — типы 32, 29, 98; обратная (59, 45) показывается
     отдельной суммой и в сравнение «локальная/нелокальная» не входит;
   - удельная логистика считается только по отправлениям, у которых прямая
     логистика уже начислена; рядом — доля таких штук («логистика
     начислена у 82% штук периода»);
   - строка с менее чем 10 штуками показывается без доли и удельной
     логистики, с пометкой «мало данных»;
   - период: 30 или 90 дней, по умолчанию 30.

Остальное — имена, раскладка по файлам, форма SQL, состав тестов —
решается по ходу и записывается в отчёт.

## Пакеты

Порядок строгий: 1 → 2 → 3 → 4. Каждый пакет — своё ревью.

### Пакет 1. Кластеры в факте продаж (риск high: схема, Ingestion)

- `SalesFact`: `?string $clusterFrom`, `?string $clusterTo`, параметры
  `normalize`, геттеры, два сегмента в `computeRowHash`.
- `OzonPostingFboListParser`: `financial_data.cluster_from/to` тем же
  `optionalNonEmptyString`; отсутствие → NULL без исключения.
- `DoctrineSalesFactWriter`: колонки в обоих upsert. Бэкфилл берёт
  склад, город и кластеры из raw текущей версии строки
  (`raw_document_id`): его непустое значение побеждает, пустое ничего не
  стирает, прочие снимки только заполняют пустое. Если в raw текущей версии
  значения нет, остаётся значение самого раннего снимка, где оно есть. `row_hash` переводится,
  когда итоговая строка совпадает со снимком во всех полях хэша.
- Миграция: две колонки `ADD`, рабочий `down()`, докблок с порядком
  бэкфилла и SQL-проверкой хэша (формула дополняется двумя сегментами).
- `SalesFactBuilder`: умолчания из фикстуры и `withClusters()`.
- Тесты: парсер на фикстуре и на отсутствии полей; изменение кластера
  меняет `rowHash`; интеграционные — upsert идемпотентен, бэкфилл
  заполняет только пустое и переводит хэш совпадающей строки.
- Список продаж и его контракт **не меняются**: кластеры нужны отчёту,
  не таблице операций.

### Пакет 2. Запрос и API отчёта (риск high: деньги, изоляция)

- `GET /api/companies/{companyId}/localization?days=30|90`. Новый
  контракт, существующие не меняются.
- DBAL query-классы в `Ingestion/Infrastructure/Query/Localization/`,
  каждый с `company_id` в первом условии и `QueryBuilder` на выходе:
  - **сводка:** штуки, доля локальных (basis points), прямая логистика
    на штуку для локальных и нелокальных, обратная логистика суммой,
    доля штук с начисленной логистикой;
  - **по кластеру доставки:** те же показатели плюс три главных кластера
    отгрузки с долями. Кластеров ограниченное число (справочник Ozon),
    но лимит всё равно стоит: 50;
  - **SKU × кластер доставки:** штуки, доля локальных, главный кластер
    отгрузки, удельная логистика локальных и нелокальных; сортировка по
    нелокальным штукам; keyset-курсор, лимит 50, максимум 200, превышение
    → 422.
- Логистика связывается с продажей по `(company_id, marketplace_account_id,
  unit_number = posting_number, marketplace_sku)`. Расходы отбираются по
  `business_date >= начала периода` — существующий индекс
  `idx_expense_fact_company_business_date`, начисление не бывает раньше
  продажи. Новых индексов нет; план запроса проверяется `EXPLAIN` на
  сиде песочницы и на объёме прода (read-only), результат — в отчёт.
- Response DTO: доли в basis points, деньги — минорные единицы + валюта,
  правило округления и определения — полями ответа. `make api-types`.
- Тесты (интеграционные): доля локальных и группировка на Builder-данных;
  округление удельной логистики на значениях с остатком; обратная логистика
  не попадает в прямую; отправление без начислений не занижает удельную
  логистику; порог «мало данных»; курсор без пропусков и дублей; **чужая
  компания не видна** (изоляция — обязательное покрытие). Функциональный —
  только изоляция через HTTP и 422 на лимите.

### Пакет 3. Экран (риск standard: фронтенд, контракт уже согласован)

- Маршрут `/companies/:companyId/localization`, пункт «Локализация»
  в сайдбаре рядом с «Выкуп».
- Хук через `companyQueryKey(companyId, 'ingestion', 'localization', {days})`
  и клиент, привязанный к компании. Типы — из схемы.
- Экран: переключатель 30/90 дней; плитки сводки; таблица кластеров
  доставки (штуки, доля локальных, откуда везли, логистика на штуку
  локальная/нелокальная); таблица SKU × кластер с догрузкой по курсору.
  Строки «мало данных» приглушены, определения — в подсказке.
- Без новых зависимостей: таблицы, без графиков.
- Форматирование — существующие `formatMinorAmount` и форматтер basis
  points; если понадобится новая чистая функция — тест Vitest на неё.
  Тест хука на msw по схеме: смена компании не отдаёт кэш предыдущей.

### Пакет 4. Выкладка и сверка

- Merge → миграция на проде → бэкфилл активного подключения по всей
  истории raw (`--from` = первый raw отправлений) → обе SQL-проверки из
  докблока миграции (хэш в окне рескана, полнота кластеров за 90 дней) →
  повторная выкладка → проверка ответа API на проде.
- **Сверка с кабинетом Ozon — критерий приёмки владельцем:** доля
  локальных продаж за 30 дней против «Индекса локализации» в кабинете
  и два-три кластера против отчёта Ozon о географии продаж. Расхождение
  ожидаемо по методике, но его величину нужно знать до того, как показывать
  отчёт клиенту.
