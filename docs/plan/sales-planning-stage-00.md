# Этап 00. Подготовка реализации планирования продаж

**Статус:** подробные планы подготовлены; решения для будущей реализации подтверждены 2026-09-20; функциональные этапы не начаты.

**Результат этапа 00:** сверенное с сервисом описание текущего состояния, порядок независимых задач, подробный план входов, выходов и проверок для каждой задачи. Перед началом каждой задачи исполнитель перечитывает её раздел и актуальный код, публикует план конкретного изменения с точными файлами и миграцией, затем действует по процессу `AGENTS.md` и `CLAUDE.md`. Если обнаружен новый внешний источник или меняется согласованная семантика, план обновляется до начала реализации соответствующей задачи.

Этот документ развивает [план Этапа 0](sales-planning-stage-0.md). Он не запускает реализацию автоматически. Задачи с отдельными границами (`Ingestion`, `Inventory`, `Planning`) получают отдельные изменения и отдельные пакеты ревью; общий выпуск происходит после завершения зависимостей.

## 1. Что уже есть в сервисе

| Возможность | Подтверждённое состояние | Следствие для Этапа 0 |
| --- | --- | --- |
| Ozon FBO | `FetchOzonPostingsHandler` сохраняет raw, историю статусов и `sales_fact`; есть повторный опрос прошлого периода | Использовать существующий сбор данных, не строить второй коннектор |
| Исход заказа | `buyout_outcome` различает T1, D, T2, P, R и неизвестное состояние; правила закреплены ADR-019/020 | Новый контракт должен выдавать количества по кабинету и SKU без двойного учёта |
| Процент выкупа | Есть отчёт Ingestion с отдельной методикой до/после передачи в доставку | Planning рассчитывает **свой** показатель; существующий отчёт не менять без отдельного решения |
| Возврат | `R` означает клиентский возврат после доставки | Для Planning `R` остаётся состоявшимся выкупом; возврат показывается отдельно |

| Карточки | `marketplace_listing` содержит `marketplace_sku`, артикул продавца, имя и фото по кабинету | Ключ плана — SKU площадки внутри кабинета; новый Catalog не нужен |
| Синхронизация | `ScheduleOzonSyncCommand` запускается каждые 900 секунд; опрос повторяет прошлые даты | Использовать существующий ритм и механизм очереди; фиксировать полноту каждого прогона |
| Остатки | В `Ingestion` и `Inventory` нет загрузки остатков FBO и их снимков | I-2 и INV-1 обязательны до готовности экрана |
| План и импорт | Модуля Planning, планов и XLSX-импорта нет | Вводить отдельным модулем; общий редактор заранее не нужен |
| Доступ | `CompanyAccessSubscriber` проверяет членство; у `CompanyMemberRole` сейчас только `owner` | Seller-члены компании читают и правят план по действующей модели; автор правки сохраняется |
| Интерфейс | Есть экран выкупа и API-клиент с `companyQueryKey`; экран выкупа не фильтрует кабинет в контракте | Planning получает собственные ключи кэша с `companyId`, `accountId`, SKU и периодом |

**Зафиксированное расхождение:** старое утверждение `docs/structure.md`, что PriceMonitoring не зависит от Ingestion, уточнено ADR-016. При изменении карты модулей применять ADR-016, не копировать устаревшую фразу.

**Не подтверждено в репозитории:** точный API Ozon для доступных остатков FBO, смысл его полей, наличие разреза по складам, время фактического выкупа и полнота старой истории наблюдений. Это задачи проверки источника, а не повод присвоить неизвестному значению ноль. В рамках этапа 00 запрос к боевому кабинету не выполнялся.

**Уточнение по I-2 от 2026-09-20:** в репозитории уже есть [сырой JSON `/v3/product/info/list`](../../api/tests/Fixtures/Marketplace/ozon/product-info-list-2026-08-13.json) с 62 строками FBO-остатков. Проверка формы, ограничения и запрос на отдельную фикстуру выбранного метода описаны в [исследовании источника](../task/ozon-fbo-stock-source-research.md). Наличие полей `present` и `reserved` не подтверждает формулу доступного остатка. Подробный технический план ближайшей задачи 0.1: [контракты и ADR](sales-planning-stage-0-1-implementation.md).

## 2. Порядок и правило автономного выполнения

```text
00 — эта программа и планы задач
  ├─ 0.1 — ADR, границы модулей и контракты
  ├─ I-1 — контракт заказов и исходов Ingestion ─┐
  ├─ I-2 — источник остатков Ozon FBO ── INV-1 ──┤
  └─ 0.2 — ручной план ── 0.3 — импорт ────────────┤
                                                 0.4 — расчёт
                                                   ↓
                                                 0.5 — история и обновление
                                                   ↓
                                                 0.6 — скорость и покрытие
                                                   ↓
                                                 0.7 — экран → 0.8 — приёмка

После Этапа 0: INV-2 — товар в пути, самостоятельная задача Inventory.
```

I-1, I-2 и 0.2 могут выполняться последовательно в любом порядке после 0.1. `Inventory` появляется только с INV-1, после подтверждения семантики источника в I-2. В каждом изменении — одна итоговая миграция, если схема меняется.

Перед **каждой** задачей: сверить ветку и diff; прочитать её правила и ADR; выписать точные файлы и критерии; выполнить одну завершённую задачу; прогнать затронутые проверки; провести независимое ревью кода; разобрать замечания. Известные сейчас решения из списка `CLAUDE.md` собраны ниже в **одной** точке согласования этапа 00. После её согласования планы отдельных задач публикуются как рабочее уведомление, без повторного запроса уже принятого решения. Красный CI, неполное ревью или недостоверный источник блокируют выпуск, а не считаются разрешением обойти проверку.

## 3. Подробные планы задач

### 0.1. Контракты и архитектурные решения

**Вход:** исходное ТЗ, `sales-planning-stage-0.md`, ADR-006/008/011/016/019/020, действующие Facade и Deptrac.

**Работа:**

1. Написать ADR о границах `Planning` и `Inventory`, направленных связях и различии процента выкупа Planning и существующего отчёта Ingestion.
2. Зафиксировать количественную классификацию: `D` и `R` — состоявшийся выкуп, `T1`, `T2`, `P` — известный невыкуп, `NULL` — неизвестный исход. Проверить это на частичных количествах и временно противоречивых данных; `R` не возвращает единицу в прогноз.
3. Зафиксировать дату плана как дату создания заказа в `Europe/Moscow`; дату наблюдения завершения хранить отдельно. Для текущей когорты показывать факт и прогноз, для сохранённого снимка — значения на тот момент.
4. Описать readonly DTO двух Facade: в каждом запросе `companyId`, `marketplaceAccountId`, набор SKU и ограниченный период; ответы содержат количество, исход, дату, источник и качество. Межмодульная граница не передаёт ORM Entity.
5. Описать модель ключей плана и истории: `(company_id, marketplace_account_id, marketplace_sku, business_date)`; номер версии правимого плана, append-only журнал изменений с автором и временем; идентификатор и входной отпечаток сохранённого расчёта. Снимок хранит параметры и происхождение, а не только итоговую цифру.
6. Зафиксировать API seller под `/api/companies/{companyId}/planning`, обязательный кабинет, правила ошибок и ограничения периода. Отдельно описать качество данных: полные, неполные, устаревшие, неизвестный исход, недостаточная выборка.
7. В ADR зафиксировать новые связи в Deptrac, план миграций по задачам, расположение настроек и механизм сохранения истории. Обновить карту модулей; не объявлять ещё не созданные папки действующими модулями.

**Минимальный API-контракт для задач 0.2–0.7:**

| Метод и путь после `/api/companies/{companyId}/planning` | Результат |
| --- | --- |
| `GET /accounts/{accountId}/skus?search&limit&cursor` | Ограниченный выбор карточек с SKU площадки и подписью продавца |
| `GET /accounts/{accountId}/skus/{sku}/plan?from&to` | Дневные значения и версии; отсутствующий день имеет `quantity: null` |
| `PUT /accounts/{accountId}/skus/{sku}/plan/{date}` | `{quantity, expectedVersion}`; для создания `expectedVersion: 0`, для изменения — прочитанная версия |
| `DELETE /accounts/{accountId}/skus/{sku}/plan/{date}` | JSON `{expectedVersion}` с прочитанной версией, запись в журнал и снятие плана |
| `POST /accounts/{accountId}/imports/preview` | Ошибки строк, изменения и одноразовый `previewId` без правки плана |
| `POST /accounts/{accountId}/imports/{previewId}/apply` | Атомарное применение; повтор возвращает уже записанный результат |
| `GET /accounts/{accountId}/skus/{sku}/daily?from&to` | Текущий дневной ряд, качество и версии источников |
| `GET /accounts/{accountId}/skus/{sku}/calculations?cursor&limit` | Исторические снимки с keyset-пагинацией |

Период дневного чтения по умолчанию — последние 30 дней, максимум 90 дней; интервал `from..to` включителен. Все строковые SKU кодируются как один сегмент URL. При неподходящем SKU, дате, количестве или слишком большом периоде — `422`; при отсутствии кабинета внутри компании — `404`; при чужой компании — действующий ответ проверки членства; при конфликте версии — `409`. Контракт каждого ответа типизируется через генерируемую схему API.

**Проверка:** ADR не противоречит ранее принятым решениям без явной записи о новом решении; каждая цифра исходного ТЗ имеет владельца; Deptrac-направление одностороннее.

**Готовность:** методы, семантика и схемные решения описаны достаточно, чтобы I-1, I-2 и 0.2 не выбирали их заново. Код и миграции начинаются в следующих задачах.

### I-1. Контракт заказов и исходов в Ingestion

**Вход:** `sales_fact`, история статусов, возвраты, `buyout_outcome`, ADR-020 и контракт 0.1.

**Работа:**

1. В `IngestionFacade` добавить пакетное чтение по компании, кабинету, SKU и датам заказа, а также ограниченный поиск карточек выбранного кабинета для выбора SKU. Не использовать текущий дневной API выкупа: его фильтр и методика не совпадают с Planning.
2. Вернуть заказанное, подтверждённо выкупленное, завершённое без выкупа, незавершённое пригодное к прогнозу и неизвестное количество. `D` и `R` включить в выкуп; `R` дополнительно назвать возвратом. Противоречивое return evidence выключает пригодность к прогнозу по ADR-019/020.
3. Вернуть время первого достоверного наблюдения исхода, время последнего полного опроса и признак регулярного опроса либо исторической дозагрузки. Если исход нельзя датировать, пометить его непригодным для скорости, сохранив факт когорты.
4. Фиксировать завершение **полного** прохода загрузки отдельно от raw-дедупликации: идентичное тело ответа при новом опросе означает свежую проверку, а не старую дату raw-документа. Ошибка пагинации или разбора не публикует полную версию.
5. Ограничить выборку и обеспечить tenant/account predicate внутри базового SQL; проверить план запросов на большом чужом cohort по правилам ADR-020.

**Проверки:** unit/integration на T1, D, T2, P, R, `NULL`, частичный выкуп и количественный возврат; повтор одного raw; исправление старого статуса; два кабинета с одинаковым SKU; неудачный и успешный повтор загрузки; EXPLAIN без скана чужих данных.

**Готовность:** сумма состояний равна заказанному количеству, один выкуп не оказывается в незавершённом прогнозе, данные другого кабинета не влияют на результат, у каждого результата есть источник и качество.

### I-2. Источник остатков Ozon FBO в Ingestion

**Вход:** доступный для подключения read-only API Ozon, текущий Ozon client/handler и каталог SKU.

**Исследование до написания миграции:** сверить актуальную документацию Ozon и сырой JSON выбранного метода. Уже сохранённый `/v3/product/info/list` подтверждает форму FBO/FBS-строк, но не смысл доступного остатка. Сравнить его с `/v4/product/info/stocks` и объявленным Ozon `/v1/product/info/stocks-by-warehouse/fbo`; для нового метода сохранить отдельную побайтовую JSON-фикстуру всех страниц, снятую человеком по правилам `CLAUDE.md`. Установить, какой метод возвращает FBO, какой `sku` и `warehouse_id` он использует, что означают `present`, `reserved` и иные поля, когда данные становятся доступными и как обозначается последняя страница. Ни один кандидат не объявлять выбранным источником до сверки с контрольным доступным остатком кабинета. Проверить, можно ли отделить FBO от FBS в одном ответе. Если API не даёт проверяемого доступного количества, остановиться на обновлении плана INV-1, не подставлять `present - reserved` по догадке.

**После подтверждения источника:**

1. Добавить read-only клиент Ozon, парсер точной формы ответа, raw-сохранение, сообщение/обработчик и полную пагинацию.
2. Сохранять источниковые количества с компанией, кабинетом, SKU, складом при наличии, временем опроса и raw-ссылкой. Естественный ключ определить по реальной форме ответа; повторный проход идемпотентен.
3. Ввести маркер завершённого полного снимка: неполная страница, ошибка API или парсера не заменяют прошлый опубликованный срез. Идентичный ответ обновляет время проверки среза отдельно от raw-дедупликации.
4. Включить сбор в существующий цикл синхронизации с контролем лимитов кабинета; не смешивать чтение с методами изменения остатков.

**Проверки:** полный и пустой ответ; много страниц; одинаковый SKU в двух кабинетах; одинаковый SKU на двух складах; повтор запроса; сбой последней страницы; изменившиеся данные источника; отказ авторизации; только read-only вызовы.

**Готовность:** есть полный, проверяемый снимок FBO с точной семантикой полей и временем обновления; нет частично опубликованного среза.

### INV-1. Модуль доступных остатков

**Зависит от:** 0.1 и I-2. Модуль `Inventory` создаётся вместе с этим изменением и ADR.

**Работа:**

1. Через `IngestionFacade` получать нормализованные строки **только полного** снимка одного кабинета. Не читать таблицы Ingestion напрямую.
2. Определить доступное количество по подтверждённой в I-2 формуле источника. Разрез по складам хранить лишь если он действительно предоставлен; агрегировать совместимые FBO-строки в SKU кабинета.
3. Хранить append-only снимки доступного остатка с ссылкой на источниковый срез. Повтор одинакового среза не создаёт дубль; нулевой остаток и отсутствие строки/неполный срез остаются разными состояниями.
4. Через `InventoryFacade` отдавать пакетное чтение актуального и исторического снимков с временем, полнотой и причиной недоступности.
5. Явно не прибавлять товар в доставке и возврате; физическое движение относится к INV-2.

**Проверки:** нулевой/неизвестный остаток; частичный снимок; повтор; изменение снимка; два склада при наличии разреза; два кабинета с одинаковым SKU; просроченное обновление; время исторического снимка.

**Готовность:** число сверено с контрольным показателем Ozon, принадлежит одному кабинету, имеет понятное происхождение и время наблюдения.

### 0.2. Ручной план

**Зависит от:** 0.1. Остатки и загрузка заказов для записи плана не нужны.

**Работа:**

1. Создать ORM-сущность дневного плана с уникальным ключом компании, кабинета, SKU и даты. `company_id` первым в составных индексах; SKU проверять по карточкам кабинета через Facade.
2. Добавить создание, чтение, изменение и снятие плана. `0` — заданный нулевой план; отсутствие записи — план не задан. Количество — целое неотрицательное.
3. Изменение выполнять с обязательной версией по ADR-008; отсутствие версии отклонять, конфликт — отдельный `409` с сохранением введённого значения в UI.
4. В той же транзакции записывать append-only журнал с автором, временем, прежним и новым значением по ADR-007/011. Снятие плана также журналировать.
5. Открыть seller API и typed frontend-контракт; проверять членство компании, принадлежность кабинета компании и изоляцию при совпадающем SKU.

**Проверки:** создание/изменение/снятие, ноль, отрицательное и дробное значение, чужой кабинет, чужая компания, два конкурентных изменения, журнал после неуспешного изменения пуст.

**Готовность:** план надёжно редактируется, а прошлое значение и автор доступны для проверки.

### 0.3. Импорт Excel

**Зависит от:** 0.2. Дополнительная backend-зависимость OpenSpout включается в план согласования до установки.

**Работа:**

1. Принимать только `.xlsx`: один лист, колонки `SKU`, `Дата`, `План, шт.`, до 10 МБ и 10 000 строк. Компания и кабинет выбираются до файла; формулы не исполняются.
2. Потоково читать строки, проверять типы и существование SKU в выбранном кабинете, календарную дату, целое неотрицательное значение и дубли `SKU + дата` внутри файла. Ошибки возвращать с номером строки, не сохраняя рабочий план.
3. Предварительный просмотр показывает новые, изменяемые и совпадающие строки. Отсутствующие в файле даты существующего плана не удаляются.
4. Сохранить ограниченную по времени версию просмотренного набора и версии затрагиваемых планов. Подтверждение применяет **весь** набор одной транзакцией через тот же сценарий записи и журнал, что ручное изменение.
5. Повтор одного подтверждения идемпотентен. Если после просмотра кто-то изменил хотя бы один затрагиваемый план, весь импорт отвечает конфликтом и требует нового просмотра.

**Проверки:** дубли, неизвестный SKU, некорректная дата и формула, пустая ячейка, слишком большой файл/ZIP, частичная ошибка, конфликт версий, повтор подтверждения, одинаковый SKU в разных кабинетах.

**Готовность:** пользователь видит точное изменение до применения; ошибочный или устаревший просмотр не меняет ни одной строки плана.

### 0.4. Расчёт процента, прогноза и сигналов

**Зависит от:** 0.1, I-1, 0.2. Остаток для этого расчёта не нужен.

**Работа:**

1. Считать собственный коэффициент SKU по 30 завершённым календарным дням и количеству единиц с известным исходом: `(D + R) / (T1 + D + T2 + P + R)`. `R` остаётся фактом выкупа, не входит в прогноз. Ноль в знаменателе даёт отсутствие собственного коэффициента.
2. При выборке менее 30 завершённых единиц использовать резервные 80% с явным источником и размером выборки. Настройки хранить версионированно, не как числа в формуле.
3. Считать прогноз только по пригодным незавершённым единицам; после суммирования округлять отображение до одного знака. Факт уже выкупленных прибавлять ровно один раз.
4. Считать ожидаемый итог, отклонение в штуках и процентах. Границы зелёной, жёлтой и красной зон брать из настроек. Нулевой/отсутствующий план, будущую дату, неполный или устаревший источник выводить отдельными состояниями.
5. Отдавать разложение результата: план, известный факт, незавершённое количество, коэффициент, его источник, прогноз, настройки, версии источников и объяснение сигнала.

**Проверки:** 10 заказано, 4 выкуплено, 2 отменено, 4 в прогнозе при 75% дают факт 4 и прогноз 3; `R`, частичные количества, неизвестное состояние, нулевой план, малую выборку, одинаковый SKU в двух кабинетах и коррекцию источника проверять отдельно. Прогонять EXPLAIN на большом чужом cohort.

**Готовность:** любой показатель воспроизводится по разложению; факт не входит во второй раз в прогноз.

### 0.5. История расчётов и обновление

**Зависит от:** 0.4. Начать сохранять снимки до выпуска первого расчётного экрана.

**Работа:**

1. Сохранять append-only снимок по компании, кабинету, SKU и дате заказа: значения, версию плана, конфигурацию, алгоритм, источники, времена и качество данных.
2. Идемпотентный ключ снимка строить по всем значимым входам и версии алгоритма. Изменение факта или настроек создаёт новый снимок; повтор на тех же входах не создаёт второй.
3. Новую текущую версию публиковать атомарно после полного расчёта. Старый воркер не может перезаписать более новую версию; сбой оставляет прежнюю с меткой устаревания.
4. Пересчитывать затронутые когорты после изменения плана или данных, а скользящие окна — при смене дня. Включать исправления старых заказов в пересчёт текущих метрик SKU.
5. Ограничить расчёт SKU, для которых есть план либо уже сохранённая история; ограничить диапазон и объём работы на сообщение. Хранить историю без автоматического удаления в Этапе 0.
6. Дать чтение сохранённого расчёта и сравнение его прогноза с позднее подтверждённым фактом той же когорты. Даты обновления заказов и остатков публиковать отдельно.

**Проверки:** два воркера и повтор сообщения, поздняя отмена/выкуп, исправление старого исхода, изменение плана, смена окна без новых заказов, сбой посреди пересчёта, сравнение вчерашнего снимка с сегодняшним фактом.

**Готовность:** архив не меняется задним числом, а текущая оценка остаётся согласованной и свежей либо явно помеченной как устаревшая.

### 0.6. Скорость и дни покрытия

**Зависит от:** INV-1, I-1 и 0.5.

**Работа:**

1. Для скорости считать подтверждённые выкупы за 14 завершённых календарных дней, включая полные нулевые дни; историческую дозагрузку не относить к текущему дню.
2. Пока 14-дневное окно регулярных наблюдений неполно, вернуть «Недостаточно данных». Указывать, что скорость основана на дате получения подтверждения.
3. Читать доступный остаток через `InventoryFacade` по конкретному кабинету и SKU. Нулевой полный снимок равен нулю; отсутствие либо просрочка снимка возвращает состояние качества без расчёта покрытия.
4. При положительной скорости рассчитывать `остаток / скорость`; при нулевой скорости показывать «Нет продаж за период», при нулевом остатке — `0` и «Нет доступного товара».
5. Сохранять использованные окно и идентификатор снимка остатка в историческом расчёте.

**Проверки:** нулевой день, полный и неполный период, backfill, нулевой и неизвестный остаток, нулевая скорость, несовпадающее время источников, изоляция кабинетов.

**Готовность:** скорость и дни покрытия не создают математически некорректных либо ложных значений.

### 0.7. Экран продавца

**Зависит от:** 0.3–0.6.

**Работа:**

1. Добавить маршрут компании с выбором кабинета, SKU и ограниченного периода. После смены кабинета сбрасывать выбранный SKU; все ключи TanStack Query включают `companyId`, `accountId`, SKU и период.
2. Дать ввод и изменение плана, импорт с предварительным просмотром и понятный конфликт версии.
3. В дневной таблице показать дату заказа, план, заказанное и незавершённое количество, прогноз, факт, ожидаемый итог, отклонение и сигнал.
4. Над таблицей показывать процент выкупа, объём выборки, источник коэффициента, доступный остаток, скорость, дни покрытия и времена обновления. По сигналу открывать его числовое объяснение.
5. Добавить просмотр старого расчёта и последующего факта. Сегодняшний остаток не копировать в исторические даты: показывать только соответствующий сохранённый снимок либо отсутствие снимка.
6. Покрыть состояния загрузки, отсутствия плана, неполных данных, пустого периода, ошибки API и устаревания. Использовать `packages/ui`, `createCompanyApiClient`, `companyQueryKey` и типы из `packages/api-schema`.

**Проверки:** Vitest с типизированным MSW проверяет смену компании и кабинета, конфликт плана, импорт, особые состояния и объяснение сигнала; Playwright — путь «план → обновление факта → новый прогноз».

**Готовность:** менеджер отвечает на десять вопросов исходного ТЗ по одному SKU, не смешивая кабинеты.

## 4. Единый список согласования перед кодом

**Решение владельца от 2026-09-20:** подтверждены методика выкупа Planning, таблицы, сообщения очереди и OpenSpout как основа будущей реализации. Новые модули Planning и Inventory и разделение их контекстов были заданы исходной задачей и уточнены при подготовке Этапа 0. Повторное согласование этих решений не требуется.

Продуктовые границы уже согласованы в разговоре: Ozon FBO, SKU внутри кабинета, план по дате заказа, сохранение состоявшегося выкупа после возврата и INV-2 после Этапа 0. Начальные значения окна, порогов и резервного процента из [плана Этапа 0](sales-planning-stage-0.md) считаются настраиваемыми значениями по умолчанию.

По `CLAUDE.md` в одном решении согласуются следующие известные изменения:

1. Новые модули `Planning` и `Inventory`; чтение через `IngestionFacade` и `InventoryFacade`; односторонние зависимости из раздела 2 и новые точные правила Deptrac.
2. Новая методика Planning с `(D + R)` в числителе и `(T1 + D + T2 + P + R)` в знаменателе, явно отличная от показателя ADR-020. Существующий отчёт Ozon сохраняет свою семантику.
3. Новые company/account-scoped таблицы плана, журнала правок, импортов, расчётных снимков, полных источниковых снимков остатков и снимков доступного остатка. Ключи фактов и индексы определяются по доказанному источнику до миграции; чужие таблицы не читаются напрямую.
4. Новые seller API из 0.1 и добавление сообщений синхронизации остатков/пересчёта в существующую очередь и цикл, без отдельного транспорта.
5. Новая зависимость OpenSpout для XLSX-импорта; допустима только зафиксированная версия, совместимая с PHP 8.4.

После согласования этого списка реализация этапов 0.1–0.8 может идти автономно с отдельным планом перед каждым этапом. Недоказанный источник остатков — техническая проверка I-2, а не вопрос пользователю о названии поля API. Если проверка обнаружит принципиально иной источник, новое внешнее требование или невозможность получить доступный остаток, соответствующий подробный план и список решений обновляются **до написания кода**. Неизвестное поле не заменяется догадкой.
