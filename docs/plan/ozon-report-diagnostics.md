# Безопасная диагностика асинхронных отчётов Ozon

Дата: 09.11.2026. Задача владельца: разработать план и выполнить **только**
диагностику ответов и связь «заказ → проверка → скачивание».
Основание: [паспорт квот, §12](ozon-advertising-quota-passport.md#12-диагностика-php-429--09112026),
[#324](https://github.com/pavelsur07/app-service-analytics/issues/324),
[ADR-026](../adr/0026-ozon-advertising-source.md).

## Границы

Только PHP-обработчики Order/Check SKU/CPO, контекст корреляции без изменения сообщений,
отдельный канал Monolog и тесты. Поведение API, идентификация фактов, raw,
авторизация, количество вызовов, расписание, retry/backoff, маршрутизация очереди,
лимитеры и политика ADR-026 не меняются. БД, зависимости и публичный API не меняются.
Не реализуются координация генераций, исправление 429 или общий счётчик квот.
Пилот Ads не включается, специальных запросов к Ozon нет.

## 1. Корреляция

Событие `accepted` связывает `order_ref` (HMAC параметров логического заказа,
включая компанию/подключение/вид/период/отсортированные кампании) и UUID отчёта
Ozon. Order-повторы имеют тот же order_ref; Check/скачивание/повторы Check
связываются по company/account/report_uuid. Каждая доставка получает новый
UUIDv7 `invocation_id`, связывающий вызовы OAuth и отчёта внутри обработчика.

Одинаковые параметры в двух независимых ресканах дают тот же order_ref:
это ссылка на логический запрос, не уникальный job ID. Различать попытки
нужно по invocation_id, времени и принятому report_uuid. Если ответ заказа
потерян или событие accepted не записалось, эту связь восстановить нельзя.
После смены APP_SECRET HMAC меняется: это диагностическая корреляция, не ключ
идемпотентности. Новые лимиты и гарантии доставки этим не появляются.

Формат сообщений не меняется. Старые сообщения без kind/to сохраняют прежние
fallback. От добавления поля UUID отказались до реализации: readonly-класс
старого воркера не обязан принимать незнакомое поле при откате.

Приёмка:

- [x] Order и его 429-повторы имеют один order_ref; accepted связывает его с report_uuid.
- [x] Check/download/повторы связаны по company/account/report_uuid.
- [x] Повторная доставка имеет новый invocation_id и прежний логический ключ.
- [x] Старые сериализованные сообщения работают без новых полей/serializer.
- [x] Компания/подключение входят в каждое событие явно; нет глобального mutable-контекста.

## 2. События и безопасные признаки

Канал `ozon_report`, JSON в stderr с уровня info в production; общий порог
warning не снижается. Существующие предупреждения `Ozon Performance API answered`
остаются единственным источником старого операционного счётчика 429: новые
события имеют другое имя и не удваивают этот счётчик.

Вокруг token/order/check/download — начало и окончание либо отказ, монотонная
длительность, order_ref/report_uuid/invocation, компания/подключение, вид отчёта, фаза и attempt.
Отдельно: заказ принят с UUID, состояние, raw сохранён, повтор назначен,
пропуск/завершение без результата. Успешный возврат клиента не равен валидному
ответу или сохранённым данным; эти события различаются. У fetcher нет статуса
успешного ответа в контракте, поэтому выдуманный HTTP 200 не записывается.

Из исключения HTTP: status, Retry-After (seconds/IMF-fixdate; missing/invalid
различаются, устаревшие формы HTTP-date сейчас считаются invalid), ограниченная подсказка из JSON error/message и известного числового
кода. Подсказка — эвристика текста, не доказанный provider limit; общий 429
не превращается в «дневная квота» или «частота». Неизвестное — unknown.
Для application/json (+json) читается префикс ≤16 KiB через seekable response
stream; Symfony уже буферизует JSON при создании HTTP exception. Неподдерживаемый
content-type/stream остаётся unknown, getContent() для диагностики не вызывается. Большие,
невалидные и недоступные тела не публикуются. Исключение/результат оригинального
вызова сохраняются; ошибка логгера или разбора диагностики не меняет обработку.

Не публикуются токены, Client Secret, Authorization, произвольные URL/query,
тела/фрагменты ответов, тексты исключений, кампании, SKU и суммы. Неизвестные
состояния/поля не выводятся произвольной строкой. Опциональный x-request-id
представляется только company-scoped HMAC: даже отражённый секрет не попадает
в журнал открытым текстом. Это локальная корреляционная ссылка, не исходный ID
для передачи поддержке; наличие такого заголовка у Ozon не предполагается.

Приёмка:

- [x] Успех и отказ каждого этапа связаны с цепочкой, attempt и доставкой.
- [x] Retry-After только наблюдается, не меняет задержки и число запросов.
- [x] Невалидные/большие/недоступные ответы дают безопасный unknown.
- [x] Секреты в любых полях синтетического ответа/исключения не появляются в логах.
- [x] Сбой логгера не ломает успех и не заменяет исходное исключение.
- [x] Канал доступен в prod, без снижения общего уровня и дублирования старого счётчика.

## 3. Проверки

Unit: нормализация ошибок, обе формы Retry-After, неоднозначные причины,
невалидный JSON, размер, недоступный response, инъекция секретов в headers/body,
неизменность ответов и исключений при сбое логгера.
Integration: SKU/CPO Order → Check → download → stored, IN_PROGRESS, 429 и
потолки повторов, legacy serialization, новые повторные доставки; клиенты — mocks.
Существующие тесты обработчиков подтверждают неизменные задержки и результаты.

Приёмка:

- [x] Затронутые unit/integration PASS; внешние API не вызываются.
- [x] `make lint stan deptrac structure-check` PASS.
- [ ] Два независимых прохода Codex CLI при недоступном Claude; замечания разобраны.
- [ ] Обязательный CI всего diff зелёный до merge, включая audit/e2e.

## 4. Выкладка и проверка

После ревью и CI обычный PR/merge/deploy. Миграций нет. Проверить версию,
здоровье контейнеров и включённый info-handler канала; использовать только
чтение конфигурации/журналов. Если штатных событий Order/Check после выкладки
пока нет, явно указать это: отсутствие событий не равно успешной live-цепочке.
Не запускать backfill/генерацию специально для проверки. Откат обычным возвратом
образа; формат сообщений не изменён, старые сообщения должны работать в новом
обработчике. Полное суточное наблюдение и исправление причин #324 —
отдельная работа, не критерий завершения этой задачи диагностики.

Приёмка:

- [x] План/карта структуры/инструкция чтения логов актуальны.
- [ ] PR объединён после обязательных проверок и ревью.
- [ ] Production version/health/config проверены без запросов Ozon.
- [ ] Фактические результаты smoke и наличие/отсутствие штатных событий описаны.

Источники: локальные контракты Symfony HttpClient и обработчики на `87edbf0`;
[Retry-After, RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3).

## 5. Чтение событий

События `ozon_report_diagnostic` имеют `schema_version=1`. Начало/исход
вызова — `request_started`, `request_returned`, `request_failed`;
`operation=token|order|check|download`. `request_returned` означает только возврат
строки клиентом, без выдуманного HTTP 200. `accepted` записывается после разбора
UUID, `state` — после разбора состояния, `stored` — после сохранения raw.
`handler_failed`/`processing_failed` не раскрывают сообщение исключения;
`retry_scheduled`/`check_scheduled` содержат фактически назначенный delay_ms.

Для каждого вызова фиксировано два события; обработчики добавляют события
переходов. Нет накопления истории в памяти, новой таблицы или метрик с
неограниченными label. Хранение/ротация — существующий Docker journald,
новый внешний сборщик не вводится.

Пример чтения метаданных за ограниченное окно оператором:

```sh
ssh conwix-prod 'journalctl --since "2026-11-09 00:00:00 UTC" --until "2026-11-09 02:00:00 UTC" -n 20000 -o json --output-fields=MESSAGE _SYSTEMD_UNIT=docker.service' \
  | jq -c '.MESSAGE | fromjson? | select(.message == "ozon_report_diagnostic" and .channel == "ozon_report") | {datetime, context}'
```

Если предел записей достигнут, окно уменьшить; полноту не предполагать.
Сначала выбрать company_id + marketplace_account_id, затем order_ref для заказов
или report_uuid для проверок. Событие accepted соединяет обе части. invocation_id
отличает доставки; attempt относится к phase, поэтому order attempt=2 не равен
check attempt=2. Отсутствующий исход после request_started не означает успех:
процесс мог завершиться, запись могла потеряться или вызов ещё выполняется.

`reason_hint_source=body_heuristic` — подсказка по ограниченным JSON-полям,
не ответ Ozon о том, какой именно лимит сработал. `reason_hint=unknown`
сохраняется при неясном/противоречивом тексте. Retry-After и provider_request_ref
наблюдаются независимо от классификации тела. Новые записи нельзя суммировать
со старым счётчиком warning 429 как отдельные HTTP-вызовы.
