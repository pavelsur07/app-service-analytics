# Виджет «Продажи»: технический план и чек-лист приёмки

Дата: 2026-11-06. Статус: план; реализация не выполнена.

Страница: `/companies/{id}/dashboard`.
API: `GET /api/companies/{companyId}/dashboard/summary`.

## 1. Результат и границы задачи

Добавить в существующий виджет две строки: «Продажи в день, ₽» и показатель
средней стоимости продажи с согласованным названием и знаменателем.
Для обеих строк показывать изменение к выбранному периоду сравнения.
Сохранить сумму, количество, спарклайн, настройки виджетов и правила полноты данных.

Расчёты выполняются на бэкенде. React получает готовые значения.
Новые зависимости, источники загрузки, таблицы и фоновые задания не планируются.
Основной вариант ниже использует количество проданных единиц.
Вариант среднего чека заказа требует уточнения плана до реализации.

## 2. Решения до реализации

- [ ] Зафиксировать смысл второго показателя. Рекомендуемое для имеющихся данных
  название — «Средняя цена продажи, ₽»: сумма продаж / проданные единицы.
  Если требуется «Средний чек, ₽», определить единицу чека: заказ или отправление,
  источник идентификатора, обработку отсутствующих идентификаторов и частичных
  продаж. Не подменять количество чеков количеством товаров.
- [ ] Согласовать добавление полей в используемый API согласно CLAUDE.md,
  раздел «Единственная точка согласования».
- [ ] Оформить уточнение денежных правил новым ADR: аналитическое среднее
  допускает точное деление и округление; распределение расходов по-прежнему
  требует аллокации с сохранением суммы. Принятый ADR-004 не переписывать.
  Согласовать связанные уточнения CLAUDE.md и документации паттернов.

Обнаруженное расхождение: ADR-004 разрешает деление денег только аллокацией,
а DashboardMetricsQuery уже рассчитывает удельные показатели через
`ROUND(numeric)`. Существующая реализация не отменяет правило.
Новый расчёт нельзя добавлять молчаливым обходом этого ограничения.

## 3. Определения и формулы

Источник продаж сохраняется: положительная выручка из ленты начислений Ozon,
по бизнес-дате начисления, с текущими фильтрами компании и валюты.
Возвраты учитываются отдельным показателем и из суммы продаж не вычитаются.
Количество — сумма `quantity`, согласно ADR-038; число строк фактов не подходит.

Обозначения: `S` — сумма продаж в копейках, `Q` — количество проданных единиц,
`D` — число календарных дней периода включительно.

| Показатель | Формула | Пустой полностью загруженный период |
|---|---|---|
| Продажи в день | `round(S / D)` | `0` |
| Средняя цена продажи | `round(S / Q)`, при `Q = 0` — `null` | `null` |

- Каждый период использует собственный `D`, включая дни без продаж.
- Календарные границы соответствуют существующему API (Europe/Moscow,
  окончание не позднее вчера, максимум 366 дней).
- Деление — точное `numeric`; результат — целые минорные единицы.
  Округление до копейки, половина от нуля. `float` не используется.
- Среднее считается из итогов периода, не как среднее дневных средних.
- Валюты не смешиваются; сохраняется текущая проверка единственной валюты сводки.
- При неполной загрузке значения отражают имеющиеся факты вместе с существующим
  предупреждением о неполноте; они не объявляются окончательными.
- Если любой период неполон, изменения новых показателей — `null`, как у остальных.
- Изменения рассчитываются существующим `DashboardChange::relativeBps`
  из итоговых значений в копейках. При нуле базы или `null` — `null`.

## 4. Техническая реализация

### 4.1. SQL и слой чтения

Файлы в `api/src/Ingestion/Infrastructure/Query/Dashboard/`:

- `DashboardMetricsQuery.php`: добавить отношения во внешнюю проекцию итогов,
  над уже агрегированными суммами. Для среднего использовать `NULLIF(Q, 0)`.
  Длительность каждого диапазона определить календарной разностью дат + 1;
  выбрать знаменатель по `current` / `comparison`.
- `DashboardTotalsRow.php`: добавить `salesPerDayMinor` и nullable
  `averageSalePriceMinor`, обновить отображение SQL-строки в DTO.

Не добавлять отдельные запросы для каждой метрики, запросы в цикле или загрузку
Entity. Сохранить фильтр `companyId`, ограничение результата и общий снимок чтения.
При отсутствии строки итогов Application формирует `0` продаж в день и `null`
средней цены. Дневные ряды и схема хранения не меняются.

### 4.2. Application

Файлы в `api/src/Ingestion/Application/Dashboard/`:

- `DashboardMetrics.php`: новые поля метрик.
- `DashboardChanges.php`: nullable `salesPerDayBps`, `averageSalePriceBps`.
- `BuildDashboardSummaryAction.php`: передача новых метрик, значения для пустого
  периода, расчёт изменений и заполнение `noChanges()`.

`DashboardChange` переиспользовать без изменения формулы. Не создавать
универсальный движок метрик ради двух отношений.

### 4.3. Контракт API

Обновить `DashboardMetricsResponse.php` и `DashboardChangesResponse.php`
в `api/src/Ingestion/Ui/Response/Dashboard/`, включая преобразование из Application.
Документировать единицы, формулы и nullable-семантику.

| Объект | Новые поля |
|---|---|
| `current.metrics`, `comparison.metrics` | `salesPerDayMinor: int`, `averageSalePriceMinor: int | null` |
| `changes` | `salesPerDayBps: int | null`, `averageSalePriceBps: int | null` |

Имена относятся к варианту средней цены единицы. Для среднего чека имена и
знаменатель изменить согласованно до реализации.

Сгенерировать `packages/api-schema/openapi.json` и
`packages/api-schema/src/schema.d.ts` командами `make api-doc-export api-types`.
Сгенерированные файлы вручную не править. Сохранить существующие поля ответа.

### 4.4. Seller UI

- В `apps/seller/src/features/dashboard/lib/widgets.ts` добавить строки после
  «Количество», использовать `moneyPrecise` и относительную динамику.
- Для продаж в день рост показывать как положительную динамику; для средней
  цены использовать нейтральную оценку: её рост сам по себе не доказывает улучшение.
- Проверить `WidgetCard.tsx`: новые строки помещаются на узком экране,
  значение и изменение остаются рядом. Менять общий компонент только при необходимости.
- Использовать существующий знак валюты форматтера, не дублировать его рядом
  с числом. Понятные подписи и описание формул закрепить в интерфейсе.
- Обновить типизированные тестовые ответы/MSW. Сохранить `createCompanyApiClient`,
  `companyQueryKey` и текущий TanStack Query hook.

- Проверить сценарий переключения компаний и периодов в существующих тестах

| Вход | Ожидаемый результат |
|---|---|
| 30 000 ₽, 20 единиц, 10 дней | 3 000 ₽/день; 1 500 ₽/ед. |
| 30 000 ₽, продажи только в 2 дня из 10 | 3 000 ₽/день |
| 100,01 ₽, 2 единицы, 2 дня | 50,01 ₽/день; 50,01 ₽/ед. |
| Полные данные, продаж нет | 0 ₽/день; средняя `—` |
| Текущий: 30 000 ₽ / 10 дней; сравнение: 12 000 ₽ / 6 дней | 3 000 против 2 000 ₽/день; +50% |
| База сравнения равна нулю | Динамика `—`, без Infinity/NaN |
| Любой период загружен неполностью | Предупреждение о неполноте; динамика отсутствует |
| Те же даты, продажи другой компании | Не влияют на показатели |

Дополнительно проверить один день, переход месяца/года, високосный день,
границы включительно, строку начисления на несколько единиц и отдельный возврат.
Внешние API в тестах не вызывать, данные готовить через Builder.

## 6. Проверки, ревью и выпуск

Команды выполнять через существующие Makefile/Docker-окружения:

```sh
make lint stan deptrac structure-check
make test-unit test-int test-func
make api-doc-export api-types
make api-types-check
make front-typecheck front-lint front-knip front-test front-build APP=seller
```

Перед merge обязателен зелёный CI всего diff, включая audit и e2e.
`make ci-local` — сводный локальный вариант; пройденный CI без причины не повторять.
При изменении общего UI проверить всех потребителей, включая extension.
Миграция не ожидается; если появится, пересмотреть объём и выполнить
`make db-rebuild-check` только после проверки локального назначения окружения.

Риск — денежные расчёты. Итоговый код проходит Claude и два прохода Codex 5A/5B
по `docs/review-package-template.md`. При недоступности Claude — новые независимые
сессии Codex 5A/5B по установленной процедуре; факт замены записать.
Исправления проходят затронутые проверки и повторное ревью.

В пакете ревью только файлы задачи. Сохранить хэш пакета, ответы, результаты
команд и число уникальных принятых замечаний каждого дополнительного прохода.
Незавершённые проверки и ревью блокируют merge.

После выполнения предусловий: PR, merge, штатная выкладка, production smoke
на разрешённой компании; сверка UI и API с одинаковыми диапазонами.
Бэкенд с новыми полями должен быть доступен до нового фронтенда.
При откате сначала вернуть прежний фронтенд, затем при необходимости бэкенд.
