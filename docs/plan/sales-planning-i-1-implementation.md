# План I-1: заказы и исходы для Planning в Ingestion

**Результат:** `IngestionPlanningFacade` отдаёт проверяемые когорты заказов, исходы и даты наблюдений строго внутри компании и кабинета. Модуль Planning не читает таблицы Ingestion. Зависимость — [контракт 0.1](sales-planning-stage-0-1-implementation.md); бизнес-граница — [ADR-024](../adr/0024-sales-planning-and-inventory-boundaries.md). Этот план описывает отдельное изменение Ingestion, без формул и таблиц Planning.

## Сверка перед кодом

Прочитать `BuyoutOutcomeQuery`, текущую view `buyout_outcome` в последней миграции, `FetchOzonPostingsHandler`, `FetchOzonReturnsHandler`, `MarketplacePostingStatusRepository`, `SalesFactRepository`, `CompanySkusQuery`, ADR-006/019/020. Сейчас `BuyoutOutcomeQuery` возвращает один исход на строку и `resolved_at`, но не даёт закреплённой версии выборки, полноты прогона, количественных аллокаций и двух независимых осей времени. `FetchOzonPostingsHandler` делает один запрос на день и отклоняет ответ у лимита; до объявления дня полным убедиться, что этот потолок не достигнут. Отдельно проверить, как количественный возврат отражается в view, не размножая заказанную единицу.

## Контракт и последовательность

**Уточнение по фактической view перед миграцией:** `buyout_outcome` уже выдаёт частичные количественные аллокации (`source_row_id + outcome`) через SQL ADR-020. Их не копировать в новую факт-таблицу: это дало бы второй изменяемый источник истины, отвергнутый ADR-020. Добавить только происхождение и охват в шести company/account-scoped таблицах: `planning_ingestion_source_state` (тип `postings|returns|catalog`, границы запроса, хэш полного ответа или отсортированного каталога, время последней успешной проверки и дата назначенного глубокого окна), `planning_ingestion_source_raw_document` (raw-ссылки текущего полного ответа окна в нативных колонках UUID), `planning_ingestion_account_state` (монотонное поколение и завершение первоначальной базы), `planning_ingestion_day_coverage` (полные регулярные проверки дня для окон), `planning_ingestion_source_row_run` (последний полный проход конкретной исходной строки, включая проход без известного исхода) и `planning_ingestion_resolution_observation` (первое наблюдение аллокации, первые доказанные даты, момент перехода текущей единицы в недатированное состояние `undated_since_at`, raw-ссылка и backfill). Для них нужны Entity схемы и одна итоговая миграция. Для последнего полного набора аллокаций исходной строки хранится монотонный номер прохода наблюдения, даже если конкретный исход исчез или вся строка стала незавершённой. Дата переносится по порядку единиц только из исходов этого прохода. Прежняя позиция отдаёт доказанную дату один раз: наследование D↔R и исторический fallback по ключу разрешены, только если позиция не назначена текущей единице своего прежнего исхода. Если сопоставленная по порядку позиция недатирована, доказанная дата собственного ключа, который не расходован другим текущим сопоставлением, сохраняется. Если выпавшая позиция позже появляется снова и для неё нет соответствующей позиции в последнем наборе исхода, её ранее доказанная дата сохраняется по тому же ключу и исходу, только когда этот же источник даты ещё не назначен другой текущей единице. Для каждой впервые доказанной даты хранится `date_lineage`: устойчивый идентификатор происхождения конкретной единицы, который переносится вместе с датами при смене позиции или D↔R. В пределах текущего набора исходов одна линия даты может быть назначена только одной единице; при конкуренции приоритет имеет позиция из последнего полного набора, затем исторический ключ, затем перенос между D и R. `firstKnownOutcomeAt` и `firstRegularlyObservedAt` наследуются из одного выбранного наблюдения: дата регулярного подтверждения другой единицы не дополняет известную дату выбранной линии. Освободившаяся единица получает новую дату только при самостоятельном доказательстве нового терминального перехода штатным проходом; иначе дата остаётся неизвестной. Повтор того же полного ответа в тот же день обновляет время проверки без смены поколения. Изменение хэша ответа того же окна увеличивает поколение даже в тот же день; новый день полного регулярного охвата и изменение дневного покрытия также увеличивают его. Первое окно создаёт исходное поколение. Происхождение `regular|rescan` передаётся в сообщении. Сообщение старого формата без этого поля помечается внутренним `legacy` и завершается до сетевого запроса и записи фактов. Новый штатный диспетчер заново опросит своё окно с явным происхождением; старые ручные сообщения дозагрузки при необходимости ставятся в очередь повторно в новом формате. Это сохраняет согласованность фактов, наблюдений и полноты при переходе между версиями. Перед включением нового диспетчера при будущей выкладке старые воркеры очереди должны быть остановлены: новый формат сообщения содержит дополнительные поля, которые старый PHP-класс не обязан десериализовать. После запуска новых воркеров штатный цикл повторно соберёт регулярные окна. Каталог обновляет поколение, чтобы курсор поиска SKU не смешивал разные снимки. Для подробного наблюдения агрегированные количества view разворачиваются в детерминированные позиции единиц внутри `sourceRowId`; `allocationKey` — номер позиции, `outcome` — отдельное текущее состояние. При `D → R` номер позиции сохраняется, а новое наблюдение наследует подтверждённую дату D той же единицы. Ozon не даёт настоящего идентификатора единицы внутри агрегированной строки; детерминированная позиция — принятая договорённость, а не доказательство физической идентичности. При изменении исходного распределения меняется `sourceVersion`, поэтому старые страницы нельзя продолжать.

Связи окна с raw-страницами в I-1 показывают **текущий** завершённый ответ и заменяются при следующем полном опросе того же окна. Неизменяемые raw-документы остаются в Ingestion; прежний полный набор страниц по одному только `sourceVersion` I-1 не восстанавливает. История расчёта в 0.5 должна сохранить использованные агрегаты и ссылки на исходные raw-документы в самом снимке Planning, прежде чем источник обновится.

Даты старых фактов без доказанного регулярного наблюдения остаются `NULL`. При D→R дата выкупа наследуется от первого D той же строки, если она доказана; сам возврат не создаёт новую продажу. Если возврат появился раньше строки продажи и нет доказательства нового терминального перехода после baseline, поздний регулярный опрос отправлений не датирует R текущим днём. При исправлении недатированного R обратно в D новое D также сохраняет неизвестную дату: текущий опрос не доказывает день старого выкупа. Для конкретного `source_row_id` текущее количество по исходу берётся из view, а metadata сохраняет лишь дату/происхождение. Визуальный статус возврата не называется датой состоявшегося выкупа. Публикация фактов, наблюдения и поколения для успешного полного прохода происходит в одной транзакции; raw остаётся самостоятельным неизменяемым слоем.

Первую дату исхода ставит регулярный проход после завершения baseline, если дата создания заказа строго позже календарного дня baseline или история статусов доказывает переход из активного состояния в терминальное после baseline. Для заказа с датой создания в календарный день baseline одной этой даты недостаточно: время создания не известно, поэтому требуется история статусов. Опрос возвратов может подтвердить уже доказанный новый исход, даже если запущен раньше опроса отправлений; впервые обнаруженная старая соседняя строка заказа без такого свидетельства остаётся недатированной. Если `R` впервые встретился вместе с новым доказанным переходом из активного заказа, он получает дату первого подтверждения выкупа; старый `R` без такого свидетельства остаётся недатированным. При исправлении прежнего терминального невыкупа старого заказа в `D` дата выкупа не придумывается; у заказа, созданного после baseline, новое доказанное терминальное состояние датируется. При сдвиге числового `allocationKey` дата уже известного исхода сохраняется по порядковому номеру единицы **внутри последнего наблюдённого набора того же исхода** раньше наследования даты другого исхода; конфликт с существующим ключом обновляет его дату, и повторный проход сохраняет результат; это детерминированная договорённость для агрегата, а не восстановление физического идентификатора товара.

1. Выделить из заказов количественные аллокации с ключом `(company, account, sourceRowId, allocationKey)`. Для одной когорты сумма `D + R + T1 + T2 + P + unknown` равна `ordered`; `D` и `R` дают `bought`, `T1/T2/P` — `terminalNoBuy`, только доказанно открытое состояние — `openEligible`. Противоречивое свидетельство о возврате и недатируемый исход получают качество, а не придуманную дату. Не менять существующий отчёт выкупа ADR-020.
2. Добавить в сообщение происхождение опроса (`regular` для штатных коротких и ежедневных глубоких проходов, `rescan` для ручной исторической дозагрузки), передав его из существующего диспетчера и команд дозагрузки. Иначе выкуп заказа, пришедший позже короткого окна, никогда не получит дату для скорости. Дневная полнота фиксируется после покрытия всего назначенного глубокого окна отправлений и возвратов; задержанное сообщение прошлого дня не помечает ни прошлый, ни текущий день полным. Для уже поставленных сообщений предусмотреть безопасную совместимость нативной PHP-сериализации очереди. Сохранить `firstKnownOutcomeAt` как первое достоверное подтверждение исхода и отдельно `firstRegularlyObservedAt` только для подтверждённого выкупа. `sourceEventAt` заполнять только если событие доказано самим ответом Ozon. У дозагруженного старого исхода без такого доказательства обе первые даты остаются `NULL` и он не попадает в сегодняшний поток/окно коэффициента. Признак `backfill` показывает происхождение текущего прохода (`rescan`) либо отсутствие доказанной даты; он не служит фильтром расчёта. Если rescan повторно наблюдает уже доказанный исход, дата сохраняется, `backfill` может быть `true`, а единица остаётся в расчёте по выбранной оси времени. `resolved_at` view сам по себе не доказывает время события.
   Первый полный суточный проход кабинета создаёт базовую историю с `backfill=true` и неизвестными датами исходов: уже существующие доставки нельзя объявить продажами сегодняшнего дня. Сразу после него день остаётся неполным для скорости: `observationCoverage` считает только даты строго позже `baseline_completed_at::date`, хотя маркер исходного полного опроса сохраняется. Полноценный ряд наблюдений начинается со следующего календарного дня. Даже при полном дневном маркере ответ для выбранного SKU и оси помечается неполным, если текущая единица с неизвестной датой впервые появилась либо повторно стала недатированной не раньше начала окна (`undated_since_at`) и исходный заказ мог попасть в окно. Первое наблюдение ключа `first_observed_at` при таком переходе не переписывается; дата начала неопределённости сбрасывается, когда единица снова получает доказанную дату. Для скорости это относится только к текущим выкупам `D/R`; невыкуп не уменьшает полноту скорости. Для окна коэффициента учитываются все текущие терминальные исходы. Такое качество рассчитывается для запрошенного SKU, не переносится на другие кабинеты и SKU. Поздний регулярный опрос уже известного исторического исхода не восстанавливает неизвестную дату задним числом.
3. Для каждого кабинета/периода фиксировать версию полного опроса и момент проверки отдельно от ID raw-документа: одинаковый raw при новом успешном опросе обновляет свежесть, ошибка разбора/лимита не делает период полным. Версию менять при исправлении любой аллокации или охвата; включать общую `sourceVersion` в расчётные ответы и курсоры страниц. `knownMarketplaceSkus` — ограниченная проверка принадлежности списка без курсора.
   Обработчики отправлений, возвратов и каталога берут одну блокировку кабинета **до** записи фактов и маркеров; возвраты собирают ключи всех страниц во временной таблице и пересчитывают исходы после полного обхода пакетами до 5000 заказов. Перед исправлением существующей строки в этот набор добавляется её прежний заказ и SKU: пересчёт охватывает обе стороны переноса. Фильтр целых затронутых заказов проталкивается в view **до** разворачивания количеств; при неизвестном номере заказа он ограничен конкретными `source_row_id`, а не всей историей NULL-номеров кабинета. Для отправлений затронутым считается весь заказ, поскольку новая sibling-строка может изменить исход других его строк.
4. Реализовать SQL с `company_id` и `marketplace_account_id` **в базовых выборках**, а не после агрегации. Когортный запрос ограничивает SKU и даты внутри materialized CTE до группировки. `planningResolutionTotals` группирует по SKU и исходу в БД, принимает максимум 200 SKU и обе оси времени; неизвестные даты в окно не входят. Перед разворачиванием количеств запрос выбирает `source_row_id`, у которых есть наблюдение нужной оси в указанном периоде и SKU. После разворачивания он повторно ограничивает **каждую текущую аллокацию** по выбранной оси и границам окна: дата другой единицы той же строки не расширяет числитель или знаменатель. Пустой массив SKU возвращает пустой результат. Контрактная ось времени объявлена в `Application/Facade`, чтобы Planning не импортировал Domain Ingestion. Страницы когорт/наблюдений/поиска имеют лимит 50 по умолчанию, максимум 200, `limit + 1` и keyset; курсор закрепляет компанию, кабинет, фильтр, ось и версию, чужой либо устаревший курсор отклоняется. Для соседних страниц расчёта Planning сверяет общую версию.

Общая версия кабинета может измениться между страницами даже из-за короткого опроса текущего дня. Контракт I-1 намеренно отклоняет такой курсор; вызывающий расчёт читает ограниченные периоды по одному SKU и после смены версии начинает этот расчёт с первой страницы. При непрерывных изменениях источник остаётся `stale`/`missing` до следующей успешной попытки, смешанный снимок не публикуется. Это ограничение глобальной версии; для гарантии прогресса на постоянно меняющемся крупном кабинете потребуется отдельный согласованный снимок чтения либо версии по затронутым окнам.
5. Поиск SKU строить по `marketplace_listing` и `sales_fact` **выбранного кабинета**; снятые с продажи SKU остаются доступными для истории. Исторический SKU ищется по префиксу без учёта регистра, как и SKU текущего каталога. Для подстроки SKU, артикула и имени и для исторического префикса добавить составные `btree_gin`/`pg_trgm` GIN-индексы с `company_id` и кабинетом впереди; выполнить `EXPLAIN` обеих ветвей на крупном кабинете и отдельно проверить пригодность индексов для редкого совпадения. Планировщик вправе выбрать первичный индекс для небольшого кабинета. Не использовать `COUNT(*)` по факт-таблице.

Полнота когорты подтверждается только тогда, когда каждый день диапазона имеет полный опрос отправлений и покрыт полным окном возвратов; отсутствие одного источника даёт `complete=false`. Поиск в текущем каталоге допускает подстроку SKU, артикула и имени; исторический SKU из `sales_fact` ищется по префиксу, чтобы чтение оставалось ограниченным индексом кабинета и SKU.

Список raw-ссылок в строке когорты ограничен 50 документами и содержит признак усечения; подробные наблюдения доступны отдельными keyset-страницами. Ссылка на каждый полный raw-ответ окна хранится в отдельной таблице с нативным типом `uuid`.

Один запрос дневного ряда или наблюдений ограничен 366 календарными днями; более длинную историю вызывающий читает отдельными периодами с проверкой общей `sourceVersion`.

`sourceVersion` включает поколение кабинета и явную версию интерпретации исходов. При изменении парсеров или семантики `buyout_outcome`, которое может иначе трактовать прежний raw, версия интерпретации увеличивается вместе с кодом; курсоры из старой версии тогда отклоняются.

## Проверки и завершение

- Unit: все `T1/D/T2/P/R/NULL`, частичные количества, возврат после выкупа, backfill, неизвестная дата, сумма аллокаций.
- Integration: одинаковый SKU у двух компаний и двух кабинетов; неизвестный и поддельный курсор; обновление версии между страницами и пакетами; повтор raw, исправление исхода, обрыв полной загрузки; SQL `EXPLAIN` на объёме чужого кабинета.
- Проверить миграцию с пустой базы, `make lint stan deptrac structure-check`, затронутые `make test-unit test-int test-func`, `make audit`; точные команды и результаты занести в пакет задачи. Коду/схеме/изоляции нужен Claude и оба прохода Codex согласно `AGENTS.md`.

**Готовность:** у любого количества есть исход, время и источник; один выкуп не находится одновременно в факте и открытом прогнозе; данные соседнего кабинета не меняют результат; неполный опрос явно виден и не выдаётся за полный.
