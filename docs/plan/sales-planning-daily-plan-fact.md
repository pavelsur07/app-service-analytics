# Дневное планирование: исходный план, факт и прогноз по когортам

Дата: 27.10.2026.

Статус: зафиксированы требования и уточнение владельца; методические и
технические решения ниже являются предложением до согласования.
Первоначально сохранение документа не означало запуск реализации.
27.10.2026 владелец поручил начать исполнение автономно; ход работы —
в [журнале задач](sales-planning-daily-tasks.md). Принятие ADR и обязательные
предусловия merge выполняются отдельно по правилам проекта.

## 1. Цель и подтверждённые требования

В начале сезона пользователь самостоятельно задаёт «План продаж, шт.»
на каждый день. Далее система показывает, как фактический и ожидаемый
результат соотносятся с этим исходным планом.

- План — заданная пользователем цель, а не вычисляемый прогноз.
- Загрузка фактов, пересчёт выкупа и прогноза не меняют дневной план.
- На каждый день добавить заказанные штуки, процент выкупа когорты,
  продажи, выручку и скорость продаж с разделением факта и прогноза.
- Продажи, выручку и скорость рассчитывать с использованием когорт заказов.
- На каждую дату показывать накопительный результат.
- Уточнение 27.10.2026: в показателе «Заказали» исключать отмены до передачи
  в доставку. Рекомендация: вычитать только подтверждённые T1, сохраняя
  исходное количество и отдельно показывая неизвестные исходы.
- Добавить календарные обозначения: «Начало сезона», «Конец сезона»,
  «Подсорт», «Продажи», «Стоп подсорт».

Не подтверждено владельцем: считаются ли выполнением плана выкупленные
штуки за вычетом клиентских возвратов. Рекомендация — нетто-продажи;
до решения нельзя автоматически менять смысл существующего плана.

## 2. Текущее состояние и ограничения

- SalesPlanning хранит плотные строки SKU × день, количество и РРЦ.
  Выручка плана вычисляется как количество × РРЦ.
- Даты плана и факта Ozon — бизнес-дни в МСК.
- ADR-040 задаёт жизненный цикл утверждения и версий, ADR-041 — пакетную
  запись строк. По документу этапа 0 на 26.10.2026 сценарии утверждения,
  версий и отмены (0.7) ещё открыты. Их готовность проверить перед реализацией
  защиты исходной цели; наличие статусов в модели не означает готовность сценариев.
- Ingestion уже рассчитывает дневные когорты, зрелость, прогноз выкупа
  и денежные показатели. Это основа для повторного использования,
  но не доказательство готовности новой методики нетто-продаж.
- IngestionFacade пока предоставляет планированию каталог, а не факты.
  Чтение новых агрегатов потребует расширения межмодульного контракта.
- BuyoutDailyQuery с денежными показателями ограничен одним SKU и 31 днём.
  Его нельзя вызывать в цикле по SKU для таблицы сезона до 184 дней.
- Действующая методика процента выкупа не равна нетто-продажам / заказанным
  штукам: отмены до передачи и клиентские возвраты имеют иной учёт.

## 3. Когорта и показатели дня — предложение

Зерно: компания × подключение площадки × SKU × бизнес-дата заказа.
Для Ozon используется существующая бизнес-дата из Ingestion, без переопределения
её по дате оплаты, доставки или возврата.

Выкуп и возврат относятся к исходной когорте заказа. Заказ 10 октября,
выкуп 15 октября и возврат 20 октября уточняют результат когорты 10 октября.
Это когортный результат, а не отчёт о денежных поступлениях за день.

| Показатель | Смысл и расчёт |
|---|---|
| План продаж, шт. | Пользовательская цель дня; смысл продажи уточняется до реализации |
| Заказали, шт. — факт | Исходное заказанное количество минус подтверждённые отмены до передачи в доставку; отмены после передачи и клиентские возвраты не вычитаются из заказов |
| % выкупа когорты — факт / прогноз | По действующей методике и правилам зрелости; знаменатель объясняется пользователю |
| Продажи, шт. — факт | Предложение: выкуплено минус уже состоявшиеся клиентские возвраты |
| Продажи, шт. — прогноз | Ожидаемый итог когорты: состоявшийся результат плюс ожидаемое изменение по незавершённым исходам, включая будущие возвраты при выборе нетто-методики |
| Выручка, ₽ — факт / прогноз | Предложение: стоимость продаж за вычетом возвратов, до комиссий и расходов, по ценам соответствующих товарных строк |
| Скорость продаж, шт./день — факт / прогноз | Продажи соответствующего вида за интервал / число календарных дней интервала |

Прогноз продаж — полный ожидаемый итог когорты, а не добавка к факту.
При наличии полного прогноза складывать его с фактом повторно нельзя.

Текущий процент выкупа `D / (D + T2 + P)` нельзя умножать на все заказанные
штуки для получения продаж. Если нужна доля нетто-продаж от заказанного,
ввести отдельный явно названный показатель с собственной методикой.
Существующий процент не переименовывать молча в новую метрику.

Выручку плана по РРЦ и результат по фактическим ценам подписывать отдельно:
их разница отражает и количество, и цену. При отсутствии подтверждённой
денежной оценки не подставлять РРЦ вместо фактической цены.

## 4. Накопительные расчёты — предложение

Для выбранного SKU или набора SKU начальная дата `s` фиксирована началом
плана / сезона. Дата `d` — конец рассматриваемого интервала.
Все значения рассчитываются по одному срезу известных данных `asOf`.

```text
План(s..d)     = сумма дневного плана от s до d включительно
Заказали(s..d) = сумма (исходные заказанные штуки − подтверждённые T1) когорт от s до d
Факт(s..d)     = сумма состоявшихся продаж этих когорт
Выручка(s..d)  = сумма состоявшейся выручки этих когорт

Оценка(s..d) = сумма итоговых результатов завершённых когорт
              + сумма ожидаемых итогов остальных когорт

Выполнение по факту, %  = Факт(s..d) / План(s..d) × 100
Ожидаемое выполнение, % = Оценка(s..d) / План(s..d) × 100
Отклонение факта, шт.   = Факт(s..d) − План(s..d)
Ожидаемое отклонение    = Оценка(s..d) − План(s..d)

Скорость факта    = Факт(s..d) / число календарных дней s..d
Скорость оценки   = Оценка(s..d) / число календарных дней s..d
```

Зрелая когорта по ADR-029 не обязательно имеет окончательно завершённые
исходы и возвраты. Её наблюдаемый факт не выдаётся за гарантированный итог.
Для нетто-методики условия завершённости и расчёт оставшегося изменения
фиксируются отдельно до реализации.

Правила агрегации:

- Складывать дневные количества и суммы, а не накопительные значения дней.
- Процент выкупа за период считать из суммарных числителя и знаменателя
  соответствующей методики, без среднего дневных процентов.
- Скорости за разные интервалы не суммировать и не усреднять без весов.
- Итог недели или месяца для накопительной строки — значение на конец
  интервала; для дневных значений — сумма дней, для отношений — пересчёт.
- Прокрутка, пагинация SKU и выбор видимого фрагмента календаря не меняют `s`.
- Поздний возврат уточняет прежнюю когорту и последующие накопительные
  результаты. Они могут уменьшиться; исходный план при этом не меняется.
- Нулевой план делает процент выполнения неопределённым; абсолютное
  отклонение при этом показывается.
- Данные отсутствуют или загружены частично — это не подтверждённый ноль.
  Неполный итог явно маркируется, а не выдаётся за полный.
- В расчётах использовать точные неокруглённые компоненты; округлять при
  выдаче результата. Округлённые дневные прогнозы не являются базой сводки.

Пример: к дате план 1 000 шт., наблюдаемый факт 700 шт., итоговая оценка
этих когорт 900 шт. Выполнение по факту — 70%, ожидаемое — 90%, ожидаемое
отклонение — −100 шт. Исходный план остаётся 1 000 шт.

## 5. Прогноз, зрелость и качество данных — предложение

- В ответе разделить наблюдаемый факт, ожидаемый итог и ожидаемое изменение.
  Не называть сумму факта и прогнозируемой части чистым фактом.
- Показывать зрелость каждой точки, долю в доставке, долю без оценки,
  время обновления и идентификатор версии методики.
- Действующие правила ADR-029/031/032/033 сохраняются для существующих
  метрик. Порог зрелости выкупа не становится автоматически порогом
  завершённости клиентских возвратов новой нетто-методики.
- Текущий день показывать как неполный. Предложение: основное сравнение
  к дате вести по вчера включительно, сегодняшний день выделить отдельно.
- Будущие фактические значения отсутствуют; подтверждённые нулевые дни
  показываются нулями только при полной загрузке соответствующих данных.
- Прогноз исходов существующих заказов и прогноз будущего спроса различаются.
  Дневной план автоматически не подменяет прогноз будущих заказов.
- Воспроизводимость сохраняемого прогноза требует версии расчёта и среза
  его входных данных. Текущий изменяемый факт сам по себе прошлый срез не восстанавливает.

## 6. Календарь сезона и enum — предложение

Сохранить запрошенные обозначения в enum типов календарных записей:

| Значение | Подпись | Предлагаемый смысл |
|---|---|---|
| `season_start` | Начало сезона | Начальная дата сезона |
| `season_end` | Конец сезона | Конечная дата сезона включительно |
| `replenishment` | Подсорт | Повторяемое событие пополнения; отправку либо поступление уточнить |
| `sales` | Продажи | Интервал продаж с начальной и конечной датами |
| `replenishment_stop` | Стоп подсорт | Граница прекращения новых пополнений |

Это не взаимоисключающий статус дня. В один день могут идти продажи
и быть подсорт; в сезоне может быть несколько подсортов.
Положение «Стоп подсорт» не останавливает продажи автоматически.
Конец сезона не прекращает учёт поздних выкупов и возвратов его когорт.

Границы сезона и привязка к SKU / группе SKU, возможность нескольких
интервалов продаж, смысл «Стоп подсорт» для уже отправленных партий
и допустимое расположение подсорта до начала сезона уточняются до схемы БД.
Этот календарь сам по себе не рассчитывает поставки и не отправляет заказы.

## 7. Подход и границы

Рекомендация: расширить существующий SalesPlanning, читать агрегаты Ingestion
через пакетный Facade и применять одну явно выбранную методику сравнения.
Ввод плана остаётся существующим пользовательским сценарием.

Альтернативы:

1. Добавить только нынешние метрики Ingestion. Меньше изменений, но они не
   превращаются автоматически в сезонные нетто-продажи с будущими возвратами.
2. Добавить нетто-методику для сравнения с пользовательским планом.
   Предпочтительно при выборе нетто-цели; нужны отдельные определения,
   проверка доступности источников и уточняющий ADR.

Выбор методики владельцем пока не сделан. Существующие планы и API нельзя
автоматически переинтерпретировать. Большой проект сезонного подсорта v2.7
остаётся отдельной отложенной работой; этот документ его не запускает.

Не входят: автоматическое изменение цели, закупки и управление партиями,
симулятор подсорта, ML-прогноз спроса, восстановление спроса при дефиците,
новые внешние зависимости и изменения Go-сервисов.

## 9. Приёмка и проверки будущей реализации

- [ ] Обновление фактов не меняет исходный план; история версий сохраняется.
- [ ] Заказ, выкуп и поздний возврат правильно уточняют исходную когорту.
- [ ] Пример 1 000 / 700 / 900 даёт 70% / 90% / −100 шт.
- [ ] Прогноз полного итога не прибавляется повторно к факту.
- [ ] Проценты взвешены по компонентам, нулевые знаменатели дают отсутствие
  процента; округления не искажают сводку.
- [ ] При смене страницы или видимого диапазона накопление не сбрасывается.
- [ ] Неделя, месяц и весь период согласованы с исходными дневными компонентами.
- [ ] Незрелость, отсутствие прогноза и неполная загрузка различимы;
  частичный результат не выглядит полным.
- [ ] Граница суток МСК, текущий день и поздние исходы покрыты сценариями.
- [ ] Компания и кабинет явно ограничивают чтения; данные и кэш компаний изолированы.
- [ ] Продажи и подсорт могут пересекаться; поздние исходы учитываются после конца сезона.
- [ ] Доступ к данным идёт пакетно, с лимитами и без межмодульного SQL.

Команды запускать при реализации по затронутым областям:

```text
make lint stan deptrac structure-check
make test-unit test-int test-func
make front-typecheck front-lint front-knip front-test front-build APP=seller
make api-doc-export api-types
make api-types-check
```

При изменении схемы обязателен `make db-rebuild-check` после проверки,
что его окружение локальное dev/test. Перед merge — зелёный обязательный CI,
включая audit и E2E. Внешние API в тестах не вызываются.

Для итогового кода — независимое ревью Claude; при изменении денег, схемы,
изоляции или критического пересчёта Ingestion — также два прохода Codex.
Ревью изменившихся частей и затронутые проверки повторяются после исправлений.
Для текущего документа без принятия ADR внешнее ревью не требуется.

## 10. Открытые решения перед началом реализации

1. Что засчитываем в выполнение цели: выкупы или нетто-продажи после возвратов?
   Рекомендация — нетто-продажи; пользователь пока не подтвердил.
   Для «Заказали» требование исключить отмены до доставки уже получено;
   способ обработки неподтверждённых исходов предложен в подробном плане.
2. Какую денежную величину называем выручкой и какой источник подтверждает
   цену и возврат? Предложение — стоимость продаж после возвратов до расходов.
3. Устраивают ли календарные записи разных типов вместо одного статуса дня;
   что означает подсорт — отправку или поступление; как задаётся «Продажи»?
4. Подтвердить область сезона, базовую версию сравнения и правила последующих
   ручных изменений цели, сохраняя исходную версию.
5. Согласовать пакетный Facade, API, модель календаря и необходимые ADR
   в рамках единой точки согласования по CLAUDE.md.

Опционально, отдельным расширением: скорость за последние 7/14 дней,
необходимый темп до конца сезона и прогноз ещё не полученных заказов.
Они не включаются автоматически в первую реализацию.
