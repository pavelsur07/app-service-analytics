# Юнит-экономика Ozon по методу начисления — план

**Ветка:** `task/ozon-unit-economics-accrual`
**ADR:** ADR-036 (новый, пишется в этой задаче)
**Риск ревью:** high — деньги, Ingestion. Claude + оба прохода Codex.

## Зачем

Сверка с отчётом кабинета «Начисления» за август 2026 (выгрузка владельца,
17 192 строки, сопоставление с продом по отправлению и SKU) показала:

| Что | Результат |
|---|---|
| Расходы `marketplace_expense_fact` | совпали с кабинетом до копейки: −642 593,07 ₽ |
| Выручка продаж из `sales_fact` | 1 215 из 1 215 сопоставимых сумм совпали |
| **Возвраты** | 102 возврата (−248 162 ₽ выручки, +119 076,30 ₽ комиссии) юнит-экономика не вычитает: в `sales_fact` они остаются `delivered` |
| Период | выручка берётся по дате заказа, расходы — по дате начисления: в одном месяце смешаны два разных периода |
| Разбор `by-day` | строка возврата (`POSTING`, `delivery: null`, только блок `commission`) пропускается молча — ноль строк, без ошибки |

## Согласовано владельцем 2026-09-28

1. Юнит-экономика целиком переходит на **метод начисления**: выручка,
   комиссия, возвраты и расходы берутся из `/v1/finance/accrual/by-day`
   по **дате начисления**, как в отчёте кабинета.
2. Возвраты — из денег Озона (строки возврата `by-day`), а не выводятся
   из статусов. Возврат в пути учитывается, как только Озон его начислил:
   момент задаёт площадка, отдельного правила по статусам нет.
3. Себестоимость — по штукам, начисленным за период: продажи минус возвраты.
4. Добор `by-day` с **01.07.2026** в рамках выкладки.
5. Предупреждение на экране о неполном покрытии периода начислениями.
6. **Не трогаем:** процент выкупа (своя логика, когорты по дате заказа),
   план-факт продаж. Оба остаются на `sales_fact` / `marketplace_return_fact`.

7. Реклама по SKU остаётся из Performance API (ADR-035): дата расхода
   совпадает с датой начисления «Оплаты за клик», сумма сверяется с `by-day`.
8. «Заказано, шт» из юнит-экономики убирается: заказы — на экране план-факта.
9. Одна таблица: выручка и комиссия пишутся в `marketplace_expense_fact`,
   новой таблицы и миграции нет.

## Шаги

1. ADR-036 и строка в CLAUDE.md.
2. `OzonFeeTypeNames`: код 0 «Выручка», список типов продажи `[0, 69]`.
3. Разбор `by-day`: строки выручки и комиссии из блока `commission`,
   проверка «штука = строка», проверка баланса начисления. Unit-тесты
   на фикстуре.
4. Читатели расходов в `UnitEconomicsQuery`: исключить типы продажи.

5. `UnitEconomicsQuery::skus`: продажи, возвраты и комиссия из ленты
   по дате начисления; себестоимость продажи по дате начисления, возврата —
   по цене исходной продажи. Integration-тесты, включая изоляцию компаний.
6. `BuildUnitEconomicsAction`, DTO, ответ API: новые поля, `orderedQuantity`
   удалить. OpenAPI и типы фронтенда.
7. Экран: «Продано», «Возвраты шт / ₽», подпись «по дате начисления»,
   текст предупреждения о покрытии; тесты.
8. Локальные проверки: stan, cs, deptrac, тесты, фронтенд.
9. Ревью Claude + Codex 5A + 5B, разбор замечаний.
10. PR, CI, merge, деплой.
11. Добор `by-day` с 01.07.2026 на проде.
12. Приёмка: август против выгрузки кабинета до копейки. Отчёт.

## Что проверено на данных

- Фикстура `finance-accrual-by-day-2026-07.json`: у всех 255 начислений
  сумма составляющих равна `total_amount` (услуги доставки + `item_fees` +
  `non_item_fee` + `sale_amount` + `sale_commission`). У всех 31 строк
  с блоком `commission` `seller_price = sale_amount`.
- Продажа: `2747 − 1263,62 (комиссия) − 76,85 (логистика) = 1406,53`.
  Возврат: `−2402 + 1104,92 = −1297,08`.
- Группа «Продажи» кабинета (Выручка + Баллы за скидки + Программы
  партнёров) за август = 2 895 370,00 ₽ = сумма `seller_price` продаж.

## Пакет 1 — продажи и возвраты из `by-day` в `marketplace_expense_fact` (backend, Ingestion)

**Новой таблицы нет — решение владельца 2026-09-28.** Блок `commission`
пишется в ту же `marketplace_expense_fact`, что и услуги. Зерно и ключ
подходят без изменений: одна сумма одного типа по одному товару в одном
начислении, `source_row_id = accrual_id | marketplace_sku | fee_type_id`
(ADR-012). Таблица становится полной лентой начислений `by-day`; имя
`expense` исторически неточно, переименование не окупается.

Из блока `commission` у товара `POSTING` — две строки:

| Строка | `fee_type_id` | Сумма |
|---|---|---|
| Выручка (цена продавца) | **0** — свой код: у Озона в `accrual/types` выручки нет | `sale_amount` со знаком площадки |
| Вознаграждение за продажу | **69** `SaleCommission` — код самого Озона | `sale_commission` со знаком площадки |

- Продажа или возврат — по знаку строки выручки: `+` продажа, `−` возврат.
  Ноль — отказ документа.
- **Штука = строка выручки.** Количества в `by-day` нет; разбор требует
  `sale_amount = seller_price` (по модулю) и иначе отклоняет документ.
  Сегодня так у всех строк, и в кабинете у каждой «Выручки» количество 1.
  Появится строка на несколько штук — узнаем отказом, а не ошибкой в штуках.
- Код 0 — константа в `OzonFeeTypeNames` («Выручка»), 69 уже есть
  в справочнике. Список «типы продажи» `[0, 69]` — одна константа, по ней
  фильтруют все читатели.
- **Проверка баланса начисления:** сумма всех разобранных строк равна
  `total_amount`, иначе документ отклоняется исключением, raw остаётся.
  Закрывает молчаливый пропуск: ни одна копейка начисления не проходит
  мимо разбора незамеченной.

**Запись** — тот же `DoctrineMarketplaceExpenseFactWriter`, тот же upsert
и та же идемпотентность. Новых Entity, Builder и writer нет.

**Миграции нет.** Возврат ищет исходную продажу по `unit_number` + SKU;
индекс `(company_id, marketplace_sku)` уже есть. План запроса проверяется
на объёме прода; если его окажется мало — индекс выносится владельцу,
а не добавляется молча.

**Читатели таблицы — что меняется:**

| Читатель | Изменение |
|---|---|
| `UnitEconomicsQuery`: расходы товара и разбивка по типам | исключить `[0, 69]` — иначе выручка попадёт в расходы |
| `UnitEconomicsQuery`: строки кабинета (SKU пустой) | нет: у выручки SKU всегда есть |
| `AdvertisingReconciliationQuery` | нет: фильтр по типу 41 |
| `LocalizationSql` | нет: фильтр по типам логистики |
| очистка неподтверждённых аккаунтов | нет: удаляет по компании |

Тест закрепляет, что сумма расходов товара не содержит типов продажи.

## Пакет 2 — юнит-экономика (backend)

`UnitEconomicsQuery::skus`:
- агрегат продаж — из строк `[0, 69]` `marketplace_expense_fact`
  по `business_date` периода вместо `sales_fact`:
  - `sold_quantity` — штуки продаж, `returned_quantity` — штуки возвратов;
  - `revenue_minor` — продажи + возвраты (нетто, возвраты отрицательные);
  - `returns_minor` — сумма возвратов отдельно, для показа;
  - `commission_minor` — комиссия продаж + возврат комиссии (нетто);
- себестоимость:
  - продажа — цена, действующая на дату начисления продажи (ADR-013, как
    сейчас, но другая дата);
  - возврат — сторно по цене **исходной продажи** (та же пара
    «отправление + SKU», строка выручки со знаком `+`). Если продажа начислена до
    начала загрузки — по цене на дату возврата. Иначе смена цены между
    продажей и возвратом давала бы фантомную прибыль или убыток;
- расходы, реклама, листинг, курсор, сортировка — без изменений.

`BuildUnitEconomicsAction` — арифметика только через `Money` (ADR-004),
как сейчас. Маржа = выручка нетто + комиссия нетто + расходы + реклама.

**Покрытие периода:** `daysWithoutExpenses` уже считает дни без загруженного
`by-day`. Теперь это дни без начислений вообще — ни продаж, ни расходов.
Поле остаётся, меняется смысл и текст на экране.

**Контракт API** (`ShowUnitEconomicsController`, OpenAPI, типы):
- `revenueMinor`, `commissionMinor` — теперь «начислено за период, нетто»;
- `deliveredQuantity` → штуки продаж, начисленных за период;
- новые: `returnedQuantity`, `returnsMinor`;
- `orderedQuantity` — удаляется.

## Пакет 3 — экран (apps/seller)

- карточка товара и итог: «Продано, шт», «Возвраты, шт», «Возвраты, ₽»,
  выручка нетто;
- предупреждение: «Начисления загружены не за весь период: за N из M дней
  их нет — выручка, возвраты и расходы за эти дни не учтены»;
- подпись периода: «по дате начисления Ozon».

Арифметики над деньгами в компонентах нет (§10), только форматирование.

## Тесты

- **unit, разбор:** продажа, возврат, несбалансированное начисление →
  отказ, `seller_price` не делит `sale_amount` → отказ, знак и валюта
  у каждой суммы; фикстура `finance-accrual-by-day-2026-07.json`
  (30 продаж, 1 возврат, 255 начислений в балансе);
- **integration, запись:** повтор того же документа не меняет строки;
  изменившаяся сумма обновляет строку, а не добавляет вторую;
- **integration, читатели:** расходы товара и разбивка по типам
  не содержат строк `[0, 69]`;
- **integration, юнит-экономика:** возврат уменьшает выручку, комиссию
  и себестоимость; себестоимость возврата — по цене исходной продажи;
  период берётся по дате начисления; изоляция — чужая компания с тем же
  номером отправления не попадает в отчёт;
- **денежная арифметика** в сборке отчёта: маржа из нетто-величин;
- **frontend:** форматирование новых полей, текст предупреждения.

## Выкладка и проверка на проде

1. PR, ревью (Claude, Codex 5A, Codex 5B), зелёный CI, merge, деплой.
2. Миграции нет — шаг пропускается.
3. Добор: `app:ingestion:backfill-ozon-expenses <companyId> <accountId>
   2026-07-01 <сегодня>` — обычный коннектор, по дню на сообщение.
   Дни, которые уже есть в raw, дают те же документы (дедупликация
   по содержимому, ADR-006), и разбор дописывает строки продаж и возвратов.
4. **Приёмка — август против выгрузки кабинета до копейки:**
   - продажи 2 895 370,00 ₽;
   - возвраты −248 162,00 ₽;
   - вознаграждение Ozon нетто −1 274 756,98 ₽;
   - расходы −642 593,07 ₽ (не изменились).
5. Июль — та же сверка, если владелец пришлёт выгрузку за июль.

**Если добор упрётся в проверку баланса** (например, компенсации 31.08:
три строки на +11 960,94 ₽, которых в фактах нет), день будет отклонён
целиком: исключение уходит в трекер, сообщение — в очередь failed.
Предупреждение о покрытии такой день **не** покажет: raw сохранён до
разбора, и контроль покрытия считает день загруженным (так же сегодня
ведёт себя незнакомая категория). Значит, в ответе `by-day` есть форма,
которую разбор не знает. Это возврат к плану с конкретным начислением
на руках, а не молчаливый обход. Отметка «день разобран» для контроля
покрытия — отдельная задача: это изменение схемы raw-слоя.
