# Юнит-экономика → вкладка «Сверка»: начисления Ozon по категориям — план

**Ветка:** `task/ozon-accrual-categories`
**Основа:** ADR-036 (лента начислений `by-day` в `marketplace_expense_fact`,
сверена с кабинетом до копейки за июль и август 2026)
**Риск ревью:** high — деньги и Ingestion. Claude + оба прохода Codex.

## Зачем

Клиент сверяет наши цифры с отчётом кабинета «Начисления». Вкладка
показывает ту же картину, что кабинет: группы начислений и статьи внутри
них за период, без разбивки по товарам, и итог к начислению. Совпадение
итога с кабинетом — видимая проверка, что данные загружены полностью.

Остальные ~100 типов справочника у клиента не встречались; куда их
относит кабинет — неизвестно, угадывать не будем. Появится тип —
он виден в «Без группы», соответствие дописывается по выгрузке.

Соответствие — константа в Domain (`OzonAccrualGroups`), рядом
с `OzonFeeTypeNames`: справочник площадки, не данные клиента.

**Известное расхождение в разбивке, не в итоге.** Кабинет относит часть
отрицательной выручки (за август 5 284 ₽ — вероятно, корректировки
продаж) к «Продажам», а мы делим строки выручки по знаку. Продажи
у нас больше, возвраты меньше на ту же сумму; нетто и итог совпадают.
Отличить корректировку от возврата по ленте нечем. Подпись под группами
это называет.

## Шаги

1. `OzonAccrualGroups`: группы, порядок, соответствие типов. Unit-тест:
   каждый тип соответствия есть в `OzonFeeTypeNames`, тип в одной группе.
2. `AccrualCategoriesQuery` (DBAL, `Infrastructure/Query/UnitEconomics`):
   `SUM(amount_minor)` по `fee_type_id`, знаку выручки
   и валюте за период, `company_id` первым условием, лимит 200 строк
   (типов у площадки 119, две строки даёт только выручка — не больше 121).
3. `BuildAccrualReconciliationAction`: группировка, итоги групп и общий
   через `Money::sum`, одна валюта или исключение (ADR-004), дни без
   начислений — существующий `ExpenseCoverageQuery`.
4. Контроллер `GET /api/companies/{companyId}/unit-economics/reconciliation`
   `?month=YYYY-MM` (Nelmio-атрибуты); неверный месяц → 422.
   OpenAPI и типы фронтенда.
5. Фронтенд: вкладки на `UnitEconomicsPage` (`?view=`), компонент
   `AccrualReconciliationPanel` — таблица групп с раскрытием, выбор периода,
   предупреждение о покрытии. Ключ кэша — через общий хелпер
   с `companyId` (§7). Денежной арифметики в компонентах нет.
6. Тесты:
   - integration, сценарий: группы и итог из строк ленты; продажа
     и возврат в разных группах; тип без соответствия — в «Без группы»;
     изоляция — строки чужой компании не попадают; период по дате
     начисления;
   - functional: изоляция через HTTP (чужая компания, тот же артикул),
     неверный месяц → 422;
   - frontend: хелпер параметра вкладки, форматирование.
7. Локальные проверки, ревью (Claude + 5A + 5B), CI, merge, выкладка.
8. Приёмка на проде: август по группам против выгрузки кабинета —
   итог 741 818,89 ₽; каждая группа услуг, вознаграждение и компенсации —
   до копейки; продажи/возвраты — нетто 2 647 208,00 ₽.

Миграции нет. Новый эндпоинт; существующие контракты не меняются.

## Решено владельцем 2026-09-28

- **Период вкладки — календарный месяц** с выбором месяца, по умолчанию
  прошлый полный: кабинетный отчёт сверяют месяцами. API принимает
  `month=YYYY-MM`.

## Дополнение 2026-09-28: начислено и возвращено

По просьбе владельца у каждой статьи — «начислено» (строки со знаком
статьи) и «возвращено» (обратный знак: возврат комиссии, эквайринга,
отмена логистики), рядом с нетто. Суммы по знаку считает запрос
(`SUM … FILTER`), разметку «начислено/возвращено» по знаку нетто —
сценарий; экран только показывает. У дохода (компенсации) обратная
строка подписана «удержано». У вознаграждения «возвращено» — это
«Возврат вознаграждения» кабинета плюс положительные строки
«Вознаграждения за продажу»: по ленте их не различить.

## Вне объёма
