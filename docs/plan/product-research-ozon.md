## 1. Цель и объём

Пользователь создаёт проект подбора товаров одной категории Ozon, выбирает
периоды исследования и получает полные помесячные сырые срезы MPStats.
К проекту можно вернуться, добавить периоды и дозагрузить неудачные месяцы.

В MVP входят проект, справочник категорий, предпросмотр, получение всех страниц,
хранение сырья, проверка полноты, кэш, прогресс и восстановление загрузки.
Очистка, склейка, фильтр продаж, панельная таблица, XLSX, обогащение, скоринг
и анализ ниши не входят. Требования к их входным данным фиксируются заранее.

### Методология

- Период исследования — именованный диапазон календарных месяцев, например
  «Зима 2025/26»: декабрь 2025 — февраль 2026. Это не отдельная выгрузка.
- Единица получения, проверки, кэша и повторной обработки — месячный срез.
- Пересекающиеся периоды сохраняют названия, но используют одни месячные срезы.
- Закрытый месяц берётся целиком; произвольные даты и скользящие 30 дней
  в MVP не поддерживаются. Неполный текущий месяц — явное исключение.
- Одна кнопка загружает весь объём, внутри — задания на месяцы и страницы.
  Сезонный агрегат не заменяет данные SKU × месяц.
- Все поля и строки исходного отчёта сохраняются без фильтров и преобразований.
- Методология требует FBS. Базовый вариант плана — фиксированное `FBS=true`,
  отображаемое в интерфейсе. Это уточнение первоначального переключателя;
  подтвердить на этапе 0, не реализовывать два режима без необходимости.
- «Новинки: Неважно»; фильтров по продажам и остаткам при загрузке нет.

## 2. Предлагаемые границы и структура

Symfony владеет проектом, компанией, автором, периодами, правами и пользовательским
API. Новый модуль и его точные связи определить в ADR. Python владеет выполнением
загрузок, справочником MPStats, снимками, кэшем и техническим журналом. Проекция
статуса в Symfony обновляется по контракту; определения параметров не дублируются.

Сервис имеет свою логическую БД, роль и префикс S3. Доступа к БД монолита нет.
Контракты — `services/_contracts/`. Один сервис и отдельный worker из того же
образа; отдельные микросервисы этапов и универсальный workflow-движок не нужны.

Предлагаемая структура, создаваемая по мере реализации:

```text
services/product-research-ozon/
├── README.md
├── AGENTS.md
├── pyproject.toml
├── migrations/
├── src/product_research_ozon/
│   ├── api/             # Внутренний API
│   ├── jobs/            # Запуски, состояния, аренда задания
│   ├── categories/      # Справочник категорий и поиск
│   ├── collection/      # MPStats, страницы, проверка полноты
│   ├── snapshots/       # Кэш и публикация снимков
│   └── infrastructure/  # PostgreSQL, HTTP, S3, логи
└── tests/
    ├── unit/
    ├── integration/
    └── contracts/
```

Правила: контроллер только принимает запрос; orchestration не содержит формул,
HTTP и SQL; клиент MPStats не меняет проект; проверка полноты не выполняет I/O.
Доступ к данным конкретного этапа расположен рядом с ним. Нет общего изменяемого
`context`, универсального `BaseService`, папки со случайной бизнес-логикой `utils`.
Границы импортов проверяются автоматически. Типизированные контракты обязательны.

### Сущности и инварианты

| Сущность | Назначение |
|---|---|
| Проект | Категория, название, комментарий, компания, автор, настройки |
| Период исследования | Название, первый и последний календарные месяцы |
| Месячный срез проекта | Уникальная потребность проекта в месяце и выбранный снимок |
| Запуск | Одно действие загрузки, зафиксированные параметры и набор месяцев |
| Попытка месяца | Конкретная попытка получения данных, ошибки и повторы |
| Снимок | Проверенный набор страниц, даты, источник и версия контракта |
| Страница | Исходные байты ответа, порядок, число строк, размер, checksum |

Один готовый снимок может обслуживать несколько проектов в разрешённой области
кэша. Периоды связываются с месячными срезами без копирования данных.
Дата получения из MPStats отличается от даты использования из кэша.
Для каждого среза: даты включительно, дней, неполнота, FBS, валюта, число строк,
`total`, время загрузки, статус и безопасное описание ошибки.

Параметры категории и FBS блокируются с первого принятого запуска. Копирование
создаёт черновик без истории попыток; пригодный кэш может использоваться повторно.
Новые периоды не изменяют состав уже выполняющегося запуска.

## 3. Общий порядок TDD и завершения этапов

Для каждого поведенческого сценария: **Red → Green → Refactor**.

1. Написать тест наблюдаемого поведения и увидеть ожидаемое падение.
2. Реализовать минимальное решение и получить зелёный результат.
3. Упростить код без изменения поведения, повторить затронутые проверки.
4. Записать команды, результаты и ограничения в отчёт этапа.

Unit-тесты — календарь, полнота и переходы состояний; integration — настоящие
тестовые PostgreSQL/S3 и конкурентность; contract — границы PHP/Python/MPStats;
functional — права и API; Vitest + типизированный MSW — UI; Playwright — пути
пользователя. Не тестировать частные методы и точный порядок внутренних вызовов.

В автоматических тестах нет запросов к MPStats, реальных токенов и подмены
глобального fetch. Фикстуры — по правилам CLAUDE.md, без запрещённых данных.
Часы, паузы и сбои управляемы в тестах; реальный сон для повторов не нужен.
PHP/Node и будущие Python-проверки запускаются через контейнеры и Makefile.

Каждый этап — законченная задача/PR с затронутыми тестами и документацией.
Миграции — одна итоговая на задачу, с восстановлением/откатом по правилам проекта.
Обязательный CI должен быть зелёным до merge. Для кода нужен Claude;
схема, изоляция, секреты и код сервиса загрузки требуют также обоих проходов
Codex. Разбор замечаний и повторные проверки обязательны. Команды и пакет —
[шаблон ревью](../review-package-template.md), порог — [CLAUDE.md](../../CLAUDE.md).

## 4. Следующая волна — за границами MVP

Отдельный план после приёмки сырой загрузки:

- Нормализация и панель SKU × месяц: продажи > 0, без фильтра по остаткам;
  пропуск значения не равен нулю. Один SKU в разных месяцах — разные наблюдения.
- Отдельные неизменяемые входы и версии обработанных результатов. Исходные
  страницы не переписываются; повтор обработки не требует API пока сырьё хранится.
- Явные колонки дат, числа дней, неполноты и происхождения данных.
- Сверка по месяцу: получено = исключено + ошибочно + принято;
  принято = записано. Ошибочные строки не позволяют выдать результат как полный.
- Хронология в выдаче через явную сортировку, не физический порядок PostgreSQL.
- Склейка и XLSX, затем обогащение, признаки, паттерны и анализ ниши.
- TDD следующей волны: точные эталоны отбора, пропуски, отсутствие двойного учёта
  пересекающихся периодов, повторяемость расчёта и равенство контрольных итогов.
