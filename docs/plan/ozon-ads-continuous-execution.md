# Постоянное наблюдение Ozon Ads: выполнение согласованного этапа

09.11.2026. Основание: поручение «Приступай» после плана из пяти шагов.
Основной план: [N0–N5](ozon-advertising-observe-launch-plan.md).
Это реестр выполнения, а не разрешение обходить входные условия основного плана.

## Результат и порядок

Постоянный observe получает оперативные JSON по рассчитанному X, локально
обрабатывает расписание и публикует предполагаемые решения. Ночные отчёты
не являются триггером его работы. Реальные команды управления не входят в этап.

Работа разбивается на законченные изменения, каждое проходит проверки,
независимые ревью и CI до merge. После завершения переход к следующему изменению
автономный. Закрытые условия live-допуска не мешают локальной разработке.

1. **Паспорт распределения и ёмкость.** Машинно проверяемый локальный документ
   распределяет подтверждённый предел между Ads/PHP/fetcher/прочими и резервом.
   Без доказанных scope/window/потребителей/начального состояния выдача допуска
   невозможна. Расчёт X учитывает верхнюю цену цикла, OAuth, повторы, границы окна.
2. **Учёт попыток.** Durable-резерв перед каждым HTTP в собственной БД каждого
   потребителя; разные реплики суммируются, ревизия/ключ не обнуляют счётчик.
   Сначала проверяем полноту учёта и bootstrap; действующую аналитику нельзя
   молча остановить из-за отсутствующего паспорта. Ads live остаётся закрытым.
3. **Постоянный цикл.** Проверка дневных окон, дедлайнов, рестартов, устаревших
   источников, конкуренции и отказов без ранних HTTP. Существующий Go engine
   расширяется только там, где обнаружен пробел; параллельный engine не создаётся.
4. **Эксплуатация.** Закрытая production-топология и независимый мониторинг,
   конфигурация/автоперезапуск/откат. Сначала без разрешённых внешних чтений.
5. **Допуск одного кабинета.** Только после доказательств N0–N4 и отдельного
   live-допуска; наблюдение работает непрерывно. Недостаток данных не объявляется
   нулём или доказанным запасом бюджета.

## Чек-листы

### 1. Паспорт и интервал

- [ ] Документ имеет версию, область/окно, источники доказательств и срок действия.
- [ ] Все три внутренних потребителя обязательны, прочие и резерв явно учитываются.
- [ ] Сумма долей и резерва ≤ подтверждённого лимита; отрицательные/переполненные значения отвергаются.
- [ ] Неизвестное внешнее потребление, scope/reset или bootstrap не дают live-допуск.
- [ ] Цена цикла и X учитывают кампании/страницы, OAuth/повторы и дополнительный цикл на границе.
- [ ] Арифметика целая, округление числа циклов вверх; числовых production-умолчаний нет.

### 2. Резервирование

- [ ] Попытки OAuth/чтений/ошибок/повторов покрыты у Ads, PHP, fetcher.
- [ ] У каждого потребителя своя БД, доступ к чужой БД не добавлен.
- [ ] Конкуренция/падение/unknown/revision/key rotation не создают квоту.
- [ ] Пустое/неполное начальное окно не считается нулевым расходом.
- [ ] Изменение долей соблюдает уменьшение → вымывание прежнего окна → увеличение.

### 3. Постоянный цикл

- [ ] Проверены дневные start/stop и смена суток без ночного рескана.
- [ ] HTTP не раньше X, локальные дедлайны не ждут X.
- [ ] Медленный/сломанный кабинет не занимает весь пул.
- [ ] Проверены недоступность БД, Ozon, рестарт, clock skew и истечение разрешений.
- [ ] Длительный стенд по N3; fake-clock проверка не выдаётся за реальное soak-наблюдение.

### 4. Эксплуатация

- [ ] Топология, ограниченные роли/сети и миграции проверены.
- [ ] Нет публичного порта/роутера и утечки сервисных токенов.
- [ ] Watcher независим от отказа контроллера и его узла либо гейт остаётся открытым.
- [ ] Production smoke проверен без специального обращения к Ozon.

### 5. Один кабинет

- [ ] Факты N0, паспорт N1, учёт N2, аварии N3, эксплуатация N4 подтверждены.
- [ ] Пара company/account и охват пилота зафиксированы, live-допуск получен.
- [ ] UI показывает время получения, следующий опрос, качество и предполагаемое решение.
- [ ] Пилот и переходы суток проверены; неувиденные события отмечены явно.

## Первая поставляемая часть: offline quota-check

Реализован ограниченный офлайн-парсер и калькулятор в Go. Он проверяет
доли всех потребителей, резерв, срок, наличие заявленных доказательств и
верхний расход Ads с округлением циклов вверх, дрейфом и дополнительным циклом.
Одинаковая область суммирует кабинеты. Есть защита от дубликатов/неизвестных
JSON-полей, слишком больших/глубоких документов, невалидного UTF-8,
нецелых/отрицательных чисел и переполнений. CLI не отражает пути, ID или
содержимое доказательств. `requires_live_admission=true` остаётся обязательным
даже при passport_ready: правильность деклараций проверяет оператор, не парсер.

Ни runtime-конфигурация, ни ledger 70000/24ч, ни допуски не изменены.
Офлайн-паспорт не перенастраивает реальные опросы; бюджет для production не назначен.
Ссылка на реализацию/поля: [README контроллера](../../services/ozon-ads-controller/README.md#офлайн-проверка-квот-перед-допуском).

Проверки первой части:

- [x] Округление границ и дрейфа, нехватка ёмкости и суммирование кабинетов покрыты тестами.
- [x] Неизвестные подтверждения и недействующий срок дают явные блокировки.
- [x] Проверены переполнения, дроби, неизвестные/дублированные поля и безопасный вывод CLI.
- [x] fmt/vet/lint после последних правок PASS; gosec не ослаблялся:
  чтение выбранного оператором файла ограничено через os.Root.
- [x] Финальный тестовый прогон, vulncheck/build после последних правок завершены.
  Полный test включает race и исходный стенд; после исправлений internal 85,0%,
  quota 92,2%; уязвимостей 0.
- [x] Два независимых ревью свежими Codex CLI вместо отсутствующего Claude завершены.
- [x] CI/merge первой части завершены; выпуск не выдаётся за запуск Go в production.

Повторная проверка источников 09.11: [официальная новость 14.09.2026](https://dev.ozon.ru/news/794-Performance-API-vvedenie-ogranichenii-na-kolichestvo-zaprosov/)
подтверждает наличие ограничений, но не scope/reset общей квоты.
[Limits](https://docs.ozon.ru/api/performance/#tag/Limits) опять не даёт читаемый
текст инструменту. Историческое [обсуждение 2023 года](https://dev.ozon.ru/community/615-Limity-po-formirovaniiu-otchetov/)
не используется как текущая спецификация. Неофициальные копии не закрывают гейт.

Оба запрошенных факта получены: только Conwix для пилотной организации,
внешнего монитора нет. Новую внешнюю зависимость требуется сначала описать
конкретным предложением по N4; существующий монитор в плане не выдумывается.

Локальные результаты первой части: `var/continuous-quota-static-final.log`,
`var/continuous-quota-tests-final.log`; fmt/vet/lint/test/vulncheck/build PASS.
Это не многосуточная N3-приёмка: выполнен существующий ограниченный стенд.
Остальные чек-листы основного этапа остаются открытыми; N0/N1 не закрываются
наличием утилиты. Никакие реальные ключи/паспорта сюда не приложены.

Для каждого случая добавлена регрессия. Повтор fmt/vet/lint/test/race/vulncheck/build
после исправлений PASS (`var/continuous-quota-fixed-gates.log`). Повторное ревью

## Вторая часть: измерение отправок PHP/fetcher

[Технический план и приёмка](ozon-performance-http-accounting.md).
Добавляются durable-счётчики до HTTP, включая OAuth и явные повторы;
проверяется отсутствие скрытых повторов и редиректов. Никакие cap, доли,
частоты и live-допуски этим изменением не назначаются. Полнота окна,
ограничение квоты и генерации отчётов остаются отдельными условиями N0–N2.

[PR #340](https://github.com/pavelsur07/app-service-analytics/pull/340) merged,

повторные 5A/5B complete, 0/0 новых замечаний. Подробные результаты — в плане
второй части. Master CI `42606220786` в итоге success после отдельного применения
API/fetcher-миграций по штатным гейтам. Production smoke 09.11 11:39 UTC подтвердил
