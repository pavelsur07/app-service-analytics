# Восстановление пароля по email — план задачи

**Цель:** продавец, забывший пароль, сам восстанавливает доступ к кабинету
по ссылке из письма, без оператора. Злоумышленник, знающий только адрес,
не может ни войти, ни узнать, зарегистрирован ли адрес в Conwix.

**Основание:** ADR-007 и ADR-021 держат восстановление пароля в списке
отложенного. Публичный pre-auth endpoint допустим только с отдельным ADR
(CLAUDE.md §1) — поэтому этап 0 обязателен и идёт до кода.

**Риск ревью:** `high` (аутентификация, секреты) — Claude 5C + Codex 5A + 5B.

**Образец:** подтверждение адреса из ADR-021 (`EmailVerificationSecret`,
`EmailVerificationToken`, `ConfirmEmailAction`, `ResendEmailVerificationAction`,
`RegistrationProtection`). Новое повторяет его механику, а не изобретает свою.

## Уточнения по итогам разбора кода (до этапа 0)

- `apiPost` на фронтенде всегда читает JSON-тело, поэтому подтверждение
  сброса отвечает `200 {"status":"password_changed"}`, а не `204`.
- Защита от роботов регистрации (`RegistrationProtection`: два лимита по
  HMAC-ключам email/IP + капча, fail closed) не привязана к регистрации по
  смыслу — она обобщается в `PublicFormProtection` и настраивается вторым
  экземпляром с лимитами сброса. Логика не копируется.
- Аудит пишет только факт смены пароля (`user.password_reset`) — изменение
  учётных данных. Запрос сброса в журнал не пишется: он ничего не меняет,
  а запись только для существующего адреса добавила бы ветке лишнюю работу
  и различие по времени.
- Сессии: Symfony `ContextListener::hasUserChanged` сравнивает хэш пароля
  при каждом восстановлении сессии, поэтому смена хэша сама разлогинивает
  все сессии. Отдельный код не пишется — поведение закрепляется тестом.
- Фронтенд-автомат капчи (`captchaFlow`) типизирован под форму регистрации;
  он обобщается параметром типа, а не копируется.

## Принципы (не меняются по ходу задачи)

- Ответ на запрос сброса одинаков для любого адреса: код, тело, время.
  Различие — только в письме: известный подтверждённый адрес — ссылка;
  неподтверждённый — письмо подтверждения адреса (не сброса); неизвестный —
  нейтральное письмо без ссылки. SMTP синхронный во всех ветках.
- Токен — 256 бит из CSPRNG; в БД только `sha256`; открытый текст только
  в письме. Письмо уходит мимо Messenger.
- Погашение — одним `UPDATE ... WHERE consumed_at IS NULL AND expires_at > now()
  RETURNING user_id`. Проверки перед записью нет (§4).
- Новый запрос гасит все непогашенные токены пользователя: живёт последняя ссылка.
- Смена хэша пароля завершает все сессии пользователя (штатный
  `hasUserChanged` Symfony — подтверждается тестом). `remember_me` в проекте нет.
- Невалидный, истёкший и погашенный токен дают один и тот же ответ.
- Сброс не подтверждает адрес и не снимает блокировку компании (ADR-017).
- Токен не попадает в логи, GlitchTip, access-логи прокси и Referer.

## Этап 2. Backend — репозиторий и запросы

- [ ] 2.1 `PasswordResetTokenRepository` (Domain) + Doctrine-реализация:
      - `issue(PasswordResetToken)` — вставка;
      - `revokeActiveForUser(Uuid $userId)` — `UPDATE ... SET consumed_at = now()
        WHERE user_id = :u AND consumed_at IS NULL`;
      - `consume(string $tokenHash, DateTimeImmutable $now): ?Uuid` — атомарное
        погашение с `RETURNING user_id`.
- [ ] 2.2 Поиск пользователя по адресу — существующий `findByEmail`
      (User без `companyId`, аутентификационная граница); докблок со ссылкой на §1.
- [ ] 2.3 Advisory-lock с уборкой неподтверждённых аккаунтов — проверить,
      нужен ли (сброс неподтверждённому не выдаётся — скорее нет; записать в отчёт).

**Результат этапа:** интеграционные тесты репозитория зелёные (этап 7.1).

**Детальный план этапа 2:**
- `issue()` — транзакция: `pg_advisory_xact_lock` по пользователю →
  гашение непогашенных → вставка. Без блокировки два параллельных запроса
  оставили бы две живые ссылки. Погашение блокировку не берёт, поэтому
  взаимоблокировки выпуска и погашения нет.
- `resetPassword()` — транзакция: `UPDATE token ... RETURNING user_id` →
  `UPDATE "user" SET password_hash ... RETURNING email` → гашение остальных
  ссылок → аудит `user.password_reset` (`company_id` пуст, актор и субъект —
  пользователь). Возвращает адрес для уведомления, сущность не гидрирует.
- Поиск по адресу — свой узкий `PasswordResetUserByEmailQuery`, по образцу
  resend, а не широкий `UserRepository::findByEmail`.

**Приёмка этапа 2:**
- [ ] Выпуск новой ссылки гасит прежнюю
- [ ] Ссылка меняет пароль один раз; повтор → null, хэш не меняется
- [ ] Истёкшая и неизвестная ссылка → null, ничего не меняется
- [ ] После сброса остальные ссылки пользователя погашены
- [ ] Аудит — ровно одна запись, без значений и без компании
- [ ] В таблице лежит только хэш

## Этап 3. Backend — сценарии (Application)

- [ ] 3.1 `RequestPasswordResetAction(email, clientIp)`:
      лимиты → нормализация адреса → `findByEmail` → ветвление по исходу →
      `revokeActiveForUser` + `issue` → синхронное письмо → аудит
      `password.reset_requested` (только для существующего пользователя).
      Возвращает `void` во всех ветках.
- [ ] 3.2 `ResetPasswordAction(token, newPassword)`:
      валидация пароля тем же валидатором, что при регистрации → `consume` →
      хэш → `changePassword` + `flush` в одной транзакции с погашением →
      аудит `password.reset_completed` → письмо-уведомление.
      Хэширование — после проверки лимита и после успешного `consume`.
- [ ] 3.3 Порт `PasswordResetEmailSender` + `MailPasswordResetEmailSender`
      (Symfony Mailer, синхронно, мимо Messenger). Три шаблона: ссылка сброса,
      нейтральное письмо, уведомление о смене пароля (без активных ссылок).
- [ ] 3.4 `AuditAction`: два новых значения.

**Результат этапа:** сценарии работают из теста без HTTP.

**Детальный план этапа 3:**
- `RequestPasswordResetAction(email, now)` — внутри shared-секции
  `EmailVerificationLifecycleGuard` (как resend: уборка неподтверждённых
  аккаунтов не удалит пользователя между поиском и выпуском ссылки).
  Три ветки, в каждой ровно один SMTP-вызов: неизвестный → нейтральное
  письмо; неподтверждённый → новый токен подтверждения ADR-021 и письмо
  подтверждения; подтверждённый → `issue()` и письмо со ссылкой сброса.
- `ResetPasswordAction(secret, passwordHash, now): bool` — хэш считает
  контроллер после проверки лимита, как при регистрации. Успех → письмо
  «пароль изменён».
- `MailPasswordResetEmailSender` на `mailer.sync`; ссылка
  `{SELLER_APP_ORIGIN}/reset-password#token=…`. Уведомление о смене
  отправляется по возможности: пароль уже изменён, и отказ SMTP после
  фиксации не должен превращать успешный сброс в ошибку — `warning`
  в журнал.

**Приёмка этапа 3:**
- [ ] Три ветки запроса шлют ровно по одному письму, правильному каждому
- [ ] Неподтверждённому ссылка сброса не выдаётся
- [ ] Письма идут синхронно, мимо Messenger
- [ ] Письмо сброса содержит токен только во фрагменте URL и срок «1 час»
- [ ] Отказ уведомления не откатывает и не скрывает успешный сброс

## Этап 4. Backend — HTTP, безопасность, границы

- [ ] 4.1 `POST /api/auth/password-reset/request` `{email, captcha}` → всегда `202`.
- [ ] 4.2 `POST /api/auth/password-reset/confirm` `{token, password}` → `204`;
      любой отказ токена → `422 invalid_or_expired`; слабый пароль → `422` валидации.
- [ ] 4.3 Request DTO + Validator, атрибуты Nelmio.
- [ ] 4.4 `security.yaml`: оба маршрута `PUBLIC_ACCESS`.
- [ ] 4.5 `rate_limiter.yaml`: `password_reset_request_ip`,
      `password_reset_request_email`, `password_reset_confirm_ip`; IP — реальный
      клиент за Traefik (как у регистрации). Капча — через `RegistrationProtection`
      или его обобщение без смены поведения регистрации.
- [ ] 4.6 Deptrac: две пары «контроллер ↔ action» вынесены из широких слоёв
      в точные class-level слои; широкий `IdentityUi` их не видит.
- [ ] 4.7 Токен не логируется: тело запроса confirm не попадает в журнал и трекер.
- [ ] 4.8 `make api-doc-export`, `make api-types`.

**Результат этапа:** `make stan`, `make deptrac`, `make lint`, `make api-types-check` зелёные.

**Детальный план этапа 4:**
- `RegistrationProtection` → `PublicFormProtection` (переименование без
  изменения поведения), два экземпляра в `services.yaml`; контроллер
  получает свой по имени аргумента.
- Ответы: request — `202` с тем же телом, что resend; `422`
  (`email_invalid`, `captcha_invalid`), `429`, `503` — как у регистрации.
  Confirm — `200 {"status":"password_changed"}`; `422 reset_token_invalid`
  для неверного формата, неизвестного, истёкшего и использованного токена;
  `422 password_too_short|password_too_long`; `429`.
- Лимит confirm по HMAC(IP) — до хэширования пароля.

**Приёмка этапа 4:**
- [ ] Оба маршрута публичны, остальные правила `access_control` не тронуты
- [ ] Deptrac: широкий `IdentityUi` не видит action'ов и границы сброса
- [ ] Регистрация ведёт себя как прежде (её тесты зелёные без правок, кроме имени класса)
- [ ] OpenAPI и TS-типы сгенерированы из кода

## Критерии готовности

1. Пользователь восстанавливает доступ сам за пару минут.
2. По ответу API нельзя отличить существующий адрес от несуществующего.
3. Ссылка одноразовая, живёт не дольше 60 минут, последняя отменяет предыдущие.
4. После сброса все прежние сессии недействительны, владелец ящика уведомлён.
5. Открытый токен не хранится нигде, кроме письма.
6. Все проверки CI зелёные, ревью `high` пройдено, сценарий проверен на проде.
