# product-research-ozon — этап 4: проверенный месячный снимок

Дата: 01.11.2026. Статус: реализация. Основание — ADR-050 и этап 4 общего плана.

## Результат и границы

Одна категория + один календарный месяц → все страницы MPStats → неизменяемое
сырьё S3, манифест и готовый снимок в собственной БД Python. FBS=1, RUB,
пустой filterModel, revenue DESC/id ASC; данные с нулевыми продажами и остатками
не исключаются. Проверки количества/ID не являются гарантией snapshot isolation
у провайдера. Тела и суммы не записываются в PostgreSQL/журнал.

Этап поставляет движок одной страницы/одного месяца. `step` выполняет не больше
одного внешнего запроса, сохраняет курсор и возвращает управление при ожидании
лимита; нет sleep или открытой SQL-транзакции во время HTTP/S3. Диспетчер,
доставка запусков из Symfony, retry budget и пользовательская загрузка — этап 5;
повторное использование закрытых снимков — этап 6, UI — 7, production Python — 8.
Существующие HTTP runs/snapshots остаются not_available до соответствующих этапов.
Worker/collection readiness выключены. Symfony и публичный контракт не меняются.

Новых зависимостей, брокеров, межмодульных связей и финансовых таблиц нет.
Одна новая Alembic-миграция технических снимков/страниц/временных ключей проверки.
Существующая миграция каталога не переписывается. Production-схема Python пока
не применяется: сервис ещё не развёрнут, активация остаётся в этапе 8.

## Правила

- Company/source передаются явно. UUIDv7 генерируются приложением. Поиск снимка
  всегда по company + source + snapshot. Входной готовый S3-ключ не принимается.
- Месяц начинается с первого числа. Закрытый месяц целиком; будущий запрещён,
  текущий — только явно, со второго числа, до вчера по Europe/Moscow. Даты,
  количество дней и признак неполноты фиксируются до получения первой страницы.
- Страница 500 строк (проверенный stage-0 профиль). Ответ должен подтверждать
  startRow/endRow/total и точную ожидаемую длину. Total неизменен, SKU —
  положительные целые ID без дублей внутри страницы и между страницами.
- Пустой total=0 — полноценный готовый снимок с предупреждением; преждевременный
  пустой ответ, изменение total, неверные ID/границы — ошибка полноты.
- В памяти только текущая страница и ограниченный список метаданных манифеста.
  Межстраничные SKU — техническая DB-проверка с UNIQUE, удаляются при завершении.
  Нет накопления всего товарного отчёта в памяти и хранения денежных фактов в БД.
- Общий provider gate этапа 3 применяется и к items: консервативная общая квота
  серверного подключения, generation fencing, 401/403 pause, Retry-After.
  Ошибки имеют безопасные коды; исходные тексты/тела/токены не логируются.
- Технический бюджет rows/pages/bytes передаётся явно и фиксируется в снимке.
  Числа тестового бюджета не объявляются квотой MPStats или production-лимитом;
  реальные ограничения проверяются до включения на этапе 8.
- Аренда снимка и CAS курсора защищают повтор шага/конкуренцию. S3 записывается
  перед DB-регистрацией; конфликт неизменяемой записи допускается только после
  проверки существующих байтов. Потерявший аренду/поколение не публикует результат.
- Готовность — DB-публикация после полного набора зарегистрированных страниц и
  успешной записи проверенного манифеста. Сбой S3/DB оставляет снимок неготовым.
  Сохранённые страницы и orphan-объекты не удаляются автоматически. GC/retention
  и диспетчер восстановления — будущие этапы; частичное сырьё не считается кэшем.
- Чтение сырья пересобирает ссылки из company-scoped DB-записей, проверяет
  размер/SHA-256. Отображаемое имя категории не участвует в техническом ключе.

## 4.1. Чистые правила и граница ответа — TDD

Цель: доказать календарь, полноту и сохранение исходных байтов.
Задачи: immutable параметры/DTO, бюджет, parser с Decimal и строгими счётчиками,
проверки формата ID/дубликатов/неполной страницы, manifest serialization.
Готовность: U01–U05 проходят; зафиксирован начальный Red до реализации.

## 4.2. Клиент MPStats и общий gate

Цель: ограниченный внешний запрос с точными параметрами и безопасными отказами.
Задачи: fixed HTTPS endpoint, token header, no redirects/proxy env, общий deadline
и предел тела; MockTransport; reuse provider gate без изменения поведения каталога.
Готовность: U06–U08, C01; отказ/лимит не порождает фиктивную страницу/готовность.

## 4.3. Журнал и неизменяемые объекты

Цель: полная прослеживаемость снимка и сохранение при сбое.
Задачи: одна Alembic-миграция, scoped SQL repository, lease/CAS, batch-проверка SKU,
страницы и манифест S3 с checksum, чтение только зарегистрированного готового сырья.
Готовность: I01–I06, M01; реальные PostgreSQL/S3 и конкурентные соединения.

## 4.4. Оркестрация страницы и приёмка месяца

Цель: воспроизводимый полный месяц без удержания worker на паузе.
Задачи: start/step/read, постоянный курсор, одна страница в шаге, атомарное завершение,
безопасная телеметрия, полный эталон из 102 страниц и 41-колоночный профиль.
Готовность: I07–I10, R01–R03; повтор ready не вызывает источник.

## 4.5. Проверки, ревью и доставка

Цель: завершённый проверенный diff и постоянные доказательства приёмки.
Задачи: Ruff/mypy strict/import-linter, весь Python-набор, runtime smoke,
полный изолированный db-rebuild-check, независимые новые CLI-сессии 5A/5B при
недоступном Claude, разбор замечаний, зелёный CI, PR/merge/deploy/smoke.
Готовность: G01–G08. Production включение Python не входит в этап.
