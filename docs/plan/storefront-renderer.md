# Серверный сбор витринной цены Ozon — план задачи

> **Статус: отклонён владельцем 2026-10-16 по итогам спайка (этап 2).**
> Витринная цена по-прежнему снимается расширением (ADR-014); дорабатывается
> оно, а не сервер. Итоги — в разделе «Итог спайка» ниже; этапы 3–19
> не выполнялись и оставлены как запись того, что было задумано.

## Итог спайка

Замеры 2026-10-16, SKU первого клиента, по одному–двум визитам на вариант:
после первого же отказа темп не поднимался.

| Откуда | Чем | Ответ Ozon |
|---|---|---|
| VPS Timeweb, AS9123 (датацентр) | HTTP GET с cookie-jar | JS-проверка, затем капча |
| VPS Timeweb | Playwright: headless-shell, новый headless | `403 Antibot Captcha` на первом визите |
| VPS Timeweb | обычный Chromium без автоматизации, под Xvfb | «Похоже, нет соединения. Выключите VPN» |
| Мобильный прокси Билайн, AS16345, три разных IP | Playwright headful | `403 Antibot Captcha` на первом визите |
| Мобильный прокси, свежий IP | обычный Chromium без автоматизации | `403 Antibot Captcha` |
| Домашний Ростелеком, AS12389 | Playwright: новый headless и headful | `403 Antibot Captcha` на первом визите |
| Тот же домашний Ростелеком | Chrome продавца с расширением | цена снимается |

Отказ приходит на втором шаге редиректа (`?__rr=1`), до любой проверки
в странице. Ozon отсекает и IP хостингов и пулов прокси, и браузер под
управлением программы — даже с домашнего IP.

**Почему не дальше.** Следующие шаги — маскировка автоматизации, решение
капч, ротация пулов прокси — это обход защиты, которой Ozon прямо заявляет
отказ автоматическому доступу: гонка, которую одному разработчику
не выдержать, риск для кабинета продавца и сбой, который выглядит как
рабочие данные. В API Ozon витринной цены нет (`marketing_price` отключён,
`customer_price` убран из `/v2/posting/fbo/list` 2025-11-05); Statistics API
продавцам не выдаётся.

**Что рассматривалось взамен.** Поставщики данных по API (MarketParser,
Priceva, MPSTATS) — законный автономный путь, но платная внешняя
зависимость; MPSpace не подошёл (мониторинг только вместе с репрайсером).
Владелец выбрал доработку расширения.

**Цель:** витринная цена (единственное число, которого не отдаёт API Ozon,
ADR-015) снимается сервером по расписанию — независимо от того, запущен ли
браузер продавца с расширением.

**Основание:** ADR-014, «На что обратить внимание потом»: «понадобилась
работа независимо от того, запущен ли браузер продавца → это серверный
headless-рендер, кратно дороже, и решение отдельное». Этот план и есть
то отдельное решение.

**Две очереди инфраструктуры:**

- **Очередь 1 (MVP)** — одна VPS со своим IP, небольшая нагрузка, без прокси.
- **Очередь 2** — пул прокси и несколько узлов. Всё, что делается в очереди 1,
  закладывается так, чтобы очередь 2 была конфигурацией и добавлением машин,
  а не переписыванием.

**Как читать план.** Этапы идут по порядку, каждый маленький и законченный:
у него есть цель, шаги, результат и признак готовности. Этапы, меняющие код,
уходят отдельными PR, чтобы ревью каждого было коротким.

## Ключевые решения (кратко)

Подробное обоснование — в ADR-039 (этап 3). Здесь — чтобы этапы были понятны.

### Стек: Node.js 24 LTS + TypeScript + Playwright (Chromium)

- **Парсер переиспользуется.** `readDisplayedPrice`
  (`apps/extension/src/ozon/price.ts`) уже читает цену из разметки
  `schema.org`, сверяет артикул и считает минорные единицы без float.
  Он выносится в общий пакет и работает и в расширении, и в сервисе.
- **Playwright** — стандарт управления браузером: изолированные контексты
  в одном браузере, прокси на контекст (нужно очереди 2), перехват запросов
  (отсечь картинки и шрифты). В репозитории он уже есть для e2e.
- **Образ** `mcr.microsoft.com/playwright:v1.X-noble`, версия точная:
  браузер и библиотека совпадают, системные пакеты Chromium не собираются руками.

Отвергнуто:

| Вариант | Причина |
|---|---|
| PHP (Panther, chrome-php) | браузер тот же, обёртки беднее, парсер пришлось бы дублировать |
| Python или Go | второй язык и второй парсер |
| Puppeteer | для нас разницы нет, а Playwright уже в репо |
| Crawlee | абстракция до второго случая; вернуться в очереди 2, если пул прокси разрастётся |
| Платные API скрейпинга | сторонний сервис видит наши SKU; российская витрина у них нестабильна |
| Stealth-плагины | сторонние, плохо поддерживаются; только если спайк покажет, что без них нельзя |

### Модель работы: сервис сам забирает задания (pull)

```
 ┌────────────── прод ─────────────────────────────┐        ┌──── VPS ──────────────┐
 │ worker-scheduler ──► storefront_capture_job     │        │ storefront-renderer   │
 │                                                 │ HTTPS  │                       │
 │ POST /api/renderer/jobs/lease      ◄────────────┼────────┤ 1. взять задания      │
 │ POST /api/renderer/jobs/{id}/result ◄───────────┼────────┤ 2. открыть карточку   │
 │   ├─► price_observation (source = renderer)     │        │ 3. разобрать цену     │
 │   └─► сырьё в S3 (ADR-024)                      │        │ 4. отправить результат│
 └─────────────────────────────────────────────────┘        └──────────┬────────────┘
                                                                       ▼
                                                                    ozon.ru
```

- У сервиса **нет доступа к базе и S3** и он **не знает `companyId`** —
  только идентификатор задания и артикул. Взломанная машина не прочитает
  ни строки данных клиентов.
- Масштабирование — добавлением машин: каждая сама берёт столько работы,
  сколько тянет. Входящих портов на VPS нет, только SSH.
- Конфигурация очередей Messenger не меняется.

### 1. ADR

**Ответ:** ADR-039 «Серверный сбор витринной цены», статус Accepted после
этапа 2 — в нём должны стоять цифры спайка. Уточняет ADR-014 (кто снимает
цену) и ADR-015 (состав наблюдения).

**Почему:** решение меняет изоляцию (§1), схему факт-таблицы и добавляет
инфраструктурный компонент — это три признака необратимого решения
по «Правилу отнесения». Принятый ADR-014 не редактируется, поэтому новый.

### 2. Где и на чём сервис

**Ответ:** `services/storefront-renderer` — новая папка верхнего уровня
рядом с `api/`, `apps/`, `packages/`. Node.js 24 LTS — той же версии, что
`docker/` уже использует (`node:24.18.1-bookworm-slim`). TypeScript в том
же `strict`, что у фронтенда.

**Почему:** `apps/` — то, что видит человек (интерфейсы, расширение).
Сервис без интерфейса туда не относится, а смешение запутает правила §10,
написанные про контур продавца. Одна версия Node на репозиторий — одна
поверхность для обновлений безопасности.

**Альтернатива:** `apps/storefront-renderer` — меньше папок верхнего уровня,
но правило «что лежит в apps» становится неочевидным.

### 3. Зависимость

**Ответ:** `playwright` (не `@playwright/test`) — точной версией, совпадающей
с `@playwright/test` в корне; базовый образ `mcr.microsoft.com/playwright`
той же версии. Обновление — одним изменением на весь репозиторий.

**Почему:** у Playwright браузер привязан к версии библиотеки; расхождение
библиотеки и образа даёт «Executable doesn't exist» на запуске. Попутно:
в корне сейчас `^1.62.1` — это расходится с правилом «версии зафиксированы»;
исправление — отдельной задачей, не в этом объёме.

### 4. Модель работы

**Ответ:** pull. Узел раз в несколько секунд спрашивает задания
(`lease`), исполняет, сдаёт (`result`). Аренда — 5 минут, пачка — до
`CONCURRENCY × 2` заданий. Узел ходит в API напрямую, не через прокси.

**Почему:** это стандартный приём для воркеров на чужих машинах
(так работают раннеры CI): исходящие соединения, никаких входящих портов,
масштабирование добавлением узлов, умерший узел возвращает задания сам
по истечении аренды. Доступ к базе с внешней машины — самое дорогое,
что можно отдать, и здесь он не нужен.

### 5. Учётные данные узла

**Ответ:**
- токен — 32 случайных байта (`random_bytes`), выдаётся один раз
  консольной командой, в базе — SHA-256 хэш;
- **без автоматического истечения**, ротация вручную раз в квартал
  (выпустить новый → заменить на узле → отозвать старый);
- отзыв — `renderer:node:revoke`, действует на следующем запросе;
- **allow-list IP узлов** на Traefik для `/api/renderer/**` — вторая линия:
  утёкший токен с чужого адреса не работает;
- rate limit на контур в Redis.

**Почему:** у машинного токена нет человека, который заметит истечение
и переподключит — автоистечение превращается в молчаливую остановку сбора,
которую CLAUDE.md запрещает. Ротация с перекрытием — практика для машинных
секретов. mTLS — сильнее, но это свой УЦ и выпуск сертификатов: на одном узле
не окупается. Allow-list работает и в очереди 2: прокси нужны только для
запросов к Ozon, к API узел ходит со своего IP.

### 6. Межарендаторная выдача

**Ответ:** да, четвёртым случаем в §1 — «выдача операционных заданий
машинному узлу». Условия все разом:

1. имя запроса показывает межарендаторность (`LeaseStorefrontCaptureJobsQuery`),
   докблок ссылается на §1;
2. запрос и контроллер — в двух узких class-level слоях Deptrac, грант
   только этой паре;
3. ответ не содержит `companyId` и ничего кроме `jobId`, артикула и региона;
4. результат принимается только по заданию, которое арендовал этот же узел;
5. `company_id` при записи берётся из строки задания, не из тела.

**Почему:** по смыслу это операционная задача, как планировщик, — только
исполняется на другой машине. Условия 3–5 делают так, что узел не узнаёт
ничего сверх публичного номера карточки и не может записать ничего в компанию,
которую сам выбрал.

### 7. `price_observation`

**Ответ:**
- `captured_by_user_id` → nullable;
- новая `captured_by_node_id` nullable, ссылка на `renderer_node` с индексом
  (§6) — какой узел снял, нужно для разбора блокировок;
- CHECK: ровно одно из `captured_by_user_id` / `captured_by_node_id` не NULL;
- новая `client_version`, запись в неё и в `extension_version` на время
  перехода; удаление `extension_version` — отдельной задачей, вторым шагом;
- новая `region` nullable — у старых строк региона нет, и угадывать его
  задним числом нельзя;
- `source`: значение `renderer` рядом с `extension`.

Все изменения — добавление колонок и снятие `NOT NULL`, без блокирующих
перезаписей таблицы.

**Почему:** правило совместимых изменений на факт-таблицах. CHECK вместо
договорённости — строка без автора неотличима от строки, записанной ошибкой.

### 8. Новые таблицы

**Ответ:** `renderer_node` и `storefront_capture_job` по составу из этапа 5.
Без партиционирования: задание — одна строка на отслеживаемый артикул,
размер ограничен потолком в 50 на компанию и не растёт со временем.

**Почему:** задание — не история, а текущее состояние; история — в
`price_observation`. Отдельная таблица заданий вместо Messenger — потому что
узел не ходит в базу, а аренда с `SKIP LOCKED` — стандартная очередь
на Postgres.

### 9. Частота

**Решение владельца (2026-10-16): раз в 30 минут**, круглосуточно, без деления
по компаниям — как у расширения. Предлагалось 60 минут; ниже — исходное
обоснование, оставлено для истории.

**Предлагалось:** раз в 60 минут, круглосуточно, без деления по компаниям.
Окончательное значение — по замерам этапа 2: если безопасный темп с одного IP
ниже, чем нужно для 60 минут, — увеличить интервал, а не рисковать IP.

**Почему:** СПП меняется по акциям и решениям Ozon, обычно не чаще
нескольких раз в день; 30 минут расширения были выбраны под цикл браузера,
а не под скорость изменения цены. Ночь не пропускается: акции Ozon часто
стартуют в полночь. Настройка на компанию — когда об этом попросит клиент.

### 10. Регион

**Ответ:** Москва для всех компаний; регион задаётся cookie, IP узла тоже
московский. В наблюдении хранится код региона.

**Почему:** продавец сверяет цену глазами в своём браузере, а большинство
продавцов и самая большая доля заказов — Москва. Хранить регион с первого
дня — дёшево; без него смена региона позже смешает два ряда в один.

### 11. Расширение

**Ответ:** неделя параллельной работы → сверка → выключение фонового обхода
новой версией расширения. Остаются: кнопка «Отслеживать цену», первый снимок
из открытой вкладки, оверлей.

**Почему:** сверка на реальных данных — единственный способ узнать,
что сервис снимает то же число. После неё фоновый обход — второй источник
тех же данных с худшей полнотой и окнами на компьютере продавца.

### 12. Сырьё

**Ответ:**
- **успех:** JSON-LD товара (несколько КБ) — raw-документ через
  `RawDocumentStorage` (ADR-024), хранится как остальное сырьё;
- **отказ:** полный HTML (gzip, до 2 МБ) — отдельный префикс
  `storefront-failures/{companyId}/…`, удаляется через 14 дней правилом
  жизненного цикла бакета, не кодом.

**Почему:** JSON-LD — то, из чего получено число, его достаточно для
перепроверки (прослеживаемость ADR-006). Полная страница нужна только
для разбора поломки, и через две недели её ценность нулевая. Удаление
правилом бакета не нарушает запрет на удаление объектов командами (§1),
но **это стоит явно записать в ADR-039**, иначе выглядит как обход.

### 13. Ошибки сервиса

**Ответ:** без `@sentry/node`. Отказ разбора уходит в API как результат
задания и пишется в журнал бэкенда `warning` с `company_id`; падение процесса
перезапускает Docker, а пропавший узел ловит сторож пульса. Журнал контейнера —
`json-file` с ротацией (`max-size: 10m`, `max-file: 5`).

**Почему:** ожидаемые отказы (капча, нет разметки) — не ошибки, и в трекере
они утопили бы настоящие (тот же принцип, что в «Наблюдаемости»). Неожиданное
падение без сторожа пульса трекер тоже не поймал бы — процесс мёртв и не
отправит ничего. GlitchTip подключается, если появятся ошибки, которые
не видны ни в результате задания, ни в пульсе.

### 14. Машина

**Ответ:** Timeweb Cloud, Москва, 2 vCPU / 4 GB RAM / 30 GB NVMe,
Ubuntu 24.04, статический IP.

**Почему:** провайдер уже есть (S3), отдельного договора и оплаты не нужно.

**Результат:** колонка «Владелец» заполнена.

## Этап 8. API выдачи и результата

**Цель:** узел забирает задания и сдаёт результат.

### 8.1 Выдача

`POST /api/renderer/jobs/lease` → `{ jobs: [{ jobId, sku, region, leaseUntil }] }`

1. `LeaseStorefrontCaptureJobsQuery`:
   ```sql
   UPDATE storefront_capture_job SET leased_by_node_id = :node,
          lease_until = now() + interval '5 minutes'
    WHERE id IN (SELECT id FROM storefront_capture_job
                  WHERE due_at <= now()
                    AND (lease_until IS NULL OR lease_until < now())
                  ORDER BY due_at
                  LIMIT :n
                  FOR UPDATE SKIP LOCKED)
   RETURNING id, marketplace_sku, region, lease_until
   ```
2. `n` — от узла, максимум 10.
3. Выдача обновляет `renderer_node.last_seen_at` — это пульс узла.
4. В ответе нет `companyId`.

### 8.2 Результат

`POST /api/renderer/jobs/{id}/result`

Тело — успех:
```json
{ "outcome": "captured", "observedAt": "2026-10-20T10:15:00.000Z",
  "displayedPrice": { "amount": 111700, "currency": "RUB" },
  "productMarkup": { "...": "JSON-LD товара" }, "clientVersion": "1.0.0" }
```
Тело — отказ:
```json
{ "outcome": "failed", "reason": "captcha", "observedAt": "...",
  "html": "<gzip base64, до 2 МБ>", "clientVersion": "1.0.0" }
```

Сервер:

1. Ищет задание по `id` **и** `leased_by_node_id` = текущий узел.
   Не нашёл — 404 (чужая или просроченная аренда).
2. `company_id` и кабинет — из найденной строки.
3. Успех — запись через `RecordPriceObservationAction` с
   `source = renderer`. Повтор результата даёт тот же `observedAt`
   и упирается в естественный ключ наблюдения (ADR-014).
4. Сырьё — через `RawDocumentStorage(companyId, …)` (ADR-024).
5. Аренда снимается; `due_at` — следующий цикл (успех) или выдержка
   5 → 15 → 45 минут (отказ), дальше следующий цикл.
6. Отказ — запись в журнал `warning` с причиной и `company_id`.

### 8.3 Тесты

- результат по чужой аренде — 404, наблюдение не записано;
- результат компании A никогда не пишет в B;
- два узла параллельно получают разные задания;
- повтор результата не создаёт второго наблюдения;
- разбор тела: float в цене, неизвестная причина, пустая валюта — 422.

**Результат:** PR, после которого задание проходит полный цикл через curl.
**Готово, когда:** тесты зелёные; `make api-types-check` зелёный.

## Очередь 2. Прокси и масштабирование

Начинается по сигналу: устойчивая доля капчи на одном IP или рост числа
компаний сверх возможностей одного IP.

**Ограничитель — IP, а не процессор.** Узел 4 vCPU / 8 GB держит 6–8
параллельных контекстов (1,5–2 карточки в секунду), но с одного IP
столько Ozon не пропустит.

Оценка: 100 компаний × 50 SKU × раз в час ≈ 5 000 карточек в час
≈ 1,4 в секунду — один узел среднего размера плюс пул прокси.

### Этап 16. Прокси в сервисе

1. `PROXIES` в конфиге: список резидентных или мобильных прокси РФ
   с «липкими» сессиями.
2. Контекст Playwright привязан к прокси; куки — на пару «узел + прокси».
3. Темп и предохранитель — на прокси, а не на узел.
4. Учёт здоровья прокси: капча или ошибка соединения подряд → прокси
   выводится из оборота на время.
5. `CONCURRENCY` = число здоровых прокси, не больше потолка по памяти.

Протокол с API не меняется.

### Этап 17. Справедливость выдачи

1. В выдаче не больше K заданий одной компании за раз — компания
   с 50 артикулами не задерживает остальных.
2. Тест: две компании, у одной в десять раз больше заданий — обе
   продвигаются.

### Этап 18. Дедупликация по SKU (по необходимости)

Одна карточка за цикл на SKU, результат — каждой компании, отслеживающей
этот SKU. Цена публичная, утечки нет, но ключ задания перестаёт быть
company-scoped — **отдельное решение и ADR**, не делается попутно.

### Этап 19. Второй и следующие узлы

1. Новая VPS по этапу 1, новый токен по этапу 13.
2. Никаких изменений бэкенда: узлы конкурируют за задания через `SKIP LOCKED`.

## Чего этот план не делает

- не снимает цену «с картой Ozon» — её нет в разметке (ADR-015);
- не убирает расширение: оверлей и кнопка отслеживания остаются;
- не меняет расчёт СПП и экран, кроме подписи источника.

## Риски

| Риск | Что делаем |
|---|---|
| Правила Ozon запрещают автоматический сбор | снимаем только отслеживаемые продавцом карточки, темпом живого посетителя; принимаем риск блокировки IP — ради этого очередь 2 |
| Блокировка IP VPS | предохранитель, тревога по доле капчи, очередь 2 |
| Цена зависит от региона | регион фиксирован и хранится в наблюдении |
| Ozon уберёт разметку `schema.org` | ломаются и расширение, и сервис; сторож свежести скажет; парсер чинится в одном месте |
| Узел скомпрометирован | нет доступа к базе и S3, нет `companyId`; результат только по своей аренде; токен отзывается командой |
