# Рефакторинг представления статусов и экрана плана продаж

## Цель и границы

Выполнить пункты 1 и 3 согласованного предложения: отделить подготовку
статуса нетто-прогноза от JSX и разнести существующие части SalesPlanPage
по обязанностям. Пользователь поручил автономное выполнение до выкладки.

Поведение, тексты, порядок пояснений, расчёты, URL, HTTP-запросы,
company-scoped кэш и lifecycle форм сохраняются. Зависимости, API,
backend, миграции, общие UI-примитивы и правила ревью не меняются.

## План реализации

1. **Чистое представление статуса.** В
   `apps/seller/src/features/sales-planning/lib/netForecastStatusPresentation.ts`
   создать `buildNetForecastStatusPresentation(cohort)`.
   Вход — существующий сгенерированный PerformanceCohortResponse или null/undefined;
   выход — readonly модель с коротким статусом, тоном и упорядоченными сообщениями.
   Перенести существующий выбор причин и удаление дублей без изменения правил.
   Проверку отображаемости количества/денег выполнять прежними форматтерами;
   ноль остаётся доступным значением, некорректная сумма — недоступной.
   PerformanceNetForecast только выводит подготовленную модель через PerformanceStatus.

2. **Состав экрана.** Перенести уже существующие компоненты в соседние файлы `ui/`:
   SalesPlanHeader, SalesPlanGrid, SalesPlanSkuForm, SalesPlanDayForm,
   SalesPlanRemoveSkuButton. Общие локальные типы выбранного дня —
   `ui/salesPlanEditorTypes.ts`; типы ответов API по-прежнему из generated schema.
   SalesPlanPage оставляет маршрутизацию, подписки, переключение режимов,
   пагинацию и композицию. Тела обработчиков и React keys сохраняются.
   Это перенос существующих обязанностей, без нового универсального слоя форм.

3. **Проверка и выпуск.** Обновить docs/structure.md, пройти seller-проверки
   и существующий E2E, собрать весь diff задачи в независимое ревью,
   разобрать замечания, дождаться зелёного CI, выполнить PR/merge/deploy
   и проверить фактический production-релиз. Результаты и ответы ревью — в PR.

## Чек-лист готовности

- Чистая функция не импортирует React/UI и не выполняет запросов или денежных расчётов.
- Проверены missing cohort, независимая недоступность количества/выручки,
  доступные нули, некорректные деньги, неизвестные причины/области обучения,
  общие и разные причины; порядок и удаление дублей прежние.
- JSX статуса отвечает только за отображение; кнопка ⓘ и её доступность сохранены.
- Шапка, таблица и формы вынесены в файлы по обязанностям;
  SalesPlanPage больше не содержит их реализаций.
- Версия выбранного дня остаётся снимком момента открытия; конфликт409
  не заменяет её свежей версией и не разрешает повторную запись.
- Сохранены локальные поля/keys при переключении edit/compare,
  сброс при смене компании/плана, readonly закрытых планов и календарь при ошибке перечитывания.
- `make front-typecheck front-lint front-knip front-test front-build APP=seller` — PASS.
- `make test-e2e` — PASS; проверены формы SKU/дня, конфликт, lifecycle,
  смена компании, оба режима, закрепление колонки и раскрытие статусов.
- Итоговый diff покрыт законченным независимым ревью по действующему исключению
  владельца docs/plan/sales-planning-review-rule.md; принятые замечания устранены.
- Обязательный CI итогового HEAD зелёный; production-версия и UI проверены,
  результаты зафиксированы в PR. Production UI с перехваченным синтетическим API
  явно отличён от проверки реальных данных компании.
