# Матрица спроса Ozon (SKU × кластер покупателя) — план

**Цель:** показать продавцу, **где покупают** каждый товар: заказы за 7/14/28
дней, среднедневной спрос, долю кластера в спросе SKU и тренд (7 дней
против 28). Матрица — фактическая картина спроса; что и куда везти,
отвечает соседний отчёт «Остатки» (`ozon-stock-placement-report.md`).

**Главное правило:** спрос считается по **кластеру покупателя**
(`sales_fact.cluster_to`), а не по складу отгрузки (`cluster_from`).
Иначе прогноз сам себя подтверждает: где товара нет, туда не отгружают,
и там «нет продаж».

**Вне объёма:** поправка спроса на дефицит в самой матрице (её делает
«Остатки»), прогноз и сезонность, WB, передача спроса в SalesPlanning
(новый метод Facade — отдельная задача со своим согласованием).

## Что известно заранее

- `sales_fact` уже хранит `cluster_from` и `cluster_to` из
  `financial_data` Ozon; названия кластеров совпадают с `cluster_name`
  снимков остатков (разведка «Остатков», 25 из 25).
- `business_date` — дата заказа по Москве; индекс
  `(company_id, business_date)` есть — миграция не нужна.
- Спрос по `cluster_to` уже считает CTE `demand_sales`
  в `StockPlacementSql` — единственное существующее определение спроса.
- Нулевой остаток выражается отсутствием строки в полном снимке (ADR-034);
  дни нулевого остатка «Остатки» уже считают (`requested_count`
  − `positive_count`).

## Решения (приняты владельцем 2026-10-23)

1. **Регион — только `cluster_to`.** `cluster_from` в отчёте не
   участвует ни в расчёте, ни в колонках.
2. **Без отменённых** (`status <> 'cancelled'`) — так же, как «Остатки»:
   оба экрана показывают одно и то же число спроса. У Ozon FBO невыкуп
   тоже `cancelled`, поэтому спрос ближе к выкупленным заказам — это
   написано в определениях ответа.
3. **Дефицит — пометкой, без пересчёта.** Ячейка SKU × кластер получает
   число дней нулевого остатка за 28-дневное окно и признак «спрос занижен
   дефицитом» (дней > 0). Спрос в ячейке остаётся фактическим.
4. **Одно определение спроса на два экрана.** Общий CTE выносится
   в `DemandSql`; им пользуются и матрица, и «Остатки». Ответ «Остатков»
   при выносе не меняется ни в одной цифре.

## Определения

- **Окна** — 7, 14, 28 полных дней, заканчивая вчерашним
  (`business_date` по Москве). Сегодняшний день не входит.
- **Заказы окна** — `SUM(quantity)` без отменённых, штуки.
- **Среднедневной спрос** — заказы 28 дней ÷ 28, в тысячных штуки
  (`demand_milli_per_day`, как в «Остатках»).
- **Доля кластера** — заказы кластера ÷ заказы SKU по всем **известным**
  кластерам за 28 дней, в базисных пунктах (`share_bps`). Строки без
  `cluster_to` — отдельная колонка «кластер не указан», в знаменатель
  доли не входят.
- **Тренд** — `(q7 / 7) ÷ (q28 / 28)` в базисных пунктах, 10000 = без
  изменений. Считается для SKU целиком и для ячейки; при `q28 < MIN_SALES`
  (10) — `null` с причиной `insufficient_sales`.
- **Неполные данные** — если загрузка продаж за вчера по какому-либо
  подключению Ozon компании не завершена (отметка дня, ADR-038), ответ
  несёт `incompleteThrough` и экран предупреждает: недогруз не должен
  выглядеть падением тренда.
- Все деления — PostgreSQL на `numeric`, округление явное
  (половина от нуля); float нет ни в SQL, ни в PHP.

## Контракт API

`GET /api/companies/{companyId}/demand-matrix?cursor=&limit=&search=`

- `clusters[]` — кластеры со спросом компании за 28 дней, по убыванию
  спроса, + `null` («не указан»), если такие строки есть. Отдаётся на
  каждой странице одинаковым: колонки не скачут между страницами.
- `items[]` — строка на SKU (сортировка: заказы 28 дней ↓, затем SKU):
  `marketplaceSku`, `orders7/14/28`, `demandMilliPerDay`, `trendBps`,
  `cells[]` — `{cluster, orders7, orders14, orders28, demandMilliPerDay,
  shareBps, trendBps, stockoutDays, demandCensored}`; ячейка отдаётся,
  если в ней были заказы или дни нулевого остатка (пустая ячейка, где
  товара не было, — «спрос неизвестен», а не «спроса нет»).
- `nextCursor` — keyset по `(orders28, marketplaceSku)`; лимит 50 по
  умолчанию, максимум 200, превышение — 422. `COUNT(*)` нет.
- `definitions` — окна, `MIN_SALES`, исключённые статусы, база региона
  (`buyer_cluster`), округление — из констант `DemandSql`.

## Этапы

Каждый этап — отдельный коммит в одной ветке `task/ozon-demand-matrix`,
перед этапом — короткий план исполнения, затем без пауз.

### Этап 1. Общий CTE спроса `DemandSql` (рефакторинг)

**Что:** `api/src/Ingestion/Infrastructure/Query/Demand/DemandSql.php`
с CTE `demand_sales` (параметры `:companyId`, `:demandFrom`, `:windowEnd`)
и константами (`EXCLUDED_STATUSES`, `REGION_BASIS = 'buyer_cluster'`).
`StockPlacementSql` берёт CTE оттуда.

**Результат:** одно определение спроса в коде; поведение «Остатков» прежнее.

**Готово, когда:**
- [ ] в `StockPlacementSql` нет собственного запроса к `sales_fact` для спроса;
- [ ] существующие тесты «Остатков» зелёные без правки ожиданий;
- [ ] `make stan`, `make deptrac`, `make lint` зелёные.

**Проверка:** `make test-int` по `StockPlacement*`; диф ответа «Остатков»
на dev-данных до/после — пустой.

### Этап 2. Запрос матрицы

**Что:** `Query/DemandMatrix/` — `DemandMatrixSql` (окна 7/14/28, доли,
тренд, дни нулевого остатка по полным снимкам — переиспользуя логику
`complete_days`/`positive_count` «Остатков»), `DemandMatrixQuery`
(отдаёт `QueryBuilder`), `DemandMatrixClustersQuery`, `DemandMatrixRow`,
`DemandMatrixSkuCursor`. Все методы — `companyId` первым параметром.

**Результат:** SQL возвращает строки SKU × кластер с метриками; запрос
в цикле нет — ячейки страницы одним запросом по списку SKU.

**Готово, когда (интеграционные тесты, данные — Builder-ами):**
- [ ] заказ со склада кластера A покупателю в кластер B считается в B;
- [ ] отменённые не считаются;
- [ ] сегодняшний заказ не входит ни в одно окно, заказ 28 дней назад — входит в 28, не в 14;
- [ ] строки без `cluster_to` — в колонке «не указан», доля считается без них;
- [ ] тренд `null` при `q28 < 10`, корректен на пороге;
- [ ] дни нулевого остатка: ноль по полному снимку → пометка; неполный снимок нулём не считается;
- [ ] keyset: две страницы без пропусков и повторов;
- [ ] данные второй компании в выдачу не попадают;
- [ ] план запроса на dev-данных идёт по `idx_sales_fact_company_business_date`.

**Проверка:** `make test-int`, `EXPLAIN` в отчёт этапа.

## Проверка задачи целиком

- Сумма заказов 28 дней по ячейкам SKU = заказы SKU (с колонкой «не указан»).
- Спрос ячейки × 28 в матрице = спрос той же пары в «Остатках» до поправки
  на дефицит — общий `DemandSql` это гарантирует, тест закрепляет.
- Сумма `share_bps` по известным кластерам SKU = 10000 ± округление.
