# MPStats MCP: проверка подключения и данных

Дата: 31.10.2026. Выполнено по прямому поручению владельца с предоставленным
тестовым токеном. Секрет не включён в документ, Git, argv процесса или файлы
выгрузки; передан процессу через stdin с отключённым echo и использован в памяти.

## Результат

Подключение к `https://mcp.mpstats.io/mcp` работает. Сервер сообщил имя
`mpstats-mcp`, версию 3.3.1 и протокол 2025-03-26.
`tools=categories` включает группировку инструментов, а не ограничение только
справочником товарных категорий. Доступны поиск Ozon и отчёт товаров.

Поиск `хидж` вернул точный путь:

```text
Аксессуары/Женские аксессуары/Платки и шарфы женские/Хиджабы и тюрбаны женские
```

Получение: `ozon_category`, report=products, d1=2026-01-01,
d2=2026-01-31, fbs=1, limit=500, start_row по next_start_row ответа.
Это MCP-обёртка провайдера, а не прямой REST; соответствие необработанному
REST-ответу и ручному CSV пока не установлено.

## Воспроизводимый дефект пагинации

На страницах start_row=2500 и start_row=3000 имеется один общий ID.
У этой строки revenue=1473. Повтор обеих страниц дал те же множества ID
и тот же дубль. На нулевой выручке пересечения намного больше: например,
страница start_row=11000 содержит 500 ID, уже встречавшихся ранее.
Размеры страниц и offsets согласованы, total в сохранённых страницах одинаков.

Гипотеза: сортировка по выручке без устойчивого вторичного ключа не задаёт
полный порядок при одинаковой выручке. Это гипотеза, не установленная причина:
нужно проверить поведение REST и/или получить разъяснение MPStats. Поля sort
в опубликованной MCP-схеме ozon_category нет. Повтор пары подтверждает дефект,
но не является повторной полной выгрузкой месяца по будущему алгоритму MVP.

Убирать дубли и объявлять результат готовым запрещено: возможны пропущенные
товары. Фильтр sales>0 тоже не исправляет исходный контракт и нарушает ТЗ.
Страницы сохраняются как материал для регрессионной проверки отказа на дублях,
а не как успешный эталон полного месяца.

## Квоты и поля

account_limits сообщил available_ozon_external=10000; use_ozon_external
изменился с 0 до 1. Это показание сервера, а не доказательство, что десятки
вызовов стоили ровно один запрос: возможны кэш/задержка счётчика. Rate-limit
в минуту этим ответом не подтверждён.

В данных присутствуют id, sales, revenue и дополнительные поля относительно
ожидаемых 41 колонок CSV. Точная карта A–AO остаётся незаполненной: CSV не получен.
Поддержка type=csv в схеме этого MCP-инструмента отсутствует. Не переносить
параметры прямого REST в MCP без подтверждения.

## Артефакты

Каталог: `var/product-research-ozon-stage0/live/` (игнорируется Git).

- `1-response.txt`: initialize; `3-response.txt`: список инструментов.
- `4-response.txt`: схемы внешней аналитики Ozon.
- `6-response.txt`: начальные лимиты; `7-response.txt`: поиск категории.
- `8-response.txt`: первая страница; `products-*.sse`: следующие страницы.
- `month-check.json`: параметры, счётчики, имена страниц и SHA-256 каждого файла.
- `repeat-2500.sse`, `repeat-3000.sse`, `repeat-check.json`: воспроизведение дубля.
- `limits-after.sse`: конечные показания квот.
- `parsed-8.json`: производная копия первой страницы для осмотра, не raw.

Исходные SSE-ответы сохранены побайтово. До записи проверялось отсутствие
токена в ответе. Сырьё не включено в Git; перед оформлением постоянных тестовых
фикстур требуется проверка допустимости данных по CLAUDE.md. Этот каталог
локальный и не является долговременным архивом.

## Влияние на этап 0

Блокер «нет никакого токена» снят для данной проверки MCP. Не доказаны доступ
к прямому REST тем же токеном, равенство схем MCP/REST, денежные единицы,
соответствие CSV, timezone и гарантии стабильности среза.

Следующий технический шаг: проверить прямой REST-контракт со стабильным
вторичным ключом ID, если он поддерживается; либо получить поддерживаемый
MPStats способ выгрузки полного снимка. MCP в текущем проверенном режиме
нельзя принять как надёжный загрузчик сырья для MVP.

Рабочий код приложения не менялся. Независимое ревью этой записи наблюдений
не требуется (только Markdown, без принятия ADR). Этап 0 остаётся открытым;
это дополнение не меняет предыдущий результат обязательного ревью ADR.
