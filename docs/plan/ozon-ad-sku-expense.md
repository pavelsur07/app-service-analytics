# Реклама Ozon по SKU в юнит-экономике — план

**Статус:** выполнен и выложен 2026-09-28 (PR #197 — пакет 1, PR #198 —
пакеты 2–3). План приведён к реализации: расхождения с первой редакцией,
возникшие по ходу ревью, отмечены в тексте.

**Цель:** у каждого SKU в юнит-экономике — расход на рекламу из данных
площадки по этому SKU; `by-day` — отдельная сверка. Решения — ADR-035.

**Вне объёма:** «Оплата за заказ» по SKU (форма отчёта неизвестна,
ADR-035 п. 7); ДРР, показы, клики на экране; реклама по модели;
Wildberries; сверка в журнал/оповещение — только признак на экране.

## Согласовано владельцем 2026-09-28

1. ADR-035: данные Performance входят в расчёт (заменяет ADR-026 п. 3),
   отбор кампаний по факту расхода (заменяет правило ADR-026 п. 4),
   `by-day` — сверка.
2. Новая факт-таблица `ad_sku_expense_fact` и её ключ.
3. Изменение контракта `GET …/unit-economics`, используемого фронтендом.
4. Денежные величины — только `Money` (ADR-004): разбор, суммы,
   остаток, сверка.

Новых внешних зависимостей, межмодульных связей и изменений очереди нет:
всё внутри Ingestion, сообщения и транспорты прежние.

## Пакет 1 — факты рекламы по SKU (backend, Ingestion)

**Домен**
- `OzonAdSkuExpense` (readonly): `campaignId`, `businessDate`,
  `marketplaceSku`, `Money $amount` (отрицательная; знак меняется через
  `Money::minus`).
- `OzonAdSkuReportParser` — один класс на обе формы (в первой редакции —
  два): `parseReport()` для асинхронного отчёта
  `{campaign_id: {report: {rows}}}` (дата `d.m.Y`, сумма с запятой,
  пропущенное поле = 0) и `parseDay()` для `products/sku` (`campaignId`
  в строке, дата ISO, сумма с точкой). Строки отдаются генератором;
  список вместо объекта, повтор тройки «кампания × день × SKU» —
  ошибка разбора.
- `OzonPerformanceMoney` — сумма Performance в `Money`: строгий шаблон
  на разделитель, не больше 13 знаков целой части (без перехода во
  float), валюта RUB — константа коннектора.
- `OzonAdExpenseParser` — `statistics/expense`: кампании с
  `moneySpent > 0` в периоде (для отбора кампаний, п. 4 ADR-035).
- Entity `AdSkuExpenseFact` (`class`, не `final`) + Builder тестов.

**Схема — одна миграция** (`Version20260928104349`)
- `ad_sku_expense_fact`, PK `(company_id, marketplace_account_id,
  source_row_id)`, `source_row_id = campaign_id|business_date|sku`;
  `amount_minor` — тип `money_minor_amount`, `currency char(3)`;
  `source_received_at`, `raw_document_id`, `row_hash`,
  `first_loaded_at`, `last_updated_at`.
- Индексы `(company_id, business_date)`, `(raw_document_id)`.
- `down()` — `DROP TABLE`.

**Запись** — `DoctrineAdSkuExpenseFactWriter`: `INSERT … ON CONFLICT …
DO UPDATE … WHERE текущая.source_received_at <= EXCLUDED.source_received_at`.
Более новый ответ с той же суммой продвигает отметку получения и ссылку
на raw; `last_updated_at` меняется только вместе с суммой.

**Разбор** — `Application/StoreOzonAdSkuExpenses`: пишет порциями по 500
по ходу разбора, весь документ — в одной транзакции (ошибка на поздней
строке откатывает уже записанное).

**Обработчики**
- `CheckOzonAdSkuReportHandler`: после сохранения `ozon_ad_sku_report`
  — разбор и запись; ошибка разбора — `UnrecoverableMessageHandlingException`
  (в трекер, без повторов). У отчёта заказов (`CpoOrders`) разбора нет.
- `FetchOzonAdCampaignStatsHandler`:
  - отбор кампаний для `orderSkuReports` и `products/sku` —
    тип `SKU` (архивные включительно) ∩ расход > 0 в загруженном
    `expense` за нужный период; кампании с расходом, отсутствующие
    в списке, — тоже;
  - после сохранения каждого `ozon_ad_sku_day` — разбор и запись;
  - неудача разбора (`products/sku` или `expense` для отбора) не обрывает
    остальные выгрузки куска: они доделываются, затем
    `UnrecoverableMessageHandlingException` с первой неудачей. Заказ
    отчёта «Оплаты за заказ» от отбора не зависит.

**Тесты**
- unit: парсеры на фикстурах — `statistics-json-many-2026-08-25.json`
  (725 строк, итог 158 960,62 ₽), `statistics-products-sku-2026-09-23.json`
  (21 строка, 4 654,82 ₽), совпадение двух форм за 23.09; отказ на чужом
  разделителе, трёх знаках после запятой, 14+ знаках целой части,
  объекте вместо списка; пропущенное поле — ноль;
- integration (в первой редакции отбор кампаний был в unit): отбор —
  архивная с расходом выбрана, «Оплата за заказ» нет, кампания с расходом
  вне списка выбрана; повтор документа не меняет результат; старый
  документ, записанный после нового, не перезаписывает; ошибка после
  первой порции не оставляет фактов; две компании — факты одной
  не видны в чтениях другой.

## Пакет 2 — сверка и юнит-экономика (backend)

- `AdvertisingReconciliationQuery(companyId, from, to)` (в первой
  редакции — `AdSkuReconciliationQuery`) — по паре «подключение ×
  кампания × день»: сумма и число строк 41 из `marketplace_expense_fact`
  (`unit_number = campaign_id`), сумма `ad_sku_expense_fact` и число её
  ненулевых строк. Только подключения, у которых в raw есть
  `ozon_ad_expense`. SQL только агрегирует; разница и допуск — в PHP
  через `Money::minus`.
- Исходы сверки в `BuildUnitEconomicsAction`: «начисления нет» при
  ненулевой разбивке — день несошедшийся, без допуска; иначе расхождение
  больше копейки на ненулевую строку SKU. Сегодняшний день (Москва)
  не сверяется: `by-day` отдаёт его только завтра.
- `UnitEconomicsQuery::skus` — третья сторона объединения: реклама
  по SKU за период входит в `FULL OUTER JOIN` (SKU с рекламой без
  продаж попадает в список) и в `margin_minor` для сортировки.
- `UnitEconomicsQuery::cabinetExpenses` — без 41;
  `UnitEconomicsQuery::advertisingTotals` — итог 41 и итог рекламы по SKU
  за период.
- `BuildUnitEconomicsAction`: у SKU `advertisingMinor`, входит
  в `deductions` через `Money::plus`; остаток `by-day(41) minus реклама
  по SKU` — строкой `cabinetExpenses` с `feeTypeId` 41 при ненулевом:
  «Реклама, не разнесённая по товарам», если реклама по SKU за период
  есть, иначе прежняя «Оплата за клик» целиком (ADR-035 п. 6).
- Сортировка `advertising` (`UnitEconomicsSort::Advertising`).
- Ответ API: `advertisingMinor` у SKU, `advertisingUnreconciledDays`
  в отчёте. Отдельного поля остатка нет (в первой редакции —
  `advertisingUnallocatedMinor`): остаток приходит строкой кабинета.

**Тесты (обязательное покрытие)**
- денежная арифметика: инвариант «реклама по SKU + остаток = итог 41»;
  знак; маржа с рекламой и порядок по марже; SKU в двух кампаниях
  суммируется; кабинет без рекламы — «Оплата за клик» целиком;
- сверка: копейка на две строки — сошлось, три копейки на две строки —
  не сошлось; нулевые строки допуск не расширяют; нет разбивки; нет
  начисления; сегодня не сверяется;
- изоляция: данные другой компании под тем же идентификатором
  подключения не попадают ни в SKU, ни в кабинет, ни в сверку —
  integration и HTTP; мутация «без фильтра компании» оба теста роняет.

## Пакет 3 — экран (apps/seller)

- Колонка «Реклама» с сортировкой; строка «Реклама по данным рекламного
  кабинета» в раскрытой строке товара; остаток — обычной строкой списка
  расходов кабинета.
- Предупреждение при `advertisingUnreconciledDays > 0`: расхождение
  названо без приписывания причины.
- Типы — из сгенерированной схемы; арифметики над деньгами
  в компонентах нет — значения приходят с бэкенда.
- Vitest: разбор и направление сортировки `advertising`. Тест ответа
  через msw из первой редакции не писался: новых функций форматирования
  нет, хук передаёт типизированный ответ без разбора.
