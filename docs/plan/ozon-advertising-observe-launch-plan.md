| N6 | Отчёт пилота и решение о следующем объёме | N5 | Аналитика, разработка, владелец продукта |

PHP владеет правами, политиками, их версиями и историей изменений. Go Ads
владеет своим расписанием, чтениями и предполагаемыми решениями. Каждый
сервис хранит свой счётчик только в своей БД. Чужая БД, общий Messenger и UI
не участвуют в разрешении оперативного HTTP. Исторические CSV принадлежат
выбранному существующему загрузчику, а не новому контроллеру.
Деньги PHP остаются в существующем `Money`; Go и контракты используют целые
минорные единицы с обязательной RUB. `float`, неявное округление и сложение
несопоставимых источников запрещены, включая промежуточные расчёты.

## 4. N1 — квоты, интервал и решения до реализации

### 4.1. Рекомендуемый вариант MVP: фиксированные доли

Разделить проверенный общий лимит `L` на доли потребителей и неприкосновенный
резерв `R`. У каждого потребителя свой атомарный durable-счётчик общей области,
разделяемый его репликами. Конфигурация долей проверяется целиком при выпуске:

```text
B_ads + B_fetcher + B_php + B_other + R <= L
```

Имена обозначают бюджет конкретной общей области, не отдельный полный бюджет
каждому кабинету. Несколько кабинетов общей организации суммируются.
Числа долей задаются после N0. Имеющиеся 70000/24ч контроллера — потолок только
его экземпляров; это не принятая доля и не общий лимитер двух сервисов.

Неиспользованный резерв не раздаётся автоматически. Изменение долей сначала
ограничивает прежнего потребителя, затем ждёт вымывания его старого расхода
из полного окна либо доказывает остаток по ledger; лишь затем увеличивает
другую долю. Простого изменения env в двух сервисах недостаточно.
Граница освобождения резерва учитывает защитное расширение окна по принятому
максимальному дрейфу часов; до проверки этой границы остаток не увеличивается.

Альтернатива: централизованный владелец резерва с синхронным протоколом,
идемпотентными заявками и обработкой неизвестного исхода. Выбирать при
доказанной нехватке фиксированного разделения. Нужен отдельный принятый ADR;
не вводить новый сервис, очередь или доступ к чужой БД в рамках варианта MVP.

### 4.2. Интервал X минут

Интервал HTTP и локальный секундный tick — разные параметры. Уже сохранённый
расход и наступивший срок пересчитываются локально, без раннего запроса Ozon.
Один цикл чтения обслуживает кабинет; кампании не умножают общий HTTP без
фактической необходимости страниц/запросов.

Для пилота определить верхнюю цену цикла `C`: список кампаний, агрегат, все
SKU-страницы. OAuth, разрешённые повторы и история резервируются отдельно.
Подобрать `X >= 600 секунд` под выделенную долю и проверить верхнюю оценку:

```text
sum((ceil(86400 / X_account) + 1) * C_account)
    + OAuth_max + retries_max + other_HTTP_max <= B_ads
```

Добавочный цикл учитывает границу окна/первый запуск; фактическая допускающая
проверка durable-счётчика обязательна независимо от оценки. Рост страниц,
числа кабинетов или цены цикла пересчитывает ёмкость до допуска нового чтения.
Если доли не хватает, увеличивается X либо уменьшается охват; ранних повторов нет.
600 секунд — текущий инженерный минимум проекта, не опубликованный период
актуализации Ozon. Более редкий опрос может пропускать быстрый рост расходов;
observe фиксирует этот предел, а не обещает предотвращение перерасхода.

Для расходующих квоту исторических отчётов отдельно считать вес кампаний,
одну генерацию с аккаунта и общий параллелизм организации. Выбрать одного
владельца генераций и проверить прочих потребителей. Этапы «запрос → ожидание
готовности → скачивание» сохраняются; status/download расходуют HTTP, а batch
из десяти кампаний не превращается в одну единицу выгрузки. История не вытесняет
оперативную долю. Неизвестный исход POST не даёт автоматически повторить генерацию.

## 5. N2 — реализация квоты и ограничения пилота

Резервировать квоту перед каждой разрешённой HTTP-попыткой, включая OAuth и retry.
Транзакция и ограничение БД защищают от конкуренции реплик. Если исход неизвестен,
резерв сохраняется до истечения окна; ошибка соединения или падение процесса
не дают вернуть его по предположению «Ozon не получил запрос». Закрытая БД,
невалидная конфигурация, истёкший grant и ошибка часов запрещают новые HTTP.

ozon-fetcher сохраняет endpoint/RPS/Retry-After limiter и получает собственный
суточный ограничитель в своей БД. Аналогично охватываются PHP/прочие обнаруженные
потребители; непокрытый потребитель блокирует допуск. Удаление ledger, смена
revision доли или ключа не обнуляют расход. Для начального неполного окна нужны
подтверждённый перенос состояния или выдержанное окно без соответствующего трафика;
начинать с вымышленного нуля нельзя.

Ввести явный allowlist пар компания/кабинет. Пустой список никого не допускает;
политика пользователя и доступность UI сами по себе не включают кабинет в пилот.
Фильтр действует до выдачи ключей и повторно перед исходящим HTTP; чужие пары
и подмена accountId отвергаются. Имена настроек/место хранения фиксируются в N1,
не добавляются публичные поля «на всякий случай». Если требуется изменение
контракта, обновляются его источник, обе стороны, OpenAPI и сгенерированные типы.

- [ ] QU-02: разные ключи/кабинеты общей области суммируются; независимые области изолированы.
- [ ] QU-03: OAuth/ошибки/retry учитываются; при отказе резерва на mock пришло 0 HTTP.
- [ ] QU-04: падение после резерва и после отправки не освобождает попытку; restart сохраняет ledger.
- [ ] QU-05: границы окна, часы, первоначальное состояние и изменение долей не дают двойной ёмкости.
- [ ] QU-06: история соблюдает собственные квоты/параллелизм, status/download учтены, неизвестный POST не дублируется.
- [ ] AD-01: пустой/чужой allowlist, scope токена, отзыв и истечение grant блокируют чтения.
- [ ] AD-02: ни один исходящий путь не разрешает изменения рекламы, включая GET с побочным эффектом.
- [ ] Схема/Entity и итоговые миграции соответствуют владельцу БД; чистая база,

## 6. N3 — длительная нагрузка и физические отказы

Расширить существующий [паспорт](ozon-advertising-stage11-passport.md) до начала
новых замеров. Сохранить профили 10/100 и 100/1000, 4 работника, сроки 5/35 секунд
для локального mock; отклонения оформлять новым профилем до теста. Эти сроки
не являются SLA Ozon. Добавить настоящий refresh каждые 60 секунд, publisher,
меняющиеся версии/отзывы и потери связи. Полные конфигурации не должны создавать
ранние HTTP или сбрасывать паузу, расход, latch и квоту.

Предлагаемая длительность mock-soak — не менее 24 часов, включая границу суток
Europe/Moscow и истечение полного окна квоты. Зафиксировать её до старта.
Ускоренные часы допустимы для граничных тестов, но не заменяют этот прогон.
Снимать p50/p95/p99/max, число независимых commit кабинетов, HTTP, CPU/RAM,
размер ledger/outbox и задержку доставки. Критерии роста ресурсов задать до замеров.

Физические эксперименты выполнять в изолированном стенде с mock Ozon: SIGKILL
работника, остановка/восстановление PostgreSQL, разрыв сети до БД/PHP/mock,
две независимые реплики и потеря узла, поздний ответ прежнему владельцу lease.
Close/Open pool и два объекта Engine уже проверены; за физический отказ их
не засчитывать. Если независимого узла нет, host failover остаётся непроверенным.

## 7. N4 — независимые тревоги и production без чтений

Сначала определить, какой существующий монитор и канал уведомлений используются.
Watcher должен переживать отказ контроллера и его узла. Если для этого требуется
новый внешний провайдер, зависимость входит в пакет N1, а не подключается по ходу.
Размещение нескольких процессов на одном хосте не доказывает такую независимость.

Watcher обходит все страницы `/internal/observations`, проверяет сам обход,
возраст/полноту результата и доступность БД. Deadline каждой политики проверяется
отдельно от `/health`. Сигналы: deadline_missed, clock_skew, permission_expired,
ошибки источников/авторизации и квоты. observed_source_age_unknown не означает
свежесть Ozon. При неполном обходе нельзя показать общий зелёный статус.

Предлагаемые цели до испытания: полный обход ≤10 секунд, тревога о просрочке
≤60 секунд от `next_tick` с учётом порога 35 секунд; доставка и подтверждение
восстановления измеряются end-to-end. Это проект внутренних порогов, не гарантия
площадки. Для масштаба пилота и пика пороги подтверждаются отдельно.

Подготовить image/release pipeline, отдельную БД/роль и минимум прав, внутренний
listener без публичного роутера, разные токены направлений, NTP-проверку,
backup/restore и журнал действий. Секреты только в принятом secret/env-контуре.
Миграции проверяются отдельно до старта, без обхода обязательного гейта.
Эксплуатационные конфигурации внешних ресурсов — `ops/` с README и картой структуры.

### Чек-лист N4 и тесты

- [ ] OP-01: при живом HTTP и остановленных workers приходит тревога по политике.
- [ ] OP-02: смерть процесса/узла/БД, ошибка токена watcher и неполная пагинация дают тревогу.
- [ ] OP-03: доставка, дедупликация, восстановление и отказ самого watcher проверены.
- [ ] OP-04: посторонний клиент не получает диагностику/ключи; публичного доступа нет.
- [ ] OP-05: исходная синхронизация часов проверена на всех узлах до допуска.
- [ ] OP-06: backup/restore сохраняет квоту, версии, дневной максимум и latch;
  неизвестное восстановленное состояние запрещает чтение до безопасного окна.
- [ ] Контроллер установлен с `ADS_ENABLED=false`; `ADS_MODE=control` не запускается.
- [ ] PHP-флаг `OZON_ADS_ENABLED` и Go-флаг `ADS_ENABLED` описаны раздельно;
  открытие UI/сохранение настройки не равно разрешению живых HTTP.
- [ ] Политики вне пилота не разрешают контроллеру HTTP даже при включённом общем UI.
- [ ] Обязательные CI/review и production smoke пройдены, реальных Ozon-чтений на этом шаге нет.

## 8. N5 — preflight и один кабинет

До старта оформить единый паспорт: точная пара company/account, существующие CPC
кампании (рекомендуется 1–3, не более текущего предела 10), X, квота/область,
длительность, ответственный и условия прекращения. Один кабинет не означает
независимую квоту, если организация общая. Проверить все разрешения и scope.
Тестовый секрет из переписки не переносить в env или документы.

Предлагаемый минимум пилота — 72 часа с тремя границами суток Europe/Moscow.
Это проверка жизненного цикла, не достаточная статистическая база для денежного
резерва. Если нужные события не встретились, отчёт фиксирует пробел, а наблюдение
продлевается по принятому паспорту; вымышленные данные не подставляются.

Последовательность: полностью готовый N4 → проверка allowlist/квоты/часов →
сохранение разрешённых политик в PHP → проверка версии и grant → включение
только observe для выбранной пары → проверка первого полного цикла и доставки
в UI → наблюдение по паспорту. Реальные обращения выполняются только в явно
разрешённом эксплуатационном контуре согласно правилам проекта.

### Чек-лист N5 и тесты

- [ ] Все N0–N4 закрыты; допуск 12 записан отдельно от публикации кода/меню.
- [ ] LW-01: выбранная пара допускается, любая другая и пустой allowlist — нет.
- [ ] LW-02: первая серия HTTP укладывается в зарезервированную долю; до X повторов нет.
- [ ] LW-03: версия политики, расход и причина решения доставлены в нужную компанию;
  чужой company/account не видит данные, кэш не смешивается.
- [ ] LW-04: агрегат/SKU сравниваются за один день и денежную базу; max не складывается,
  предыдущий максимум не теряется, неизвестный расход не становится нулём.
- [ ] LW-05: дата, пустота, свежесть источника, доставка и резерв показаны честно;
  рассчитанный «остановил бы» не назван выполненной остановкой.
- [ ] LW-06: расходы сверены с независимым источником за сопоставимый период;
  CSV запрошен/получен выбранным владельцем без нарушения квот.
- [ ] Обновление страницы/четыре Tabs/смена компании/версии/ошибки проверены в seller.
- [ ] Нулевое число операций изменения рекламы подтверждено ограничениями адаптера
  и журналом исходящих методов; не только отсутствием кнопки в UI.

### Прекращение и откат наблюдения

Немедленные условия: выход за allowlist, обход квоты, неверные часы, утечка
секретов/компаний, разрешённый путь изменения рекламы, отсутствие работающих
тревог или потеря контроля над собственным состоянием. Для обычного 429/5xx
действуют принятые backoff/blocked и тревоги; отдельный порог прекращения
по длительности ошибки фиксируется в паспорте до старта.

Отозвать разрешение пары, остановить новые чтения и активные циклы, при
необходимости закрыть исходящую сеть контроллера. Проверить отсутствие новых
HTTP на границе адаптера и срок завершения уже отправленных запросов.
Флаги требуют принятого механизма reload/restart; изменение env само по себе
не останавливает уже работающий процесс. Сохранить ledger/runtime и доказательства,
не применять down с удалением состояния. Повторный запуск проходит новый preflight.
Откат observe не останавливает рекламные кампании и не восстанавливает их бюджет.

- [ ] RB-01: репетиция отключения на mock подтверждает сроки прекращения чтений,
  включая grant ≤120с и HTTP deadline ≤10с; фактическая граница измерена.
- [ ] RB-02: отключение/повторный старт не обнуляют квоту, расход, latch и историю.
- [ ] RB-03: выбраны ответственный, канал эскалации, действия и доказательства восстановления.

## 9. N6 — отчёт пилота и следующий допуск

### Чек-лист N6

- [ ] Выполнены срок и выборка паспорта; указаны пропуски/недоступные наблюдения.
- [ ] Опубликованы HTTP/остатки квот, интервалы, ошибки, задержки обработки/доставки
  и измеренная полнота. Время HTTP не выдано за watermark расхода Ozon.
- [ ] Есть сверка денежных сумм и объяснения расхождений по одинаковой базе/дате.
- [ ] Нет ложных нулей, межарендаторных утечек, ранних повторов и сброса дневного максимума.
- [ ] Неизвестные резерв/свежесть оставлены неизвестными; observe не доказывает
  предотвращённый перерасход и не закрывает Q1/Q3–Q7 автоматически.
- [ ] Найденные дефекты исправлены, затронутые проверки и обязательное ревью повторены.
- [ ] Решение записано: продлить observe, устранить пробелы или готовить проект control.
  Нет автоматического расширения на следующие кабинеты.

Control остаётся отдельным объёмом: реализация исполнителя этапа 09,
доказательства полномочий/идемпотентности/подтверждения stop, горизонт риска и
денежный запас, новый preflight и принятый допуск 13. Старые предполагаемые
решения observe не ставятся в очередь исполнения. Политика включается явно,
после повторной проверки текущих данных и состояния кампании.

## 11. Доказательства, проверки и порядок поставки

Каждый пункт приёмки получает: ID теста/сценария, дату, source SHA, конфигурацию
без секретов, команду, результат, ссылку на постоянный отчёт и ограничения.
Артефакты `var/` локальны; итоговые выводы и hashes сохраняются в документации/PR.
Логи не содержат денег, ключей, полных ответов API или произвольных сырых ошибок.
Контролируемые фикстуры и отчёты сверки хранятся отдельно по правилам данных.

Поставка каждого законченного изменения: затронутые локальные проверки →
независимое ревью → исправления → зелёный обязательный CI полного diff →
merge/выкладка/разрешённые миграции → production smoke с выключенными чтениями.
Лишь N5 открывает выбранный live-допуск после всех своих предусловий.

- Go: `make ozon-ads-controller-lint ozon-ads-controller-vet ozon-ads-controller-test
  ozon-ads-controller-vulncheck ozon-ads-controller-build ozon-ads-controller-stand`;
  для изменённого fetcher — его `lint/vet/test/vulncheck/build`.
- PHP при изменениях: `make lint stan deptrac structure-check` и затронутые
  unit/integration/functional. Схема — обязательный `make db-rebuild-check`
  только проверенного локального dev/test-окружения.
- API при изменениях: генерация из источника и `make api-types-check`;
  контракт обеих сторон проверяется без живого Ozon.
- Seller при изменениях: `make front-typecheck front-lint front-knip front-test
  front-build APP=seller`, нужные MSW/Playwright; общий UI — все потребители.
- Обязательные audit/e2e и весь CI не ослабляются. Для кода квот, сервисов,
  схем и границ доступа — установленный high-порог независимого ревью;
  недоступный Claude заменяется свежими CLI 5A/5B по правилам проекта.

объявляются выполненными и не заменяются прежними результатами другого diff.
