Секундные кандидаты заменены минутным проектным профилем; результаты измерений ниже сохранены.

Позже владелец передал численные лимиты; они сохранены и пересчитаны в документе
по квотам. Отметки о недоступных числах ниже относятся к моменту исходного исследования.

Дата: 08.11.2026. Режим: исследование, фикстуры и документация. Код приложения,
конфигурация, тесты и реклама не изменялись. Генерация аналитического отчёта
создаёт отчёт и потребляет соответствующие квоты, но не меняет кампанию.

## 1. Источник расходов: проверка API

### 1.1. Область исследования

Проверены 60 запросов в 21 варианте method/path после нормализации UUID,
из них 57 HTTP 200, один 400, два 404; авторизация — отдельно, три раза.
Длительность отдельных HTTP-запросов: 0,161356–0,345917 с. Это время получения
ответа в коротком последовательном прогоне, не SLA и не задержка актуализации расходов.

Основная спецификация [Performance API](https://docs.ozon.ru/api/performance/)
снова не вернула читаемое содержимое. Поэтому нельзя заявить, что проверены
вообще все существующие методы и версии. Ниже приведён охват обнаруженных
семейств аналитики; непроверенные методы названы отдельно. Вызовы управления
кампаниями, ставками, товарами и бюджетами исключены из исследования.

### 1.2. Синхронные методы

Общий префикс таблицы — `/api/client/`. Явный период — `dateFrom=dateTo=YYYY-MM-DD`.

| Метод | Фактический результат | Оперативное применение |
|---|---|---|
| GET `campaign` | 101 запись; 10 работающих SKU/CPC и одна SEARCH_PROMO | Инвентаризация и наблюдаемый статус; денежные поля бюджета не заменяют расход |
| GET `statistics/campaign/product` | CSV сразу, 65 строк за сегодня/вчера | Доступен без создания UUID; формат экспорта |
| GET `statistics/campaign/product/json` | JSON сразу, 65 строк за каждый день; фильтр по campaignIds работает | Выбран основной источник CPC |
| GET `statistics/daily` и `/json` | CSV/JSON сразу, сегодня и вчера по 10 строк в JSON | Контрольная дневная сверка; отсутствие строк требует интерпретации |
| GET `statistics/expense` и `/json` | Сегодня CSV без данных/JSON rows=[], вчера JSON содержит 10 строк | Кандидат для последующей финансовой сверки; непригоден как единственный источник сегодняшнего нуля |
| POST `statistics/products/sku` | JSON сразу; все 10 работающих CPC, сегодня 15 строк, вчера 16 | SKU-сверка и защитный максимум по кампании; расходы предварительно суммировать по SKU |
| GET `statistics/campaign/media` и `/json` | CSV-заголовок / JSON rows=[] | Метод доступен, содержательная полнота для медийной кампании не проверена |

Синхронный JSON агрегата содержит `moneySpent` строкой с запятой; SKU — `expense`
строкой с точкой. `ctr` и другие неденежные метрики могут иметь разный масштаб
и формат; их нельзя автоматически сравнивать одинаковым парсером.

### 1.3. Асинхронные методы и трёхшаговая цепочка

Подтверждено для подробной статистики CPC:

1. `POST /api/client/statistics` для CSV либо `/statistics/json` для JSON.
   Тело: campaigns=[49761882 как строка], dateFrom=dateTo=2026-11-08, groupBy=DATE.
   Ответ — UUID, а не сам отчёт.
2. `GET /api/client/statistics/{UUID}`. В этом прогоне наблюдались NOT_STARTED и OK;
   для CPO также IN_PROGRESS. У OK появился относительный link на скачивание.
3. `GET /api/client/statistics/report?UUID=...` возвращает CSV или JSON,
   выбранный на этапе заказа. `/json` не делает генерацию синхронной.

| Семейство | Заказ | Итог | Генерация по updatedAt − createdAt |
|---|---|---|---|
| Подробный CPC CSV | POST `statistics` | CSV скачан, строка SKU и итог | 10,099511 с |
| Подробный CPC JSON | POST `statistics/json` | JSON скачан, rows и totals | 5,351961 с |
| CPO товары | POST `statistic/products/generate/json` | JSON скачан, rows=[] | 1,315018 с |
| CPO заказы | POST `statistic/orders/generate/json` | JSON скачан, rows=[], overExpenses=0 | 7,666762 с |
| Поисковые запросы | POST `statistics/phrases/json` | JSON скачан, непустые строки | 8,719874 с |
| Все товары CPO: товары | GET `statistics/all_sku_promo/products/generate/json` | 404 «Кампания не найдена», UUID нет | Не измерено |
| Все товары CPO: заказы | GET `statistics/all_sku_promo/orders/generate/json` | 404 «Кампания не найдена», UUID нет | Не измерено |
| Атрибуция | POST `statistics/attribution/json` | 400 «Неподдерживаемый тип рекламной кампании» для выбранной CPC | Не измерено |

Опрос выполнялся раз в 5 секунд с ограничением количества попыток; фактическое
ожидание клиентом включает округление до опроса, сеть и скачивание. Разница двух
генераций не доказывает, что JSON всегда генерируется быстрее CSV.

`GET statistics/list` до и после генерации вернул `items=[], total="0"`, хотя
известные UUID успешно получены и скачаны. Этот список нельзя делать единственным
способом поиска незавершённых отчётов; собственные UUID необходимо сохранять.

### 1.4. Что проверено только по документации или ограничено кабинетом

- `POST statistics/video` и JSON-вариант: семейство упомянуто в официальном
  дайджесте [O3]; подходящего видеокабинета/кампании для содержательной проверки нет.
- Атрибуция: маршрут принял запрос, но не поддержал тип выбранной кампании;
  успешная генерация и состав строк этим не подтверждены.
- Медийная статистика и CPO: пустые ответы не подтверждают полноту и состав
  непустой строки. 404 all_sku не доказывает отсутствие метода у других кабинетов.
- Прочие версии, агрегаты продаж, балансы и рекомендованные ставки требуют
  полной спецификации. Они не заменяют проверенный суточный расход CPC.
- Численные квоты и максимальные batch-размеры не установлены нагрузочными
  экспериментами. Успешный batch из 10 — наблюдение, не доказанный максимум.

### 1.5. Период и часовой пояс

Для 2026-11-08 статус сгенерированного отчёта вернул границы
2026-11-07T21:00:00Z — 2026-11-08T20:59:59Z. Это подтверждает сутки UTC+03
для данного сценария и кабинета, но не всех методов/регионов Ozon.

В агрегате выбранной кампании получены:

| Параметры | moneySpent |
|---|---|
| dateFrom=dateTo=2026-11-08 | 56,52 ₽ |
| from/to с границами 08.11 и смещением +03:00 | 360,19 ₽ |
| from/to с границами 08.11 и Z | 56,52 ₽ |
| from/to за 07.11 + dateFrom/dateTo за 08.11 | 56,52 ₽ |

Причину интерпретации from/to не считаем доказанной. Для MVP использовать только
проверенные dateFrom/dateTo с явным днём; параметров по умолчанию и from/to избегать.
В ТЗ день привязан к часовому поясу подключения, подтверждённому исследованием.

### 1.6. Сопоставление источников

За вчера 10 кампаний совпали между product JSON, daily JSON, expense JSON и
суммами SKU. За сегодня product/daily совпали, expense пуст, а в первом наборе
SKU был выше агрегата у четырёх кампаний. В последующих трёх сериях:

| Кампания | product и daily | SKU до чтения product | SKU после | Разница |
|---|---|---|---|---|
| 14275771 | 1,03 ₽ | 4,63 ₽ | 4,63 ₽ | 3,60 ₽ |
| 16017246 | 1 895,40 ₽ | 1 929,12 ₽ | 1 929,12 ₽ | 33,72 ₽ |
| 23253271 | 474,73 ₽ | 485,71 ₽ | 485,71 ₽ | 10,98 ₽ |

Все три серии дали эти различия; SKU до/после совпал. Это ослабляет объяснение
простым приростом между двумя последовательными чтениями, но не доказывает
причину расхождения или всегда большую свежесть SKU. Наблюдение короткое,
доказанной верхней границы задержки и watermark нет.

Отдельный фильтр архивной кампании вернул явную строку moneySpent=0. Это отличается
от отсутствующей строки, но не доказывает безопасность первого старта нового дня.

**Решения владельца в текущем обсуждении:**

- D1: основной источник — агрегированный JSON, SKU — сверка, асинхронные отчёты — история.
- D2: при расхождении учитывать большую сопоставимую сумму и сохранять различие.
- D3: защита бюджета важнее полного расходования; при потере контроля — запрос защитной остановки.

Точность сравнения: одна кампания, отчётный день, валюта, НДС и состав расходов;
SKU сначала агрегируется внутри кампании. Складывать product и SKU нельзя.

## 2. Измеримые требования: проверено и предложено

HTTP-время измерено; максимальная свежесть, допустимый риск и промышленная
ёмкость ещё не доказаны. Вопрос о масштабе заменён предложением безопасного старта:

| Параметр | Предложение для проверки, не гарантия |
|---|---|
| Пилот | Один кабинет, волны 1 → 3 → 10 CPC; расширение по результатам |
| Основной опрос | Кандидат X=10 минут либо больше по расчёту квот; результаты HTTP-замеров не задают частоту |
| Приоритет | Принят D3: более ранняя остановка допустима |
| Защитный запас | Рассчитывать по риску; фиксированные 10% не считать доказанной защитой |
| Стенд | Профили нескольких кабинетов, общих квот и пиковых дедлайнов; цели фиксируются до прогона |

Нужно определить порог близости к лимиту, допустимые ошибки чтения и срок утраты
контроля. Best practice: задавать их через оставшийся бюджет и оценку риска,
а не одной одинаковой частотой для всех кампаний. Конкретные значения принимаются
после серии измерений и квот; произвольные цифры не становятся release-gate.

## 3. Состояния: проверка полноты

Основной пробел текущего плана — отсутствие полной таблицы переходов.
В [проекте ТЗ](ozon-advertising-technical-spec.md) выделены независимые состояния
политики, операции и наблюдения Ozon. Нужны сценарии первого дня, ручного изменения,
истечения разрешения, позднего ответа и явного возобновления.

Рекомендация: явная команда возобновления после аварийной/ручной блокировки;
штатный бюджетный стоп может разрешать следующий день по новому preflight.
Нельзя автоматически считать неактивный статус доказательством ручного действия.

## 4. Алгоритм бюджета: принятое основание и пробелы

Приняты D2/D3. Контрольный расход — максимум пригодных сопоставимых наблюдений
и ранее принятого расхода того же дня. Финансовые корректировки хранятся отдельно.
Запас округляется вверх в копейки; скорость расходования — оценка, не верхняя граница.

Не установлен безопасный начальный запас для кампании без наблюдений. Рекомендуется
блокировать автоматический старт до пригодной основы оценки; альтернативный
ограниченный bootstrap с отдельным малым бюджетом требует собственного решения
и подтверждённого механизма ограничения на Ozon. Самостоятельно включать его нельзя.

## 5. Данные и API: проверка технической определённости

Данных в фикстурах хватает для проектов парсеров, но не для полного API-контракта
управления. В ТЗ нужно зафиксировать поля политики, версии, наблюдения, операции,
владения и аудита; статусы ошибок, конкурентное редактирование, курсорную доставку
изменений и полную синхронизацию после потери курсора. Подробности — в проекте ТЗ.

Best practice: PHP хранит намерение, Go — исполнение; подтверждение применённой
версии отделено от сохранения. Отключение доставляется как версия/маркер удаления,
а не исчезает из списка без объяснения.

## 6. Конкуренция и восстановление: проверка гарантий

Live-запросы записи не выполнялись. Не проверены повтор команд, их задержки,
фактическая остановка и поддержка idempotency/fencing площадкой. Поэтому
внутренняя аренда не объявляется гарантией единственного внешнего эффекта.

Рекомендация: один владелец кампании, проверка версии перед отправкой,
неопределённые операции блокируют старты; новый владелец сначала сверяет Ozon.
После позднего старта при желаемом stopped запрашивается остановка, пока право
действует. Полное отсутствие перерасхода при сетевом разделении не гарантируется.

## 7. Проверяемые сценарии

Каталог в проекте ТЗ связывает требования и тесты: предусловия, событие, результат,
уровень и фикстуру/мок. Это описание будущих тестов, не написанные или пройденные тесты.
Отдельные группы: формат/полнота, деньги, состояния, контракты/права, конкуренция,
Tabs и нагрузочные/аварийные проверки. Проверки живого API остаются исследованием.

## 8. Интерфейс и эксплуатация

Требование владельца сохранено: один пункт «Озон Ads», все страницы внутри через
Tabs. Вкладки: «Кампании», «Стратегии», «История действий», «Настройки».
Показывать основной расход, контрольную сумму для защиты и факт расхождения так,
чтобы пользователь понимал раннюю остановку; технические формулы не помещать в основной flow.

Нужны конкретные сигналы: просроченная проверка кампании, устаревшая версия,
unknown-операция, неподтверждённая остановка и исчерпание ёмкости. Heartbeat
процесса не подтверждает контроль всех кампаний. Runbook должен описывать ручную
проверку Ozon и судьбу активных кампаний при выключении сервиса.
