## 1. Решения и блокирующие вопросы

Приняты владельцем:

- D1: агрегированный JSON с явными датами — основной источник; SKU — сверка;
  асинхронные отчёты — история.
- D2: для защиты учитывать большую сопоставимую сумму, сохранять расхождение.
- D3: защита бюджета важнее полного расходования; при потере контроля
  запрашивать остановку, запрещать новые старты.
- D4: кампания без достаточной истории сначала наблюдается; автоматический
  запуск разрешается только после пригодной основы для защитного запаса.
- D5: после смены суток ждать пригодных данных нового дня; отсутствие строки
  не считать нулём. При готовности внутри окна повторить preflight, вне окна не запускать.
- U1: один пункт «Озон Ads», остальные страницы — внутренние Tabs.

Все остальные технические детали ниже предложены до принятия ADR.

| Вопрос | Способ закрытия | Блокирует |
|---|---|---|
| Q1: полнота/новый день/задержка | Ожидание выбрано D5; серия подтверждает покрытие и нули | Живое управление |
| Q2: квоты | Числа получены из текста владельца; остаются scope/reset, определение активных и исключения методов | Допуск интервалов/масштаба |
| Q3: начальный запас | D4: сначала наблюдение; остаются достаточность истории и параметры | Запуск |
| Q4: принадлежность кабинета | Подтверждённая привязка и один владелец независимо от API-ключей | Любую запись |
| Q5: start/stop Ozon | Схема, состояния, повторы, подтверждение; моки и отдельный пилот | Исполнитель |
| Q6: численный риск/нагрузка | Паспорт и пороги до проверок | Приёмку выпуска |
| Q7: отсутствие watermark | Принять остаточный риск и запас либо отказаться от гарантии | Живое управление |

Предложение пилота: один кабинет, волны 1 → 3 → 10 CPC. Обычный опрос —
кандидат X=10 минут после допуска по квотам; расчёт может потребовать большего X.
Для генераций с расходованием квоты при A=K и резерве 30%: 1–9 кампаний —
10 минут, 10 — 15 минут, 20 — 30 минут, 50 — 60 минут. Это один такой источник;
для двух вес удваивается. Оперативные исключения учитываются отдельно.
Секундное ускорение около лимита не предлагается. Stop по расписанию/решению
имеет отдельный дедлайн и резерв. Это проектный профиль, не SLA Ozon.
Фиксированного 10%-запаса нет.

## 2. Компоненты и данные

### 2.1. Граница первого выпуска

Первый выпуск — observe по [разделу 3.1 плана](ozon-advertising-stages.md#31-первый-выпуск-и-отдельный-допуск-управления).
В него входят модели/контракты, чтение, расчёт предполагаемых решений и Tabs.
Рабочий исполнитель изменения рекламы не подключён. Текущий документ описывает
также будущий control; его API и команды не считаются доступными в observe.

| Действие | Observe первого выпуска | Control после отдельного допуска |
|---|---|---|
| Читать кампании/расходы, получать токен, генерировать аналитический отчёт | По allowlist, правам и квотам | По тем же границам |
| Сохранять настройки расчёта и предполагаемые решения | Допускается, с явной пометкой наблюдения | История observe остаётся только историей |
| Менять рекламу через start/stop, ставки, бюджеты или любые методы с эффектом | Отклоняется до сети, включая GET с побочным эффектом | Только разрешённый объём, выбранная политика и preflight |
| Вызвать API реального управления напрямую | Ошибка режима, рабочее задание не создаётся | Авторизация, версия, idempotency и остальные проверки |

Защита строится по разрешённым операциям, а не запрету всего POST:
авторизация и аналитические отчёты тоже используют POST. UI показывает
«Режим наблюдения: реклама не изменяется автоматически», блокирует реальные
start/stop и не выдаёт предполагаемую остановку за защиту бюджета.

Наличие неизвестного расхода/запаса допускается как явно отображённый результат
observe; запуск при этом не разрешён. Перед первым живым observe обязательны
проверки доступа/изоляции, границ коннектора, квот, CI и независимое ревью
соответствующего diff. Непроверенная схема start/stop не блокирует reader на моках.

Переход к control — явная активация выбранных политик после допуска, с новой
версией/проверкой условий. Старые решения observe не становятся командами.
Обратный переход с активного control: сначала запрет новых start, затем stop
и сверка в пределах действующего права, и только после этого observe. Если
stop не подтверждён, переход не объявляется безопасно завершённым. Экстренный
отзыв права немедленен и отдельно сохраняет неподтверждённые результаты.

### 2.2. Будущие компоненты и хранение

PHP Advertising хранит намерение, права и пользовательский аудит. Go
ozon-ads-controller хранит применённые политики, наблюдения, дедлайны и операции;
читает, решает, вызывает и сверяет напрямую. Ingestion отвечает за историю.
UI работает с PHP. Общая очередь не участвует в критическом пути остановки.

UUIDv7 создаются приложением, PostgreSQL uuid. Деньги — Money, целые копейки
bigint и валюта. Внешние ID — проверенные десятичные строки без JavaScript Number.
Scope включает company/account/policy IDs и external_campaign_id.

| Запись / владелец | Предлагаемые поля |
|---|---|
| Политика / PHP | id, scope, kind=cost_control, version, desired_mode, daily_limit_minor, currency, timezone, start_local, stop_local, updated_at, actor_id |
| Версия / PHP | policy_id/version unique, полный снимок, actor_id, created_at |
| Доставка / PHP | revision, scope, policy_version, kind=upsert/disable, created_at |
| Runtime-проекция / PHP | applied_version, desired_state, observed_state, observed_at, effective_spend_minor, reason, operation_state |
| Применённая политика / Go | scope, version, settings, permission_expires_at, applied_at |
| Наблюдение / Go | id, scope, report_day, source, fetched_at, source_updated_at nullable, amount_minor, currency, tax_basis, coverage, quality_reason |
| Контроль дня / Go | scope/day unique, high_water_spend_minor, reserve_minor, effective_spend_minor, blocked_reason |
| Дедлайн / Go | scope, task_kind, due_at, priority, generation |
| Владение / Go | внешний кабинет/кампания, owner_id, generation, lease_until |
| Операция / Go | operation_id, scope, policy_version, generation, target_state, phase, attempt, next_attempt_at, last_error_class, created_at, confirmed_at nullable |
| Предметный аудит | актор/система, scope, версия, причина, observation/operation IDs, время |

Unique защищает одну действующую политику на кампанию/подключение. Q4 отдельно
решает дубли внешнего кабинета с другими ключами. Company-scoped индексы
начинаются с company_id; индекс диспетчера дедлайнов согласуется в ADR.
Все списки с лимитом, история — keyset. Политика физически не удаляется до
доставки disable и завершения сверки.

Go не обращается к БД Conwix. Ключи только в памяти в пределах права. В
технических логах нет сумм, ключей и тел ответов; деньги аудита — в защищённом
предметном контуре. Retention каждого типа определяется в ADR; автоматическое
удаление до принятия сроков не включается.

## 3. Предлагаемый API и доставка версий

Новый seller-префикс: `/api/companies/{companyId}/ozon-ads`, обычная сессия.
Права просмотра и управления различаются; членство само по себе не даёт запись.
Это проект новых контрактов, не описание существующих маршрутов.

| Метод/суффикс | Результат |
|---|---|
| GET `/campaigns` | Нужные колонки, account/status-фильтры, limit/cursor и качество данных |
| GET `/policies/{id}` | Настройки, версия/ETag, applied_version и runtime |
| POST `/policies` | Сохранение настройки; ещё не запуск Ozon |
| PATCH `/policies/{id}` | If-Match обязателен; 412 при конфликте версии |
| POST `/policies/{id}/pause` | 202 + operation ID; остановка подтверждается отдельно |
| POST `/policies/{id}/resume` | 202, новый preflight вместо безусловного start |
| POST `/policies/{id}/disable` | Версия отключения, остановка и выход из управления |
| GET `/operations/{id}` | Фаза/причина/время без секретов |
| GET `/events` | Company-scoped keyset-история с лимитом |

POST управления принимает application Idempotency-Key, scoped на компанию,
политику и действие. Повтор ключа/payload возвращает одну операцию, иной payload
с тем же ключом — 409. Unique constraint и обработка конфликта обязательны.
Это дедупликация у нас, не гарантия idempotency Ozon.

Деньги: amountMinor/currency; окно HH:mm, IANA timezone. Положительный лимит,
start < stop внутри суток MVP, только поддерживаемые валюты/типы. Ошибки 401,
403, 404 для отсутствующего/чужого объекта, 409 конфликт действия, 412 версия,
422 неверные/неподдерживаемые настройки; конверт — по действующему API проекта.

Внутренний контракт: изменения по непрозрачному курсору, ack applied_version,
runtime. PHP атомарно сохраняет политику и изменение доставки; Go применяет
атомарно до ack. Старый повтор не откатывает новую версию. Простая последовательность
ID не доказывает порядок видимости commit: в ADR выбрать snapshot/delta-протокол,
который не теряет поздние commit и умеет полную пересинхронизацию.

Disable/отзыв доставляются явно. Частичный список не заменяет полный, исчезновение
из страницы не является disable. При потере/истечении курсора — полная сверка.
Схемы `services/_contracts/` версионированы и проверяются обеими сторонами.

## 4. Состояния и переходы

Независимы: desired_mode enabled/paused/disabling/disabled; operation phase
planned/sending/unknown/confirming/succeeded/failed; исходный provider status
с observed_at; ручная/защитная/конфликтная блокировка.

| Событие | Требуемый результат |
|---|---|
| Окно открыто, данные/права пригодны, бюджет есть | Planned start, повторный preflight перед HTTP |
| Время >= stop или достигнут бюджетный порог | Desired stopped, отмена неотправленного start, запрос stop |
| Потеря контроля/скоро истечёт разрешение | Защитный stop до истечения права, новые start запрещены |
| Право отозвано | Нет неавторизованных вызовов; blocked/unknown и тревога |
| Уменьшили B | Новая версия, пересчёт, уже понесённый расход сохранён |
| Повысили B после стопа | Само повышение не делает resume |
| Новый день после штатного бюджетного стопа | Новый контекст и preflight, не обнуление по пустому ответу |
| Новый день после ручной/защитной блокировки | Блокировка сохраняется до resume |
| Внешний статус расходится с ожидаемым | Сверка/конфликт, без недоказанной атрибуции действия человеку |
| Ответ команды потерян | Unknown, запрет start, чтение состояния |
| После stop подтверждён целевой статус | Succeeded; продолжить ограниченную сверку поздних начислений |

Окно полуоткрытое: start включительно, stop исключительно. Приоритет:
полномочия → stop/запрет start → сверка unknown → расходы → допустимый start → история.
Полномочия не обходятся ради stop. Один кабинет не блокирует сроки другого.

## 5. Алгоритм бюджета

1. Проверить scope, день, валюту, НДС, состав расходов и полноту.
2. P — расход агрегата. S — сумма уникальных SKU-фактов внутри кампании при
   полном пригодном ответе; повтор ключа не удваивает сумму.
3. C = max(P, пригодный S при наличии, ранее принятый C этого дня).
   Сохранить наблюдения, разницу и основу решения; несопоставимый S исключить.
4. R — округлённая вверх оценка расхода за время данных/проверки/stop/восстановления
   плюс резерв ошибки, без float. Скорость наблюдения не является верхней границей.
5. При C >= max(0, B − R) запросить stop. Для start нужны пригодный R и
   C + R < B наряду с окном/правами/качеством данных.
6. Коррекция вниз не освобождает бюджет автоматически; финансовая история
   хранит её отдельно от оперативного high-water.

Пропавшие SKU/страницы и изменения состава требуют оценки полноты. Отсутствие S
не равно нулю; работа только по резерву требует отдельного правила. По D2 любое
расхождение в копейку не является автоматическим stop: оцениваются остаток и риск.

Новый день начинается с неизвестного расхода. Явный ноль за нужный день отличается
от пропуска, но требует Q1. Без основы R автоматический bootstrap не добавляется.
Отсутствующий watermark не заменяется fetched_at или обещанием возраста данных.

## 6. Конкуренция и восстановление

Один владелец внешней кампании, lease с generation, атомарный захват/unique БД.
Перед HTTP проверяются version, generation, право и desired_state. Операция
сохраняется до HTTP, транзакция не держится во время сети. При рестарте sending
означает неопределённый исход и требует сверки.

Lease не отменяет отправленный запрос старого владельца. Новый сначала сверяет
неопределённые операции, блокирует start; поздний start при desired stopped
вызывает stop в пределах права. Exactly-once внешнего HTTP не обещается.

Повторы ограничены дедлайном/квотой. 429 учитывает подтверждённый Retry-After,
иначе backoff с jitter; 401 — ограниченное обновление, 403 — без бесконечных
повторов. Неопределённую команду не повторять вслепую.

При потере БД новые start запрещены; аварийный stop известных кампаний из памяти
в пределах права определяется ADR. После полного рестарта без БД нельзя обещать
список/ключи. При полном отказе инфраструктуры остаются ограничения Ozon.

## 7. Интерфейс и эксплуатация

«Озон Ads» → Tabs: «Кампании», «Стратегии», «История действий», «Настройки».
Вкладка в URL `view`, неизвестное значение нормализуется в «Кампании».

| Tab | Содержание |
|---|---|
| Кампании | Ozon-статус, управление, основной/учтённый для защиты расход, лимит, окно/timezone, время, причина, переход к стратегии/истории |
| Стратегии | Форма суммы/окна, версия сохранения/применения, pause/resume/disable по правам |
| История действий | Актор/система, время, причина, версия, команда/подтверждение; keyset без COUNT по растущему журналу |
| Настройки | Подключение, доступность управления, timezone/ограничения, существующий сценарий ключей |

Обязательны direct link/reload/Back/Forward, клавиатура, узкий экран, несохранённые
формы и company/account-изоляция. Accepted/unknown не означают подтверждённый stop.
Будущая реализация: packages/ui, TanStack Query, createCompanyApiClient,
companyQueryKey, генерированные типы. Денежной арифметики в компонентах нет.

Сигналы: пропущенный дедлайн кампании, старая applied_version, длительный unknown,
неподтверждённый stop, квоты/ошибки и исчерпание ёмкости. Heartbeat недостаточен.
Runbook: ответственный, сверка Ozon, ротация/отзыв, запрет start, stop и восстановление.
Rollback начинается с запрета start и сверки кампаний; unknown не считается безопасным выходом.

## 9. Связь с этапами

| Этапы | Детализация и группы |

D1–D5/U1 приняты; источники и генерация проверены в пределах исследования.
Q1–Q7 закрываются до зависимого кода/пилота. Ближайшее исследование — граница
суток и квоты. К реализации управления сейчас не переходим.

Подготовительная реализация будущего observe может идти параллельно с внешними
проверками после принятия ADR/контрактов его объёма. Полная готовность управления
не является предусловием разработки чтения и UI, но перед живым observe должны
быть приняты его собственные квоты, доступ и гейты. Текущее поручение дополняет
только план и само по себе не снимает ограничение на написание кода.
