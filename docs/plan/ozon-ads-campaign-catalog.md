# Ozon Ads: каталог рекламных кампаний в кабинете

09.11.2026. Задача владельца: в кабинете Вумджой ООО не видны кампании,
непонятно, что выбирать для наблюдения. Это исправление пользовательского
сценария вкладки «Кампании» из этапа 10, без включения live или управления.

## Диагноз

Production-проверка только метаданных: найдено одно целевое подключение;
состояния подключения и рекламы active, последний сохранённый список кампаний
09.11.2026 12:25:27, наблюдений нет. Ключи, тела и суммы не выводились.
Frontend запрашивает политики наблюдения вместо каталога, скрывает таблицу при
выключенном интерфейсе наблюдения, форма требует ручной ID.

## Изменение

1. Ingestion сохраняет техническую проекцию уже полученного списка кампаний:
   одна актуальная запись на company/account, whitelist метаданных в JSONB,
   ссылка на immutable raw, время получения и признак полноты. Исходные факты
   и raw не меняются. Старая конкурентная загрузка не перезаписывает новую.
2. Новый company-scoped endpoint Ingestion читает проекцию через DBAL/SQL,
   отдаёт readonly DTO, ограниченную keyset-страницу и время/полноту. Это новый
   endpoint, существующие контракты подключений/политик не меняются. Advertising
   backend не получает новой межмодульной зависимости или доступа к чужой БД.
3. Проекция обновляется при существующей PHP-загрузке списка и сохранении
   результата пробы ключа. Отдельная company/account-scoped команда строит её
   из последнего сохранённого raw для уже подключённого кабинета. Новых Ozon
   HTTP, расписаний, маршрутов очереди и внешних зависимостей не добавляется.
4. «Кампании» показывает каталог независимо от флага наблюдения: название,
   ID, Ozon-статус, тип, оплату и время получения. Пустой подтверждённый список,
   отсутствие загрузки, неполнота и ошибка различаются. Архив можно показать
   явно; отсутствие в неполном списке не объявляется удалением кампании.
5. Форма нового наблюдения выбирает кампанию из каталога. SKU само по себе не
   доказывает CPC: используется поле PaymentType из сохранённого ответа.
   Неподдерживаемые/архивные кампании имеют объяснение. Существующую политику
   можно выключить при ошибке каталога. Конфигурация live-допуска не меняется.

Проекция содержит только ID, title, state, advObjectType, PaymentType, total
и метаданные получения. Бюджеты/ставки/расходы из raw в неё не копируются.
Читается фактическое `PaymentType` с заглавной буквы; в существующей fixture
`total` — строка. Утилита не считает число строк доказательством полноты без
сопоставимого total. Источник Ozon не опрашивается при открытии страницы.

## Разбор первого независимого ревью

Приняты все четыре замечания (5A — 2, 5B — 2 новых):

1. Неудача разбора отправляется в действующий трекер через порт Shared\Domain\ExceptionTracker (HubInterface только в Infrastructure),
   с фиксированным исключением без тела/цепочки исключений; raw остаётся сохранённым.
2. Новый каталог использует общий стандарт страниц: по умолчанию 50, максимум 200.
3. Время получения списка пробы фиксируется сразу после HTTP-ответа до проверки SKU.
   Регрессионный тест вставляет более свежий снимок во время этой проверки.
4. Raw дедуплицирует одинаковые ответы, поэтому восстановить последнее повторное
   наблюдение после утраты проекции невозможно. Bootstrap получает явный `restored`,
   показывает время первого сохранения ответа и предупреждение о неподтверждённой
   актуальности; существующую проекцию никогда не заменяет. Следующее штатное
   получение снимает признак восстановления. Это проверяется сценарием A → B → A.

Новые внешние зависимости не вводились: используется установленный трекер Sentry/GlitchTip.
Повторные проверки/ревью и эксплуатационные результаты фиксируются в PR #343.
