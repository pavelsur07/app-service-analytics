# Этап 5. Обязательный TOTP системных администраторов

Статус: вариант, OTPHP 11.5.0 и изменения admin API согласованы владельцем
25.10.2026 ответом «Согласовать вариант из плана». Реализация, проверки, независимое ревью и production-поставка завершены
26.10.2026; личный authenticator каждый владелец подключает сам при входе.

## Задача и результат

Пароль администратора сам по себе не открывает привилегированные действия.
Сначала подтверждается пароль, затем одноразовый TOTP или резервный код.
Ограниченные состояния входа/enrollment не дают доступа к данным клиентов.
Существующие владельцы проходят настройку; первый внешний администратор
получает доступ только с MFA, как требует ADR-017.

## Решения для согласования одним пакетом

1. Новая backend-зависимость `spomky-labs/otphp` **11.5.0**, зафиксированная
   версия; библиотека реализует TOTP, собственная криптография не пишется.
   Перед установкой — Composer audit и проверка совместимости зависимостей.
   Основание версии: https://github.com/Spomky-Labs/otphp/releases/tag/11.5.0
2. Изменение admin API: после пароля возвращается явное состояние ожидания
   MFA; маршруты `/api/admin/auth/mfa/status`, `/enroll`, `/confirm`, `/verify`,
   `/recovery-codes` имеют DTO и ограничения по состоянию. `/api/admin/auth/me`
   не выдаёт полный профиль до полного входа. Seller/extension не меняются.
3. Enrollment существующих владельцев без отключения MFA всем: после
   пароля доступны только настройка фактора/выход. Остальные действия
   запрещены до подтверждения TOTP. Экран показывает секрет и otpauth URI
   для ручного добавления в authenticator; новой QR-библиотеки нет.
4. Потеря устройства: одноразовый резервный код + пароль. При потере всех
   кодов — только операторская процедура через SSH/CLI с проверкой личности
   вне приложения, журналом и завершением прежних сессий; публичного
   аварийного endpoint и обхода по паролю не создавать.

Новая зависимость требует явного согласования по `CLAUDE.md` →
«Единственная точка согласования»; до ответа она не устанавливается.
Настоящий документ сам не принимает новый ADR.

## Файлы и границы

- Новый ADR уточняет ADR-007/017, фиксирует onboarding/recovery и границы
  неполной сессии. Обновляется указатель ADR и операционный checklist.
- Identity Domain: состояние MFA администратора, encrypted secret,
  последний принятый time-step, одноразовые recovery-коды и версия MFA.
- Infrastructure: adapter OTPHP, шифрование секрета через штатный sodium,
  атомарные операции подтверждения/погашения, ограниченные попытки в Redis.
- Ui: admin security handlers и общий guard, DTO/контроллеры MFA,
  запрет привилегий для неполного входа, команда аварийного восстановления.
- `apps/admin`: настройка, второй шаг входа, резервные коды, повторное
  подтверждение чувствительных операций. Примитивы/токены packages/ui.
- Источник OpenAPI/генерация TS; одна итоговая миграция со схемой Entity
  и обратимым down либо явно проверенным восстановлением.

## Безопасные значения предлагаемого контракта

- TOTP: 6 цифр, период 30 секунд, допустимая погрешность ±1 шаг.
- Секрет не менее 160 бит случайности; хранение только зашифрованным.
- Принятый time-step погашается атомарно, второй конкурентный запрос
  тем же шагом не считается успешным.
- Challenge MFA — 5 минут, максимум 5 попыток, ограничение по
  администратору и IP; новый challenge не обходит общий лимит.
- 10 резервных кодов, каждый не менее 128 бит случайности; только хэши
  в БД, показ единожды. Перевыпуск аннулирует предыдущий набор атомарно.
- Смена/сброс фактора меняет версию MFA и завершает прежние сессии.
  Успешное завершение второго шага меняет идентификатор сессии.
- Секреты, QR/URI и коды не попадают в логи, audit values, телеметрию,
  сообщения очереди и review-пакеты. В audit — только факт и актор.
- IP allowlist/VPN и парольный throttling сохраняются.

## Уточнение проверки телеметрии

В установленном Sentry SDK `send_default_pii: false` не выключает request
body capture (по умолчанию medium). Это расходится с комментарием проекта
о запрете отправки тел запросов. Для выполнения принятого требования не
передавать MFA-коды явно задаётся `max_request_body_size: never`; before_send
также удаляет request.data и очищает secret/provisioningUri/recoveryCodes
в extra/breadcrumbs, включая массивы. Изменение подтверждается отдельным
RED→GREEN тестом настоящего Sentry Event. Фактическая отправка боевых
секретов в GlitchTip этим статическим выводом не утверждается.
