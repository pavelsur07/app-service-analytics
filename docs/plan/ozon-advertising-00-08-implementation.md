## Что входит

Advertising: ORM-политика Money, версия, права company/account, аудит через
IdentityFacade, API GET/POST/PUT и подтверждённая проекция последнего решения.
PHP использует существующий Shared Money; в БД bigint/currency.

Go: собственная БД/роль/HBA; атомарная версия конфигурации, аналитический
allowlist, OAuth, лимитер HTTP, reader JSON+SKU, persisted account leases,
дедлайны окна, консервативный high-water расхода и latch до нового дня.
Проекция доставляется в PHP отдельно от локального планировщика.

Исполнитель, UI, долговременный журнал всех наблюдений, продовая топология и
живая выкладка не входят. Операции этапа 09 не представлены пустыми сущностями.
Навигация «Озон Ads»/четыре Tabs остаётся в плане этапа 10. `observe` не является
защитой бюджета; `sourceAgeKnown/budgetProtectionActive=false` в seller API.

## Протокол дальнейшего исследования 02/04

Перед живым сбором закрепить срок ≥3 суток с двумя границами UTC+03 и
существующими активными/неактивными кампаниями. Aggregate/SKU читать не чаще
одного цикла/10 минут, один цикл на кабинет; 3 HTTP чтения + auth при необходимости,
не более 577 обычных запросов/кабинет/сутки без повторов. При 429 увеличить паузу,
повторы ограничены; нагрузку/429 специально не провоцировать. Сохранять только
санитизированные ответы, HTTP status/Content-Type, dateFrom/dateTo, captured_at,
SHA/размер, точный состав кампаний. Отдельно проверять неполные/удалённые SKU.
Ключ в этих артефактах отсутствует. Этот протокол не является выполненной серией.

Для управления ещё нужны общий план квот с другими потребителями, проверка
внешней идентичности кабинета и организации, подтверждение полноты/НДС,
принятый горизонт риска и численный критерий допустимого ущерба. Наблюдаемый
максимальный темп расхода не объявляется верхней границей будущего расхода.


Разбор замечаний и границы итогового пакета: [ревью 00–08](ozon-advertising-00-08-review.md).
После шести принятых замечаний добавлены регрессии: дробное время HTTP, гонка
версии и high-water, отмена чтения при отзыве, строгий nullable-контракт,
сохранение отказа ключа через рестарт. Повторный полный rebuild после изменения

Последующие 10 принятых замечаний и исправления описаны в отчёте ревью.
