# Паттерны

Что мы используем и что сознательно не используем. Живой документ:
меняется вместе с практикой, в отличие от ADR.

Раздел «не используем» существует не для полноты. Модели генерируют код
по большинству примеров в интернете, а большинство примеров — это Symfony 5–6,
Doctrine-магия и React середины десятых. Явный запрет дешевле,
чем повторное объяснение на ревью.

# Backend

## Куда положить код

Сверяться с таблицей, а не решать заново каждый раз.

| Вопрос | Размещение |
|---|---|
| Обрабатывает HTTP? | `Ui/Controller/` |
| Оркестрирует сценарий (несколько шагов, транзакция)? | `Application/` |
| Описывает правило предметной области? | `Domain/Policy` или `Domain/Service` |
| Неизменяемое значение с правилами? | `Domain/ValueObject/` |
| Простое чтение или запись одной сущности? | `Infrastructure/Repository/` |
| Список, отчёт, агрегация? | `Infrastructure/Query/` |
| Общается с внешним API? | `Infrastructure/Api/` |
| Нужен другому модулю? | `Application/Facade/` |
| Нужен всем модулям и не про предметную область? | `Shared/` |
| Консольная команда? | `Ui/Command/` |

Если ответ «и то, и другое» — значит, класс делает две вещи и его надо разделить.

## Синхронно или асинхронно

| Признак | Решение |
|---|---|
| Меньше двух секунд, пользователь ждёт результат | синхронно |
| Больше трёх секунд | асинхронно |
| Обращение к внешнему API | асинхронно, всегда |
| Побочный эффект (письмо, уведомление) | асинхронно |
| Нужен повтор при сбое | асинхронно |
| Цепочка тяжёлых шагов | асинхронно, каждый шаг — отдельное сообщение |

Промежуток две-три секунды — зона решения; при сомнении асинхронно,
потому что синхронный сценарий нельзя повторить при сбое.

## Модификаторы классов

| Модификатор | Для чего |
|---|---|
| `class` | Entity — Doctrine строит proxy наследованием, `final` его ломает |
| `final class` | Action, Controller, Repository, Query, Handler, Facade, Builder |
| `final readonly class` | DTO, Message, сервисы без состояния |
| `enum` | без `final` — перечисления финальны по языку, `final enum` не компилируется |

Правило для Entity проверить на используемой версии Doctrine и зафиксировать
результат здесь: в новых версиях механизм ленивой загрузки мог измениться.

В каждом файле — `declare(strict_types=1)`. Конструктор — `private readonly`,
только конструкторная инъекция.

## Структура кода

**Используем**

- Модульный монолит, слои `Domain` / `Application` / `Infrastructure` / `Ui`.
- Вход в модуль — Facade в `Application`.
- Интерфейс репозитория в `Domain`, реализация в `Infrastructure`.
- `final` по умолчанию, `readonly` где возможно, конструкторная инъекция.

### Когда интерфейс в `Domain` нужен

Интерфейс — не единица переиспользования, а точка, где `Domain`
намеренно перестаёт знать про `Infrastructure`. Заводится, когда
выполняется хотя бы одна из причин:

1. **Есть вторая реализация сейчас.** Не «когда-нибудь сменим Doctrine
   на Mongo» — второй implementer уже существует, не гипотетический.
2. **Тест обязан подменить реализацию дублёром**, потому что настоящая
   недоступна в тестах: внешний API, время, случайность (CLAUDE.md §9 —
   «Обращения к внешним API в тестах запрещены»).
3. **Потребитель — слой `Application`, `Application/Facade` или `Ui`
   без доступа к `Infrastructure`** по `api/deptrac.php`. Прямой `use`
   на класс из `Infrastructure` оттуда — нарушение границы слоя,
   `make deptrac` красный. Эта причина покрывает Repository- и
   Encryptor-интерфейсы даже при единственной реализации и без
   тестового дублёра — сверяться с `deptrac.php`, не решать на глаз:
   слой `Ui`, в отличие от `Application`/`Facade`, в некоторых модулях
   доступ к `Infrastructure` может иметь (синхронное чтение), это тоже
   смотреть в конфиге, а не по аналогии.

Ни одной из причин нет — интерфейс лишний: единственная реализация,
без тестовой подмены, вызывается только оттуда, где `Infrastructure`
и так доступна по Deptrac.

**Не используем**

| Что | Почему |
|---|---|
| Symfony Bundle на каждый модуль | церемония ради церемонии внутри одного приложения |
| Папки `Services`, `Helpers`, `Utils`, `Managers`, `Common` | не про предметную область, притягивают бесхозный код |
| Сеттерная инъекция, service locator, `$container->get()` | скрывает зависимости, ломает статический анализ |
| Статические фасады в стиле Laravel, синглтоны | непроверяемо, неявное глобальное состояние |
| Трейты как способ переиспользования бизнес-логики | наследование под видом композиции; логика уезжает из домена |
| Абстрактные базовые классы «на будущее» | абстракция до второго случая |
| Интерфейс без второго implementer'а, тестового дублёра и Deptrac-границы | абстракция без причины, лишние строки |

## Запись данных

**Используем**

- Doctrine ORM — только для записи.
- Сущность создаётся конструктором или именованным конструктором
  в валидном состоянии. Сеттеров нет там, где есть инвариант.
- Value Object для величин с правилами: `Money`, идентификаторы.
- Собственные Doctrine Type для Value Object.
- Небольшие агрегаты; связи между модулями — по идентификатору, не ассоциацией.
- Таблицы фактов пишутся через DBAL — вставка с обновлением при
  конфликте по естественному ключу. ORM этого не умеет; это не обход
  правила «ORM — только для записи», а его продолжение: правило о том,
  кто инициирует запись, а не о том, есть ли у таблицы Entity-класс.
- Класс Entity есть у каждой таблицы без исключения, включая
  факт-таблицы: он участвует в `migrations:diff`, `schema:validate`
  и в Builder тестов. Отсутствие ORM-записи (`persist()`/`flush()`)
  не означает отсутствие класса — это два независимых вопроса
  (CLAUDE.md §6).

**Не используем**

| Что | Почему |
|---|---|
| `ServiceEntityRepository` и автоподстановка репозитория | магия, которую модели воспроизводят из старых примеров; зависимость не видна |
| `EntityManager` в контроллере или консольной команде | слой `Ui` не должен знать про персистентность |
| Doctrine lifecycle callbacks и listeners с бизнес-логикой | логика срабатывает невидимо, тестируется тяжело, ломается порядком flush |
| Active Record, методы `save()` на сущности | сущность начинает знать про хранилище |
| Каскады на всё подряд | неожиданные удаления; каскад включается точечно и осознанно |
| `ArrayCollection` в публичном API модуля | утечка деталей ORM наружу |
| ORM-ассоциации между модулями | превращает границы модулей в фикцию |

**Оптимистичная блокировка** (ADR-008) — на сущностях, которые правит человек:
себестоимость, планы, учётные данные подключений, справочники.
Версия отдаётся в ответе на чтение и обязательна в запросе на изменение;
конфликт — отдельный код ответа, не молчаливая перезапись.
На таблицах фактов версии нет.

## Чтение данных — ключевое правило

**Все списки читаются SQL-запросом через DBAL и маппятся в readonly DTO.
Гидрация сущностей для отображения запрещена.**

Причина: гидрация тысячи строк создаёт тысячу объектов, кладёт их
в identity map и unit of work, и всё это живёт до конца запроса.
На таблицах фактов это разница между десятками миллисекунд и секундами,
причём деградация нелинейная и проявляется на боевых объёмах,
а не на тестовых.

**Используем**

- DBAL Query Builder или прямой SQL в `Infrastructure` модуля.
- Выборка только нужных колонок, никогда `SELECT *`.
- Результат — `readonly` DTO, собранный явно.
- Агрегации выполняет PostgreSQL, не PHP.
- Любой список имеет лимит; максимум на страницу зафиксирован в конфиге.

**Не используем**

| Что | Почему |
|---|---|
| `findAll()`, `findBy()` для экранов | гидрация всей выборки |
| `->getResult()` с сущностями для списков | то же самое |
| Doctrine `Paginator` поверх ORM-запроса | гидрирует и делает три запроса |
| Сериализация Entity в JSON-ответ | контракт API начинает зависеть от схемы БД |
| Ленивая загрузка внутри цикла | классический N+1, невидимый в коде |
| Фильтрация и сортировка в PHP после выборки | БД делает это на порядки быстрее |
| `SELECT *` в любом виде, включая `select('t.*')` в QueryBuilder | ответ ломается при изменении схемы; тянутся неиспользуемые колонки |

Гидрация сущностей допустима только там, где объект действительно
изменяется: загрузили, изменили, сохранили, обычно одна-две штуки.

## Сценарии и асинхронность

**Используем**

- Команды и запросы как отдельные классы в `Application`.
- Синхронные сценарии вызываются напрямую из `Ui`.
- Асинхронные — сообщения Symfony Messenger.
- Доменные события — внутри модуля, через Messenger.

**Не используем**

| Что | Почему |
|---|---|
| Полноценный CQRS с раздельными базами | решает проблему масштаба, которой нет |
| Event Sourcing | необратимое усложнение ради аудита, который решается журналом |
| Командная шина для синхронных вызовов | косвенность без выгоды; прямой вызов читается лучше |
| Saga / процесс-менеджеры | нет распределённых транзакций, нечего оркестрировать |

## HTTP-слой

**Используем**

- Обычные контроллеры, атрибут `#[Route]`.
- DTO запроса + Symfony Validator.
- Явный DTO ответа.
- Единый формат ошибки: HTTP-статус + код + сообщение.
- OpenAPI-схема генерируется из кода.

**Не используем**

| Что | Почему |
|---|---|
| API Platform | абстракции плохо генерируются моделями и дорого отлаживаются одним человеком |
| Symfony Forms для API | спроектированы под HTML-формы; для JSON избыточны |
| Сериализационные группы на сущностях | контракт API привязывается к модели хранения |
| Аннотации вместо атрибутов | Symfony 5-стиль |
| Роутинг в YAML | маршрут живёт далеко от обработчика |

# Frontend

## Компоненты

**Используем:** функциональные компоненты и хуки. Логика — в хуках,
разметка — в компонентах.

**Не используем**

| Что | Почему |
|---|---|
| Класс-компоненты | устарели с 2019 |
| HOC, render props | заменены хуками; ухудшают типизацию и стек ошибок |
| Разделение Container / Presentational | устарело, роль выполняют хуки |
| `forwardRef` без необходимости | в React 19 ref передаётся пропом |

## Состояние

**Используем**

- Серверные данные — TanStack Query, единственный слой. Кэш, повторные
  попытки, инвалидация — его зона.
- Клиентское состояние — `useState` / `useReducer`; Context только
  для узкого и редко меняющегося (текущая компания).
- URL — источник правды для фильтров, периода, страницы и `companyId`.

**Форма ключа кэша:** `['company', companyId, <модуль>, <сущность>, ...параметры]`.
Собирается только общим хелпером. `companyId` — второй элемент всегда,
включая запросы, которые «и так про одну компанию».

**Безопасные значения по умолчанию в хуках — только для коллекций.**
Пустой массив вместо `undefined` избавляет таблицу от проверок и это полезно.
Для денежных показателей значение по умолчанию запрещено: ноль вместо
«ещё не загрузилось» — не отсутствие данных, а неверная цифра, которой
пользователь поверит. Состояния загрузки, ошибки и пустоты для таких экранов
различаются явно.

**Не используем**

| Что | Почему |
|---|---|
| Redux / MobX / Zustand для серверных данных | дублирует TanStack Query и рассинхронизируется с ним |
| Глобальный стор для «текущей компании» | второй источник правды против URL; ломает две вкладки |
| `useEffect` + `fetch` для загрузки данных | ручные гонки, отсутствие кэша и отмены |
| `localStorage` как кэш данных | переживает смену пользователя на общем компьютере |
| Прокидывание пропсов через пять уровней | либо контекст, либо композиция |

## Списки и таблицы

**Правило: пагинация, сортировка и фильтрация всегда серверные.**
Клиент не получает набор, который сам должен резать.

**Используем:** TanStack Table в headless-режиме — состояние таблицы
без навязанной разметки; виртуализация при количестве строк выше двух сотен.

Подключается вместе с первой клиентской сортировкой/переупорядочиванием
колонок, не раньше: у первой витрины (список продаж Ozon, пакет 6-7
tracer bullet) пагинация и сортировка целиком серверные, headless-модели
управлять нечем — таблица там обычная `<table>`. Не итог отказа
от библиотеки, а применение того же принципа, что и для UI-примитивов
(«третье повторение», не первое).

**Не используем**

| Что | Почему |
|---|---|
| Загрузка всех строк с сортировкой на клиенте | ломается на первом крупном клиенте |
| Готовые «тяжёлые» гриды с собственной моделью данных | тянут стили и логику, конфликтующие с серверной пагинацией |
| Бесконечная прокрутка без курсора | смещение при вставке новых строк, дубли и пропуски |

## Структура и стили

**Используем:** feature-based раскладку; Tailwind; чистые функции
форматирования отдельно от компонентов.

**Границы импортов проверяются линтером**, а не договорённостью
(`import/no-restricted-paths`):

```
shared/     ← не импортирует из features/
features/A  ← не импортирует из features/B; общее уходит в shared/
app/        ← импортирует что угодно; из него не импортирует никто
```

Это фронтендовый аналог Deptrac. Без механической проверки границы
исчезают за пару месяцев.

**Не используем**

| Что | Почему |
|---|---|
| Обязательное деление на «умный» и «глупый» компонент | Container/Presentational под новым именем; роль выполняет хук. Делить по необходимости, а не по правилу |
| Barrel-файлы `index.ts` внутри приложения | циклические импорты, ломают tree-shaking, замедляют сборку. **Исключение — `packages/ui/src/index.ts`:** это публичный вход пакета, его граница. Запрет касается файлов-пересыльщиков внутри `apps/*/src`, а не границы переиспользуемого пакета |
| Atomic Design, полный Feature-Sliced Design | церемония, рассчитанная на команду |
| Runtime CSS-in-JS | стоимость на рендере, лишний слой |
| Арифметика над деньгами в компонентах | считает бэкенд; компонент только форматирует |

# Пагинация

Два режима, выбор не по вкусу, а по природе таблицы.

| | Offset | Keyset (курсор) |
|---|---|---|
| Где | справочники, админские списки, настройки | таблицы фактов и всё, что растёт с объёмом данных клиента |
| Номера страниц | есть | нет, только «дальше» |
| Общее количество | есть | не запрашивается |
| Стоимость глубоких страниц | растёт линейно: БД читает и отбрасывает смещение | постоянная |
| Устойчивость к вставкам | строки съезжают между страницами | устойчиво |

**Правило.** Таблица растёт вместе с объёмом данных клиента — keyset.
Справочник ограниченного размера — offset. Сомнение решается в пользу keyset.

## Контракт списочного эндпоинта

Параметры: `?page=1&limit=50` для offset, `?cursor=...&limit=50` для keyset.

| Параметр | Значение |
|---|---|
| `limit` по умолчанию | 50 |
| `limit` максимум | 200 |
| `limit` свыше максимума | 422, не молчаливое обрезание |
| Запрошенная страница за пределами набора | 422, не 500 и не пустой список |
| Ответ offset | `items`, `total`, `pages`, `page`, `per_page` |
| Ответ keyset | `items`, `next_cursor` (`null` в конце) |

**Query-класс отдаёт `QueryBuilder`, а не массив.** Иначе пагинатор не сможет
построить запрос подсчёта, и правило «все списки постранично» становится
невыполнимым. Собирать результат в массив — задача вызывающего кода.

Эндпоинт, отдающий список без ограничения количества, не выкладывается.
Это касается и внутренних, и служебных ручек.

`COUNT(*)` на таблицах фактов не выполняется. «Страница 5 из 240»
для миллионов строк — это полный проход по индексу ради числа,
на которое никто не смотрит.

Курсор кодирует значения полей сортировки последней строки, а не смещение.
Сортировка обязана быть однозначной: если сортируем по дате,
в ключ добавляется идентификатор строки, иначе строки с одинаковой датой
теряются или дублируются.

Список без лимита не отдаётся никогда, даже внутренний.

# Логирование

Уровень выбирается не по силе ощущений, а по одному критерию:
**требует ли запись действия человека.**

| Уровень | Когда | Пример |
|---|---|---|
| `error` | сломано, нужно чинить | не удалось записать факт, неожиданный ответ БД |
| `warning` | отклонение, которое система обработала сама | площадка ответила 429, повтор через минуту |
| `info` | значимое событие бизнес-процесса | синхронизация завершена, обработано N строк |
| `debug` | подробности для отладки | тело запроса, промежуточные состояния |

**Ответ 4xx клиенту — не инцидент.** Неверные параметры запроса, отсутствующая
сущность, конфликт версий — это `info` или ничего. В `error` они превращают
трекер в шум, а шум означает, что настоящие ошибки перестают замечать.

**Внешний сбой становится `error` только после исчерпания повторов.**
Первая неудача обращения к площадке — `warning`; окончательный отказ
обработчика — `error`.

**В цикле не логировать по записи.** Тысяча строк — одна итоговая запись
с количествами успехов и отказов, а не тысяча сообщений.

**Обязательно в контексте каждой записи:** идентификатор запроса или сообщения
и `company_id`.

**Запрещено логировать:** учётные данные площадок, содержимое кук и заголовков
авторизации, персональные данные. Тело ответа внешнего API — только на `debug`
и только в объёме, нужном для разбора.

# Node-окружение

**Все npm-команды выполняются внутри контейнера** (`node-seller` /
`node-admin` в `docker-compose.yml`), на хосте — запрещены. Причина не
стилистическая: `node_modules` — общий bind-mount между хостом и
контейнером, и запуск `npm install` на хосте перезаписывает нативные
бинарники (`rollup`, `esbuild`, `@tailwindcss/oxide`) под libc хоста.
Ловили дважды: у `apps/admin` `vitest` не стартовал вообще —
`@rollup/rollup-linux-x64-musl` был подменён на `-gnu` после установки
с хоста, при том что контейнер работает на musl (тогда ещё alpine).

**`npm ci`, не `npm install`**, для воспроизводимой установки строго
из `package-lock.json` — `install` тихо допускает дрейф лока.

**Версия образа Node зафиксирована явно** (сейчас `node:24.18.1-bookworm-slim`,
не `latest`, не плавающий мажор `24`).

**glibc (`bookworm-slim`), не alpine.** Экосистема Node вокруг Vite
(`rollup`, `esbuild`, `oxc`, `@tailwindcss/oxide`, браузеры Playwright)
собирается и тестируется прежде всего под glibc; musl — вторичная,
менее обкатанная цель. За выбор alpine уже заплатили дважды (Playwright
на musl не запускается в принципе — не баг конфигурации, апстрим её не
поддерживает; нативный биндинг rollup слетел при рассинхронизации
хост/контейнер). glibc также совпадает с тем, что реально соберёт
production-фронтенд, и с образом `playwright` (`mcr.microsoft.com/playwright`,
тоже Ubuntu/glibc) — один libc на весь фронтенд-тулинг, а не три.

`package-lock.json` обоих приложений содержит поле `libc` (пишет npm >= 11,
которого не было в `node:22-alpine`) — без него npm не знает, какой из
платформенных бинарников ставить, и это не косметика, а причина
падения `admin`.

## Одобрение install-скриптов (npm allow-scripts)

npm 11 по умолчанию не запускает postinstall-скрипты пакетов, ещё не
одобренных явно (сейчас — `esbuild`, `unrs-resolver`; нативные бинарники
собираются/копируются в этом скрипте, без него оба останутся заглушками).
Без действия это только предупреждение — тихо зависит от того, кто и как
запускал install, ровно то, чего требовалось избежать.

**Решение — нативный механизм npm, не сторонний инструмент
(`@lavamoat/allow-scripts` и подобные не нужны):**

- `npm approve-scripts <pkg> --allow-scripts-pin` пишет
  `allowScripts: { "pkg@version": true }` прямо в `package.json` —
  решение закоммичено, не зависит от локального состояния машины,
  разработчика или CI-агента.
- `fsevents` (опциональная macOS-зависимость chokidar/vite, здесь никогда
  не устанавливается — весь npm только в Linux-контейнерах) явно
  запрещена через `npm deny-scripts`: `allowScripts: { "fsevents": false }`.
  Явный отказ вместо тихого пропуска — тот же принцип, что и одобрение.
- `.npmrc` каждого приложения: `strict-allow-scripts=true` — превращает
  предупреждение в отказ `npm ci`/`npm install` для ЛЮБОГО будущего
  пакета с неодобренным install-скриптом. Без этой строки политика
  одобрения ничего не блокирует — установка просто пройдёт с
  предупреждением, которое легко не заметить.
- `package.json`: `"engines": {"npm": ">=11.16.0"}` + `.npmrc`:
  `engine-strict=true` — `allowScripts`/`strict-allow-scripts` появились
  в npm 11.16; без проверки версии на более старом npm вся политика
  молча не действует, а `npm ci` просто выполнит скрипты как раньше.

Решение применяется один раз на новый непроверенный пакет
(`npm approve-scripts` / `npm deny-scripts`), не на каждую установку.

## Контракт API (OpenAPI)

`nelmio/api-doc-bundle` был в `composer.json` с ранней стадии, но не
зарегистрирован: `composer.json` → `extra.symfony.allow-contrib: false`
запрещает Flex применять неофициальные рецепты, а у этого пакета рецепт
контрибный. Поэтому регистрация бундла (`config/bundles.php`)
и `config/packages/nelmio_api_doc.yaml` (заголовок документации,
`path_patterns: ['^/api(?!/doc$)']`, чтобы не попадали служебные роуты
вроде `/_error/{code}`) написаны руками — это конфигурация бундла,
не описание самой схемы. Схему по-прежнему целиком генерирует код:
атрибут `#[OA\Response(content: new Model(type: ...::class))]` на методе
контроллера ссылается на readonly DTO ответа, конкретные поля схемы
выводятся `ObjectModelDescriber` через PropertyInfo (конструкторная
экстракция уже включена в `config/packages/property_info.yaml`).

`make api-doc-export` вызывает `nelmio:apidoc:dump` — консольную
команду, не HTTP-роут: не нужен ни поднятый веб-сервер, ни маршруты
`/api/doc`, `/api/doc.json` (не регистрировались за ненадобностью).

**Запрет ручных типов ответа на фронтенде (CLAUDE.md §10)** проверяется
типизированным ESLint-правилом `local/no-manual-api-response-type`
(`apps/*/eslint-rules/no-manual-api-response-type.js`, дублируется
в обоих приложениях — они независимы, общего кода нет). Правило смотрит
по существу, не по имени: у каждого вызова `apiGet<T>()` (единственная
точка входа API-ответов — прямой `fetch` запрещён везде, кроме
`src/api/`) через TS type checker находит объявление `T` и проверяет,
рукописное ли оно (`interface`, либо `type` с телом-объектом) —
неважно, как `T` называется: `AppInfo`, `PingResult`, `AppInfoDto`
ловятся одинаково. Проходит только тип, ссылающийся на схему
(`type X = components['schemas']['X']` — индексированный доступ,
не собственное описание полей).

Первая версия проверяла по суффиксу имени (`*Response`/`*Dto`) — дырявая
в обе стороны: тип без суффикса проходил, не-API тип с суффиксом ловился
ложно. Заменена по итогам ревью (см. `docs/adr/` не создавался — это не
архитектурное решение, а починка существующего правила).

Правилу нужен TS type checker → `languageOptions.parserOptions.projectService`
включён, но только для `files: ['src/**/*.{ts,tsx}']` — вне `tsconfig.json`
(`include: src`) типизированный парсинг падает на `eslint.config.js`,
`vite.config.ts` и подобных.

Обратная гарантия — `make api-types-check` в `ci-local`, требующий
соответствия закоммиченного `schema.d.ts` файлу, сгенерированному
из кода.

### `overrides` на js-yaml в packages/api-schema

`packages/api-schema/package.json` держит `"overrides": { "js-yaml": "4.3.1" }`.
Это не предпочтение версии, а обход тупика в чужих диапазонах:
CVE-2026-59870 (квадратичное потребление CPU при разборе `!!omap`)
закрыт в `js-yaml@4.3.1`, но `@redocly/openapi-core@1.34.18` пинит
`js-yaml` жёстко на `4.3.0`, линия 1.x на этой версии закончилась
(исправление ушло в 2.x), а `openapi-typescript@7.13.0` — последний
выпущенный — объявляет `^1.34.6` и в 2.x не пойдёт. Внутри объявленных
диапазонов правки не существует, поэтому `npm audit fix` на ней
не срабатывает: он не выходит за диапазоны.

Риск подмены низкий: 4.3.0 → 4.3.1 — патч с бэкпортом того же
исправления, публичный API не менялся. Проверка не на доверии —
`make api-types-check` перегенерирует `schema.d.ts` этим самым
`js-yaml` и требует совпадения с закоммиченным.

**Снять, когда** `openapi-typescript` перейдёт на `@redocly/openapi-core@2.x`:
тогда `overrides` становится ложью о дереве зависимостей и удаляется
вместе с этим абзацем. Проверять при плановом обновлении зависимостей
(`operations-checklist.md`, «Раз в месяц»).

## Playwright — общий конфиг

**Один `playwright.config.ts` в корне репозитория, а не по одному
в каждом приложении.** Сценарии нужны обоим приложениям, а Playwright
покрывает этот случай штатно — через `projects`: у каждого проекта свой
`testDir` (`apps/*/tests/e2e`) и свой `baseURL`. Один прогон, один отчёт,
одна закреплённая версия браузеров.

Отсюда следствия, каждое из которых иначе выглядит необъяснимым:

| Что | Почему так |
|---|---|
| `package.json` в корне — только `@playwright/test` | конфиг в корне резолвит свой импорт по правилам Node: вверх от файла, а не вбок в `node_modules` приложения |
| `working_dir: /var/www` у контейнера `playwright` | без локального `node_modules` рядом `npx` тянет свежий пакет из реестра и обходит файловую систему от `/` |
| в репозиторий смонтирован весь корень, не только `./apps` | `testDir` двух проектов указывают в оба приложения, контейнер должен видеть их из одного корня |
| `outputDir: 'var/playwright'` | артефакты пишутся рядом с конфигом, а не в `apps/*/`, и попадают в уже игнорируемый `var/` — отдельных строк в `.gitignore` и `.dockerignore` не нужно |
| `@playwright/test` объявлен только в корне, в приложениях его нет | одна закреплённая версия на репозиторий; spec-файлы внутри приложений резолвят импорт вверх по дереву — туда же, куда и конфиг |
| `@playwright/test` в `ignoreDependencies`, `playwright` в `ignoreBinaries` (`knip.json` обоих приложений) | из приложения импорт и бинарник выглядят незадекларированными: они объявлены уровнем выше |
| `exclude: ['tests/e2e/**']` в `vite.config.ts` | Vitest иначе подберёт playwright-сценарии как свои и упадёт |

Версия `@playwright/test` совпадает с тегом образа
`mcr.microsoft.com/playwright` в трёх местах — корневой `package.json`,
оба приложения, `docker-compose.yml`. Браузеры предустановлены в образе
под конкретную ревизию; расхождение версий означает докачку браузеров
в рантайме.

Запуск — `make test-e2e` (оба проекта). Один проект отдельно —
`npx playwright test --project=admin`.

## Данные и статусы

**Статус читается без цвета.** Цвет — усиление, а не носитель смысла:
рядом обязателен знак, стрелка или подпись. Причины две и обе
не гипотетические — дальтонизм и чёрно-белая печать отчёта, который
клиент несёт бухгалтеру.

**Отрицательные числа — минус, не скобки.** Скобочная нотация
бухгалтерская, и половина пользователей читает `(300)` как сноску.

**Числа — `tabular-nums`.** Без него цифры в колонке пляшут по ширине,
и глазом не сравнить два значения. Включено глобально для `table`,
`input` и `output`: забыть про частный случай проще, чем вспомнить.

**Цвет статьи затрат закреплён навсегда.** Пользователь запоминает
логистику как бирюзовую; перекраска ломает узнавание отчёта, который
он смотрит каждую неделю. Менять значение `--color-chart-*` — то же
самое, что переименовать статью.

**Базовый размер интерфейса — 14px, не 16.** Продукт про плотность
данных: на экране таблица, а не статья. Задаётся на `body`, а не
на `html`, — иначе поехала бы вся шкала отступов, она в `rem`.

**Все токены публикуются через `@theme static`.** Часть цветов нужна
графикам в runtime, а не Tailwind-классам; обычный `@theme` удалил бы их
из production CSS как неиспользуемые. Светлые значения задаёт тема,
тёмные пары переключаются обычным `prefers-color-scheme`: вложенный
`@theme` Tailwind поднимает в глобальный `:root`.

**IBM Plex Sans поставляется локально через Fontsource.** Внешнего запроса
к Google Fonts нет; браузер загружает только нужные unicode-range и веса.

## Граница примитив / фича

**Примитив не знает предметной области.** У `Button` нет
`variant="save-costs"`; такая кнопка живёт в `features/*/ui`. Как только
примитив начинает знать про себестоимость, он перестаёт быть общим —
и следующая фича скопирует его вместо переиспользования.

**Компонент выделяется на третьем повторении разметки**, не на первом
и не «на будущее». Два раза — совпадение, три — паттерн.

**Экран компонует примитивы, а не пишет цвета и отступы напрямую.**
Отсюда же следует, что примитивы не принимают `className`: разрешив
его, мы разрешили бы экрану переопределять то, ради чего примитив
заводился.

**Длинная строка утилит в экране — признак невыделенного примитива.**
Не повод сократить её произвольным значением, а повод посмотреть,
не третье ли это повторение.

## Запрет произвольных значений

`text-[13px]`, `mt-[7px]`, `bg-[#3a7bd5]`, `w-[calc(100%-2rem)]`,
`[&>div]:flex`, `[mask-type:luminance]` — ошибка линтера
(`local/no-arbitrary-tailwind`, оба приложения).

Это главный способ превратить проект в свалку: через полгода девять
оттенков синего, ни один не назван. Правило проверяет все формы записи
сразу — ловящее `text-[13px]`, но пропускающее `bg-[#fff]`,
обнаружится через полгода на двадцати местах.

Проверяются строковые литералы целиком, а не только атрибут
`className`: словари вариантов в примитивах — обычные константы,
и пропустить их значило бы оставить дыру ровно там, где классов больше
всего.

Осознанное исключение оформляется подавлением с причиной:

```
// eslint-disable-next-line local/no-arbitrary-tailwind -- причина
```

Причина обязательна по договорённости; механической проверки на неё
нет, но без неё исключение неотличимо от забытого подавления.

## Чего в UI Kit нет и почему

| Что | Почему |
|---|---|
| `class-variance-authority` | вариантов у примитива три-четыре, словарь `Record<Variant, string>` даёт ту же типобезопасность пятью строками. Зависимость окупается на десятке компонентов со сложной композицией вариантов, а не на четырёх |
| `tailwind-merge` | нужен, чтобы разрулить `cn("p-2", className)` — но `className` наружу не выставлен. Нет переопределения снаружи — нечего и склеивать. Появится headless-компонент, которому нужен проброс — вернуться к вопросу |
| Storybook | витрина компонентов при четырёх примитивах дороже самих примитивов; эталон уже есть — макет |
| Headless-библиотеки | до первого диалога или выпадающего списка. Тогда же и выбирать, зная требования |
| `Table`, `Dialog`, `Dropdown`, `Select`, `DatePicker`, `Tabs`, `Skeleton` | общий примитив не нужен до третьего продуктового повторения. Первая таблица и её skeleton живут в своей фиче; переносить их в пакет заранее нельзя |

# Сборка образов

## База образов

**PHP — alpine. Node и Playwright — glibc.** Расхождение осознанное,
не недосмотр: у экосистем разная цена musl. Расширения PHP собираются
из исходников под ту libc, что в образе, и проблем с musl не создают;
нативные модули вокруг Vite (`rollup`, `esbuild`, `oxc`,
`@tailwindcss/oxide`) и браузеры Playwright собираются и тестируются
прежде всего под glibc, а под musl ломались дважды — Playwright
на musl не запускается в принципе (`docs/patterns.md`,
«Node-окружение»).

Версия базового образа фиксируется до патча (`php:8.4.24-fpm-alpine`).
Плавающий тег означает, что образ, собранный сегодня и через месяц
из одного коммита, — разные образы; воспроизводимость сборки тогда
держится на времени, а не на содержимом репозитория.

## Один Dockerfile, несколько стадий

`docker/php/Dockerfile`, стадия выбирается через `--target`.

| Стадия | Что добавляет |
|---|---|
| `base` | `pdo_pgsql`, `libpq`, `fcgi`, `WORKDIR` |
| `prod-deps` | composer и `composer install --no-dev`; стадия сборки, в образ не попадает |
| `prod` | код внутри образа, opcache без проверки mtime, прогретый кэш, healthcheck, `www-data` |
| `dev` | pcov, composer, `memory_limit=512M`; код монтируется томом |

**`php.ini` активируется явно, разными пресетами.** Официальный образ
кладёт `php.ini-production` и `php.ini-development` и **не включает
ни один** — без `mv` php работает на встроенных умолчаниях, а они ближе
к development. В prod это две утечки, а не вопрос удобства:
`display_errors=On` отправляет фатальные ошибки и предупреждения
в HTTP-ответ вместе с путями (Symfony ловит исключения, но не то, что
падает до загрузки ядра), а `zend.exception_ignore_args=0` кладёт
аргументы функций в стектрейсы — туда приезжают ключи площадок
и данные компаний.

Файлы `conf.d/zz-*.ini` читаются после `php.ini` и продолжают
перекрывать нужное: в dev `memory_limit=512M` побеждает 128M
из пресета. Проверяется запуском в конвейере, не чтением Dockerfile.

**opcache не устанавливается.** Официальный образ уже собрал его
и включил через `conf.d/docker-php-ext-opcache.ini`; повторный
`docker-php-ext-install opcache` распаковывает исходники PHP и собирает
то же расширение заново — 116 с сборки `base` против 19 с. Стадия `prod`
задаёт только настройки, отдельным ini. Перед добавлением расширения
стоит проверить `php -m` в базовом образе: часть уже там.

**Не два файла.** Два файла означают дублированную базу, которая
разъезжается: расширение добавят в dev и забудут в prod, и разница
вылезет на боевом, где её некому заметить. Здесь общая часть физически
одна — стадия `base`.

**В dev оба сервиса (`php-fpm`, `php-cli`) собирают одну стадию `dev`.**
Разными остаются роли, не образы: один обслуживает FastCGI, другой —
оболочка для инструментов. Отдельная стадия под cli дала бы вторую
сборку и второй кэш ради поднятого лимита памяти в процессе, который
в dev всё равно ничем не ограничен.

## Чего нет в prod-образе

| Что | Почему |
|---|---|
| dev-зависимости Composer | исполнимый код, который никто не проверял на пригодность к проду |
| pcov, xdebug | перехват выполнения: штраф на каждый вызов и лишняя поверхность атаки |
| composer | при компрометации позволяет доустановить в работающий образ что угодно |
| `memory_limit=512M` | поднимали под PHPStan; в проде это снятый предохранитель от утечки |
| `tests/`, `docs/`, `.git`, `var/` | исключены в `.dockerignore` |
| смонтированный том с исходниками | код копируется внутрь: образ обязан быть самодостаточным |

Проверяется не чтением Dockerfile, а шагом конвейера: после публикации
образ запускается и в нём ищутся `composer`, `phpunit`, `phpstan`,
`deptrac` и `pcov`. Опечатка в `--target` собирает последнюю стадию
файла, и образ при этом рабочий — заметить такое чтением трудно.

## Порядок слоёв

```
COPY api/composer.json api/composer.lock ./
RUN composer install --no-dev --no-scripts ...
COPY api/ ./
RUN composer dump-autoload --optimize --classmap-authoritative
```

Манифесты отдельным слоем до кода. Иначе правка одного PHP-файла
инвалидирует установку всех зависимостей, и каждая сборка в конвейере
становится полной.

Проверено: при сброшенном слое зависимостей `composer install`
занимает 5,3 с, при правке PHP-файла помечается `CACHED`.

## Один prod-образ на веб и воркеры

Образ `php-fpm` содержит и бинарь `php`, поэтому воркеры Messenger
поднимаются из него же с переопределённой командой
(`docker-compose.prod.yml`). Два образа означали бы, что код
веб-процесса и воркера может разъехаться; ошибки этого класса —
«в API работает, в фоне нет» — ищутся часами, потому что оба процесса
выглядят исправными.

Долгоживущему процессу нужен `init: true`: без него PID 1 — сам воркер,
а PID 1 не получает действий по умолчанию для сигналов, и SIGTERM
без установленного обработчика просто игнорируется. Docker дождётся
таймаута и убьёт процесс SIGKILL посреди обработки сообщения.

## Периодические задачи — свой цикл, не `symfony/scheduler`

`worker-scheduler` (`docker-compose.prod.yml`) — тот же образ, команда
с `while` + `sleep($interval)` внутри, не `symfony/scheduler`. Пакет
даёт DSL повторяющихся сообщений и переиспользует инфраструктуру
Messenger (`Worker`, обработку сигналов) — оправдан, когда независимых
периодических задач с разным ритмом несколько; для одной задачи это
зависимость и абстракция ради одной точки вызова. Не cron на хосте —
он живёт вне `docker-compose.prod.yml` и вне git, а этот файл
существует именно чтобы топология была записана исполнимо, не прозой.

Условие пересмотра: вторая независимая периодическая задача с другим
ритмом — тогда `symfony/scheduler` окупает себя, а `worker-scheduler`
с самодельным циклом на каждую задачу — дублирование.

## Статика фронтенда — артефакт конвейера, не стадия образа

Собранный фронтенд выкладывается артефактом прогона, а не запекается
в образ. Где его отдавать — nginx рядом с приложением, отдельный образ,
объектное хранилище — решение развёртывания, которое ещё не принято;
запекание в образ приложения выбрало бы за него и заодно связало правку
стиля с пересборкой и перевыкладкой PHP.

Артефакт берётся из задачи `e2e`, которая фронтенд уже собрала: вторая
сборка ради артефакта была бы той же работой второй раз. Номер прогона
общий с тегом образа, поэтому пара «образ — статика» восстанавливается
однозначно.

## Описание prod-окружения

`docker-compose.prod.yml` — не выкладка, а исполнимая запись двух
решений: из какого образа поднимаются веб-процесс и воркер, и как
воркер получает сигнал остановки. Проза расходится с реальностью молча,
compose-файл проверяется запуском. Хостов, реквизитов и секретов
в нём нет — значения приезжают из окружения площадки.

# Конвейер

Один файл — `.github/workflows/ci.yml`. Набор проверок тот же, что
у `make ci-local`; конвейер вызывает те же цели Makefile, а не повторяет
команды. Второе определение того, как запускается PHPStan, разошлось бы
с первым в течение месяца.

## Фильтры по путям

| Изменено | Что запускается |
|---|---|
| `apps/**` | typecheck, ESLint, Prettier, Vitest, knip, сборка |
| `api/**` | PHP-CS-Fixer, PHPStan, Deptrac, structure-check, PHPUnit |
| `packages/api-schema/**` | обе половины — контракт общий |
| `docs/**`, `README` | ничего сверх обязательного |
| `.github/`, `Makefile`, `docker-compose.yml`, `docker/`, `api/migrations/` | всё целиком |

Последняя строка — про то, КАК прогоняются проверки, а не что
проверяется. Фильтровать её нельзя: фильтр судил бы сам о себе.
Отсутствие базы для дифа (новая ветка, переписанная история) означает
полный прогон — «не знаю, что менялось» обязано означать «проверяю всё».

**Вне фильтров, всегда:** `api-types-check`, `composer audit`,
`npm audit`, оба сценария Playwright. Это не осторожность, а условие
допустимости самих фильтров: ломает фронтенд именно правка бэкенда,
и пропуск контрактной проверки обменял бы минуты прогона на ручную
ловлю рассинхронизации.

**Playwright гоняется и на коммите, который трогает только `api`.**
Исходный критерий готовности Stage 4 требовал обратного и противоречил
правилу «всегда»; противоречие разрешено в пользу «всегда».

## Кэш

| Что | Ключ |
|---|---|
| `api/vendor` | `api/composer.lock` |
| `apps/*/node_modules`, `packages/api-schema/node_modules`, корневой `node_modules` | соответствующий `package-lock.json` |
| образ php (`docker save` целиком) | `docker/php/Dockerfile` |
| результат PHPStan (`api/var/phpstan`) | `composer.lock` + `phpstan.neon` + sha, с `restore-keys` |

Ключ строится по содержимому файла блокировки, не по ветке: иначе кэш
не переиспользуется между ветками и смысла в нём нет.

**`npm ci` при попадании пропускается целиком**, а не ускоряется: он
намеренно стирает `node_modules` и ставит заново, поэтому кэш каталога
npm сократил бы установку, но не отменил. Кэшируется сам `node_modules`,
шаг обходится по `cache-hit`. Это безопасно ровно потому, что за
пределы `node_modules` `npm ci` здесь ничего не пишет.

**`composer install` при попадании выполняется всё равно.** Он не
только раскладывает `vendor`, но и выполняет `post-install-cmd` —
`cache:clear` и `assets:install`. Пропуск шага даёт `vendor` без
прогретого `api/var/cache`, и php-fpm отвечает 500 на первом же
запросе: под `www-data` он не может создать каталог кэша в дереве,
принадлежащем хосту. Ошибка выглядит как поломка фронтенда
(«Ошибка: HTTP 500» на стартовом экране), хотя фронтенд исправен.

Отсюда общее правило, стоившее одного красного прогона: **кэш обязан
экономить скачивание, а не отменять установку.** Пропускать шаг можно
только там, где у установки нет побочных действий за пределами
кэшируемого каталога.

**Образ php кэшируется целиком через `docker save`/`docker load`,
не послойно.** Послойный кэш buildx требует стороннего действия
(`docker/setup-buildx-action`) ради того же результата: образ
одностадийный, при попадании по хешу Dockerfile переиспользуется
он весь. Ключ по содержимому Dockerfile, поэтому правка образа
инвалидирует кэш.

PHPStan — единственный кэш с `sha` в ключе и `restore-keys`: запись
происходит каждый прогон, чтение поднимает ближайший предыдущий
результат. С ключом только по `composer.lock` кэш застыл бы на первом
прогоне и с ростом кода перестал бы что-либо ускорять.

## Триггер — только `push`

Без отдельного `pull_request`: форков нет, PR показывает проверку
с прогона своего head-коммита, а два триггера дали бы два прогона
на каждый коммит в ветке с открытым PR.

Существеннее экономии то, что у `push` всегда есть
`github.event.before`, поэтому диф считается одинаково на `master`
и на ветке — в фильтрах одна ветка кода вместо двух.

## Версия сборки

Тег — `<номер прогона>-<короткий хеш>`, например `7-a1b2c3d`. Попадает
в `APP_VERSION` production-образа, оттуда в параметр `app.version`
и в ответ эндпоинта версии; стартовый экран показывает то, что вернул API.

**Отдельной версии внутри бандла фронтенда нет намеренно.** Два
источника ответа на вопрос «что развёрнуто» расходятся молча, и первым
о расхождении узнаёт клиент. Локально `APP_VERSION` остаётся
`0.1.0-dev` в `api/.env` — собранный мимо конвейера образ обязан
отличаться от собранного им, поэтому значение по умолчанию
в стадии `prod` заведомо неправдоподобно (`0.0.0-unbuilt`).

Внутри образа `api/.env` тоже лежит и содержит `0.1.0-dev`, но
выигрывает не он: Symfony Dotenv не перетирает уже заданные переменные
окружения, поэтому `ENV APP_VERSION` из Dockerfile перекрывает файл.

## Что собирает конвейер

Стадию `prod` из `docker/php/Dockerfile` — устройство стадий
и что в prod-образ не попадает, в разделе «Сборка образов».
Ни nginx, ни менеджера процессов в образе нет: это решения
развёртывания, а развёртывание в конвейер не входит.

# Сеть окружения: два имени у одного хоста

**Адреса `*.conwix.localhost` работают только снаружи, из браузера
разработчика.** Внутри docker-сети они недостижимы: по RFC 6761 резолверы
glibc и большинство других жёстко отображают весь домен `.localhost`
в loopback, игнорируя любой DNS, включая docker.

**Для обращений между контейнерами используются `*.conwix.internal`** —
тот же vhost nginx, вторым `server_name`. Браузер и HTTP-клиент выставляют
`Host` сами из URL, обходить ничего не нужно.

Отсюда правило: **любой тест или сервис, ходящий по HTTP внутри сети,
использует `.internal`; `.localhost` — только для человека.**

Что уже пробовали и почему не работает:

| Подход | Почему нет |
|---|---|
| `networks.aliases` с именем `app.conwix.localhost` | резолвер не спрашивает DNS про `.localhost` вообще |
| `baseURL: http://nginx` + переопределение заголовка `Host` | Chromium запрещает менять `Host` при обычной навигации |

# Как менять этот файл

Отказ от паттерна или добавление библиотеки фиксируется здесь
в том же коммите, что и код. Если решение необратимо или дорого
отменяемо — это ADR, а не строчка в таблице.

Запись в разделе «не используем» снимается так же, как ставится:
осознанно и с причиной, а не тем, что кто-то однажды написал иначе.
