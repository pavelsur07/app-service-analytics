# CLAUDE.md

Правила работы с этим репозиторием. Читается агентом перед любой задачей.

---

## Продукт

**Conwix** — SaaS-аналитика для селлеров маркетплейсов (Wildberries, Ozon).
Репозиторий: `app-service-analytics`.
Три функциональных блока: контроль план-факт продаж, анализ юнит-экономики,
анализ остатков товаров.

Данные клиентов — финансовые, клиенты конкурируют между собой.
Утечка данных между компаниями — не баг, а прекращение продукта.

Стадия: pre-PMF, первые клиенты. Команда: один разработчик + LLM-ассистирование.
Оптимизируем скорость доставки и понятность, не масштаб.

### Политика версий фреймворка

Проект живёт на LTS-ветке Symfony. Текущая — 7.4 (выпущена в ноябре 2025,
исправления ошибок до ноября 2028, безопасности — до ноября 2029).

Обновление до следующей LTS (8.4, ожидается в ноябре 2027) планируется
заранее. Условие готовности к переходу — нулевое число предупреждений
об устаревших вызовах. Их накопление обсуждается как технический долг,
а не игнорируется.

Ветка 8.x на текущей стадии не используется: минорные версии живут
восемь месяцев, что означает обязательное обновление каждые полгода.

PHP — 8.4 (активная поддержка до конца 2026, безопасности — до конца 2028).

### Паттерны

Полный список «что используем / что не используем и почему устарело» —
`docs/patterns.md`. **Читать перед написанием кода.** Модели часто выдают
стиль Symfony 5–6 и Doctrine-магию, которых здесь нет.

## Модули

Спроектированы и существуют в коде:

```
Shared        технический слой: Money, Doctrine-типы, UUID, базовые исключения.
              Предметной логики не содержит.
Identity      Company, User, membership, MarketplaceAccount. Источник companyId.
Ingestion     коннекторы к площадкам, raw-слой, расписание, лимиты запросов,
              нормализация в факты.
```

Новый модуль создаётся, когда появляется задача, которую некуда положить,
и решение по нему записано в ADR. Заранее пустые модули не заводятся.

**Зависимости строго вниз.** Ingestion → Identity → Shared.
Обратных вызовов нет ни одного. Межмодульное общение — только через Facade
в `Application`. Прямой импорт чего-либо из чужого модуля мимо Facade
запрещён и проверяется Deptrac.

Карта репозитория — `docs/structure.md`.

## Обязательные правила

### 1. Изоляция арендаторов

Каждый метод репозитория, читающий данные компании, первым параметром
принимает `string $companyId`. Метода без него не существует.
Поиск сущности компании по одному лишь идентификатору запрещён.
Первым столбцом любого составного индекса по данным компании идёт `company_id`.

Контекст компании передаётся явно, не берётся из глобального состояния
и не хранится в сессии. В маршрутах API — `/api/companies/{companyId}/...`.

### 2. Идентификаторы

UUIDv7 через `symfony/uid`, генерация в приложении до вставки.
В PostgreSQL — нативный тип `uuid`. Строковое хранение запрещено.

Таблицы фактов суррогатного ключа не имеют. Первичный ключ естественный:
`(company_id, marketplace_account_id, source_row_id)`. Хэш содержимого строки
в первичный ключ НЕ входит — он является колонкой-детектором изменений.
Подробнее — ADR-006.

### 3. Деньги

Денежные величины представлены Value Object `Money` = сумма в минорных
единицах + код валюты ISO 4217. Валюта обязательна, умолчания нет.
Хранение — `bigint` через собственный Doctrine Type; код валюты —
отдельная колонка `char(3)`, одна на строку факта.
Конструктор не принимает `float`. Тип с плавающей точкой в денежных
вычислениях запрещён линтером, включая промежуточные значения.
Операция между величинами разных валют завершается исключением;
молчаливое приведение по курсу запрещено.

Деление денег выполняется только через аллокацию с распределением остатка;
правило округления указывается явно, значения по умолчанию нет.
Сторонняя библиотека денег не появляется в сигнатурах домена — только внутри `Money`.

### 4. Идемпотентность

Каждый обработчик очереди идемпотентен: повторный запуск на тех же входных
данных не меняет результат.

Защита строится на уникальном индексе в БД с перехватом конфликта на вставке.
Проверка существования перед вставкой защитой не является: между проверкой
и вставкой два параллельных воркера пройдут её оба. Конструкция
«найти, и если не найдено — записать» запрещена во всех видах,
включая вынесенную в трейт или базовый класс.

Где у результата есть естественный ключ — а у всех фактов он есть —
идемпотентность обеспечивается уникальным индексом на самих данных.
Отдельная таблица обработанных сообщений для этого не нужна.

Она нужна только обработчикам, не оставляющим следа в данных (отправка
письма, вызов внешнего API). Тогда: уникальный индекс на идентификаторе
сообщения, отметка ставится ДО обработки в той же транзакции, повторная
вставка перехватывается как конфликт и приводит к выходу.

Идемпотентность не равна неизменности: данные площадок меняются задним
числом. Повторная загрузка изменившейся строки обновляет её, а не создаёт
вторую. Правила — в ADR-006.

### 5. Чтение списков

Любой список читается SQL-запросом через DBAL и маппится в `readonly` DTO.
Гидрация сущностей для отображения запрещена: `findAll`, `findBy`
и `getResult` с сущностями для экранов не применяются.

Выбираются только нужные колонки. Агрегации делает PostgreSQL.
Список без лимита не отдаётся никогда.

Пагинация: keyset для таблиц, растущих с объёмом данных клиента;
offset — только для справочников ограниченного размера.
`COUNT(*)` на таблицах фактов не выполняется.
Лимит по умолчанию 50, максимум 200, превышение — ответ 422.
Query-класс отдаёт `QueryBuilder`, а не массив.

Подробнее — `docs/patterns.md`.

### 6. Запись данных

Любое новое поле-ссылка на сущность другого модуля получает индекс
в той же миграции. Если фильтрация всегда идёт вместе с компанией —
составной индекс, `company_id` первым столбцом.

Пакетная обработка сбрасывает изменения порциями по ходу цикла,
а не одним вызовом в конце: иначе память растёт линейно объёму пакета.

Запросы в цикле запрещены. Связанные данные загружаются одним запросом
по списку идентификаторов.

### 7. Кэш на фронтенде

Ключ запроса к данным компании формируется только через общий хелпер.
Форма: `['company', companyId, <модуль>, <сущность>, ...параметры]`.
Литеральные массивы в качестве ключа запрещены.

Без этого при переключении компании клиент отдаст данные предыдущей
из кэша — бэкенд при этом отработает правильно.

### 8. Почта

Отправка только через Symfony Mailer. Прямые SMTP-вызовы запрещены.

### 9. Тесты backend

Разделение на unit / integration / functional с раздельным запуском.
Уровень определяется зависимостями: нужна БД — не unit.

Подготовка данных — только через Builder соответствующей сущности.
Глобальные фикстуры запрещены. Builder создаётся в том же изменении,
что и сущность, не содержит бизнес-логики и не вычисляет значения,
которые проверяет тест. Builder неизменяем: каждый метод возвращает
новый экземпляр.

Обращения к внешним API в тестах запрещены; парсеры проверяются
на зафиксированных фикстурах ответов.

**Обязательное покрытие:**
- денежная арифметика и аллокация расходов;
- идемпотентность каждого обработчика очереди;
- изоляция данных между компаниями.

CRUD, контроллеры, рендер — не тестировать.

### 10. Тесты и проверки frontend

TypeScript `strict` со всеми флагами, включая `noUncheckedIndexedAccess`.
`any` запрещён на уровне ошибки линтера.

Типы ответов API импортируются только из сгенерированной схемы;
ручное описание типов ответов запрещено.

Сетевые запросы — только через клиент, привязанный к компании;
прямые вызовы `fetch` и `axios` запрещены.

`localStorage` используется только для ключей из разрешённого списка.
Арифметика над денежными величинами в компонентах запрещена.

**Обязательное покрытие:**
- чистые функции форматирования и вычислений;
- изоляция кэша при смене компании;
- разбор ошибок API.

Тесты идут через мок-сервер, отвечающий по схеме OpenAPI.
Один сквозной сценарий Playwright: вход, выбор компании, просмотр данных,
переключение компании.

## Проверки CI

Все блокируют merge. Проверка, которую можно проигнорировать, — не проверка.

**Backend:** PHPStan level 9 (+ phpstan-doctrine, strict-rules), PHP-CS-Fixer,
Deptrac, PHPUnit, синхронность OpenAPI-схемы.

**Frontend:** `tsc --noEmit`, ESLint, Prettier, Vitest, синхронность
сгенерированных типов, проверка неиспользуемого кода, порог размера бандла.

**Обе половины:** проверка зависимостей на известные уязвимости
(`composer audit`, `npm audit`). Версии зафиксированы, но не заморожены:
обновление зависимостей — плановая работа, а не реакция на инцидент.

Baseline PHPStan пустой. Добавление подавления — сигнал, что правило
перестало работать; обсуждается, а не делается молча.

## Работа с данными маркетплейсов

Полностью — в ADR-006. Ключевое:

**Данные меняются задним числом.** Площадки перевыпускают отчёты,
доначисляют комиссии и возвраты через недели, иногда в пределах квартала.
Отсюда — немутируемый raw-слой, обновление факта вместо вставки второй
строки, скользящее окно пересчёта и периодический глубокий рескан.

**Битемпоральность.** Каждая факт-строка знает бизнес-дату (когда событие
произошло), время первой загрузки и время последнего обновления.

**Бизнес-дата — в часовом поясе площадки**, задаётся конфигурацией
коннектора, не выводится из данных.

**Прослеживаемость.** Каждая строка факта ссылается на raw-документ,
из которого получена её текущая версия.

**Объяснимость расчёта.** Клиент сверяет цифру с отчётом площадки.
Результат расчёта хранится с разложением по компонентам и с указанием
применённого метода учёта себестоимости и правила аллокации.

Лимиты запросов к API — на уровне подключения, не глобальные.

## Миграции и изменения схемы

Миграции — единственный необратимый шаг повседневного цикла.
Всегда человеческое ревью, никогда автоматическое применение без него.

На таблицах фактов действует правило совместимых изменений:
сначала добавить новое, наполнить, переключить чтение, только потом
удалить старое. Изменение или удаление колонки одним шагом на таблице
с миллионами строк блокирует запись и останавливает продукт.

Каждая миграция прогоняется на копии боевых данных до применения.

## Безопасность и аудит

Учётные данные площадок шифруются; мастер-ключ — в секретах окружения.
Подробнее — ADR-007.

Аудит-журнал обязателен для: изменения себестоимости, изменения планов,
добавления и изменения учётных данных подключений, входа администратора
в данные клиента.

Подключение имеет состояние `active` / `broken` / `revoked`.
Ответ площадки об отсутствии авторизации переводит в `broken`
и порождает уведомление клиенту. Молчаливая остановка синхронизации
запрещена.

## Наблюдаемость

Ошибки — в трекер. Отдельно от ошибок обязателен контроль свежести данных:
отсутствие новых фактов по активному подключению дольше суток порождает
оповещение. Это не техническая метрика, а основное обещание продукта:
устаревшие данные выглядят как рабочие и не вызывают исключений.

В логах — идентификатор запроса и `company_id`. Обращение вида
«не сходится за 15 июля» должно превращаться в один запрос по логам.

## Процесс работы над задачей

Три инструмента ревью — Claude Code, Codex CLI, Kimi CLI — установлены
на одной машине. Внешний ревьюер не видит правил этого файла и добросовестно
предложит то, что здесь отвергнуто: API Platform, `findAll()`, Redux для
серверного состояния, Symfony Forms, глобальные фикстуры. Поэтому на ревью
уходит не только диф, а диф вместе с выдержкой правил и релевантными ADR,
и заранее задано правило принятия замечаний.

### Цикл работы

```
1. Разбор       — CLAUDE.md, релевантные ADR, docs/patterns.md
2. План         — что меняем, какие файлы, критерий готовности
3. STOP?        — если сработало условие остановки, спросить и ждать
4. Реализация   — код + тесты в одном изменении
5. Самопроверка — по чеклисту ниже
6. Внешнее ревью — если задача попадает под порог риска
7. Разбор замечаний — принять / отклонить с причиной
8. Повтор 4–7 до отсутствия принятых замечаний
9. Отчёт        — что сделано, что отклонено и почему, чем проверять
```

Задача не закрывается с невыполненным принятым замечанием.

### Когда остановиться и спросить

Не писать код, а задать вопрос, если задача требует:

- изменения схемы БД на таблицах фактов (партиционирование, ключи, индексы);
- новой миграции любого рода;
- нового межмодульного взаимодействия или Facade;
- новой внешней зависимости — установка пакета без согласования запрещена
  и на бэкенде, и на фронтенде;
- изменения конфигурации очереди, транспортов или маршрутизации сообщений;
- изменения контракта API, уже используемого фронтендом;
- обхода любого из правил выше;
- решения, которое противоречит принятому ADR;
- расширения объёма задачи за пределы поставленного.

Миграции БД — единственный необратимый шаг повседневного цикла.
Всегда человеческое ревью, никогда автоматически. `merge` и принудительная
перезапись истории — тоже никогда автономно.

### Порог внешнего ревью

Два ревью на каждый коммит избыточны по времени и вниманию.
Порог задаётся риском изменения.

| Что затронуто | Ревью |
|---|---|
| Миграции и схема данных | оба |
| Денежная арифметика, аллокация, округления | оба |
| Аутентификация, секреты, изоляция арендаторов | оба |
| Ingestion: идентификация фактов, идемпотентность, пересчёт | оба |
| Контракт API | один |
| Новый сценарий или обработчик без перечисленного выше | один |
| Конфигурация, стили, тексты, документация | не требуется |

При сомнении — на ступень выше.

### Пакет для ревьюера

Собирается `make review-prepare` (цели Makefile — Stage 3) по шаблону
`docs/review-package-template.md`:

1. Постановка задачи одним абзацем.
2. Диф изменений.
3. Раздел «Обязательные правила» из этого файла целиком.
4. Тексты ADR, относящихся к затронутой области.
5. Явная просьба: проверять соответствие приложенным правилам, а не
   предлагать общепринятые альтернативы; при несогласии с самим правилом —
   сказать об этом отдельным пунктом, а не оформлять как дефект кода.

Ревьюер не запускает тесты и не собирает проект — его задача читать.
Прогон проверок — работа Makefile и конвейера.

### Разбор замечаний

| Замечание | Действие |
|---|---|
| Указывает на нарушение записанного правила | принять, исправить |
| Указывает на реальный дефект — ошибка, гонка, утечка, N+1 | принять, исправить |
| Предлагает альтернативу, отвергнутую в ADR | отклонить со ссылкой на ADR |
| Вкусовое: стиль, именование, «я бы сделал иначе» | отклонить с одной строкой причины |
| Указывает на пробел в самих правилах | не исправлять код молча — вынести отдельно |

Расхождение между ревьюерами разрешается соответствием ADR, а не
большинством голосов: два инструмента — не голосование, их ценность в том,
что они ошибаются по-разному. Замечание о пробеле в правилах ценнее
найденной опечатки — оно чинит не одно изменение, а все будущие; такие
случаи превращаются в правку `docs/patterns.md` или новый ADR.

### Финальная самопроверка

Порядок фиксированный, первый пункт всегда первый.

```
1.  Каждый метод репозитория принимает companyId; поиска по одному id нет
2.  Ключ кэша на фронтенде содержит companyId
3.  Списки читаются через DBAL, сущности для отображения не гидрируются
4.  Ни один список не отдаётся без ограничения количества
5.  Деньги — Money с валютой; float в денежных вычислениях нет
6.  Обработчик очереди идемпотентен через уникальный индекс,
    конструкции «найти, и если нет — записать» нет
7.  Новое поле-ссылка получило индекс в той же миграции
8.  Запросов в цикле нет
9.  Тесты написаны в том же изменении; обязательное покрытие соблюдено
10. Границы модулей не нарушены — Deptrac зелёный
11. Отладочный вывод, закомментированный код, TODO без задачи — отсутствуют
12. Документация обновлена: structure.md при изменении структуры,
    patterns.md при изменении паттерна или зависимости
```

Красный пункт означает, что задача не закончена: исправить и пройти
чеклист заново, а не отметить и объяснить.

### Отчёт по задаче

```
Задача:    одно предложение
Сделано:   список изменений по существу
Файлы:     затронутые пути
Ревью:     кто ревьюил, сколько замечаний принято
Отклонено: замечание → причина
Проверка:  команды, которыми ревьюер может убедиться
Открыто:   что осталось и почему
```

**Не входит в процесс:** этапный конвейер с гейтами выкладки (оправдан
на большой команде с владельцем, который неделями не смотрит в код; здесь —
церемония); внешнее ревью как блокирующая проверка в CI (ответ модели
недетерминирован, ставить на нём гейт сборки нельзя); автоматическое
применение замечаний без разбора.

## Принципы

**Скучные технологии.** Меньше компонентов, шире распространённость,
больше примеров. Экзотика — это выдуманные API при генерации и
отсутствие ответов при отладке.

**Не абстрагировать до второго случая.** Абстракция коннектора площадки
пишется после второго коннектора, не до первого.

**Тонкая полоска насквозь.** Новая функциональность доводится до экрана
на одном узком случае, потом расширяется вширь.

**Обратимость важнее оптимальности.** Для необратимых решений (схема БД,
модель арендатора, идентификаторы, деньги) — думать долго и записывать ADR.
Для обратимых — делать и переделывать.

## Документация: что где лежит

| Файл | Что содержит | Изменяемость |
|---|---|---|
| `CLAUDE.md` | правила и ссылки, точка входа для агента | по мере накопления правил |
| `docs/adr/` | необратимые решения с альтернативами и издержками | принятый ADR не редактируется |
| `docs/structure.md` | карта репозитория, назначение папок | живой документ |
| `docs/patterns.md` | используемые и отвергнутые паттерны, библиотеки | живой документ |
| `docs/operations-checklist.md` | эксплуатация, что проверять и когда | живой документ |
| `docs/review-package-template.md` | шаблон пакета для внешнего ревью | живой документ |

**Правило отнесения.** Решение необратимо или дорого отменяемо
(схема данных, границы модулей, контракт API, технология, которую нельзя
убрать за день) — ADR. Решение о том, как мы пишем код сегодня, —
`patterns.md`. Где лежит файл — `structure.md`. Всё, что нужно агенту
в каждой задаче, — `CLAUDE.md`.

При изменении структуры папок обновляется `structure.md` в том же коммите.
При отказе от паттерна или добавлении библиотеки — `patterns.md`
в том же коммите.

## Решения

Принятые архитектурные решения — в `docs/adr/`. Перед изменением,
затрагивающим схему данных, границы модулей или контракт API,
прочитать релевантный ADR.

| | |
|---|---|
| ADR-001 | Выбор технологического стека |
| ADR-002 | Модель владения: пользователь, компания, магазин |
| ADR-003 | Стратегия генерации идентификаторов |
| ADR-004 | Представление денежных величин |
| ADR-005 | Стратегия тестирования и подготовка данных |
| ADR-006 | Ingestion: сырьё, идентификация фактов, пересчёт |
| ADR-007 | Аутентификация, секреты и жизненный цикл подключений |
| ADR-008 | Конкурентное редактирование |
