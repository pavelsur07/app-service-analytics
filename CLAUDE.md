Правила работы с этим репозиторием. Перед любой задачей читать вместе с

## Продукт

**Conwix** — SaaS-аналитика для селлеров маркетплейсов (Wildberries, Ozon).
Репозиторий: `app-service-analytics`.
Три функциональных блока: контроль план-факт продаж, анализ юнит-экономики,
анализ остатков товаров.

Данные клиентов — финансовые, клиенты конкурируют между собой.
Утечка данных между компаниями — не баг, а прекращение продукта.

Стадия: pre-PMF, первые клиенты. Команда: один разработчик + LLM-ассистирование.
Оптимизируем скорость доставки и понятность, не масштаб.

### Политика версий фреймворка

Проект живёт на LTS-ветке Symfony. Текущая — 7.4 (выпущена в ноябре 2025,
исправления ошибок до ноября 2028, безопасности — до ноября 2029).

Обновление до следующей LTS (8.4, ожидается в ноябре 2027) планируется
заранее. Условие готовности к переходу — нулевое число предупреждений
об устаревших вызовах. Их накопление обсуждается как технический долг,
а не игнорируется.

Ветка 8.x на текущей стадии не используется: минорные версии живут
восемь месяцев, что означает обязательное обновление каждые полгода.

PHP — 8.4 (активная поддержка до конца 2026, безопасности — до конца 2028).

## Модули

Спроектированы и существуют в коде:

```
Shared        технический слой: Money, Doctrine-типы, UUID, базовые исключения.
              Предметной логики не содержит.
Identity      Company, User, CompanyMember (членство, ADR-002), MarketplaceAccount.
              Источник companyId.
Ingestion     коннекторы к площадкам, raw-слой, расписание, лимиты запросов,
              нормализация в факты.
PriceMonitoring  список отслеживаемых артикулов и наблюдения цены,
              снятые расширением с карточки Ozon (ADR-014). Не коннектор:
              данные приносит клиент, мы их не забираем у площадки.
Links         короткие ссылки для собственных кампаний и сырые события
              переходов; публичный redirect остаётся частью монолита (ADR-022).
```

Новый модуль создаётся, когда появляется задача, которую некуда положить,
и решение по нему записано в ADR. Заранее пустые модули не заводятся.

**Зависимости строго вниз.** Ingestion → Identity → Shared;
PriceMonitoring → Identity → Shared; Links → Identity → Shared.
PriceMonitoring читает Ingestion
только через его Facade и только на чтение экрана СПП (ADR-016);
обратного вызова нет. Обратных вызовов нет ни одного. Межмодульное общение — только через Facade
в `Application`. Прямой импорт чего-либо из чужого модуля мимо Facade
запрещён и проверяется Deptrac.

Карта репозитория — `docs/structure.md`.

## Обязательные правила

### 1. Изоляция арендаторов

Каждый метод репозитория, читающий данные компании, первым параметром
принимает `string $companyId`. Метода без него не существует.
Поиск сущности компании по одному лишь идентификатору запрещён.
Первым столбцом любого составного индекса по данным компании идёт `company_id`.

Контекст компании передаётся явно, не берётся из глобального состояния
и не хранится в сессии. В маршрутах API — `/api/companies/{companyId}/...`.

**Префикс контура** перед `companies/{companyId}` допустим, когда клиент
предъявляет не сессию, а собственные учётные данные и живёт на отдельном
firewall: `/api/extension/companies/{companyId}/...` (ADR-010). Значимо
здесь не расположение сегментов, а то, что `companyId` остаётся в пути —
проверка членства ищет его в атрибутах маршрута и от префикса не зависит.

Префикс не заводится ради группировки по смыслу («отчёты», «настройки») —
только под отдельный контур аутентификации, и тогда он обязывает:
у контура своя проверка области действия предъявленных учётных данных.
Одного членства мало — участник двух компаний пройдёт его для обеих,
и токен, выпущенный на первую, читал бы вторую
(`ExtensionTokenScopeSubscriber`).

**Исключение — межарендаторное чтение** ровно в трёх случаях:
**операционные системные задачи** (планировщик, онбординг),
**аутентификационная граница** (поиск учётных данных по предъявленному
секрету и явно описанный pre-auth lifecycle) и **системный контур**
(раздел Admin, ADR-017: управляет сервисом целиком, компании у его
экранов нет по построению).
Пользовательские сценарии за пределами этих трёх — нет.

Условия все разом: чтение называется так, что его межарендаторная
природа видна из имени (`findByEmail`, `ActiveOzonAccountsQuery`,
`AllCompaniesForAdminQuery`, не `findAll`/`list`); класс/метод ссылается
на этот пункт правил в докблоке; граница проверяется Deptrac явно,
не общим доступом слоя — у широкого `*Infrastructure`-слоя есть
исключение через `mustNot`, а узкий слой дают только тому, кому он
действительно нужен.

Кому именно «нужен» — зависит от случая, и это единственное, чем третий
случай отличается от первых двух:

- операционная задача и проверка предъявленных учётных данных выполняются
  **мимо контроллера** (планировщик, слой безопасности), поэтому `*Ui`
  их узкого слоя не видит ни при каких обстоятельствах;
- операция pre-auth lifecycle может войти через публичный контроллер
  только когда отдельный ADR называет endpoint и доказывает, почему
  обычная security-граница неприменима. Такой endpoint не читает и не
  возвращает данные компании: он либо подтверждает предъявленный
  одноразовый секрет, либо выполняет нейтральный побочный эффект для
  введённого адреса. Запрос и контроллер выносятся из широких слоёв
  в две точные class-level границы Deptrac; грант получает только эта
  пара. Первый такой случай — confirm/resend email в ADR-021;
- системный контур читает **из контроллера** — иначе экрана не будет
  вовсе. Поэтому узкий слой выдаётся и на стороне Ui: контроллер
  выносится из широкого `*Ui` через `mustNot` в собственный слой
  (`IdentityAdminAccountsUi`), и грант получает он один. Ui продавца
  запроса по-прежнему не видит, и это проверяется Deptrac, а не
  договорённостью.

**Узкий слой — на класс, а не на контур.** «Все контроллеры админки» —
не узкий слой: межарендаторное чтение нужно одному экрану, остальным
admin-контроллерам оно не нужно и выдаваться не должно.

**Аутентификационная граница** выделена отдельно, потому что происходит
внутри обработки пользовательского запроса — но до контроллера и мимо
него, в слое безопасности. Проверить предъявленный секрет, не найдя его
сначала по всем компаниям, физически невозможно: компанию сообщает сама
найденная строка.

Признак, отделяющий обычную проверку учётных данных от «мне неудобно
передавать companyId»: **результатом чтения является сам `companyId`**.
Код, который компанию уже знает, этим путём ходить не имеет права,
и Deptrac закрывает его так же строго, как для операционных задач.
Примеры: `UserRepository::findByEmail` (вход),
`ExtensionTokenByHashQuery` (токен расширения, ADR-010).

Pre-auth lifecycle из предыдущего пункта уже обычной
аутентификационной границы: результат не может содержать данные компании.
Подтверждение по секрету может только открыть сессию найденному
пользователю, а lookup по адресу — только отправить одинаково выглядящее
письмо. Сам адрес никогда не даёт доступ к аккаунту или данным.

Метод репозитория (интерфейс со `companyId` в остальных методах
без исключений) годится только когда сущность структурно не имеет
`companyId` (`UserRepository::findByEmail` — User, поиск до выбора
компании); если сущность компанию имеет — отдельный DBAL-запрос вне
репозитория (`ActiveOzonAccountsQuery` — планировщик синхронизации;
`ExtensionTokenByHashQuery` — проверка токена; тот же приём,
что у `UserCompaniesQuery`), не метод, снимающий скоуп с уже
company-scoped интерфейса.

Для системного контура вопрос не возникает: `Company` компанию
не «имеет», она ею и является, а читает её отдельный запрос
(`AllCompaniesForAdminQuery`) — в `CompanyRepository` метода поиска
по одному лишь идентификатору по-прежнему нет.

**Индекс следует за запросом, а не за таблицей.** Требование
`company_id` первым столбцом написано для чтений, у которых компания
есть, — то есть для всех, кроме перечисленных исключений. У разрешённого
межарендаторного чтения компании нет по определению, и ведущим столбцом
там стоит то, по чему идёт отбор: диапазон времени у контроля свежести
(`idx_marketplace_raw_document_received_at`), состояние подключения
у планировщика. Индекс с `company_id` впереди такой запрос не ускоряет,
а заставляет читать таблицу целиком — то есть исполняет букву правила,
ломая то, ради чего оно написано.

Проверка та же, что и для самого чтения: ведущий столбец не `company_id`
допустим ровно там, где Deptrac держит запрос в узком слое и его
межарендаторная природа видна из имени. В остальных случаях —
`company_id` первым, без обсуждения.

### 2. Идентификаторы

UUIDv7 через `symfony/uid`, генерация в приложении до вставки.
В PostgreSQL — нативный тип `uuid`. Строковое хранение запрещено.

Таблицы фактов суррогатного ключа не имеют. Первичный ключ естественный:
`(company_id, marketplace_account_id, source_row_id)`. Хэш содержимого строки
в первичный ключ НЕ входит — он является колонкой-детектором изменений.
Подробнее — ADR-006.

### 3. Деньги

Денежные величины представлены Value Object `Money` = сумма в минорных
единицах + код валюты ISO 4217. Валюта обязательна, умолчания нет.
Хранение — `bigint` через собственный Doctrine Type; код валюты —
отдельная колонка `char(3)`, одна на строку факта.
Конструктор не принимает `float`. Тип с плавающей точкой в денежных
вычислениях запрещён линтером, включая промежуточные значения.
Операция между величинами разных валют завершается исключением;
молчаливое приведение по курсу запрещено.

Деление денег выполняется только через аллокацию с распределением остатка;
правило округления указывается явно, значения по умолчанию нет.
Сторонняя библиотека денег не появляется в сигнатурах домена — только внутри `Money`.

### 4. Идемпотентность

Каждый обработчик очереди идемпотентен: повторный запуск на тех же входных
данных не меняет результат.

Защита строится на уникальном индексе в БД с перехватом конфликта на вставке.
Проверка существования перед вставкой защитой не является: между проверкой
и вставкой два параллельных воркера пройдут её оба. Конструкция
«найти, и если не найдено — записать» запрещена во всех видах,
включая вынесенную в трейт или базовый класс.

Где у результата есть естественный ключ — а у всех фактов он есть —
идемпотентность обеспечивается уникальным индексом на самих данных.
Отдельная таблица обработанных сообщений для этого не нужна.

Она нужна только обработчикам, не оставляющим следа в данных (отправка
письма, вызов внешнего API). Тогда: уникальный индекс на идентификаторе
сообщения, отметка ставится ДО обработки в той же транзакции, повторная
вставка перехватывается как конфликт и приводит к выходу.

Идемпотентность не равна неизменности: данные площадок меняются задним
числом. Повторная загрузка изменившейся строки обновляет её, а не создаёт
вторую. Правила — в ADR-006.

### 5. Чтение списков

Любой список читается SQL-запросом через DBAL и маппится в `readonly` DTO.
Гидрация сущностей для отображения запрещена: `findAll`, `findBy`
и `getResult` с сущностями для экранов не применяются.

Выбираются только нужные колонки. Агрегации делает PostgreSQL.
Список без лимита не отдаётся никогда.

Пагинация: keyset для таблиц, растущих с объёмом данных клиента;
offset — только для справочников ограниченного размера.
`COUNT(*)` на таблицах фактов не выполняется.
Лимит по умолчанию 50, максимум 200, превышение — ответ 422.
Query-класс отдаёт `QueryBuilder`, а не массив.

Подробнее — `docs/patterns.md`.

### 6. Запись данных

Два независимых вопроса, которые раньше отвечали одним «да» или «нет»
на оба сразу — и путались: кто пишет таблицу через ORM, и существует
ли для неё класс Entity. Ответ на первый не определяет ответ на второй.

**Кто пишет.** Doctrine ORM делает `persist()`/`flush()` только над
данными, редактируемыми человеком: справочники, учётные данные
подключений (например, `MarketplaceAccount`), себестоимость, планы.
**Факт-таблицы (например, `sales_fact`) ORM никогда не пишет — запись
идёт через DBAL, вставкой с обновлением при конфликте по естественному
ключу.** ORM этого не умеет, и SQL здесь не обход правила «ORM только
для записи», а его продолжение — правило о том, кто инициирует запись,
не о том, есть ли модель.

**Есть ли класс Entity — да, у каждой таблицы без исключения, включая
факт-таблицы.** Отсутствие ORM-записи не отменяет класс: он участвует
в `migrations:diff`, `schema:validate` и в Builder тестов — Doctrine
просто никогда не вызывает для него `persist()`. Модификатор — как
у любого Entity: `class`, не `final` («Модификаторы классов»),
исключений для фактов нет. Ссылочные поля на Entity другого модуля
(`listing_id` и подобные) — scalar-поля без `#[ManyToOne]`: связь
по идентификатору, не Doctrine-ассоциация.

Отсутствие ORM-записи у факт-Entity — не хардкод и не пропущенная
модель. Структура записи (`INSERT ... ON CONFLICT` по естественному
ключу) обязательна и проверяется так же строго, как если бы запись
шла через ORM: ключ и правило обновления при конфликте — часть контракта
таблицы, а не деталь одного обработчика.

Любое новое поле-ссылка на сущность другого модуля получает индекс
в той же миграции. Если фильтрация всегда идёт вместе с компанией —
составной индекс, `company_id` первым столбцом.

Пакетная обработка сбрасывает изменения порциями по ходу цикла,
а не одним вызовом в конце: иначе память растёт линейно объёму пакета.

Запросы в цикле запрещены. Связанные данные загружаются одним запросом
по списку идентификаторов.

### 7. Кэш на фронтенде

Ключ запроса к данным компании формируется только через общий хелпер.
Форма: `['company', companyId, <модуль>, <сущность>, ...параметры]`.
Литеральные массивы в качестве ключа запрещены.

Без этого при переключении компании клиент отдаст данные предыдущей
из кэша — бэкенд при этом отработает правильно.

### 8. Почта

Отправка только через Symfony Mailer. Прямые SMTP-вызовы запрещены.

### 9. Тесты backend

Разделение на unit / integration / functional с раздельным запуском.
Уровень определяется зависимостями: нужна БД — не unit.

Подготовка данных — только через Builder соответствующей сущности.
Глобальные фикстуры запрещены. Builder создаётся в том же изменении,
что и сущность, не содержит бизнес-логики и не вычисляет значения,
которые проверяет тест. Builder неизменяем: каждый метод возвращает
новый экземпляр.

Обращения к внешним API в тестах запрещены; парсеры проверяются
на зафиксированных фикстурах ответов.

**Фикстура — побайтовый ответ боевого кабинета, и это решение,
а не недосмотр.** В репозитории лежат настоящие суммы, артикулы, номера
отправлений и города доставки первого клиента. Обезличивание отвергнуто:
ценность фикстуры в том, что её форма настоящая, а подменённые значения
прячут ровно те дефекты, ради которых фикстура и снята — приведение
типов, знаки, точность, пустые поля. Репозиторий приватный, и данные
в нём — данные того же продавца, который ими и владеет.

**Диф уезжает внешнему ревьюеру целиком**, включая фикстуры. Это входит
в то же решение и принимается сознательно: пакет ревью идёт в Claude Code и, по уровню риска, Codex CLI,
то есть наружу. Оба канала предусмотрены процессом независимого ревью.

Границы, за которыми решение перестаёт действовать:

- **личные данные покупателей** — имя, телефон, адрес, электронная
  почта. Сегодня их в ответах площадки нет: проверено на снятых
  фикстурах, максимум — город доставки. Появились — фикстура
  обезличивается перед коммитом, без обсуждения;
- **данные третьих лиц** — `legal_info.company_name` и `legal_info.inn`
  в ответе Ozon сегодня пусты, но существуют: первый же заказ
  от юридического лица положит в фикстуру контрагента, который своего
  согласия не давал. Тот же порядок — обезличить;
- **второй клиент в одном репозитории.** Данные первого лежат здесь
  потому, что он же и владелец продукта. Для чужой компании это
  перестаёт быть правдой в момент подключения.

**Обязательное покрытие:**
- денежная арифметика и аллокация расходов;
- идемпотентность каждого обработчика очереди;
- изоляция данных между компаниями.

CRUD, контроллеры, рендер — не тестировать.

**Запрет — на тесты ради самого контроллера, не на функциональный
уровень.** Оговорка нужна, потому что буквальное чтение («любой тест
через `KernelBrowser` запрещён») противоречит и обязательному покрытию
выше, и тому, как набор устроен с самого начала: изоляция арендаторов
проверяется только сквозь HTTP — обе проверки живут в подписчиках
`kernel.controller`, а не в контроллере, и вызвать их иначе нечем.
То же у идемпотентности приёма: повтор запроса — это и есть предмет
проверки.

Поэтому через HTTP проверяется: обязательное покрытие из списка выше;
разбор ввода на границе доверия (тело от клиента, чьи данные проверить
больше негде); намеренный сигнал наружу, который иначе пропадёт молча.
Не пишутся: тесты, проверяющие, что контроллер вернул то, что ему
передал сценарий; проверки кодов ответа ради самих кодов; рендер.

Признак, отделяющий одно от другого: **если тест удалить, узнаем ли мы
о поломке иначе.** Про утечку данных между компаниями — не узнаем.
Про то, что контроллер отдал 200 вместо 201, — узнаем от первого же
клиента, и это дёшево.

### 10. Тесты и проверки frontend

TypeScript `strict` со всеми флагами, включая `noUncheckedIndexedAccess`.
`any` запрещён на уровне ошибки линтера.

Типы ответов API импортируются только из сгенерированной схемы;
ручное описание типов ответов запрещено.

Сетевые запросы — только через клиент, привязанный к компании;
прямые вызовы `fetch` и `axios` запрещены. Исключение — точный
allow-list Identity-эндпоинтов, вызываемых до выбора компании:
`/api/auth/login`, `/api/auth/logout`, `/api/auth/me` по ADR-002 и
`/api/auth/sign-up`, `/api/auth/email-verification/resend`,
`/api/auth/email-verification/confirm` по ADR-021. Они идут через
`apiGet`/`apiPost` напрямую, не через `createCompanyApiClient`.
`fetch` вне `src/api/` по-прежнему запрещён — исключение про компанию,
не про точку входа.

**Правило написано про контур продавца и на системный контур
не распространяется** (`apps/admin`, ADR-017). Там компании нет ни у
одного запроса: раздел управляет сервисом целиком, и клиента, привязанного
к компании, не существует и не появится — весь `/api/admin/**` идёт через
`apiGet`/`apiPost` напрямую. Что при этом остаётся в силе дословно:
`fetch` вне `src/api/` запрещён, типы ответов — только из схемы, ключ
кэша — только через хелпер (`adminQueryKey`, форма
`['admin', <сущность>, ...параметры]`).

Признак, по которому решается вопрос для будущего третьего контура:
привязка к компании обязательна там, где ответ содержит данные одного
арендатора. Отсутствие `companyId` в пути — следствие, а не причина,
и само по себе исключением не является.

`localStorage` используется только для ключей из разрешённого списка.
Арифметика над денежными величинами в компонентах запрещена.

**Обязательное покрытие:**
- чистые функции форматирования и вычислений;
- изоляция кэша при смене компании;
- разбор ошибок API.

Тесты идут через мок-сервер, отвечающий по схеме OpenAPI: `msw`
с типизацией хендлеров по сгенерированной схеме (`openapi-msw`).
Подмена глобального `fetch` и `Response`, собранный руками, запрещены —
так тест успешно проходит на ответе, которого контракт не допускает.
Ответ, которого в схеме нет намеренно (HTML от прокси, пустое тело),
описывается сырым хендлером `msw` с пояснением, почему он не типизирован.

Один сквозной сценарий Playwright **на приложение**, и сценарии разные,
потому что разное и проверяют.

`apps/seller` — вход, выбор компании, просмотр данных, переключение
компании. Данных у компаний должно быть заведомо разное количество —
иначе переключение неотличимо от отданного кэша предыдущей.

`apps/admin` — вход, действие системного раздела, выход. Выбора
и переключения компании там нет по построению (ADR-017), и требовать их
означало бы требовать невыполнимого. Предмет проверки другой: что контур
закрыт до входа и что действие, доступное только верхней роли,
выполняется именно ею.

## Работа с данными маркетплейсов

Полностью — в ADR-006. Ключевое:

**Данные меняются задним числом.** Площадки перевыпускают отчёты,
доначисляют комиссии и возвраты через недели, иногда в пределах квартала.
Отсюда — немутируемый raw-слой, обновление факта вместо вставки второй
строки, скользящее окно пересчёта и периодический глубокий рескан.

**Битемпоральность.** Каждая факт-строка знает бизнес-дату (когда событие
произошло), время первой загрузки и время последнего обновления.

**Бизнес-дата — в часовом поясе площадки**, задаётся конфигурацией
коннектора, не выводится из данных.

**Прослеживаемость.** Каждая строка факта ссылается на raw-документ,
из которого получена её текущая версия.

**Объяснимость расчёта.** Клиент сверяет цифру с отчётом площадки.
Результат расчёта хранится с разложением по компонентам и с указанием
применённого метода учёта себестоимости и правила аллокации.

Лимиты запросов к API — на уровне подключения, не глобальные.

## Миграции и изменения схемы

Необратимо не создание миграции, а два других события: её применение
к данным, которые нельзя пересоздать, и её попадание в историю `master`.
Локальная база пересоздаётся командой `make down-clear`, поэтому применение
миграции в песочнице обратимо и остановки не требует.

**В песочнице разработки** (dev- и тестовая база этого `docker-compose`)
миграции создаются и применяются агентом свободно, без вопроса.
Человеческое ревью — на merge, не на применении.

**К моменту ревью:**

- в ветке одна миграция на задачу. Промежуточные итерации разработки
  («добавил колонку, передумал, переименовал») не коммитятся: база сносится,
  миграция генерируется заново одна и проверяется с нуля. История —
  артефакт, который поедет в прод, а не журнал отладки;
- `make db-rebuild-check` зелёный — полный цикл с пустой базы без кэшей;
- `down()` рабочий либо явная пометка «откат только восстановлением»;
- на таблицах фактов соблюдено правило совместимых изменений: сначала
  добавить новое, наполнить, переключить чтение, только потом удалить старое.

Изменение или удаление колонки одним шагом на таблице с миллионами строк
блокирует запись и останавливает продукт.

**Применение к боевым данным** выполняет агент, отдельным шагом после
выкладки и по её отказу на гейте `doctrine:migrations:up-to-date`
(«Периметр автономной работы»). Предусловия — зелёный `db-rebuild-check`,
рабочий `down()`, соблюдённое правило совместимых изменений; после
применения агент проверяет результат на проде.

**Автоматического применения внутри выкладки нет и не планируется.**
Гейт остаётся: он превращает миграцию в отдельное осознанное действие
с отдельным результатом, а не в шаг, который проезжает незамеченным
вместе с образом.

## Безопасность и аудит

Учётные данные площадок шифруются; мастер-ключ — в секретах окружения.
Подробнее — ADR-007.

Аудит-журнал обязателен для: изменения себестоимости, изменения планов,
добавления и изменения учётных данных подключений, входа администратора
в данные клиента.

Подключение имеет состояние `active` / `broken` / `revoked`.
Ответ площадки об отсутствии авторизации переводит в `broken`
и порождает уведомление клиенту. Молчаливая остановка синхронизации
запрещена.

## Наблюдаемость

Ошибки — в трекер. Отдельно от ошибок обязателен контроль свежести данных:
отсутствие новых загрузок по активному подключению дольше суток порождает
оповещение. Это не техническая метрика, а основное обещание продукта:
устаревшие данные выглядят как рабочие и не вызывают исключений.

**Меряется загрузка, а не факты.** У продавца бывает день без единого
заказа: фактов не появится, и «нет новых фактов» назвало бы исправную
синхронизацию сломанной. Тревога, которая иногда врёт, перестаёт читаться
через неделю — и это отказ контроля, а не его издержка. Признак живой
синхронизации — новый raw-документ: он приходит при любом объёме продаж,
потому что пустой ответ площадки тоже ответ и тоже доказывает, что связь
есть, ключи живы и воркер работает.

**Порог считается от того, как часто загрузка оставляет след**, а не
берётся круглым числом. Буквальные «сутки» ошибочны: raw-документ
дедуплицируется по содержимому (ADR-006), и на тихом подключении соседние
документы отстоят ровно на сутки — суточный порог отличался бы от этого
интервала на минуты, и любое смещение тика давало бы ложную тревогу.
Реализация берёт 36 часов (`NotifyStaleAccountsAction`).

**Контроль знает, что именно он сторожит.** Raw-слой общий для всех
выгрузок подключения, и оповещение обязано отбирать документы по типу
отчёта: иначе исправная соседняя синхронизация — например, каталога —
обновит отметку за вставшую синхронизацию продаж, и сторож промолчит
ровно тогда, когда должен кричать.

**Свежесть считается по каждой выгрузке отдельно**, а не одной отметкой
на подключение. У выгрузок общий тик, но не общая судьба, и наполовину
живое подключение — не редкость, а самый частый случай. Хуже того, он же
и самый тихий: вставшие расходы при живых продажах дают не пустой экран,
а рабочий, с маржой, завышенной на всю логистику и возвраты.

Что под контролем, записано явно и списком (`NotifyStaleAccountsAction`,
сегодня — продажи и расходы). Каталог в него не входит: вспомогательный
список для оверлея, отдельная тревога по нему пока не окупается.

В логах — идентификатор запроса и `company_id`. Обращение вида
«не сходится за 15 июля» должно превращаться в один запрос по логам.
Оба поля добавляет процессор ко всем записям сразу
(`Shared\Ui\RequestContextProcessor`): поле, которое надо не забыть
в каждом вызове, однажды забудут — и именно в той строке, ради которой
журнал открыли.

**Журнал и трекер — разные вещи, и обработчика Sentry в конфиге журнала
нет намеренно.** Трекер ловит ошибки; журнал пишет и то, что ошибкой
не является — ожидаемое доменное условие уровня `warning`. Отправлять
такое в трекер значит топить настоящие ошибки в шуме. Обратное тоже
верно: порог журнала в prod — `warning`, не `error`, иначе одиночное
предупреждение, за которым ошибки не следует, не попадёт в него никогда
(`config/packages/monolog.yaml`).

## Периметр автономной работы

Правило, которое агент читает, агент может истолковать в свою пользу —
особенно под конец длинной задачи, когда до зелёного остался один шаг.
Поэтому границы задаются окружением, а не списком разрешённых действий:
отсутствующий DSN истолковать нельзя.

- В контейнерах песочницы нет реквизитов staging и production — оттуда
  применить миграцию физически некуда. Доступ к боевому серверу — отдельный
  SSH-ключ вне репозитория и вне контейнеров, под алиасом `conwix-prod`
  в `~/.ssh/config`; именно через него применяется миграция к боевым данным.
- Реальных ключей кабинетов площадок в dev-окружении нет. Разработка
  коннектора идёт на зафиксированных фикстурах; живой запрос выполняет
  человек один раз, чтобы фикстуру получить. Ключи площадок в отдельных
  случаях дают право менять цены и остатки — это действие вне репозитория,
  и запрет на merge его не останавливает.
- `master` в песочнице не чекаутится, работа всегда в ветке задачи.
- Запрет прямого push и force-push в `master` — настройкой репозитория
  на стороне хостинга, а не git-хуком: хук лежит в репозитории,
  а репозиторий агент правит.
- `api/.env.local` в `.gitignore`, реальных значений в песочнице нет.

Публикация образа в ghcr идёт только с `master`, поэтому предусловия
merge (зелёный конвейер, пройденный порог ревью) одновременно являются
предусловиями выкладки. Второй предохранитель не нужен.

**Всё, что не выходит за границы песочницы и не попадает в `master`,
агент делает сам и не спрашивает.**

**Никогда автономно:** принудительная перезапись истории; обращение
к реальному кабинету площадки; коммит секретов и реальных ключей.

### Merge, миграции и доступ к серверу — разрешение постоянное

Раньше здесь стояло требование спрашивать разрешение на **каждый**
merge в `master` и на **каждое** применение миграции к боевым данным —
командой в текущем диалоге, а не общим согласием с прошлого повода.
Требование снято владельцем 15 августа 2026 после восьми задач, где
оно срабатывало по два-три раза за задачу и ни разу ничего не остановило.

Действует постоянное разрешение, спрашивать не нужно:

- **merge в `master`** своих PR;
- **применение миграций к боевым данным** и перезапуск выкладки;
- **доступ к боевому серверу** под алиасом `conwix-prod` — чтение
  состояния, диагностика, эксплуатационные команды приложения
  (`messenger:failed:retry`, добор данных, проверка свежести).

**Что разрешение не отменяет — предусловия.** Они не про согласие,
а про готовность изменения, и проверяются агентом самостоятельно:

- конвейер зелёный, порог внешнего ревью пройден, принятые замечания
  исправлены;
- у миграции рабочий `down()` либо явная пометка «откат только
  восстановлением», `make db-rebuild-check` зелёный, на факт-таблицах
  соблюдено правило совместимых изменений;
- после применения агент проверяет результат на проде и докладывает
  фактом, а не намерением.

**Остаётся запрещённым автономно, и разрешением выше не покрывается:**
принудительная перезапись истории; обращение к реальному кабинету
площадки (ключи площадок дают право менять цены и остатки — это
действие вне репозитория, и никакой запрет на merge его не остановит);
коммит секретов и реальных ключей; удаление или перезапись боевых
данных, которые нельзя восстановить из площадки или из резервной копии.

Последний пункт — единственный, ради которого стоит остановиться
и спросить: у него нет отката, а у merge и у миграции со `down()` он
есть.

## Процесс работы над задачей

Реализация — Codex или Claude Code. Независимое ревью через Claude Code
обязательно для каждого итогового изменения, включая конфигурацию и документацию.
Если реализует Claude, проверяет другая новая сессия Claude, без контекста автора.
Самопроверка и субагенты Codex обязательный проход Claude не заменяют.
Для рисковых изменений дополнительно выполняются два прохода Codex CLI с
разными ролями. Команды и параметры — `docs/review-package-template.md`.

Внешний ревьюер получает только явно приложенный контекст и может предложить то,
что здесь отвергнуто: API Platform, `findAll()`, Redux для серверного
состояния, Symfony Forms, глобальные фикстуры. Поэтому на ревью уходит
не только диф, а диф вместе с выдержкой правил и релевантными ADR,
и заранее задано правило принятия замечаний.

### Цикл работы

```
1. Разбор       — AGENTS.md, CLAUDE.md, релевантные ADR, docs/patterns.md
2. План         — что меняем, какие файлы, критерий готовности
3. STOP?        — если сработало условие остановки, спросить и ждать
4. Реализация   — код + тесты в одном изменении
5. Самопроверка — по чеклисту ниже
6. Внешнее ревью — всегда Claude; дополнительно Codex по уровню риска
7. Разбор замечаний — принять / отклонить с причиной
8. Повтор 4–7 до отсутствия принятых замечаний
9. Отчёт        — что сделано, что отклонено и почему, чем проверять
```

Задача не закрывается с невыполненным принятым замечанием.

### Когда остановиться и спросить

Останавливает **решение**, а не действие. Не писать код, а задать вопрос,
если задача требует:

- изменения схемы БД на таблицах фактов (партиционирование, ключи, индексы);
- нового межмодульного взаимодействия или Facade;
- новой внешней зависимости — установка пакета без согласования запрещена
  и на бэкенде, и на фронтенде;
- изменения конфигурации очереди, транспортов или маршрутизации сообщений;
- изменения контракта API, уже используемого фронтендом;
- обхода любого из правил выше;
- решения, которое противоречит принятому ADR;
- расширения объёма задачи за пределы поставленного.

Миграция под уже принятое решение поводом для остановки не является:
её создание и применение в песочнице обратимы (см. «Миграции и изменения
схемы»). Останавливает выбор состава ключа, партиционирования и индексов —
то есть решение, которое эта миграция исполняет.

Границы, которые не снимаются согласованием, — в «Периметре автономной
работы».

### Порог внешнего ревью

**Единица ревью — один предмет, а не одна задача.** Большой diff разбивается
на предметные пакеты. Их совокупность должна покрывать все изменения задачи,
включая новые файлы. Ревью выполняется перед закрытием задачи и merge, а не
после каждой отдельной правки.

| Что затронуто | Обязательное ревью |
|---|---|
| Миграции и схема данных | Claude + оба прохода Codex |
| Денежная арифметика, аллокация, округления | Claude + оба прохода Codex |
| Аутентификация, секреты, изоляция арендаторов | Claude + оба прохода Codex |
| Ingestion: идентификация фактов, идемпотентность, пересчёт | Claude + оба прохода Codex |
| Контракт API, остальные сценарии и обработчики | Claude |
| Конфигурация, стили, тексты, тесты, документация, правила агента | Claude |

При сомнении — высокий риск. `REVIEW_RISK=high` — безопасное значение по
умолчанию; `standard` выбирает автор, проверив, что рисковые области не затронуты.
Выбор уровня риска сознательно оставлен автору: по одному пути файла нельзя
надёжно определить влияние на деньги или изоляцию. Основание standard записывается
в CHECKS пакета; перед merge автор сверяет всю задачу с таблицей риска и составом
полученных ревью. Порог обязательного Claude агент самостоятельно не снижает. Дополнительный
проход нельзя считать независимым Claude, если его выполнил Codex.

| Прогон | Роль |
|---|---|
| Claude Code, 5C | критерии приёмки, соответствие правилам и реальные дефекты |
| Codex CLI, 5A | соответствие записанным правилам и ADR |
| Codex CLI, 5B | дефекты поведения, гонки, утечки и неверные результаты |

В отчёте фиксировать уникальные принятые замечания каждого дополнительного
прохода сверх предыдущих. Ответ модели — материал для разбора, не голосование
и не автоматическое разрешение на merge.

**Незавершённое ревью не считается проверкой.** Таймаут (потолок 900 секунд),
ошибка CLI или авторизации, пустой ответ, план вместо заключения, неверный хэш
пакета и status=incomplete означают отказ проверки. Успешного кода возврата
процесса недостаточно. Сократить предмет пакета и повторить; если Claude
остаётся недоступен, завершить независимую работу и явно сообщить о блокировке
ревью. Задачу не закрывать и merge не выполнять; молчаливой замены Claude нет.

### Пакет для ревьюера

Собирается `make review-prepare`; `make review` собирает и запускает ревью.
Оба используют явный `REVIEW_PATHS_FILE`: точные пути файлов задачи, по одному
на строку. Пакет включает изменения относительно проверенной базы, в том числе
закоммиченные, незакоммиченные, новые и удалённые файлы. Реальный git-index
не меняется. Чужие правки не включать; список пакета сверять с составом задачи.
Если свой и чужой код меняются в одном файле, сначала изолировать свою задачу
в отдельной рабочей копии: фильтрация выполняется по файлам, не по строкам.

База — merge-base с доступным origin/master или master. Автор проверяет
актуальность базовой ссылки; без базы нужен явный REVIEW_BASE. Автоматического
fallback на HEAD нет: он скрывал бы уже закоммиченные изменения.

Пакет содержит:

1. Предмет, критерии приёмки, выполненные проверки и их ограничения.
2. base, HEAD, точный список файлов, полный diff и SHA256 готового пакета.
3. Обязательные правила CLAUDE.md и AGENTS.md.
4. Релевантные ADR и дополнительный контекст из REVIEW_CONTEXT_FILE.
5. Одну инструкцию роли: 5A, 5B или 5C.
6. Формат законченного JSON-заключения, связанного с хэшем пакета.

ADR выбираются явно параметром ADR или по ссылкам в дифе; автор проверяет
полноту выбора. Отсутствие ссылок не доказывает, что ADR неприменимы.
Сгенерированные файлы можно не читать построчно только при явном перечислении
и успешной проверке их генерации. Нужный окружающий код прикладывает автор;
ревьюер не должен считать отсутствующий контекст проверенным.

Запросы, полные ответы, метаданные CLI и статусы сохраняются отдельными
прогонами в var/review. Предыдущие результаты не перезаписываются. Фактическая
модель берётся из метаданных CLI; если их нет, так и указывается. Локальные
артефакты не являются постоянным архивом — в отчёте нужны хэш, путь и сводка.

Перед запуском проверяется целостность и актуальность снимка. После исправлений
повторяются затронутые тесты и ревью изменённых частей с актуальным контекстом;
итоговая совокупность пакетов должна покрывать всё изменение. Все принятые
замечания должны быть устранены. status=complete означает получение заключения,
а не отсутствие дефектов или автоматическое принятие изменения.

Ревьюер не меняет файлы, не запускает тесты и сборки, не вызывает следующее ревью.
Прогон проверок — работа автора и CI. Секреты и запрещённые данные в пакет не
попадают; разрешённые фикстуры передаются в границах §9.

### Разбор замечаний

| Замечание | Действие |
|---|---|
| Указывает на нарушение записанного правила | принять, исправить |
| Указывает на реальный дефект — ошибка, гонка, утечка, N+1 | принять, исправить |
| Предлагает альтернативу, отвергнутую в ADR | отклонить со ссылкой на ADR |
| Вкусовое: стиль, именование, «я бы сделал иначе» | отклонить с одной строкой причины |
| Указывает на пробел в самих правилах | не исправлять код молча — вынести отдельно |

Самоклассификация ревьюера — подсказка, а не приговор: метка проверяется,
не принимается на веру.

Расхождение между ревьюерами разрешается соответствием ADR, а не
большинством голосов: два инструмента — не голосование, их ценность в том,
что они ошибаются по-разному. Замечание о пробеле в правилах ценнее
найденной опечатки — оно чинит не одно изменение, а все будущие; такие
случаи превращаются в правку `docs/patterns.md` или новый ADR.

### Финальная самопроверка

Порядок фиксированный, первый пункт всегда первый.

```
1.  Каждый метод репозитория принимает companyId; поиска по одному id нет
2.  Ключ кэша на фронтенде содержит companyId
3.  Списки читаются через DBAL, сущности для отображения не гидрируются
4.  Ни один список не отдаётся без ограничения количества
5.  Деньги — Money с валютой; float в денежных вычислениях нет
6.  Обработчик очереди идемпотентен через уникальный индекс,
    конструкции «найти, и если нет — записать» нет
7.  Новое поле-ссылка получило индекс в той же миграции
8.  Запросов в цикле нет
9.  Тесты написаны в том же изменении; обязательное покрытие соблюдено
10. Границы модулей не нарушены — Deptrac зелёный
11. Отладочный вывод, закомментированный код, TODO без задачи — отсутствуют
12. Документация обновлена: structure.md при изменении структуры,
    patterns.md при изменении паттерна или зависимости
13. Миграция в ветке одна; make db-rebuild-check зелёный
14. В диф не попали секреты, реальные ключи площадок, .env.local
```

Красный пункт означает, что задача не закончена: исправить и пройти
чеклист заново, а не отметить и объяснить.

### Отчёт по задаче

```
Задача:    одно предложение
Сделано:   список изменений по существу
Файлы:     затронутые пути
Ревью:     кто ревьюил, сколько замечаний принято,
           хэш пакета и путь к ответу; уникальные принятые замечания
           каждого дополнительного прохода; незавершённые прогоны отдельно
Отклонено: замечание → причина
Проверка:  команды, которыми ревьюер может убедиться
Открыто:   что осталось и почему
```

**Не входит в процесс:** этапный конвейер с гейтами выкладки (оправдан
на большой команде с владельцем, который неделями не смотрит в код; здесь —
церемония); внешнее ревью как блокирующая проверка в CI (ответ модели
недетерминирован, ставить на нём гейт сборки нельзя); автоматическое
применение замечаний без разбора.

## Принципы

**Скучные технологии.** Меньше компонентов, шире распространённость,
больше примеров. Экзотика — это выдуманные API при генерации и
отсутствие ответов при отладке.

**Не абстрагировать до второго случая.** Абстракция коннектора площадки
пишется после второго коннектора, не до первого.

**Тонкая полоска насквозь.** Новая функциональность доводится до экрана
на одном узком случае, потом расширяется вширь.

**Обратимость важнее оптимальности.** Для необратимых решений (схема БД,
модель арендатора, идентификаторы, деньги) — думать долго и записывать ADR.
Для обратимых — делать и переделывать.

## Документация: что где лежит

| Файл | Что содержит | Изменяемость |
|---|---|---|
| `CLAUDE.md` | правила и ссылки, точка входа для агента | по мере накопления правил |
| `docs/adr/` | необратимые решения с альтернативами и издержками | принятый ADR не редактируется |
| `docs/structure.md` | карта репозитория, назначение папок | живой документ |
| `docs/patterns.md` | используемые и отвергнутые паттерны, библиотеки | живой документ |

| `docs/review-package-template.md` | шаблон пакета для внешнего ревью | живой документ |

**Правило отнесения.** Решение необратимо или дорого отменяемо
(схема данных, границы модулей, контракт API, технология, которую нельзя
убрать за день) — ADR. Решение о том, как мы пишем код сегодня, —
`patterns.md`. Где лежит файл — `structure.md`. Всё, что нужно агенту
в каждой задаче, — `CLAUDE.md`.

При изменении структуры папок обновляется `structure.md` в том же коммите.
При отказе от паттерна или добавлении библиотеки — `patterns.md`
в том же коммите.

## Команды

Вход — `Makefile` в корне репозитория; `make` без аргументов печатает
этот же список с описаниями. Makefile отвечает только за Docker
и оркестрацию; внутри контейнера всё выполняют composer- и npm-скрипты
(`api/composer.json`, `apps/*/package.json`) — Makefile их вызывает,
а не повторяет. Все фронтендовые команды идут через контейнеры
`node-seller` / `node-admin`, никогда через хост (`docs/patterns.md`,
«Node-окружение»).
