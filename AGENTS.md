# AGENTS.md

Правила работы агента в Conwix — SaaS-аналитике маркетплейсов.

## Контекст и источники правил

- Перед работой прочитать этот файл и `CLAUDE.md`, затем `docs/patterns.md`,
  `docs/structure.md` и ADR, относящиеся к задаче.
- Архитектурные и предметные правила остаются в существующих документах;
  этот файл задаёт рабочий процесс и кратко напоминает ключевые ограничения.
- Процесс ревью определён ниже и в `CLAUDE.md` → «Процесс работы над задачей».
  Команды и формат пакета — `docs/review-package-template.md`. Требования
  согласованы: Claude обязателен всегда, дополнительные проходы Codex — по риску.
- Расхождение документации и кода фиксировать явно. Существующий код сам по себе
  не отменяет правило; пробел или конфликт правил не исправлять молчаливым обходом.

## Работа над задачей

- Общаться на русском. Сначала определить результат, затронутые области и проверки.
- Проверить ветку, `git status` и исходный diff. Сохранять чужие изменения;
  не включать их в коммит и пакет ревью своей задачи без явного основания.
- Работать в ветке задачи. Делать минимальное законченное изменение;
  не добавлять попутный рефакторинг, зависимости и абстракции вне задачи.
- Принятые в задаче решения выполнять самостоятельно. Согласование уже принятого
  решения не запрашивать повторно. Для новых решений соблюдать условия остановки
  из `CLAUDE.md`; не считать создание миграции самостоятельным поводом для остановки.
- PHP, Composer, Node и npm запускать через контейнеры и существующие цели Makefile.
  `make init`, `make down-clear` и `make db-rebuild-check` удаляют локальные тома:
  перед запуском самостоятельно убедиться, что цель — локальное dev/test-окружение.
  Повторное разрешение владельца для этой проверки не требуется.
- Не ослаблять линтеры, Deptrac, тесты и пустой PHPStan baseline ради зелёного результата.

## Архитектура и данные

- Backend: PHP 8.4, Symfony 7.4, Doctrine, PostgreSQL. Модули:
  `Shared`, `Identity`, `Ingestion`, `PriceMonitoring`, `Links`.
- Соблюдать слои `Domain`, `Application`, `Infrastructure`, `Ui` и зависимости
  из Deptrac. Межмодульный доступ — через разрешённые Facade; новые связи требуют ADR.
- Чтения данных компании явно принимают `companyId`; company-scoped методы
  репозиториев — первым параметром. Межарендаторные исключения допустимы только
  по `CLAUDE.md` §1, с точными границами Deptrac. Членство не заменяет проверку
  области действия токена расширения или прав системного администратора.
- UUIDv7 генерировать в приложении, хранить нативным PostgreSQL `uuid`.
- Деньги — `Money`, целые минорные единицы и обязательная валюта.
  `float` запрещён и в промежуточных денежных расчётах; округление задавать явно.
- Списки — DBAL/SQL, нужные колонки, readonly DTO, обязательный лимит;
  растущие таблицы — keyset-пагинация. Не гидрировать Entity для списков,
  не выполнять запросы в цикле и `COUNT(*)` по факт-таблицам.
- Человеческие изменения писать через ORM, факты — через DBAL по правилам
  естественного ключа и upsert. Entity для описания схемы обязательны и у фактов.
- Обработчики очереди должны выдерживать повтор и конкуренцию. Защита от дублей —
  ограничение БД и корректная обработка конфликта, не предварительная проверка.
  Конкретные гарантии внешних побочных эффектов проверять по соответствующему ADR.
- Миграции: одна итоговая миграция на задачу, проверка с пустой базы,
  рабочий `down()` либо явно описанное восстановление; для фактов — совместимые изменения.

## Frontend и контракт

- `apps/seller`, `apps/admin`, `apps/extension` — разные контуры.
  Не переносить исключения одного контура на другой.
- TypeScript strict, без `any`. Ответы API типизировать из `packages/api-schema`.
  Сгенерированные OpenAPI и TS-типы не исправлять вручную:
  менять источник, выполнять `make api-doc-export api-types`, проверять `make api-types-check`.
- Данные компании запрашивать через `createCompanyApiClient`, ключи кэша —
  через `companyQueryKey`. Для admin — системный клиент и `adminQueryKey`;
  pre-auth и extension соблюдать по собственным правилам и ADR.
  Прямой `fetch` вне разрешённого API-слоя запрещён.
- Серверное состояние — TanStack Query. Денежную арифметику не помещать в компоненты.
- Использовать примитивы и токены `packages/ui` и действующую дизайн-систему;
  не дублировать общие компоненты и не вводить произвольные стили в обход токенов.

## Проверки

- Тестировать риск и поведение: изоляцию компаний и кэша, права и границы доверия,
  деньги, идемпотентность, ошибки API. Не писать тесты, повторяющие реализацию.
- Backend: unit/integration/functional по зависимостям, данные через Builder.
  Внешние API в тестах не вызывать. Frontend: Vitest и типизированный MSW,
  без подмены глобального fetch. Playwright — сценарии seller и admin.
- Для backend: `make lint stan deptrac structure-check` и затронутые тесты
  (`make test-unit`, `make test-int`, `make test-func`; последние требуют готовой тестовой БД).
- Для frontend: `make front-typecheck front-lint front-knip front-test front-build APP=seller`
  с нужным APP; для общего UI проверять всех потребителей, включая popup расширения.
- Для схемы БД: `make db-rebuild-check`. Для API: `make api-types-check`.
  Также выполнять `make audit` и `make test-e2e` в подготовленном окружении.
  Перед merge все обязательные CI-проверки должны пройти;
  `make ci-local` — существующий сводный локальный прогон.
- Записывать выполненные команды и результаты. Недоступная или незапущенная
  проверка не считается успешной; её ограничение отражать в отчёте.

## Обязательное независимое ревью через Claude

- Команды: `make review` собирает пакет и запускает Claude; `make review-claude`
  проверяет уже подготовленный пакет. Обязательны TASK, CRITERIA, CHECKS и
  REVIEW_PATHS_FILE (точные файлы задачи, по одному на строку). REVIEW_RISK=high
  по умолчанию добавляет оба прохода Codex; standard допустим только вне рисковых областей.
- Каждое изменение, включая документацию, конфигурацию, тесты и этот файл,
  до закрытия задачи и merge проходит ревью в отдельной новой сессии Claude Code.
  Это правило действует на итоговый набор изменений задачи, не на каждую итерацию редактирования.
- Новая сессия не наследует разговор автора и не читает инструкции из рабочей копии.
  Глобальная конфигурация и штатная авторизация CLI на хосте сохраняются;
  полная изоляция от пользовательских настроек хоста этим процессом не гарантируется.
- Самопроверка автора, Codex и его субагенты не заменяют Claude.
  Если автор — Claude, ревью выполняет другая сессия Claude с отдельным контекстом;
  обязательные дополнительные проходы Codex для рисковых изменений сохраняются.
- Для схемы/миграций, денег, аутентификации/секретов/изоляции и критической логики
  Ingestion сохраняются оба прохода Codex: соответствие правилам и поиск дефектов.
  Claude обязателен дополнительно. Для остальных изменений обязателен минимум Claude.
- Ревьюер получает задачу и критерии приёмки, полный diff задачи, необходимый
  окружающий код, релевантные правила и ADR, перечень выполненных проверок.
  Рецензирует соответствие правилам и реальные дефекты, не правит файлы и не запускает сборки.
- Зафиксировать базовый commit, HEAD, список файлов и хэш пакета с полным diff,
  включая новые файлы задачи. Проверить, что пакет не содержит чужие изменения.
  Сверить список файлов пакета со списком файлов задачи; при расхождении пересобрать.
  Отсутствие достоверной базы или неполный diff означает неполное ревью.
- Большой diff разбить по предметам; совокупность пакетов обязана покрывать всю задачу.
  Сгенерированные файлы можно не читать построчно, если проверена их генерация
  и они явно перечислены в пакете. Секреты, персональные данные и данные чужих
  клиентов не передавать; для разрешённых фикстур соблюдать `CLAUDE.md` §9.
- Сохранять запрос и полный ответ в `var/review/` с идентификатором пакета,
  временем, фактической моделью из метаданных CLI и статусом завершения;
  если CLI не сообщает модель, указать это явно, не полагаться на самоописание модели.
  Текущий адаптер разбирает modelUsage Claude; для Codex сохраняет сырой вывод
  и явно отмечает, что модель не извлекалась. При разборе Codex сверить её
  по сохранённому выводу CLI, если он содержит эти сведения.
  Не затирать предыдущие прогоны. В итоговый отчёт включать сводку: `var/review/`
  является локальным рабочим каталогом, а не гарантированным постоянным архивом.
- Каждое замечание разобрать: принято и исправлено / отклонено с доказательством
  или ссылкой на ADR / отдельный пробел в правилах. Метка ревьюера не заменяет проверку.
- После исправлений повторить затронутые проверки и ревью изменившихся частей,
  передав обновлённый контекст. В итоге все изменения должны быть покрыты актуальным ревью,
  все принятые замечания устранены. Замечания вне задачи не исправлять попутно;
  явно указать, почему они не блокируют результат, либо признать задачу незавершённой.
- Таймаут, ошибка авторизации, пустой или недочитанный ответ — ревью не пройдено.
  Успешный код возврата CLI без содержательного заключения также не считается ревью.
  Уменьшить пакет и повторить; при сохраняющейся недоступности закончить независимую
  работу и сообщить о блокировке ревью. Не объявлять задачу завершённой и не выполнять merge.
  Не заменять Claude другим инструментом без явного изменения требования владельцем.

## Готовность и отчёт

- Задача завершена, когда выполнены критерии приёмки, пройдены обязательные проверки
  и независимое ревью, устранены принятые замечания, актуализированы контракт и документы.
- Отчёт: что изменено; чем проверено; кто ревьюил и где ответ; принятые и отклонённые
  замечания; оставшиеся ограничения. При нескольких проходах указать количество
  уникальных принятых замечаний каждого дополнительного прохода сверх предыдущих.
  Не заявлять успешную проверку без её результата.
- Merge, production-операции и миграции выполнять в рамках действующего разрешения
  и предусловий из `CLAUDE.md`. Этот файл не расширяет периметр разрешений.
